# The demo, 2026-10-26: the local cell, from web/

Lane DR, from the cell runs on main through 2026-10-26; audited against main by lane D1 at 20:50 UTC. Everything runs on the
local cell with paper, fixture brokers and recorded data only: no live credential, no real order
(`AGENTS.md` rule 8). The cell's own report (`cargo xtask cell demo --scenario demo`) is the
up-to-date list; this page says what to run, what you will see, and what is not yet real.

**Rehearse at 13:35Z, demo after it is green.** Lane DR runs the whole cell demo at 13:35 UTC on
Tuesday 2026-10-27, five minutes after the window opens, and reports its first stop; the founder's
demo follows once that rehearsal is green, later in the same window. Nothing about the loop can be
proved outside the window, so the rehearsal is where a failure is found and fixed, not the demo.
The in-session path has a test of its own that does not wait for the window:
`mandate-daemon`'s `the_demo_envelope_decides_asks_and_proposes_once_granted_in_session` runs the
deployed runtime's wiring over this envelope at a Tuesday-session clock and proves decide, ask,
grant and the proposal to the executor.

**The trade loop's window: Tuesday 2026-10-27, 13:30 to 20:00 UTC** (9:30 to 16:00 in New York).
The crossover decides only on a fresh output, and its output from a daily close stays fresh for
one day; openings trade only in the regular session. Tuesday's session is the first in which both
hold: Monday's close, the day before, is still fresh, and the market is open ("When the trade loop
can run" below). Outside the window the demo shows steps 1 to 3, 5 and 7, and step 4 up to the
model: each agent's stream holds its `ObservationRecorded` and its `ModelOutputRecorded`, whose
`expires_at` is already past, and no `DecisionMade` follows, since the runtime decides on no stale
output. The runtime records no separate "stale" event; the expired `expires_at` is the reason.

## Bring it up

On x86_64 Linux with docker, `kubectl`, and the tools `bash .cursor/install.sh` installs (k3d, helm,
kubeconform), plus Node.js at `web/.nvmrc` and `npm ci` in `web/` for the browser part. The scenario
refuses to start without `kubectl` (#2699). Keep
ample disk free: in lane DR's sandbox runs on 2026-10-26, the kubelet evicted the cell's pods for
disk pressure with about 13.5 GB free (an observation of that machine, not a documented limit).

```bash
cargo xtask cell up                        # build the images, start k3d, install the journal, vault and workspace
cargo xtask cell demo --scenario demo      # the story's steps in the cell, web/ driven headless by Playwright
cargo xtask cell down                      # when done
```

- Behind a TLS-inspecting proxy, set `MANDATE_CELL_CA_BUNDLE` to the proxy's CA bundle first.
- On a sandboxed VM that refuses a negative `oom_score_adj`, set `MANDATE_CELL_RESTRICT_OOM=1`
  before the cluster is created.
- In a Claude Code cloud session, lanes DR and IAC needed all of this on 2026-10-26:
  - Start the Docker daemon first (`nohup dockerd &`, then wait for `docker info`). Without it
    `ci cell-demo` skips and still exits 0, unless `MANDATE_CELL_REQUIRED` is set.
  - Set `MANDATE_CELL_CA_BUNDLE=/root/.ccr/ca-bundle.crt` (the session's proxy CA),
    `MANDATE_CELL_RESTRICT_OOM=1` and `MANDATE_CELL_LOW_EVICTION=1` before the cluster is created,
    or CloudNativePG never starts. Run `cargo xtask cell down` first if a cluster exists.
  - `CARGO_INCREMENTAL=0` saves disk for the image builds. It no longer harms `cargo xtask ci
    mutants`, which builds with it on (#2680).
  - Keep 16 GB or more free (#2745 adds a 2 GiB `research-artifacts` volume). If disk runs low during a run, prune docker images; never delete
    `target/cell-static`, whose binaries the cell's image tags are computed from throughout the run.
- To see step 3's news part (the monitor run, the thesis invalidated, and the thesis exit's order
  and fill), set `MANDATE_CELL_LOOP_WAIT_S=1000` before `cell demo`. The recorded news item arrives
  900 seconds after the research agent is deployed, and without the variable each research link is
  read for 60 seconds only, so those links read `not reached`. The wait is per link, and the loop
  stops reading at the first link not seen, so a broken run costs at most one wait.
- Before `--scenario demo`, run `npm ci` in `web/` and install Playwright's Chromium
  (`npx playwright install chromium`, from `cdn.playwright.dev`): the scenario installs neither, and
  without them its `web/` steps read `not run`.
- The scenario leaves nothing served when it ends: its report says what each step did, and the
  cell stays up until `cell down`. Plain `cargo xtask cell demo` (no `--scenario`) keeps `web/` up in
  the foreground (Ctrl-C stops it), but it serves the chart's fixed demo workspace, not the
  scenario's run workspace; there is no documented way yet to watch the run's workspace live.
- `cargo xtask ci cell-demo` is the same scenario without the browser, as CI runs it; CI's
  `cell-demo-web` job runs it with the browser required (`MANDATE_DEMO_WEB_REQUIRED`).
- `cell demo` forwards the API to http://127.0.0.1:8787 and the stub sign-in issuer to
  127.0.0.1:8090, and signs `web/` in as the demo owner (`demo-owner`).

## When the trade loop can run

The crossover reads daily closes, and an output is fresh for at most one day (its horizon is the
pinned `max_output_age_s`, which the mandate schema caps at 86400; mandate spec §8.2). Openings
trade only in the regular session. So the runtime can decide and the order can fill only in a
regular session whose previous trading day closed within the last 24 hours: not on a Monday, whose
latest close is Friday's and already stale, nor on the day after a market holiday. While the US is
on daylight time, until 2026-11-01, that is 13:30 to 20:00 UTC, Tuesday to Friday; from then, 14:30
to 21:00 UTC; an early close shortens it.

The demo takes the conservative reading and shows the trade loop in such a session, tomorrow's.
Reading freshness in trading sessions instead would loosen a freshness rule, which only the founder
can decide (DEC-79).

## If something goes wrong

- **If the agent shows "Selling only" (`exits_only`) with the alert "The account did not
  reconcile"** (`OwnerAlertSent` of kind `reconciliation`, every agent on the account held under
  `reconciliation:incomplete`): the executor held the account's openings because the journal
  refused one of its batches (DEC-2805), it met a broker answer its core could not apply
  (DEC-2821), or a reconciliation run was incomplete (DEC-140). Exits, protective orders and the
  kill switch still run. The owner lifts the hold with an acknowledgment naming it (journal spec
  v0.104, DEC-2830; E7-4b, lane L1: #2723, #2727, #2734, #2739):
  1. Find the hold's record: the `event_id` of the `AgentModeApplied` on the account stream that
     applied it (`to` `exits_only` or `paused`, `restriction` beginning `reconciliation:`). An
     `incomplete` hold names every agent (`agent` `*`), so `mandate agent status <agent>`, which
     lists only the agent's own records, shows neither it nor its id. In the cell, read it from
     the journal:

     ```sh
     kubectl -n ws-<workspace> exec journal-1 -c postgres -- psql -U postgres -d mandate -At -c \
       "select event_id, p->>'agent', p->>'restriction', p->>'to' from (select event_id, recorded_at,
          convert_from(body, 'UTF8')::json->'payload' as p from journal.events
          where event_type = 'AgentModeApplied') e
        where p->>'restriction' like 'reconciliation:%' order by recorded_at"
     ```

     Each line is one record. A hold is its agent and restriction together: the one to acknowledge
     is the last line, `exits_only` or `paused`, with no later `normal` line for the same agent and
     restriction.

  2. `mandate agent acknowledge <agent> <that event_id> --subject reconciliation`, with any agent
     of the account, shows a code and commits nothing; run it again with `--code <code>` to record
     it.
  3. The executor checks the copy and lifts the hold it names: the next record on the account
     stream is an `AgentModeApplied` back to `normal` for that restriction (the same query's last
     line then reads `normal`), and openings are submitted again unless another restriction, a kill
     switch or an owner's pause, still holds the agent. A hold applied again after the
     acknowledgment needs a new one (`trigger_superseded`).

  **On `main`, not yet seen in a cell.** If the hold does not lift, the recovery is a fresh cell:
  `cargo xtask cell down`, `cargo xtask cell up`, then the scenario again on the new, empty journal.
- **If `cell demo` stops with "stop it with `pkill -f 'port-forward deployment/api'`"**, an earlier
  forward holds port 8787: run that, then `cell demo` again.
