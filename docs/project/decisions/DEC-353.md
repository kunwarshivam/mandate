## Decision

1. §9.2's autonomy row compares the two versions with `delegations` removed, and reads the new
   version's delegations for the rules and default they lift. Two of its reducing changes become
   increasing when an order that reached an undelegated ask could reach an ask a delegation lifts:
   - widening a single-comparison `ask` rule that a delegation of the new version lifts;
   - removing a rule whose `then` is not `auto` when a delegation of the new version lifts a later
     rule or the default.
2. Three changes stay reducing even when their orders land on an ask a delegation lifts:
   - removing an `auto` rule;
   - narrowing a single-comparison `auto` rule;
   - a kept rule's `then` going from `auto` to `ask`.

   The orders they move were `auto` and stay `auto`. A delegation now decides them and spends its
   budget on them, and once it is suspended or spent they are `ask`, which is stricter.

   The third shape cannot arise between two valid versions. V-041 refuses a delegation naming a rule
   that is not an `ask`, so the old version cannot carry one on the rule while its `then` is `auto`.
   A delegation added in the new version makes the delegations row increasing. So it has no MC-J
   case; the fuzz reaches it only through versions V-041 refuses.
3. MI-29 is reworded to the strictness it stood for, the delegation half of MI-11. A version
   classified risk-reducing or neutral never makes any decision less strict than the previous
   version made it, with each version's delegations in force, for the same action at the same time,
   usage and suspension state. An order `auto` by a rule may become `auto` by a delegation. Before,
   MI-29 said a reducing version "never lets a delegation lift a decision the previous version's
   delegations would not have lifted", and the three changes in item 2 break that wording.
4. V-042 keeps its basis, the delegations removed from both versions. A version that is increasing
   only because of what its own delegations lift is reducing on that basis, so it carries them over.
   Dropping them would be circular: they are what made the version increasing, and it needs step-up
   regardless.
5. The rule reads the rules, not the orders. It also calls some changes increasing that move no
   order, for example when a delegation's caps or `when` exclude every order the change moves, or
   when an earlier rule shadows the rule the change touches. That errs toward step-up, never toward
   authority.

   One bullet of the row carries no delegation condition and needs none only because of V-041: a
   rule added whose `then` is at least as strict as every later rule and the default. V-041 refuses
   a delegation naming a rule the version does not have, so no carried delegation can name the
   added rule. A delegation added with it makes the delegations row increasing. If V-041 ever let a
   delegation name a rule its version lacks, adding that rule as an `ask` would move orders from an
   undelegated ask onto the delegation, the #444 defect. `fuzz_delegated_rule_changes` therefore
   asserts, as a negative control, that V-041 refuses both versions this item and item 2 rely on.
6. The reference model takes the rule (`classify_autonomy`'s `lifted`). `fuzz_delegated_rule_changes`
   asserts MI-29 as worded here, comparing decisions only. Some of its versions name a source that is
   not an ask. Some of its changes widen the rule a delegation names, make its source an ask, or
   remove a rule ahead of it. Some narrow the delegations in the same version. `mutants.py` asserts
   its shared probe is clean on the unmutated model before any mutation. MC-J01 to MC-J10 pin each
   shape, each with a control that has no delegation.

## Rationale

§9.2 classified rule changes with the delegations removed and delegation changes on their own, so a
change neither row saw as widening could move orders from an undelegated ask to a delegated one:
`fuzz_review_changes` found it with seed 1 (#444). That also left `mutants.py`'s shared probe failing
on the unmutated model, so every one of its 122 mutants scored caught whatever it did.

The founder chose strictness over the literal text, because the three changes in item 2 move no
order toward more authority, and calling them increasing would put step-up on owners who are
tightening.

## Alternatives considered

- **Keep MI-29's text and tighten §9.2 to match it.** This was round 2's draft, and the founder did
  not take it. Under it, removing or narrowing an `auto` rule, or making a rule or the default an
  `ask`, would be increasing whenever a delegation lifts where the orders land. It costs step-up, as
  measured on two enumerations:
  - **The independent review of round 1.** Its enumeration covered every ordered pair of small
    autonomy configurations and every V-041-valid delegation list. Of the changes §9.2 called
    reducing before this decision, the rule of item 1 makes 3,388 increasing:
    - 1,134 decide an order less strictly (#444);
    - 1,152 have a delegation lifting a decision it did not lift before, with the decision unchanged;
    - 1,102 move no order.
  - **The author's enumeration**, which used rules over two ids, `gt` and `lte`, two values and all
    three verdicts, and delegations with no caps or `when`. It compared the readings:
    - Item 1 makes 1,976 pairs increasing: 680, 552 and 744 in the same three groups.
    - The tightened reading would add 1,268 more: 768 where a delegation lifts an order a rule
      decided `auto`, and 500 where no order moves.
    - Of the 34,060 changes the tightened reading called reducing, none decided less strictly.
- **Any rule change while delegations exist is increasing:** the simplest rule, but every tightening
  of a rule would need step-up while a delegation stands.
- **Move V-042 to the new basis**, so a version made increasing by its own delegations drops them.
  This would be a tightening, and it terminates, since re-created delegations are new and the
  delegations row calls them increasing anyway. Not taken: the version already needs step-up, and
  the owner would re-create the same delegations with no gain in protection.
- **Fix the fuzz seed:** this hides a real MI-11 violation.
