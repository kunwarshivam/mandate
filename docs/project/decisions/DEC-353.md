# DEC-353: A rule change that can send an order to a delegated ask is risk-increasing

| | |
|---|---|
| **Status** | Accepted; the founder question below is Proposed |
| **Date** | 2026-10-02 (UTC) |
| **Decided by** | The stream H builder (agent), under DEC-79 and DEC-176: it only tightens a classification. Round 1 of [#471](https://github.com/kunwarshivam/mandate/pull/471), ruled by the coordinator, took the stricter of the two readings it found |
| **Story or claim** | [#444](https://github.com/kunwarshivam/mandate/issues/444), from E6-13's review ([#443](https://github.com/kunwarshivam/mandate/pull/443)); claim [#439](https://github.com/kunwarshivam/mandate/issues/439); mandate spec §9.2, MI-11, MI-29, V-042 |

## Decision

1. §9.2's autonomy row compares the two versions with `delegations` removed, and reads the new
   version's delegations for the rules and default they lift. A change it would otherwise call
   reducing is increasing when, after it, a delegation of the new version could lift a decision no
   delegation lifted before. That is any of:
   - widening a single-comparison `ask` rule that a delegation of the new version lifts;
   - removing a rule, whatever its `then`, when a delegation of the new version lifts a later rule or
     the default;
   - narrowing a single-comparison `auto` rule when a delegation of the new version lifts a later
     rule or the default;
   - making a rule or the default `ask` when a delegation of the new version lifts it. V-041 already
     keeps a valid version's delegation off a source that is not an ask, so this only matters for a
     version V-041 would refuse; it is there so that the rule does not depend on V-041.
2. MI-29's text does not change. Round 1's draft kept "removing an `auto` rule" reducing, because
   its orders were already `auto`. But the orders can land on a delegated ask, and a delegation then
   lifts a decision it did not lift before, which MI-29 as written forbids (MC-J06 measured it). The
   same is true of narrowing an `auto` rule. Rewording MI-29 to fit would narrow what a safety
   invariant promises, which DEC-79 reserves for the founder, so the rule is tightened instead.
3. V-042 keeps its basis, the delegations removed from both versions. A version that is increasing
   only because of what its own delegations lift is reducing on that basis, so it carries them over.
   Dropping them would be circular: they are what made the version increasing, and it needs step-up
   regardless.
4. The rule reads the rules, not the orders. It also calls some changes increasing that move no
   order, for example when a delegation's caps or `when` exclude every order the change moves, or
   when the rule a change moves orders past is shadowed by an earlier one. That errs toward step-up,
   never toward authority.
5. The reference model takes the rule (`classify_autonomy`'s `lifted`). `fuzz_delegated_rule_changes`
   asserts MI-11 (no reducing rule change decides less strictly) and MI-29 as written (no reducing
   rule change decides by a delegation an order no delegation decided before). It compares decisions
   only. Its draws include delegations that name a source that is not an ask. `mutants.py` asserts
   its shared probe is clean on the unmutated model before any mutation, and seeds one bug per
   condition. MC-J01 to MC-J10 pin each shape with a control that has no delegation.

## Rationale

§9.2 classified rule changes with the delegations removed and delegation changes on their own, so a
change neither row saw as widening could move orders from an undelegated ask to a delegated one:
`fuzz_review_changes` found it with seed 1 (#444). That also left `mutants.py`'s shared probe failing
on the unmutated model, so every one of its 122 mutants scored caught whatever it did.

## Alternatives considered

- Any rule change while delegations exist is increasing: the simplest rule, but every tightening of
  a rule would need step-up while a delegation stands.
- Keep removing or narrowing an `auto` rule reducing, and reword MI-29 to its stated purpose (the
  delegation half of MI-11): this is the founder question below. Not taken, because it narrows a
  safety invariant.
- Move V-042 to the new basis, so a version made increasing by its own delegations drops them: a
  tightening, and it terminates, since re-created delegations are new and the delegations row calls
  them increasing anyway. Not taken: the version already needs step-up, and the owner would
  re-create the same delegations with no gain in protection.
- Fix the fuzz seed: it hides a real MI-29 violation.

## Founder question (Proposed)

Should MI-29 be reworded to its stated purpose, so that removing or narrowing an `auto` rule ahead
of a delegated ask is reducing again? The orders it moves were `auto` and stay `auto`; a delegation
now decides them, spends its budget on them, and leaves them `ask` once it is suspended or spent.
Until the founder answers, the tightened rule stands.

What each reading costs in step-up, measured over every ordered pair of small autonomy
configurations: rules over two ids, `gt` and `lte`, two values and all three verdicts, 0 to 2 rules,
every default; the same delegations in both versions, each lifting an ask source of both, with no
caps or `when`; orders of 100, 200, 400, 600 and 800 USD.
- Of the pairs §9.2 called reducing before DEC-353, round 1's reading makes 1,976 increasing: 680
  where an order is decided less strictly (#444), 552 where a delegation lifts a decision it did not
  lift before, and 744 where no order moves.
- The tightened reading makes 1,268 more increasing: 768 where a delegation lifts an order a rule
  decided `auto`, and 500 where no order moves.
- Of the 34,060 changes the tightened reading calls reducing, none decides less strictly and none
  lets a delegation lift a decision no delegation lifted before. Round 1's reading had 852 of the
  second.

The independent review of round 1 measured round 1's reading the same way over a wider enumeration.
Of the 3,388 pairs it newly calls increasing, 1,134 decide less strictly, 1,152 have a delegation
lifting what it did not lift before, and 1,102 move no order.
