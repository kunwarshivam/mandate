## Context

The founder allowed `cli_confirm` for a paper grant made in the web app (DEC-2605 row 5), and
DEC-2103 item 7 bounds it: an `approve` only, in a paper workspace, against a challenge this server
issued for the same principal, workspace, and action, within its 300 s, once, and confirmed in the
CLI, never in the browser session that asked. It left open how the CLI's confirmation reaches the
server. The CLI has no API session: it appends to the control stream on the host, as `mandate
approvals approve` does, and its `--user` is the owner's word. So the confirmation is anchored in
the journal, and host write access is what keeps the browser from making it, the trust paper
`cli_confirm` has always had (mandate spec §6.1). No passkey can be verified until S3 enrols one,
so this decision covers `cli_confirm` only.

## Decision

1. **The shown code.** The web app shows, with a challenge from DEC-2103 item 1's route, a code
   made from the challenge's `webauthn_challenge` and nothing secret: the first 40 bits of those
   32 bytes as 8 Crockford base-32 characters (`0-9A-HJKMNP-TV-Z`), displayed as `XXXX-XXXX`. The web app computes
   it from the challenge answer's `webauthn_challenge`, so that answer gains no member. It
   binds a confirmation to the one challenge the owner saw. It is not a secret and needs not be
   one: it is spent with its challenge, which lives 300 s and is used once (DEC-2103 item 5), and
   what keeps it from the browser's own submission is that only the host appends to the control
   stream.
2. **The CLI command.** `mandate step-up confirm --workspace <ws> --principal <ULID> --agent <id>
   --approval <ULID> --challenge <ULID> --code <code>`, paper only. The CLI reads the approval
   from the control stream and shows it as `approvals show` does, so the owner confirms what the
   journal holds, never what the browser claims. It takes the action digest from that record: the
   approval's content hash (identity spec §7.2 step 1). It normalizes the code (upper case, the
   hyphen dropped, Crockford's `I` and `L` as `1` and `O` as `0`) and refuses a code of any other
   shape, appending nothing. It then appends one `StepUpConfirmed` (journal spec §9.29) and nothing
   else: it grants nothing, and the browser still submits the grant.
3. **The event.** `StepUpConfirmed` on the workspace control stream, schema version 1, envelope
   environment `paper`, written by a `user` actor whose `id` is `principal`:
   `{challenge, action_kind: "approve", action_digest, principal, code, confirmed_at}`, where
   `confirmed_at` is the event's own `event_time` in whole seconds (rule 242), so the window check
   8 judges cannot be moved by a value the writer chose apart from the record. A challenge is
   confirmed at most once on a stream (rule 243), so a second confirmation for one challenge is
   refused before it is appended.
4. **The principal.** The CLI's `--principal` is the principal's ULID text, the id the API writes
   as `actor.id` and `responder` on every event it commits for that principal. The verifier
   accepts a confirmation only when its `principal` equals the session's principal, and only while
   the subject link (workspace API spec §3.11 item 7, DEC-1023) names that principal on some line,
   read at verification as at a refresh; a principal no line names counts as missing
   (`step_up_missing`). The members read never stands in for the link.
5. **What the grant carries.** The browser submits the grant with step-up evidence
   `{assertion_id: <challenge_id>, authenticated_at: <issued_at>, method: "cli_confirm"}`,
   `authenticated_at` in whole seconds and equal to the challenge's `issued_at`, the earliest the
   gesture can have happened (DEC-662 item 7).
6. **The verifier's order.** For `cli_confirm` evidence, after DEC-2103 item 4's `live` refusal,
   at the server's clock `now`, the first failing check answers, and nothing is recorded:
   1. the action is `approve`, else `step_up_method`;
   2. the challenge `assertion_id` names is held, else `step_up_missing`;
   3. its principal, workspace, action kind, and action digest are the request's, else
      `step_up_mismatch`;
   4. `now` is within its `[issued_at, expires_at]`, and `authenticated_at` is its `issued_at`,
      else `step_up_stale`;
   5. no earlier control-stream event carries it as `step_up.assertion_id`, else `step_up_reused`
      (API-17);
   6. exactly one `StepUpConfirmed` on the control stream names it, else `step_up_missing`;
   7. that confirmation's `action_kind` and `action_digest` are the challenge's, and its
      `principal` is the session's, else `step_up_mismatch`; the subject link names the principal,
      else `step_up_missing` (item 4);
   8. its `confirmed_at` is within the challenge's `[issued_at, expires_at]`, else `step_up_stale`;
   9. its `code` equals item 1's code for the held challenge, compared in constant time, else
      `step_up_missing`.
   The grant then commits with that evidence, and the challenge is dropped from the store in the
   same step, so a second grant with it is `step_up_missing` here and `step_up_reused` on the
   journal.

   This order governs `cli_confirm` evidence. It differs from identity spec §7.2 step 4's, which
   governs `passkey` evidence (unused before current, the binding before the credential, the
   digest last): a `cli_confirm` step-up has no credential or signature, and its binding is judged
   before its life and its reuse, so the first failing check names the challenge's own fault
   before the journal's. Both orders draw on the same five `step_up_*` codes (workspace API spec
   §3.5), and every check in either refuses; only which code a step-up failing two checks gets
   differs.
7. **What this never changes.** The runtime still judges the grant's evidence at its effective
   time as mandate §6.1 says (window, reuse, method per environment). A confirmation is not
   step-up evidence and is never read by the runtime or the executor. `live` stays refused
   (`live_unavailable`, DEC-2103 item 4), and `cli_confirm` for any other kind is
   `step_up_method`.

## Rationale

The journal is the one channel the CLI and the API already share, and only the host writes it, so
a confirmation there is one the browser cannot make. The CLI reading the approval itself means the
owner confirms the journal's record, so a browser that names another digest gets
`step_up_mismatch`. A code from the challenge's own bytes needs no key and nothing new to store,
and the challenge's single use and lifetime spend it.

## Alternatives considered

- **No API grant: the web app shows the `approvals approve` line.** Rejected: it works today but
  does not carry out the founder's answer.
- **A code from a secret only the host holds.** Rejected for now: the host's write access already
  separates it from the browser, and a key would need its own storage and rotation.
- **Map the CLI's user through the members read.** Rejected by the coordinator: the subject link
  is the server's one principal mapping.
- **Journal the challenge when issued.** Rejected in DEC-2103 item 2; the confirmation names it.
