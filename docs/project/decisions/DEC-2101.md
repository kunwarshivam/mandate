## Context

The demo cell's owner should create, confirm, and deploy a mandate version from the web app. The
workspace API spec lists the routes (§4.1, §4.2) and the confirmation's checks (§5.1), but the
server cannot yet serve them as written: step-up is not verified (E9-4), drafts and the compiler
have no journal events registered, `MandateConfirmed` version 2 with its agent link is not
registered (E10-15), the confirmation screen's worst-case figures have no producer, and the server's
artifact store is read only. The CLI already writes each event (`mandate version create`, `version
confirm`, `agent deploy`; DEC-530), and the runtime reads what it writes.

## Decision

1. **The routes.** `POST /v1/workspaces/{ws}/mandate-versions` (`create_version`), `GET
   …/mandate-versions/{mandate_version}/confirmation`, `POST …/mandate-versions/{mandate_version}/confirm`
   (`confirm_version`), `POST …/agents` (`deploy`), and `POST …/agents/{agent_id}/go-live`
   (`go_live`); the names in brackets are §3.4's operation names. Each mutating route takes
   DEC-1007 item 1's order: the session, the CSRF mark, `Idempotency-Key`, the body (decoded
   strictly: none is an API-7 operation), then authorization by its matrix row. The rows are
   "Draft a mandate version", "Confirm a version" (both of its rows grant the operator alone, so
   the server authorizes the reducing row and adds step-up for an increasing verdict), and "Deploy,
   go live". Every one of these routes, the confirmation read included ("Draft a mandate version"),
   serves a **user** principal only: a client's "propose only" cell is not served, so a value a
   client wrote is never recorded `user_entered` (V-022, V-038). The events and their members are the CLI's, so nothing downstream changes, and each
   commits through DEC-1007 item 6's append before its answer.
2. **One step-up port, verifying nothing until E9-4.** The server judges evidence through one port
   that takes the action's kind and digest (§3.6) and returns verified evidence or a §3.5 code.
   Until E9-4 binds it, the port verifies nothing: a call that needs step-up and carries none is
   `step_up_required`, and one that carries evidence is `step_up_missing`, with nothing committed.
   This is DEC-1007 item 3 and item 10's refusal of a grant, applied to the confirmation and the
   deployment: an assertion the server has not checked is never recorded as step-up. Through the
   API, every risk-increasing confirmation and every deployment is therefore refused until E9-4;
   the CLI stays the path for both. The routes are complete behind the port, so binding it is the
   only change E9-4 makes here.
3. **A version is created from the document itself.** Drafts and the compiler wait for their
   journal events (E10-15). The body is the mandate document, as the CLI reads it from a file, so
   no compiler can propose `auto`, a delegation, pinned instruments, the environment, or the
   connection (V-022, V-038): every envelope path's provenance is `user_entered`, as DEC-530 has it.
   - It must parse as a mandate in the control stream's environment. A `live` document is
     `live_unavailable` (rule 8); another environment, or one unlike the stream's, is `invalid`.
   - §4.1 makes a version need a passing validation. The server runs the confirmation's own check
     here, every V-rule but V-002 as if every envelope path were confirmed, and the pinned
     instruments' registration, so a version the confirmation would refuse is never recorded.
     The CLI checks these only at confirmation; checking earlier only refuses sooner.
   - It stores the canonical document under its version (mandate spec §9.1) and the CLI's record
     (`kind`, `mandate_version`, `user`), then commits `MandateVersionCreated` version 1.
   - A version the control stream already records answers `200` with that event and commits
     nothing (§3.5's "already recorded"), as the CLI returns the earlier event. A repeat under a
     stored key is compared before anything is validated again (item 9); both answers carry the
     warnings as validated now.
   - The answer is `202` `commands/version-created`: `command_id`, `phase`, `mandate_version`, and
     the warnings' codes, so the client can open the confirmation screen.
4. **The confirmation screen serves what the server computes, for a new mandate.** Its members are
   the stored document, `agent_id` and `base_version` (both `null`), `classification`, the
   envelope paths V-020 requires, the warnings' codes, `step_up_required`, and `screen_digest`:
   the SHA-256, written `sha256:<hex>`, of journal spec §4's canonical form of exactly the seven
   members `mandate_version`, `agent_id`, `base_version`, `classification`, `required_paths`,
   `warnings`, and `step_up_required` (never the envelope's `as_of`; a member added later joins
   the digest only with a new version of the read). The warnings depend on the journal and the
   validation date, so the digest can move between the read and the confirm; the confirm is then
   refused `classification_changed`, and §3.5's row for it says so. A first
   version is `risk_increasing`: no earlier version bounds any path, and mandate spec §9.2 treats
   what it cannot bound as increasing (V-047 already reads a first version as a deployment that is
   not reducing). Worst-case figures, the unasked dollars, provenance badges, and the crypto gap
   disclosure are not served until their producers exist; the screen states only what it has.
5. **Confirmation is served for a new mandate only.** `MandateConfirmed` version 1 has no agent
   link, and the CLI's confirmation names none, so the server cannot record which agent a later
   version is for. A confirmation naming an `agent_id` is `invalid` at `/agent_id`, and a
   `base_version` with no agent, which no new mandate has, `invalid` at `/base_version` (a
   `stale_base` must name a current base, and there is none). The rest of §5.1's order follows:
   - the version is recorded on the control stream and stored, else `not_found`;
   - `classification_shown` equals the server's, else `classification_changed`;
   - `confirmed_paths` is exactly the envelope paths, and the version passes the V-rules as if
     confirmed, else `invalid` with each V-code (V-020 among them): the record then names every
     path the owner confirmed and no other;
   - `warnings_acknowledged` holds every warning code the screen showed, else `invalid` at
     `/warnings_acknowledged` (a tightening: §5.1 records them, and the screen requires them);
   - `screen_digest` equals the screen's now, else `classification_changed`, the code whose
     meaning is "the screen you saw is not the server's now"; the client reloads the screen;
   - a version the control stream's last `MandateConfirmed` already names answers `200` with that
     event and commits nothing, as the CLI does;
   - step-up, bound to §5.1's digest, SHA-256 of the canonical `{agent_id, base_version,
     mandate_version}`, kind `confirm_version`.
   The record keeps the CLI's members (`kind`, `mandate_version`, `step_up`, `user`, `warnings`)
   with the verified evidence, and adds the request's `record`, `screen_digest`, and
   `warnings_acknowledged`. It commits `MandateConfirmed` version 1, its paths ascending.
   `control_stream_frozen` is not sent: the journal has no freeze yet (journal spec §11); when it
   has one, every confirm is refused under it.
6. **Deploy takes the CLI's checks, in its order** (DEC-530 item 9). The body, decoded strictly,
   is `agent_id`, `mandate_version`, `backtest_id` (an id or `null`; backtests are not served, so
   it is recorded in the record and never read), `record`, and `step_up`. Its request schema and
   its `mandate-api` type land together in a later change: `mandate-api`'s tests require every
   request schema to have its type, and ES-22 keeps a schema out of a code change, so the server
   decodes the body with its own closed type until then (backlog).
   - An agent id that names no agent stream is `invalid` at `/agent_id`.
   - A version not recorded, or not in the store, is `not_found`.
   - A version never confirmed is `invalid` at `/mandate_version`; one with a later confirmation
     after it is `stale_base`, naming the latest confirmed version (API-19).
   - An agent already deployed with the same version answers `200` with its `AgentDeployed`; with
     another version, `invalid` at `/agent_id` (the CLI's `agent_active`).
   - Every V-rule for the agent (V-002, V-006, and V-032 included) and the pinned instruments'
     registration, else `invalid` with the V-codes, B3's rejections in words. V-002 reads the
     equity of the latest `AccountSnapshotRecorded` on the account stream of the document's
     connection (its `account_ref` on the control stream); with none, the equity is 0 and V-002
     refuses, the fold's own rule for a fact never seen. This tightens the CLI, which leaves V-002
     to the executor's check when the version is applied; the executor still checks it then.
     Creating and confirming a version leave V-002 out, as the CLI does: no agent is deployed
     yet, and deployment checks it.
   - Step-up, bound to the SHA-256 of the canonical `{agent_id, mandate_version}`, kind `deploy`.
   It stores the CLI's record (`agent_id`, `kind`, `mandate_version`, `step_up`, `user`) with
   `backtest_id` and the request's `record`, and commits `AgentDeployed` version 1 with
   `config_refs.mandate_version`. A refusal commits nothing; `DeploymentRejected` waits for the
   deployment manager to journal its own refusals, as the CLI writes none.
7. **Go live is always refused.** After item 1's checks and the deploy row, before the body is
   read: `409` `live_unavailable` (B5, rule 8). Nothing is committed.
8. **The store is written only by adding objects.** `MANDATE_API_ARTIFACTS` becomes writable to
   these routes, each object under its own digest; the store never replaces one. Without the
   setting these routes answer `journal_unavailable`, with nothing committed. A record stored
   before an append that then fails is a content-addressed object no event names, which is
   harmless and is what the CLI leaves too.
9. **Idempotency.** Each event's id is §3.4's derivation from the key. A repeat whose id is stored
   is compared before any step-up is judged, so a lost answer replays rather than being refused for
   a used assertion: the same event type, actor, and the members the request fixes (the version
   and paths of a confirm, the agent and version of a deploy, the version of a create) replay the
   stored outcome; anything else is `idempotency_conflict`.
10. **This change follows DEC-990 item 3:** the spec first (ES-22), then one PR with the tests
    first, failing on stubs.

## Rationale

The CLI's events are what the runtime reads, so the server writes exactly those. Every open choice
refuses rather than records: no unverified step-up, no version a confirmation would refuse, no
confirmation for an agent the event cannot name, and no screen digest the server did not compute.
The demo still needs step-up for its web confirmation and deployment, and binding E9-4's verifier
to item 2's port is the one change that unlocks them.

## Alternatives considered

- **Accept `cli_confirm` evidence from the web app.** The CLI's code proves the owner typed it on
  their own host; a browser sending the same shape proves nothing, and the server would record an
  unverified assertion as step-up.
- **Serve drafts now.** `MandateDraftSaved` has no registered schema, so a draft could not be
  journaled; the document body gives the same result without a new event.
- **Confirm a deployed agent's version with `MandateConfirmed` version 1.** The event would not
  name the agent, so neither the executor nor a reader could tell which agent it is for.
- **Refuse a mismatched screen digest as `invalid`.** The request is well formed; what changed is
  the server's state, which `classification_changed` names.
