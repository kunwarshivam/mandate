## Context

#1457 serves pause, the kill switch, and Skip (DEC-1007). E10-12 also needs resume, Stop, owner
exit, acknowledgment, and command status. §5.4 says the API forwards a missing step-up for resume,
Stop, and acknowledgment, and lets the stream owner refuse it; DEC-1007 item 3 forwards no
assertion the server has not verified. The CLI writes each of these events today (`mandate agent
resume`, `stop`, `exit`, `acknowledge`), and the runtime and executor fold them.

## Decision

1. **The routes.** `POST /v1/workspaces/{ws}/agents/{agent_id}/resume` (`resume`), `…/stop`
   (`stop`), `…/exits` (`owner_exit`), `…/acknowledgments` (`acknowledge`), and `GET
   …/commands/{event_id}`. Each command takes DEC-1007 item 1's order, its matrix row of the same
   name, finds the agent as DEC-1007 item 5 does (an agent an `AgentDeployed` names, else the one
   404), and appends as DEC-1007 item 6 does. Resume, Stop, and acknowledgment are strict; an owner
   exit is an API-7 operation and lenient (§5): its `instrument` is strict and its bid
   confirmation all or nothing.
2. **The events are the CLI's.** Resume, Stop, and owner exit commit `OwnerCommandIssued` version 1
   with journal spec §9.11's members, as `issued` writes them: a resume and a Stop name the agent as
   `agent` and `subject`, scope `agent`; a Stop carries `release`; an owner exit names the agent as
   `agent`, scope `instrument`, the asset as `subject`, and the confirmed `bid`, `bid_size`, and
   `floor` (each `null` without a full confirmation). An acknowledgment commits `OwnerAcknowledged`
   with `agent`, `event`, `user`, `risk_clock`, `submitted_at`, and `step_up`. `submitted_at` and
   `risk_clock` are the second of receipt. A digest reference in the payload (a Stop's
   `warning_shown`) is listed in `artifact_refs`, as the CLI lists it.
3. **A Stop's warning is the platform's.** A Stop with `release` must name as `warning_shown` the
   content reference of the CLI's release warning text (`RELEASE_WARNING`, DEC-136), else `invalid`
   at `/warning_shown`; the request schema already ties `warning_shown` to `release`. So the journal
   names only a warning the platform defines and shows, never one a client made up.
4. **Step-up is forwarded only once verified.** Resume, Stop, and acknowledgment carry as `step_up`
   the evidence DEC-2100 item 2's port verified, or `null`; the port's refusal does not refuse the
   command, as §5.4 says. Until E9-4 binds the port, every one is `null`, so the runtime or executor
   refuses each with `OwnerCommandRefused` `step_up_missing`, journaled where the specs put it. An
   owner exit forwards `null` likewise: it is still routed and loses only the owner-exit privilege
   (mandate spec §6.1). A client renders the refusal from command status, never "stopped". Under
   `independent_approval_required` an acknowledgment also fails closed (`not_independent`):
   `OwnerAcknowledged` does not carry its requester yet (journal spec §9.5), as the CLI's does
   not. Recording a command the owner will see refused is the spec's design: the
   refusal is the record, and the CLI stays the path that carries step-up.
5. **Members with no journal place are kept, not recorded**, as DEC-1007 item 4 has it: `record`
   for each, and an owner exit's `quoted_at` and `step_up`. Idempotency compares what is journaled
   but `submitted_at` and `risk_clock`.
6. **Command status reads direct causation.** The command is found by equality with a
   control-stream event id, else `not_found`. Its steps are the events whose `causation_id` is the
   command, on each deployed agent's stream and each account stream the control stream names
   (`account_ref` of a `ConnectionEstablished`), in that stream order and then `seq` order, each
   with its payload's `reason` when it is a lowercase code, else `null`. The phase is the most
   final step's: `refused` (`OwnerCommandRefused`, `ApprovalResponded` `refused`,
   `MandateVersionApplied` `rejected`), else `applied` (`AgentModeChanged`, `AgentModeApplied`,
   `KillSwitchActivated`, `MandateVersionApplied` `applied`, `ApprovalRevalidated` `act`), else
   `ended` (`ApprovalRevalidated` `skip`, `ApprovalTimedOut`, `ApprovalCanceled`), else `taken`
   for any step, and `recorded` with none. Only direct causation counts, so an order a kill switch
   canceled, which names its own cause, is not a step; a stream that cannot be read is
   `journal_unavailable`, never a shorter list. The read is authorized by the "View agents,
   positions, decisions" row, for users only until client tokens land (E10-14).
7. **The hold and its lift stay unmounted** until the runtime folds `hold_openings` (DEC-1007
   item 1).
8. **This change follows DEC-990 item 3.**

## Rationale

Each command is the CLI's event, so the runtime and executor judge it as they judge the CLI's. No
unverified assertion reaches the journal, and every refusal is recorded by the stream owner that
makes it. Command status claims only what the owning streams journaled.

## Alternatives considered

- **Refuse resume, Stop, and acknowledgment at the API until step-up is bound.** §5.4 has the
  stream owner refuse them so the refusal is journaled; refusing earlier would leave no record.
- **Follow causation transitively in command status.** It would list every order a kill switch
  touched, which needs the executor's own causation chains to be closed first; the phase is the
  same either way.
