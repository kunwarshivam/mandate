## Decision

1. **One's own memberships.** §4.2 gains the row "List one's own workspace memberships": `self` in
   the eight member columns (item 5), no step-up, and blank for Cl, SA, HC, and PO.
   - `GET /v1/me/workspaces` (identity spec §4.5) is the one route outside every
     `/v1/workspaces/{ws}` path. It is authorized by a full session of a user principal against
     that row. It is never authorized for a reduction-only session, a client, a service account,
     the host CLI, or a platform operator.
   - It reads one table, the **membership index**: a per-principal table in the workspace
     deployment's store, with row-level security keyed on the authenticated principal. It holds one
     row per (principal, workspace): `{workspace_id, label, state, roles with each role's
     effective-from}`. Each row is written in the same transaction as that workspace's `Member*`
     events and its label changes.
   - It returns only the rows whose state is `active`, each as `{workspace_id, label, roles}`.
     `roles` holds the roles effective at the read, so a member whose roles are all still cooling
     off gets the workspace with no roles. The answer covers this deployment's workspaces only.
     The global directory is not read (ID-15).
   - The E9-8 tests owe `no_principal_reads_the_membership_index_of_another`.
   - It yields no `TenantContext` and reads no workspace's data, so absent and foreign workspaces
     look the same (ID-8).
   - A failed lookup is refused `membership_unavailable`. This is not a risk-reducing operation,
     and no kill-switch route needs the list.
2. **One's own notification address.** §4.2 gains the row "Add or remove one's own notification
   address (a push subscription; later an email address)": `own` in the five workspace
   columns (WA, Op, Ap, Vi, Au), with **S** for both adding and removing, and blank for the org
   columns, Cl, SA, HC, and PO.
   - An address is per workspace: it is held in that workspace's vault namespace (§9.1), and
     authorized at that workspace's scope through a membership that reaches it.
   - The `own` cell's grammar covers one's own notification addresses as well as one's own
     credential.
   - In v0.3, an org owner or admin without a workspace membership receives no notice, because
     every inbox and every address is a workspace's. To receive the org's identity and
     account-security notices, an owner holds a workspace membership. A retail sign-up always holds
     one. Lane L3's notifications follow-up owes an org-scope inbox, and an org-scope address waits
     for a later proposal.
   - ID-4 lists it.
   - Workspace API §3.6 gains the step-up kind `notification_address`.
   - Who receives which notice class stays §4.1's receive column. Holding an address grants
     nothing.
   - A second row, "List one's own notification addresses (opaque references only)", has no
     step-up and is `own` in the same five columns. It authorizes listing those addresses, and the answer never carries an endpoint or a
     key.
3. **Who may obtain a step-up challenge.** A challenge for an action is authorized exactly as the
   §4.2 row that action needs (§7.2 step 1).
   - A principal that may not perform the action cannot obtain a challenge for it.
   - Clients, service accounts, the host CLI, and platform operators, whose cells on every **S**
     row are blank, never obtain one.
   - A reduction-only session is refused `reduction_only`.
   - A challenge for a risk-reducing row (an owner exit) follows the same path as the operation.
     When the live membership read fails, it is authorized from the session's roles snapshot and
     carries `membership_unverified` (DEC-642 item 10). A membership outage therefore never
     refuses it.
   - Owed to E9-4: `a_principal_who_may_not_act_cannot_obtain_a_challenge`, which asserts that no
     client, service account, host CLI, or platform operator ever obtains a challenge on any **S**
     row.
4. **`refresh_failed`.** `SessionRevoked` gains the reason `refresh_failed`, for a refresh the
   provider answered with neither a grant nor a deprovision signal (§6.4 route 1, for example a 408
   or a 429). It ends the session. It is not a deprovision signal (§11.1), so route 2 stays open.
   The journal schema gets the reason with E9-7's identity events. Owed to E9-1 (claim #758), in
   builder B2's session tests: `any_other_answer_ends_the_session_with_every_permission`.
5. **Principal scope and the `self` cell.** The matrix grammar gains the cell `self`. It grants the
   row to a user principal, through a full session, for its own data only, at **principal scope**:
   - no workspace or organization;
   - no membership read and no `TenantContext`: it yields the sealed `PrincipalContext` of
     [DEC-832](DEC-832.md) item 7, binding the principal's ID, which the principal-scope tables'
     APIs take in place of any principal ID;
   - whatever its memberships' states.

   At principal scope, a reduction-only session is refused `reduction_only`. A client, a service
   account, the host CLI, and a platform operator (blank columns) are refused `forbidden`. An agent
   or a process (no column) is refused `no_membership`, as DEC-643 sets.

   A `self` row has `self` in all eight member columns and is blank in every other column, and the
   parser asserts both. Owed to E9-2, the matrix parser's test:
   `self_rows_refuse_reduction_only_forbidden_and_no_membership`.

   ID-2 is amended to match: besides an effective role in a membership that reaches the scope, and
   a non-member principal's own column, it allows a `self` row to a user principal with a full
   session, whatever the states of its memberships, and nothing else. Principal-scope tables carry the principal's ID, with row-level security
   keyed on the authenticated session.

   A **full session** belongs to the deployment and is not bound to one workspace. Its roles
   snapshot is written for every workspace of the principal's membership index when it opens, and
   `MemberActivated` and `MemberReactivated` add to it in the same transaction, so a first request
   to any of its workspaces during an outage still finds a snapshot. `GET /v1/me/session` returns
   the session's own kind and expiry.
6. **Reduction-only sessions name their workspaces.**
   - `POST /v1/reduction-sessions/challenges` takes nothing and returns a challenge.
   - `POST /v1/reduction-sessions` takes the passkey assertion. Nothing workspace-specific is read
     or returned before it verifies.
   - The session covers every workspace where the verified credential has a row, each
     with that row's snapshot.
   - Its answer, and `GET /v1/me/session`, list those workspaces as `{workspace_id, label}`.

   The web app can therefore reach pause and the kill switch without the membership index.
   - In each covered workspace, the session authorizes only from that workspace's credential row:
     its four rows, and only where that row's roles grant them.
   - The challenge route is unauthenticated. It is rate-limited per address and device, and its
     challenges live 300 s.
   - Route 2 keeps serving every key the workspace holds, as it did before v0.3: the assertion
     comes from a discoverable credential, or from a non-discoverable key whose credential ID the
     client supplies with it. A member whose only key is non-discoverable therefore keeps the
     outage kill switch and pause. Whether to narrow the route to discoverable credentials only is
     the founder's question [DEC-833](DEC-833.md) (Proposed), because the narrowing would weaken
     rule 13 for those members; until the founder decides, the route serves both.
   - Owed to E9-1: `reduction_session_challenge_reads_and_returns_nothing_workspace_specific`.
   - **No membership oracle.** Every failure of `POST /v1/reduction-sessions` (an unknown credential
     ID; a known one whose row was removed or suspended; a bad signature; an expired or used
     challenge; a refused subject) returns one identical answer, 401 `unauthenticated`: the same
     status, body and headers, with no distinguishing timing. The route is rate-limited per address
     and per device, like the challenge route. Owed to E9-1:
     `reduction_session_failures_are_indistinguishable`.
7. **The authentication plane, and per-workspace ends.**
   - Some routes create, read or end the caller's own session and authorize nothing else. They
     sit outside the matrix and outside ID-2, and §4.2 lists them: sign-in and its callback,
     refresh, sign-out, opening a reduction-only session, and `GET /v1/me/session`. Every other
     route needs a row.
   - A session belongs to the deployment, so ending a membership acts on that workspace only.
     `MemberDeactivated` and `MemberRemoved` do the following in the same transaction:
     - remove the workspace from every session snapshot and credential row of the member;
     - revoke the member's client tokens there;
     - close the member's streams there.
   - Snapshots hold only memberships that reach their scope (`active` or `cooling_off`).
   - The membership index's writer for workspace W writes only W's rows.
   - A deprovision signal ends every session of the subject in the deployment.
   - When a deactivation or removal ends a member's membership in a workspace, the member's
     notification addresses in that workspace are removed in the same transaction. The removal is
     one `NotificationAddressChanged` `removed` per address, carrying the same actor as the
     membership event it rides in, with no step-up:
     - the deactivating admin or the member who left, on the request path;
     - `system`, when the separate process deactivates (directory sync, SCIM).

     A reactivated member is told by an in-app notice to add an address again. This was asked for
     by lane L3. Owed to E9-7:
     `deactivation_removes_the_workspace_notification_addresses_in_one_transaction`.
   - **This item supersedes DEC-642's wording** where DEC-642 item 9 says `MemberDeactivated`
     revokes the member's sessions and suspends their passkey credentials, and where item 10 and its
     pinned test `a_deactivated_member_is_refused_through_an_outage` speak of the member's sessions,
     tokens, and route-2 attempt being refused. Under this item the event removes that workspace
     from each session snapshot and credential row, and closes a session only when it has nothing
     left to reach (reason `deactivated`). The reason is that a session now belongs to the
     deployment, not to one workspace.
   - **The effect on the deactivated workspace is unchanged**, and DEC-642 item 10's founder-accepted
     guarantee is kept whole: in that workspace, with or without a membership-store outage, the
     member's sessions, client tokens, and route-2 attempt are refused, because a deactivation
     always wins over the snapshot. `a_deactivated_member_is_refused_through_an_outage` stays
     pinned, unweakened, and asserts that in the deactivated workspace and, as a new assertion, that the
     member's other workspaces are still served. Nothing in this item loosens item 10. Everything
     else in DEC-642 stands.

8. **Back from an outage only within the idle limit.**
   - A session that an outage left reduction-only keeps pause and the kill switch with no idle
     limit (§6.4 route 1), and those requests count as activity.
   - A later granted refresh restores it to a full session only if its idle timeout has not lapsed
     since its last admitted request. Otherwise the session ends.
   - A session ended by its idle or absolute limit, here or anywhere, is journaled as
     `SessionRevoked` with the reason `expired`, which §12.1 gains.
   - So an unattended session cannot regain full power just because the provider returns. It is
     a tightening, and `mandate-authn`'s session work (E9-1, claim #758) carries it. Owed to E9-1:
     `a_lapsed_idle_session_is_not_restored_by_a_granted_refresh`.

## Rationale

- **Item 1.** Every workspace route names `{ws}`, so a signed-in user had no way to learn it. The
  answer holds only the caller's own memberships, read by a principal-keyed query, so it reaches
  no workspace's data. Adding the row keeps ID-2's rule that a permission absent from the matrix
  is denied.
- **Item 2.** A stolen session could redirect safety notices to an attacker's browser, or silence
  them. Those notices are how an owner learns of a takeover (identity spec §13). So both adding
  and removing an address need step-up, the conservative reading. Clients and service accounts get
  none, because removing a channel weakens how the owner is reached.
- **Item 3.** Minting a challenge for an action one may not perform serves no one, and refusing it
  only narrows access.
- **Item 5.** The route has no workspace, so `own`, whose scope is a membership's, could not express
  it: a member with every role still cooling off would have been refused. A distinct cell lets the
  ID-2 parser check it, and keeps the table the single source.
- **Item 6.** The kill switch must not depend on the membership index, which fails closed. Covering
  every workspace of the verified credential needs no choice before verification, so nothing is
  read or returned for someone who has not proved the passkey, whichever kind of key it is, and
  every failure of the assertion route answers alike (owed to E9-1:
  `reduction_session_failures_are_indistinguishable`) (owed to
  E9-1: `reduction_session_challenge_reads_and_returns_nothing_workspace_specific`). A
  discoverable-only route would be a further narrowing and is not taken here ([DEC-833](DEC-833.md)).
- **Item 4.** It names the end reason that §6.4 route 1 already implies, so the record says why a
  session ended.

## Alternatives considered

- **No row for the memberships route, authorized by the session alone.** Rejected: it would grant
  a permission outside the matrix, which ID-2 denies (the review of PR #766, round 1, major 1).
- **Reusing the passkey row for notification addresses.** Rejected: an address is not a
  credential, and step-up evidence must name its own action.
- **No step-up for removing an address.** Rejected: removing one silences the takeover signal, so
  it is not a risk reduction.
- **Reading the global directory for the list.** Rejected: it holds IDs and role names only
  (ID-15), with no label and no cool-off state.
- **Serving discoverable credentials only on route 2.** Not taken: it would remove the outage
  kill switch and pause from members whose only key is non-discoverable, which weakens rule 13 and
  is the founder's call under DEC-79. Proposed as [DEC-833](DEC-833.md); route 2 serves both until
  decided.
- **Choosing a workspace before the passkey verifies.** Rejected: it would let anyone enumerate a
  credential's workspaces.
- **Including `cooling_off` memberships in the list.** Rejected for now: the coordinator asked for
  active memberships only, and a cooling-off member's workspace appears once the member is active.
