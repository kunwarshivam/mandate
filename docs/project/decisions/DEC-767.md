# DEC-767: Verification takes its trusted start from a manifest or anchor in the journal, never from the request

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The agent in lane L5, under DEC-79 and DEC-176: a reading of an unclosed API contract that adds a bound or a refusal and loosens no rule |
| **Story or claim** | E12-6 ([#756](https://github.com/kunwarshivam/mandate/issues/756)); E12-1 (#745), E12-2 (#747), E12-3 (#748); workspace API spec §4.8.1 |

## Decision

1. `POST /verifications` takes `stream_id`, `from_seq`, `to_seq` (or `null` for the head), and
   `trusted_start`: `genesis` (only with `from_seq` 1), a `SegmentExported` manifest hash whose
   first `seq` is `from_seq`, or an `AnchorComputed` event whose leaf for the stream is at
   `from_seq` − 1. The trusted `prev_hash` is read from that object.
2. A trusted start that is absent, foreign, or does not fit the range is 422 with violation
   `trusted_start`, the same for absent and foreign.
3. One run covers at most 1,000,000 events.
4. The result is `pass` or `fail` with the first failure's `seq` and journal spec §11 check code;
   it is served only after its `VerificationRun` commits. A failure is the same record §11's
   response keys on; the API takes no other action.

## Rationale

A caller-chosen `prev_hash` would let anyone "verify" a tampered range against a hash of their
choosing. Journal spec §11 already says the trusted start comes from a manifest or anchor.

## Alternatives considered

- **Accept `trusted_prev_hash` in the request.** Rejected for the reason above.
- **No size bound.** Rejected: an unbounded synchronous run is a denial of service.
