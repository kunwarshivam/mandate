## Context

DEC-1175 lets the deployment manager start an OAuth connect's token exchange once, as a bare pod,
and stop it when its request closes. The exchange is the one process that reaches the live token
host, and it logs in to the vault as its connection's own ServiceAccount (DEC-2060). This decision
fixes what the chart admits for it, what the manager may create and delete, how the Kubernetes
adapter launches it, and how the manager reads its request. DEC-1175 is Accepted and its text does
not change; this file carries what came after it.

## Decision

1. **The admission pin is per process.** The deploy-manager's pod policy reads the pod's
   `mandate.dev/process` label and holds it to that process's template alone: its images; exactly
   its containers' commands and arguments, the container count included; its Secrets (none for the
   exchange); its read-only claims; and its projected volume. A token exchange runs as an `x`-and-hex
   account, every other process as `default`. The exchange's process entry is `one_shot`: never a
   standing Deployment, it runs its pinned launch with no probe.
2. **Each policy literal holds one CEL type.** The API server's CEL checker refuses a map or list
   literal that mixes types, which a Python mirror of the rules could not see (#2077's first cell
   run). Each launch is `[command, args]` by container name, each projected volume one string
   (`audience|seconds|path|mode|item=field`), and the account check uses plain equalities. A test
   checks that every policy variable keeps one type at each depth.
3. **The tests evaluate the rendered CEL.** `deploy/tests/test_cell.py` evaluates each policy's own
   expressions with cel-python (`cel-python==0.5.0`, in the Python workspace's dev group;
   `docs/dependencies.md`), as the API server evaluates them, over each template as the manager
   starts it and each attack: a rule that is dropped or loosened, `|| true` included, or a list that
   is widened, admits an attack and fails the tests. cel-python asks for PyYAML 6.0.2 or later, which
   only adds wheels, so a uv override keeps the workspace's 6.0.1 (the reference's). The same pods
   and attacks were applied to a k3s API server as the manager's own account, and it agreed with
   cel-python on every case it reached admission for.
4. **The manager makes and deletes the exchange's account, bounded.** Its Role creates, gets, lists
   and deletes `serviceaccounts` in its namespace. A second policy, over create, update and delete
   alike (a delete reads the account as it stands, `oldObject`), refuses any account not named as
   DEC-2060 names an exchange's, `x` and an even count of lowercase hex digits, at most 129
   characters, so neither `default` nor the manager's own account; one that mounts a token or holds
   a Secret or pull secret; and one without the manager's, this workspace's and the
   `token-exchange` labels. The manager copies the workspace label from the process's template, the
   chart's value, never derived from the workspace id.
5. **An executor's account comes with the change that runs the executor as it.** The pod policy
   cannot pin an executor pod to its own `<hex>` account unless the same change makes the adapter
   name and create that account, which needs the executor's connection, and the executor slot is
   keyed by `account_ref`. Pinning it alone would refuse the executor pods the manager makes today.
   So, for now, executor pods stay on `default` and the accounts policy admits the exchange's form
   only; the change that starts the executor for a connect (DEC-2627 item 5) brings the executor's
   account, its adapter and manager code and its pod-policy pin together.
6. **The exchange's account is named in its environment.** CEL cannot hex the pod's subject, so
   the manager sets `MANDATE_SUBJECT_ACCOUNT`, the account it computed, beside `MANDATE_SUBJECT`. The
   pod policy requires each of the exchange's containers to name each exactly once, the account
   equal to the pod's `serviceAccountName`; the exchange refuses to start unless that account is `x`
   and the hex of `MANDATE_SUBJECT`'s bytes. So the process that reaches the live token host cannot
   log in as another connection's role short of its own binary being wrong.
7. **No root, no added capability, no chosen node.** Every pod the manager makes sets
   `runAsNonRoot`, names no uid 0 for the pod or any container, adds no capability, and names no
   host alias or node. The three templates already hold this.
8. **The projected volume is exactly the vault token and the namespace.** A `vault_token` process
   mounts one projected volume, mode 0444, read-only at `/run/mandate/vault-token`: the token
   (audience `mandate-vault`, 600 seconds, `token`), then one downward item, `metadata.namespace` at
   `namespace`, with no mode of its own. The pod policy refuses any other source, order, field,
   item or mode.
9. **The launch is at the image root.** Release images put each binary at `/<name>`
   (`xtask/src/image.rs`), so the exchange runs `/mandate-token-exchange` with no argument, reading
   its connection from `MANDATE_SUBJECT`, and the chart's tests refuse a container whose launch names
   a `mandate-` binary anywhere else.
10. **When the exchange starts.** The manager starts it on the request itself, after creating its
    account; no record says the vault role exists. The exchange's login retries a missing role or an
    unreachable vault with a short capped backoff until its deadline, and stops at once on any other
    refusal (DEC-2060's recommendation).
11. **How the adapter runs it.** The orchestrator's start takes the `lifetime` the request has left,
    for a token exchange only, and a standing process never one. The pod's `activeDeadlineSeconds`
    is that lifetime in whole seconds, rounded down, and no exchange is created with less than a
    second left or with none. Before the pod the adapter makes the account (point 4), keeping one
    that already exists, and asks for no pod until it does. A stop deletes the account, then the
    pod, so a stop that fails leaves the pod listed and the manager asks again; either already gone
    is done. The process label, template file and pod name use the chart's spelling
    (`token-exchange`, `tx`); the journal and `MANDATE_PROCESS` keep `token_exchange`. The deadline
    counts from the start's journaling and the pod's from when the kubelet takes it, so a pod can
    outlive its request by its scheduling delay: the code it would redeem has expired by then, and
    the vault grant's own 600 seconds still bound it.
12. **How the manager reads a request.** A version-2 `ConnectionRequested` with `credential`
    `oauth` wants its connection's exchange until a record closes it: a `ConnectionEstablished` of
    either version, a `ConnectionRefused` with occasion `connect`, or a `ConnectionRevoked`. A
    closing record read before the request also closes it. The exchange's lifetime is the request's
    `recorded_at` plus 600 seconds less the pass's time. A start journaled but not seen carried out
    is asked of the orchestrator again only while that lifetime is a second or more, and only by
    the manager that journaled it: after a restart it counts as the one attempt. Once the request
    closes, the manager stops every instance still listed, exited or not, so its pod and account
    are deleted.

## Rationale

Each point narrows what a compromised or careless manager can create: another process's image,
launch, credentials or account under the exchange's label, a root or privileged pod, an account
that is not a connection's exchange's, or the deletion of one that is not. Evaluating the policies'
own CEL in the tests makes a loosened rule fail, where a mirror of it passed. Keeping the executor's
account for the change that runs the executor as it adds no account nothing uses.

## Alternatives considered

- **Keep the Python mirror of each rule.** Rejected (the security review of #2077): `|| true` on a
  rule passed it.
- **Compare each rendered expression with a literal.** Rejected while a pinned evaluator works
  behind the proxy: it checks the text, not what the text admits.
- **Pin executor pods to `<hex>` now.** Deferred (point 5): it would refuse today's executor pods.
- **Check the account's hex in CEL.** Not possible: CEL has no byte-to-hex function, so the
  exchange checks it (point 6).
