## Context

§9.14 makes an `AnchorComputed` a trusted start only when it has a `token`, and the resolver of
DEC-893 and DEC-895 checks that start row's §11 checks 1, 2 and 4 and its root. None of them reads
the token itself. A row whose leaf `hash` was rewritten, its `root` recomputed over the new leaves
and the row re-hashed, keeping its old `token` ref, passes every one of those checks and starts the
range at the forged hash: today it is a start in the reference (`start_from_rows`) and in the Rust
resolver of PR [#1244](https://github.com/kunwarshivam/mandate/pull/1244). The token is the one
part of the row a hot-store writer cannot forge, because its imprint is the original root.

Workspace API §4.8.1 step 2.2 already lists "the trusted-start anchor" among the anchors whose
token is checked, and rule 132 already requires an `anchor` start's range to end failed or
incomplete. Neither the vectors nor the code pin it, and no row vector pinned the `token` guard on
the rows path: a seeded bug dropping it passed review.

## Decision

1. **The start anchor's token is verified.** A range whose trusted start is an `AnchorComputed`
   runs §11's token check on that anchor, as it does on an in-range anchor. Its place is workspace
   API §4.8.1's run order, step 2.2, unchanged: after `anchor_root_mismatch`, among the anchors
   that step reads, in ascending anchor `seq`, reported for the range with `seq` `null` (rule
   111). The resolver stays a lookup over rows; the run reads the token from the same snapshot.
2. **An invalid token fails.** A token that does not verify, or whose imprint is not the start
   anchor's `root`, fails the range `tsa_token_invalid`: `result: fail`, a SEV-1 and §11's "On
   failure", never a start that passes. A token ref whose artifact is absent from a store that
   answers, or does not re-hash to its ref, cannot carry the imprint, so it fails the same way.
   Since §4.8.1 runs the per-event checks first, a start whose leaf `hash` was forged usually
   shows first as `prev_hash_mismatch` at `from_seq`; either way the run fails.
3. **An unverifiable token is incomplete, never a pass.** A token whose imprint matches but which
   cannot be verified (no TSA certificate chain, no network, and until DEC-265 item 1's crypto half
   lands, every token) leaves the check incomplete, cause `token_unverifiable`, exactly as DEC-789
   items 1 to 4 and 9 say for an in-range anchor. An artifact store that cannot be read is an
   outage and is treated the same way; that arm is this decision's own reading, not DEC-789's,
   which says nothing of an unreadable store. It is the one reading with an effect a restore drill
   can see: `token_unverifiable` is the cause DEC-789 item 9 lets a drill pass on, so a drill would
   pass while the token store is down. That is no looser than today, when nothing checks the start
   token, and tightening the drill rule is the founder's (DEC-79). The range records `failure: null`,
   `incomplete: {check: tsa_token_invalid, cause: token_unverifiable}`, `start: {kind: anchor,
   anchor_event_id}` and a full `checked`; with no range failed, the run's `result` is
   `incomplete` (rule 133). A range that also checks an in-range anchor with a `null` token records
   `anchor_unstamped` (DEC-789 item 7). The start anchor itself never gives `anchor_unstamped`:
   item 4 refuses it before the run.
4. **An unstamped anchor is no start, on every path.** An `AnchorComputed` whose `token` is `null`
   is refused before the run, 422 `trusted_start` with nothing recorded (§9.14; DEC-783 item 8),
   however sound its row. The vector `cold_records.trusted_starts.row_cases`
   `anchor_unstamped_and_rehashed` pins it on the rows path: the good start anchor with `token:
   null`, re-hashed, canonical, on the workspace's control stream, requested by its `event_id`,
   refused with cause `no_start`. That is the cause the reference already gives: the lookup never
   matches an unstamped anchor (`trusted_start`'s `token` guard), so the row is never a candidate.
   `anchor_unstamped` was not taken for it, because that word is DEC-789 item 7's cause for a range
   that ran; the Rust error is `TrustedStartError::Refused` either way (DEC-893 item 5). The seeded
   bug `row.unstamped_ok`, the guard dropped on the rows path, is caught by this case alone.

### The sequence

1. **This change:** item 4's row vector and seeded bug, this decision, and backlog E12-8. It lands
   before the change that removes the old `trusted_starts.records` and `cases`, whose
   `unstamped_anchor_is_no_start` is today the guard's only other pin.
2. **Token vectors:** the reference's start-anchor token check over a run, with an oracle and
   seeded bugs: a token whose imprint is the root (`incomplete`, `token_unverifiable`); one whose
   imprint is not (`tsa_token_invalid`); a leaf rewritten, the root recomputed and the row
   re-hashed with the old token kept (`fail`); a token artifact absent (`tsa_token_invalid`); and
   an unverifiable start beside an in-range `null`-token anchor (`anchor_unstamped`).
3. **Spec text,** by lane L2, which owns the journal spec.
4. **Pending tests** for the run's token check on the start anchor (AU-8, DEC-787 item 8).
5. **The implementation,** in the run's logic in `mandate-audit`, after PR #1244's resolver.

**Spec follow-up (lane L2):** journal spec §9.14 "What a verifier reads", one sentence that the run
verifies an anchor start's token under §11's token check; §11's per-range list and the first bullet
of "Incomplete", naming the trusted-start anchor among the anchors the token check reads, and that
a token artifact absent or not re-hashing fails `tsa_token_invalid`. Workspace API §4.8.1 step 2.2
and rules 132 and 133 already say enough and need no change.

## Rationale

Each item ends in `fail`, `incomplete`, or a refusal a run that today could start and pass, never
the reverse. Without item 1, a forged anchor start whose root was recomputed is judged only by the
chain it vouches for. Items 2 and 3 are DEC-789's own outcomes: an outage is never a false
`tsa_token_invalid` and never a pass, and a token that cannot carry the root fails.

## Alternatives considered

- **Verify the token in the resolver and refuse with 422.** Not taken: the resolver reads rows only,
  a refusal records nothing and raises no SEV-1, and §4.8.1 already places the check in the run.
- **Treat an unverifiable start token as a failure.** Rejected: it would raise a SEV-1 on every
  anchor-start run until DEC-265 item 1 lands, which DEC-789 refused.
- **A separate refusal cause, such as `anchor_unstamped`, for the unstamped start row.** Not taken:
  item 4.
