## Context

DEC-1005 item 2 says only the web deploy job names the `production` environment, and
`web/scripts/workers.mjs` refuses any other workflow that does, or that holds a `CLOUDFLARE_`
value. #1454 then added `.github/workflows/r2-lockcheck.yml`. It is dispatched from `main` only,
runs one job in `production`, and reads R2's key and the Cloudflare token in its one step. The
`web` checks run only on pull requests that touch `web/`, so #1454 never ran them, and the guard
has failed on `main` since.

## Decision

1. `PINNED_PRODUCTION_WORKFLOWS` in `web/scripts/workers.mjs` lists the other workflows that may
   use the `production` environment, each with the SHA-256 of the text a reviewer read. Today it
   lists only `r2-lockcheck.yml` (`fb00fb81…c2d8e`).
2. A listed workflow passes only byte for byte. Any edit, a comment included, fails until someone
   re-reads it and moves the pin in a reviewed change. The Cloudflare-command allowlist still
   applies to it, so it cannot deploy the Worker.
3. Every other workflow keeps DEC-1005 item 2's rule unchanged.

## Rationale

ES-12's property is that no pull-request job can reach the environment. The pinned file holds it
(dispatch only, `main` only), and the pin keeps it holding, because any change is a guard failure a
reviewer must clear. Parsing its shape would be a second, weaker copy of the review.

## Alternatives considered

- **Allow any workflow that runs only on `main`.** That is wider than what `main` carries, and it
  lets a new holder of the token in without a review of the guard.
- **Keep the rule and leave `main` red.** Every `web/` pull request would fail.
