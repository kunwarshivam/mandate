## Context

web/'s instrument search lists `GET /instruments`, which carries no price. A customer picking an
instrument sees no real price.

The workspace's data process (`mandate-datad`) stores bars on the artifact volume the API server
already mounts read-only. On staging these are IEX bars from Alpaca (DEC-2082); in the local cell
they are the recording. `mandate-bars` holds the one trust rule every decision reads them through
(DEC-2385). The API server may link it: it is layer 7, and the API server, layer 9, does not forbid
it.

What is not available to the API:
- **A live bid or ask.** The executor's quotes stay in its process and are never journaled.
- **A minute close.** `mandate-bars`' minute reader hands out volumes only.
- **A mark for every instrument.** `MarkUpdated` marks exist only for each deployment's own
  instrument, on its account stream, and only in session.

## Decision

1. **A new read, `GET /instruments/{id}/price`,** answering `read-models/instrument-price`. It is
   kept apart from `GET /instruments`, so the catalogue stays a journal fold and a bars failure
   never fails it. It is authorized as the catalogue reads are, writes nothing, and is served in a
   `live` workspace too.
2. **What it serves:** the last trusted daily bar of the instrument's symbol, as `mandate-bars`'
   `trusted_daily_bars` admits it at the API's clock. That is the close of the last completed
   regular equity session. It is served as `close`, with its bar's `bar_start`, `timeframe`
   `1Day` and the `source`. `as_of` names the control stream, as every read's does.
   - It is never called a bid, a quote or a current price.
   - A client shows it as the last close, with its session.
3. **The instrument** is the one `GET /instruments` lists with that `instrument_id`. An id it does
   not list is the one 404 (`not_found`), and a control stream it cannot fold is
   `journal_unavailable`, as for the catalogue.
4. **Not reported, never a stub.** When no trusted bar can be served, the read answers `200` with
   `reported` `false` and one `reason`:
   - `no_store`: the API was given no bars root (`MANDATE_BARS` unset), or the root does not exist.
   - `not_covered`: the instrument's asset class is not `us_equity`, since the stored bars and their
     trust rule are the equity calendar's.
   - `no_bars`: the symbol's dataset has no manifest at the path the root and the clock name.
   - `untrusted`: anything `mandate-bars` refuses or cannot read.

   No `close` is sent with any of them.
5. **The source** is `alpaca-iex` when the root is a generations root (`mandate-bars`'
   `is_generational`), and `recorded` otherwise. The chart gives the API process `MANDATE_BARS` as
   it gives the runtime and the executor. The chart change rides the same promotion as
   `mandate-datad` (#2961).
6. **The clock.** The API reads its host clock once per request, the instant the envelope serves
   as `served_at`. That clock names the generation and the last completed session, as
   `cool_off_ends` is the API's clock (§3.6). No record is dated by it, and nothing is written.

## Rationale

This is the honest real price the platform holds: a stored, trust-checked close. It names its
session, so a customer never mistakes it for a live quote. Keeping it off the catalogue read keeps
that read's contract, and its failure modes, exactly as DEC-2136 set them.

## Alternatives considered

- **A `last_price` member on `GET /instruments`.** Rejected: one bars failure would then need its
  own member on every row, or would fail a read the create depends on.
- **The executor's mark.** Rejected: it exists only for a deployment's own instrument, only in
  session, and is not the instrument search's set.
- **A minute close.** Deferred: `mandate-bars` would need a new minute reader that hands out
  closes, a safety-critical change of its own. A backlog row records it.
- **Live quotes.** Out of scope: they would need a journaled quote record and a source the API can
  reach, which no process provides.
