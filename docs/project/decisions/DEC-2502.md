## Context

A member may hold up to 10 active web-push addresses in a workspace (workspace API §4.11), one per
browser. The dispatcher's send is keyed by an `AddressHandle`, `(recipient, channel)` (DEC-710
item 4), and its record, `NoticeAttempted`, names a recipient and a channel but no address (journal
spec §9.15). So one handle must become N sends, and a verdict on one browser's subscription
(`404`, `410`, a `3xx`) must mark that subscription and not the member's other browsers, which
workspace API §4.11 already lists one by one with their own status. The recipient is a
`mandate_notify::Recipient` (`[a-z][a-z0-9_]{0,63}`); the member in `NotificationAddressChanged` is a
`PrincipalId`, a ULID.

## Decision

1. **The vault entry.** An `address_ref` names one entry in the workspace's vault namespace,
   holding `{member, endpoint, p256dh, auth, key_id}` with the workspace API's bookkeeping (§5.7:
   the request digest, `version`, `written_at`). `key_id` names the VAPID key the browser subscribed
   under (DEC-2503 item 5). The entry is personal data (NT-2); `address_ref` is the `added` event's
   own id and is never derived from the address.
2. **The active set comes from the journal, never the vault.** The dispatcher folds
   `NotificationAddressChanged` on its workspace's control stream, which it already reads (§5.1
   step 1): an address is active while its last event is `added`. It folds its own notice stream for
   each address's marks (item 6). It never lists the vault to find addresses; a vault entry with no
   committed `added` is never sent to (workspace API §5.7's inert entry).
3. **The recipient's form.** A principal's recipient id is `p_` followed by the principal's ULID
   text in lowercase: 28 characters, inside `Recipient::parse`'s alphabet, starting with a letter.
   It is reversible (drop `p_`, upper-case, parse the ULID) and deterministic, so the dispatcher
   joins a `NotificationAddressChanged`'s `member` to `NoticeIssued.recipients` with no table, and
   NT-8's and NT-6's oracles can do the same from the journal alone. No recipient in this form
   parses as a notice id (32 hex digits) or a ULID (upper case, no `_`). The dispatcher process
   refuses an audience entry (DEC-2500 item 7) in any other form; the pure crate's `Recipient` is
   unchanged.
4. **One handle fans out to every active address.** For a notice's send on `(recipient, web_push)`,
   the dispatcher sends to each of the recipient's addresses that is active, not marked
   `unreachable` (item 6), and on the allowlist (§4.6), one send per address, each judged and
   retried on §5.3's schedule on its own. The set is the addresses active at the step that makes
   the channel's first attempt for the notice; an address added later gets nothing for an earlier
   notice (DEC-704 item 4's rule for recipients, applied to addresses), and an address removed later
   gets nothing more (spec §5.1), save DEC-795's one last send. A crash inside that first step can
   let an address added before the restart join: more delivery, never less. A
   `notification_address_changed` notice's own `added` address is active at its cause, so it is
   included. **The fan-out is concurrent and bounded by one deadline.** The sends of one handle
   start together and run concurrently, and each, its vault read included, has the one 10-second
   deadline of DEC-2500 item 6, past which it is `retryable` (`timeout`, or `provider_error` for a
   vault read that has not answered, item 7). So a handle's fan-out settles within 10 seconds of
   its start whether it holds 1 address or 10: the address count adds nothing to a step's length,
   and a cause's first attempt per address is made no later than a single-address send's would be,
   which keeps NT-6's 60 seconds and DEC-2500 item 6's drain unit (the send in flight is this one
   fan-out). The handle's records (item 5) are appended once its sends settle, in `address_ref`
   order, before the step's next handle is sent; an append that does not commit stops the step
   there (DEC-704 item 3, read with the handle as the unit), and a send of the handle whose record
   did not commit is made again by the next step under its own key (at least once, NT-8).
5. **One idempotency key and one record per address.** The key a provider sees is DEC-710 item 5's
   digest over `{"address", "channel", "notice", "recipient"}`, with `address` the `address_ref`,
   so two browsers never share a key. Each send's outcome is its own `NoticeAttempted`, carrying
   the `address_ref`, numbered from 1 per address. That needs a journal spec change (owed, below):
   `NoticeAttempted` version 3 adds `address_ref` (non-null exactly when `channel` is `web_push`,
   listed in the event's `pii_refs` as on the control stream), and the reason `address_retired`
   (only with `abandoned`) for a send whose address was removed, or marked `unreachable` by another
   attempt, before its next attempt. Until it
   merges, the dispatcher makes no web-push attempt at all: there is no record that could hold one.
6. **A verdict marks one address.** A `NoticeAttempted` whose reason is one of §5.6's five marks the
   address its `address_ref` names `unreachable`, and only that one; its `channel_lost` notice goes
   to the member's other channels, the member's other active web-push addresses included, and the
   pull channels. `address_missing` is reported once per address (§5.6). DEC-729 item 4's interim
   stands: `401` and `403` are `permanent { provider_error }` and mark nothing, so a signing fault or
   a rotated key cannot mass-mark addresses.
7. **A vault that does not answer is not a missing address.** `address_missing` is only the vault's
   definite answer that no entry exists for the handle's `address_ref`. A vault that is unreachable,
   sealed, or refuses the dispatcher's identity is `retryable { provider_error }`: it marks nothing,
   raises no `channel_lost`, and retries inside the class's window.
8. **The address lives only for its send.** The adapter reads the entry for one send, holds it in
   memory as a `secrecy` value, and drops it when the send returns. No type that holds an endpoint
   or a key has a `Debug` or `Display` that prints it (DEC-790 item 6); the HTTP client's errors,
   which can carry the request's URL, are mapped to §5.2's closed reasons without being formatted,
   logged, or kept.
9. **The record carries no part of the address.** `NoticeAttempted` holds the `address_ref` and
   nothing derived from the endpoint, its host, or which push service it is on (DEC-2500 items 9
   and 10).
10. **Not the most recent address alone.** The option of sending only to the member's most recently
    added active address, leaving their other browsers to the pull channels, is rejected. It would
    deliver a `notification_address_changed` notice about an address an attacker added with a stolen
    session and step-up only to the attacker's own browser, the newest, and to none of the member's,
    which is the out-of-band signal DEC-795 exists for; and DEC-795's last send to a removed address
    is by definition not to the newest. It reduces safety delivery (NT-6), so it is not an interim
    either: until item 5's record exists, the interim is no web push at all, as DEC-2504's interim
    already holds, with the pull channels carrying every notice.

## Owed by other changes

- **Journal spec** (L3): `NoticeAttempted` version 3 (item 5), its consistency rules, and §9.15's
  terminal rule per address.
- **Workspace API spec §5.7** (lane A1, which owns `PUT /me/channels/web_push`): the entry's
  `key_id` (DEC-2503 item 5).
- **The fan-out timing test** (L3, with E8-14's dispatcher change): a recipient with 10 active
  addresses on a push service that holds every request to its deadline gets every address's first
  attempt, and the handle's 10 records, within one 10-second deadline of the handle's start; with
  one address hung and nine answering, the nine are not delayed past it; and a SIGTERM during that
  fan-out exits `drained` well inside `DRAIN_BOUND` (item 4, DEC-2500 item 6; spec NT-6).
- **Infrastructure §5.2 and the vault policy rows** (L3, the E21-32 follow-up): the dispatcher's
  read of its workspace's address entries, with no wildcard that reaches past them.

## Rationale

The specs already say to send to every address the member holds (notifications §3.2's
`notification_address_changed` row, §5.1 step 3) and to show each address's own status (workspace
API §4.11). Items 1 to 7 are the mechanics that make those sentences true with N addresses. Item 3
picks the form that is reversible without a lookup table, so no mapping can drift or be edited to
redirect notices. Item 7 closes a gap in which a vault outage could have raised a `channel_lost`
for every address in the workspace.

## Alternatives considered

- **Most recent address only:** item 10.
- **One record per handle, summarising its addresses.** Rejected: a verdict on one browser would
  either mark them all or be lost, and the record could not say which address an oracle should
  count.
- **A recipient id from a hash of the principal.** Rejected: not reversible, so the join needs a
  table that someone could edit.
- **The 32-hex form of the principal's 128 bits.** Rejected: it would parse as a `NoticeId`.
