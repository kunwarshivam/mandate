# DEC-2105: A `cli_confirm` challenge's life is half-open, and its confirmation's second must end within it

| | |
|---|---|
| **Status** | Accepted (agent: DEC-176 readings that only tighten DEC-2104 item 6; each adds no risk) |
| **Date** | 2026-10-19 (UTC) |
| **Decided by** | `claude-code` (lane L1, claim [#759](https://github.com/kunwarshivam/mandate/issues/759)), under DEC-79 and DEC-176 |
| **Story or claim** | E9-4 S2; claim #759; #1766; amends [DEC-2104](DEC-2104.md) item 6 checks 2, 4 and 8 |

## Context

DEC-2104 item 6 says the verifier judges `now` and `confirmed_at` "within" a challenge's
`[issued_at, expires_at]`. The core already reads a challenge's life another way:
`mandate_passkey::stepup::ChallengeRecord::is_current_at` is `issued_at <= now < expires_at`, and the
server's `Challenges` store drops a challenge once `now` reaches `expires_at` (DEC-2103 item 5). The
closed bracket is wider than both, and `confirmed_at` is a whole second, so "within" does not say
whether a second that starts before expiry but ends after it counts. The verifier's tests (#1766)
pin these bounds, so they are read here before the code lands.

## Decision

1. **Check 4: the life is half-open.** `now` passes when `issued_at <= now < expires_at`, as
   `ChallengeRecord::is_current_at` and the store keep it. At `expires_at` the challenge is
   `step_up_stale`.
2. **Check 8: the confirmation's whole second ends within that life.** `confirmed_at`, a whole
   second, passes when `floor(issued_at) <= confirmed_at` and `confirmed_at + 1 s <= expires_at`.
   A confirmation in the last part of a second that straddles expiry is `step_up_stale`, never
   admitted.
3. **Check 2: the lookup comes before the expiry drop.** The verifier looks up the challenge the
   evidence names before the store drops expired challenges, so a challenge held past its life
   answers `step_up_stale` at check 4 rather than `step_up_missing` at check 2. Either refuses;
   this fixes which code the owner sees.

## Rationale

Each item only refuses: item 1 removes the instant `expires_at` itself, item 2 removes the part of
the last second that may fall after expiry, and item 3 changes only which refusal is reported.
Items 1 and 3 make the verifier agree with the core and the store it reads. No item admits a
step-up DEC-2104 refused.

## Alternatives considered

- **The closed bracket, as DEC-2104 item 6 wrote it.** Rejected: it admits `now == expires_at`,
  which the core and the store already treat as expired.
- **`confirmed_at < expires_at`.** Rejected: a confirmation made late in the second that begins
  just before expiry would pass after the challenge expired.
