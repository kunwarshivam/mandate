# DEC-991: The founding grant is written once, by `mandate workspace found`, through the one membership writer, deciding inside the append's attempt

| | |
|---|---|
| **Status** | Accepted (agent: reversible engineering readings under DEC-79 and DEC-176; each only refuses or narrows, and none loosens a rule) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (builder of claim [#1445](https://github.com/kunwarshivam/mandate/issues/1445)), under DEC-79 and DEC-176 |
| **Story or claim** | Lane ID1 (E9-7 follow-up, demo blocker for A1, #1444); claim #1445; identity spec §3.2, §4.3, ID-13; journal spec §9.12 |

## Context

The workspace API server authenticates the founder and then refuses every workspace route with
`no_membership`: no binary writes the founding `MemberActivated` that journal spec §9.12 and
identity spec §3.2 describe, and `append` refused every `Member*` type as `unknown_event_type`.

## Decision

1. **The journal admits `MemberActivated` alone.** `mandate-journal` registers `MemberActivated`
   at schema version 1 on the control stream, with rules 96, 98 to 100, 103, 105, and 106, tested
   against every `MemberActivated` case of the `membership` vectors. The other six `Member*` types
   stay `unknown_event_type` until E9-7 (#760) registers them. Admitting one type of seven only
   narrows what the journal accepts.
2. **The writer is the `control_services` system.** The grant's envelope is written by the same
   `system` actor that opens the control stream (the vectors' `founding` draft), in the stream's own
   environment, read from its `StreamOpened`. Its event id is DEC-290's derivation over the member
   at the head it is appended at. The CLI's private `Writer` gains `Founder`, which writes
   `MemberActivated` and nothing else.
3. **Only a new workspace is founded.** The grant commits only on a control stream that holds
   its `StreamOpened` and nothing else (`workspace_not_new` otherwise, `workspace_not_open` on an
   empty one). So its `independent_approval_required: false` is the workspace's effective policy
   (mandate spec §4.3: the platform and retail profiles do not require it, and no `PolicyChanged`
   or `WorkspaceProfileAssigned` can have preceded it). The spec only asks for the grant at
   creation; this reading is the strict one.
4. **One mapping from a stored envelope to a membership record.** `mandate_identity::control_entry`
   maps each of the seven `Member*` envelopes to its `MembershipRecord` and any other record to
   `ControlEntry::Other`. A membership record that does not map is an error, never skipped. The
   seal stays inside `mandate-identity`. The workspace store's adapters (A1's lookup among them)
   use this function rather than their own reading. `control_entry` is public, so any crate can
   build a `MembershipRecord` from a value. Only a holder of the seal can fold records
   (`MembershipFold::new` takes the `Seal`), so a record built this way grants nothing. A later
   slice may narrow the input to a stored event.
5. **The decision is made inside the writer's attempt.** `write_membership`'s loop becomes
   `write_decided`, which asks its caller what to commit from the view each attempt read, at the
   instant it stamps. `found_workspace` decides there, so a moved head re-runs the decision. Two
   bootstraps racing on one stream cannot both grant: the second re-reads and finds the first's
   grant. `write_membership` is unchanged in behaviour.
6. **Idempotent, for a Kubernetes Job.** When the stream's first membership record is this
   member's founding grant, written exactly as `founding_grant` writes it, a run commits nothing,
   prints that the workspace is already founded, and exits 0. Any other first membership record
   refuses it with `members_exist` and a non-zero exit. A fence, an unavailable journal, or an
   answer lost after the commit is read as a moved head, after a backoff. The re-read then finds a
   grant that did commit, so nothing is written twice.
7. **No more than the owner bundle.** The roles are `OWNER_BUNDLE` (workspace admin, operator,
   approver; identity spec §4.3), never chosen: the command takes no role. The member is a ULID
   the operator passes (`--member`), so a Job's retries name the same principal. The command never
   takes a name, an address, or an identity-provider subject. The sign-in method is required, with
   no default. `session_ref` is null, since the system writes without a session (rule 105). A
   re-run that names another method for the same member still reads as already founded: the
   method records how the founder signed in and grants nothing.
8. **The owner bundle is the retail one** (identity spec §3.2, §4.3). A workspace whose
   organization is not retail would need its founding roles and policy read from its profile.
   Item 3 refuses any workspace with a record before its founding grant, so no profile can have
   been assigned yet. That reading is owed with the organization story (E9-2).

A Kubernetes Job runs it as `mandate workspace found --workspace <id> --member <ULID> --method
oidc --journal <DSN without a password> --store <dir>`, with `PGPASSWORD` from the Job's secret.
It needs `restartPolicy: OnFailure` and no other state. The Helm chart (lane K1, #1432) owns the
manifest.

## Rationale

The founder needs one membership before any route serves. Writing it through the one writer
(DEC-646) keeps the order rule and the seal in one place. Deciding inside the attempt is what
makes "never two founders" hold under concurrency, not only sequentially.

## Alternatives considered

- **Check for members before calling `write_membership`.** Refused: two concurrent runs both pass
  the check, and the second's moved-head retry re-runs only the order guard, so it would commit a
  second founding grant.
- **Mint the member's ULID inside the command.** Refused: a Job retry would mint another one and
  then be refused, though the first run's grant committed.
- **Register all seven `Member*` types now.** That is E9-7's claim, and the founding grant needs
  only one.
