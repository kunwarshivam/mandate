| **Decided by** | `claude-code` (builder), under DEC-79, DEC-176 and DEC-921 |
| **Story or claim** | E7-26; claim [#1391](https://github.com/kunwarshivam/mandate/issues/1391); DEC-943 ("Not covered"); DEC-920, DEC-923, DEC-940; mandate spec §6.4 check 3, V-024; identity spec §3.2, §4.2, §4.3 |

`runtime_view` in `mandate-shell` handed the runtime `autonomy.approval.approvers` as written:
`role:approver`, `role:owner`, `role:workspace_admin` or `user:<id>`. Admission check 3 tests the
answer's `responder`, an opaque user id, for membership in that set, so it refused every grant
`not_an_approver` and no production build could admit one (DEC-943, Not covered). The builder's
size and classify refuse any view that differs from `runtime_view`'s own, so the resolution has
to live in `runtime_view`, where all three read it.

## Decision

1. **The source is the record DEC-923's check reads.** The run reads the workspace's members off
   the control stream it already folds for the confirmed version (`confirmed_version`): the
   workspace owner is the `user` of the mandate connection's latest `ConnectionEstablished` or
   `ConnectionRevoked` by `seq`, a revocation outranking an establishment at the same `seq`. This
   is the user `mandate approvals approve` takes as the workspace owner for a live grant
   (`live_scope`, DEC-923 item 1), so the CLI and the runtime name the same person. The owner
   exists only while that record is an establishment whose `user` is non-empty text.
2. **One member, holding every workspace role.** Phase 1 is a one-person workspace (DEC-505
   item 3): its one member is the owner, who holds workspace admin, operator and approver
   (identity spec §3.2's owner bootstrap, §4.3). So `role:approver`, `role:owner` and
   `role:workspace_admin` each resolve to the owner, `user:<id>` resolves only when `<id>` is the
   owner, and nothing else resolves. The resolved set is the owner or empty.
3. **What the run cannot read resolves no one.** No record for the connection, a revocation, a
   record whose `user` is absent, `null`, not text or empty, and any §9.12 membership record
   (`MemberInvited` … `MemberRemoved`) on the stream each give `Members::Unread`. A membership
   record means the workspace may have more than one member, whose roles the run does not fold
   (the identity crate's fold needs a seal the shell may not hold), so the one-member reading no
   longer holds. With `Unread` every reference resolves to no one.
4. **An empty set is handed, not refused at admission of the mandate.** `runtime_view` hands the
   runtime the resolved set, empty or not. An `auto` cycle never reads it and runs as before; an
   `ask`'s every grant is refused `not_an_approver` by check 3, the wait holds to the deadline,
   and nothing is sent (`AGENTS.md` rule 3). A paper run on V-001's paper default (no connection
   record, DEC-910 item 2) is in this case, exactly as before this decision.
5. **Plumbing.** `ConfirmedVersion::members` carries the reading from the fold to
   `Artifacts`, which hands it to `RunContext::members`; `runtime_view` calls
   `approvers::resolve` over it. `grant_marks.rs` drops its `Approvable`, `Sizes` and `Classifies`
   doubles and runs the production mandate and builder stages over a stream that records the
   founder's connection; its policy-supplying sink (gap 2, #1374) stays.

## Rationale

Check 3 needs user ids, and the only identity the founder's journal carries is the user who
recorded the connection; DEC-923 already made that user the approver for live grants, so reading
the same member keeps one notion of "the owner" across the CLI and the runtime. Admission stays
the runtime's alone (DEC-920): the shell only turns references into the ids the runtime compares,
and the runtime still checks the actor kind, delivery, hash, lateness, step-up and quorum.

Every reading admits no one DEC-923 does not already name, and each case the run cannot read
fails closed to the empty set, which is the merged behaviour.

## Alternatives considered

- **Resolve `role:approver` alone.** Rejected: identity spec §3.2 gives the one-person owner every
  workspace role, so leaving `role:owner` or `role:workspace_admin` unresolved would refuse a
  mandate V-024 accepts, and it adds no protection, since the set is the same one user.
- **Fold the §9.12 membership records with `mandate-identity`'s `MembershipFold`.** Rejected for
  this lane: building one needs the identity seal, which `xtask/layers.toml` keeps from the shell,
  and the founder's stream holds no membership record. Until a lane wires it, a stream with one
  resolves no one (item 3).
- **Refuse the run when the set is empty.** Rejected: it would stop `auto` cycles that never ask,
  a refusal with no risk to prevent; check 3 already refuses every grant.
- **Resolve in a wrapper stage around the mandate source.** Rejected: the builder's size and
  classify compare the view they are handed with `runtime_view`'s own, so a wrapper's view is
  refused, which is why the tests needed three doubles.
