# DEC-998: `ModelInvocationRecorded` is closed on the agent stream, and the model gateway's meter stream is added (journal spec v0.46)

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79, taken under DEC-176. It admits records that were impossible, picks the stricter of two folds the inference spec left open, and loosens no existing rule) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (builder, lane I1), under DEC-79 and DEC-176 |
| **Story or claim** | E15-8; DEC-432 items 11, 19, 20, 22; backlog E15-12 minors 7 and 8; claim [#1459](https://github.com/kunwarshivam/mandate/issues/1459); PR #1473 |

Before this decision, `ModelInvocationRecorded` was catalogued on the agent stream with no
registered payload, so `append` refused it as `unknown_schema`, and the meter stream the inference
spec proposes (§3.6) did not exist. No gateway call could be journaled before its output was used
(INF-10), and spend could not fold from the journal (INF-6, INF-7). The compiler's record was
already closed on the control stream (DEC-670). These are the readings this lane takes. (This
decision was first drafted as DEC-996, a number lane I3 had already reserved; it was renumbered
before merging.)

## Decision

1. **Agent-stream members.** Journal spec v0.46 §9.19 closes `ModelInvocationRecorded` on the
   agent stream at schema version 1 with §9.9's members (DEC-432 item 11), `purpose` limited to
   `research`, `llm_signal`, and `fast_signal`, and no draft members, then:
   - `guard_rule`, the guard rule a refused prompt broke, or `input_contract` (rule 148);
   - `reservation` (`ulid?`), the call's meter reservation, `null` exactly for a refusal or a cache
     hit (rule 149);
   - `observations` (`[ulid]`), the retrieved context as the run's `ObservationRecorded` event ids
     (agent harness spec §10.1 ask 3, DEC-432 item 22), strictly ascending (rule 150);
   - `verdicts`, one per candidate in the response, theses first and then invalidations, each with
     its `kind` and a result that fits it: `judged` or one of the agent harness spec §6.5 check
     reasons (rule 151). This is the "room for the candidates' verdicts": a harness refusal is
     journaled here, and a candidate handed on is journaled by admission (`ThesisProposed`) or by
     its invalidation record (E19-5, not yet catalogued). With it, the agent harness spec §6.2
     precondition for verdicts is met once `mandate-journal` registers the record; the invalidation
     precondition (E19-5) still stands.
2. **A refused prompt is not stored.** On the agent stream `prompt_ref` and `request_digest` are
   both `null` exactly when the outcome is `input_rejected`, and `guard_rule` names the rule (rule
   148). The guard refuses a prompt because it holds a credential, an account identifier, personal
   data, or another workspace's value (inference §8.3). Storing that prompt, or the canonical request
   that holds it, as an artifact would put the very content the guard caught into the journal
   (INF-8, INF-14). The control stream's §9.9 record requires `prompt_ref` for every outcome; until a
   version 2 of it takes the same reading, the compiler makes no gateway call (journal spec §9.9 and
   inference spec §3.6 now say so).
3. **The meter stream.** A new stream type, `meter:{workspace_id}`, owned by the workspace's one
   meter writer, fenced by epoch (DEC-432 item 20). It holds `StreamOpened`, `MeterReserved` (the
   maximum cost, appended before the first attempt), and `MeterSettled` (the actual cost, appended
   once). Rule 158 makes each call reserve once and settle at most once, against its own
   reservation, and rule 153 refuses a second `ModelInvocationRecorded` of one call on the agent
   stream, as the inference spec's idempotency says (§3.4). The range grammar (§9.13) and the
   anchors' stream types (§9.14) name the meter stream, so it can be verified and exported.
4. **What the meter counts** (E15-12 minor 7). The meter stream holds exactly the calls that could
   cost money: those admitted by every cap. A refusal, `meter_unavailable` included, and a cache
   hit have no meter record; they are on the caller's `ModelInvocationRecorded` alone. INF-6's "one
   metering record per call" is that `ModelInvocationRecorded`, and inference spec INF-6, its
   oracle, §7.1 and §7.4 now say so.
5. **One crash fold** (E15-12 minor 8). The inference spec said both that a crashed call's
   reservation "stays counted" (§7.3) and that it is "settled as spent at its maximum" (§9). The
   fold here is the first, written once: an open reservation counts at its maximum, forever, and
   nothing settles it later. Only a reservation's own settlement lowers spend, down to that call's
   cost; a crash, a restart, or a hand-over never does.
6. **Zero attempts** (rules 152 and 157). A call that reserved and then found its deadline already
   passed, or found no key in the vault, sends nothing and records `attempts` 0 with no response, no
   tokens, and no cost. On the agent stream that is the one exception to rule 74's `attempts` ≥ 1;
   the control stream's rule 74 is unchanged, and the meter settlement says the same.
7. **Periods.** A reservation carries its risk day, which the meter writer asserts from its own
   clock. Daily caps sum one risk day; the monthly cap of DEC-997 sums every risk day of one
   calendar month. No other period exists at this version, so the license's cycle allotment
   (inference spec §7.3) is not folded yet.
8. **No live call before the meter is durable.** Until `mandate-journal` registers §9.19,
   `mandate-gateway` keeps its meter in an in-process store behind the same fold. Such a store forgets
   open reservations on a crash, so it serves tests and recorded-response runs only; no live gateway
   call is made until the meter stream is journaled (and DEC-997 is Accepted).
9. **Checks left to the verifier.** Cross-stream agreement (the record's `reservation`, `call_id`,
   and cost against the meter stream), a settlement's cost against its price table, and an output
   event following an `ok` record (INF-10) are checked by no rule at append; a §11 verifier check is
   a follow-up.
10. **The version number.** v0.44 (#1450, rules 137 to 142) and v0.45 (#1472, §9.18, rules 143 to
    145) are taken by open changes, so this is v0.46, §9.19, rules 146 to 158. Whichever merges
    later merges `main`, keeps every entry, and renumbers only if an earlier one's numbers moved.
11. **Two PRs** (ES-22). The spec PR carries the spec text, the reference, the `model_gateway`
    vectors, the regenerated fixtures, and this file. `mandate-journal`'s registration of the four
    records and the meter stream type follows in its own code change, with tests written first.
12. **Two readings found in the gateway's review** (DEC-176: each only refuses more, adds no risk).
    a. A `200` whose reported model or provider is missing or differs from the pin is
    `identity_mismatch` whatever the rest of its shape, and its endpoint is benched (INF-2). The
    identity is read before the shape, so a substituting endpoint cannot pass as `schema_invalid`
    and keep serving. b. An attempt the provider billed, or may have, is never retried, even when
    it failed in transport: the reservation holds one attempt's maximum, so a second billed attempt
    could settle above it and past a cap (INF-6). Inference spec §3.4 says both.

## Follow-ups

- **The compiler's `input_rejected` prompt** (item 2): a §9.9 version 2 of the control-stream
  record with a nullable `prompt_ref` and `request_digest` under rule 148's reading.
- **`mandate-journal` registration** (item 11).
- **The §11 verifier checks** of item 9.

## Rationale

The members are the ones the inference spec and the agent harness spec already asked for; closing
them admits exactly the gateway's records. The meter stream is the inference spec's design, and the
readings picked (no meter record for a call that cannot cost money; an open reservation counted at
its maximum forever; a refused prompt stored nowhere) are the ones that can only refuse more calls or
keep less sensitive content.

## Alternatives considered

- **A separate verdict event.** The agent harness spec allows either. Rejected for now: the verdicts
  are a function of one response and are journaled in the same batch, and a second record would need
  its own cause rule. A later version can split it out.
- **Settle a crashed call at its maximum on restart.** Rejected (item 5): it needs a record written
  by whoever restarts, and a writer that crashed again before writing it would leave the same open
  reservation anyway.
- **Store the refused prompt with the secret redacted.** Rejected (item 2): redaction is a second
  parser of the very content the guard found; not storing it is simpler and loses nothing an
  auditor needs, since the outcome and the rule are recorded.
- **Keep `request_digest` as a bare digest for `input_rejected`.** Rejected: §4 makes a `ref` a stored
  object, and a digest-typed member used nowhere else would be a second shape for one member.
