# DEC-763: The gate view serves GateDecided as recorded and attributes the reason code to the first failing check

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The agent in lane L5, under DEC-79 and DEC-176: closes an unclosed contract by the reading that adds no risk (DEC-176 item 2) |
| **Story or claim** | E12-6 ([#756](https://github.com/kunwarshivam/mandate/issues/756)); E12-1 (#745), E12-2 (#747), E12-3 (#748); workspace API spec §4.8.1 |

## Decision

1. The gate view serves one `GateDecided`: its envelope ids and hash, `intent_id`, `verdict`,
   `reason_code`, `data_profile`, `risk_clock`, `checks` in recorded order with `inputs` and
   `computed`, `quotes_used`, `marks_used`, every `config_refs` entry, and `rule_set` from
   `config_refs.rule_set`.
2. Each check row carries a `reason_code`: the decision's code on the first check whose result is
   `fail`, `null` on every other. Results are the closed set `pass`, `fail`, `not_reached`; any
   other recorded value is served as `other` with the recorded text, never interpreted. A
   non-`allow` verdict with no `fail` check (a `hold` or `defer`) leaves every check's code `null`
   and `decisive_check` `null`, with the decision's code at the top.
3. Another event type in the workspace is 422 `invalid` (`not_a_gate_decision`); outside it, the
   404 of DEC-760.
4. Nothing is recomputed or looked up elsewhere.

## Rationale

`GateDecided`'s checks carry no per-check code, and trading spec §9.1 reports the first failing
check's code, so the attribution is exact and needs no new fact. Serving the record as is keeps the
view checkable against the body.

## Alternatives considered

- **No per-check code.** Rejected: J6 asks for the code beside the check that produced it.
- **404 for a non-gate event.** Rejected: the event is in the caller's workspace, and a 404 would
  read as "absent".
