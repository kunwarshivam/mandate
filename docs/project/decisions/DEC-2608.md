# DEC-2608: A merge train that tests approved pull requests together once, then lands each

| | |
|---|---|
| **Status** | Proposed |
| **Date** | 2026-10-18 (UTC) |
| **Decided by** | Proposed by the agent (lane CT); the coordinating agent accepts or declines it, as a reversible process and CI change (DEC-79). It changes no check and buys nothing |
| **Story or claim** | No story; CI throughput (lane CT). On 2026-10-18 about 24 approved pull requests' `ci` runs queued for over an hour and nothing merged |

This is a write-up for a decision, not yet a decision. Nothing is built until it is accepted, and
items marked **open** are settled first.

## What the runners measured

Every number below is from the Actions REST API for 2026-10-17 18:00 to 2026-10-18 20:50 UTC.

- **The account was full.** Its plan runs 40 jobs at once. At 20:47 UTC 38 were in progress,
  about 390 were queued, and `merge` jobs, which do about 12 seconds of work, had waited a median
  of 10 minutes (p90 17, max 31) behind them: Actions queues an account's jobs in arrival order
  with no priority.
- **A ready pull request ran `ci` 2.3 times on average.** 149 runs on 25 ready branches: 7 ran
  once, 12 twice, 6 three to seven times. Runs cancelled by a newer push used 2,251 of 6,477
  sampled `ci` runner-minutes (35 percent).
- **37 percent of runs (55 of 149) were on a "Merge main into …" head.** Most resolved a real
  conflict on a shared file (journal spec versions, backlog rows, `ci.yml`), because the pull
  request beside it had just landed.
- **Most of a run does not depend on its mutants.** One run is 18 to 26 jobs before mutants,
  about 70 runner-minutes: `select`, lint, three test shards, pending, Python, portable, rh-sim,
  `full-checks`, five cell jobs, six schema-mutant shards when selected, and the two aggregates.
  Mutants add one shard a mutant up to 192 (DEC-538), and were about a third of `ci`'s minutes.

So the cost is not one run a pull request but one run for every time main moves under it. With
twenty pull requests approved at once, each landing makes the next one stale, a conflict, a merge
of main, and a new full run.

## Proposal

1. **A batch.** When at least two pull requests pass every check `merge-approved.sh` makes except
   the `ci` one (open, not a draft, on `main`, labelled by an approver, one approved head equal to
   the current head, description written by an approver, mergeable), the `merge` workflow builds
   `train/<run id>` from main's tip by squashing each of them on in approval order. One that does
   not apply cleanly on the batch so far is left out of this batch, and keeps its own path. A
   batch takes at most `MERGE_TRAIN_SIZE` pull requests (start at 6) and at most 192 planned
   mutants together, so no shard carries more than DEC-498 item 1 allows; the plan is computed
   on the batch's diff before it is dispatched.
2. **One `ci` run on the batch.** The workflow dispatches `ci` on `train/<run id>`. Events that a
   workflow's own `GITHUB_TOKEN` creates start no workflow, but `workflow_dispatch` does. A
   dispatched run already resolves its diff base as the merge base with `origin/main`
   (`choose_base`, `.github/scripts/base-ref.sh`), which is main's tip the batch was built on, so
   `select`, the mutation plan and every diff-scoped job judge exactly the batch's diff. Every job
   and every required check runs as on a pull request: nothing is skipped for a batch.
3. **Landing.** When that run's `fast` and `full` both ran and passed, each pull request is
   squash-merged in batch order with `sha` set to its approved head, as today. Before each, the
   gate re-reads everything as now and also requires that main's tip is the batch's base plus
   the batch's own earlier members, and after the last, that main's tree equals the batch
   branch's tree. Any mismatch stops the train; the remaining pull requests keep their own path.
4. **Red batch: bisect.** A red batch of one is that pull request's own failure, reported on it as
   today. A red batch of more splits in halves, each dispatched as a batch on the same base, until
   the failing pull request is isolated; the rest land. A batch never lands on a run that did not
   test it.
5. **`merge-approved.sh` accepts one more kind of green.** Besides the latest `pull_request` run
   on the head, it accepts a green `workflow_dispatch` run on a `train/` branch whose recorded
   members include this pull request at its approved head, and whose base is main's tip at landing
   minus the batch's own earlier members. Every other condition stays.
6. **Approved pull requests stop paying for main moving under them.** A pull request in a batch
   needs no merge of main to land, because the batch is built on main's tip. One left out of a
   batch for a conflict is the only one that needs a merge of main.

## Open (settled before building)

- **Does an approved pull request still run its own `ci` on `ready_for_review`?** If it does, the
  train adds a run rather than replacing one, and only items 6 and the conflict cases save
  anything. If the coordinator approves while the pull request is a draft and the train marks it
  ready only as it lands, the per-PR run is replaced by the batch run, and the run that marking it
  ready starts must be one the train does not wait for.
- **The spec guard** reads the pull request's description for DEC citations (`MANDATE_PR_BODY`).
  A batch run has no description; the train passes the members' descriptions, joined, or the guard
  runs per member in the train job.
- **Fairness.** A pull request that keeps failing in batches must not hold others back; after one
  isolated failure it leaves the train until its head changes.
- **The coordinator's approval stays per pull request and bound to its head** (DEC-175). Nothing
  here lets a batch land a head nobody approved.

## Expected effect

With 24 approved pull requests and batches of 6 that pass: 4 runs of about 70 non-mutant
runner-minutes each instead of 24 to 55 (one to 2.3 a pull request), the same mutants in total,
and no merge-of-main runs for the members. A red batch of 6 costs 2 to 3 more runs to bisect.
These are estimates from the averages above, not measurements.

## Alternatives considered

- **GitHub's merge queue.** It needs a `merge_group` trigger on every required workflow and
  branch protection that requires those checks; this repository's ruleset requires none and
  `merge-approved.sh` is the gate (DEC-175). It also gives no control over the 192-mutant limit.
- **Require branches to be up to date.** Declined: every landing would make every other approved
  pull request re-run `ci`, the cost this proposal removes.
- **More concurrency (larger runners or a higher plan).** Spending is the founder's (DEC-79).
