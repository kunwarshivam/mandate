## Context

DEC-2044 moved staging's cluster from `nyc3`, which refused it for capacity, to `nyc1`. The next
staging plan (run 39213327884) stopped at DEC-2044's own precondition: `DigitalOcean does not offer
s-2vcpu-4gb in nyc1; it offers it in: ams3, blr1, fra1, lon1, sfo2, sgp1, syd1, tor1`. Neither New
York region offers the size now. Every other preflight line, Access included, was ready.

## Decision

1. **Staging's cluster and VPC run in `tor1`**, which offers `s-2vcpu-4gb` at the same 24 USD.
   The estimate is unchanged at **57 USD a month** (two nodes at 24 USD, 5 USD of Spaces, 40 GB of
   volumes at 0.10 USD). That is under staging's 65 USD share and DEC-2605's 150 USD cap. The
   state bucket stays in `nyc3` (DEC-2044 item 2), and production stays in `nyc3`.
   - The next apply replaces only the VPC that the first apply made in `nyc3`, since a VPC's region
     cannot change. It is empty, because the cluster was never created. The tag and firewall have
     no region. Nothing else is destroyed.
   - The bootstrap's kubeconfig context is `do-tor1-mandate-staging`. A test checks it against
     each root's region.
2. **A size missing from a region names the alternatives.** The `budget` module also lists the
   region's sizes. When the node size is not offered there, the plan's error names the regions
   that offer it, and the region's available sizes with the same vCPUs and memory, with their
   monthly prices. So a later shortage shows its own way out, by region or by size. Momentary
   capacity, as in `nyc3`'s 422, still shows only when the cluster is created.

## Alternatives considered

- **`s-2vcpu-4gb-amd` or `-intel` in New York:** no agent can read which of them `nyc1` or `nyc3`
  offers today, and they cost more (28 USD or more a node, which would use the whole 65 USD share).
  Item 2's message now names them if the founder prefers New York later.
- **A region outside DEC-995's answer, such as `sfo2`:** the founder was not asked about it.
