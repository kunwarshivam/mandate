|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The L3 builder agent under DEC-79 (reversible engineering readings) and DEC-176 (each item takes the reading that adds no risk), at the L3 lane lead's direction; reviewed by the L2 lane, which owns the API |
| **Story or claim** | E8-14, slice S8e, claim [#753](https://github.com/kunwarshivam/mandate/issues/753); [workspace API spec](../../specs/workspace-api.md) §4.10, §5.7; [notifications spec](../../specs/notifications.md) §4.6, NT-2 |

## Decision

1. **Routes.** `PUT /me/channels/web_push`, `POST /me/channels/web_push/{address_ref}/remove`
   (a POST, so no intermediary drops the step-up evidence; a missing body is `step_up_required`),
   and `GET /me/channels/web_push`, for the authenticated member's own addresses only. The endpoint
   and keys go to the vault; the journal, logs, responses, and problem documents carry only
   `address_ref`, the `added` event's own id (API-11's shape, NT-2). A member's endpoints are
   de-duplicated by a keyed hash held only in the vault, and a member holds at most 10 addresses
   (`address_limit`). A foreign or unknown `address_ref` is an ordinary 404 (API-9, NT-10).
2. **Step-up on both adding and removing.** A stolen session could add an attacker's browser to
   watch a member's notices, or remove the member's own address to silence the safety notices that
   tell them about a new passkey, a new device, or a role grant before the attacker acts. Both are
   bound to their own digest under a new step-up kind, `notification_address`. The conservative
   reading: it costs a member one ceremony when they turn on push in a new browser.
3. **Authorization.** The identity spec §4.2 row "Add or remove one's own notification address (a
   push subscription; later an email or chat address)": **S** for both adding and removing, `self`
   (principal scope, a full user session) for the org owner, org admin, billing admin, workspace
   admin, operator, approver, viewer and auditor, and none for a client, a service account, the host CLI, or a platform operator. Its
   step-up kind is `notification_address` (identity spec ID-4). Both were added by the identity
   spec's owner in identity spec v0.3 ([#811](https://github.com/kunwarshivam/mandate/pull/811),
   DEC-816 item 2), with a second row for the listing, "List one's own notification addresses
   (opaque references only)", `self` without **S**. #811 also prints both rows in this spec's §3.7
   and the kind in §3.6.
4. **Not an API-7 operation.** Removing an address is not risk reduction: it removes a member's
   out-of-band signal. Both routes may be refused like any other change (rate limit, frozen control
   stream, missing step-up).
5. **The record and its order.** One control-stream batch: `NotificationAddressChanged`
   `{member, channel, action: added | removed, address_ref}` with the step-up evidence, and its
   `OwnerAlertSent` (`notification_address_changed`). `address_ref` is in the event's `pii_refs`
   (journal spec §6.4); the step-up digest's inputs are never journaled. Setting writes the vault
   first, put-if-absent under the derived `address_ref`, then appends: the one exception to API-3's
   order, safe because an entry with no committed `added` event is never read. Removing appends
   first and deletes the vault entry only after the last send to it. Workspace API spec §5.7 gives
   the outcome of a crash at each step. The journal spec row is
   [#805](https://github.com/kunwarshivam/mandate/pull/805) (DEC-720).
6. **A safety notice for the change** (the L3 lane lead accepted it as a tightening: it only adds a
   safety notice). Notifications spec §3.2 gains `notification_address_changed`: cause
   `NotificationAddressChanged` with its `OwnerAlertSent` in the same control-stream batch, class
   `safety`, text key `account_changed`, sent to the member on every push channel they hold after
   the change (an address just added included), once more to the address just removed, and in the
   pull channels. A member whose address someone else removed learns of it on that last send, the
   single exception to "send only where the last event is `added`" (notifications spec §5.1). It is
   not `channel_lost` (§5.6).

## Rationale

The address is the one piece of personal data the push path needs, and the only one a member
supplies to it. Keeping it in the vault and the journal record opaque keeps NT-2 true by
construction; requiring step-up both ways closes the takeover path that adding or silencing a
channel opens.

## Alternatives considered

- **Step-up only for removing.** Rejected: an added attacker browser receives every notice the
  member does, which tells the attacker when the member is being asked to approve.
- **The address in the journal event.** Rejected: NT-2 keeps addresses out of the journal.
- **A route for an admin to set another member's address.** Rejected: an address is the member's
  own; an admin can deactivate a member, which ends their notices.
