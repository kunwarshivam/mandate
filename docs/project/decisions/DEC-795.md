| **Story or claim** | E8-14, slice S8e, claim [#753](https://github.com/kunwarshivam/mandate/issues/753); [workspace API spec](../../specs/workspace-api.md) §4.10, §5.7; [notifications spec](../../specs/notifications.md) §4.6, NT-2 |

## Decision

1. **Routes.** `PUT /me/channels/web_push`, `DELETE /me/channels/web_push/{address_ref}`, and
   `GET /me/channels/web_push`, for the authenticated member's own addresses only. The endpoint
   and keys go straight to the vault; the journal, logs, responses, and problem documents carry only
   a random `address_ref` (API-11's shape, NT-2).
2. **Step-up on both adding and removing.** A stolen session could add an attacker's browser to
   watch a member's notices, or remove the member's own address to silence the safety notices that
   tell them about a new passkey, a new device, or a role grant before the attacker acts. Both are
   bound to their own digest under a new step-up kind, `notification_address`. The conservative
   reading: it costs a member one ceremony when they turn on push in a new browser.
3. **Authorization.** The identity spec §4.2 row "Add or remove one's own notification address (a
   push subscription; later an email or chat address)": **S** for both adding and removing, `own`
   for the org owner, org admin, billing admin, workspace admin, operator, approver, viewer and
   auditor, and none for a client, a service account, the host CLI, or a platform operator. Its
   step-up kind is `notification_address` (identity spec ID-4). Both were added by the identity
   spec's owner in identity spec v0.3 ([#811](https://github.com/kunwarshivam/mandate/pull/811),
   DEC-816 item 2), which also prints the row in this spec's §3.7 and the kind in §3.6.
4. **Not an API-7 operation.** Removing an address is not risk reduction: it removes a member's
   out-of-band signal. Both routes may be refused like any other change (rate limit, frozen control
   stream, missing step-up).
5. **The record.** `NotificationAddressChanged` `{member, channel, action: added | removed,
   address_ref}` on the control stream, written by workspace services after the vault write and
   before the answer; a failed append deletes the vault entry again, and the dispatcher sends only to
   addresses whose last event is `added`. `address_ref` is listed in the envelope's `pii_refs`
   (journal spec §6.4). Its journal spec row goes in the journal spec change that closes the
   notification records (#805, DEC-720).
6. **A safety notice for the change** (the L3 lane lead accepted it as a tightening: it only adds a
   safety notice). Notifications spec §3.2 gains `notification_address_changed`: cause
   `NotificationAddressChanged` with its `OwnerAlertSent` in the same control-stream batch, class
   `safety`, text key `account_changed`, sent to the member on every push channel they hold after
   the change, once more to the address just removed, and in the pull channels. A member whose
   address someone else removed learns of it on that last send. It is not `channel_lost` (§5.6).

## Rationale

The address is the one piece of personal data the push path needs, and the only one a member
supplies to it. Keeping it in the vault and the journal record opaque keeps NT-2 true by
construction; requiring step-up both ways closes the takeover path that adding or silencing a
channel opens.

## Alternatives considered

- **Step-up only for removing.** Rejected: an added attacker browser receives every notice the
  member does, which tells the attacker when the member is being asked to approve.
- **The address in the journal event.** Rejected: NT-2 keeps addresses out of the journal.
- **A route for an admin to set another member's address.** Rejected: an address is the member's
  own; an admin can deactivate a member, which ends their notices.
