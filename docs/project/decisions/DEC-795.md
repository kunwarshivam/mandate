|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The L3 builder agent under DEC-79 (reversible engineering readings) and DEC-176 (each item takes the reading that adds no risk), at the L3 lane lead's direction; reviewed by the L2 lane, which owns the API |
| **Story or claim** | E8-14, slice S8e, claim [#753](https://github.com/kunwarshivam/mandate/issues/753); [workspace API spec](../../specs/workspace-api.md) §4.10, §5.7; [notifications spec](../../specs/notifications.md) §4.6, NT-2 |

## Decision

1. **Routes.** `PUT /me/channels/web_push`, `POST /me/channels/web_push/{address_ref}/remove`
   (a POST, so no intermediary drops the step-up evidence; a missing body is `step_up_required`),
   and `GET /me/channels/web_push`, for the authenticated member's own addresses only. The endpoint
   and keys go to the vault; the journal, logs, metrics, responses, and problem documents carry only
   `address_ref`, the `added` event's derived id (API-11's shape, NT-2). **Active** addresses, those
   whose last event is `added`, are derived from the journal: only they match an endpoint already
   held (`200`, no event), count toward the limit of 10 (`address_limit`), and are listed. The vault
   answers the endpoint question itself from a keyed hash it never exports. A foreign or unknown
   `address_ref` is an ordinary 404 (API-9, NT-10).
2. **Step-up on both adding and removing.** A stolen session could add an attacker's browser to
   watch a member's notices, or remove the member's own address to silence the safety notices that
   tell them about a new passkey, a new device, or a role grant before the attacker acts. Both are
   bound to their own digest under a new step-up kind, `notification_address`. The conservative
   reading: it costs a member one ceremony when they turn on push in a new browser.
3. **Authorization.** Identity spec §4.2's rows "Add or remove one's own notification address (a
   push subscription; later an email or chat address)", **S** for both adding and removing, and
   "List one's own notification addresses (opaque references only)", without **S**: each `own` in
   the five workspace columns (workspace admin, operator, approver, viewer, auditor), at the
   workspace's scope through a membership that reaches it, and blank for every org role, a client,
   a service account, the host CLI, and a platform operator. The step-up kind is
   `notification_address` (identity spec ID-4). The identity spec's owner added them in
   [#811](https://github.com/kunwarshivam/mandate/pull/811) (DEC-816 item 2), which also prints the
   rows in this spec's §3.7 and the kind in §3.6. Addresses are per workspace, in its own vault
   namespace (identity spec §9.1).
4. **Not an API-7 operation.** Removing an address is not risk reduction: it removes a member's
   out-of-band signal. Both routes may be refused like any other change (rate limit, frozen control
   stream, missing step-up).
5. **The record and its order.** One control-stream batch: `NotificationAddressChanged`
   `{member, channel, action: added | removed, address_ref}` with the step-up evidence, and its
   `OwnerAlertSent` (`notification_address_changed`). `address_ref` is in the event's `pii_refs`
   (journal spec §6.4); the step-up digest's inputs are never journaled.
   - Both routes look the derived event id up first, so a retry after a lost answer returns it
     without judging step-up again; a same-key retry with a different body is
     `idempotency_conflict`.
   - Both append with the control stream's expected head (journal spec §5.1), re-reading the
     member's active set on `HeadMismatch`, so duplicates, an eleventh address, and a double
     removal cannot commit.
   - Setting writes the vault first, put-if-absent and bound to the request digest, appends, then
     puts the entry again; a failed second put answers `unknown`, retryable. This is the one
     exception to API-3's order, safe because an inert entry is never read. A sweep deletes an
     entry with no event once it is more than 24 hours old, by a conditional delete; an active
     address whose entry is still missing is recorded `address_missing`, which raises
     `channel_lost` without marking it unreachable.
   - A PUT of the endpoint of an active but unreachable address replaces it: `removed` for the old
     reference and `added` for the new one in one batch, with one notice.
   - Removing appends first and deletes the entry only after the last send to it.
   - A deactivation or removal that ends a member's membership in a workspace appends `removed` for
     each of their active addresses there inside its own commit, with the authenticated principal
     as actor (DEC-642), `null` step-up evidence (allowed only for a `removed` in such a commit), and
     no notice: identity spec §5.2 step 2 (#811, DEC-816 item 7).

   Workspace API spec §5.7 gives the outcome of a crash at each step. The journal row is owed by
   the journal spec change that closes the notification records; the routes stay Planned until it
   merges.
6. **A safety notice for the change** (the L3 lane lead accepted it as a tightening: it only adds a
   safety notice). Notifications spec §3.2 gains `notification_address_changed`: cause
   `NotificationAddressChanged` with its `OwnerAlertSent` in the same control-stream batch, class
   `safety`, text key `account_changed`, sent to the member on every push channel they hold after
   the change (an address just added included), once more to the address just removed, and in the
   pull channels. A member whose address someone else removed learns of it on that last send, the
   single exception to "send only where the last event is `added`" (notifications spec §5.1). It is
   not `channel_lost` (§5.6).

7. **Two failure labels added to the closed reason enum** (an amendment to DEC-700 item 8's
   closed `reason` set, a tightening: each only labels a failure that was otherwise unnamed).
   - `address_missing`: an active address whose vault entry is gone. The attempt is a terminal
     `failed`; it does not mark the address `unreachable`; it raises `channel_lost` once per address
     until the member sets it again or removes it. Setting the same endpoint again puts the entry
     back.
   - `retry_window_ended`: the one last send to a removed address whose entry is already gone is
     `abandoned` with this reason, not `address_missing`.

   The journal rows are owed by the L3 lane's journal follow-up for the notification records.

## Rationale

The address is the one piece of personal data the push path needs, and the only one a member
supplies to it. Keeping it in the vault and the journal record opaque keeps NT-2 true by
construction; requiring step-up both ways closes the takeover path that adding or silencing a
channel opens.

## Alternatives considered

- **Step-up only for removing.** Rejected: an added attacker browser receives every notice the
  member does, which tells the attacker when the member is being asked to approve.
- **The address in the journal event.** Rejected: NT-2 keeps addresses out of the journal.
- **A route for an admin to set another member's address.** Rejected: an address is the member's
  own; an admin can deactivate a member, which ends their notices.
