|---|---|
| **Status** | Accepted (agent: reversible engineering readings under DEC-79, each under DEC-176 — each refuses more or fills a gap by the reading that adds no risk; none touches live money, spending, legal text or a safety rule) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The R14/R15 builder (Claude Code), under DEC-79 and DEC-176; one PR with its tests first (DEC-921) |
| **Story or claim** | E7-26; the [R0 rehearsal](../tasks/r0-rehearsal.md)'s R14 and R15; claim #1428 |

The placing run refused `the runtime refused its input: ConnectionChecked is not interpreted
until the story that writes it` (`crates/mandate-runtime/src/state.rs`, `fold`'s catch-all),
because the connect check DEC-946 journals is the account stream's second record and the
runtime's fold listed no such type (R14). The executor's fold refused it too (`E7-2`, its
`owner_elsewhere`), one step later on the same replay. The dry run on the rehearsal's Monday clock
decided nothing because the model's output was past its age (R15). These are the readings that
close them.

## Decision

1. **What the runtime folds.** `ConnectionChecked` (journal spec §9.8) is interpreted: the latest
   one of the deployment's own connection (`connection_id` equal to the deployment's) is held as
   whether every listed check passed and its risk clock. A check of another connection is read
   and validated but governs nothing here: another connection's failure says nothing of this
   one, and its pass must never clear this one's failure.
2. **A failed check refuses openings.** While the latest own check has any result `failed`, an
   `open` or `increase` is judged in the runtime's dry run as `deny`, reason `account_restricted`,
   before the gate is asked. That is the outcome connections spec §8.1 gives a later check's
   failure (`suspended`, agents `exits_only`) and trading spec §7.3 row 5 the gate's reason for
   it. The executor's own halt (`AccountRestrictionChanged`, then `AgentModeApplied`, committed
   before the failed check, journal spec §9.8) is unchanged; this is the runtime refusing the
   same openings from the record itself, so neither depends on the other arriving first. A
   connect-time failure (`connect`, `reconnect`, `reauthorize`) refuses the connection and moves
   no state (DEC-674), and reading it here only refuses more. The reason is the gate's existing
   code, so no new reason enters trading spec §9.1.
3. **A stale check refuses openings.** A passing check covers an opening while
   `now < at + 86 400` risk-clock seconds (`CONNECTION_CHECK_COVERS_S`, one day: the period of
   the daily check, connections spec §8.1 and §9.2). From then on the opening is refused as in
   item 2 until a newer passing check is folded. `now` is the evaluation's tick, or for a grant
   the second the response is processed at. The spec states no bound; any bound only refuses
   more, so DEC-176 lets an agent take it. Consequence for the founder's live run: an
   opening more than a day after the last check needs a fresh one; a second
   `mandate-paper --connect-check` appends only its `ConnectionChecked` (DEC-946 item 6) and
   renews it. The executor's `executor_start` and `daily` checks are not written yet (E7-17).
4. **Never an exit** (`AGENTS.md` rule 13). Items 2 and 3 read only proposals whose purpose adds
   risk (`open`, `increase`). A risk exit, an owner exit, a discretionary exit, a protective order
   and a kill switch's flatten are judged as before, whatever the checks say; the restart's
   re-hand is unchanged. The same dry run governs a grant's re-validation (mandate spec §6.4 check
   11): a grant read after a failed or stale check is skipped `dry_run` `deny`,
   `account_restricted`, and nothing is handed.
5. **What still refuses.** A `ConnectionChecked` whose shape is outside journal spec §9.8 refuses
   the fold `non_canonical_payload` rather than guessing (DEC-85): no `connection_id`, an unknown
   `occasion`, `results` missing or not a list, an item that is not an object or names an unknown
   check (`uniqueness` included: it is the control services', never the executor's) or an
   unknown result, a failure with no reason or a pass with one (rule 58), a list missing `scope`,
   `environment` or `account` (rule 57; `contract` may be absent, since only an MCP connection
   lists it and the record does not say which it is), and a risk clock that is neither the
   canonical integer nor a §4.7 timestamp on the whole second. `ConnectionStateChanged` and
   `ConnectionCredentialRefreshed`, which nothing writes yet, and every unknown type still refuse
   `not_interpreted`. In the executor, `ConnectionChecked` folds as a record only: its risk clock
   is read like every account event's, and the halt it may follow is the executor's own earlier
   records.
6. **No absent check is a failure.** With no `ConnectionChecked` of its connection folded, the
   runtime leaves openings to the other gates, as before: Phase 1 paper connections journal none,
   and a live connection cannot be recorded without a passing connect check (journal spec §9.8
   rule 68, `connection record`'s `check_missing`). `FOLD_VERSION` stays 1: no golden journal
   holds a `ConnectionChecked`, so no committed fold output changes.
7. **R15: the age rule is unchanged, and on a Monday it decides nothing.** The model's output is
   the moving-average crossover's opinion at the close of the last completed regular session
   before the run clock (`mandate_modelhost::evaluate`), and is fresh only while
   `now − as_of ≤ max_output_age_s` and `now < expires_at` (mandate spec §8.1; the builder's
   check). The mandate schema caps `max_output_age_s` at 86 400. So on Monday 2026-10-19 at
   15:00 UTC the latest possible output is Friday's 20:00 UTC close, 67 hours old, and no script
   change can produce an output that is fresh at that clock without relaxing the rule: the
   script already writes the bars at the sim clock, and the model's output follows the bars and
   the calendar. The dry run on a Monday (or the day after a holiday) correctly decides nothing.
   The script now expects the spec's answer on a day the output is fresh: the R0 mandate asks
   for every opening (DEC-529), and a run without `--place-one-order` never asks, so 2l passes
   when it stops at `Classify: the proposal classified ask` with nothing sent. The rehearsal is
   run on Monday as asked, and also on Tuesday 2026-10-20 at 15:00 UTC, where the output is fresh,
   to reach the steps behind it. For the founder: a live order on a Monday cannot come from a
   daily-close model under the current schema; that is a limit on the envelope, not a defect, and
   widening `max_output_age_s` past a day would be a spec change for the founder to make.

## Rationale

The record is now on every live account stream, so refusing it stops every live replay. Folding it
as inert would discard a fact that, by the specs, halts openings; folding it into the dry run makes
the runtime refuse the same openings the executor's restriction refuses, from the journal alone and
deterministically on replay, without touching the mode machine (no new `AgentModeChanged`), so no
committed journal changes. Reading only risk-adding purposes keeps rule 13 by construction.

## Alternatives considered

- **A local hold in the effective mode** (`exits_only` while the check fails or is stale): it would
  journal `AgentModeChanged` copies the spec gives to the executor's `AgentModeApplied`, and a
  staleness hold read against the replayed risk clock could differ from the live one at a restart.
- **Inert, as the other record-only types**: simplest, but leaves a failed check with no effect in
  the runtime until the executor's restriction arrives.
- **A new reason code** (`connection_check_failed`, `connection_check_stale`): clearer, but a new
  gate reason is a trading spec §9.1 change (ES-22); `account_restricted` is already the spec's
  outcome for an unusable connection.
- **For R15, a rehearsal mandate with a longer `max_output_age_s`**: the schema refuses above a
  day, and it would be relaxing the age bound the dispatch rules out.
