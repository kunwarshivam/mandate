## Context

`POST /approvals/{id}/responses` records a Skip and refuses every `approved`, `step_up_required`
without evidence and `step_up_missing` with it, until step-up is bound (DEC-1007 item 10).
DEC-2104 decides how a paper grant made in the web app is confirmed in the CLI and how the API
verifies it, and the server's port now binds that verifier. It leaves open what the API checks
before the port, what it commits, and the grants it does not yet serve. The CLI's `mandate
approvals approve` commits the same grant from the host, and the runtime judges both alike.

## Decision

1. **The API judges no more than §5.2 says.** No new problem code is added. The first failing
   check answers, after the session, CSRF mark, key and body checks: an unknown approval (404),
   the matrix row, the approvers (item 7), a delegation (item 4), `live` (item 6), then the
   step-up checks.
   - An approval no agent stream requested is 404 `not_found`, as for a Skip.
   - A `content_hash` other than the journaled request's fails DEC-2104 item 6, since the CLI
     confirmed the journal's hash, and is `step_up_mismatch`.
   - An approval already answered or past its deadline, with a confirmation that verifies, is
     recorded and answers `202`. The runtime refuses it (checks 1 to 12, DEC-155 item 5), as it
     refuses the CLI's.
2. **The commit is the CLI's.** A grant that verifies commits one `ApprovalResponseSubmitted` on the
   control stream whose payload equals what `mandate approvals approve` writes for the same
   approval, content hash, responder, and evidence. The `responder` is the principal's ULID
   (DEC-2104 item 4). The envelope differs only where the API's writes always differ: the event id
   is the §3.4 key's, and the actor is the session's.
3. **The evidence as §9.7 types it.** `ApprovalResponseSubmitted.step_up.authenticated_at` is an
   integer risk-clock second (journal spec §9.7). The presented evidence carries the challenge's
   `issued_at` at the server's full precision, which DEC-2104 item 6 compares exactly. The API
   journals it truncated down to the whole second, never later than the instant verified, so the
   runtime's 300 s window can only shrink: it fails closed. A repeat (§3.4 step 1) compares the
   truncated form.
4. **No delegation yet.** A grant with a non-null `delegation` is §5.3's batch, which is not served.
   It is `invalid` at `/delegation` (422), after the body is decoded and before any step-up check,
   and commits nothing. It adds no risk: it refuses a risk-increasing call.
5. **Through the port.** The grant judges its evidence with the port's `asserted` method, kind
   `approve` and digest the content hash, with no assertion, so the passkey half adds only its wire
   member.
6. **Scope.** `paper` only; `live` stays `live_unavailable`. A passkey grant, with
   `step_up_assertion` on `commands/approval-response-request` and `StepUpAsserted` in its batch,
   follows DEC-2128's shape in its own change.
7. **Approvers, refused at the API (the founder, 2026-10-26).** As §5.2 says, the API refuses a
   grant from a user the approval's mandate does not list in `autonomy.approval.approvers`:
   `forbidden` (403), committing nothing. The mandate is the version the request binds
   (`trigger.mandate_version` in its content), read from the artifact store. A reference
   `user:<id>` lists the principal whose id it names; `role:<role>` lists every principal the
   workspace's membership fold (§9.12, the one the matrix check reads) gives that role. A version
   that is not stored, does not parse as a mandate, or a membership read that fails, refuses the
   grant `journal_unavailable`: never a pass. The runtime keeps its own check 3
   (`not_an_approver`), so two independent gates judge it. DEC-1007 item 10's departure stays a
   Skip's alone.

## Rationale

- Item 7 is the founder's: an approval is the platform's one human gate on a risk-increasing
  order, so the API refuses a non-approver itself rather than leaving the runtime the only gate.
- Item 1 keeps the API a convenience in front of the runtime: refusing locally what only the
  runtime decides would need new codes and a second judgement that could disagree with it.
- Items 2 and 3 make a grant made in the web app indistinguishable in the journal from the CLI's,
  so the runtime and any audit read one shape.
- Item 4 refuses rather than half-serves a batch whose rules belong to another story.

## Alternatives considered

- **Refusing a late or answered grant in the API, as `approvals approve` does.** Rejected for item
  1's reason.
- **Journaling the wire timestamp as presented.** Rejected: it breaks §9.7's closed type.
