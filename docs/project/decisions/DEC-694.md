## Decision

1. **Two new modules in `mandate-connections`: `revoke` and `manager`.**
   - `revoke` holds the ordinary and compromised revoke of workspace API §4.5 and §5.6.
   - `manager` holds the connection manager's side of connect: the pending record of connections
     §5.2 step 1, check 4, and the establishment or the teardown of step 6.
   - Each takes the facts it decides on as inputs and returns a typed **plan**: either an ordered
     list of effects, or a refusal with its reason. It never returns both.
   - Each plan's inputs make "the fold cannot answer" a value of its own type, so a caller cannot
     pass it as "no positions" or "stopped" ([DEC-693](DEC-693.md) items 6 to 8).
   - The crate stays pure (DEC-691 item 1): no clock, randomness, I/O, or async. No plan or effect
     carries a secret (rule 7).
2. **`mandate-api-server` maps plans to journal drafts.**
   - It turns each effect into its event in order: for example, the compromised revoke's
     `OwnerCommandIssued` (`kill_switch`, connection scope) and then `ConnectionRevoked`
     (`compromised`), in one batch.
   - It appends them, and it reports a refusal without appending.
   - The order, the members, and the refusals are tested in `mandate-connections`. The mapping and
     the append are tested in the server.
3. **`mandate-connections` takes no dependency on `mandate-journal`.** Its layering entry
   (`xtask/layers.toml`) is unchanged. The plan types name effects in the crate's own terms, and
   only the server knows the event types.
4. **Q4: the pending connection is journaled, as connections §5.2 step 1 says.**
   - Connections §5.2 step 1 and §9.1 say the connection manager creates a pending record
     (`connecting`) at start. `crates/mandate-connections/src/record.rs` keeps no record for
     `connecting`. The coordinator ruled to follow the spec: the code is tightened toward it.
   - **Journal spec §9.8 has no event for it.** §9.8 says the manager assigns `connection_id` and
     `account_ref` when the connect starts, but nothing records that. The first control-stream
     record of a connect is `ConnectionEstablished` (version 2) or `ConnectionRefused`. The
     executor's `StreamOpened` and `ConnectionChecked` come on the account stream only once a token
     is stored. §9.8 also says "`connecting` leaves no record but a `ConnectionRefused`".
   - **A journal-spec entry is owed.** It joins the coordinator's journal-spec queue behind #1009,
     #1009's code PR, L2's `connections.py` tightening, and L1's §9.12. It must:
     - add a control-stream event for the pending connection, with its `connection_id`,
       `account_ref`, broker, environment, user, and step-up. It carries no credential, account
       number, or fingerprint (§9.8's preamble);
     - be the event that commits in the transaction where the connect's step-up challenge is marked
       used. Identity §7.2 step 5 requires one, and today the start commits no event;
     - reconcile the sentences it contradicts: §9.8's "`connecting` leaves no record but a
       `ConnectionRefused`" and "nothing else is kept of a refused connect", and connections
       §9.1's "no record kept beyond the refusal event";
     - add a stream rule that a connect's `ConnectionEstablished` or `ConnectionRefused` (occasion
       `connect`) follows that connection's pending record.
   - **The `manager` slice journals the pending record once that entry lands.** It also gives
     `record.rs` a `connecting` record. Until then no slice journals an unregistered event, and the
     start route is not served.

## Rationale

DEC-691 put the connect core in a pure crate so every rule is testable without a network, and kept
the adapter thin. Revoke and connect management are rules of the same kind: which events, in what
order, refused when. Plans keep them pure and keep the journal's event types in one place, the
server, without a second layer edge for a safety-critical crate. Journaling the pending record
closes a gap where the start of a connect, and the step-up spent on it, left nothing in the journal
(rule 5: journal before acting).

## Alternatives considered

- **Put revoke and manager logic in `mandate-api-server`.** Rejected: that crate is async and
  impure (DEC-691), so the safety rules would be tested only through HTTP.
- **Have `mandate-connections` build journal drafts itself.** Rejected: it adds a dependency on
  `mandate-journal` to a pure layer-6 crate, and spreads event construction over two crates.
- **Keep no pending record, and change the spec to match the code.** Rejected by the coordinator:
  it loosens the spec toward the code, which DEC-176 leaves to the founder. It would also leave the
  connect's step-up with no event to commit with.
