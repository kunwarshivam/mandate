| | |
|---|---|

| **Date** | 2026-10-16 (UTC) |
| **Decided by** | The R1 builder (Claude Code), under DEC-79 and DEC-176; one PR with its tests first (DEC-921) |
| **Story or claim** | E7-12, E7-11; the [R0 rehearsal](../tasks/r0-rehearsal.md)'s blocker R1; [first live trade brief](../tasks/first-live-trade.md) K1b; claim #1377 |

`mandate connection record --environment live --broker robinhood` refuses `check_missing`
because no binary journals the `ConnectionChecked` it binds (journal spec §9.8 rule 68):
`mandate_connections::checks::run` was linked by none. These are the readings that close it.

## Decision

1. **Where the check runs: the runner, not the CLI.** The dispatch asked to wire the checks into
   "the CLI's connection gesture". The specs put the broker-facing checks in the connection's
   executor and keep the control services, which the CLI plays in Phase 1, off every broker
   (connections spec §5.2: "the API process, which never calls the broker"; journal spec §9.8's
   connect sequence; the `mandate-connections` crate's own process table), and only the runner
   may hold Robinhood's host (DEC-529 item 3, ES-23's narrowing). So the founder's connection
   gesture is two commands: `mandate-paper --connect-check`, which reads the broker and journals
   the check, then `mandate connection record --checked <id>`, which confirms it exactly as
   before. `connection record` is unchanged: it still refuses `check_missing`,
   `check_other_connection` and `check_failed`, so no version can bind a connection whose
   latest connect check did not pass. This is the R1 fix the rehearsal record proposed, and the
   reading that keeps every process boundary.
2. **What the mode takes, and refuses first.** `mandate-paper --connect-check --workspace …
   --account-ref … --connection … --journal … --confirm-live`, nothing else on the command line.
   The agentic account's number, which comes from the founder (DEC-875 item 1), is read from
   `MANDATE_RH_ACCOUNT_NUMBER`, never from an argument, and is never printed, journaled or
   kept. In order, before any credential is read: an Alpaca variable naming a host (the run's
   own check), no `--confirm-live` (`LiveUnconfirmed`: a Robinhood connection is live only), a
   connection id that is not an identifier, an account ref that is not a ULID, a workspace that
   makes no stream id, and an unset or empty account number each refuse with nothing read or
   written; then core dumps off (LT-9), then the login at the endpoint this build pins
   (DEC-937 item 2: none in the default build, which refuses `robinhood_not_built`; loopback
   only in the rehearsal build). A login that fails journals nothing, since no check ran.
3. **What the checks read.** One MCP session over the login's token: `initialize`, the whole
   tool list, and then, only when that listed, `get_accounts` through the Robinhood connector's
   own account check (DEC-875 item 1). The `CheckInput` is Robinhood, `live`, `mcp_oauth`,
   occasion `connect`, no pinned contract (the first connect pins). The grant is the listed tool
   names, so a fund-movement name fails `scope` with `fund_movement` (CN-2); a session that made
   no listing has no grant to show and is given an unread one, which `scope` refuses as
   `scope_mismatch`, and `contract` fails `tools_missing`. The account is `read` and dedicated
   only when the connector's check passed, that is when exactly one account is agentic and it
   is the recorded number; every other answer — not agentic, absent, two agentic accounts, or
   unreadable — is `account_unreadable`, since telling them apart would mean reading other
   accounts' records, which the connector never returns (CN-8). Nothing else is read.
4. **The MCP session's two additions** (`mandate-mcp`). `McpTransport::with_bearer` sends the
   token as `authorization: Bearer` on every request, the header marked sensitive and the token
   a `SecretString` that no `Debug` prints; this is the first half of O2, the session carrying
   the login's token. `McpClient::connect_to_check` is the first connect of a check: it lists
   and pins as `connect` does, but a fund-movement or missing tool refuses nothing; it is
   reported in `Listed` (the names, and whether every allowlisted tool was there) and halts
   openings, so the failed check is journaled rather than lost. The check calls only
   `get_accounts`; `connect` is unchanged for every other caller.
5. **The personal-data reference without a vault.** Journal spec §9.8 records the broker account
   id only as `account_pii_ref`, a vault reference. No vault exists for this order (DEC-529
   item 3), so the account id is stored nowhere, and the reference is `pii_` followed by the
   check's own event id: a well-formed reference (rule 62) that resolves to nothing and names
   nothing. The fingerprint comparison stays out of reach, as the CLI already says, and
   `connection record`'s `account_maybe_connected` keeps refusing a second connection of the
   same broker and environment in its place.
6. **What is journaled.** On `acct:{workspace}:{account_ref}`, after taking its ownership (the
   executor is the stream's single writer): `StreamOpened` when the stream is new (head 0), then
   `ConnectionChecked`, in one batch at that head, with ids derived from the epoch and the head
   (the shell's account id space), so a retried batch is the same batch. Both envelopes say
   `live`, are written by the `system` actor `executor`, and carry no causation. The check lists
   every result ascending by check (rule 57), each reason exactly when it failed (rule 58), the
   reference exactly when the account was read and then also in `pii_refs` (rule 62), and
   `risk_clock` on the check's whole second (§4.7). A failed check is journaled and the mode
   still exits non-zero, naming the first failed check in §8.1's order and the event id, never
   the account. An append that does not commit (or is not already committed) is
   `the journal could not be written` and no check. A passing check prints `checked <event id>`
   only, the id `--checked` takes. A second check appends only its `ConnectionChecked`; the CLI
   binds the latest one.
   The derived ids carry no stream component (the shell's `Ids`, as its own account ids), so
   two different account streams first checked in one journal at the same epoch and head would
   derive the same id, and the second append is refused rather than mixed up. One founder
   account needs one stream; stream-scoped ids are backlog debt with the shell's.
7. **Paper Alpaca is unchanged.** The spec's paper connect is the OAuth connect through the
   token-exchange process and the vault (connections spec §5.2, DEC-821), which does not exist
   yet; the runner's paper session reads API keys from its environment, another credential than
   any connect would record, so a check of it would be evidence about the wrong credential. A
   paper run needs no connection record (V-001, DEC-910 item 2), so nothing about paper changes:
   the mode is Robinhood's alone, and `connection record --broker alpaca` keeps refusing
   `check_missing` until the paper connect sequence exists.
8. **The rehearsal.** `scripts/r0-rehearsal.sh` gains step 2d2, the connect check against
   `mandate-rh-sim` through the simulator's login page, and binds its printed id at 2e and 2f in
   place of the made-up one. Its scopes become the nine allowlisted tools exactly (it listed a
   `get_quotes` the contract does not have and left out two).

## Rationale

Every reading keeps the process boundaries the specs draw and the one live host where DEC-529
put it, and every unclear outcome fails the check rather than passing it: an unread grant, an
unread account, a session that never listed. Journaling failures as well as passes is what
§8.1 and rule 68 ask: the record of a refused connect is evidence, and the CLI already binds
only the latest connect check, so a failed one can never be recorded and a later passing one
supersedes it.

## Alternatives considered

- **Run the checks inside `mandate connection record`.** Rejected: it would put a broker session
  and the live host in the control services' binary, against connections spec §5.2 and
  DEC-529 item 3, and give the CLI, which `xtask/layers.toml` keeps off the order path, a
  network path to the broker.
- **Refuse at the MCP connect and journal nothing.** Rejected: rule 68 and §8.1 make the failed
  check part of the record, and a connect that disappears leaves the founder no evidence of why.
- **Take the account number as an argument.** Rejected: an argument shows in the process list;
  the environment variable is read once and never written anywhere.
- **Journal the check for paper too, from the runner's environment keys.** Rejected for now (item
  7): it would record a check of a credential no connect recorded.
