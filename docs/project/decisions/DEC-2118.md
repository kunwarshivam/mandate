## Context

The review of the passkey routes ([#2021](https://github.com/kunwarshivam/mandate/pull/2021),
DEC-2115) passed with five items owed: what a retried registration challenge answers, the exact
shape of a passkey id, the coupling of `step_up` and `step_up_assertion`, how a client tells
`step_up_stale`'s two meanings apart, and the pending state of the step-up record the enrol route
cites. One optional item asked whether a reused passkey id needs its own pointer.

## Decision

1. **A retried registration challenge.** While the server holds the registration challenge, a
   retry with the same `Idempotency-Key` answers it unchanged, the same bytes. Once a submit has
   dropped it, or it has expired, the same key is refused `idempotency_conflict` and never revives
   it; the client asks again under a new key. A fresh challenge under the old key is rejected: its
   `challenge_id` is the key's derived id, so the key would name two challenges, and the step-up
   digest `{"op": "enrol", "registration": <challenge_id>}` would bind to bytes the member never
   saw. This is a deliberate exception to API-4's "a repeat with the same body returns the first
   outcome": the challenge is never journaled, so there is no first outcome to return.
2. **A passkey id's shape.** `PasskeyId` is 22 to 1,364 characters (16 to 1,023 bytes) of unpadded
   base64url, and no length whose remainder by 4 is 1, which no byte string encodes to:
   `minLength`, `maxLength`, and the pattern `^(?:[A-Za-z0-9_-]{4})*(?:[A-Za-z0-9_-]{2,3})?$`. The
   suggested single pattern `^(?:[A-Za-z0-9_-]{4}){5,340}(?:[A-Za-z0-9_-]{2,3})?$` is not taken: it
   admits 20 characters (15 bytes) and refuses 1,364 (1,023 bytes).
3. **The step-up pair.** `commands/passkey-enrol-request` takes `step_up` and `step_up_assertion`
   both null or both set (a `oneOf`), so half a step-up is refused `invalid` by the schema before
   any check reads it.
4. **The stale first enrolment.** `step_up_stale` also means a first enrolment whose session was
   opened more than 300 s before (DEC-2115 item 2). That refusal carries one violation at
   `/session`, and an expired challenge carries none, so a client tells them apart: the first
   signs the member in again, the second asks for a new challenge.
5. **A reused passkey id.** A passkey id the stream has ever enrolled is `invalid` with no
   violation path, as any response `mandate_passkey::enrol` rejects is. A pointer at `/passkey_id`
   would tell a caller that another member's authenticator was enrolled. This replaces DEC-2115
   item 2's "`invalid` at `/passkey_id`"; the rest of that item stands.
6. **§9.32 is planned.** The enrol route's `StepUpAsserted` (journal spec §9.32) is marked planned
   until journal spec v0.71 specifies it.

Not taken: refusing the registration challenge early when every passkey of the member is in its
cool-off. The enrol route already refuses it `step_up_missing` (DEC-2115 item 2), and a
challenge costs nothing but a slot under the limits.

## Rationale

Each item removes an ambiguity a client or the server would otherwise resolve its own way. Item 1
takes the stricter of the two readings the review offered; items 2 and 3 move checks into the
schema; item 4 adds no code; item 5 discloses less.

## Alternatives considered

- **A fresh challenge under the old key** (item 1). Rejected, as item 1 says.
- **A new error code for the stale first enrolment** (item 4). Rejected by DEC-2115 already; the
  violation path tells the meanings apart without growing the problem schema.

## Follow-ups

- S3.3's pending tests in `mandate-api-server` pin items 1, 3, 4 and 5; the schema examples pin
  items 2 and 3.
