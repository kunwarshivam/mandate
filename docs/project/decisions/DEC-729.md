## Decision

`mandate_dispatcher::push_status(status, message_id)` gives the outcome a push service's HTTP
status is journaled as, on either route: a relayed send gets the status back unchanged (DEC-724
item 6), and a direct send receives it itself.

1. **Any `2xx` (200 to 299) is `accepted`.** RFC 8030 answers a push message `201 Created`, and
   every `2xx` is a success in HTTP, so none is retried. The outcome carries the caller's
   `message_id` unchanged as `provider_message_id`: the relay returns no push service message id,
   and which id the dispatcher journals is the dispatcher process's own choice (E8-10). The journal
   refuses `delivered` without an id, so a `2xx` with an empty `message_id` is the closed
   `DispatchError::NoMessageId`, never an `accepted` with no id; any other status maps as below
   whatever the id.
2. **Any `3xx` is `permanent { address_rejected }`.** Spec §4.6: "A send follows no redirect: a
   `3xx` answer is a permanent failure, `address_rejected`." This item only restates it.
3. **`404` and `410` are `permanent { address_rejected }`.** RFC 8030 §7.3 (Subscription
   Expiration) has a push service answer `404 (Not Found)` to an application server that sends to
   an expired subscription. `410 (Gone)` is HTTP's "no longer available, and likely permanently"
   (RFC 9110 §15.5.11), and the browsers' push services answer it for a subscription that was
   unsubscribed or expired. They are the only statuses besides a `3xx` that mark the address
   `unreachable` and raise `channel_lost` (§5.2, §5.6).
4. **`400` is `permanent { provider_error }`. `401` and `403` are Proposed for the founder.** A
   `400` is a malformed request: a fault of the deployment's own request, which a retry cannot heal
   and which is no verdict on the member's address (DEC-728's reading). It is not unambiguous: some
   push services, FCM and Apple's among them, can answer `400` for an invalid token, which is
   arguably a fault of the address. Not marking is the safe side, and the founder or a later
   decision may revisit it. RFC 8292 §4.2 answers an
   absent VAPID header with `401` and an invalid one, or one whose key does not match the
   subscription's, with `403`. Whether that is a verdict on the address changes what the owner is
   told, so it is the founder's (DEC-723). The options are:
   - (a) `permanent { provider_error }`: it never marks an address and raises no `channel_lost`;
   - (b) `permanent { auth_failed }`: it marks the address `unreachable`, raises `channel_lost`, and
     raises an operator alert, following §5.6's precedent for a platform credential;
   - (c) as (a), plus an operator alert raised by the dispatcher process (E8-10).

   A variant of any of them: `401` as `retryable { provider_error }` rather than permanent. RFC 8292
   lets an application server retry with a fresh token, `prepare` already signs a fresh header for
   every attempt (DEC-726 item 3), and a skewed clock can heal inside the `safety` window, so a
   retry could deliver what a permanent result would drop.

   **Until the founder decides,** the merge coordinator ruled on 2026-10-09 that `401` and `403`
   take the most conservative option, (a): `permanent { provider_error }`, never `auth_failed`, no
   address marked, and no `channel_lost`. The operator alert of (c) is a backlog row for E8-10, not
   part of this decision. **Whatever the founder chooses, a deployment-side signing fault must never
   be able to mass-mark addresses**: one signing bug, rotated key, or skewed clock makes every
   subscription answer `401` or `403` at once.
5. **`413` is `permanent { too_large }`.** The push body is fixed (DEC-790 item 2), so a retry sends
   the same body again. It marks nothing.
6. **`429` is `retryable { rate_limited }`.** This restates spec §5.3: a provider `429` retries.
7. **Any `5xx` (500 to 599) is `retryable { provider_error }`.** A fault of the push service may
   heal, so it is retried on §5.3's schedule inside the class's window. It marks nothing.
8. **Every other status is `retryable { provider_error }`.** This covers a `1xx`, every `4xx` not
   named above, and anything outside 100 to 599. An answer the spec and RFC 8030 do not name is
   retried inside the class's window, so no `safety` notice loses a retry to it. It never marks an
   address, because only items 2 and 3 do.

## Rationale

Spec §4.6 and §5.3 name only a `3xx` and a `429`; DEC-724 item 6 leaves the rest of the mapping to
the dispatcher. An outcome can go wrong in two ways. A mark is not reversible by the platform: it
applies to every later notice on that channel, `safety` ones included, until the member re-verifies
the address (§5.6). A permanent result for a fault that would heal drops the rest of a notice's
retries. So exactly three things mark: a `3xx`, because spec §4.6 says so; and `404` and `410`,
because RFC 8030 §7.3 and HTTP's `Gone` name a subscription that no longer exists. Nothing else
marks. Only the deployment's own deterministic faults stop, and everything else retries within the
window §5.3 already bounds.

**Item 4's residual.** Under the interim (a), one deployment-wide fault cannot mark every member's
address: a signing bug, a rotated key, or a skewed clock would otherwise make every subscription
answer `401` or `403`, mark them all `unreachable`, and fan `channel_lost` out to every member, with
no way back short of each member re-verifying. The cost is that a subscription that really is bound
to another key keeps being tried and failing `provider_error` with no `channel_lost`, so the member
is not told. Each such attempt is journaled `failed`, and the pull channels list every notice
throughout (NT-5). Spec §5.2 still says `auth_failed` marks the address; the interim only says that
no push service status is `auth_failed` until the founder decides.

## Alternatives considered

- **`401` and `403` as `auth_failed`** (item 4's option (b)). Left to the founder, not taken as
  the interim: the credential is the deployment's own key, not the member's address, and without a
  guard one deployment fault would mark every address.
- **`401` and `403` as `retryable { provider_error }`.** Not the interim: DEC-728 item 1 rejects
  retrying a deterministic fault of the deployment's request for up to 24 hours. A retryable `401`
  is still a variant for the founder under item 4.
- **Every unknown status as `permanent { provider_error }`.** Rejected: a status the dispatcher
  cannot read would end a `safety` notice's retries on a guess.
- **Only `201` as `accepted`.** Rejected: a push service that accepted a message with another `2xx`
  would be sent it again every 15 minutes for the whole window.
