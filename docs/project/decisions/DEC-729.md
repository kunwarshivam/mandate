## Decision

`mandate_dispatcher::push_status(status, message_id)` gives the outcome a push service's HTTP
status is journaled as, on either route: a relayed send gets the status back unchanged (DEC-724
item 6), and a direct send receives it itself.

1. **Any `2xx` (200 to 299) is `accepted`.** RFC 8030 answers a push message `201 Created`, and
   every `2xx` is a success in HTTP, so none is retried. The outcome carries the caller's
   `message_id` unchanged as `provider_message_id`: the relay returns no push service message id,
   and which id the dispatcher journals is the dispatcher process's own choice (E8-10).
2. **Any `3xx` is `permanent { address_rejected }`.** This restates spec §4.6: a send follows no
   redirect, and a `3xx` is a permanent `address_rejected`.
3. **`404` and `410` are `permanent { address_rejected }`.** RFC 8030 answers a subscription that
   has expired or been removed with one of them. They are the only statuses besides a `3xx` that
   mark the address `unreachable` and raise `channel_lost` (§5.2, §5.6).
4. **`400`, `401` and `403` are `permanent { provider_error }`, never `auth_failed`.** A `400` is a
   malformed request, and RFC 8292 §4.2 answers an absent VAPID header with `401` and an invalid
   one, or one whose key does not match the subscription's, with `403`. Each is a verdict on the
   deployment's own request or header, which is the same for every member, so a retry cannot heal
   it, and none is a verdict on the member's address. This is DEC-728's reading: `auth_failed`
   would read the deployment's own header fault as the address's, which DEC-726 item 5 keeps the
   relay from causing for that reason.
5. **`413` is `permanent { too_large }`.** The push body is fixed (DEC-790 item 2), so a retry sends
   the same body again. It marks nothing.
6. **`429` is `retryable { rate_limited }`.** This restates spec §5.3: a provider `429` retries.
7. **Any `5xx` (500 to 599) is `retryable { provider_error }`.** A fault of the push service may
   heal, so it is retried on §5.3's schedule inside the class's window. It marks nothing.
8. **Every other status is `retryable { provider_error }`.** This covers a `1xx`, every `4xx` not
   named above, and anything outside 100 to 599. An answer the spec and RFC 8030 do not name is
   retried inside the class's window, so no `safety` notice loses a retry to it. It never marks an
   address, because only items 2 and 3 do.

## Rationale

Spec §4.6 and §5.3 name only a `3xx` and a `429`; DEC-724 item 6 leaves the rest of the mapping to
the dispatcher. An outcome can go wrong in two ways. Marking an address is not a reversible
outcome: the member must re-verify it (§5.6), so a marking guess silences that channel for every
later notice, `safety` ones included. A permanent result for a fault that would heal drops the rest
of a notice's retries. The reading takes neither risk on a status it cannot read: only a redirect
and a gone subscription mark, only the deployment's own deterministic faults stop, and everything
else retries within the window §5.3 already bounds.

**Residual, flagged for the founder.** Item 4 keeps one deployment-wide fault from marking every
member's address: a signing bug, a rotated key, or a skewed clock would otherwise make every
subscription answer `401` or `403`, mark them all `unreachable`, and fan `channel_lost` out to every
member, with no way back short of each member re-verifying. The cost is that a subscription that
really is bound to another key keeps being tried and failing `provider_error` with no
`channel_lost`, so the member is not told. Each such attempt is journaled `failed`, and the pull
channels list every notice throughout (NT-5). An operator alert on repeated `provider_error`, like
§5.6's for a platform credential, is left to the dispatcher process (E8-10). Spec §5.2 still says
`auth_failed` marks the address; this decision only says that no push service status is
`auth_failed`.

## Alternatives considered

- **`401` and `403` as `auth_failed`** (spec §5.6 reads `auth_failed` as a revoked credential).
  Rejected: the credential here is the deployment's own key, not the member's address, and one
  deployment fault would mark every address.
- **`401` and `403` as `retryable { provider_error }`.** Rejected: DEC-728 item 1 already rejects
  retrying a deterministic fault of the deployment's request for up to 24 hours.
- **Every unknown status as `permanent { provider_error }`.** Rejected: a status the dispatcher
  cannot read would end a `safety` notice's retries on a guess.
- **Only `201` as `accepted`.** Rejected: a push service that accepted a message with another `2xx`
  would be sent it again every 15 minutes for the whole window.
