# DEC-665: Who may obtain a step-up challenge: issuance takes the authorization's context

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | Agent (lane L1 builder, claude-code), under DEC-79 (reversible engineering) and DEC-176 (item 3 only refuses) |
| **Story or claim** | E9-4 P3, claim [#759](https://github.com/kunwarshivam/mandate/issues/759); identity spec §7.2 step 1, §4.5, DEC-816 item 3 |

## Decision

1. **The witness is the context.** `mandate_passkey::stepup::issue_challenge(&TenantContext,
   Action, AssertionId, issued_at)` returns `Issued` (the record and `membership_unverified`) or
   `IssueRefusal`. Only `authorize` builds a `TenantContext`, so a caller with no authorization
   cannot express the call. An `own` row's context comes through `PrincipalContext::into_tenant`,
   an org row's (an org owner approving break-glass) through `OrgContext::into_workspace`.
2. **The row is the action's.** Refusals in order: `authorize`'s, as §4.5 orders them (DEC-643
   codes); then `forbidden` when the context was authorized for another §4.2 row than the one `action.kind` needs (workspace API
   §3.6: `stop` and `resume` share one row, `member_invite` is the members row, `role_grant` the
   roles row, `credential_enrol` the own-passkey row); then `IssueError::OutOfRange`.
3. **A row without S gets no challenge** (DEC-176: it only refuses). No §3.6 kind names such a row,
   so a context for one is always refused `forbidden`, and no ID-5 action can be asked for step-up.
4. **`membership_unverified` is carried, not refused.** §7.2 step 1 says a membership outage never
   refuses an owner exit's challenge. `authorize` flags only risk-reducing rows, and the owner exit
   is the only one with S, so it is the only challenge an unverified context obtains. The flag
   rides on `Issued` for the challenge store. The record's canonical form, and so its WebAuthn
   challenge, is unchanged.
5. **No principal-kind check of its own.** Clients, service accounts, the host CLI, and platform
   operators are blank on every S row, so `authorize` refuses them, and a reduction-only session is
   refused `reduction_only`. A second check could never fire, so no test could pin it.
6. `ChallengeRecord::issue` stays public as the challenge store's rebuild path (DEC-662 item 7). The
   request path issues only through `issue_challenge`.

## Rationale

§7.2 step 1 authorizes a challenge exactly as its action's row; taking the context makes that a
type.

## Alternatives considered

- **A `Permitted<P>` marker per kind (DEC-655):** 18 markers, and the kind is request data, so the
  route would match on it anyway.
- **Taking `&Authorized`:** its principal- and org-scope arms have no workspace to bind.
- **Refusing every unverified context:** contradicts §7.2 step 1 for the owner exit.
