# DEC-447: `StreamOpened` and `OwnerCommandRefused` carry no `risk_clock`

| | |
|---|---|
| **Status** | Accepted (agent, reversible engineering, DEC-79; DEC-176: the readings add no member and refuse nothing that was conforming, so they add no risk) |
| **Date** | 2026-10-03 (UTC) |
| **Decided by** | The stream K builder (claim [#137](https://github.com/kunwarshivam/mandate/issues/137)); a rider on [DEC-446](DEC-446.md) item 1 |
| **Story or claim** | E7 journal: the account stream's executor records ([DEC-360](DEC-360.md)); journal spec v0.13 §9.5 |

## Decision

[DEC-446](DEC-446.md) item 1 puts `risk_clock` on the three executor records §9.5 closes at
`schema_version` 2, under §9.2's "the executor writes it on every account-stream event". Two
account-stream payload schemas are not read that way and stay at `schema_version` 1 with no
`risk_clock`:

1. **`StreamOpened`.** The fold reads no clock from the opening: `risk_clock` is the latest tick
   the executor had seen (§2, mandate spec §5.2), and at seq 1 there is none — a stream opens
   before the first `ClockAdvanced` reaches it. Writing the member would force a sentinel value
   that means "no tick yet"; not writing it says the same thing by absence. The registered
   `STREAM_OPENED_V1` (the version-3 vectors' seq 1: `stream_type`, `workspace_id`, `broker`,
   `account_ref`) stands unchanged, and §9.2's sentence is read as it always was for the opening:
   of the events the fold replays risk state from, the opening is the one that carries no clock
   because it precedes the clock. DEC-81's list of risk inputs never named it.
2. **`OwnerCommandRefused`.** Its schema is shared by both streams that write it (§9.2, DEC-291:
   the executor on the account stream for a refused acknowledgment, the agent runtime on the agent
   stream for a refused resume or Stop), and the fold's read of it is the refusal's `effective_at`,
   "never risk-clock seconds" (§9.2). Giving the account stream's copy a member the agent
   stream's cannot have would split one closed schema by stream, which §9.2's single table
   deliberately does not do. The refusal is also no risk input of mandate spec §5.2's: it records
   that a command was not applied, which moves no risk state.

## Rationale

The readings keep the member where it does work (the records the fold clocks by) and off the two
records where it would be a sentinel or a stream split, and they refuse nothing: neither schema
lists the member today, and none of the fold's reads change.

## Alternatives considered

- **Take §9.2's "every account-stream event" literally, both included.** Rejected: the opening
  would carry a clock that exists only after it, and the refusal schema would fork by stream.
