## Context

DEC-823 item 4 had Cloudflare build `main` from its own GitHub connection, so that no Cloudflare
credential existed outside the founder's account, and no workflow held a token or ran
`wrangler deploy`. E21-38 instead asks for a deploy from `main` "by a workflow whose deploy token
is an environment secret no PR job can read (ES-12)". The founder has created that environment:
`production`, restricted to the `main` branch, with the secrets `CLOUDFLARE_API_TOKEN` and
`R2_SECRET_ACCESS_KEY` and the variables `CLOUDFLARE_ACCOUNT_ID`, `R2_ACCESS_KEY_ID` and
`R2_ENDPOINT`. Agents never see the values.

## Decision

1. **One job deploys.** `.github/workflows/web-deploy.yml` has one job, `deploy`. It runs on a push
   to `main` that touches `web/` or the workflow, or on `workflow_dispatch`, and only when
   `github.ref` is `refs/heads/main` and the switch of item 7 is on. It builds the Worker (`npm run cf:build`), runs the same dry
   run and size budget as pull requests (DEC-731 items 5 and 6), and then, as its last step, runs
   `node_modules/.bin/wrangler deploy`: the `wrangler` that `npm ci` installed from the lockfile,
   never `npx`, which fetches a package the lockfile does not hold instead of failing. No other workflow, job or npm script deploys, uploads or logs in to
   Cloudflare. The check is an allowlist: outside that step, a workflow line or npm script that
   names Wrangler, OpenNext or a Cloudflare action must be exactly the pull request's dry run
   (`node_modules/.bin/wrangler deploy --dry-run --outdir .wrangler/dry-run`) or the `cf:build` and `cf:preview`
   scripts, so a deploy hidden by flags, quotes, a path or a comment fails the check. It catches
   drift, not an attacker: a script file that spawns Wrangler, or a command spelt to dodge it,
   would pass. What holds the token is the environment, which GitHub gives to jobs on `main` only. This replaces Cloudflare's own GitHub build (DEC-823 item 4's second bullet), so the
   founder does not connect one, and two deploys never race.
2. **The token stays in the environment.** Only the deploy job names `environment: production`.
   Only its last step reads a secret, and only `secrets.CLOUDFLARE_API_TOKEN`, with
   `vars.CLOUDFLARE_ACCOUNT_ID`. The build step reads only `vars.NEXT_PUBLIC_*` values, which are
   public and which Next inlines (DEC-823 item 5). No job-level `env` reads a secret or variable,
   so the token is never in the environment while the bundle is built. The `web` workflow, which
   runs on pull requests, reads no secret and no variable (ES-12). The job does not read the R2
   secret or variables: the Worker has no R2 binding, and they belong to lane S1 (E21-40).
3. **Least rights.** The workflow sets `permissions: {}`, the job reads contents only, and the
   checkout keeps no credential, and the workflow's only top-level keys are `name`, `on`,
   `permissions`, `concurrency` and `jobs`, so no top-level `env` or `defaults` reaches every step.
   `web/scripts/workers.mjs` checks items 1 to 3 on every pull request
   that touches `web/`, through the `web` unit tests, and fails when any of them is undone.
4. **Vercel keeps `main` until the cutover.** `vercel.json` stays, still deploying `main` alone
   (DEC-465 item 1), because `owlhead.ai` and `www.owlhead.ai` still point to Vercel and removing
   the file would let Vercel build every branch. It goes in a later change, once the founder has
   moved the domains to the Worker and disconnected the Vercel project. This is a tightening of
   DEC-823 item 3, under DEC-176; the check allows the file only while it deploys `main` alone.
5. **The Worker stays unaddressed until the founder routes it.** `workers_dev` and `preview_urls`
   stay false (DEC-731 item 3), and `wrangler.jsonc` names no route, so a deploy changes no DNS. The
   founder adds the custom domain in the dashboard. The check also refuses a committed route and a
   `build` command, which would run repository code in the step that holds the token.
6. **The public variables are the environment's.** Next inlines `NEXT_PUBLIC_*` values when it
   builds, so the deploy job, not the Cloudflare dashboard, supplies them: the founder adds
   `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` as variables of the
   `production` environment when Supabase is ready. Until then a deploy has sign-in off, so it
   serves the fixture preview as the e2e suite sees it, and the beta form is closed
   ([DEC-987](earlier-900-1999.md#dec-987)). Neither value is a secret (DEC-823 item 5).

What DEC-823 item 4 keeps: no Cloudflare credential in a repository secret, a committed file, the
Worker's configuration or a script; no `wrangler login`; and the account protected by a hardware
key or MFA.

7. **Off until accepted.** The job's condition is
   `github.ref == 'refs/heads/main' && vars.WEB_DEPLOY_ENABLED == 'true'`. Until the founder accepts
   this decision and sets the repository variable `WEB_DEPLOY_ENABLED` to `true`, GitHub skips the
   job, so no step runs and nothing reads the token (AGENTS.md rule 9: the most conservative option
   while a founder decision is Proposed). It is a repository variable, not one of the environment's,
   because a job's condition is read before its environment is. Clearing the variable turns the
   deploy off again. The check requires this exact condition.

## Rationale

The environment gives the token to `main` alone, so a pull request, including an agent's, cannot
read it, which is what DEC-823 item 4 protected. Deploying from GitHub runs the same checks the
pull request passed, and the guard keeps the shape from drifting. DEC-823 item 7's trade stays as
it was: merging to `main` is the deploy.

## Alternatives considered

- **Keep Cloudflare's own build (DEC-823 item 4).** No token in GitHub, but E21-38 asks for the
  environment, and the founder has set it up.
- **A repository secret.** Any workflow on any branch could read it.
- **Deploy from `web.yml`.** It runs on pull requests, so the token would sit one condition away
  from a pull-request job.
- **Remove `vercel.json` now, as #878 did.** Vercel would then build every branch until the
  founder disconnects it.
