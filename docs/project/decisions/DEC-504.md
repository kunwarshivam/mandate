## Decision

1. **The content object.** For a `quant.` model, the content hash is the SHA-256 of the
   canonical JSON ([journal spec §4](../../specs/journal.md)) of one object:
   - `kind`: `quant_model_content`, and `content_version`: 1;
   - `model_id` and `model_version`;
   - `code`: the source files whose bytes implement the model's signal and its mapping to an
     output, each as `{path, sha256}`, sorted by `path`, paths relative to the repository root;
   - `params_schema`: every parameter's name and type and bounds, with no default (DEC-52);
   - `inputs`: what the model reads (for `quant.ma_crossover`: complete daily closes of the pinned
     instrument, the trading day's boundary per asset class, at least `slow_periods` of them);
   - `output`: how a signal becomes an output (for `quant.ma_crossover`: `Long` is direction
     `long`, conviction 1, confidence 1; `Flat` and `Undecided` are no output, DEC-157 item 4);
   - `methodology` (method only, no performance claim, mandate spec §8.1) and `authorship`:
     `platform`.
2. **The hash is computed from the code that was built.** The host embeds each listed file's
   bytes at compile time and computes the object and its hash from them. A test pins the expected
   hash for each registered `(model_id, model_version)`: any edit to a listed file fails that test
   until the model gets a new version and its new hash is registered. A model whose code changed
   cannot keep its version (rung 2 of the trust ladder).
3. **Registration.** The content object is stored as an artifact under its hash, then a
   `ConfigSnapshotRegistered` (kind `model_version`) records `model_id`, `model_version`,
   `content_hash`, the sorted parameter names, and `admits_instruments: false`
   ([journal spec §9.2](../../specs/journal.md#92-control-stream-payload-schemas-dec-261)). The
   deployment's `model_registry` object ([DEC-484](DEC-484.md) item 4) lists the same five members.
   Because the artifact is stored, `ModelOutputRecorded.content_hash`, a `ref`, re-hashes (journal
   spec §11 check 6).
4. **No reuse of a version.** A registration never gives an `(id, version)` that the same journal
   already registered a second hash. E7-7's fixture pinned `quant.ma_crossover` 1.0.0 to the hash
   of a two-member file `{"id","version"}`; no control stream ever registered it, and it is
   deleted with the E7-7 assembly.
5. **Withdrawal** is `PlatformOperatorAction` (`model_withdrawn`), whose schema stays open
   (DEC-261 item 9). Until it closes, a quant model is stopped by a new mandate version or a kill
   switch, never by the host.

## Rationale

Mandate spec §8.1 says the hash covers a model's code and parameter schema, and the mandate pins
it (V-007). Today's E7-7 hash covers only the id and version text, so a change to the crossover
would keep the pin the owner confirmed. Hashing the source bytes the binary was built from, and
failing the build when they change under an old version, makes "what I pinned is what runs" hold
for quant models without a registry service.

## Alternatives considered

- **Hash only `{id, version}`** (today's E7-7 artifact). Rejected: it covers no code, against §8.1.
- **Hash the built binary.** Rejected: it changes with the toolchain and with every unrelated
  change, and cannot be recomputed from the repository.
- **Golden input and output vectors instead of source bytes.** Rejected as the hash: a change that
  agrees on the vectors would keep the pin. Vectors stay as tests of the code.
