# DEC-2106: What `mandate step-up confirm` checks before it appends, and in what order

## Context

DEC-2104 item 2 names the command, its flags, the code's normalization, and the one record it
appends. It leaves open the refusal codes, the order of the local checks, what a re-run does, and
what the command prints. The CLI's other owner commands answer each of these the same way
(`approvals approve`, DEC-155 item 5, DEC-290): every check is local and refuses with a code,
appending nothing, and a re-run of a command that did commit finds it. This decision applies that
pattern to `step-up confirm`.

## Decision

1. **Paper only, with no `--environment` flag.** The confirming owner is the principal, in `paper`.
   The command writes as a `user` actor whose `id` is `--principal`, so rule 242's actor clause holds
   by construction. `--principal` is a ULID, not the opaque id the other commands' `--user` takes.
2. **The order.** The first failing check answers, and nothing is appended:
   1. the workspace names a control stream, else `owner_workspace_invalid`;
   2. `--principal` is a canonical ULID, else `principal_invalid`;
   3. `--challenge` is a canonical ULID, else `challenge_invalid`;
   4. `--code` normalizes as DEC-2104 item 2 says, else `code_invalid`. It is 8 characters, or 9
      with the one hyphen fifth, as the web app displays it (`XXXX-XXXX`). Lower case is upper
      cased, `I` and `L` read as `1` and `O` as `0`, and every other character must be Crockford
      base 32;
   5. the control stream is `paper`, from its first event, else `workspace_environment`
      (DEC-952);
   6. the approval is pending on the agent's stream and its content hashes to its stated hash, else
      `not_pending` or `content_mismatch`, as `approvals show` answers;
   7. the request is on a `paper` stream, else `paper_only`;
   8. the owner's clock is before the request's deadline, else `late`, as `approvals approve`
      answers. A grant past it would be refused anyway;
   9. no `StepUpConfirmed` on the control stream names the challenge (rule 243), else
      `challenge_confirmed`. The one exception is item 3.
3. **A re-run finds its confirmation (DEC-290).** An earlier `StepUpConfirmed` for the challenge
   with the same `action_digest`, `principal` and `code` is this command already committed. It is
   reported as committed and nothing is appended, whatever its `confirmed_at`. Any other earlier
   confirmation of the challenge is item 2.9's refusal.
4. **Appended where it was checked.** The record is appended at the control-stream head the
   command read its rows at, and nowhere else. When the stream has moved, the command reads the
   rows again and decides again, from item 2.5, so rule 243 is judged against every row the append
   follows. `confirmed_at` is the whole second of the `event_time` the record carries, so rule 242's
   time clause holds by construction.
5. **What it prints.** Before the outcome, it prints the approval as `approvals show` prints it, so
   the owner sees what the journal holds. Then it prints `confirmed <challenge> as event <id> at
   seq <n> for <content_hash>`, or `already confirmed <challenge> as event <id> at seq <n> for
   <content_hash>` for item 3. A refusal prints nothing, and no message names the DSN.

## Rationale

Every code but `principal_invalid`, `challenge_invalid`, `code_invalid` and `challenge_confirmed` is
one the owner commands already use, with the same meaning. The shape checks come first, so a
mistyped flag opens no journal. Checking against the journal's own approval keeps the owner from
confirming what the browser claims (DEC-2104 item 2). Appending at the head the rows were read at
makes rule 243 hold for one writer. Two writers racing are still possible, and the verifier
refuses the grant when they leave two confirmations (journal spec §9.29).

## Alternatives considered

- **Refuse every second confirmation of a challenge, a re-run included.** Rejected: an owner whose
  first run lost its answer could not learn that it committed (DEC-290).
- **Accept a code with any number of hyphens or spaces.** Rejected: the web app shows one form, and
  a looser parser accepts what the owner did not read.
