# DEC-1178: A dev or ci cell's fixture answers an issued token's account, and the executor reads it there

| **Story or claim** | E10-23 (the cell's OAuth connect, end to end); DEC-1176 (the fixture pod), DEC-2625 (the fixture provider), DEC-2633 (the cell's token and authorize URLs), DEC-2339 (the exchanged executor's connect check), DEC-2345 (check 4's fingerprint); claim #1901 |

## Context

In a dev or ci cell the token exchange redeems the browser's code at the fixture provider
(DEC-1176), and the exchanged executor then runs the connect check (DEC-2339). The check reads the
broker's account through `mandate_alpaca`'s `GET /v2/account`, which goes to Alpaca's real paper
host, and the cell must never reach it (rule 8). So a cell's connect ends with no
`ConnectionChecked`, and never with `ConnectionEstablished`.

## Decision

1. **The fixture's account endpoint.** The fixture provider serves `GET /alpaca/v2/account`.
   - It sits under `/alpaca/`, so it is never Alpaca's own `/v2/account`.
   - The Host must be exactly the fixture's public host (DEC-1176 item 8). The request must carry
     `Authorization: Bearer <token>` naming a token this provider issued at
     `/alpaca/oauth/token` and still holds, and nothing else: no query and no body.
   - It answers 200 with `application/json` `{"id": <id>}`. The id is the first 16 bytes of the
     token's SHA-256, formatted as a version 4, variant 1 UUID. So each connect has its own account,
     and check 4 (DEC-2345) refuses no second connect in a drill as a duplicate.
   - Any other bearer, or none, is 401 with an empty body. A query or a body is 400. Any other
     method is 404.
   - The fixture never logs a token or an id.
2. **The tokens it holds.** The provider keeps the tokens it issues in memory, at most 4,096.
   Beyond that, a redemption is answered `temporarily_unavailable`, as a full code store is
   (DEC-2625 item 5).
3. **The executor reads it there (lane X).** In a debug build, in the dev or ci tier, and only
   when `MANDATE_ALPACA_ACCOUNT_URL` is exactly `http://oauth-fixture:8091/alpaca/v2/account`,
   the exchanged executor's connect check reads the account there in place of Alpaca's host.
   A release build that finds the variable set refuses to start. This is DEC-2633's fence for the
   token URL, applied to the account read.
4. **The chart.** Under `mandate.oauthFixtureOn`, which any tier but dev or ci refuses
   (DEC-1176), the executor pods the deployment manager starts carry that variable and
   `MANDATE_DEPLOYMENT_TIER`, reach the fixture's pod on 8091 and nothing new besides, and the
   fixture's policy admits them. With it off, nothing is rendered. Staging's executor egress
   still names only `paper-api.alpaca.markets` and `data.alpaca.markets`.

## Alternatives considered

- **A fixed account id for every token.** Rejected: check 4 would refuse a drill's second
  connect as a duplicate, not for the reason the drill means.
- **Overriding the paper host.** Rejected: `mandate-alpaca` compiles in exactly one host, and
  `mandate-shell` pins that there is no `--host`.
