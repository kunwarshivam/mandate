## Context

Every step-up the web app asks for answers `step_up_missing` today. Workspace services are to be
the WebAuthn relying party for step-up (identity spec §6.1, DEC-820 item 2), and
`mandate-passkey` already reads a registration (`enrol`) and judges an assertion against a stored
credential (`stepup::consume`, DEC-660, DEC-662). What does not exist yet is the record of a
member's credentials, the routes that enrol and remove one, the way an assertion reaches the
server, and the relying party's settings for a deployment. The founder approves from a phone, so
the path must need nothing but the browser (`cli_confirm` stays the host CLI's own method).

The web app's sign-in passkeys are Supabase Auth's (DEC-211), a separate relying party that holds
its own public keys, so workspace services cannot verify them.

## Decision

1. **The relying party is per-deployment configuration** (identity spec §6.1). The API server's
   settings name one RP ID and one origin, `https://` followed by exactly that RP ID. A server whose
   origin is anything else refuses to start. Staging is RP ID `app-staging.owlhead.ai` with origin
   `https://app-staging.owlhead.ai`, and the managed production deployment is `app.owlhead.ai` with
   `https://app.owlhead.ai`. Both are settings, never code.
2. **A credential is recorded on the workspace control stream** (journal spec §9.31).
   `CredentialEnrolled` names:
   - the member, as a principal ULID;
   - the credential id, as unpadded base64url;
   - the COSE public key, as an artifact reference, so the key itself is never in the payload
     (identity spec §12.1);
   - its algorithm, `es256` or `eddsa`;
   - the signature counter at enrolment;
   - the cool-off end, or null;
   - the step-up that authorized it, or null for the first.

   `CredentialRemoved` names the member, the credential id, and the step-up that authorized it.
   A member's credentials are the fold of these two events over the stream. A credential id is
   enrolled at most once on a stream, and is never enrolled again once removed.
3. **A passkey step-up leaves its assertion on the record.** The event a passkey step-up
   authorizes is appended in one batch with `StepUpAsserted`, which names:
   - the challenge;
   - the credential id;
   - the signature counter the assertion carried;
   - the raw assertion as an artifact reference (identity spec §7.2 step 5);
   - its `causation_id`, the event it authorized.

   The step-up evidence on the authorized event keeps its three members (journal spec §9.2,
   mandate spec §6.1), so no event that already carries step-up changes. A credential's last
   counter is the greatest counter of its `StepUpAsserted` records, else its enrolment counter.
4. **The enrolment ceremony** (workspace API spec §3.6):
   1. The member asks for a registration challenge: 32 bytes from the operating system's
      generator, held in memory for 300 s, bound to the principal and workspace, used at most once
      (the submit that reads it drops it, whatever its outcome), and never journaled. The answer gives the RP ID, the user handle (the principal's 16 bytes), and the
      member's enrolled credential ids to exclude.
   2. The member submits the authenticator's response, its credential id, attestation object,
      and client data, with step-up as item 5 says.
   3. The server reads it with `mandate_passkey::enrol` (attestation `none`, the configured origin
      and RP ID, user verification), stores the public key's COSE bytes as an artifact, and commits
      `CredentialEnrolled`.
5. **Which enrolment needs step-up, and the first one** (identity spec ID-4 and §10.1, the
   coordinator's Q1 answer):
   - A member with a credential past its cool-off enrols another only with passkey step-up from
     it. The step-up's kind is `credential_enrol`, and its action object is
     `{"op": "enrol", "registration": <challenge_id>}`. The new credential has no cool-off.
   - A member with no credential on the stream may enrol one with a full session opened within the
     last 300 s and no step-up. That credential starts in the 24-hour cool-off of §10.1: it cannot
     step up until the cool-off ends, and the owner is alerted that a passkey was added. The alert
     carries only opaque ids and generic text, never the credential, its key, or the device
     (`AGENTS.md` rule 6).
     No rule is weakened: until it ends, the member is where they were with no passkey.
   - A member whose every credential is still cooling off cannot enrol another until one has ended.
6. **Removal** is passkey step-up of kind `credential_enrol` with the action object
   `{"op": "remove", "credential": <credential id>}`, from any of the member's credentials past
   cool-off, the one removed included, and commits `CredentialRemoved`. The step-up kind enum does
   not grow. Removing a member's last credential returns them to a first enrolment: the next one
   needs a fresh full session and waits the 24-hour cool-off, as item 5 says.
7. **The assertion's wire.** A request carrying passkey step-up names the challenge in its
   `step_up` evidence, as today, and sends the authenticator's `credential_id`,
   `authenticator_data`, `client_data_json` and `signature`, each unpadded base64url, in a sibling
   member `step_up_assertion`. The server stores that object's canonical bytes as the raw-assertion
   artifact. `authenticated_at` is the challenge's `issued_at` (DEC-662 item 7).
8. **The verifier.** For `passkey` evidence, at the server's clock, the server's step-up port
   folds the member's credentials from the control stream and judges the assertion with
   `mandate_passkey::stepup::consume`, in its order (identity spec §7.2 step 4, DEC-662):
   - the method for the environment;
   - the challenge is held, unused and current, and names this principal, workspace and action;
   - the credential is the principal's, enrolled, not removed, and past its cool-off;
   - the signature, user verification, and a counter above the last;
   - the action's digest.

   It then drops the challenge, as `cli_confirm` does (DEC-2104 item 6). `cli_confirm` evidence
   keeps DEC-2104's verifier, paper `approve` only. The same verifier serves every kind the
   challenge route issues, so `approve`, `confirm_version`, `deploy` and `connection` need no
   verifier of their own.

   Two consequences hold for both methods:
   - Until this verifier is bound, the `cli_confirm` port answers `step_up_missing` for evidence of
     any other method once check 1 has passed. It verifies only its own method, and the binding
     dispatches each method to its own verifier.
   - The challenge is taken inside verification, before the grant's event is committed. If that
     commit then fails, the challenge is gone, and the owner asks for a new one and confirms or
     signs again. It fails closed: a challenge never verifies twice.
9. **The sign-in passkey stays Supabase's** (the coordinator's Q2 answer, DEC-640's reading for
   now). The member registers a second passkey with the workspace's relying party. The same RP ID
   is fine, since a credential is chosen by its id. Step-up asks only for the member's enrolled ids
   (`allowCredentials`), so the browser never offers the sign-in passkey for a step-up. When
   workspace services also take passkey sign-in (DEC-640's single enrolment), these credentials
   carry over unchanged.
10. **What this never changes.** `live` grants stay refused at the API (`live_unavailable`,
    DEC-2103 item 4); a passkey makes a live step-up verifiable, but admitting live is the founder's
    (DEC-79). The runtime still judges the evidence at its effective time (mandate spec §6.1).
    Pause and the kill switch never need step-up (ID-5).

11. **How the records are handled as personal data** (the #1993 review's N4). Neither record
    carries `pii_refs`. The credential id and the public key's artifact are handled as identity
    records under journal spec §6.4, as `actor.id` is: kept for the records retention period, and
    not touched by `PersonalDataErased`. This is an engineering reading of how the journal handles
    them, not a legal classification; the founder can revise it in the after-the-fact review.

## Rationale

The control stream already carries every owner fact the server judges a grant by, so credentials
live there too, replayable and verifiable (§7.2 step 5's audit). A separate `StepUpAsserted` keeps
the counter and the raw assertion on the record without changing the evidence object that some
thirty event schemas carry. `mandate-passkey` already holds every check, so the server adds
storage and wiring, not new cryptography. The first-enrolment cool-off keeps ID-4's guarantee: a
session alone never yields a working step-up credential sooner than recovery would.

## Alternatives considered

- **Widen the step-up evidence with the credential, counter and assertion.** Rejected: it changes
  every event that carries step-up, and the runtime, which reads evidence, would need them all.
- **Journal only the credential id's hash.** Rejected: the server needs the ids themselves for
  `allowCredentials`, and an id is not secret.
- **A first enrolment with no cool-off.** Rejected by the coordinator (Q1): a phished session
  could enrol a working credential at once.
- **Move passkey sign-in to workspace services now.** Deferred (Q2): larger, and these
  credentials carry over unchanged when it lands.
