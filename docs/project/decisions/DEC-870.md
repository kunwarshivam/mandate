# DEC-870: A replacement successor's own record carries its own broker order id

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The C3 part-2 tests builder (Claude Code), under DEC-79 and DEC-176: the reading only lets a replacement's cancel find its order after a restart, refuses by default where no id is given, and loosens no rule |
| **Story or claim** | E7-6, the [first live trade brief](../tasks/first-live-trade.md)'s C3; journal spec §9.16; [DEC-869](DEC-869.md) items 3 and 4; [DEC-860](DEC-860.md) item 7; #1163 (part 1) and its review minor 1 |

## Decision

1. **The reading.** Journal spec §9.16 defines `broker_order_id` as "the broker's own id for the
   order named by `client_order_id`". When a replacement record arrives, the executor writes two
   `OrderStateChanged` version-2 records from it:
   - the old order's record, which carries the old order's id as its `broker_order_id`, with the
     new order's id staying in `replaced_by_broker_order_id` beside `replaced_by`, as at version 1;
   - the successor's own record (`client_order_id` the successor's key, `replaces` the old key),
     which carries the replacement record's `replaced_by_broker_order_id` as its
     `broker_order_id`, or `null` when the broker record gives none.
2. **The rebuild.** The connector's rebuild of its `client_order_id` → order id map reads only each
   key's own `broker_order_id` members (§9.16), so a successor is found by its own record. Its
   instrument and side are those of the order it `replaces`, back to that chain's `OrderSubmitted`.
   A successor's id is never taken from the old order's `replaced_by_broker_order_id`, so a
   version-1 stream gives a successor no recoverable id.
3. **What it does not do.** A successor whose own record carries `null` has no recoverable id: its
   cancel is `NotSent` (`no_order_id`), the shell stops and alerts the owner (DEC-85), and nothing
   is guessed (CN-7). No risk state, limit, or order state reads the member (DEC-869 item 4).

## Rationale

Before this reading a replacement's new order carried no id of its own, so after a restart its
cancel, the kill switch's order-by-order ones included, would always have escalated. The id is the
one the broker gave for that order in the same record; nothing is inferred. #1163's review asked
for the reading to be recorded before the connector's rebuild relies on it.

## Alternatives considered

- The successor's record carries `null` always: rejected, a replacement could then never be
  cancelled after a restart without the owner.
- The rebuild reads the old order's `replaced_by_broker_order_id` for the successor: rejected, it
  reads a member of another order's record and would treat version-1 records as carrying an id,
  which §9.16 says they do not.
