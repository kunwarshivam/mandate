# DEC-2113: Who the caller is: `principal_id` on one's own session, and one's own memberships from the hosted control stream

## Context

`web/` (lane W2) must know who is signed in and what that principal may do in the workspace, to
label "you" in the members list and approvals and to hide what the caller's roles cannot use.
Identity spec §4.5 already specifies `GET /v1/me/session`, answering `{kind, expires_at}`, and
`GET /v1/me/workspaces`, answering `{workspace_id, label, roles}` from the membership index. Neither
names the principal, the server serves neither, and the hosted server holds no membership index:
it authorizes from the control stream's membership fold (DEC-2110).

## Decision

1. **`GET /v1/me/session` names the caller.** Its answer adds `principal_id`: the session's own
   principal, in the opaque form the journal already records as the actor's id (a ULID). Nothing
   else is added: no session reference, cookie, token, refresh digest, subject, or issuer. The route
   stays on the authentication plane (§4.2, DEC-816 item 7): it reads only the caller's own session
   record and yields no context.
2. **`expires_at` is when the session ends untouched.** It is the earlier of the session's idle and
   absolute deadlines (§6.2), not the access token's: a refresh does not move the absolute one, and
   any admitted request moves the idle one.
3. **`kind`** is `full` or `reduction_only`; only a reduction-only session (§6.4 route 2) carries
   `workspaces`. Until route 2 is served (E9-1), the route answers a full session only: a session an
   outage narrowed (route 1) reaches pause and the kill switch alone, and is refused
   `reduction_only` (403) here as on every other ordinary route, so `reduction_only` is listed as
   planned.
4. **The hosted index is the control stream's fold.** A deployment that hosts one workspace from its
   control stream (§3.11) serves `GET /v1/me/workspaces` from that stream's membership fold, read at
   the request's instant, as its membership index: it answers that workspace, with the roles in
   effect then, when the caller is an `active` member of it, and `[]` otherwise. A member whose roles
   are all still cooling off gets the workspace with `roles: []`, as §4.5 says. Absent and foreign
   workspaces are never named. A failed read is `membership_unavailable` (503).
5. **`label` is `null` until one is recorded.** No event records a workspace's display label in this
   deployment yet, and the deployment's configuration holds none; the API never invents one.
6. **Neither answer names a stream.** `as_of` is `[]` on both, the envelope's case of a response
   that reads no stream: one's own session is no stream, and §4.5's route reads the membership
   index, which is not a journal stream however a deployment keeps it. A watermark of the hosted
   control stream would also tell a non-member that the workspace exists.
7. **Shapes.** `read-models/session` and `read-models/my-workspaces` close both answers under
   `schemas/workspace-api/`, each with valid and invalid examples and the mutation sweep.

## Rationale

The caller's own id is not secret: it is in every journal row the caller writes and reads, and it
reaches no one but the caller. Reading the index from the fold the server already authorizes with
gives the web app the roles the server enforces, so the two never disagree. A workspace-scoped
`/me` would need a new matrix row (§4.2's "rows, not routes") for what two specified routes already
answer.

## Alternatives considered

- **`GET /v1/workspaces/{workspace_id}/me` answering `{principal_id, roles}`.** Refused: a new row,
  and a second source of the roles §4.5 already serves.
- **Serve the session reference as the caller's id.** Refused: it is a credential-shaped value
  (§6.2) and identifies the session, not the principal.
- **Take `label` from the deployment's configuration.** Refused for now: the configuration holds
  none, and adding one is a deployment change of its own.
