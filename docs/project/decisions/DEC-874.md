# DEC-874: An odd broker id or the order of the records never makes a key placeable

| **Story or claim** | E7-6, the [first live trade brief](../tasks/first-live-trade.md)'s C3; journal spec §9.16; [DEC-870](DEC-870.md) item 2; [DEC-872](DEC-872.md); the three review minors #1200 and #1202 left for a follow-up |

## Decision

This adds three readings to [DEC-872](DEC-872.md), which stays as written. Each is about how
`RobinhoodConnector::restore` reads the account stream.

1. **Odd ids.** §9.16 makes `broker_order_id` non-empty text or `null`. A version-2
   `OrderStateChanged` whose `broker_order_id` is present and is neither (the empty string, a
   number, an array, an object, or a boolean) leaves its key in doubt, whatever readable id the
   key's other records carry. Its cancel is `NotSent` (`no_order_id`) and a `Submit` of it is
   `Unknown` (`Ambiguous`), with nothing called. A missing member (version 1) and `null` still
   carry no id and are not odd.
2. **Inheritance is read after the whole stream.** A successor without its own `OrderSubmitted`
   takes the instrument and side its origin has once every record is read, back through the
   `replaces` chain, never what the origin had when the successor's record arrived. So an
   `OrderSubmitted` of the origin that disagrees with an earlier one leaves both the origin and
   every successor that inherits from it in doubt, wherever it falls in the stream. A `replaces`
   chain that loops back on itself reaches no `OrderSubmitted`, so its keys are in doubt.
3. **A key's own submit wins wherever it falls.** DEC-872 item 3's "a key's instrument and side
   come from its own `OrderSubmitted`" holds regardless of record order: a successor's own
   readable `OrderSubmitted` that arrives after its `OrderStateChanged` gives it its own instrument
   and side, and its cancel goes by its one id with them. One that cannot be read, or two that
   disagree, still leave it in doubt (DEC-872 item 3).

Together, which keys are placed, by which id and with which instrument and side, depends only on
each key's own records and their relative order, never on how the stream interleaves different
keys' records.

## Rationale

The review of #1202 left three minors. An empty-string id was the key's one id, so a cancel could
go out with `order_id: ""`, and a non-string id was skipped, so the key could cancel by an id the
odd record may contradict. A successor kept its origin's instrument and side as they were when its
record arrived, so a later disagreement under the origin was missed. A successor's own submit that
arrived after its inheriting record left it in doubt, which fails closed but contradicts DEC-872
item 3. Items 1 and 2 refuse more. Item 3 places a key only where DEC-872 item 3 already says it is
placeable: the id rule (one unshared non-empty text id on the key's own records) is unchanged, and
the instrument and side are the key's own journaled ones, which is what DEC-872 item 3 prefers over
the chain. A cancel is risk-reducing (`AGENTS.md` rule 13), so leaving such a key in doubt only
because of record order would deny a cancel the journal fully supports.

## Alternatives considered

- Accept the empty string as an id: rejected, §9.16 rules it out and the cancel would name no
  order.
- Skip a non-string id and read the key's other ids: rejected, the record that carries it is
  corrupt, and nothing says which id is the broker's.
- Keep inheriting at the time the successor's record arrives: rejected, the result would depend on
  how the stream interleaves two keys' records, which journal order does not make meaningful.
- Keep a late own submit in doubt: rejected, it contradicts DEC-872 item 3 and denies a cancel the
  journal supports, with no id rule loosened by allowing it.
