## Context

DEC-1012 item 6 let `mandate-daemon` run only over an in-memory journal, and refuse without
`--fixture`, until the post-R0 hook wires production ports. The cell's `processes.json` listed the
runtime but marked it not built, so `cargo xtask cell demo` never started it, and the chart had no
way to start a service or probe it. This decision runs the same process, on the same deny-all
wiring, on the cell's Postgres journal.

## Decision

1. **The binary runs on the journal `MANDATE_JOURNAL_DSN` names.** Without `--fixture`,
   `mandate-daemon run` opens that journal through `mandate-store`'s `PgStore`, as the scheduler
   does, and with none set it refuses with `runtime_start_failed: journal_dsn_missing` rather than
   running on a journal of its own. `--fixture` keeps the in-memory journal. This supersedes DEC-1012
   item 6's "Without `--fixture`" sub-item only.
2. **The wiring stays deny-all in both.** Both journals run `fixture::wiring`: a gate that denies
   every proposal, a plan that proposes nothing, and a flatten planner with nothing held. The
   process can journal its own stream's opening and the owner's kill switch, and nothing else. No
   order can be proposed, and the crate still reaches no broker (`xtask/layers.toml`). The production
   ports remain the post-R0 hook (DEC-968 item 6, lane P5). Paper only, as before.
3. **The cell builds and runs it.** `cargo xtask cell up` builds `mandate-daemon` statically
   beside the CLI, as the `runtime` image (`deploy/cell/images/runtime.Dockerfile`: scratch,
   non-root, the binary only), tagged by the binary's SHA-256, imports it, and sets
   `images.runtime`. `processes.json` marks `runtime` built. Where the `mandate` image is pulled by
   digest instead, no runtime image is published yet, so the runtime is left out of that cell and
   the demo names it skipped.
4. **A service's launch lives in the process list.** A service in `processes.json` may carry
   `args`, which start it, and `probe`, its own binary asked `livez` or `readyz` over its socket on
   the pod's `/tmp` (DEC-994 item 5). `{workspace}` and the new `runtime` values (`agent`,
   `connection`, `owner`: ids only) fill them. The chart renders them as the container's arguments
   and its `exec` readiness and liveness probes, and Compose as its command and `CMD` health check.
   A runtime image named without its deployment fails the render rather than starting a runtime for
   no agent (`AGENTS.md` rule 3).
5. **The local cell runs one demo deployment.** `deploy/cell/values/k3d.yaml` names agent
   `demo-agent`, connection `demo-paper` and owner `demo-owner` in workspace `ws1`. `cargo xtask
   cell demo` reports the runtime ready; the paper agent part still waits on the executor, and so
   does research's model gateway line: a deny-all runtime runs no research loop, so that line waits
   for the post-R0 wiring rather than reading as ready.
6. **A stopping journal waits 10 seconds for its clients.** The journal chart's default for
   CloudNativePG's `smartShutdownTimeout` is 10 seconds (a value, at most 180), so it holds for every
   cell the chart renders, the managed one included, not only k3d. With the runtime in the cell, the
   restart drill went from 33 seconds to three and a half minutes, which fits the default 180-second
   smart shutdown waiting on the runtime's pooled connection before the fast shutdown that follows
   it anyway; that is the observed cause, not one a run has isolated. A fast shutdown aborts only
   uncommitted transactions; an acknowledged commit is durable (`synchronous_commit`, `fsync`).

## Rationale

The E2E lane needs the runtime running in the cell, and the cell's journal is the one the
runtime will run on after R0. Running the deny-all wiring there exercises the process's real
lifecycle: its epoch on Postgres, its probes, its drain on SIGTERM, and the chart's network policy,
without any route to an order.

## Alternatives considered

- **Keep `--fixture` in the cell.** The process would run, but on a journal of its own inside the
  pod, so nothing in the cell could see it, and the Postgres path would first run with the post-R0
  hook.
- **Wire production ports now.** That is the post-R0 hook's, and it touches R0's files.
- **Pass the deployment by environment variables.** The binary already takes flags. Filling the
  flags from values keeps one way to start it, in the cell and by hand.
