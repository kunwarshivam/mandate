# DEC-982: `cp-agent`'s inbound checks: a signed envelope over the canonical body, one pinned Ed25519 key per kind, and a port it declares

| | |
|---|---|
| **Status** | Accepted (agent: reversible engineering readings under DEC-79, taken under DEC-176; each only refuses more than design CP-5 requires, and none adds an effect) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (builder, managed-cells lane G0), under DEC-79, DEC-176, DEC-440 items 3 and 5, and DEC-921 |
| **Story or claim** | E20-3; plan DEC-967 lane G0; claim [#1436](https://github.com/kunwarshivam/mandate/issues/1436) |

Control-plane design §3 and CP-5 say that `cp-agent` verifies each inbound instruction against a
key pinned in the installed release, never the TLS channel, and hands it to workspace control
services, which journal it (journal spec §9.17, [DEC-981](DEC-981.md)) before it takes effect.
The design names no wire form, signature scheme, or interface. These are the readings this lane
takes in `mandate-cp-agent`.

## Decision

1. **The wire form.** An inbound message is one JSON object of at most `kind`, `key_id`, `body`, and
   `signature`, received in journal spec §4's canonical form (RFC 8785) and at most 64 KiB. A
   message in any other form, however its signature reads, is refused `malformed`: one document
   then has exactly one digest, so a replay re-spaced or reordered can neither dodge §9.17's
   de-duplication nor take the genuine message's sequence (the review of #1467). `kind` is one of
   `license`, `release_manifest`, `release_withdrawn`, `catalog_entry`, `data_bundle`; anything
   else, including every outbound kind and `receipt`, is refused `out_of_list` with `message:
   unknown` and no sequence (journal spec rule 142).
2. **What is signed.** The signature is Ed25519 over `mandate-cp/1 ‖ 0x00 ‖ kind ‖ 0x00 ‖ key_id ‖
   0x00 ‖ canonical(body)` (journal spec §4's canonical JSON), as 128 lowercase hex characters.
   Binding the kind and the key ID means a signature for one kind never verifies as another, even
   under the same key (a withdrawal relabeled as a manifest is `bad_signature`).
3. **One pinned key per kind.** The installed release pins `(key_id, kind, public key)` for the four
   offline keys of DEC-440 item 5: license, release, registry, data. A license verifies only under a
   license key, a manifest or withdrawal only under a release key, a data bundle only under a data
   key, and a catalog entry under the release key when its `kind` is `connector_package` and the
   registry key when it is `model_registry_entry` (design §3.8 allows either; this is the tighter
   reading). A key that is not pinned, or pinned for another kind, is `unknown_key`. A release pins
   each key ID once and only a 32-byte key; `pin` refuses anything else.
4. **The order of checks** fixes which reason is recorded: over 64 KiB or not JSON → `malformed`;
   kind outside the list → `out_of_list`; not canonical, or an envelope member outside the four →
   `malformed`; no signature → `unsigned`; key → `unknown_key`; signature → `bad_signature`; body
   outside its closed schema → `malformed`; a license that does not name this deployment →
   `not_addressed`. Whether its organization has a workspace here is workspace services' check,
   since a managed cell hosts many organizations. The body is parsed with the envelope, but only
   two of its members are read before the signature verifies: `kind`, to choose a catalog
   entry's key (a tampered `kind` then fails the signature), and `sequence`, recorded on a refusal
   when it is an integer of at least 1, so a refused replay is auditable; it is never trusted. The
   body's schema is judged only after the signature verifies.
5. **Closed bodies.** Each body has exactly the members journal spec §9.17 records (a manifest adds
   its image digests, at least one, by component, strictly ascending), with §9.17's rules 138 and
   139 applied before hand-over, so a verified instruction always maps onto a record `append`
   accepts. Integers are bounded by the canonical form, at most 2^53 − 1; a consumer doing date
   arithmetic with `grace_days` uses checked arithmetic.
6. **The port.** `cp-agent` declares `InstructionSink` with `hand_over(Verified)` and
   `refused(Refusal)`; workspace control services implement it. `Verified` has private fields and
   only `receive` builds one, so they can never be handed an unverified instruction (rung 1 of the
   trust ladder). The answer is `Journaled`, `AlreadyApplied` (the digest in effect, DEC-981 item
   5), `Refused` (CP-9's `replayed`), or `Unavailable` (nothing journaled, nothing applied; `cp-agent`
   keeps the message). Anti-rollback is the implementer's (DEC-981 item 4).
7. **Layering.** `mandate-cp-agent` is a pure, safety-critical layer-1 crate depending on
   `mandate-canon`, `mandate-time`, and `ring` (already registered, verification only outside its
   tests). Its `forbidden_internal` list names the journal crates, the mandate registry
   (`mandate-spec`), the runtime, the executor, the connections and vault crates, and the process
   crates, so it can never append, hold a writer epoch, place an order, or read a credential (CP-4).

## Rationale

Ed25519 is what `ring` already verifies for the passkey and token checks, so the crate adds no
dependency; a detached signature over our own canonical bytes avoids pulling in a JOSE or COSE
library. Domain separation by kind and key is the cheapest defense against a confused-deputy
replay across kinds. Requiring the canonical form costs one serialization and makes the digest a
document's identity. The size cap bounds what unauthenticated input can cost before the signature
is checked.

## Alternatives considered

- **JWS (or COSE) documents.** Standard, but needs a new dependency or a hand-rolled base64url and
  header parser, and its algorithm field is a known foot-gun. Rejected for v1.
- **Accept either release or registry key for any catalog entry** (design §3.8's literal "Release or
  registry key"). Looser than needed; rejected for the per-kind binding.
- **Verify in workspace services.** Would put the link's parser inside the journal writer's
  process boundary; the design puts it in `cp-agent`.
