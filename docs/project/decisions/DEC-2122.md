| **Story or claim** | E9-4 S3; claim #759; [journal spec](../../specs/journal.md) v0.71 §9.31, §9.32; [DEC-2108](DEC-2108.md) items 3 and 8; [DEC-2121](DEC-2121.md) |

## Context

DEC-2108 item 3 puts the assertion behind each passkey step-up on the record, as `StepUpAsserted`,
with rules 252 to 254 reserved for it. Its spec waited behind v0.69 and v0.70. Item 8 has the
verifier judge an assertion with `mandate_passkey::stepup::consume`, which also refuses an
assertion whose backup-eligible flag differs from the one recorded at enrolment. §9.31's
`CredentialEnrolled` does not record that flag, so the verifier would have nothing to hold the
assertion to.

## Decision

1. **`StepUpAsserted` is journal spec §9.32**, at schema version 1, with rules 252 to 254. It is
   unchanged from its draft except for its version: v0.71, since v0.69 and v0.70 landed first.
2. **`CredentialEnrolled` version 2 adds `backup_eligible`**, a boolean after `sign_count`: the
   registration's BE flag. It is the coordinator's option (a), the stricter of three. The others
   were reading the flag back from a stored copy of the registration, or dropping the check.
   Under (a) the check stays and its input is journaled.
3. **Version 1 stays registered and unchanged**, as `AgentDeployed` version 1 did when version 2
   came (DEC-1171). Rule 249 reads both versions alike, and existing readers and their vectors are
   untouched. The API writes version 2 only. A version 1 credential carries no flag, so the verifier
   never counts it for step-up: it fails closed rather than assume either value. No deployment
   holds a version 1 enrolment.
4. **Vectors.** Version 2 has its own `credential_enrolled_v2` section, so the `credentials` section
   stays what a version 1 reader checks. That section's version-refusal case moves from version 2 to
   version 3, which both readings refuse.
5. **The fold reads version 2 before anything writes it.** DEC-2121's fold (`mandate_passkey::credentials`,
   #2096 and #2116) maps `CredentialEnrolled` at version 1 only. It maps `StepUpAsserted` to an
   unread `Asserted` record, on which step-up's view fails closed and route 2's view skips. A
   version 2 row would fail to map, so neither view could be built, which would deny route 2's
   reduction-only opening (`AGENTS.md` rule 13). So the fold's reading of version 2, and of
   `StepUpAsserted`'s counter, ships before, or with, the first writer of either. That is the
   next tests-first pair, ahead of the enrol route that writes version 2 (S3.3).

## Rationale

Journaling the flag keeps `consume`'s check, and the input it judges stays on the record an auditor
replays. Keeping version 1 registered keeps every existing test and fixture valid, and a version 1
credential that never steps up costs nothing, since none exists.

## Alternatives considered

- **Read the flag from a stored copy of the registration's authenticator data.** Rejected: it adds
  an artifact the verifier must fetch and parse, and the fact still isn't on the record.
- **Drop the backup-eligible check.** Rejected: it weakens a check `consume` makes today.
- **Change version 1 in place.** Rejected: version 1 is closed and registered (#2068). Changing it
  would break a reader and the vectors it checks.

## Follow-ups

- The tests-first pair that registers `CredentialEnrolled` version 2 and `StepUpAsserted` in
  `mandate-journal`, and teaches DEC-2121's fold to read both.
- The verifier slice: build `stepup::EnrolledCredential` from a version 2 enrolment, its key
  artifact, and the greatest asserted counter.
