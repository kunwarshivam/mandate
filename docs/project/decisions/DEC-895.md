## Context

DEC-893 item 1 runs §11 check 1 on the start row only, after §9.14's lookup found it. Two readings
were left open:

- The reference read row bodies for the lookup with a lenient `json.loads`, so a body with a
  repeated key still matched and counted towards `ambiguous_start`. A Rust lookup built on
  `mandate_canon::parse`, which rejects repeated keys, skips that row and starts from another
  match. The two disagree, and the Rust outcome is the looser one: a row whose payload a parser
  that keeps the first value reads one way and a parser that keeps the last reads another is
  silently ignored.
- DEC-787 item 3 names checks 1, 2 and 4, none of which compares an `AnchorComputed`'s `root` with
  its `leaves`. A leaf `hash` edited and the row re-hashed passed all three, and the anchor started
  the range at the forged hash.

## Decision

1. **Every candidate row passes §11 check 1 before the lookup.** For a manifest or anchor request,
   a row on the control stream of the range's own workspace (by its columns) whose `event_type`
   column is the one the request needs (`SegmentExported` for a manifest request, `AnchorComputed`
   for an anchor request) and whose body does not parse with duplicate keys rejected and
   re-canonicalize to its own bytes refuses the request, whichever record it might be. Its payload
   cannot be known, so it can never be skipped, and it is never counted as a match either. The
   cause in the reference vectors is `non_canonical`, §11 check 1's own code, whose text already
   includes "duplicate keys rejected": the check is the same, it runs on more rows. A separate code
   such as `unreadable_candidate` was not taken because it would split one check's failure into two
   names and change no outcome; the Rust error stays `TrustedStartError::Refused` (DEC-893 item 5).
   Genesis reads no row and is unaffected.
2. **An anchor start row passes §11's root check.** After checks 2 and 4 (item 1 having run check
   1), an `AnchorComputed` start row's leaves must be in strictly rising `stream_id` byte order and
   §10's Merkle root over them must equal its `root`, as `verify_anchor`'s `AnchorRootMismatch`
   requires; otherwise the start is refused, cause `anchor_root_mismatch`. `verify_anchor` checks
   the leaf order as well as the root, so both are required here.
3. **The vectors and the resolver catch up.** `cold_records.trusted_starts.row_cases` gains four
   cases: a duplicate-key copy of the start `SegmentExported` beside the good row, and of the start
   `AnchorComputed` beside the good row (both `non_canonical`), an anchor whose leaf `hash` was
   edited and the row re-hashed, and one whose leaves were reversed with the root recomputed over
   them (both `anchor_root_mismatch`). The seeded bugs `row.skip_unparsed`, `row.anchor_root` and
   `row.anchor_order` are each caught. Existing keys and cases are unchanged.

## Rationale

Both readings refuse where the earlier reading starts, and refusing a start changes no state: the
run is 422 `trusted_start` with nothing recorded, and the caller can retry once the store is
repaired (DEC-894 item 2's alert, E12-7, covers telling an operator). Item 1 makes the outcome
independent of how a parser treats a repeated key, which is the property check 1 exists for. Item 2
holds the start to the same anchor check the range walk applies, so a start is never trusted on an
anchor the run itself would report as `anchor_root_mismatch`.

## Alternatives considered

- **Skip a candidate that does not parse.** Rejected: it is the looser reading, and which record
  the row holds cannot be known.
- **Refuse on any control-stream row that fails check 1, whatever its type.** Not taken: a row of
  another type is never a match for the request, and the narrower rule closes the ambiguity. It
  stays open as a later tightening.
- **Check only the root, not the leaf order.** Rejected: `verify_anchor` requires both, and an
  anchor out of order is malformed under rule 113.
