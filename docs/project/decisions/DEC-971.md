## Decision

1. **One image a release binary, written byte for byte by xtask.** `cargo xtask release images`
   writes an OCI image layout for each binary of a [DEC-972](DEC-972.md) release: an empty base,
   one uncompressed tar layer holding only the static binary at `/<binary>` (owned by root, mode
   0555), and, when the binary is signed, a second layer holding only `/<binary>.sig` (0444). The
   config runs the binary as its entrypoint as user `65532:65532`, with no `Cmd`, no environment,
   no working directory, no shell and no account. An image is a pure function of its binary and
   signature, so it needs no Docker daemon, and the binary's layer is the same whoever signed it.
   A read-only root filesystem is the pod's setting (E21-36's chart); nothing in the image writes.
   `mandate-rh-sim`'s image is the loopback test double for the local cell's drills (DEC-124),
   never a broker.
2. **The start-up check (OPS-15)** is `mandate-release`'s `startup::check_running`, which a
   process runs before anything else. It reads its tier from `MANDATE_DEPLOYMENT_TIER` (`dev`,
   `ci`, `staging`, `production`). **No setting, or one it does not know, is production.** It reads
   the running executable's bytes (`/proc/self/exe`) and the signature beside the path it started
   from (`<executable>.sig`, or the file `MANDATE_RELEASE_SIGNATURE` names), a cosign signature:
   ECDSA P-256 with SHA-256, DER, base64, verified with `ring`. Then:
   - a signature that verifies against a **compiled-in release key** (`startup::RELEASE_KEYS`)
     starts in every tier, as `release`;
   - in **dev and CI only**, an unsigned build starts as `unsigned`, and a signature that verifies
     against the test key `MANDATE_RELEASE_TEST_KEY` names starts as `test`. Outside dev and CI the
     test key's file is not even read;
   - every other case is refused, with a generic code and exit status 2: `release_unsigned`
     (no signature outside dev and CI), `release_signature_not_verified` (a signature no trusted
     key verifies, **in every tier**), `release_signature_malformed`, `release_unreadable`.
   The admitted value carries the build digest, which the process journals as `actor.build`.
   The tier is a setting of the pod, so whoever can set a pod's environment can run an unsigned
   build as `ci`: the chart (E21-36) sets `MANDATE_DEPLOYMENT_TIER` itself, from the cell's values,
   and no tenant or workspace input reaches it. A wrong signature is refused whatever the tier.
3. **Where the check runs.** `mandate-agentd` runs it first in `main`. `mandate-rh-sim` does not:
   it is the test double, never run against a broker. `mandate` (the CLI) runs it after R0, with
   DEC-972 item 7's slice, because its entry is R0's (DEC-967 item 2). The long-running processes
   E21-30 adds run it through `mandate-process`'s start-up hook (E21-28) once that lands.
4. **CI signs only with an ephemeral test key.** `release images --test-sign` makes a cosign key
   pair with no password, signs each binary offline (no transparency log), deletes the private
   half, and keeps the public half. `release drill` then runs `mandate-agentd` from three images
   unpacked as a runtime unpacks them (the test-signed one, the same binary unsigned, and one
   signed by a key nothing trusts) and requires the refusals and admissions item 2 states. Every
   `release` workflow run does this, pull requests included.
5. **Publishing: from a push to `main` only, to GHCR, by digest** (per arch, under one
   multi-arch index: [DEC-1060](DEC-1060.md)). The `publish` job holds the
   only `packages: write` and `id-token: write` in the workflow, runs only on a push to `main`
   (an xtask test checks both), rebuilds the release and requires `build-a`'s digest, then pushes
   each image to `ghcr.io/kunwarshivam/mandate/<binary>` as `main-<commit>`. It requires the
   registry to report the image's own digest, signs that digest keyless with cosign under the
   run's GitHub OIDC identity, attaches the binary's SBOM as a CycloneDX attestation, and keeps
   `PUBLISHED` (each `image@sha256:…`) as the run's artifact. The push uses the OCI distribution
   API through `curl`, with the token only in 0600 header files and cosign's stdin, never on a
   command line or in a log, and an upload location the registry names on another host is
   refused, so the token goes only to the registry. The repository is public, so its GHCR images
   cost nothing (H5); GHCR makes a new package private, so the founder sets each of the three
   public once after the first `publish` (no spend), or the cell pulls with a read token.
6. **Promotion.** `main` → the local cell's CI drills (lane C1 pulls the images by digest, or uses
   the run's layouts) → staging once H1 exists, as its own story. Nothing deploys from a branch.
   Published images carry no binary signature until item 7 is decided, so they start only in dev
   and CI.
7. **Proposed, the founder's:** the founder's hardware key (ES-17, H8) is the only release key,
   and none is wired: `RELEASE_KEYS` is empty, so today **no binary starts in staging or
   production**. The founder decides (a) when to add the hardware key's public half to
   `RELEASE_KEYS` and sign releases with it off CI, and (b) whether hosted cell #1, paper and demo
   only, may run before that as `ci`. Until the founder answers, the conservative option holds:
   nothing starts outside dev and CI unsigned.

## Rationale

OPS-15 asks for a start-up check that refuses an unsigned binary outside dev and CI, and infrastructure §11 asks
for distroless, non-root images with no shell. An attacker who could change a pod's environment
could set the tier to `dev`, so the tier only loosens what is unsigned or test-signed, never what a
wrong signature is: a wrong signature is refused everywhere, and the release keys come from the
binary itself, not its environment. Keyless signatures prove which workflow published an image,
but checking them needs Fulcio's chain and Rekor at start, so the in-process check verifies
against pinned keys. Writing the layout in xtask gives a reproducible image without an unpinned
daemon.

## Alternatives considered

- **`docker buildx` or `ko`:** a daemon or tool outside D-7, and image digests that depend on it;
  the image is three JSON documents and a tar.
- **A tier taken from the trading environment** (live means production): the check would then pass an unsigned binary
  running paper in a hosted cell, which OPS-15 forbids.
- **A trust file read at start in every tier:** whoever can change the pod could add a key.
- **Keyless verification in process:** Fulcio's chain and an online transparency log at every
  start, for a check that a pinned key does offline.
- **`cosign load` to push:** it only reads layouts `cosign save` wrote.
