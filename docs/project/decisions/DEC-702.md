# DEC-702: The notice id is minted through an injected secure-random source

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The L3 builder agent under DEC-79 (a reversible engineering decision) and DEC-176 (it only tightens DEC-438 item 10) |
| **Story or claim** | E8-16, claim [#753](https://github.com/kunwarshivam/mandate/issues/753); [notifications spec](../../specs/notifications.md) §4.2, §10; E8-9, E8-10 |

## Decision

1. **The source is a trait** in `mandate-notify` that yields 128 random bits. `mandate-dispatcher`
   implements it over the operating system's CSPRNG in production; tests inject a deterministic
   fixture, so every test that depends on an id replays exactly.
2. **`NoticeId` has no constructor from an event id** or any other journal value. It is made only
   by minting from the source, or by parsing exactly 32 lowercase hex digits (to resolve a link),
   which no ULID is.
3. **The Telegram linking code** (DEC-700 item 2) uses the same source.

## Rationale

DEC-438 item 10 keeps event ids, whose leading bits are their creation time, out of payloads. A
type with no path from an event id holds that at rung 1, and an injected source keeps the pure core
free of I/O while letting tests pin ids without weakening production randomness.

## Alternatives considered

- **Call the OS random source inside `mandate-notify`.** Rejected: the crate is pure, and tests
  could not replay ids.
- **Derive the id from the event id with a keyed hash.** Rejected: one leaked key would link every
  notice to its event, and a derivation is a constructor from an event id.
