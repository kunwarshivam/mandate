# DEC-698: When several refusals hold for an ordinary revoke, it refuses with the first in a fixed order, step-up first

## Decision

1. **An ordinary revoke (`plan_ordinary`) that more than one refusal holds for refuses with the
   first of these, and only that one:**
   1. `StepUpNotVerified`: the step-up evidence for the request's digest does not count.
   2. `FoldCannotAnswer`: the agents fold or the positions fold cannot answer (DEC-693 item 7).
   3. `PositionsHeld`: the positions fold answers that positions are held.
   4. `AgentsNotStopped`: the agents fold answers that an agent on the connection is not stopped.
2. With none of them holding, it commits `[ConnectionRevoked (owner)]`, as before.
3. The compromised revoke is unchanged: it takes no fold, and without valid step-up it still
   commits the kill switch alone ([DEC-697](DEC-697.md)).
4. A test pins the order exhaustively over every combination of step-up, agents fold, and
   positions fold, with its own oracle, so a swap of any two refusals fails it.

## Rationale

- **Step-up first.** A caller whose step-up does not count learns nothing about the account's
  agents, positions, or folds. Any other order would let an unverified caller tell "positions
  held", "agents running", and "fold behind" apart by trying a revoke, which is account state the
  step-up is meant to gate (§5.6, API-17). Position state stays with those who may act on it, as
  `AGENTS.md` keeps it out of notifications and logs that leave the deployment.
- **`FoldCannotAnswer` before `PositionsHeld` and `AgentsNotStopped`.** No refusal states a fact
  the folds did not establish (DEC-693 item 7). If one fold cannot answer, a `PositionsHeld` or
  `AgentsNotStopped` from the other would still be read as the whole answer; the owner is told to
  retry or use the compromised path instead.
- **`PositionsHeld` before `AgentsNotStopped`.** Both are established facts; positions are the
  one that matters to the owner deciding what to do next (flatten before revoking), and a fixed
  order makes the refusal deterministic and testable.
- An order is a tightening: every request refused before is refused now, with one fixed reason.

## Alternatives considered

- **Leave the order to the implementation.** Rejected: the review of the R1 implementation found
  that swapping `PositionsHeld` or `FoldCannotAnswer` ahead of `StepUpNotVerified` passed every
  test, and that swap leaks position and fold state to a caller without step-up.
- **Report every reason that holds.** Rejected: it leaks the same state to an unverified caller,
  and §3.5 gives one error code per response.
- **`AgentsNotStopped` before `PositionsHeld`.** Equally safe; rejected only to keep the order the
  implementation documents.
