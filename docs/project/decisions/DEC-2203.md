## Context

Agent harness spec v0.1 made a research run one model call over a context that deterministic code
assembled: the model named no read (HI-4) and the gateway offered no tools (INF-5). §13 item 6 left
multi-call runs open. The founder has now closed it:

> "it has to be agentic harness, as what we are selling/the product is agent harness for trading."

and framed the shape as "like Claude Code for trading": one agent loop per agent, read tools that
run freely within bounds, action tools that are proposals mediated by the deterministic harness as a
coding agent's permission system mediates its tool calls, the autonomy policy as the permission mode,
the owner's instructions as owner input inside the envelope, the journal as the transcript, and
pause and the kill switch as the interrupt. The trading side does not change: the model writes
opinions, never orders (`AGENTS.md` rule 4), and the order builder, the gate, the autonomy rules,
and the envelope are untouched (rule 11).

## Decision

1. **The research run is an agent loop (the founder, 2026-10-17).** A run is a bounded sequence of
   model turns. In each turn the model calls tools or ends the run.
2. **The core owns the loop; the worker does the I/O.** Each turn is one gateway call, with its own
   call id, reservation, and `ModelInvocationRecorded`. The core journals each turn's record, mediates
   its proposal calls in the batch that record heads, dispatches its reads only after that, journals
   every item a read returned as `ObservationRecorded` and every tool call as `ToolCallRecorded`,
   and only then emits the next turn. The loop's state and bounds are a pure fold of the run's
   records (`mandate-research-run`), so a replay recomputes them. The worker never appends (HI-16).
3. **The mode is pinned content.** The research entry gains `mode` (`single_call` or `agentic`), its
   tool declarations, and its loop bounds, inside the content hash, and left out of a `single_call`
   entry's canonical object, so no existing hash or pin changes. Moving an agent to `agentic` is a
   new signal-model version the owner confirms, and its confirmation screen says what changes.
   Mandate spec §8.1's definition of the content hash names them too: the hash covers more, which
   only tightens (DEC-176).
4. **Read tools read only from the store.** `news`, `filings`, `filing_text`, `bars`, and `quote`
   take typed arguments (data-universe symbols, bounded windows and counts, item ids the run already
   received, at most five search terms) and read the workspace data service's point-in-time store
   (data-plane spec §4.6) under the run's frozen scope. A tool call never causes a fetch from a
   source, so no text the model wrote leaves the deployment except in its own gateway call (HI-26).
   A `fundamentals` tool waits for the data plane's XBRL facts.
5. **Proposal tools map onto paths that already exist.** `propose_thesis` is a candidate thesis:
   §6.5's checks, then §8.5's admission, then the builder at its scheduled evaluation, with the
   admission ceiling on its first order. `propose_entry` (instrument and thesis; no side, size, or
   price) is a dry run of the evaluation for that instrument: the builder sizes, the gate dry-runs,
   §6.2 classifies AUTO, ASK, or DENY, and nothing is submitted; the order, if any, is the next
   scheduled evaluation's, since an evaluation the cadence does not list would change an envelope
   field. The model is told the classification and a reason code, never a size, price, or dollar
   figure. `invalidate` and `propose_exit` are the invalidation of §6.7 (E19-5's record): removal,
   built-in AUTO, exits paced and never denied. `note` stays in its run's record and nothing reads
   it. No proposal is a new way to an order.
6. **The gateway returns tool calls as data and runs none.** INF-5 becomes: the gateway offers the
   model only the tool declarations pinned in its entry, and executes nothing. A reply is a final
   output or one to four tool calls, each naming a tool offered in that turn with arguments valid
   against its pinned schema; a reply with any tool call is a tool-call reply. Anything else is
   `schema_invalid`, so the error kinds and the journal's `outcome` set stay as they are. Provider
   plugins, web search, code execution, and `transforms` stay off. DEC-997 item 2's routing lock
   keeps its other members; its "no `tools`" member is amended only for these pinned declarations,
   and stays with DEC-997's acceptance by the founder.
7. **The last turn offers proposals only.** The model can still give its opinion in turn
   `max_turns`, but read no more. Once no tool call is left, no tool is offered and the model must
   end. The model is told its run kind and remaining turns and tool calls in every turn.
8. **Every bound ends the run.** Pinned defaults, engineering values (DEC-431 item 7's rule): 6
   turns, 16 tool calls a run and 4 a turn, 4 theses, 24,000 bytes a read and 96,000 a run, a
   900 s deadline on the risk clock, and a 10 s read timeout. A reply asking for more tool calls than
   are left runs none of them; each is recorded refused `call_budget`, and the run ends. A turn the
   run's ceiling cannot cover ends `budget_exhausted`. The deadline cancels the run. Only result
   size trims, because the model cannot know it before it asks.
9. **Budgets are configuration, and no figure is hardcoded.** The founder clarified on 2026-10-17:
   "$50 is my demo cap and not customer". DEC-997 item 3's $50 a month is the platform's own
   provider spend for the demo and dev deployment: a deployment setting, separate from every
   workspace's. A workspace's monthly budget, its per-agent caps, and its per-run ceiling
   (`research_run_cost_cap_usd`) are its own configuration. With no run ceiling set, no agentic run
   starts (rule 3). The request carries `spend_ceiling_usd`, the ceiling less the run's earlier
   turns' cost as the core folds them, and the gateway admits a turn only if its reservation fits
   under it and under every other cap. It only refuses.
10. **Records.** Journal spec v0.49 §9.22 closes `ToolCallRecorded` (the turn, its index, the tool,
    arguments and result as artifacts, result and reason, bytes, `truncated`, the observations it
    returned) and `ResearchRunEnded` (kind, how it ended, turns, tool calls, bytes), with rules 171
    to 177. `ModelInvocationRecorded` is unchanged: a turn's candidates under rule 151 are its
    proposal calls. Lane I2's E19-5 change takes v0.48 and the rules from 165; whichever lands
    second renumbers.
11. **A run replays from the journal, and re-runs from its recorded responses.** Replay never calls a
    model (HI-3). Driving the loop again with the recorded fake keyed by each turn's
    `request_digest`, over the same store snapshot and the run's frozen scope, with recorded read
    failures replayed as recorded, reproduces every record of the run byte for byte (HI-25). That is
    what CI and the demo run on.
12. **A crash ends the run; no resume yet.** Turns already recorded stay; reservations stay counted;
    no turn is re-sent under its old call id; a run is never resumed, because the turn in flight has
    no journaled start to attribute its reservation to. A journaled turn start, and resuming from it,
    is E19-14.
13. **The single call stays, with no runtime fallback.** `single_call` entries stay registered and
    pinnable. A failed agentic run is missing; it is never retried as a single call, because a second
    try until something answers would select outputs (DEC-432 item 3). The internal paper and demo
    agents may pin an agentic entry once E19-6's adversarial bench and a §8.3 regression evaluation
    pass on it; users' agents also need its own DEC-99 forward evaluation (DEC-431 item 16).
14. **Proposed (founder, compliance): may the agent propose mandate changes?** The coordinator asked
    for `propose_mandate_change`: a draft new version with a diff and reasons, always ASK whatever
    the autonomy policy, entering as a platform proposal of envelope values (mandate spec §7),
    reviewed by the owner with the validator and change classification, confirmed only with
    step-up, rate-limited per agent, expiring with no change when unanswered. A platform agent that
    proposes, say, a larger position limit comes close to platform-generated advice (`AGENTS.md`,
    "Do not"), so whether it may and how it is worded is the founder's (DEC-79, compliance text).
    The spec specifies it; no entry declares it until the founder accepts.
15. **Proposed (founder, pricing): who pays for a customer's model calls,** a plan's allotment or
    the customer's own provider key. Both work as designed: `key_owner` and the caps serve either
    (inference spec §7.1, §7.4). Until decided, internal workspaces use the platform key.
16. **Two run kinds, one loop.** `ideate` (mode `normal`, room in the working universe; every
    proposal tool) and `monitor` (`exits_only`, or a full universe, with an active thesis; only
    `invalidate`, `propose_exit`, and `note`, over held instruments and active theses). Both run on
    `behavior.research.interval_s`; a monitoring interval of its own is a new envelope field, so
    E19-14 with a mandate spec change.
17. **The run's scope is frozen at its start:** cut-off, allowlist version, and data universe. A
    change mid-run never widens a read; what the run proposes is judged under the version in effect
    when it is mediated (HI-17).
18. **`ask_owner` waits for its records.** It needs a journaled question, an in-app delivery with
    an opaque notification (rule 6), and a control-stream answer a later run reads as owner input.
    The spec states its contract; E19-14 adds the journal and notifications changes, and no entry
    declares it until then.

## Rationale

The founder's item 1 is the product. The rest is how to take it without moving a risk boundary: the
model chooses what to read, inside the data universe, the allowlist, the cut-off, and a budget, and
it gives opinions through proposals that land on paths the mandate already governs. A fooled model
can read more allowlisted data, spend up to its run's ceiling, and propose; it still cannot size,
price, place, approve, or change the envelope, and everything it proposes is admitted or classified
by the same deterministic rules as before (HI-10). Every step is journaled before it is used, so
INF-10 and DP-3 hold per turn as they held per run.

## Alternatives considered

- **Tools as a tagged union in the output schema:** works without provider tool support, but weaker
  models fill it poorly, and it is tool use under another name. Native tool calls with gateway-side
  validation keep the same boundary.
- **Execute tools inside the gateway:** the gateway would need data-plane access and the order
  builder, and would stop being the one place that only brokers calls.
- **`propose_entry` triggers an evaluation at once:** an evaluation the cadence does not list changes
  an envelope field (rule 11, as E19-12 found for event triggers), so it only classifies.
- **Let the model fetch URLs or search the web:** breaks DP-9 and DEC-101, and opens exfiltration
  through query strings.
- **Truncate on every bound instead of ending the run:** keeps going after the model asked for more
  than it was allowed. Only result size, which the model cannot know, trims.
- **Fall back to a single call, or resume after a crash:** a second sample after a failure selects
  outputs; a resume cannot count the lost turn's reservation without a journaled turn start.
- **A per-run cost figure pinned in the entry:** budgets are the workspace's to set, and the founder
  asked that none be hardcoded.
