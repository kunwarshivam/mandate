## Context

Agent harness spec v0.1 made a research run one model call with no tools, over a context that
deterministic code assembled. The founder closed that on 2026-10-17:

> "it has to be agentic harness, as what we are selling/the product is agent harness for trading."

and described the shape as "like claude code for trading". The coordinator turned that into a
design input and a research memo (HybridAgent and about twenty other sources), which ADR-0005 lands
with the departures it records. The trading side does not change: the model writes opinions, never
orders (`AGENTS.md` rule 4), and the order builder, the gate, the autonomy rules, and the envelope
are untouched (rule 11).

## Decision

1. **The research run is an agent loop (the founder, 2026-10-17).** A run is a bounded session of
   model turns and tool calls, with a trigger, a context, a budget, and a transcript.
2. **The core owns the loop; the worker does the I/O.** Each turn is one gateway call with its own
   call id, reservation, and `ModelInvocationRecorded`. The core journals each turn's record with its
   tool calls, mediates any action in that batch, dispatches reads and thinks only after it, journals
   every item a read returned and every result, and only then emits the next turn. The loop's state
   folds from the run's records (`mandate-research-run`), so a replay recomputes it. The worker never
   appends (HI-16).
3. **The mode is pinned content.** The research entry gains `mode` (`single_call` or `agentic`), its
   tool declarations, and its loop bounds, inside the content hash, and left out of a `single_call`
   entry's canonical object, so no existing hash, pin, or recorded request digest changes. Moving an
   agent to `agentic` is a new version the owner confirms, with a confirmation-screen disclosure.
   Mandate spec §8.1's definition of the content hash names them too: the hash covers more, which
   only tightens (DEC-176).
4. **Read tools read only internal stores.** `market.bars`, `market.quote`, `news.search`,
   `news.get`, `filings.search`, `filings.get`, `memory.positions`, `memory.theses`, `memory.runs`,
   `records.query`, and `mandate.read` read the data service's point-in-time store or the agent's own
   folds, under the run's frozen scope. A tool call never causes a fetch, so no argument the model
   wrote leaves the deployment (HI-28). `market.screen`, `fundamentals.get`, and `calendar.get` are
   declared when the data plane serves them.
5. **The guaranteed path ends in today's structured output.** An `agentic` entry pins
   `final_output` (the run reads and thinks, and ends with `{theses, invalidations}` plus a typed
   `watch` list, judged once by §6.5 as a single call is) or `action_tools` (`propose_thesis` and
   `invalidate` mediated mid-run with their verdicts fed back). `final_output` is the demo's path;
   `action_tools` follows when its evaluations pass (item 13), with its theses committed only at a
   normal end (item 25).
6. **The gateway returns tool calls as data and runs none.** INF-5 becomes: the gateway offers the
   model only the run's menu of pinned declarations, and executes nothing. A reply with any tool call
   is a tool-call reply; an undeclared or unoffered tool, invalid arguments, or more calls than the
   per-turn bound is `schema_invalid`. Provider plugins, web search, code execution, and `transforms`
   stay off. DEC-997 item 2's routing lock keeps its other members; its "no `tools`" member is
   amended only for pinned declarations, with the founder's acceptance of DEC-997.
7. **Menus are fixed per run kind, before anything untrusted is read.** Tools outside the menu are
   left out of every turn's schema. A `monitor` run gets read and think tools and only risk-reducing
   actions; only an `ideate` run may propose a thesis. The last turn offers only action tools, or
   none; once no tool call is left, none.
8. **Every bound ends the run, except result size.** Pinned defaults, engineering values (DEC-431
   item 7's rule): 8 turns, 24 tool calls a run and 4 a turn, 4 theses, 24,000 bytes a read and
   96,000 a run, two identical denials, a 900 s deadline on the risk clock, a 10 s read timeout. A
   reply over the tool calls left runs none of them; a bound reached in a reply's batch refuses that
   call and every call of the reply with no result yet (`run_ended`), so every call still has one
   result, and only mediated calls are rule 151 candidates. The core screens reads against the
   frozen scope before any dispatch. A reply's invalidations are mediated before its theses, as E19-5
   judges them (DEC-2202). A
   `monitor` run's pinned output schema has no theses. The model cannot know a result's size before it
   asks, so only size trims.
9. **Budgets are configuration; no figure is hardcoded.** The founder clarified on 2026-10-17: "$50
   is my demo cap and not customer". DEC-997 item 3's $50 a month is the platform's own provider
   spend for the demo and dev deployment, a deployment setting. A workspace's monthly budget,
   per-agent monthly caps, and per-run ceiling (`research_run_cost_cap_usd`) are its own
   configuration, read from deployment configuration until a policy key exists, and with no run
   ceiling set no agentic run starts (rule 3). Each turn reserves its own maximum through the meter,
   and the request's `spend_ceiling_usd` (the ceiling less the run's earlier turns) lets the gateway
   refuse a turn the run cannot afford. Reserving a whole run up front, as the design input
   proposed, would hold budget other agents need and count the whole run at its maximum after a
   crash.
10. **Records.** Journal spec v0.50 §9.23 closes `RunStarted`, `ToolCallRecorded`,
    `ToolResultRecorded`, `RunSummaryRecorded`, and `RunEnded`, with rules 171 to 183. v0.48 and
    rules 165 to 168 are DEC-1170's, and v0.49 (§9.22, rules 184 to 187) is lane I2's E19-5
    (DEC-2202); lane EX's explainer takes the rules from 190; whichever lands later renumbers its
    version.
11. **A run replays from the journal, and re-runs from its recorded responses.** Replay never calls a
    model (HI-3). Driving a run again with the recorded fake keyed by each turn's `request_digest`,
    the same store snapshot, the run's frozen scope, and its recorded read failures reproduces every
    record byte for byte. CI and the demo run on that.
12. **A crash ends the run; no resume yet.** Recorded turns stay, reservations stay counted, no turn
    is re-sent under its old call id, and a run is never resumed: the turn in flight has no journaled
    start to attribute its reservation to. A journaled turn start, and resuming from it, is E19-14.
13. **The single call stays, with no runtime fallback.** `single_call` entries stay registered and
    pinnable. A failed agentic run is missing and never retried as a single call (DEC-432 item 3). The
    internal paper and demo agents may pin an agentic entry once E19-6's adversarial bench and a §8.3
    regression evaluation pass on it; users' agents also need its DEC-99 forward evaluation (DEC-431
    item 16, DEC-103).
14. **`propose_exit`: yes (the founder, 2026-10-17).** A research exit request is a new origin of
    `discretionary_exit` in mandate spec §6.1: the order builder exits the agent's whole position in
    the instrument at its next scheduled evaluation (cadence unchanged), paced by the conduct
    controls, deferred outside the regular session for equities, and never denied (rule 13). It
    reduces risk, so it takes effect at once and stands however the run ends; it is mediated after
    invalidations and before theses, and its result (`exit_requested` or `not_held`) is what the
    core folds the request from. It is declared, like `invalidate`, only in an `action_tools` entry, and only once E19-14 adds
    what the order path needs: a structured record of the request with its instrument, a fourth
    `DecisionMade.exit_origin` (journal spec §9.1, rule 8), mandate spec §8.3's builder branch for a
    stored request, and trading-domain spec §9.1's origin.

15. **`propose_mandate_change` at any time (the founder, 2026-10-17).** `ideate`, `monitor`, and
    `owner` runs may propose. The safeguards stay: always ASK whatever the autonomy policy, the diff
    shown with its §9.2 classification, step-up to confirm, never applied by the model, expiring
    unanswered, rate-limited (HI-27). A `monitor` run, and any event-triggered run once those exist,
    may propose only a change the classification calls risk-reducing; risk-increasing proposals come
    from scheduled `ideate` and `owner` runs. Declared once E19-14 adds its record and the draft path
    to the owner.

16. **Who pays: both, from day one (the founder, 2026-10-17).** A plan's monthly model allowance and
    an optional bring-your-own key, for every deployment, managed included, metered per workspace
    either way; this supersedes DEC-432 item 16's platform keys only for managed deployments. A
    customer's key lives in the vault, is used only by the gateway, and is never shown to a model or
    logged (rule 7).

17. **Event triggers wait for a mandate spec change.** A run started by a news item, a filing, a
    price move, a fill, or a refusal adds an evaluation trigger the mandate does not list, and
    triggers are envelope fields (rule 11), as E19-12 found. `ideate` and `monitor` runs are
    scheduled until E19-14 adds triggers, their debounce, and their rate limit.
18. **The run's scope is frozen at its start** and journaled in `RunStarted`: cut-off, allowlist
    version, data universe, ceiling, deadline, menu. A late reply to a cancelled run is still
    journaled after its `RunEnded`, with no verdicts and no tool calls, and an item already on the
    agent stream is named again, never re-observed. A change mid-run never widens a read; what the
    run produces is judged under the version in effect when it is judged (HI-17).
19. **The agent sees its limits as percentages of the allocation, never amounts (the founder,
    2026-10-17).** `mandate.read` shows the envelope's limits that way; HI-11 and §6.4 admit
    percentages and still forbid every dollar figure of the agent or account. Refusal codes still
    carry no limit value.

20. **`ask_owner`: in-app, with an email ping of generic text only (the founder, 2026-10-17).** The
    ping says the agent has a question and carries an opaque id, never the question (rule 6);
    unanswered questions expire with no action. Declared once E19-14 adds the question and answer
    records and the delivery.

21. **Untrusted text is contained.** Every action records its provenance; tool results are
    spotlighted as data (defence in depth only); corroboration is computed from the platform's own
    reads, the run's seed, never from the model's tool reads (HI-18, mandate spec §8.4); the model
    sees only a closed set of codes, mapped from §8.5's seventeen reasons, and every reason that
    reflects an autonomy rule, a halt, a budget, a disclosure, another agent, or account state
    reaches it as `not_admitted`; the gate's reasons never reach it; a second identical refusal ends
    the run. Every model-written text a surface shows passes the `forbidden_language` check first.
22. **The serving regime is pinned.** The reasoning mode and effort and `top_p` join temperature and
    the seed in the pinned content and the canonical request; the OpenRouter provider stays locked
    with fallbacks off (DEC-67). The prompt's order is stable (system prompt, tool schemas, brief,
    memory, trigger, transcript) so prompt caching serves the prefix.
23. **Run summaries are typed and read back as untrusted:** instruments read, a `watch` list from a
    closed set of reasons, and counts. No free prose. Instruments are asset IDs (journal spec §9.3's
    `asset_id`), as the thesis records' are.
24. **What stays the same in the records:** `ModelInvocationRecorded` gains no turn index (its order
    in the run gives it, and the record is closed and being registered); no compaction under v0.2's
    bounds.

25. **Risk-increasing proposals commit only when a run ends normally (a tightening, DEC-176; the
    coordinator's proposal of 2026-10-17).** In an `action_tools` run, `propose_thesis` gets a
    provisional verdict mid-run (§6.5's checks and §8.5's admission against the core's fold), fed
    back as `admissible` or a code. It takes effect only when the run ends `done` (the model ends it,
    or its last turn completes): the core judges it again against the state at that moment and
    journals that judgment as its thesis record. Any other end discards every pending thesis, listed
    in `RunEnded.discarded`. Risk-reducing actions (`invalidate`) take effect at once and stand
    whatever ends the run (rule 2, MI-19). So no end that cuts a run off (a cap, the ceiling, the
    deadline, a bound, a mode or version change, an error) leaves an admission the uncapped run would
    not have made, and HI-9 holds in its strict form for every mode. `max_turns` and an exactly spent
    tool-call budget are the run's announced shape, told to the model every turn: they end it `done`,
    named in `RunEnded.bound`, and HI-9 compares them with a run whose model ended at that point. A
    thesis §8.5 refuses provisionally is journaled at once, so its precise reason is kept whatever
    ends the run; only `admissible` theses are pending. An earlier
    draft of this item proposed weakening HI-9 for the founder instead; this replaces it. The entry
    pins `output` (`final_output` or `action_tools`), which the registry checks against its tools and
    output schemas, refusing any mismatch, so no action call reaches a run that cannot mediate it.

## Rationale

The founder's item 1 is the product; the rest takes it without moving a risk boundary. The model
chooses what to read, inside the data universe, the allowlist, the cut-off, and a budget, and it
gives opinions only through paths the mandate already governs. A fooled model can read more
allowlisted data and spend up to its run's ceiling; it still cannot size, price, place, approve, or
change the envelope, and what it proposes is judged by the same deterministic rules (HI-10). Every
step is journaled before it is used, so INF-10 and DP-3 hold per turn as they held per run.

## Alternatives considered

- **Tools as a tagged union in the output schema:** weaker models fill it poorly, and it is tool use
  under another name.
- **Execute tools inside the gateway:** the gateway would need the data plane and the builder.
- **Fetch URLs or search the web:** breaks DP-9 and DEC-101 and opens exfiltration.
- **Truncate on every bound instead of ending the run:** keeps going after the model asked for more
  than it was allowed.
- **Retry as a single call, or resume after a crash:** a second sample after a failure selects
  outputs; a resume cannot yet count the lost turn's reservation.
- **A per-run cost figure pinned in the entry:** budgets are the workspace's to set.
