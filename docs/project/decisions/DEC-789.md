## Context

`verify_tsa` never answers `Ok` ([DEC-265](../04-decision-log.md#decisions) item 1): it checks
that the token holds the anchor's imprint, and a token that does is refused as
`TsaVerificationIncomplete`, because the RFC 3161 signature, the certificate chain, and
revocation are not verified. The CLI prints that as `result: failed, tsa_verification_incomplete`
([DEC-490](DEC-490.md) item 6). Journal spec §11 had no word for it, and a `VerificationRun` could
record only `pass` or `fail`, so a requested run over a stamped anchor had no honest result.

## Decision

1. **Option (iii): `incomplete`.** Journal spec §11 gains an **incomplete** outcome: a check that
   cannot yet be proven either way. It is neither a pass nor a failure. At this version only the
   token check can be incomplete.
2. **How it is recorded.** `VerificationRun` version 2 ([DEC-788](DEC-788.md)): each range's
   `incomplete` is `{check, cause}` or `null`: `check` names the check it could not finish
   (`tsa_token_invalid`), and `cause` why (items 7 and 9: `token_unverifiable` or
   `anchor_unstamped`). `result` gains `incomplete`. The `cause` member is this decision's, added
   to version 2 in the same change that introduces version 2, so no version 3 is needed. Rule 133: `fail` when any range failed; else `incomplete` when any
   range is incomplete; else `pass`. A failed range records no incomplete check (rule 132). It names
   a check reported for the range, so it carries no `seq`, in agreement with rule 111.
3. **It never stops a run.** The checks after it still run, and a failure any of them finds is
   the range's result.
4. **What it raises.** No SEV-1 and none of §11's on-failure responses: nothing was found wrong.
   No alert that pages anyone: until the crypto half lands every stamped token is incomplete, so a
   paging alert would fire on every run that reads an anchor. It is reported as an informational
   row of infrastructure design §8.2 (item 9). A `null` token is already alerted as §10's
   timestamping gap. It is not a pass either: nothing that requires a pass takes it as one, except
   a restore drill under item 9.
5. **The workspace API.** A run over a stamped anchor (an `anchor` trusted start, or an in-range
   anchor's leaf) ends `incomplete` at best: never `pass`, and never a `tsa_token_invalid` for a
   token whose imprint matches. A token without the imprint is still a real `tsa_token_invalid`.
   `first_failure` stays `null` on an incomplete run.
6. **The vocabularies.** The library's `TsaVerificationIncomplete` and the CLI's
   `tsa_verification_incomplete` line are this outcome under their own words; the CLI keeps its
   non-zero exit, since a command line has no third outcome, and journals nothing. The CLI prints
   `result: failed, tsa_verification_incomplete` (DEC-490 item 6): its `failed` is only its output
   form and its exit code, and the spec does not count it as a failure. This decision does not
   change the CLI.
7. **Sub-question 1: an in-range anchor whose `token` is `null`** does not skip the token check.
   Its check cannot finish, so the range is `incomplete`, never `pass` (journal spec §11). Settled
   by the reading that cannot produce a pass. The two causes are recorded apart, as `cause`:
   - **`token_unverifiable`**: a stamped token whose imprint matches, which `verify_tsa` cannot
     yet verify (DEC-265 item 1);
   - **`anchor_unstamped`**: an anchor the range checks whose `token` is `null`.

   A range that meets both records `anchor_unstamped`, the cause that stays an incident under item
   9. The record lists no anchors, so no append rule can check that precedence; the run's tests
   must ([DEC-787](DEC-787.md) item 8).
8. **Sub-question 2: a manifest start that only the hot store vouches for** is not a trusted start:
   422 `trusted_start`, nothing recorded ([DEC-787](DEC-787.md) item 5, journal spec §9.14).
   Settled by the reading that cannot produce a pass.

9. **Restore drills accept a token-only incomplete** (Accepted: the founder, relayed by the
   coordinator session session_01BFjCWYU2cDwPmFkR3RAHQK, 2026-10-09 ~18:27 UTC; the founder's
   words: "Accept token-only incomplete").
   - **A restore drill passes** (infrastructure design OPS-8, §6.3 step 3, §6.4) when every event
     of every stream it verifies was walked (`checked` is the whole range), no range failed, and the
     token check is the only check incomplete, with cause `token_unverifiable` (below).
   - **Any other incomplete check, and any failure, is an integrity incident** under OPS-8, as
     before: SEV-1, legal hold, and no agent trades.
   - **Token-only means cause (a) alone** (the narrower reading under DEC-176, ruled by the
     coordinator, 2026-10-09 ~18:33 UTC, the founder informed). Journal spec §11 names two causes
     of an incomplete token check. **(a)** A stamped token whose imprint matches, which cannot yet
     be verified cryptographically (DEC-265 item 1): it counts, and the drill passes. **(b)** An
     anchor the range checks whose `token` is `null` (item 7): nothing outside the journal ever
     vouched for it, so a drill that meets it stays an **integrity incident** under OPS-8. Item 7
     is unchanged: such a run still records `incomplete`, never `fail`, and raises no SEV-1 alert;
     only the drill's treatment differs. A check that a later version lets end incomplete does not
     count for a drill unless a decision says so.
   - **How a drill tells the causes apart: from the record.** Each incomplete range's `cause`
     (item 7). The drill passes only when the run is `pass`, or `incomplete` with every event
     walked and every incomplete range's `cause` `token_unverifiable`. Any `anchor_unstamped` is
     an integrity incident.
   - **The alerts.** Infrastructure design §8.2's "Journal verification failure" (SEV-1, RB-09)
     fires on a `VerificationRun` with `result: fail` only. A `result: incomplete` is reported in
     its own row, "Journal verification incomplete", at the severity Informational, which pages no
     one; the `VerificationRun` itself is the record, and a drill's record names it once E21-25
     defines one.

When the RFC 3161 half lands and `verify_tsa` can answer `Ok`, the incomplete arm goes for the
token check, and rule 132's clause that an anchor start never passes goes with it, in that change.

## Rationale

`incomplete` is honest (it says what was and was not proven), it is recorded (an auditor can see
every run and what it could not finish), and it raises no false alarm. A run that cannot prove its
anchor's timestamp has still walked and checked every event; calling that a failure would page
on call and freeze the control stream for nothing, and calling it a pass would overstate what was
proven.

## Alternatives considered

- **(i) Record `fail tsa_token_invalid`.** Rejected: every run over a stamped anchor would raise a
  false SEV-1, freezing mandate and deployment changes for a control stream and teaching on call to
  ignore the alert.
- **(ii) Refuse 422 and record nothing.** Rejected: the run's real findings (every event checked,
  every other check passed or failed) would go unrecorded, an auditor could not verify any range
  entered from an anchor at all, and a refusal would hide that the limit is the token, not the
  request.
