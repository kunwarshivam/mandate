## Context

`verify_tsa` never answers `Ok` ([DEC-265](../04-decision-log.md#decisions) item 1): it checks
that the token holds the anchor's imprint, and a token that does is refused as
`TsaVerificationIncomplete`, because the RFC 3161 signature, the certificate chain, and
revocation are not verified. The CLI prints that as `result: failed, tsa_verification_incomplete`
([DEC-490](DEC-490.md) item 6). Journal spec §11 had no word for it, and a `VerificationRun` could
record only `pass` or `fail`, so a requested run over a stamped anchor had no honest result.

## Decision

1. **Option (iii): `incomplete`.** Journal spec §11 gains an **incomplete** outcome: a check that
   cannot yet be proven either way. It is neither a pass nor a failure. At this version only the
   token check can be incomplete.
2. **How it is recorded.** `VerificationRun` version 2 ([DEC-788](DEC-788.md)): each range's
   `incomplete` names the check it could not finish (`tsa_token_invalid`) or is `null`, and
   `result` gains `incomplete`. Rule 133: `fail` when any range failed; else `incomplete` when any
   range is incomplete; else `pass`. A failed range records no incomplete check (rule 132). It names
   a check reported for the range, so it carries no `seq`, in agreement with rule 111.
3. **It never stops a run.** The checks after it still run, and a failure any of them finds is
   the range's result.
4. **What it raises.** No SEV-1 and none of §11's on-failure responses: nothing was found wrong.
   No alert of its own: until the crypto half lands every stamped token is incomplete, so an alert
   would fire on every run that reads an anchor. A `null` token is already alerted as §10's
   timestamping gap. It is not a pass either: nothing that requires a pass takes it as one.
5. **The workspace API.** A run over a stamped anchor (an `anchor` trusted start, or an in-range
   anchor's leaf) ends `incomplete` at best: never `pass`, and never a `tsa_token_invalid` for a
   token whose imprint matches. A token without the imprint is still a real `tsa_token_invalid`.
   `first_failure` stays `null` on an incomplete run.
6. **The vocabularies.** The library's `TsaVerificationIncomplete` and the CLI's
   `tsa_verification_incomplete` line are this outcome under their own words; the CLI keeps its
   non-zero exit, since a command line has no third outcome, and journals nothing.
7. **Sub-question 1: an in-range anchor whose `token` is `null`** does not skip the token check.
   Its check cannot finish, so the range is `incomplete`, never `pass` (journal spec §11). Settled
   by the reading that cannot produce a pass.
8. **Sub-question 2: a manifest start that only the hot store vouches for** is not a trusted start:
   422 `trusted_start`, nothing recorded ([DEC-787](DEC-787.md) item 5, journal spec §9.14).
   Settled by the reading that cannot produce a pass.

When the RFC 3161 half lands and `verify_tsa` can answer `Ok`, the incomplete arm goes for the
token check, and rule 132's clause that an anchor start never passes goes with it, in that change.

## Rationale

`incomplete` is honest (it says what was and was not proven), it is recorded (an auditor can see
every run and what it could not finish), and it raises no false alarm. A run that cannot prove its
anchor's timestamp has still walked and checked every event; calling that a failure would page
on call and freeze the control stream for nothing, and calling it a pass would overstate what was
proven.

## Alternatives considered

- **(i) Record `fail tsa_token_invalid`.** Rejected: every run over a stamped anchor would raise a
  false SEV-1, freezing mandate and deployment changes for a control stream and teaching on call to
  ignore the alert.
- **(ii) Refuse 422 and record nothing.** Rejected: the run's real findings (every event checked,
  every other check passed or failed) would go unrecorded, an auditor could not verify any range
  entered from an anchor at all, and a refusal would hide that the limit is the token, not the
  request.
