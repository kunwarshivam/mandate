# DEC-478: Messages fills the window, and chat renders Markdown

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-06 (UTC) |
| **Decided by** | A Cursor agent, at the founder's request ("the gutter on the messages should be zero ... the chat should be able to handle any formatting"), under DEC-79: a reversible interface decision that weakens no safety rule |
| **Story or claim** | W4 web redesign (claim #297), with [DEC-476](DEC-476.md) and [DEC-477](DEC-477.md) |

## Decision

1. **Messages runs edge to edge.** On `/messages` the shell drops the page frame: no side gutter, no
   content width, no page footer. The threads, the open thread and the rail fill the window from
   under the header to its foot (on a phone, to the tab bar), each pane scrolling on its own, and
   the page itself never scrolls. The fixture tag the footer carried moves into the threads pane.
   Every other screen keeps the page frame (`PAGE_FRAME` in `web/src/components/shell/frame.ts`).
   Loading, unreachable, empty and not-found states sit in the page frame, since they are not a
   conversation.
2. **The log follows like a modern chat.** A thread opens at its latest entry and follows new ones
   while the reader is at the end. Only scrolling up stops the following; content growing, or the
   log's own smooth scroll, never does. Within 48px of the end it follows again. While the reader
   is away, a "Jump to latest" pill sits over the composer. Sending a message always follows it.
   Under reduced motion every scroll is instant. The copilot's log behaves the same way
   (`useFollow` in `web/src/components/chat/follow.tsx`).
3. **Chat text is GitHub-flavoured Markdown, rendered safely** (`Markdown` in
   `web/src/components/chat/markdown.tsx`, with `react-markdown` and `remark-gfm`). Tables, code
   blocks, inline code, lists, task lists, quotes, headings, emphasis, strikethrough, rules and
   autolinks render. Wide tables and long code lines scroll inside the message, never the page.
   The safety rules:
   - Raw HTML is shown as text, never parsed.
   - Nothing is fetched: images render as "[Image not shown: alt]", and every URL attribute but a
     link's address is dropped.
   - A link may go only to a page in the app, an anchor on the same message, or an `https` address.
     Any other address (`javascript:`, `data:`, `http:`, `mailto:`, a protocol-relative `//host`
     or `/\host`) is dropped and its words kept as text. External links open in a new tab with
     `noopener noreferrer nofollow`, and say so.
   - Task-list boxes are drawn as icons, never as checkboxes, and no Markdown renders a button.
   - Headings are demoted under the screen's own headings (h1 becomes h4).
4. **Model-written text shows its links but never opens them.** Setup's replies and the desk's
   quotes render Markdown with `links="show"`: the words are kept and the address is printed beside
   them. Model output stays quoted and never renders a button (PX-18, DEC-477 item 2).
5. **Record answers stay plain text.** An answer from the record is written by code and is never
   parsed as Markdown, so a figure or a name can never turn into markup. Figures that read as a
   table come as structured data (`AnswerTable` in `web/src/lib/ask-record.ts`) and render as a
   real table with column headers; "How close is it to its limits?" is the first.
6. **The product speaks without hedging.** Answers carry no "From the record" mark, the Messages
   and copilot composers no note under them, and the desk no line on who wrote it: an unlabelled
   answer is Owlhead's, and a screen reader hears "Owlhead:" before it. What sets model output apart
   is unchanged: it is quoted, named and never a button (PX-18), so dropping the mark from
   code-written answers loses no distinction. Setup's composer keeps its note, which says a fixture
   stands in for the model (DEC-473).
7. **No copy button.** Copying an answer or a code block stays text selection, because
   `web/DESIGN.md` bans clipboard copy of agent names and instruments, which a message can contain.

## Rationale

The thread is the screen's work surface, so a page gutter and a content width only shrank it, and
two scrollbars (the page's and the log's) made the composer drift. Owners paste tables, lists and
code; showing the asterisks and pipes was the gap the founder named. Rendering Markdown from text
the platform does not control is the risk, so everything that could fetch, run or navigate
somewhere unsafe is dropped at the renderer, and record answers, which carry money figures, never
pass through it.

## Alternatives considered

- **Streamdown** (Vercel's streaming Markdown for AI chat): renders raw HTML by default, and brings
  Shiki, Mermaid and KaTeX, about 100KB more for features this app does not show. Rejected.
- **`marked` or `markdown-it` with `dangerouslySetInnerHTML` and a sanitizer:** HTML strings in the
  page, safe only as long as the sanitizer's settings are. Rejected for React elements built
  directly.
- **A Markdown subset written here:** every GFM edge case (tables, nested lists, autolinks) would be
  ours to get right. Rejected.
- **`flex-direction: column-reverse` to open at the end without script:** reverses `scrollTop` and
  focus order and makes the follow logic browser-specific. Rejected for a hook that scrolls to the
  end once the thread has rendered.
- **Keep the page frame and only widen the column:** still two scrollbars and a drifting composer.
  Rejected.
