## Context

Identity spec §6.4 route 2 and workspace API spec §4.10 route 2 item 2 refuse a reduction-only
session to a member "whose identity-provider subject was refused by the provider since their last
successful sign-in". `mandate_authn::SessionRecord::open_reduction_only` judges that from a
`SubjectStanding` (the last sign-in and the last deprovision signal), and identity spec §11.1
says a deprovision signal also blocks route 2.

The workspace API server never sees a deprovision signal:
- The browser obtains its access tokens from the provider and presents them.
- `POST /v1/sessions/refresh` maps a token that does not verify to `Answer::Failed`, which
  `mandate-authn` records as a failed refresh (`refresh_failed`), never `ProviderAnswer::Deprovision`.
- No back-channel logout endpoint exists.
- No journal event records a deprovision: `SessionRevoked` is not yet registered (§3.11 item 9).

So nothing could ever feed a deprovision into the standing, the check would always pass, and a
standing kept in memory would be lost on every restart.

## Decision

1. **The gap.** Until a server-side deprovision source exists, route 2 cannot see a provider's
   refusal. A departed employee disabled in the provider, whose membership no admin has yet
   deactivated, could open a reduction-only session: pause and the kill switch, nothing else, for 15
   minutes (identity spec §13's "departed employee" row expects this to be blocked).
2. **The interim, until the founder decides item 3.** The workspace API server keeps an in-memory
   `SubjectStanding` per member: its last successful sign-in (`POST /v1/sessions`). Route 2's judge
   always runs this lookup, against a decoy principal when the passkey is unknown, so it adds no
   oracle (§4.10 item 4). It refuses the session, with the one 401, when any of these holds:
   - **No sign-in seen.** The process has seen no successful sign-in of the member since it
     started. A restart loses the standing, so after one each member needs a fresh normal sign-in
     before route 2 serves them again.
   - **A membership change.** The member's membership of the hosted workspace has a record on the
     control stream (journal spec §9.12: a role change, a deactivation, a removal, any `Member*`
     record naming them) committed at or after their last sign-in, an instant both share counting
     as after, the conservative reading. The journaled membership then stands in for the
     deprovision signals an admin acts on.
   - **A deprovision.** The standing holds a deprovision at or after the last sign-in, as
     `open_reduction_only` already judges. It has no source yet and is kept for item 3.

   Route 2 only ever reduces risk, so this narrows when a member can reduce risk without the
   provider; it never adds risk. The code marks each of these as interim under this decision.
3. **For the founder: where the deprovision signal comes from.** The options:
   - (a) **Keep the interim** (item 2) as the v1 rule and record the residual. A member disabled
     at the provider, with no membership change since their last sign-in on this process, keeps
     route 2 until an admin deactivates them.
   - (b) **Journal the signal.** The server learns of a deprovision (a back-channel logout endpoint,
     or the browser's refresh reporting the provider's `invalid_grant`), and journals
     `SessionRevoked` with reason `deprovisioned`, which is registered and folded on the control
     stream. The standing then survives a restart and needs no in-memory sign-in record, at the
     cost of a new journal event and an endpoint.
   - (c) **Require SCIM** before route 2 is enabled. A deprovision then commits `MemberDeactivated`
     directly (identity spec §11.1, planned), and the membership check in item 2 covers it.

   The agent recommends (b) for v1: it closes the gap without depending on an admin, and its
   records survive a restart.

   **The founder chose (b) on 2026-10-25** (`SessionRevoked` with reason `deprovisioned`, from a
   back-channel logout or a refresh's `invalid_grant`). Item 2's interim stays in force until it
   lands (backlog E9-13).

## Rationale

The rule cannot be enforced as written, because the signal it reads does not reach the server.
Item 2 refuses route 2 in exactly the cases where the server cannot know the member's standing,
which keeps route 2 available to a member who signed in on this process with no membership change
since. That is the case route 2 exists for: the provider failed after the member was in.

## Alternatives considered

- **Ship the check as written, always passing.** Rejected: it claims a safety rule it cannot
  enforce.
- **Hold route 2 until a signal source exists** (the coordinator's option b of 2026-10-22).
  Rejected for now: pause and the kill switch would then depend on the provider until item 3 lands.
- **Refuse route 2 entirely after a restart until an operator re-enables it.** Rejected: a fresh
  sign-in is the member's own way back, and it needs no operator.
