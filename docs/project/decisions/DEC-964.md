The coordinator reserved DEC-964 for this decision.

## Context

DEC-529 item 3 lets no CI or release build enable the runner's `live` feature except one
compile-only `cargo check`, and `cargo xtask live-feature` enforces it. DEC-963 item 1 made every
`mandate-paper` test pass in the `live,rh-sim` build, the build the R0 rehearsal runs, and its
item 3 proposed that CI run it, leaving the decision to the founder.

The coordinator asked: "DEC-529 item 3 lets CI build the `live` feature only in one compile-only
check. Should CI also run the tests in the `live,rh-sim` build (simulator only, it still can't
reach real Robinhood)?" The founder answered, as the coordinator relays it: "Yes, run them".

## Decision

1. **One CI job tests the runner's rehearsal build with `live`.** The job `fast-rh-sim-live` of
   `.github/workflows/ci.yml` runs `cargo nextest run --locked --no-tests=fail --package
   mandate-paper --features live,rh-sim`: the tests of every crate that declares both `live` and
   `rh-sim`, which is the runner alone, since only the crate marked `live_feature` may declare
   `live`. An xtask test holds the crates declaring both equal to the runner and checks the job
   runs each. The required `fast` verdict needs the job.
2. **The build dials loopback alone.** In a build holding `rh-sim`, `rh-sim` wins over `live`
   (`Build::CURRENT` is the rehearsal), `MCP_HOST` and its pin are not compiled, and the endpoint
   is refused unless it is plain `http` on an IPv4 loopback address (DEC-922 items 1 and 2). A
   test in the suite the job runs,
   `a_build_holding_rh_sim_dials_loopback_alone_whatever_else_it_holds`, pins that the build that
   runs is the rehearsal, pins only the simulator's loopback host, dials nothing without the
   simulator's endpoint, and refuses Robinhood's own endpoint and any host off loopback.
3. **No credential reaches the job.** The step runs `.github/scripts/no-credentials.sh` first in
   the same shell, which fails, naming only the variables and never a value, when any
   environment name holds `KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `PASSWD`, `CREDENTIAL`, `ALPACA`,
   `APCA` or `ROBINHOOD` in any case. `cargo xtask live-feature` refuses the job when any of its
   lines, or the workflow's top-level `env:`, names `secrets` or `github.token`, when an `env:`
   name there holds one of those pieces, or when the step is not exactly the guarded run.
4. **The live-feature check allows exactly this.** Besides the one compile-only check, one
   workflow line may pass `live`: `cargo nextest run` of the runner alone with exactly `live` and
   `rh-sim` (bare or as `<runner>/<feature>`), and only in `fast-rh-sim-live` of `ci.yml`. The
   same form in another job, another workflow, a script or build file, a second time, with
   another package, the whole workspace, another subcommand or another feature, is refused; that
   run may hold no live-only package. Every other refusal of DEC-529 item 3 stands: no other
   build, test or run with `live`, no `--all-features`, nothing that turns `live` on implicitly.
5. **Its own job, under ten minutes.** The run is a job of its own rather than a step of
   `fast-pending` (DEC-464): from a cold target it built and passed all 236 tests in about
   70 seconds on 4 cores. No `cargo xtask` group runs it, so `cargo xtask ci fast` and
   `cargo xtask check` do not; the `fast` jobs run `cargo xtask ci fast` plus this one job
   (DEC-871 as narrowed here). The live-feature check reads the build in the workflow itself,
   which it could not if xtask ran it.

## Rationale

DEC-963 left the `live` halves of its build-reading pins checked only by the founder's local
build. Running them in CI keeps the build the rehearsal and the live order use from rotting, and
the rehearsal build is the one `live` build that cannot reach a broker. Putting the invocation in
the workflow rather than in xtask keeps it where the live-feature check can see, place and limit
it, and the guard and the check together keep credentials out of the only CI job that enables
`live`.

## Alternatives considered

- **A `live,rh-sim` run inside `cargo xtask ci test-rh-sim`.** Rejected: the live-feature check
  reads workflows, not xtask's own commands, so it could not limit the run to one job, and the
  nightly workflow's `cargo xtask ci nightly` would run it too.
- **A step in `fast-pending`.** Rejected under DEC-464: add a shard rather than lengthen one.
- **The guard only as a static check.** Rejected: an action may write variables at run time, so
  the guard also runs in the shell that starts the tests.
