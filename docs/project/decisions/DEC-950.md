# DEC-950: `ApprovalCanceled` is closed at schema version 1 as `{approval, reason}`, with no legacy `rebound`

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79, taken under DEC-176. It admits a record that was impossible, refuses a legacy value no journal can hold, and loosens nothing) |
| **Date** | 2026-10-16 (UTC) |
| **Decided by** | `claude-code` (builder, the grant-deadline-wake lane), under DEC-79, DEC-176 and DEC-921 |
| **Story or claim** | E7-26; DEC-944 item 5; claim [#1403](https://github.com/kunwarshivam/mandate/issues/1403) |

Before this decision, `ApprovalCanceled` was catalogued on the agent stream but had no registered
payload, the gap `ApprovalTimedOut` had before DEC-944. `append` refused every draft of it as
`unknown_schema`, so when a tightening canceled a pending ask — a version applied (mandate spec
§2.2), a mode tightened to exits-only or stricter (§5.9), the owner's pause or Stop, or a kill
switch — the runtime's record of the cancel could not be journaled. It failed closed: nothing the
ask bound was acted on. These are the readings this lane takes.

## Decision

1. **Members.** Journal spec v0.43 §9.7 closes `ApprovalCanceled` at schema version 1 with exactly
   the two members its §9 row names and the runtime's `cancel_approvals` writes:
   - `approval` (`ulid`): the ask's `ApprovalRequested` `event_id`;
   - `reason`: one of `version_applied`, `mode_tightened`, `owner_pause`, `owner_stop`,
     `kill_switch`.

   It requires `mandate_version` in `config_refs`, as its catalogue entry already does. It carries
   no content, instrument, owner identity, or free text (`AGENTS.md` rule 6).
2. **No legacy `rebound`.** The §9 row reads a legacy `rebound` as a cancel for either of the first
   two reasons. No journal can hold one, because every `ApprovalCanceled` was refused until v0.43,
   and the runtime never writes it, so the closed schema refuses it as `non_canonical`. This is
   the tighter reading; the row's sentence stays for a record written outside this journal.
3. **No cause rule.** Unlike `ApprovalTimedOut` (rule 135), the cancel's cause is the tightening,
   whose record differs by reason and by stream, and the runtime's writer passes none today.
   Requiring a cause would change the runtime and the mandate reference cases, which pin the
   cancel's members (MC-E08, MC-E18 and MC-E31), in the same change, and ES-22's spec guard
   refuses that. No rule reads `causation_id` at this version; a later version can add one.
4. **The version number.** v0.42 is taken by another open change (`ApprovalRequested` version 2),
   so this is v0.43. Whichever merges second merges `main` and keeps both entries.
5. **Two PRs.** As DEC-944 item 4: the spec PR carries the spec text, the reference, the
   `approval_cancellations` vectors and the regenerated fixtures, and this file; the code PR
   carries `mandate-journal`'s registration, with tests written first and shown failing before it.

## Rationale

The gap failed closed, but it also meant a tightening the runtime folded could never be recorded
on the agent stream, so a replay could not see why a pending ask ended. Closing the schema with the
members the runtime already writes admits exactly its record and nothing else.

## Alternatives considered

- **Accept `rebound`.** Rejected: it would admit a value the runtime never writes and no journal
  holds, which only widens what a malformed writer could record.
- **Require the tightening as the cause.** Deferred (item 3): it costs a runtime change and a
  mandate reference-case change in one PR, which ES-22 refuses, for a link a reader can already
  follow by the batch the cancel was journaled in.
- **One PR.** CI's `fast` check would stay red on the spec guard. Refused.
