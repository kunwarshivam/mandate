## Context

In paper, connecting Alpaca and approving a grant show a step-up challenge and a code, and wait for
the founder to confirm them with `mandate step-up confirm` or `confirm-connect` against staging's
journal and artifact store. Nothing could run that on staging: the cluster's API admits only each
`infra` run's own runner (DEC-2028), and a hand-run `kubectl` is no paved path. The code expires 300
seconds after the challenge, so whatever runs it must start fast and need one human act.

`infra.yml`'s one job is the only place the repository names a cloud credential, and `cargo xtask
lint` keeps it so (ES-12, DEC-2014). A second credentialed workflow would widen that rule.
`mandate-ci-do` also runs pull requests' cell jobs, so a cloud token there would sit beside
untrusted code (DEC-2614 item 2 refused the same).

## Decision

1. **A fourth action on `infra.yml`.** `action: step-up` with one optional input, `confirm`: the
   string the web app shows beside a CLI-confirm code, `connect:<challenge>:<code>` or
   `approve:<challenge>:<code>:<agent>:<approval>`. It reaches the secret step only as the
   environment variable `MANDATE_STEP_UP`; `cargo xtask lint` refuses `inputs.confirm` on any other
   line, so it can never run as a script. The job, its environment `infra-staging`, its hosted
   runner, its build and its close step are unchanged. The founder dispatches and approves his own
   run. It shares the environment's concurrency group, so it never runs beside an apply, whose
   window it would otherwise close.
2. **The string is read before any cloud call.** A challenge ULID, a code of eight letters and
   digits (`XXXX-XXXX` or bare), and ids of 1 to 128 letters, digits, `_` or `-`; anything else is
   refused. The workspace (`api.workspace`) and the principal (`founding.member`) come from staging's
   values, never from the string.
3. **The window opens outside a plan, through DigitalOcean's API.** The step-up action runs no
   OpenTofu: it sets the control plane to the closed addresses and this runner's `/32`, reads it
   back, fetches a kubeconfig that expires in 900 seconds, and closes the window and reads it back
   however the run ends, as `infra close` does again.
4. **One Job from the chart's own control run.** With `stepUp.template` (staging alone, which the
   schema enforces) the workspace chart renders `control-template`, a CronJob that is suspended and
   never scheduled (31 February), whose job template is exactly the `control` run's Job: its image,
   the `mandate_control` role, the journal DSN, the artifact store, and its egress. The action makes
   one Job from it, `step-up-<run>-<attempt>`, with the CLI's arguments alone changed, and no owner,
   so the kill-switch admission policy, which refuses a control Job a CronJob owns, admits it as the
   founder's and the CronJob can mint none. It shows the CLI's output, which names the confirmation
   and holds no secret, deletes the Job, and fails the run unless the Job succeeded. Re-running is
   idempotent through the CLI (DEC-2106 item 3).
5. **Expiry is the web app's to judge.** The API holds a challenge 300 seconds and never journals
   it, so neither the CLI nor the action can tell an expired one. The action reads the challenge's
   age from its ULID's time, which the browser stamped, and warns past 300 seconds; it never refuses
   on it, since a skewed browser clock would refuse a live challenge. Its last line tells the
   founder to press Approve or Continue again, and to ask for a new challenge if the web app says it
   expired.

## Rationale

The action keeps every rule `infra.yml` already enforces: one credentialed job, the founder's
approval, a commit on `main`, a hosted runner, a window closed and read back. The Job keeps the
control run's pod by construction rather than by copy. The single string makes the dispatch one
paste, which is what fits inside 300 seconds.

## Alternatives considered

- **A separate `step-up.yml`.** It would be a second credentialed workflow, which ES-12 and
  DEC-2014's guard exist to prevent.
- **`mandate-ci-do` for speed.** It runs pull requests' code, so a cloud token there is refused.
- **A Job rendered by `helm template` on the runner.** It needs helm and staging's merged values on
  the runner, and could drift from what Flux applied; the template is what Flux applied.
- **A standing in-cluster service that confirms.** It would be a new credentialed surface, and
  passkey step-up (S3.3b) is the planned path that needs none.

## Consequences

- `infra.yml` offers `step-up`; FOUNDER-STEPS section J says how to use it.
- Staging runs the workspace chart from a digest-pinned release (DEC-2016), whose schema refuses an
  unknown value, so staging's overlay sets `stepUp.template` in the promotion that pins a chart
  carrying it, never before; until then the action stops at reading the template.
- The hosted runner's queue can delay a run past 300 seconds; the founder then asks for a new
  challenge and dispatches again. DEC-2614's reserved runner, once accepted, removes that queue.
