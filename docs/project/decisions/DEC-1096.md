# DEC-1096: Over the workspace API the web app reads the read models as served, and shows its own five screens, with "not reported" for what the API does not serve

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The `claude-code` builder of lane W2, under DEC-79 and DEC-176, on the coordinator's direction of 2026-10-17 ("show 'not reported' for members the API doesn't serve, never invent them") |
| **Story or claim** | E11-9, claim [#1443](https://github.com/kunwarshivam/mandate/issues/1443); supersedes [DEC-975](DEC-975.md) item 5 for agents and approvals; the read models of lane A1's #1446 and #1499 (DEC-979, DEC-1020, DEC-1021) |

## Decision

1. **The read models as served.** `web/src/api/read-models.ts` decodes `read-models/agents`, `agent`,
   `approvals` and `approval` exactly as their schemas state them: every required member, decimals
   as canonical strings (a JSON number is refused), the closed enums (mode, environment, approval
   state, side, purpose, time in force), the label's shape, and the content hash an answer binds
   (API-12). Each per-id read must answer for the id asked. DEC-975 item 5's fixture-shaped bodies
   for agents and approvals, and its dashboard, positions, orders and timeline reads, are dropped.
2. **The reads the schemas do not define yet are optional.** `GET /health` and `GET /connections`
   keep DEC-975 item 5's bodies; a 404 is "not reported" (each health component reads stale with no
   time, and no connection is known, so stop-all falls back to the workspace scope), never the
   deployment down.
3. **Nothing is invented.** A member the API serves as `null`, or does not serve, shows as "not
   reported": an agent's name, mode, mandate or account positions (`account_positions`, the
   account's holdings at its last reconciliation, both agents' on a shared account), a request's time in force or protection,
   and limit usage, which no read serves until E6-4 journals it. No figure is computed in a missing
   member's place, and no P&L is shown, since the API serves none.
4. **Five screens of their own.** Over the API, Home, the agents, one agent, the approvals and one
   request are `web/src/components/api-screens/`: they read the runtime's `view` and nothing from
   the fixtures. Each page picks its screen by the data source (`BySource`); `/demo` and the
   fixtures keep the fixture screens unchanged.
5. **Every other screen says it is not available yet.** Over the API, a screen not built on the read
   models shows "Not available from your deployment yet" and nothing else (`WorkspaceGate`), until
   its read models are served.
6. **A deadline is a time.** `ApprovalRequested.deadline`, integer risk-clock seconds, is shown as
   those seconds read as Unix time in UTC, as lane A1 confirmed: the scheduler's `ClockAdvanced`
   time, monotone, which may lag the wall clock by up to a tick.
7. **No environment and no feed time is assumed.** The environment shown is the connection's, or the
   one every agent read names; otherwise, and before any read answers, it is "unknown", and the
   badge says "Environment not reported", so a live account is never labelled paper. A kill switch
   sent then carries `environment_shown: null`. A health feed the API does not serve has no time
   (`as_of: null`) and reads "not reported" on the status strip, the alerts and the unreachable
   notice; no time from the device's clock stands in for it.
8. **Commands keep their routes.** An answer binds the content hash the approval read gave; pause-all
   pauses every agent the last read listed as not stopped; stop-all uses the connection the last read
   named.

## Rationale

The coordinator asked for the read models to replace DEC-975's provisional bodies and for nothing
to be filled in. The fixture screens compute headroom, P&L and charts from members the API does not
serve; showing them over the API would mean inventing those members or showing empty figures as if
they were zero. Screens of their own, as narrow as the read models, keep rule 3 and are what the
demo shows; each new read model lets a fixture screen move across.

## Alternatives considered

- **Mapping the read models into the fixture types.** The missing members (headroom, P&L, orders,
  fills) would have to be invented or zeroed; refused.
- **Making every fixture screen tolerate missing members.** A change across dozens of screens before
  the demo, for members that arrive one read model at a time.
- **Hiding the screens the API does not serve.** The navigation would change by data source; a plain
  notice keeps the app's shape and says why.
