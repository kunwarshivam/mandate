G1b's row says: `ask` openings wait for the grant (LT-4); the quote cross-check (DEC-529 item
12); bounded reads until LT-10; then `journal export`. It does not say which answer releases the
submit, in what order differing answers are read, what tolerance the cross-check compares at,
when the watch may stop reading, or who writes the export. These are the readings G1b's tests pin.
DEC-911 was the highest number on `main` and every branch when this was reserved.

## Decision

1. **The grant wait (LT-4).** The runner reads the control stream for the answers to the `ask` its
   run journaled (mandate spec §6.4: an answer reaches the runtime only as
   `ApprovalResponseSubmitted`, committed by `mandate inbox approve`), and the submit is released
   by the answers in journal order: the first answer naming the ask's approval decides it. An
   answer whose `verdict` or `content_hash` member the runner cannot read refuses as a difference
   — never a guess at what it meant (`AGENTS.md` rule 3). An answer repeating the request's
   content hash releases the submit when its verdict is `approved` and the run's clock is still
   before the request's deadline; the same answer read at or after the deadline denies, because a
   late grant is not admitted (mandate spec §6.4 check 2) and the timeout is a deny (rule 3). A
   `skipped` verdict with the request's hash denies whenever it is read; journal spec §9.1's
   legacy `denied` reads as `skipped`. An answer repeating any other content hash — whatever its
   verdict — is **a refusal with nothing sent** (LT-4's own sentence), and the run ends refused
   rather than waiting on it: the approval stays pending on the journal for any later
   evaluation, which the runtime's own fold decides, never this run. While the wait lasts the
   submit stays blocked and nothing else the run holds back moves: exits, protective orders and
   risk exits never wait on an approval (rule 13, MI-23), and the run keeps the watch's registered
   poll interval (DEC-853 item 6), so the wait is bounded by the request's own deadline. The
   exactly-once is the cycle's own one-order door (FT-1, DEC-157 item 12), which every answer
   still has to pass: this seam releases, it never submits. Admission — mandate spec §6.4's
   checks 1 to 7 and re-validation — stays the runtime's (K1a's CLI re-checks are convenience
   only, DEC-155 item 5); this seam is the runner's second check on the one order a live run
   holds, so a grant that cannot be shown to bind the request the run journaled sends nothing.
2. **The quote cross-check (DEC-529 item 12).** The collar and the risk mark read the broker's
   own quote (the ask `review_equity_order` re-reads), and before the opening leaves it must
   agree with the independent IEX ask **within the collar**: the broker's ask sits inside the
   closed band the IEX ask prices at the collar's aggressiveness for the asset class — the same
   `x` the gate's collar reads (trading spec §9.6's table; 1% for the liquid-equity tier, 2%
   otherwise), each end rounded the way `Price::collar_bound` rounds, so the band is only ever
   narrower ([DEC-163](../04-decision-log.md#decisions) item 2). The agreement is symmetric: a
   broker quote that jumps either way refuses, because both the collar and the mark read it. A
   disagreement beyond the collar refuses **before any submission** (trading spec §4.2's row: the
   opening is refused and nothing is sent), and a missing broker or independent quote refuses
   the same way, because an opening already requires a fresh IEX quote (§4.2) and a check that
   cannot be made is not passed (rule 3). The cross-check refuses the run's opening alone: an
   exit or a protective order is priced as §5.6 prices it and never waits on this seam (rule 13);
   the runner's one live order is the only order it reaches.
3. **Bounded reads until LT-10.** The live watch's every wake asks this seam whether the run may
   end, and the answer is LT-10's own pair of halves. The run may end when the entry is
   **terminal** and any filled quantity is covered — nothing filled (flat) or the profile's
   strongest protection resting over the whole of it (DEC-529 item 7's one GTC stop-limit). It
   may also end with a filled quantity uncovered, but only once the unprotected interval is
   journaled and its alert key is in the run's report (LT-10's second half): the interval's
   journaling is the executor's (`ProtectionChanged`, bounded by `max_unprotected_s`, trading
   spec §5.4), and what the seam observes is the run's report holding the interval's alert key
   (`unprotected_interval_limit`, notifications spec §4.2's `protection` row). Until either half
   holds the run keeps reading — the entry still working included, since LT-10's first half asks
   for a terminal entry. The reads are bounded by the same bounds the paper watch already holds
   (DEC-853 item 5): the run's bound hands the entry to the executor's cancel as before, and at
   the cap — the session's end — a watch whose LT-10 does not hold fails closed with its own
   refusal and never reads again, so no implementation of this seam can loop unboundedly. A
   watch whose LT-10 holds at or past the cap ends clean, because no further read is needed.
4. **The export evidence (then `journal export`).** At its end the run names the exportable
   evidence it holds: the journal it appended to and the three streams R0 step 6 exports — the
   agent stream, the account stream and the workspace control stream, in that order, named as
   journal spec §2 names them (`agent:{workspace_id}:{agent_id}`,
   `acct:{workspace_id}:{account_ref}`, `ctl:{workspace_id}`). A run that kept no journal (no
   `--journal`, the dry run of R0 step 4) has no exportable evidence and the naming refuses,
   because the run wrote nothing the export could read. The runner writes no export itself: an
   export is journaled before it is served (`ExportCreated`, journal spec §9.13, API-16), and
   that journal is the CLI's door — `mandate journal export` of the paper brief's V0 — never
   the runner's, so the runner never reads, writes or replaces an export file, and never prints
   the journal's DSN (rule 7).

## Rationale

Each reading is the one that refuses more. Ending the run on a differing content hash sends
nothing where a patient reading might still have sent, and it cannot widen anything: the runtime
never loses the approval, which stays pending on the journal. Reading the answers in journal
order makes the fold total and replay-stable, and lets a single pending test pin each outcome.
The cross-check's tolerance borrows the collar's own `x` rather than naming a new number, and the
symmetric band is bounded by the same narrow-rounding ends the gate's collar uses, so the check
cannot admit a price the collar itself would refuse. Ending the watch on LT-10 rather than on a
bare terminal entry keeps the run over the position until it is covered or the interval is
recorded — the paper watch's FT-11 already held the paper half; LT-10's second half adds the
report's alert key, which is the one thing a run's report can show of an interval it had to
leave. Capping the reads reuses the session end the paper watch already fails at, so the live
wait cannot outlive the day. Naming the evidence rather than writing the export keeps the one
journaled export door the spec has, and a dry run with nothing journaled exports nothing.

## Alternatives considered

- **Fold the runtime's admission into the runner.** Rejected: mandate spec §6.4's checks 1 to 7
  and re-validation are the runtime's own fold, re-implementing them in the runner would give
  two admissions to drift, and the seam needs none of them to hold LT-4's own door.
- **Keep waiting after a differing hash, for a grant that repeats the right one.** Rejected:
  LT-4 says any difference is a refusal with nothing sent; the patient reading leaves a run
  alive on an answer that already proved it was not shown this order's content.
- **A named cross-check tolerance separate from the collar.** Rejected: DEC-529 item 12 says
  "within the collar", and the collar's `x` is registered, pinned, and read by the gate already;
  a second number could only differ from it.
- **Check the quote's bid beside its ask.** Rejected for this seam: the run's one order is a buy
  opening, which the collar prices against the ask; the bid the runner never prices against is
  the executor's world, not the runner's.
- **End the watch once the entry is terminal, as the paper watch does.** Rejected for live:
  the brief's R0 step 5 keeps the run until LT-10 holds, and a terminal entry with the stop not
  yet resting is exactly the unprotected interval LT-10 exists for.
- **Read past the session end while the stop is still unsettled.** Rejected: the cap is the
  paper watch's own bound, and a wait that outlives the session is a loop with no bound left.
- **Let the runner write the segment files itself.** Rejected: journal spec §9.13 journals an
  export before it is served, which the runner cannot do; two export doors would leave the
  journaled one unfenced, and `mandate journal export` already exists.
