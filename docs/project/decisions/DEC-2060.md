# DEC-2060: per-connection processes log in to the vault with Kubernetes auth, through roles the dedicated provisioner makes on connect

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-19 (UTC) |
| **Decided by** | an agent (Claude Code, lane V2), under DEC-79, at the coordinator's direction; it carries out the founder's choice of a dedicated provisioner (DEC-2605 row 23, DEC-2630 item 7) and widens no process's reach |
| **Story or claim** | E21-32, claim [#1442](https://github.com/kunwarshivam/mandate/issues/1442); DEC-2605 row 23; DEC-2630 item 7 |

## Context

DEC-2630 item 7 gives one dedicated provisioner the power to make each connection's vault
login when the connection is made. Its spike used AppRole with a templated policy keyed by the
role's name. Two more spikes on OpenBao 2.7.1 found a narrower design: Kubernetes auth, where the
vault checks the process's own ServiceAccount token with TokenReview on every login, so a role
binds a running workload rather than a secret id anyone holding it can use. They also found that
OpenBao folds role names and ACL policy names to lowercase, while KV v2 paths keep their case: a
role written `Ab` and then `aB` is one role, `ab`, bound by the second write.

## Decision

1. **Who logs in this way.** A connection's executor and its token exchange. Platform identities
   keep AppRole and their mounted Secrets (DEC-2630 items 1 and 6).
2. **ServiceAccounts.** Both kinds run in the workspace's namespace (`ws-ws1` on staging), so its
   default deny, egress policies and admission rules cover them. An executor runs as the
   ServiceAccount named by its connection id's bytes in lowercase hexadecimal; its token exchange
   as `x` and the same digits. An executor's name has an even number of characters and an
   exchange's an odd number, so neither is ever the other's, and lowercase hex is a Kubernetes
   name for every id. No platform process's name in `deploy/cell/charts/workspace/processes.json`
   can be one, and a test reads that file to check it.
3. **One storage segment.** A connection's code and token are stored at
   `connections/<segment>/code` and `.../token`, where the segment is `x` and the hex
   (`mandate_vault::policy::connection_segment`). `kv_path`, and so every writer and reader (the
   API, the connection manager, the secret import, the token exchange, the executor and
   revocation), goes through it. No two ids share a segment, whatever their case, and the segment
   is exactly the exchange's ServiceAccount name.
4. **Two mounts, two templated policies.** `kubernetes-executor` and `kubernetes-exchange`
   (`Mounts`). Each kind has one policy, written once and never per connection, keyed by
   `{{identity.entity.aliases.<accessor>.metadata.service_account_name}}`:
   - the executor's reads `connections/x<name>/token`;
   - the exchange's reads the client secret and `connections/<name>/code`, deletes that code's
     metadata, and creates and updates `connections/<name>/token`.

   A test puts each kind's bound ServiceAccount into its policy and checks the result is exactly
   the policy written from `kv_path` for the same connection, over ids chosen to collide under a
   raw, unprefixed or case-folding layout, including a 64-character id and the pair `Ab`/`aB`. An
   accessor that is not one plain path segment (a quote, a brace, a newline) is refused, since it
   would end the template or the policy.
5. **Roles named by their ServiceAccount.** A role is `auth/<mount>/role/<ServiceAccount name>`,
   never the raw id, so folding to lowercase never merges two connections' roles. It binds exactly
   that one ServiceAccount in exactly the workspace's namespace, with audience `mandate-vault`,
   `alias_name_source = serviceaccount_uid` (one entity per ServiceAccount object), the kind's one
   policy, and its lifetimes: the executor's 86400 s, at most 2592000 s; the exchange's 600 s, at
   most 600 s. The login's verdict accepts only the role and the ServiceAccount name the identity
   expects.
6. **The provisioner's policy.** On each Kubernetes mount it may create, update and read
   `auth/<mount>/role/+` and nothing else. It must send all eight parameters (`required_parameters`),
   and each but `bound_service_account_names` is pinned to its one value (`allowed_parameters`). So
   it can reach no policy, token, secret or other mount, and cannot widen a role's namespace,
   policy, audience, alias source or lifetimes. A test reads the policy's own text and checks that
   every role request sends exactly the required parameters, with the pinned values.
7. **The token.** Each pod mounts a projected ServiceAccount token, audience `mandate-vault`,
   600 s, at `/run/mandate/vault-token/token`, with `automountServiceAccountToken: false`, so a
   token the cluster's API server accepts is not one the vault accepts. The process reads it with
   `mounted::read_service_account_token`, by the rules of DEC-2630 item 6. The vault reaches the
   Kubernetes API for TokenReview by its address range (lane GO, #2012).
8. **What it retires.** Neither a connection's executor nor its token exchange logs in with
   AppRole any more. Their AppRole roles, the executor's credential files and Secrets (DEC-2630
   items 1 and 5), the exchange's single-use grant (DEC-821 item 2), and the connection manager's
   grant paths on `auth/approle/role/exchange-<id>/` are all removed in one later pair (PRV-2c),
   with the drills that use them; a pod's own token replaces them. So the widening of the
   connection manager's grant paths that the earlier plan needed is moot, and the connection
   manager gains nothing.
9. **Who makes the ServiceAccounts.** The deployment manager, not the provisioner, which stays
   vault-only (DEC-2605 row 23). It creates `x<hex>` on the connection's `ConnectionRequested`,
   before the exchange's pod, and deletes it when the request closes; it creates `<hex>` with the
   executor and deletes it when the executor stops. Both are named by
   `mandate_vault::kubernetes::service_account_name`, with `automountServiceAccountToken: false`
   and no secrets, and an admission policy on ServiceAccounts in the namespace pins the name form
   `^x?[0-9a-f]+$` (lanes D1, K1, K2 and K3).

## Residuals, disclosed

- The provisioner's policy cannot pin `bound_service_account_names` to one name: OpenBao's
  parameter constraints take fixed values, not a template of the path. A holder of its token could
  bind a role to any ServiceAccount names in the namespace. Since each policy is keyed by the
  logging-in account's own name, such a login still reaches only the entries of the connection
  that name belongs to; the reach is whoever can run a pod as that account, which already takes a
  namespace-level grant in `ws-ws1`. The provisioner holds no other power.
- The role's name is not tied to the ServiceAccount it binds by the vault; only the provisioner's
  code ties them. The login's verdict (item 5) refuses a mismatch on the process's side.
- `update` lets the provisioner rebind an existing role, for the same reason as the first
  residual.
- Nothing deletes a role yet. A revoked connection's roles stay, though its entries are deleted
  and its pods are stopped. Planned: the provisioner deletes both roles on revocation, with its
  policy granting `delete` on `auth/<mount>/role/+` and nothing more.
- Until PRV-2c retires them (item 8), the AppRole roles and policies of an executor and an
  exchange are named by the raw id (`executor-<id>`, `mandate-executor-<id>`), which OpenBao
  folds to lowercase, so a connection id with a capital letter cannot log in there: the vault
  returns the folded role name and the login's check refuses it. It fails closed, and no live
  connection uses such an id.

## Rationale

A ServiceAccount token that the vault checks on every login cannot be copied the way a secret id
can, and a templated policy means no policy is ever written per connection. So the provisioner's
power is only to make roles of one fixed shape. One segment function, shared by every path and
both policies, makes the contract one thing that a single test checks, instead of two layouts that
could drift.

## Alternatives considered

- **AppRole with a templated policy on the role's name** (DEC-2630 item 7's spike). Rejected: its
  credential is a secret id that can be copied out of the pod, and OpenBao folds role names to
  lowercase.
- **A separate namespace for the token exchanges.** Rejected: the `x` prefix keeps the two kinds
  apart in one namespace, and a second namespace would need its own default deny, egress and
  admission rules.
- **The raw id as the storage segment.** Rejected: the executor's policy reads `x<name>`, so a raw
  layout would let connection `c1`'s executor read the entries of a connection whose id is
  `x6331`.
