## Decision

1. **A primary and a synchronous standby, and every commit waits for the standby.** The
   journal-db chart's Cluster has at least two instances (the values schema refuses one),
   `synchronous_commit = on`, and CloudNativePG's
   `synchronous: {method: any, number: 1, dataDurability: required}`. `required` keeps the standby
   in `synchronous_standby_names` while it is down, so a commit waits for it rather than commits on
   the primary alone. These are written in the template, not values, since a value could only
   weaken them.
   - **The reading of "appends wait and return `Unavailable`"** (E21-41's criterion). With the
     standby down, Postgres has flushed the commit locally and holds it until a standby confirms
     it, and only then makes it visible. An append whose writer gives up while it waits therefore
     cannot be reported `Unavailable`, which `mandate-journal-pg` defines as "nothing was
     written": the commit may still land when the standby returns. So the criterion is read as
     "never `Committed`, and never visible", with `Ambiguous` for an abandoned commit, as the
     crate's contract already says: re-query by `event_id` before acting (journal spec §5.3;
     infrastructure §2.1). This only tightens the criterion, under DEC-176. An append refused
     *before* its commit because no synchronous standby is streaming, so that `Unavailable` is
     returned with nothing written, is a later slice in `mandate-journal-pg`.
2. **WAL and base backups through CloudNativePG's Barman Cloud plugin**, not the operator's
   in-tree `barmanObjectStore`. The in-tree path has been deprecated since CloudNativePG 1.26 and
   needs the `system` Postgres images, which are deprecated too; the plugin works with the
   `minimal` image the cell already pins. The plugin's chart `plugin-barman-cloud` 0.8.1 comes from
   its GitHub release, checked by SHA-256, and its two images (`plugin-barman-cloud` and its
   sidecar, v0.15.1) are pinned by digest (D-5, DEC-990 item 1). The chart renders an
   `ObjectStore` (`journal-archive`), names it as the Cluster's WAL archiver, and schedules a
   daily base backup through the same plugin, with a retention policy. WAL is compressed with gzip.
   - **A key of the archive's own.** The ObjectStore reads its access key from a Secret
     (`archive.keyFrom`, `journal-archive-key` by default) that holds only that key; no database
     role's credential is ever the archive's, and a chart test refuses one that is.
   - **Not journal spec §6.2's store.** The WAL archive and base backups are not write-once
     objects (DEC-973 item 6), so the lock check of E21-40 does not gate them; they go to the S1
     endpoint (R2 for cell #1). Nothing that §6.2 lists is written there.
3. **The plugin's TLS without cert-manager.** The operator and the plugin authenticate each other
   with two certificates the plugin's own chart would have cert-manager issue from a self-signed
   Issuer. A small chart of ours, `deploy/cell/charts/backup-plugin-tls`, makes the same two
   self-signed certificates in the cluster (`genSelfSignedCert`): the server's for the
   `barman-cloud` Service, the client's for the operator, each its own CA. They are valid for 365
   days, kept across upgrades, and remade by an install or upgrade within 30 days of their end;
   `cargo xtask cell up` then restarts the plugin, which reads them only at start. No certificate
   or key is ever a value (DEC-822 item 4).
4. **The journal's egress, narrowed.** The journal's pods reach only the cluster DNS, the
   Kubernetes API (which the instance manager and the plugin's sidecar call), each other on 5432
   and 8000, and the archive's endpoint. The API's addresses are `/32`s read at install from the
   `kubernetes` Service and its EndpointSlice, since a policy controller may see either; a
   rendering with no cluster must name them, and fails rather than opening the port to all. The
   archive is reached either by CIDRs of /24 or narrower on one port, or, for a store in the
   cluster, by its namespace and pod labels, exactly one of the two. A plain-HTTP endpoint is
   accepted only for a Service in the cluster.
5. **The local cell's stand-in for the S1 endpoint** is the MinIO image the object store's
   conformance suite already pins (`docs/dependencies.md`, test only), as its own chart,
   `deploy/cell/charts/archive-store`, in its own namespace: one bucket on an `emptyDir`, a key made
   in the cluster and handed to the workspace's namespace as `journal-archive-key`, ingress only
   from the journal's archive clients (the label the Cluster gives its pods), and no egress at all.
   It is the local and CI cell's only; cell #1 and a managed cluster archive to the S1 endpoint.
   Disclosed: in the local cell the archive's traffic is plain HTTP inside the cluster.
6. **Failure domains, said in the Cluster.** `failureDomain: separate` (the default) makes "each
   instance on its own node" a scheduling rule, so a standby with no other node stays pending
   rather than sharing one. `shared`, the local cell's, lets the instances share the one node, and
   the Cluster's `mandate.dev/failure-domain` annotation says the standby is then no second
   failure domain; `cargo xtask cell up` prints it. This is the "disclosed in the cell's own
   status, not hidden" of E21-41 for a one-node cell.
7. **Two drills, in a CI job of their own.** `standby-down` fences the standby, tries an append,
   and requires that it neither commits nor becomes visible on the primary and that its Job ends
   on its deadline; then it unfences the standby, requires a synchronous standby to stream again,
   a new append to commit, and every stream written to verify by journal spec §11. Seeded, the
   cluster's durability is set to `preferred` first, and the drill must report the commit that
   lands on the primary alone. `archive` writes a stream, closes its WAL segment, takes a base
   backup, and requires Postgres to report the segment archived and Barman's own tools, reading the
   store with the archive's key from a pod of their own, to list the backup and fetch the segment
   back. Seeded, the archive points at another bucket of the same store, which Postgres cannot
   tell, and the drill must report the segment missing. Both run in `cargo xtask ci cell-journal`,
   a job beside `cell`, so each stays inside ten minutes (DEC-464).
8. **What the next slices of E21-41 add**, the story staying open until they land: the
   point-in-time restore drill that passes journal spec §11 over every stream (OPS-8); the failover
   drill with intents in flight, zero duplicates and zero lost acknowledged appends, and the old
   primary fenced before promotion (DEC-434 item 15); cell #1's values, with the instances on
   different droplets and DEC-995 item 6's one-region disclosure, and the archive's R2 endpoint and
   CIDRs; and the writer-side `Unavailable` of item 1.

## Rationale

OPS-2's "durable" is `synchronous_commit = on` with a synchronous standby, and the failure that
matters is the quiet one: a standby that drops out and a primary that keeps committing alone. Only
`dataDurability: required` keeps that from happening, at the cost of appends waiting, which is the
safe default rule 3 asks for: appends fail, so no order is sent, and protection rests at the broker
(infrastructure §2.1, the primary-failure row). The in-tree archive is on its way out of the
operator, and building the cell on it would mean a migration with the archive's history at stake.
cert-manager would bring a cluster-wide controller and three more images to issue two certificates
that never leave the cluster. Narrowing the journal's egress closes the last `- {}` the workspace
chart's default-deny left open.

## Alternatives considered

- **`dataDurability: preferred`.** Refused: it drops a down standby from the synchronous set, so
  the primary commits alone, which is what OPS-2 forbids; the `standby-down` drill plants it as its
  bug.
- **The in-tree `barmanObjectStore` with the `system` image.** Refused: deprecated, as is the image
  it needs.
- **cert-manager for the plugin's certificates.** Refused for now: more surface than two
  self-signed certificates; a later cell that runs cert-manager for other reasons can switch the
  plugin's chart back to it with values.
- **Archive egress to `0.0.0.0/0` on 443.** Refused: it lets a compromised database pod reach any
  host on the internet.
- **A required anti-affinity everywhere.** Refused for the local cell: its one node could never
  schedule the standby. `shared` is allowed only with the disclosure.
