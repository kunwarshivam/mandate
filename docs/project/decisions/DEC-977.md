## Decision

1. **The interface.** A new safety-critical crate, `mandate-vault`, defines `SecretSource`: a
   session with the vault as one identity. It writes a secret without reading it back, reads
   once (the token exchange, for its code and the client secret), deletes every version, leases
   an executor's token (`lease`, `renew`, `revoke`), and issues and revokes the single-use
   token-exchange grant. Every call is async, and the clock is an argument, never read.
2. **The policy table** (infrastructure §5.2), one function both backends obey:

   | Identity | Read | Write | Delete |
   |---|---|---|---|
   | API | — | every code | every code and token |
   | Connection manager | — | — | every code and token; issues and revokes grants |
   | Token exchange for `c` | `c`'s code, the client secret | `c`'s token | `c`'s code |
   | Executor for `c` | `c`'s token | — | — |
   | Runtime | — | — | — |
   | Secret import | — | the client secret | — |

   The API's token delete and the import identity keep DEC-692's local roles. The OpenBao
   policies are generated from this table with every path written out per connection. None holds
   `*` or `+`. A runtime's policy is a comment alone, because OpenBao refuses an empty one.
   `provision` rewrites them when a connection is added.
3. **The local backend** checks the table in code before it touches a file, so it refuses
   exactly what OpenBao refuses, and maps the local vault's refusals as follows: a failure to
   reach the files is an outage; a file that fails its checks or decryption is an integrity
   refusal. Its grants live in memory in the issuing process (`GrantBook`). On the demo host the
   manager and the exchange share the executor's process; DEC-692 item 6 enforces the grant in
   code there.
4. **The OpenBao backend.** It uses AppRole, one role per process type and connection, because
   AppRole works the same in the cell, in Compose, and on a customer's site. Kubernetes auth can
   replace the login later without changing the interface. A login is refused unless the role it
   reached is the claimed identity's own. Its secret id is a value the caller read from a mounted
   file, never an environment variable. The client:
   - speaks HTTPS only and trusts only the CA certificate it is given;
   - uses no proxy and follows no redirect, with a 10-second timeout;
   - stores each secret base64 in a KV v2 mount;
   - never puts a response body in an error.

   A grant is a single-use AppRole secret id for the connection's exchange role. The id and the
   token it yields each live 10 minutes. Revoking a grant already spent is a no-op. Only 400,
   401, 403 (refused), 404 (missing), and 503 (sealed) are the vault's own answers; any other
   status, a standby's redirect or a 429 included, is an outage, so it never drops a lease.
5. **Manual unseal by default.** The cell's OpenBao uses Shamir unseal, and an operator (the
   founder) unseals it after every restart. That costs nothing. Auto-unseal through a key service
   (H4, about $1 to $5 a month) remains the founder's decision. The client reads `sys/seal-status`
   before every login: a sealed or uninitialized vault is `Sealed`, an outage. So:
   - a running executor keeps its lease (item 7);
   - no new process starts until the vault is unsealed;
   - its agents stay `Recovering`, with protection at the broker (infrastructure §5.2).
6. **The dev server is for tests only.** A server with in-memory storage is refused. Only the
   `dev-server` feature allows one, and only this crate's own tests turn that feature on. CI runs
   OpenBao 2.7.1, pinned by digest (D-5), in dev mode with TLS and a fresh random fake root token.
   That token goes only into a file whose path is in the environment. CI runs the suite as a new
   `cargo xtask ci openbao` part of `full` and in every `mutants` shard.
7. **Leases and E21-9's renewal rule.** A lease lasts 24 hours and is renewed every hour
   (infrastructure §5.2's Proposed defaults), capped by the backend's own expiry. `LeaseKeeper`
   applies the rule:

   | Event | Effect on the lease |
   |---|---|
   | A renewal fails with an outage | Kept until it expires |
   | Any other refusal (the token deleted, the policy changed, tampering) | Dropped at once: that is a revocation |
   | A renewal for another connection | Dropped |
   | The lease reaches its expiry | Dropped |
   | A renewal after the lease was dropped | Brings nothing back |

   An executor's OpenBao token lives at most 30 days through renewals. Logging in again past that
   is V3's work.

## Residuals, disclosed

- The connection manager holds each grant's secret id until it hands it to the exchange it
  starts, so a compromised manager could log in as that connection's exchange for 10 minutes:
  read its code and the client secret, and write its token. It can read no token. This follows
  from infrastructure §5.2's grant; a response-wrapped grant would close it and is follow-up.
- `provision` leaves the policies and roles of a removed connection in place, and each run
  issues new secret ids without revoking the old ones. The cell's deployment manager (D1) owns
  that cleanup.

- A secret from OpenBao passes through an unzeroized `serde_json` string on the way to its
  `secrecy` box; only the process that may read it holds it.
- No vault operation is journaled yet (DEC-976 item 6). OpenBao's own audit device is the cell's
  (K1); the journal event comes with its spec change.
- No metric exists yet, so the canary scan covers `Debug` output, errors, and refusals only.

## Not in this decision

Wiring the executor to its lease (V3, E21-9), the cell's OpenBao chart and its storage (K1, S2),
and the key-permission checks at executor start (E21-9).

## Alternatives considered

- **One identity for every process, checked in code.** Rejected: the vault itself must refuse,
  or a compromised process reads everything.
- **Wildcard paths (`connections/+/token`) in the API's and the manager's policies.** Rejected
  by E21-32's "no wildcard": the policies are regenerated per connection.
- **Kubernetes auth now.** Deferred to K1. It ties the backend to the cluster, and the local and
  Compose cells have none.
- **Auto-unseal now.** It is a spend (H4), so the founder decides it.
