# DEC-399: E6-4's `trim_proposals` implementation: the readings of mandate §5.5's trim

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-02 (UTC) |
| **Decided by** | the stream G builder (claim [#123](https://github.com/kunwarshivam/mandate/issues/123)) under DEC-79 and DEC-176: reversible engineering readings of mandate §5.5 and DEC-65, none of which proposes a trim the spec does not ask for or holds back one it does |
| **Story or claim** | E6-4, the implementation PR (DEC-77 stage 2) for the trim tests merged in [#136](https://github.com/kunwarshivam/mandate/pull/136) |

## Decision

1. **Shape.** `mandate_risk::trim_proposals` is `trim::proposals`, a new module of the crate. It
   returns at most one `TrimProposal` per instrument in `AgentSnapshot::market_values`, in
   instrument order, each a `Purpose::RiskExit`. The market value is what §5.5 compares, so an
   instrument with no market value is not trimmed, the way check 2 reads a missing market value
   as zero. The quantity held comes from `AgentSnapshot::positions`. With no entry there, the
   quantity is zero, and nothing is sold.
2. **Which rung confirms.** A trim is proposed only while a rung with `scale_action:
   trim_to_target` has been active, per `RiskSnapshot::active_rungs`, for at least
   `breach_confirm_s`. The boundary allows, as every limit comparison in the crate does (DEC-129
   item 15). A `limit_buys` rung never trims, however long it has been active. The target is
   `size_factor × cap` with stream F's `size_factor`, the product of every active rung's factor.
   It is not a product of the confirmed rungs alone, because §5.5 sells down "to factor × cap" and
   defines the size factor over the active rungs. `hand::two_active_rungs_multiply` pins the product
   of two rungs that are both active and confirmed, so it does not separate the two readings. They
   differ only while a deeper rung is still confirming. Then this reading trims to the deeper
   target, which sells more and adds no risk (#466 review, round 1, m5).
3. **The figures.** `cap` is check 2's `min(max_position_usd, max_position_fraction × E)` at the
   risk snapshot's agent equity, and both call `limits::position_cap`. The band
   is `rebalance_band × cap`, which is §5.5's wording and `properties::a_trim_never_sells_below_the_target`'s
   oracle. The comparison `MV − factor × cap ≥ band` is exact on `UsdExact`. There is no
   `factor < 1` guard. `reference/mandate/ref.py`'s builder has one, but §5.5 does not, and the
   property's factor-1 arm requires a trim above the cap. The reading only adds trims, which are
   risk exits, and it can differ from `ref.py` only for a position above the cap itself while a
   `trim_to_target` rung of factor 1 is confirmed, which no reference case states.
4. **The quantity.** The sell is `ceiling(excess × held ÷ MV)` on the instrument's grid, capped at
   the quantity held. `MV ÷ held` is the price the market value was taken at, so this is
   `ref.py`'s `ceil_inc((mv − factor × cap) ÷ bid, inc)` wherever MV is `held × bid`, as in
   family B. The grid is whole shares unless the instrument is fractionable, and then nine places,
   which is how the participation slice reads it. `mandate-num` gains
   `UsdExact::ceiled_quotient`, the rounding up, and `UsdExact::of_ratio`, which brings the size
   factor in exactly. Check 2 and the trim call one `limits::position_cap`, so they read one
   cap by construction (#466 review, round 1, m4).
5. **The guards.** A sell of zero, or one below the instrument's `min_order_size` (§5.3 rule 2's
   minimum, the gate's only minimum input), is not proposed. An equity trims only when
   `session_at` says `Regular`. Crypto trims in any session. Nothing trims while the goal is
   `Holding`. A position at least the band above its target with no instrument snapshot is refused with
   `GateError::InstrumentUnknown`, because its class, grid and minimum cannot be known. This is
   rule 3's refusal: it adds no risk, and the executor's other exit paths do not depend on it. A
   position inside the band never needs its snapshot.
6. **The family-B harness is a follow-up.** `crates/mandate-refcases/src/mandate/order_builder.rs`
   still does not compare a `trim_to_target` case's trim, `origin` or `trim_withheld`, so MC-B17
   and MC-B30 to MC-B32 stay owed, now to "E6-4's family-B trim arm". Their `OWED` rows pin the
   answer instead of the stub's text: MC-B17 gets a 3-share `RiskExit`, which is the case's
   expected `qty`, and MC-B30 to MC-B32 get none. The comparison, and how `trim_withheld` is
   derived when the API returns no guards, is a backlog row ("E6-4 harness: family B's trim arm
   compares the trim").
7. **A trim already working is subtracted before the next is sized** (#466 review, round 1, m1,
   which the coordinator raised to a major).
   - **The input.** `trim_proposals` gains `account: &AccountSnapshot`. `AgentSnapshot::working_orders`
     holds only the agent's `ClientOrderId`s. The instrument, side, open quantity and protective flag
     of each order are in `AccountSnapshot::working_orders`, which is where §5.3 rule 4's
     `sell_available` reads them. The coordinator's ruling on #466 chose this signature change and
     named `crates/mandate-risk/tests/hand.rs` and `crates/mandate-risk/tests/properties.rs` under
     DEC-77's 2026-09-27 amendment. In those files, each existing call gains only the account
     argument.
   - **What counts as on sale.** The agent's own open sells in the instrument that are not
     protective, read as `sell_available` reads them at the **first gate decision** (§5.3's closing
     paragraph). The re-run before submission counts protective legs too, so it is not the reading
     here. A protective order is not a trim in progress. (Corrected after #466's round-2 review,
     m1, on the coordinator's ruling; the code did not change.)
   - **The sizing.** The sell is `ceiling((excess × held − on_sale × MV) ÷ MV)` on the grid, capped
     at `held − on_sale`, or zero when more than the position is on sale. That zero is enforced by
     the value subtraction for any non-negative target. The `Negative` arm of `held − on_sale` is a
     defensive guard for a negative cap, which `trim::tests::a_negative_cap_with_more_on_sale_than_held_proposes_nothing`
     pins.
   - **The minimum applies to the remainder.** §5.5's "only if the order meets the minimum" is now
     judged on what is left after the open sells. So up to one minimum lot of excess can stay above
     the target while a trim rests, as it already can when the whole excess is below the minimum.
     This sells less, never more.
   - **The netting assumes a resting sell ends.** A trim is a `risk_exit`. Trading spec §5.4's
     bounded unprotected interval (`max_unprotected_s`) has the executor cancel an unfilled exit,
     re-place protection and alert, and the next evaluation then proposes the trim again. Without
     that, a sell that never fills would hold the position above its target with no new trim. This
     sits beside the backlog row "Pace `trim_to_target` sells like discretionary exits"
     (#466 round-2 review, n1 and n2).
   - **The effect.** Without this, a resting trim was re-proposed in full at every evaluation, so a
     3-share trim of 10 shares could put 9 on sale. This reading sells less than round 1's code,
     never more, and holds §5.5's "sold down to factor × cap" across evaluations.

## Rationale

The tests merged in #136 fix the signature and seven behaviours. The remaining choices are the
places §5.5 leaves to the implementation: the price a market value implies, the grid, the minimum
and a missing input. Each choice above takes the reading that matches `ref.py` on every reference
case. Where `ref.py` and §5.5 differ (the `factor < 1` guard), it takes §5.5's text, which trims
more.

## Alternatives considered

- **Use `ref.py`'s `min_order_usd`.** The gate has no dollar minimum input. Inventing one would add
  a field no snapshot supplies.
- **Skip an instrument with no snapshot instead of refusing.** That would silently drop a risk exit
  the spec asks for. A refusal is visible to the caller.
- **Make the target the product of the confirmed rungs only.** That trims less while a deeper rung
  is still confirming, and contradicts `hand::two_active_rungs_multiply`.
