# DEC-876: A key that names two different `replaces` targets is in doubt

## Decision

This adds one reading to [DEC-872](DEC-872.md) and [DEC-874](DEC-874.md), which stay as written.
It is about how `RobinhoodConnector::restore` reads the `replaces` members of one key's
`OrderStateChanged` records.

1. **Two targets.** A key whose `OrderStateChanged` records name two or more different keys in
   `replaces` is in doubt, in any order of those records. Its cancel is `NotSent`
   (`no_order_id`) and a `Submit` of it is `Unknown` (`Ambiguous`), with nothing called. Neither
   the first link nor the last decides, and it does not matter whether the targets' instruments
   and sides agree.
2. **Its own submit does not rescue it.** The key stays in doubt even when it has its own readable
   `OrderSubmitted`, before or after its links, and one unshared non-empty text id.
3. **Successors inherit the doubt.** A successor without its own `OrderSubmitted` whose `replaces`
   chain passes through such a key reaches no instrument and side, so it is in doubt too
   (DEC-874 item 2). A successor with its own readable `OrderSubmitted` does not inherit
   (DEC-872 item 3), so this item does not touch it.
4. **One target twice is one link.** Records that name the same key in `replaces` more than once
   name one target. The key is read as if it had one link, and is placed or in doubt exactly as
   DEC-872 and DEC-874 already say.
5. **The targets are not touched.** Each key that such a key names keeps its own reading. With
   one unshared id and its own readable instrument and side it still cancels by that id
   (`AGENTS.md` rule 13).

## How this fits DEC-872 item 3 and DEC-874 item 3

DEC-872 item 3 says "a key's instrument and side come from its own `OrderSubmitted`", and DEC-874
item 3 says that holds wherever the submit falls. Item 2 here holds a key in doubt that has such a
submit. These are two different questions, so the items do not conflict:

- DEC-872 item 3 and DEC-874 item 3 say *where* a placed key's instrument and side come from.
- Whether a key is placed at all has further conditions that a readable own submit does not
  override. DEC-872 item 2 (a shared id) and DEC-874 item 1 (an odd id beside a readable one)
  already hold in doubt keys that have their own readable submit.
- Item 2 here is one more condition of that kind. It is also the same principle as DEC-872 item
  3's second sentence: when a key's own records contradict each other (two disagreeing submits
  there, two different origins here), the key is in doubt.

If the two readings were taken to conflict, this decision would take the one that holds the key
in doubt, because it is the tighter one (DEC-176).

## Rationale

The review of #1236 found that `restore` kept the first `replaces` target a key names
(`parents.entry(key).or_insert(old)`). With two targets whose submits disagree, and no own submit,
the key cancelled with the first target's instrument and side, or with the second's if the records
were swapped. A mutant that made the last link win survived every test. That is the order
dependence DEC-874 removed elsewhere: journal order between a key's two links says nothing about
which order the key replaced.

A well-formed stream never names two targets under one key:

- A successor's key is `md-r-<origin>`, derived from the one `OrderStateChanged` event that
  recorded its replacement (trading-domain spec §5.7's `replaced` row,
  `ClientOrderId::for_replacement`), so it replaces exactly one order.
- Two different targets under one key mean the key's records are corrupt or come from two
  different orders. Nothing in the stream says which one the broker's order is.

So the key is escalated to the owner (DEC-85) rather than cancelled against a guess (CN-7).

## Consequences and safety

- **Only towards in doubt.** Items 1 to 3 hold keys that main places. Items 4 and 5 change nothing
  that main does.
- **A cancel is withheld only where the key's own records contradict each other.** The ruling asked
  whether this blocks a risk-reducing action that is otherwise clearly safe. The one action it
  withholds is the cancel of such a key by its one id. That cancel is not clearly safe:
  - the key's records disagree about which order it is, as with DEC-872 item 3's two
    disagreeing submits and DEC-874 item 1's odd id, both of which withhold the same cancel;
  - the shell stops and alerts the owner (DEC-85), who can cancel at the broker.

  Every key that does not name two targets is unaffected. That includes the targets themselves and
  successors with their own submit.
- **No key is placed again.** A `Submit` of such a key was already `Unknown` on main, because the
  journal names it (DEC-860 item 4, DEC-872 item 1), and stays so.

## Alternatives considered

- **Let the first link win (main):** rejected. The result depends on record order, and the key may
  be cancelled against an instrument and side it never had.
- **Let the last link win:** rejected for the same reason.
- **Let the key's own submit rescue it:** rejected. The key's own records contradict each other
  about which order it is, and DEC-872 already holds a key in doubt for that.
- **Hold the key in doubt only when the targets disagree:** rejected. Two targets that agree are
  still two orders, and nothing says the broker's id belongs to either.
- **Hold every target in doubt too:** rejected. Each target's own records are consistent, and a
  successor's corrupt record should not withhold a cancel that the target's own records fully
  support (`AGENTS.md` rule 13).
