## Decision

1. **HLD flow C step 4 is a fan-out.** The HLD's "escalation chain (push → SMS → phone call)" is
   replaced by DEC-438 item 6's fan-out: every configured push channel at once and one reminder.
   The ordered chain waits for E8-7 and a mandate schema field (spec §12 item 5).
2. **The Telegram linking code** (spec §4.5) is 128 bits from the notice id's secure random source
   (DEC-702), written as 26 base32 characters; it lives 10 minutes; it is single use, spent by the
   first message that carries it whether or not an address is recorded; a new code revokes the
   owner's earlier one; and an unknown, expired, or spent code records nothing and gets no reply
   that tells those cases apart. The residual (whoever uses a live code first binds their own chat
   and receives the opaque notices) is in spec §9.
3. **The web push envelope is fixed per class** (NT-1, spec §4.6). `urgency` and TTL: `action`
   `high` and 3 600 s; `safety` `high` and 86 400 s; `info` `normal` and 21 600 s, the same direct
   or relayed, never from a deadline or any subject's time. The push endpoint is an address under
   NT-2.
4. **No mail leaves while `[[EMAIL-FOOTER]]` stands** (rung 2, spec §4.4). While the email
   template's footer is the placeholder, the only mail transport that can be constructed is the
   recorded-fixture transport, and a CI check fails if any other exists. A transport that reaches a
   mail server ships only with the footer wording DEC-438 item 24 leaves to the founder and counsel.
5. **A coalesced safety notice meets NT-6's 60-second bound at the window's end** (spec §5.4). The
   window opens at the first message's send; a notice joins it only if its cause committed after
   that send; a cause committed before it goes in the first message. The window ends 60 seconds
   after the send, so each joined notice is sent within 60 seconds of its own commit.
6. **`OwnerAlertSent` carries a kind, not a text.** The mandate reference cases'
   `OwnerAlertSent {subject, text: "tripwire_fired"}` is read as `{subject, kind: risk_limit}`; the
   text key `attention_needed` is derived from the kind at rendering and never journaled on the
   record. The reference cases and code change in E8-9 (slice S4).
7. **Wording fixes with no new rule.** NT-5 states why check 4 is its only effect (an approval
   gates only a risk-adding action; rules 2 and 13); §3.2's preamble names `channel_lost`'s cause as
   the dispatcher's own `NoticeAttempted`; §5.5 says where the notice stream's type is described and
   that `StreamType` and `StreamId::parse` must be extended first (E8-10); what becomes of
   `ApprovalRef::of_requested_event` is said once, in spec §4.2, and the workspace API spec §3.9
   points there.

## Rationale

Every item either sends less (a fixed envelope, a single-use short-lived code, no mail transport
before its footer), names a bound the spec already claimed, or fixes wording a reviewer found. None
adds a feature, and the freeze rule after round 1 allows only these minors.

## Alternatives considered

- **TTL from the approval's deadline.** Rejected: it tells the relay and the push service when a
  request expires, which NT-1 keeps from them.
- **A six-digit Telegram code.** Rejected: 20 bits can be guessed by anyone who can message the
  bot; 128 bits need no rate limit to stay unguessable.
- **A reviewer's promise instead of a check for the email footer.** Rejected: the trust ladder puts
  a rule that must hold on the highest rung that can hold it.
- **Coalescing by the first notice's commit time.** Rejected: under dispatcher lag the window could
  close before a later notice's 60 seconds, or after; anchoring at the send and admitting only later
  commits makes the bound hold by construction.
