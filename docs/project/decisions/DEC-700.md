## Decision

1. **HLD flow C step 4 is a fan-out.** The HLD's "escalation chain (push → SMS → phone call)" is
   replaced by DEC-438 item 6's fan-out: every configured push channel at once and one reminder.
   The ordered chain waits for E8-7 and a mandate schema field (spec §12 item 5).
2. **The Telegram linking code** (spec §4.5) is 128 bits from the notice id's secure random source
   (DEC-702), written as 26 base32 characters; it lives 10 minutes; it is single use, spent by the
   first message that carries it whether or not an address is recorded; a new code revokes the
   owner's earlier one; and an unknown, expired, or spent code records nothing and gets no reply
   that tells those cases apart. E8-12's acceptance tests each of these. The residual (whoever uses a live code first binds their own chat
   and receives the opaque notices) is in spec §9.
3. **The web push envelope is fixed per class** (NT-1, spec §4.6). `urgency` and TTL: `action`
   `high` and 3 600 s; `safety` `high` and 86 400 s; `info` `normal` and 21 600 s, the same direct
   or relayed, never from a deadline or any subject's time. The push endpoint is an address under
   NT-2.
4. **No mail reaches anyone but the founder while the general footer is unresolved** (spec §4.4,
   with the founder's [DEC-820](DEC-820.md) item 4, which covers only the founder's own account).
   The only transports are the recorded fixture and a founder-only SMTP transport bound at
   construction to a one-address allowlist, the single founder address the deployment's
   configuration names, read from the vault; its send takes no recipient (rung 1). Any other
   recipient, another workspace's owner included, is refused at the adapter as
   `permanent { recipient_not_permitted }` before any connection; that reason is not retried, marks
   no address `unreachable`, and raises no `channel_lost` (spec §5.2). E8-11's tests pin both, and
   E8-11 builds an `xtask` check in `cargo xtask ci fast`'s lint (rung 2) that fails, while the
   general footer is `[[EMAIL-FOOTER]]`, on any other implementor of the mail transport trait (the
   primary rule) or on a crate from its configured deny-list of mail-sending crates (`lettre` and
   similar) anywhere but the founder-only transport. The change that supplies counsel's general
   footer removes the check, and only that change may add a transport that can address anyone else.
5. **A coalesced safety notice meets NT-6's 60-second bound** (spec §5.4). The dispatcher's read
   watermark, not a send's time, decides grouping: the causes read in one pass with no window open
   go at once as the first message; a cause read in a later pass, including one that committed
   while the first send was in flight, joins the open window, which ends 60 seconds after the
   earliest commit among its joined causes and never later than 60 seconds after it opened, without
   waiting on the first send's outcome; a cause read when its commit is already 60 seconds old goes
   at once on its own, its age being its journal commit time against the dispatcher's clock (a skew
   shows as lag, which the lag alert covers). Every cause is therefore sent within 60 seconds of its
   own commit while the dispatcher keeps up.
6. **`OwnerAlertSent` carries a kind, not a text.** The mandate reference cases'
   `OwnerAlertSent {subject, text: "tripwire_fired"}` is read as `{subject, kind: risk_limit}`; the
   text key `attention_needed` is derived from the kind at rendering and never journaled on the
   record. The reference cases and code change in E8-9 (slice S4).
7. **Wording fixes with no new rule.** NT-5 states why check 4 is its only effect (an approval
   gates only a risk-adding action; rules 2 and 13); §3.2's preamble names `channel_lost`'s cause as
   the dispatcher's own `NoticeAttempted`; §5.5 says where the notice stream's type is described and
   that `StreamType` and `StreamId::parse` must be extended first (E8-10); what becomes of
   `ApprovalRef::of_requested_event` is said once, in spec §4.2, and the workspace API spec §3.9
   points there.
8. **The delivery reasons are closed and each says what it does** (spec §5.2, §5.3, §5.5, §5.6,
   §5.7; found while closing the journal schemas). §5.2's enum adds `bounced`, `complained`, and
   `unsubscribed` (from receipts). Exactly `address_rejected`, `auth_failed`, `bounced`,
   `complained`, and `unsubscribed` are permanent, mark the address `unreachable`, and raise
   `channel_lost`. The brief's own opt-out is not one of them: its `List-Unsubscribe` points at the
   workspace's own one-click endpoint (RFC 8058), keyed by the brief's notice id, which stops only
   the brief and marks nothing, so a brief opt-out never silences safety mail; a provider
   `unsubscribed` receipt is never read as a brief opt-out. `abandoned` carries
   `not_pending` for `action` only and the new `retry_window_ended` for `safety` (24 hours) and
   `info` (6 hours) only.

## Rationale

Every item either sends less (a fixed envelope, a single-use short-lived code, no mail transport
before its footer), names a bound the spec already claimed, or fixes wording a reviewer found. None
adds a feature, and the freeze rule after round 1 allows only these minors.

## Alternatives considered

- **TTL from the approval's deadline.** Rejected: it tells the relay and the push service when a
  request expires, which NT-1 keeps from them.
- **A six-digit Telegram code.** Rejected: 20 bits can be guessed by anyone who can message the
  bot; 128 bits need no rate limit to stay unguessable.
- **A reviewer's promise instead of a check for the email footer.** Rejected: the trust ladder puts
  a rule that must hold on the highest rung that can hold it.
- **Anchoring the window at the first send** (v0.2's first draft). Rejected in review: a cause that
  commits while the first send hangs at the provider would be in neither group and could be held
  past its 60 seconds or dropped. Anchoring on the read watermark and each joined cause's own commit
  makes the bound hold by construction.
- **A fixed one-message-per-60-seconds rate.** Rejected: after a lag it would hold a notice past its
  bound; the bound wins over the message count.
- **The `action` TTL equal to the approval's window.** Rejected: it would tell the relay and the
  push service the deadline. A shorter fixed TTL only drops an interruption; retries, the pull
  channels, and the timeout to `skip` cover it.
