|---|---|
| **Status** | Accepted (agent: reversible engineering readings under DEC-79, taken under DEC-176. They admit records that `append` refused, carry no content, and change no other record, rule, or reading) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (builder, managed-cells lane G0), under DEC-79, DEC-176, DEC-440 items 1 to 3, and DEC-921 |
| **Story or claim** | E20-3; plan DEC-967 lane G0; claim [#1436](https://github.com/kunwarshivam/mandate/issues/1436) |

The [control-plane design](../../design/control-plane.md) §3.8 names ten records "provisional until
the journal spec registers the events (E20-3)". Until now `append` refused each as
`unknown_event_type`, so no control-plane message could be journaled, and so none could take
effect (CP-5). E20-3 asks that they be registered with vectors before any message flows (ES-22).
These are the readings this lane takes.

## Decision

1. **Ten records, closed at schema version 1, on the workspace control stream.** Journal spec
   v0.44 §9.17 closes `ControlPlaneEnrolled`, `LicenseApplied`, `LicenseStateChanged`,
   `ReleaseOffered`, `ReleaseInstalled`, `ReleaseWithdrawnNoticed`, `CatalogEntryRegistered`,
   `DataBundleImported`, `UsageReportSealed`, and `ControlPlaneMessageRefused`, each on
   `ctl:{workspace_id}` only. Workspace control services, the stream's single writer, append them as
   a `system` actor (rule 137). `cp-agent` verifies and hands over, and never appends (design §3,
   CP-4, CP-5).
2. **A deployment-wide instruction is journaled per workspace.** An enrollment, license, release,
   catalog entry, or data bundle covers a deployment, which hosts many workspaces in a cell. It is
   journaled on the control stream of each workspace it covers, before it takes effect there. A
   workspace opened later has the deployment's enrollment and the instruction of each kind in
   effect journaled on its own stream before its first `AgentDeployed`. Each workspace's stream
   then holds every control-plane fact that bounds it, and tenant isolation (journal spec §7) is
   unchanged. The site's own acts (`ReleaseInstalled`, `ReleaseWithdrawnNoticed`,
   `ControlPlaneMessageRefused`) go on every hosted workspace's stream; a `UsageReportSealed`, one
   per deployment, organization, and period (so it carries `org_id`), goes only on the streams of
   that organization's workspaces, so no workspace holds another organization's counts. A
   `LicenseApplied` lists every deployment of its organization the license covers: the
   organization's own metadata, accepted.
3. **No free text.** Every member is an `id`, a closed enumeration, an `integer`, a `timestamp`,
   or a `digest` (CP-1). Signed documents (license, manifest, withdrawal, report) are named by the
   SHA-256 of their bytes as received, a bare-hex `digest`, and are not stored in the artifact store
   at this version, so §11 check 6 does not look for them. The enrollment token and the private key
   are never journaled.
4. **Anti-rollback (CP-9) stays with the writer at this version.** `LicenseApplied`,
   `ReleaseOffered`, `ReleaseInstalled`, `CatalogEntryRegistered` (per `kind`), and
   `DataBundleImported` (per `dataset`) carry the document's `sequence`, at least 1 (rule 139).
   Workspace services judge each instruction against the highest of its kind journaled on the
   stream, as design CP-9 says. `append` and §11 compare no sequences across records: a §11 range
   rule over them is a later change, recorded in the backlog row of E20-3's code PR.
5. **A replay is refused; a re-delivery is not.** An instruction with a lower sequence, or the
   same sequence and another digest, is refused and journaled `ControlPlaneMessageRefused` with
   reason `replayed`. One whose digest equals the instruction in effect is already applied and is
   not journaled again, so a periodic pull does not fill the stream. This is the tighter of the two
   readings of design CP-5's "replayed (older sequence)": an equal sequence with other content is
   refused too. A withdrawal carries no sequence and is never `replayed`: repeating it only
   restricts again. A message whose digest was already refused is not journaled again, so one bad
   message repeated cannot fill the stream. A lapse ends with a new license's `LicenseApplied`,
   then the `LicenseStateChanged` out of `lapsed`. Rule 142 also requires a refusal of an `unknown`
   message to be `out_of_list` or `malformed`, and a `replayed` refusal to carry its sequence.
6. **No effect on an agent from these records.** `LicenseStateChanged` into `lapsed` restricts no
   agent until mandate spec §5.9 lists `license_lapsed` (E20-4; DEC-440 item 13 stays Proposed).
   Nothing here is read by `ValidationContext`, the gate, or a fold, and nothing maps to a
   `JournaledFact`.
7. **Enumerations.** Mode `managed_cell`, `hybrid` (design §3.2); license states `valid`,
   `renewal_due`, `grace`, `lapsed` (§3.3); features `hybrid`, `connected_clients` (§3.3's closed
   list as it names it); install triggers `promotion`, `operator`, `update_window`, `rollback`
   (§3.4, infrastructure §7.4); withdrawal reasons `defect`, `security`, `superseded`; catalog
   kinds `connector_package`, `model_registry_entry` (§3.6); refused kinds the five inbound
   instructions and `unknown`; refusal reasons `unsigned`, `bad_signature`, `unknown_key`,
   `replayed`, `out_of_list`, `malformed`, `not_addressed` (CP-5). A data bundle's `dataset` is an
   `id`, since data plane spec §6 names no closed list of datasets.
8. **Vectors.** A new generated `control_plane` section of `journal.yaml`
   (`reference/journal/control_plane.py`): a base draft of each record, an invalid draft for every
   member type and rule, valid drafts for the cases a rule might be misread to refuse, and every
   seeded bug caught. The test vectors stay version 3.

## Rationale

The design already fixes what may cross the link and what it may cause; this change only gives
those records a closed shape so the code PR can journal them. Keeping them on the workspace control
stream reuses the stream, writer, fencing, tenancy, and verification that exist, where a new
deployment-level stream would add a stream type, a tenant that is no workspace, and a §11 walk for
it. Per-workspace fan-out costs a few records per workspace per instruction, which is small.
Leaving sequence comparison to the writer matches the design's CP-9 ("a site refuses ... against
the highest sequence it has journaled") and keeps `append`'s rules per record, as the other closed
schemas are; the range rule can follow without changing these shapes.

## Alternatives considered

- **A deployment stream (`site:{deployment_id}`).** One record per instruction and one place for
  CP-9's highest sequence, but a new stream type, a subject outside every workspace's tenancy, and
  new §11 and anchoring scope. Rejected for v1; the per-workspace records carry the same members, so
  a later move is a copy, not a reshape.
- **Store the signed documents as artifacts (`ref`).** Lets an auditor re-verify a signature from
  the journal alone, at the cost of artifact storage and §11 check 6 for every pull. Deferred: the
  digest binds the bytes, and the documents are re-fetchable from distribution.
- **An `append` rule comparing sequences.** Would need stream state at append, which no closed
  schema's rule reads today. Deferred to a §11 range rule (item 4).
