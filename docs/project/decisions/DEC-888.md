## Context

A `ConnectionRevoked` is a control-stream record (§9.2, §9.10): `append` refuses one on any other
stream (`wrong_stream`). §11 does not re-run `append`'s schema checks on a stored chain, so a
stored account-stream `ConnectionRevoked` (from a writer bug, a restore, or a rehashed chain) was
judged by nothing. Before v0.37 the spec text left it open. DEC-885 said a `ConnectionRevoked` is
never judged and never fails closed, with control-stream revocations in mind. Its own unanchored
scan, and `reference/journal/connections.py`'s `judged()`, already count every connection record
on an account stream, a revocation included. The reference fold skipped it on a full chain and in
an anchored range, and the Rust fold (`connection_rows` in
`crates/mandate-journal/src/connection_fold.rs`) skips it in every run, unanchored ranges included.

## Decision

1. **The ruling.** A `ConnectionRevoked` belongs to the control stream. One on an account stream
   breaks rule 68 and is reported at that record as `connection_lifecycle_mismatch`, rule 68, on a
   full chain and in an anchored range, whether or not the stream is bound. §9.8 rule 68 gains a
   **Revocation** clause.
2. **Unanchored.** It is a connection record on an account stream, so an unanchored range fails
   closed at it, cause `unanchored` (DEC-885 item 4), as DEC-885's scan already reads.
3. **Control-stream revocations are unchanged.** No rule judges one, anchored or not, so a
   revocation, and §5.6's compromised revocation whose kill switch shares its batch, is never
   refused or failed closed (DEC-885 I6 stands for control streams). This amends I6 and item 4
   only for account streams.
4. **Vectors and order (ES-22).** A new section, `connection_revocations`, holds 6 cases: an
   account-stream revocation refused under rule 68 on a bound and an unbound full chain and in an
   anchored range, failing closed in an unanchored range, and two controls with the same
   revocation on the control stream that pass. The reference fold refuses it at the start of the
   account-stream branch; the mutant `stream.68.revoked` removes that refusal and is caught. The
   section is its own, as `connection_requests` and `connection_ranges` were, because the Rust
   fold still skips the record, so the tests and implementation PRs that read the section follow.
   Until they do, `main` stays green.

## Rationale

The record can only reach a stored chain by bypassing `append`. A verifier that passes it would
report a chain sound that `append` would have refused, and the account stream's fold would carry
on past a record that says the connection ended on the wrong stream. Failing closed matches
`AGENTS.md` rule 3: ambiguity resolves to the safe default. Refusing it holds no risk reduction,
because no writer can append it. The real revocation is the control-stream record, which stays
unjudged.

## Alternatives considered

- **Ignore it, as the folds did.** Rejected: §11 would
  pass a stored record `append` refuses, and the unanchored and anchored runs would disagree with
  DEC-885's own scan, which already counts it as judged.
- **Treat it as ending the account stream's connection** (a revocation the account fold reads).
  Rejected: it would give an account-stream record a meaning §9.8 never wrote, and widen what a
  stored chain can say.
- **A new code, such as `connection_stream_mismatch`.** Rejected: rule 111's closed list would
  change, while rule 68 already owns "what an account stream may hold".
