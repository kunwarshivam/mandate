## Context

DEC-2129 item 7 has the API refuse a grant from a user the bound mandate does not list in
`autonomy.approval.approvers`, and its item 8 records that the runtime refused every grant once the
control stream held a §9.12 record. DEC-2384 (lane AP) makes the runtime fold §9.12, and the
coordinator asked that both gates resolve the references through one function. The runtime's
reading is narrower than item 7's in two ways: it requires the approver role for every reference,
as V-024 says approvers are users with the approver role, and the membership fold has no org owner
role for `role:owner` to read.

## Decision

1. **One resolution, read at the membership fold.** A reference lists only an `active` member (a
   member in its cool-off does not count), and only while that member holds the effective
   `approver` role:
   - `user:<id>`: the member whose principal id, as its ULID text, is exactly `<id>`;
   - `role:approver`: every such member;
   - `role:workspace_admin`: every such member who also holds `workspace_admin`;
   - `role:owner`: such a member whom a founding `MemberActivated` (no invitation) made, since the
     founder is the org owner (identity spec §3.2) and the fold holds no org owner role.
   A fold that cannot answer is a refusal, never an empty pass.
2. **It replaces DEC-2129 item 7's list.** The rest of item 7 holds: `forbidden`, the bound version,
   users only, and `journal_unavailable` when the version or the fold cannot be read.
3. **One function, two gates.** The API's grant route and the runtime's admission check 3 call the
   same resolution, and each keeps its own call site and refusal. The function has its own property
   tests against an oracle written apart from it, and each gate's tests assert their outcome.
4. **The matrix row before the 404.** DEC-2129 item 1's order reads with the matrix row first, as
   for a Skip: a principal the Approve row does not admit is `forbidden` for any approval id, so
   the answer never shows whether an approval exists. Then the 404, the approvers, the delegation,
   `live`, and step-up.
5. **DEC-2129 item 8 ends with DEC-2384.** Once the runtime folds §9.12, a founded workspace's
   grants are judged, not refused wholesale.

## Rationale

Items 1 and 4 only narrow: item 1 the set item 7 named, item 4 what a refusal reveals. Under item
1 no one the API admits is refused by the runtime for being unlisted, and no new user is admitted
anywhere. Item 3 is the coordinator's: two resolutions would drift.

## Alternatives considered

- **Keeping item 7's wider list.** Rejected: the API would admit grants the runtime refuses.
- **Two implementations.** Rejected for item 3's reason; the gates stay two by their call sites.
