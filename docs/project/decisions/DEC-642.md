## Decision

1. **Who constructs it.** Only the authorization step (`mandate-identity`'s `authorize`)
   constructs a `TenantContext`, and only when it authorizes a permission at a workspace's scope.
   Its fields are private; it has no public constructor, no `Default`, no deserializer, and no
   `Clone`. An org-scope authorization yields no `TenantContext` directly: it yields a sealed
   `OrgContext` that fans out to one `TenantContext` per workspace of the organization
   ([DEC-832](DEC-832.md)).
2. **What it carries.** The workspace and its organization, the authenticated principal (its ID
   and kind), and the one permission authorized. Callers read them; nobody sets them.
3. **Data APIs take only a context.** Every store, cache, queue, journal, and vault API over a
   workspace's data takes a `&TenantContext`, or the `SystemContext` of item 5, through one
   sealed trait only those two types implement, and reads the workspace from it; none takes a
   bare workspace ID. A request's context lives for one request, built after the uncached
   membership read of §6.2, and is never stored or serialized.
4. **The membership read.** Authorizing needs a read before any context exists. `authorize`
   builds the `MembershipQuery` itself (the principal, or a client's user, and the scope) and
   reads through the membership lookup it is given, which takes only that query and returns
   memberships only. No data API accepts a `MembershipQuery`, and the caller passes no membership
   list. `MembershipLookup` is sealed and implemented only by the workspace store crate;
   `Membership` has private fields and is built only by that store; test doubles live behind
   `cfg(test)` or in `mandate-identity`'s dev-only test support.
5. **`SystemContext`, for the deployment's background processes.** They act with no request and
   no principal behind them (ID-5), yet nothing they commit is anonymous (ID-1). They hold a
   `SystemContext`: one workspace and the process's workload identity, recorded as `actor.kind`
   `agent` for an agent's runtime and `system` for the executor and the scheduler. It is not an
   output of `authorize`.
6. **Unrepresentable from a request, by crate boundary, with no Cargo feature** (the #766 third
   review). `SystemContext` and its only constructor live in `mandate-identity-system`. Only the
   bootstrap crates of the agent runtime, the executor, and the scheduler, which E9-8 creates, may
   depend on it: an allowlist, checked through a new `allowed_dependents` key in
   `xtask/layers.toml`. That check is owed by E9-8, under a claim on the shared `xtask`, and does
   not run before it lands.
7. **Two seal crates** (the #766 fourth review), so no crate that builds sessions or memberships
   can mint a context. `mandate-tenant` holds only the `Tenant` trait and its sealing supertrait;
   its allowed dependents are `mandate-identity` and `mandate-identity-system`, and nothing else.
   `mandate-identity-seal` holds the tokens the constructors of `Membership` and `Session` and the
   impls of `MembershipLookup` require; its allowed dependents are `mandate-identity`,
   `mandate-authn`, the workspace store crate, and `mandate-identity-testkit` (`tool` layer,
   dev-only). The planned crates are listed in `layers.toml`'s `planned` (DEC-525).
8. **The request path never holds a `SystemContext`** (the lane lead's ruling, a tightening).
   Every write workspace services' request path makes is attributed to the authenticated
   principal, including revoking a deactivated member's sessions and client tokens (§5.2 step 2),
   which carry the deactivating admin as actor. System-attributed control writes
   (refresh-family revocation on expiry, deprovision signals, scheduled expiry) come only from a
   separate process. A back-channel logout's endpoint verifies the provider's logout token
   (signature, `iss`, `aud`, `events`) and writes it only to a non-journal relay table (an
   outbox), attributed to the verified issuer; the separate process reads it and commits
   `SessionRevoked{deprovisioned}` as `system`. The request path commits nothing to the journal. A
   `SystemContext` never gates risk reduction (`AGENTS.md` rule 13).
9. **`Session`** has private fields and is built only by §6's code (`mandate-authn`), from the
   session record it reads for the request, and by test support. It carries its `session_ref`, the
   workspace it was opened in, its kind, and a **roles snapshot**: the principal's effective roles
   in that workspace and its organization (for a client token, its user's), each with its cool-off
   end, as of the last successful membership read. Cool-off is evaluated at use (§8.3), so a stale
   snapshot is only ever narrower. A route-2 session takes its snapshot from the passkey's
   credential-table row (§3.3), which carries a snapshot per (credential, workspace): enrolment
   writes it, and reactivation un-suspends the credential and rewrites it in the same
   transaction. `MemberDeactivated` revokes
   the member's sessions and client tokens and suspends their passkey credentials, and
   `MemberRoleChanged` rewrites every one of their snapshots, each in the same transaction, so a
   snapshot is never wider than the committed membership in that workspace's store. Organization
   events are rewritten into each workspace's store as they arrive; in hybrid and on-prem
   deployments the snapshot and the live read are equally stale until then, so there a snapshot
   can be as wide as the live read would be, never wider.
10. **A failed membership read never refuses a risk-reducing operation.** This is a narrow
    carve-out from ID-3, in service of `AGENTS.md` rule 13, that adds no trading risk. It is
    **accepted by the founder, 2026-10-08** (recorded on #766). It is not a DEC-176 tightening: it
    loosens ID-3's fail-closed rule for the risk-reducing rows, with rules 2, 3, and 13 as its
    reason, and in hybrid and on-prem deployments the snapshot it reads can be as wide as the live
    read (item 9). Only a new decision of the founder reverses it, and then `membership_unavailable`
    applies to every row again. **Provenance:** the coordinator's
    ruling of 2026-10-08 on #766's API-7 amendment, in the coordinator's session (the one PR #762
    links), relayed by the L1 lead: "`membership_unavailable` must
    never be the outcome of a risk-reducing operation (AGENTS.md rules 2, 3, 13) … A failed
    membership read may refuse only operations that add or keep risk, or that change
    configuration", with the roles snapshot as the mechanism, and its two pins (a deactivation
    always wins over the snapshot; the audit view shows unverified records). It supersedes the
    reduction-only-session exemption of the third and fourth review rounds. The founder then accepted
    it on 2026-10-08. The lead's record of the
    ruling is on #766: https://github.com/kunwarshivam/mandate/pull/766#issuecomment-6063331360.
    - **The set:** workspace API-7's operations (pause, holding new openings, an owner exit, Skip,
      removing or narrowing a delegation and away mode, kill-switch engage at agent, connection or
      workspace, or org scope) and ID-5's other never-gated reductions (revoking a client,
      tightening a workspace's or an organization's policy), which the final review added (m5).
    - **The rule:** on a failed membership read, a user's or a client's request on one of them is
      authorized from its session's roles snapshot against the same §4.2 row, for every session
      kind; a reduction-only session still reaches only its four rows. The context carries
      `membership_unverified`, and the committed event records `membership_unverified: true`
      beside its `session_ref` (owed to the journal's envelope with §12.1). `membership_unavailable`
      refuses only the other rows, and only users and clients. Step-up still applies where §4.2
      asks for it (an owner exit), verified locally with no membership read; a reduction-only
      session cannot present step-up (§7.3), as before, and that is not a new refusal. A failed
      session-record read refuses the request; nothing could be journaled then.
    - **The tests it owes** (the ID-3 and ID-5 fuzz, over user and client request operations):
      with an injected membership-store outage, `membership_unavailable` never occurs across the
      set, each such operation commits with `membership_unverified: true`, and no operation outside
      the set commits; and `a_deactivated_member_is_refused_through_an_outage` (E9-7, E9-8):
      deactivate, inject an outage, and the member's sessions, tokens, and a route-2 attempt are
      refused. `membership_unverified: true` stays in the record, displayed by the workspace API's
      audit read model (§4.8) and the web audit trail.
11. **A 408 or 429 on a route-1 refresh ends the session, and is not a deprovision signal** (a
    tightening, on the lane lead's ruling, which replaces the bounded keep of the final review's
    first round): like any other non-5xx answer it ends the session at once, as v0.1 already said;
    it is not among §11.1's deprovision signals (`invalid_grant`, a disabled or revoked subject, a
    back-channel logout), so route 2, the workspace-local passkey, stays open, and `AGENTS.md` rule
    13 holds through route 2. Keeping anything on a 408 or 429 would have extended access over
    v0.1.

## Rationale

ID-8 says the context is the one way to name a workspace below the API; this fixes the type's
shape so lanes L2 and L4 code against one contract, and a compile-fail test can prove it. Items 4
and 5 close the two paths a context alone leaves open (#766 review, M2): the read that
authorization itself needs, and the automated paths that have no request.

## Alternatives considered

- **A context with a public constructor guarded by convention.** Not unrepresentable (trust ladder rung 1).
- **`Clone`.** Not needed (`&TenantContext` serves every store), and it would let a context outlive its request more easily.
