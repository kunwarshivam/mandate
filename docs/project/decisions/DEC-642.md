# DEC-642: The TenantContext contract

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The lane L1 builder agent, under DEC-79 and DEC-176: it makes ID-8 concrete and narrows what data APIs accept |
| **Story or claim** | E9-2 (claim #757), E9-8; [identity spec](../../specs/identity.md) v0.2 §4.5 |

## Decision

1. **Who constructs it.** Only the authorization step (`mandate-identity`'s `authorize`)
   constructs a `TenantContext`, and only when it authorizes a permission at a workspace's scope.
   Its fields are private; it has no public constructor, no `Default`, no deserializer, and no
   `Clone`. An org-scope authorization yields no `TenantContext`.
2. **What it carries.** The workspace and its organization, the authenticated principal (its ID
   and kind), and the one permission authorized. Callers read them; nobody sets them.
3. **Data APIs take only a context.** Every store, cache, queue, journal, and vault API over a
   workspace's data takes a `&TenantContext`, or the `SystemContext` of item 5, through one
   sealed trait only those two types implement, and reads the workspace from it; none takes a
   bare workspace ID. A request's context lives for one request, built after the uncached
   membership read of §6.2, and is never stored or serialized.
4. **The membership read.** Authorizing needs a read before any context exists. `authorize`
   builds the `MembershipQuery` itself (the principal, or a client's user, and the scope) and
   reads through the membership lookup it is given, which takes only that query and returns
   memberships only. No data API accepts a `MembershipQuery`, and the caller passes no membership
   list, so the read reaches no workspace data and no forged list reaches the step. A lookup that
   cannot answer refuses (`membership_unavailable`).
5. **`SystemContext`, for the deployment's background processes.** They act with no request and
   no principal behind them (ID-5), yet nothing they commit is anonymous (ID-1). They hold a
   `SystemContext`: one workspace and the process's workload identity, recorded as `actor.kind`
   `agent` for an agent's runtime and `system` for the executor and the scheduler. It is not an
   output of `authorize`.
6. **Unrepresentable from a request, by crate boundary** (the #766 re-review). The
   `SystemContext`'s fields are private, and its one constructor is reachable only through the
   small crate `mandate-identity-system`, which alone switches it on in `mandate-identity`. Every
   request-serving crate (`mandate-api`, `mandate-api-server`, and the workspace services'
   identity crate) lists `mandate-identity-system` in `forbidden_internal` (DEC-525). The crate,
   those `xtask/layers.toml` entries, and a check that no other crate switches the constructor on
   land with the E9-8 code.
7. **The request path never holds a `SystemContext`** (the lane lead's ruling, a tightening).
   Every write workspace services' request path makes is attributed to the authenticated
   principal, including revoking a deactivated member's sessions and client tokens (§5.2 step 2),
   which carry the deactivating admin as actor. System-attributed control writes (refresh-family
   revocation on expiry, deprovision signals, scheduled expiry) come only from a separate process.
8. **It never gates risk reduction.** Automated exits, protective orders, and kill switches proceed
   without any check a `SystemContext` could fail (`AGENTS.md` rule 13).

## Rationale

ID-8 says the context is the one way to name a workspace below the API; this fixes the type's
shape so lanes L2 and L4 code against one contract, and a compile-fail test can prove it. Items 4
and 5 close the two paths a context alone leaves open (#766 review, M2): the read that
authorization itself needs, and the automated paths that have no request.

## Alternatives considered

- **A context with a public constructor guarded by convention.** Not unrepresentable (trust ladder rung 1).
- **`Clone`.** Not needed (`&TenantContext` serves every store), and it would let a context outlive its request more easily.
