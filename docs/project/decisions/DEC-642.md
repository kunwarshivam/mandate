# DEC-642: The TenantContext contract

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The lane L1 builder agent, under DEC-79 and DEC-176: it makes ID-8 concrete and narrows what data APIs accept |
| **Story or claim** | E9-2 (claim #757), E9-8; [identity spec](../../specs/identity.md) v0.2 §4.5 |

## Decision

1. **Who constructs it.** Only the authorization step (`mandate-identity`'s `authorize`)
   constructs a `TenantContext`, and only when it authorizes a permission at a workspace's scope.
   Its fields are private; it has no public constructor, no `Default`, no deserializer, and no
   `Clone`. An org-scope authorization yields no `TenantContext`.
2. **What it carries.** The workspace and its organization, the authenticated principal (its ID
   and kind), and the one permission authorized. Callers read them; nobody sets them.
3. **Data APIs take only a context.** Every store, cache, queue, journal, and vault API over a
   workspace's data takes a `&TenantContext`, or the `SystemContext` of item 5, through one
   sealed trait only those two types implement, and reads the workspace from it; none takes a
   bare workspace ID. A request's context lives for one request, built after the uncached
   membership read of §6.2, and is never stored or serialized.
4. **The membership read.** Authorizing needs a read before any context exists. `authorize`
   builds the `MembershipQuery` itself (the principal, or a client's user, and the scope) and
   reads through the membership lookup it is given, which takes only that query and returns
   memberships only. No data API accepts a `MembershipQuery`, and the caller passes no membership
   list. `MembershipLookup` is sealed and implemented only by the workspace store crate;
   `Membership` has private fields and is built only by that store; test doubles live behind
   `cfg(test)` or in `mandate-identity`'s dev-only test support.
5. **`SystemContext`, for the deployment's background processes.** They act with no request and
   no principal behind them (ID-5), yet nothing they commit is anonymous (ID-1). They hold a
   `SystemContext`: one workspace and the process's workload identity, recorded as `actor.kind`
   `agent` for an agent's runtime and `system` for the executor and the scheduler. It is not an
   output of `authorize`.
6. **Unrepresentable from a request, by crate boundary, with no Cargo feature** (the #766 third
   review). `SystemContext` and its only constructor live in `mandate-identity-system`. Only the
   bootstrap crates of the agent runtime, the executor, and the scheduler, which E9-8 creates, may
   depend on it: an allowlist, checked through a new `allowed_dependents` key in
   `xtask/layers.toml`. That check is owed by E9-8, under a claim on the shared `xtask`, and does
   not run before it lands.
7. **Two seal crates** (the #766 fourth review), so no crate that builds sessions or memberships
   can mint a context. `mandate-tenant` holds only the `Tenant` trait and its sealing supertrait;
   its allowed dependents are `mandate-identity` and `mandate-identity-system`, and nothing else.
   `mandate-identity-seal` holds the tokens the constructors of `Membership` and `Session` and the
   impls of `MembershipLookup` require; its allowed dependents are `mandate-identity`,
   `mandate-authn`, the workspace store crate, and `mandate-identity-testkit` (`tool` layer,
   dev-only). The planned crates are listed in `layers.toml`'s `planned` (DEC-525).
8. **The request path never holds a `SystemContext`** (the lane lead's ruling, a tightening).
   Every write workspace services' request path makes is attributed to the authenticated
   principal, including revoking a deactivated member's sessions and client tokens (§5.2 step 2),
   which carry the deactivating admin as actor. System-attributed control writes
   (refresh-family revocation on expiry, deprovision signals, scheduled expiry) come only from a
   separate process. A back-channel logout's endpoint verifies the provider's logout token
   (signature, `iss`, `aud`, `events`) and writes it only to a non-journal relay table (an
   outbox), attributed to the verified issuer; the separate process reads it and commits
   `SessionRevoked{deprovisioned}` as `system`. The request path commits nothing to the journal. A
   `SystemContext` never gates risk reduction (`AGENTS.md` rule 13).
9. **`Session`** has private fields and is built only by §6's code (`mandate-authn`) and by test
   support. It carries its `session_ref`, the workspace it was opened in, and its kind.
10. **A failed membership read fails closed for every row except risk reduction** (the lane lead's
    ruling, recorded as an agent reading under DEC-176, with `AGENTS.md` rule 13 as its reason: it
    adds no risk, since a pause and a kill switch never add any, rule 3, and it keeps ID-3 for every
    other row). `membership_unavailable` applies only to users and clients, never to the host CLI,
    a service account, or a platform operator. The exemption covers Pause and the agent-scope and
    connection-or-workspace-scope kill-switch engage rows, not the org-scope one. On those rows, at
    its own workspace's scope, a user's reduction-only session (§6.4 routes 1 and 2) is authorized
    from the session alone when the session record itself is read and unrevoked, and the committed
    event carries `membership_unverified: true` beside its `session_ref` (owed to the journal's
    pause and kill-switch events with §12.1's changes). A session read that fails too is refused.
    The bound needs no timer: §5.2 step 2 revokes a deactivated member's sessions in the same
    transaction as `MemberDeactivated`. Any other session meeting a failed read there is refused
    `membership_unavailable` with the hint to use route 2, whose passkey public keys are in the
    workspace deployment's credential table (§3.3). A reduction-only session is still refused
    after a deprovision signal. The ID-3 and ID-5 fuzz assert that such a pause or engage commits
    with `membership_unverified: true` and nothing else does.

## Rationale

ID-8 says the context is the one way to name a workspace below the API; this fixes the type's
shape so lanes L2 and L4 code against one contract, and a compile-fail test can prove it. Items 4
and 5 close the two paths a context alone leaves open (#766 review, M2): the read that
authorization itself needs, and the automated paths that have no request.

## Alternatives considered

- **A context with a public constructor guarded by convention.** Not unrepresentable (trust ladder rung 1).
- **`Clone`.** Not needed (`&TenantContext` serves every store), and it would let a context outlive its request more easily.
