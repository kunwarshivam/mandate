# DEC-531: Broker rules are a declared capability profile, not code

|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and AGENTS.md rule 9; the spec text it needs is SP1 in the brief, which the founder approves as a protected path) |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | An agent (Claude Code, the builder of the first live trade brief), at the founder's direction on 2026-10-08 that broker rules must not be coded as one-off rules that need rework |
| **Story or claim** | E7-6, E7-15; [first live trade brief](../tasks/first-live-trade.md); [ADR-0004](../../adr/0004-broker-capability-profiles.md) |

The coordinator assigned DEC-531 after this decision's first number, DEC-530, collided with the
E10-16 D2 builder's reservation.

## Decision

1. **Each connector declares a capability profile**: a typed, versioned value listing what its
   broker accepts, built from the broker's published contract and nothing else. For each asset
   class and session: the order types allowed; for each order type, the quantity forms allowed
   (whole, fractional, notional); the times in force; the protection forms offered (bracket, OCO,
   one resting stop-limit, none); and idempotency (a client order id, whether a retry with it is
   idempotent, whether orders can be queried by it).
   The type and its canonical hash live in `mandate-domain` (layer 1, pure, hashed through
   `mandate-canon`), below both of its readers: `mandate-builder` (layer 5) cannot depend on
   `mandate-executor` (layer 6). `BrokerConnector` gains `fn profile()` in the executor.
2. **Shared code reads the profile and never names a broker or branches on asset class to learn
   a broker rule.** The order builder sizes to the quantity form the profile allows for the order
   type the policy chose; protection takes the strongest form the profile offers for the
   position; reconciliation looks up by client id when the profile says it can, and otherwise
   takes one shared fallback (DEC-529 item 4); deployment refuses a mandate whose order policy
   or protection needs something the connection's profile lacks.
3. **Our policy stays separate from broker facts.** Platform rules (`AGENTS.md` rule 12: limit
   openings in the regular session; no short sales) are the gate's and the policy's, never a
   profile row. The builder intersects the two: Robinhood's "fractional only for market orders"
   and our "openings are limit orders" leave whole shares, with no Robinhood code anywhere.
4. **The profile is journaled and pinned.** Its canonical hash is registered as configuration
   (`ConfigSnapshotRegistered`, kind `broker_profile`) and, for MCP brokers, tied to the
   contract hash (connections spec §6.2 rule 3). A changed profile is a new version; a
   connector whose live contract no longer matches its profile halts openings.
5. **Alpaca moves first.** Trading spec §5.2 already is Alpaca's profile, written as a table.
   Alpaca's connector declares it, and the executor's `asset_class == Crypto` choice of a single
   stop-limit (`protection.rs`) becomes a profile lookup. Behavior on Alpaca does not change;
   the existing tests pin it.
6. **Scope now is only what the first live order reads**: order types and quantity forms for
   US equities in the regular session, times in force, protection forms, and idempotency. Rows
   for crypto, extended hours and options are added when a story needs them, in the same shape.

## Rationale

The founder ruled that Robinhood's quirks must not become code that needs rework. Every rule
the first draft of the live brief would have hard-coded (whole shares for limits, no OCO, no
query by client id) is a fact about one broker that will differ for the next broker and may
change at Robinhood. As data, each is one row; the code that reads it is written and tested once.
It also pays down an existing debt: the executor today infers "no OCO" from the asset class
being crypto, which is Alpaca's rule hidden in shared code.

## Alternatives considered

- **Robinhood branches in the connector and executor:** faster by perhaps two PRs, rejected by
  the founder as rework.
- **A full broker-neutral rewrite of trading spec §5 before any code:** the right end state, but
  slower; item 6 takes only the rows the first live order reads.
- **Capabilities negotiated at runtime from the broker's tool schemas:** rejected; broker
  metadata never changes what the connector may do (CN-9).
