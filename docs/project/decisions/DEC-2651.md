# DEC-2651: After a merge it made, `merge.yml` also dispatches `release` and `web-deploy` on `main`, and `release`'s post-merge dispatch runs the push's publish path

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-30 (UTC) |
| **Decided by** | an agent, as a reversible CI change (DEC-79) |
| **Story or claim** | No story; process and CI. #3018, #3020 and #3021, merged by `merge.yml` on 2026-10-30, got no `release` run: the last release runs on `main` were run 1677 and earlier, the founder's manual merge of #3003 at 07:29Z |

## Decision

1. A merge `merge.yml` makes pushes to `main` with that workflow's own `GITHUB_TOKEN`, and GitHub
   starts no workflow for such a push. DEC-2610 item 4 made up for that for `ci` only. So after a
   run of `merge.yml` that merged at least one pull request, its dispatch job, renamed from
   `ci-on-main` to `post-merge`, dispatches on `main`, once each and in this order, the three
   workflows a push to `main` starts: `ci` with `post_merge: true` (DEC-2610), `release` with
   `post_merge: true`, and `web-deploy`. A failed dispatch does not stop the ones after it. The job
   still holds `actions: write` and nothing else, checks out nothing and reads no secret, and
   nothing else in `merge.yml` dispatches.
2. `release.yml` takes the `workflow_dispatch` input `post_merge` (boolean, default `false`), as
   `ci.yml` does. A run with it runs the push's publish path, `publish-amd64`, `publish-arm64` and
   `publish-index`, whose condition is now a push to `main`, or a dispatch on `main` with
   `post_merge` true. Every `release-signing-*` job, the founder-signed path, now runs only on a
   dispatch on `main` with `post_merge` false, so a post-merge run never waits on the founder's
   approval of the `release-signing` environment, and a manual dispatch, which leaves the input at
   its default, runs only the signing path, as before. The signing condition reads
   `inputs.post_merge == false` rather than a negation, which leak-guard L12 refuses on a job with
   an environment.
3. A post-merge dispatch joins the pushes' concurrency group, `release-refs/heads/main`, which
   cancels nothing, so a burst of merges, by people or by `merge.yml`, releases once at its tip as
   DEC-2025 says. Any other dispatch keeps its own group, `release-dispatch-refs/heads/main`, so a
   signing run waiting on the founder never holds the releases.
4. `web-deploy` is dispatched after every such merge, not only one that touched `web/`: the merge
   job would have to list each merged pull request's files to know, and a deploy builds and ships
   only `main`'s web app. Its own `WEB_DEPLOY_ENABLED` switch and its `environment: production`
   still apply (DEC-1005), and `web/scripts/workers.mjs` still pins its shape and that nothing
   else deploys.
5. `xtask` pins the change: `the_merge_workflow_runs_ci_on_main_after_a_merge_it_made` holds the
   three dispatch lines exactly, in order, as the only `run:` lines of `post-merge` and the only
   dispatches in `merge.yml`; and `the_post_merge_dispatch_publishes_and_never_signs` reads every
   publish and signing job's condition and the concurrency group from `release.yml` and judges
   them with an evaluator of GitHub's expression language, for a push, a post-merge dispatch and
   a plain dispatch, on `main` and on another branch.

## Trust is unchanged

- **The same code.** A dispatch on `main` builds `main`'s tip, the commit the push would have
  built, and the publish jobs still require the rebuild to match the digest `compare` proved
  reproducible.
- **The same identity.** A dispatch on `main` runs this same file at `refs/heads/main`, so the
  keyless signature's OIDC identity, the certificate subject
  `https://github.com/kunwarshivam/mandate/.github/workflows/release.yml@refs/heads/main` that
  the clusters' `charts.yaml` and the `release-signed` image policy verify, is the push's. Neither
  pins the triggering event.
- **The founder-signed path is untouched.** Its five jobs, its environment, its key and its steps
  are as DEC-2024 and DEC-2026 left them; only their condition gains `post_merge` false, which a
  manual dispatch always has unless someone sets it.
- **No new holder of a right.** Starting a dispatch already took `actions: write` on the
  repository; `merge.yml` held it already for `ci` (DEC-2610), and DEC-175's gate still decides
  what reaches `main`.

## Rationale

Since DEC-175, most merges land through `merge.yml`, so `release.yml`'s push trigger fired only for
the founder's own merges, and staging's charts, which verify the push path's keyless signatures,
fell behind every auto-merge. A plain dispatch could not stand in, because a dispatch runs only
the founder-signed path. The input gives the dispatch the push's path explicitly, the way
DEC-2610 did for `ci`, without loosening the signing path or the leak-guard (DEC-2032).

## Alternatives considered

- **Merge with a token whose pushes start workflows** (a person's or an app's). Declined: a new
  credential to hold and rotate, which DEC-175 avoided on purpose.
- **Treat every dispatch on `main` as a push.** Declined: the founder's signing dispatch would then
  also publish, and there would be no way to run only the signing path.
- **Dispatch `web-deploy` only when the merged pull request changed `web/`.** Declined for now:
  the job would need to read each merged pull request's file list, which GitHub pages, for a deploy
  that changes nothing when the web app did not change.
