## Decision

### Step-up action digests (kind `connection`)

Workspace API §3.6 says a step-up digest is the SHA-256 of the action's canonical object. §5.6
gives that object for a compromised revoke, `{connection_id, compromised: true}`. Nothing names it
for a connect or an ordinary revoke. Each object below binds every request member a replay could
vary.

1. **The canonical encoding** is the one §3.6 and identity spec §7.2 step 1 already use, written out:
   - Build the JSON object with exactly the members listed.
   - Ids are strings, as the API receives them. `compromised` is a JSON boolean. The other values
     are the lowercase strings shown.
   - Write it in journal spec §4's canonical form (RFC 8785 with §4's constraints: keys sorted by
     bytes, no whitespace).
   - The digest is the SHA-256 of those bytes, written as §3.1 writes every hash.

   This is how §3.4 builds the idempotency object. The challenge record of identity §7.2 then binds
   the digest with `action_kind: connection`, the principal, and the workspace.
2. **Connect** (`POST /connections/oauth/start`): `{action: "connect", workspace_id, broker,
   environment: "paper"}`.
   - `environment` is always `"paper"`, because Alpaca OAuth connects paper only (DEC-821 items 3
     and 7). A live start is refused before any challenge would matter (connections §5.2).
   - There is no `connection_id` yet, because the connection manager assigns it at start.
   - A member the start body gains later that changes what is connected joins this object in the
     same change.
3. **Ordinary revoke** (`POST /connections/{id}/revoke`, `compromised` `false` or absent):
   `{workspace_id, connection_id, compromised: false}`.
   - An absent `compromised` binds `false`, so the absent and `false` spellings of one request
     have one digest.
   - Evidence for an ordinary revoke can never be spent on a compromised one, or the reverse,
     because the two objects differ in `compromised`.
   - A connect object can never equal a revoke object, because their member sets differ.
4. **The compromised revoke binds `workspace_id` too** (the reading that tightens):
   `{workspace_id, connection_id, compromised: true}`.
   - §5.6 binds only `{connection_id, compromised: true}`. Every digest here binds its workspace,
     so evidence never depends on a connection id being unique across workspaces. That matters
     most where no challenge record names the workspace, as with `cli_confirm`.
   - **Owed spec text:** workspace API §5.6's `step_up` row must read "SHA-256 of
     `{workspace_id, connection_id, compromised: true}`". The coordinator's spec queue makes that
     change; this PR does not edit the spec. Nothing on `main` computes the old object today.
   - The kill-switch half still commits without valid step-up (API-7, DEC-158 option (c)), so
     binding a member more never blocks the kill switch.
5. **Worked vectors** for a later test, with workspace `ws_01` and connection `conn_01`:

   | Action | Canonical bytes | SHA-256 (hex) |
   |---|---|---|
   | Connect | `{"action":"connect","broker":"alpaca","environment":"paper","workspace_id":"ws_01"}` | `6aea75170af9b4fea7c631e4c5f2c5f9614eb223395f9ab80cd1d19c92f840d8` |
   | Ordinary revoke | `{"compromised":false,"connection_id":"conn_01","workspace_id":"ws_01"}` | `fde6740d31abaff7b41651470ffbfc60ab0cd853534383d877196441ff7417db` |
   | Compromised revoke | `{"compromised":true,"connection_id":"conn_01","workspace_id":"ws_01"}` | `aece2f391435e53c580b832edbf832a4b3aa3a4d454fe144756ee7dbdb40fb9d` |

### Where the revoke reads positions

6. **An ordinary revoke's refusal comes from the journal folds, never from a read model.**
   - The facts are: an agent on the connection holds positions, or is not stopped (workspace API
     §4.5, connections §5.4 and §9.1).
   - The API folds them from the journal: the control stream for which agents are on the
     connection and their commands, and each of those agents' streams and the connection's account
     stream for mode and positions.
   - Read models (§4.7) are never the authority for this refusal, or for any refusal (§6.2,
     API-7, API-14).
7. **A fold that cannot answer refuses the ordinary revoke.**
   - "Cannot answer" means the fold is unavailable, stale, or behind its watermark: its `seq` for a
     stream it needs is behind that stream's head as read in the same request.
   - The revoke never assumes "no positions" or "stopped" (`AGENTS.md` rule 3). An ordinary revoke
     is not risk reduction (§4.5), so refusing it adds no risk.
   - The refusal says to retry, or to use the compromised path. Its error code is owed to §3.5,
     with the digest text of item 4.
   - **The compromised path stays available whatever the fold's state.**
8. **The compromised revoke shows positions it cannot know as "unknown".**
   - §5.6 step 3 says the confirmation and the alert name the positions left at the broker. When
     nothing authoritative answers (the account stream's fold is unavailable, stale, or behind its
     watermark), they say "unknown", never 0, "none", or an empty list.
   - The display never blocks or delays the batch. No fold read sits before the append, so the
     kill switch reads no read model and waits on nothing (API-7, API-8, `AGENTS.md` rule 13).
   - Each value is assembled for display only, after the batch commits, or separately for the
     pre-confirmation render.

## Rationale

- **Digests.** API-17 binds step-up to one action, which needs a fixed object for every action
  that takes step-up. Binding the workspace and every varying member means one piece of evidence
  authorizes exactly one request. Adding a member only narrows what evidence can authorize, so it
  is a tightening (DEC-176).
- **Folds.** A read model may lag the journal. A revoke that removes the only credential able to
  exit or re-protect must not pass on a lagging "no positions". Refusing the ordinary revoke when
  the fold cannot answer costs the owner a retry. The compromised path still exists for a credential
  that must go now.
- **"Unknown".** Showing 0 for positions we could not read would tell the owner nothing is left at
  the broker, unprotected, when something might be. That is the false safe answer rule 3 forbids.

## Alternatives considered

- **Keep §5.6's object without `workspace_id`.** Rejected: an extra member costs nothing, and the
  digest then never relies on connection ids being unique across workspaces.
- **One revoke object for both paths, with the path chosen by the body.** Rejected: evidence for an
  ordinary revoke could then authorize the compromised one, and the reverse.
- **Refuse the ordinary revoke from the read model, as §6.2 allows for a risk-increasing call.**
  Rejected: the coordinator ruled that read models are never the authority for a refusal. The fold
  is what the stream owners decide from.
- **Treat an unanswerable fold as "no positions".** Rejected by `AGENTS.md` rule 3.
- **Hold the compromised revoke until positions are known.** Rejected by rule 13 and API-7.
