# DEC-360: Where the executor journals what its fold reads beyond the registered IntentReceived and OrderSubmitted

| | |
|---|---|
| **Status** | Proposed |
| **Date** | 2026-10-02 |
| **Decided by** | The founder: every option either adds members to a schema the spec closes or changes what the executor can replay, and adding members loosens the spec toward the code (DEC-176) |
| **Story or claim** | Stream K's account-stream writers (DEC-174 item 5, DEC-307 item 5), PR #441 |

## Decision

1. **Found.** Re-deriving #441's pins from journal spec §9.1 and the schemas `mandate-journal`
   registers shows that the executor's own fold needs members those schemas do not carry:
   - `IntentReceived` (§9.1: nine members, `INTENT_RECEIVED_V1`). `fold::intent_received` reads
     the protective prices `stop` and `take_profit` from it (`prices_of`), so a protected opening
     replayed from a conforming record would lose its protection.
   - `OrderSubmitted` (not closed by §9; `ORDER_SUBMITTED_V1` has eight members). `journal_rung`
     writes, and the fold reads back (`request_of`, the order set), `agent`, `purpose`,
     `intent_id`, `extended_hours`, `stop_price`, `order_class`, `take_profit`, `stop`, and a
     ladder rung's `rung` and `at_floor`. A resubmission after a confirmed absence rebuilds the
     exact request from these (trading spec §5.7), and the order's agent and purpose drive the
     restrictions and the exit rules.
   - Both. `Batch::journal` stamps `risk_clock` on every account-stream event and the fold
     requires it (DEC-302 item 1), while §9.2 says the executor "writes it on every account-stream
     event". Neither registered schema lists it, and the vectors' `IntentReceived`, `GateDecided`,
     and `OrderSubmitted` carry none (DEC-174 item 5).
2. **The options.** (a) A journal spec change that adds these members to `IntentReceived` and to a
   closed `OrderSubmitted` (and `risk_clock` to every account-stream schema), with vectors, as
   DEC-302 did for the snapshot. (b) Move them to records that can carry them: the protective
   prices to `ProtectionChanged`, and the submission's executor-only members to a companion
   record journaled in the same batch, with the fold reading them from there. (c) A mix: (a) for
   `risk_clock`, which §9.2 already says the executor writes everywhere, and (b) for the rest.
   **Recommended: (c).** `risk_clock` on every account-stream event is already the spec's own
   sentence, and the rest keeps `IntentReceived` the exact copy of the proposal that §9.1 and
   rule 10 make it.
3. **Meanwhile, the conservative option.** #441's pins hold §9.1 and the registered schemas as
   they stand (DEC-307), and no writer gains a member here. The executor's `IntentReceived` and
   `OrderSubmitted` drafts stay refused at `append` exactly as they are on `main` today (DEC-174
   item 5): an opening is never gated, which adds no risk (rule 3). An exit or a protective order
   is journaled through `OrderSubmitted` before it is sent (rule 5), so while the drafts are
   refused no exit leaves through the journal either; that is today's state, not one this
   decision creates, and the fix must land before any adapter journals the executor's drafts for
   real (the tracer slices). The fee step's `AccountSnapshotRecorded` and the `risk_clock` stamp
   do not wait for this: their schema carries `risk_clock`, and DEC-305 and DEC-306 pin them.

## Rationale

The pins can only hold what the spec and the registered schemas say. Stating the gap here, rather
than in a pin that a conforming writer could not pass, keeps the tests honest and puts the one
choice that loosens a closed schema in front of the founder.

## Alternatives considered

- Pin the executor's current members and amend the spec to match. Rejected: that loosens §9.1
  toward the code, which only the founder may do (DEC-176).
- Drop the members from the drafts now. Rejected: the fold could no longer replay a protected
  opening or rebuild a resubmission, which would leave a filled entry unprotected after a restart
  (`AGENTS.md` rule 13).
