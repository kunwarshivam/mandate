# DEC-840: Q2's account rules: declared by the connector, carried by the preflight, and a reported deficit refuses the paper opening

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | An agent (Claude Code, the Q2 tests builder), under DEC-79 (reversible engineering choices) and DEC-176 (item 4 only tightens) |
| **Story or claim** | Q2, E7-19 slice 3 remainder; claim [#851](https://github.com/kunwarshivam/mandate/issues/851); [first paper trade brief](../tasks/first-paper-trade.md) Q2 and X-9 |

## Context

The brief says Q2 takes the account type and the day-trading regime "from the connector, which
declares them for Alpaca". No connector declares them today. `BrokerConnector::profile` returns a
`CapabilityProfile` (DEC-531), which holds order cells and idempotency claims only, and nothing in
`mandate-alpaca` names an account type or a regime. Trading spec §7.2 states both per broker:
"Account type: Alpaca: always margin" and "Day-trading regime: Alpaca: `intraday_margin`".

## Decision

1. **The connector declares the rules as data.** `mandate-alpaca` gains
   `account_rules::alpaca() -> AccountRules`, re-exported as `alpaca_account_rules`, beside
   `alpaca_profile`. `AccountRules` holds an `AccountType` (`mandate-accounting`) and a
   `DeclaredRegime` (`IntradayMargin` or `LegacyPdt`). The declaration names the regime only; the
   figures each regime reads are the broker's account answer.
2. **The preflight carries the declaration.** `BrokerFacts` gains `account_rules`, which
   `preflight` fills from `alpaca_account_rules()`. A fixture can replace it, and that is how the
   tests show a different declaration flows through.
3. **The tests PR carries the declaration and the field, and adds no stub.** This departs from
   the DEC-77 tests-PR shape of stubs only, which DEC-83's mutant skip assumes, on DEC-524 item
   1's precedent; the mutants of the real code still run. A stub for either would fail every
   preflight, which breaks the passing paper, tracer and registered runs. A shell value in the field would be the X-9
   constant moved, not removed. So the declaration is real data in the tests PR, pinned by a
   passing test (`mandate-alpaca`'s `alpacas_declared_account_rules_are_section_7_2s`). The gate
   template is left unchanged until the implementation PR. Q2's pending tests therefore fail on
   the template's answer, not at a stub, and each has an `xtask/behaviour-only` row that the
   implementation PR deletes.
4. **Under `intraday_margin`, the paper run refuses its opening on a reported deficit.** §9.2
   says "if the broker reports a deficit, agents go `exits_only`". DEC-524's "Not decided here"
   records that nothing does this yet, and the gate denies nothing per order on a deficit. The
   paper run places only an opening. So the shell refuses the assembly before any `POST`, as
   `Absent { what: "an account with no maintenance deficit" }`. A maintenance figure
   `BrokerAccount::maintenance_excess` refuses (a negative requirement, DEC-524 item 2) is refused
   as `Absent { what: "the broker's maintenance excess" }`, and is never read as no requirement.
   A zero excess is no deficit and passes. This only tightens and adds no risk (DEC-176,
   `AGENTS.md` rule 3, the brief's FT-8). It lapses when the deficit becomes the `exits_only` mode
   §9.2 names.
   The refusal applies only to assembling an opening run. No position-management, exit,
   protective-order or crash-recovery path (E1b, recovery) may call it or be gated by it
   (`AGENTS.md` rule 13).
5. **The mapping.** The gate's `account_type` is the declared type. `IntradayMargin` maps to
   `DayTradeRegime::IntradayMargin { maintenance_excess }`, with the executor's
   `BrokerAccount::maintenance_excess`, and `LegacyPdt` maps to `DayTradeRegime::LegacyPdt`.
   `prior_close_equity` is the broker's `last_equity` under either regime (DEC-524 item 4).

## Rationale

- §7.2 states the rules per broker, so the broker's connector is the one place that knows them.
  DEC-531 item 1 keeps such facts out of shared code that reads a broker's name. The shell's
  paper module already reads Alpaca's types (`AssetSnapshot`, `LatestQuote`), so a free function
  beside `alpaca_profile` adds no new coupling.
- Carrying the declaration in `BrokerFacts`, which already holds what the broker answered, lets a
  test vary it without a second connector.

## Alternatives considered

- **A field of `CapabilityProfile`.** Rejected for Q2. The profile is canonical and hashed, and it
  is registered as a `broker_profile` configuration snapshot. Adding a member changes its schema,
  every profile hash, and `mandate-domain`. That is right when a second connector (Robinhood's
  `legacy_pdt`, DEC-620) needs it, and it is left for then.
- **A method on `BrokerConnector`.** Rejected: every fake connector in the executor's tests would
  need it, for a fact the preflight already reaches through `mandate-alpaca`.
- **A stub declaration, so the pending tests stop at a stub.** Rejected, as item 3 says.
- **Let a deficit flow to the gate as a negative excess.** Rejected for the paper run. The gate
  approves the opening, and §9.2 says agents go `exits_only`.
