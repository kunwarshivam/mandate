## Context

§11's `connection_lifecycle_mismatch` checks stream rules 66, 67, 68, and 131 "on every range", and
rule 131's ranges clause says a range's fold "starts empty at its trusted start". That suits rule
131's existence requirement, which DEC-699 already confines to the full-chain run. It does not suit
rules 66 to 68, which read records that a range can begin after:

- **control stream:** a range that begins after an establishment and then holds a rotation, a
  `reauthorize` or `reconnect` refusal, or a re-establishment. An empty fold has no establishment,
  so rule 66 or 67 refuses a valid record;
- **account stream:** a range that begins after the binding copy and then holds a state change, a
  `daily` or `executor_start` check, or a clear on a rotation from before it. An empty fold has no
  binding and no suspension, so rule 68 refuses a valid record.

Each is a false SEV-1 (§11, "On failure"): it pauses agents or freezes mandate changes on a sound
journal. An empty fold also misses real breaks whose evidence lies before the range. The
coordinator ruled option (b): the range is anchored on fold state derived from the stored chain
before its trusted start, and an unanchored range fails closed, as `held_mismatch`
(`verify_agent_stream_anchored`) and DEC-782 item 4 do.

## Invariants

Written before the rules, and each a check in `reference/journal/connections.py` that the range
mutants below are shown to fail:

- **I1, agreement.** For a chain C whose records before position k break no rule, the range
  C[k..] anchored on the fold of C[..k] reports exactly what the full-chain run reports for those
  records: the same first record, the same rule, or none. Checked on every split of every
  full-chain sequence in `connections` and `connection_requests` (`ranges.agree`).
- **I2, nothing invented without an anchor.** An unanchored range never reports a rule. Its only
  failure is the fail-closed cause, at its first record a stream rule judges, found by an
  independent scan (`ranges.unanchored`).
- **I3, nothing passed without an anchor.** An unanchored range never passes a record that rule
  66, 67, 68, or 131 judges.
- **I4, the anchor of nothing.** A range from `seq` 1 is anchored on nothing before it: it is the
  full-chain run.
- **I5, no read model.** The anchor is derived only by folding the stored chain from `seq` 1; a
  chain that breaks a rule before the range yields no anchor, so the range fails closed rather
  than trusting a broken state.
- **I6, risk reduction is never held.** No rule judges a `ConnectionRevoked`, anchored or not, so
  a revocation, and §5.6's compromised revocation whose kill switch shares its batch, is never
  refused or fail-closed by a range.

## Decision

1. **The connection anchor.** For a range of stream `s` with trusted start `from_seq = n`, the
   connection anchor is the state the fold of rules 66, 67, 68, and 131 holds after `s`'s records
   `1` to `n − 1`, folded in `seq` order exactly as the full-chain run folds them. It is the whole
   of what those rules read:
   - **on a control stream:** each connection id's first `ConnectionEstablished` (its version,
     `broker`, `environment`, and `account_ref`); its latest `ConnectionEstablished` or
     `ConnectionRevoked`; its latest scopes (its establishment's or its latest rotation's); each
     `account_ref` and the id whose establishment first named it (CN-5); the open
     `ConnectionRequested` records with their members (`connection_id`, `account_ref`, `broker`,
     `environment`, `user`, `step_up`); every `account_ref` a request named; rule 67's two sets,
     the ids whose latest revocation closed a request and the ids revoked by a revocation that
     closed none; and whether the stream holds a request at all, which binds it to rule 131;
   - **on an account stream:** the connection that owns it (the first connection record's
     `connection_id`); the latest copy of `ConnectionEstablished` (`broker`, `environment`,
     `account_ref`), or none while the stream is `connecting`; for each check occasion, the
     latest `ConnectionChecked`'s position, whether it passed every result, and whether it listed
     `contract`; each rotation copy's event id and the position of the `reauthorize` check it
     followed; the state the last `ConnectionStateChanged` left (`active` with none); whether that
     record was a `condition_cleared`; and the position of the last entry into `suspended`.

   Positions are `seq` values on the stream, so the range continues the same order.
2. **How it is derived.** Only by that fold over the stored chain before the trusted start: the
   hot store, or the segments a canonical export holds from `seq` 1. Never from a read model, a
   cache, or the connection manager's or executor's in-memory state, which are what a broken chain
   would have corrupted. The fold stops at a record that breaks a rule; a chain that breaks one
   before the range yields no anchor (I5), and the full-chain run reports that record. A caller
   that cannot read the chain before the range, as the CLI over an export cannot (DEC-782 item
   4), has none.
3. **An anchored range** checks rules 66, 67, 68, and 131 on every record in it, from the anchor's
   state, as the full-chain run would (I1). **Rule 131's closing existence is checked too**: the
   anchor carries the open requests and whether the stream is bound by a first request, which is
   all the requirement reads. DEC-699 confined it to the full-chain run only because an empty fold
   could not see a request before the range; with the anchor it can, and checking it refuses only
   what the full-chain run already refuses, sooner. This amends DEC-699 item 3's ranges clause.
   A range from `seq` 1 is anchored on nothing (I4).
4. **An unanchored range** fails closed at its first record that rule 66, 67, 68, or 131 judges: a
   `ConnectionRequested`, `ConnectionEstablished`, `ConnectionCredentialRotated`, or
   `ConnectionRefused` on a control stream, or any connection record on an account stream. Each of
   these can be broken by a record before the range (an earlier establishment, holder, request,
   binding, check, or state), so none can be judged from the range alone. A `ConnectionRevoked`
   passes (I6). Records before that first one are not judged, and none after it is reached.
5. **The fail-closed outcome.** It is reported as `connection_lifecycle_mismatch` at that record's
   `seq`, as `held_mismatch` reports its own "no anchor" case, so `VerificationRun`'s closed list
   of codes (rule 111) and its consumers are unchanged. The verifier's own report gives the cause
   `unanchored` in place of the rule number, so a reader can tell "could not be verified from this
   range" from "broke rule 66": the reference vectors' `expect` is `{outcome: Unanchored, code:
   connection_lifecycle_mismatch, index}`. It is a failure, with §11's SEV-1 path: a range that
   cannot be judged is not passed (`AGENTS.md` rule 3).
6. **The cause check stays full-chain only.** `connection_cause_mismatch` follows a cause across
   the control stream and its account streams, which no range holds together; nothing here changes
   it.
7. **Vectors and order (ES-22).** `reference/journal/connections.py` takes the stored chain before
   a range (`before`, or `null` when the caller cannot read it), derives the anchor by folding it,
   and fails closed without one. A new section, `connection_ranges`, holds 22 range cases: anchored
   ranges that are valid (a rotation, a `reauthorize` and a `reconnect` refusal, a
   re-establishment, a connect closing the anchor's request, a daily check and a state change after
   the binding, a clear and acknowledgment on the anchor's rotation), anchored ranges with a real
   break (a widening rotation, a re-establishment while live, an `account_ref` the anchor's holder
   owns, a connect with no request, a reused `account_ref`, a state change from the wrong state, a
   clear on a rotation from before the suspension), and unanchored ranges that fail closed (a
   rotation, a `reconnect` refusal, a request, a daily check, a revocation then a request, and a
   chain broken before the range), with one unanchored range of revocations only that passes. The
   one existing range vector, `connection_requests`' `range_after_an_unseen_request`, gains the
   chain before it (`before`: the request it closes) and keeps its answer, Valid. Range mutants:
   `range.anchor_ignored` (the v0.34 empty fold), `range.unanchored_empty` (no fail-closed),
   `range.existence_skipped` (DEC-699's range exemption kept in an anchored range),
   `range.revoke_judged` (a revocation fails closed), and `range.broken_prefix` (an anchor folded
   from a broken chain); each is caught. `stream.131.range` is retired: checking existence in an
   anchored range is now the rule. The code change that reads `connection_ranges` replaces
   #1145's empty-fold `verify_connection_lifecycle_range` with an anchored run and the
   fail-closed run; L5's W3 (the CLI's connection checks, DEC-782 item 5) consumes it.

## Rationale

The anchor is the full-chain run's own state at the trusted start, so an anchored range cannot
disagree with the full chain (I1), and the weekly full-chain run stays the backstop. Failing closed
without an anchor follows §11's existing pattern for `held_mismatch` and DEC-782 item 4: a check
that cannot read what it needs does not pass, and does not invent a rule break either. Reusing the
check's own code keeps rule 111's closed list and the `VerificationRun` schema unchanged; the cause
keeps the report honest. Every unanchored connection record fails closed, rather than only those
whose verdict the range "might" get wrong, because every one of them can be broken by a record
before the range; a finer split would pass records the full chain refuses.

## Alternatives considered

- **Keep the empty fold.** Rejected: false SEV-1s on valid ranges (above) and missed breaks whose
  evidence predates the range.
- **Skip rules 66 to 68 in a range (option (a)).** Rejected: it loosens §11, which says the rules
  are checked on every range, and passes records the full chain refuses.
- **An anchor without rule 131's open requests, keeping existence full-chain only.** Rejected: the
  anchor is the fold state, and leaving part of it out would make an anchored range disagree with
  the full chain for no gain.
- **A new code, such as `connection_unanchored`, in rule 111's list.** Rejected for now: it
  changes `VerificationRun`'s closed schema and every reader of it, while `held_mismatch` already
  reports its unanchored case under its own code. The cause carries the distinction.
- **Deriving the anchor from the connection manager's or executor's state.** Rejected: that is a
  read model, and verification exists to catch the chain and the state disagreeing.
