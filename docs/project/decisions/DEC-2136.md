# DEC-2136: The catalogue reads, the registered instruments and signal models a version may name

| **Decided by** | `claude-code` (lane WB) |

## Context

`POST /mandate-versions` takes the mandate document itself (DEC-2101 item 3). The server admits a
pinned instrument only when the latest registered `instrument_snapshot` names its asset id with its
symbol (`versions.rs`, `instruments`), and V-007 admits a signal model only when a `model_version`
registration names its id, version, content hash and parameters. Both lists live on the control
stream as `ConfigSnapshotRegistered` rows, and no route serves them. So the web app cannot build a
document the create accepts: it can only invent an asset id or a model hash, which the server
refuses and which would put made-up values in front of the owner. The set-up over the API therefore
creates nothing today (lane WB's row 1).

## Decision

1. **Two reads**, under §4.1, each taking the "Draft a mandate version" row, users only, writing
   nothing, and reading the control stream only:
   - `GET /instruments`, `read-models/instruments`: for each instrument id an `instrument_snapshot`
     registration names, the latest one's stored snapshot's `instrument_id`, `symbol` and
     `asset_class`, its `content_hash` as `snapshot`, and its row's `recorded_at`, sorted by symbol
     then id;
   - `GET /signal-models`, `read-models/signal-models`: for each `(model_id, model_version)` a
     `model_version` registration names, the latest one's payload members, its row's `recorded_at`,
     and `content`, the object stored under its `content_hash`, sorted by id then version.
2. **The same records the checks read.** `GET /instruments` lists exactly the `(asset id, symbol)`
   pairs the create's instrument check admits, and `GET /signal-models` exactly what V-007 reads, so
   a document built from them passes those two checks by construction, and one that names anything
   else is refused as today.
3. **Fail closed.** A registration whose stored object the store cannot give makes the read
   `journal_unavailable`, never a shorter list, so a client never offers a partial catalogue as the
   whole one.
4. **No performance, no ranking.** The model read serves the registration and the platform-authored
   content object only: no scorecard, backtest figure, hit rate or order of preference (DEC-99,
   DEC-126). The client lists what is registered; the owner chooses (rule 11), and nothing here is a
   recommendation.
5. **Order.** This spec slice lands first, then the server's routes, then the web app's use of
   them, each in its own change.

## Rationale

- The records are already the authority for the checks; serving them lets a client stop guessing,
  and adds no path that changes the envelope or the journal.
- Serving the stored content object rather than a second description keeps one source for a model's
  parameters and bounds: the one its content hash names.

## Alternatives considered

- **A fixed catalogue in the web app.** Rejected: its ids and hashes drift from what a deployment
  registers, and the server then refuses every version.
- **Accepting a symbol and resolving the asset id on the server.** Rejected: the document is hashed
  as sent (mandate spec §9.1), so the server would have to rewrite what the owner confirmed.
