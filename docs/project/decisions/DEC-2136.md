## Context

`POST /mandate-versions` takes the mandate document itself (DEC-2101 item 3). The server admits a
pinned instrument only when the latest registered `instrument_snapshot` names its asset id with its
symbol (`versions.rs`, `instruments`), and V-007 admits a signal model only when a `model_version`
registration names its id, version, content hash and parameters. Both lists live on the control
stream as `ConfigSnapshotRegistered` rows, and no route serves them. So the web app cannot build a
document the create accepts: it can only invent an asset id or a model hash, which the server
refuses and which would put made-up values in front of the owner. The set-up over the API therefore
creates nothing today (lane WB's row 1).

## Decision

1. **Two reads**, under §4.1, authorized like the other reads by the "Draft a mandate version" row,
   users only, writing nothing, served in a `live` workspace too (a read adds no risk), and empty
   lists for an empty control stream:
   - `GET /instruments`, `read-models/instruments`: the fold the create's instrument check reads,
     every `instrument_snapshot` registration in stream order, the latest per stored
     `instrument_id`, with the snapshot's `instrument_id`, `symbol` and `asset_class`, the
     registration's `content_hash` as `snapshot`, and its row's `recorded_at`, sorted by symbol
     then id;
   - `GET /signal-models`, `read-models/signal-models`: the registry V-007 reads, the latest
     `model_version` registration per `model_id` (whatever its version) less every id a later
     `model_withdrawn` withdrew, with that registration's payload members, its row's `recorded_at`,
     and a projection of its content (item 4), sorted by id.
2. **The pinnable, as the checks admit them.** Every listed instrument pair is one the create's
   check admits, and every pair a valid document can pin and the check admits is listed: a snapshot
   whose id is not an asset id, whose symbol is not 1 to 32 characters, or whose class is not
   `us_equity` or `crypto` is omitted, since the mandate schema's `instrument_ref` refuses it. Every
   listed model is one V-007 admits at its listed version, and no admitted one is missing. A
   superseded version or a withdrawn model is not listed.
3. **Fail closed where the check does.** Any instrument registration whose stored snapshot the store
   cannot give, superseded or not, makes `GET /instruments` `journal_unavailable`, as it makes the
   check refuse, so a client never offers a partial list as the whole one. V-007 reads only the
   registration row, so the model listing never depends on the store; only its `content` does,
   and that is `null` when the store cannot give or parse the object.
4. **A fixed projection, no performance, no ranking.** A model's `content` keeps only
   `authorship`, `methodology`, `params_schema`, `inputs` and `output` of the stored object, each
   when present: no prompt template, model identity, retrieval plan, tool declaration or source
   path reaches a client. Nothing about how a model performed is served (no scorecard, backtest
   figure, hit rate or order of preference; DEC-99, DEC-126). The client lists what is registered;
   the owner chooses (rule 11), and nothing here is a recommendation.

## Rationale

- The records are already the authority for the checks; serving them lets a client stop guessing,
  and adds no path that changes the envelope or the journal.
- Projecting the stored content object rather than writing a second description keeps one source
  for a model's parameters and bounds, the one its content hash names, while the allowlist keeps
  internal prompt content and source paths off every drafting role's screen; it is the tighter
  reading DEC-176 lets an agent take.
- The order of the changes (this spec slice, then the server's routes, then the web app's use of
  them) follows the spec guard.

## Alternatives considered

- **A fixed catalogue in the web app.** Rejected: its ids and hashes drift from what a deployment
  registers, and the server then refuses every version.
- **Accepting a symbol and resolving the asset id on the server.** Rejected: the document is hashed
  as sent (mandate spec §9.1), so the server would have to rewrite what the owner confirmed.
