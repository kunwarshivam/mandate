# DEC-2521: The respond route refuses a grant whose request and decision disagree on deferred checks

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | `claude-code` (lane GL), under DEC-176: it only refuses grants, adds no risk, and weakens no safety rule; the coordinator assigned the task |
| **Story or claim** | [DEC-2519](DEC-2519.md)'s alternatives (the respond-route follow-up); [workspace API spec](../../specs/workspace-api.md) §3.5 and §5.2 |

## Context

DEC-2519 made the approval read serve the causing decision's deferred checks, and the web app offers
only Skip when a request's checks are not exactly its decision's. Only the web app enforced that:
another client of `POST /approvals/{id}/responses` could still grant such a request. A grant of a
request that hides a deferral approves an order without the approver being told which checks have not
run (mandate spec §6.4). The binding gate still runs them when the order is placed, but the approval
itself would be uninformed.

## Decision

1. **A new problem code, `deferral_mismatch`:** `409`, `effect: none`, `retryable: false`, title
   "Request does not match its decision". It is in §3.5's table, `ProblemCode`, and
   `envelope.schema.json`.
2. **The respond route refuses a grant with it** when the request's deferred checks are not exactly
   those of the `DecisionMade` its `causation_id` names on the agent stream. The request's checks are
   version 3's non-empty list, or none for versions 1 and 2. The grant is also refused when that
   decision is not on the stream, when a version 3 decision lacks its list, and when the request's
   list is not a valid one for its version: empty, or not distinct check names, the shape the web
   app also refuses. The rule is the one the read applies (DEC-2518, DEC-2519).
3. **Order:** after the role (`forbidden` first) and before the paper check, the step-up evidence, and
   the port. A refused grant commits nothing and leaves the challenge unspent.
4. **A Skip is never refused for it** (API-7: reducing risk never needs approval).
   A repeat, under its key, of a grant committed before this rule is refused too, since the check
   precedes the replay. That only refuses, and the first grant stays recorded.
5. **Rendering:** the web app has already offered no Approve for such a request since DEC-2519. Lane D1's
   rendering of refusals in words covers this code.

## Rationale

The server must enforce what the screen shows. An approval that names the wrong checks cannot be
granted truthfully, and refusing the grant adds no risk: the request can still be skipped, and it
otherwise times out to its safe default. The runtime writes a request and its decision in one batch
with equal lists (rule 292), so no real approval is refused.

## Alternatives considered

- **`invalid` (422).** Refused: the body is well formed, and the problem is the journaled request.
  A named code lets the client say why in words.
- **Refuse only when the decision is found and differs, and let a missing decision through.** Refused:
  ambiguity resolves to the safe default (non-negotiable 3).
- **The §11 `verify` record instead.** It stays its own debt (`E21-30-approval-deferral-range-check`):
  a record, not a refusal.
