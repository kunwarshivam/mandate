# DEC-484: Bind policy and model-registry snapshots in decision journal envelopes

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-06 (UTC) |
| **Decided by** | Cursor coordinator under DEC-79 and DEC-176 |
| **Story or claim** | E7-19; claim #171 |

## Decision

1. Journal spec §9 gains two configuration-reference kinds: `policy_set`, the canonical snapshot
   of every ancestor policy level folded for the deployment, and `model_registry`, the canonical
   snapshot of the registered models admitted for that deployment.
2. `DecisionMade` version 2 keeps version 1's payload and requires `mandate_version`,
   `policy_set`, and `model_registry`. `ModelOutputRecorded` version 2 likewise keeps version 1's
   payload and requires `mandate_version` and `model_registry`. Version 1 stays registered for
   historical records, so the writer cannot reinterpret an old shape as a conforming new append.
3. `ConfigSnapshotRegistered` version 2 keeps version 1's payload and adds `policy_set` and
   `model_registry` to `kind`. Their model-only members are null or empty, as for every non-model
   kind. Version 1's closed kind vocabulary remains unchanged.
4. A policy-set object is
   `{kind: "policy_set", policy_set_version: 1, levels: [policy…]}`. Each item is one complete
   `schemas/policy.schema.json` document; levels are in platform, organization, workspace order,
   with at most one of each. A model-registry object is
   `{kind: "model_registry", model_registry_version: 1, models: [{model_id, model_version,
   content_hash, params, admits_instruments}…]}`; models and each model's parameter names are
   strictly sorted and unique.
5. A version-2 model output's registry contains exactly one entry matching its model id, version,
   and content hash. The validated production input separately checks the mandate's parameter keys
   and admission capability against that same entry before a cycle starts.
6. The policy and registry objects are configuration artifacts, not payload artifacts. They are
   named in `config_refs`; `artifact_refs` remains exactly the sorted set of digest references in
   the payload.

## Rationale

DEC-475 requires every effective production-cycle input to be content addressed in the journal.
The mandate hash cannot stand for policy: `PolicyChanged` can tighten the effective overlay without
creating a mandate version. The model content hash cannot stand for the registry either: the
registry controls whether that model identity, version, parameters, and content hash are admitted.
Without separate references, replay can choose different policy or registry facts while presenting
the same mandate and model content hashes.

This closes the gap by the safer reading under DEC-176. It adds typed evidence and append-time
requirements, weakens no invariant, and permits no new action.

## Alternatives considered

- Treat policy and registry as part of `mandate_version`: rejected because both change
  independently of the confirmed mandate document.
- Put their hashes in `artifact_refs`: rejected because §3 defines that field as the exact set of
  digest references in the payload, while these are configuration inputs.
- Add the keys but leave them optional: rejected because another writer could still produce an
  unauditable production decision.
- Bind only `DecisionMade`: rejected for the registry because `ModelOutputRecorded.ignored` is
  judged against the effective registry snapshot before a decision exists.
