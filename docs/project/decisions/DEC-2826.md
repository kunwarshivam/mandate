# DEC-2826: The executor restricts the account first when its connection is unusable, then records the state change

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79 and DEC-176. It writes records the specs already define, in the order journal spec §9.8 requires; it only adds a restriction, and lifts or loosens nothing) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane EX) |
| **Story or claim** | E7-2z (backlog `E7-2-connection-restriction.md`), slice C: the executor's writer and fold. Trading spec §7.3 row 5; connections spec CN-6, §8.2, §9.1; journal spec §9.8 (`ConnectionEstablished` rule 68, `ConnectionStateChanged` rules 59 to 61), §9.5 rule 309; DEC-687, DEC-2520, DEC-2816 |

## Context

Trading spec §7.3 row 5 restricts the account to closing while its connection is `degraded` or
`suspended`, under the cause `connection_unavailable`, and DEC-2520 names that cause's alert. No
code wrote that restriction or `ConnectionStateChanged`, and the executor's fold refused the
record as not interpreted. Journal spec §9.8 says the halt is never behind a connection record:
the restriction and the agents' modes are committed before the state change, in a later batch.
Slice D makes `mandate-executord` detect the troubles; this slice is the core that acts on them.

## Decision

1. **A level-triggered input.** `Input::Connection(ConnectionTrouble)` reports that the connection
   is unusable: `Degraded` with a degrading reason (`network_errors`, `rate_headroom`,
   `contract_drift`) or `Suspended` with a suspending one (`authorization_failed`,
   `credential_expired`, `refresh_failed`, `check_failed`, `lease_expired`), the reasons rule 59
   allows. The shell reports it at every step while the trouble holds; the core is idempotent, so
   a report that changes nothing journals nothing.
2. **The restriction first.** While `connection_unavailable` is not in force, the step journals only
   `AccountRestrictionChanged` (`closing_only`, cause `connection_unavailable`, reason code
   `account_restricted`), every agent's `AgentModeApplied` `exits_only`, and the owner's
   `connection_unavailable` alert, through the same `restrict` as the broker's causes (rule 309:
   once per cause, beside a stricter one only the cause is told). One step is one batch, so the
   state change can only come in a later step.
3. **Then the state change, once per stay.** Once the cause is in force, a later step journals
   `ConnectionStateChanged` from the state the stream holds to the reported one with its reason.
   A new reason while staying in the same state is journaled once too (connections spec §8.2,
   DEC-687); a reason already journaled in this stay is not again.
4. **Held while suspended.** A degrading report while the stream holds `suspended` journals nothing
   (rule 60: `degraded` is never entered from `suspended`; DEC-687 item 1).
5. **Nothing before the establishment.** Before the stream holds its copy of
   `ConnectionEstablished`, only the restriction is journaled: rule 68 refuses a state change
   before it, and the restriction must not wait for it.
6. **The fold reads the record.**
   - **The copy.** The copy of `ConnectionEstablished` records the connection id, `active`, with no
     causes. A reconnect's copy of the same id keeps the state the stream holds (CN-12). A copy
     naming another id is refused as non-canonical, since one account stream holds one connection
     (rule 68).
   - **The state change.** A `ConnectionStateChanged` folds only for that id and only from the state
     the stream holds; one before the copy, for another id, or from another state is refused as
     non-canonical. Rules 59 and 60 are `append`'s to judge and are not judged again in the fold.
   - **The causes.** The causes outstanding are those journaled since the connection entered its
     state or since the latest `condition_cleared` or `acknowledged`, which record none (DEC-687
     item 1). So a cause that recurs after the condition cleared is journaled again, and the
     acknowledgment E7-2y must refuse then has a record to read.
7. **The alert at once.** Connections spec §9.2 alerts the owner of a `degraded` connection after a
   configured period (Proposed: 5 minutes) for network errors and low headroom, and at once for
   contract drift. Here the `connection_unavailable` alert goes out with the restriction, at once,
   for every cause. This is the reading DEC-176 lets an agent take: it adds an alert and delays
   none, and trading spec §7.3 row 5 restricts at once with its distinct alert. A delay for the
   transient causes, once the period is decided, is the lift and alert work of E7-2y.
8. **Out of scope.**
   - **E7-2y:** lifting the restriction when the connection is `active` again, and the owner's
     acknowledgment.
   - **Slice D:** mapping connector errors to this input, with an ambiguous error read as
     `degraded`, never as healthy.
     - It also adds `Input::Connection` to the inputs whose core error `mandate-executord` holds
       rather than stops on (DEC-2821), so a refused restriction never stops the exits.
     - It updates journal spec §9.5's sentence that leaves this restriction and its alert to
       E7-2z. Until slice D, no production path sends the input, so that sentence still holds for
       every deployment. The lift's rules there (v0.102, DEC-2824) read this writer's records: a
       cause journaled after `condition_cleared` holds the lift, as DEC-687 item 2 wants.

## Consequences

- A connection the platform cannot use now halts openings on the account before anything records
  why, and the owner is told by its own kind.
- Replaying the stream rebuilds the connection's state, so a restart journals no state change twice.
- Until slice D, nothing in production sends the input; tests drive it.
