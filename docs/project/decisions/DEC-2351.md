# DEC-2351: The owner is told when a kill switch did not reach an account whose agents are all retired

| | |
|---|---|
| **Status** | Accepted (agent: an engineering reading under DEC-79 and DEC-176 that adds an owner alert DEC-2344 item 1 already requires, approved by the coordinator on 2026-10-22; it adds a notice, changes no trading rule, and its text is the generic `attention_needed`) |
| **Date** | 2026-10-22 (UTC) |
| **Decided by** | `claude-code` (lane D1, the staging push), under DEC-176 |
| **Story or claim** | E8-17, E21-33; notifications spec §3.2, §3.4 (v0.9); journal spec §9.15 (v0.78); DEC-2344 items 1 and 2; DEC-438; claim #1901 |

## Context

DEC-2344 item 1 has the deployment manager start an executor no agent wants for a kill switch that
covers it. If that executor crash-loops before it ends, the switch is not applied: the manager
journals `ProcessCrashLooped` and raises the operator alert `kill_switch_unapplied` (infrastructure
design §8.2, RB-14). DEC-2344 says the owner's alert is the notification service's, from that
`ProcessCrashLooped`, with generic text and opaque ids only, and that it and `retirement_held`
(item 2) join the notification spec's owner alerts with the implementation of items 1 and 2. The
manager's implementation (#2290) raises only the operator's alert; the notification spec has no
kind for either.

## Decision

1. **A kind `kill_switch_unapplied`** in notifications spec §3.2, class `safety`, text key
   `attention_needed`, recipients the account's owners and every workspace admin, as for an
   account-wide kill switch.
2. **Its subject is an unapplied crash loop**, derived from the control stream alone, so no record
   gains a member: a `ProcessCrashLooped` of an executor whose run (its starts from the latest one
   before the loop whose cause is not `restart`) began with a `kill_switch` start journaled while no
   agent of its account was deployed and not stopped, with no `AgentDeployed` on a connection of the
   account between that start and the loop. A crash's restart has cause `restart`, so the run's
   first start, not its latest, decides; a deployment during the run makes it an ordinary one, so
   its loop is `crash_loop` alone, after a manager restart too. The deployment manager, which
   writes the loop, writes the `OwnerAlertSent` (`kill_switch_unapplied`) in its batch (journal spec
   rule 130), and none for any other loop. This is the manager's own `held` state: set by such a
   start, cleared by a deployment on the account, and by a start for any cause but `restart` or a
   `kill_switch` no agent wants.
3. **One notice per loop, and a new run per later switch.** The cause is that one
   `ProcessCrashLooped`, so a manager that restarts and raises its operator alert again sends the
   owner nothing more (notifications spec §3.4). A covering switch after an unapplied loop starts a
   new run, which is restarted after a crash like the first; if it loops too, that is a new
   `ProcessCrashLooped`, operator alert, and notice, so no unapplied switch goes unreported
   (`AGENTS.md` rule 13).
4. **Journal spec v0.78** adds the kind to §9.15's closed set (33 kinds to 34) and stream rule 266,
   which accepts `kill_switch_unapplied` only on an unapplied crash loop. Its vectors are the
   `kill_switch_unapplied` section's control streams, judged by the fold and an independent oracle,
   with each seeded bug caught; the kind's parser vectors are the code's (`mandate-notify`,
   `mandate-journal`).
5. **Who can cover such an executor.** A connection's switch, the workspace's, and an agent's of
   an agent once deployed on the account (journal spec §9.21). An operator's switch is the
   platform's own action and starts nothing here. Whichever it was, no agent runs on the account, so
   the recipients are the account's owners and every workspace admin.
6. **`retirement_held` is not in this decision.** It has no journaled subject: nothing records that
   a retirement has waited 24 hours. It needs an agent-stream record from the runtime, with its
   `OwnerAlertSent` in the batch, stream rules, and reference vectors, in a spec change of its own.
7. **Before staging.** The kind's code (the kind enum, its class and text key, the manager's
   `OwnerAlertSent`) and `retirement_held`'s record and kind are an E8-17 backlog row marked needed
   before staging; until it lands, only the operator is told (RB-14).

## Rationale

An unapplied kill switch on an account nothing else runs on is the case an owner most needs to
hear about, and the only actor who can then act is the owner, in the broker's own console: the
operator never trades on an owner's account. Hanging the notice on the manager's own record keeps
the rule that a notice answers one committed cause, written by its stream's owner.

## Alternatives considered

- **The dispatcher raises it from the operator alert.** Rejected: operator alerts are not
  journaled, so the notice would answer no committed cause (NT-5) and could repeat at every manager
  restart.
- **Reuse `kill_switch`.** Rejected: that kind says a switch was activated; this one says it was
  not applied, and an owner must not read the two as the same news.

## Risks

- Until E8-17 lands, the owner is not told; RB-14 has the operator escalate.
- An executor that ends `Succeeded` without applying a switch it could not reach (a revoked
  connection whose token is destroyed) raises nothing. DEC-2343's executor exits only once its
  switches are applied, so it crash-loops instead, and this alert fires.
