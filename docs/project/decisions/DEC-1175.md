# DEC-1175: The deployment manager starts an OAuth connect's token exchange as one Pod, once

| | |
|---|---|
| **Status** | Accepted (agent: reversible engineering decisions under DEC-79 and DEC-176; each admits a record that was impossible or narrows what the manager may start, and none touches an order, a limit, or an exit) |
| **Date** | 2026-10-19 (UTC) |
| **Decided by** | `claude-code` (lane D1, the staging push), under DEC-79 and DEC-176 |
| **Story or claim** | DEC-2627 items 1 and 5 (lane D1's two record-driven starts); E21-33; journal spec §9.21; connections spec §5.2 steps 4 to 6; infrastructure design §3.4, §3.5 |

## Context

DEC-2627 gives lane D1 two starts: on a control-stream `ConnectionRequested` at version 2 with
`credential` `oauth`, one token-exchange process for the connection, stopped at the request's
`recorded_at` plus 600 seconds; and on its success, the pending connection's executor. Journal spec
§9.21 closes the manager's records to two processes, `runtime` and `executor`, and the manager
journals every start before it acts (§5.2). The exchange's start therefore needs a record §9.21
admits, and a reading of DEC-2627's "Job" that fits how the manager runs processes.

## Decision

1. **§9.21 admits the exchange's start and stop** (journal spec v0.70). `ProcessStartIssued`'s and
   `ProcessStopIssued`'s `process` add `token_exchange`, whose `subject` is the `connection_id`; the
   start's `cause` adds `requested` and the stop's `request_closed`. Rule 167 reads `deployed` or
   `requested` exactly at generation 1, and rule 256 ties `requested` and `request_closed` to
   `token_exchange` both ways. `ProcessCrashLooped` keeps `runtime` and `executor` only.
2. **One attempt.** The manager starts an exchange once, at generation 1, and never again: not
   after it exits, whether it failed or succeeded, not for a kill switch, and not after a
   crash. The code it would exchange is read once (DEC-821 item 2, DEC-2627 item 4, DEC-2628), so
   a second attempt could only fail, and since the exchange logs in with its own pod token
   (DEC-2060) the manager's refusal to start it twice is the second fence.
3. **Stopped when its request closes.** A running exchange is deleted, journaled first as a
   `ProcessStopIssued` with cause `request_closed`, as soon as its request closes:
   `ConnectionEstablished`, `ConnectionRefused` with occasion `connect`, or `ConnectionRevoked`.
   Otherwise it ends on its own by the deadline. No kill switch starts or stops it: it holds no
   order.
   "One start" and "stopped only when its request closes" are writer rules, the manager's, as a
   slot's order of generations is (§9.21): `append` sees one record at a time, so no record check
   refuses a `token_exchange` stop at a generation above 1, or a stop with no start before it.
4. **A Pod, not a Kubernetes Job, in the workspace's namespace.** The manager creates the exchange
   as it creates every process: one bare Pod with `restartPolicy: Never`, here with
   `activeDeadlineSeconds` set to the whole seconds from the start to the request's `recorded_at`
   plus 600 seconds. A Pod that never restarts is the one attempt a Job with `backoffLimit: 0`
   would be, and the manager's API rights stay the pods of its namespace (DEC-986): a Job
   controller would add a second actor that creates pods. It runs in the workspace's own
   namespace, so the token-exchange egress policy, the default-deny and the deploy-manager's
   admission policy all cover it, as the ServiceAccount DEC-2060 names (`x` and the connection id's
   lowercase hex), with only its projected vault token and no Secret. The manager starts nothing
   for a request at or past its deadline, or one whose connection is closed.
5. **What the start reads.** Only the control stream: the request's version, `credential`,
   `connection_id`, `account_ref` and `recorded_at`, and the closing records. A version-1 request
   or an `api_key` one starts nothing (DEC-2621 item 1).

## Rationale

Every start the manager makes is journaled before it acts and recovered from the journal after a
restart; the exchange's start keeps that, so a second manager or a restarted one never starts a
second exchange for one connection (§9.21's slot rule). Admitting a record is the reading that adds
no risk (DEC-176): no record written today is refused. A Pod keeps the manager's one API and its
narrow rights, and its deadline ends the exchange when the state it would redeem expires.

## Alternatives considered

- **A Kubernetes Job with `backoffLimit: 0`.** Rejected: the same one attempt, with a second
  controller creating pods and the manager's role widened to `batch/jobs`.
- **Start the exchange without a record.** Rejected: §9.21 journals every start before it acts, so
  a restarted manager could start the exchange twice.
- **Retry a failed exchange.** Rejected: the code is spent on the first attempt (DEC-821 item 2).
