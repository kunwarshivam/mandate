| **Story or claim** | E17-2, its journal half (and E17-9's `ThesisRevised`); stream J, claim [#132](https://github.com/kunwarshivam/mandate/issues/132); spec PR on `agent/j3-thesis-schemas-spec` |

## Decision

1. **Scope.** Journal spec v0.9 adds §9.4, which closes the two agent-stream records §9.1 left "with their own stories": `ThesisProposed` and `ThesisRevised`. The tracker's E17-2 row names it as the crate's outstanding journal half.
    - §9.2's conventions carry over, and the rules continue at 34.
    - The two events share one schema, because mandate spec §8.4 gives one thesis table for both. The one difference, the revision, is a rule (rule 34), not a second schema.
    - Until the schemas are registered in `mandate-journal` (a tests PR and an implementation PR, DEC-77), both stay refused at `append` as `unknown_schema`, as they are today. No fold reads them, so nothing fails open.
2. **The members and where each comes from.**
    - **The thesis.** `thesis_id`, `lineage_id`, `revision`, `predecessor_thesis_id`, `instrument_id`, `asset_class`, `direction`, `horizon_s`, `conviction`, `confidence`, `evidence_sources`, `corroboration`, `invalidation`, `allowlist_version`, `admitted`, and `reason` are `mandate-research`'s `ThesisEntry`, member for member. `evidence` becomes `evidence_ref`, a `ref?`, because the entry holds an optional digest of an artifact.
    - **The model's identity.** `model_id`, `model_version`, and `content_hash` are §9's "research agent id, version, and content hash". They are typed as `ModelOutputRecorded`'s, so `content_hash` is a stored `ref`.
    - **The instants.** `as_of` and `expires_at` are §8.2's output fields. Check 2 reads them, so a record that omits them could not show why check 2 failed.
    - **The artifacts.** `prompt_ref` and `response_ref` are §8.4's "the prompt and response as artifacts". Both are required, because every thesis comes from one model invocation.
    - **The autopsy.** `autopsy_ref` is §9's "what the revision changed" and §8.6's "names what the autopsy found and what changed" (DEC-111). It is an artifact, because it is model text.
    - **The types.**
      - `instrument_id` is an `id`, because an asset ID is a lowercase UUID (mandate spec §3). This is DEC-403's reading for `UniverseChanged`.
      - `asset_class` is the mandate schema's two values, from reference data (DEC-132 item 6).
      - `direction` is `text` as given, as on `ModelOutputRecorded`, so a direction v1 does not allow can be recorded and ignored.
      - `evidence_sources` is `[text]`, not `[id]`, in the order given with duplicates kept. Check 14 refuses a thesis that cites a source off the allowlist, and that refusal is journaled, so the record has to hold whatever was cited, as cited. `SourceId` itself only refuses the empty string, and the writer copies the model's list verbatim.
      - `invalidation` is the model's own text (mandate spec §8.4). It is model prose in the payload, which DEC-126 and counsel question 35 hold off the approval screen, so the display story asks the founder before showing it verbatim.
      - `corroboration` is the platform's kind, never the model's (DEC-132 item 7).
      - `reason` is §8.5's seventeen codes, which are the crate's `RefusalReason::code`.
3. **The rules, each a reading that only refuses (DEC-176).**
    - **Rule 34.** `ThesisProposed` exactly at revision 0, and no autopsy on it. This is §8.4 ("a revision is `ThesisRevised`") and the crate's "the entry type follows the revision number, not the verdict".
    - **Rule 35.** `reason` is null exactly on admission. This is §8.5's "the first failure decides and is the journaled reason".
    - **Rule 36.** Checks 1 to 3, recomputed from the record's own members, exactly as `mandate-research`'s `failed` computes them, with check 2 compared to the nanosecond. When one fails, the reason is the first that fails. When none fails, the reason is none of the three.
    - **Rule 37.** Check 15, from the record's platform-derived `corroboration`. A null corroboration fails check 15, so the first failure is at check 15 or earlier. A non-null one passes it.
    - **Rule 38.** `config_refs.model_version` names the record's own `content_hash`, as rule 22 binds `AgentDeployed`'s mandate version. A thesis has exactly one model, so the reference cannot mean another.
    - **No order rule on `evidence_sources` (#490 round 1, M1).** The first draft had a rule 38 requiring the list strictly ascending by bytes, on the claim that the writer sorts it. The writer does not: `thesis_event` copies the model's list. And approved mandate case MC-N07 journals a `ThesisProposed` refused at `source_not_allowlisted` that cites `src.filings` before `src.anonymous_blog`, so that rule refused a record §8.5 says is journaled. Refusing it at `append` would lose the audit entry for exactly the refusal check 14 exists to make (`AGENTS.md` rule 5). So the rule is gone, the old rule 39 is now 38, and the list is recorded in the order given, duplicates kept, as §9.1 records `ModelOutputRecorded.evidence`. Two alternatives were not taken:
      - **Canonicalise in the writer (sort and dedupe).** Rejected: it discards the model's order and a repeated citation for no safety gain, and the record would stop being "what was cited".
      - **Keep the rule and change MC-N07.** Rejected: MC-N07 is an approved mandate case and is right as it stands.
    - **Why no rule refuses a record §8.5 says is journaled.** Every record a correct writer makes for an admitted, refused, or ignored thesis passes. The vectors list every thesis record the approved mandate reference cases journal (36 records in 24 of the MC-N cases), rebuild each as a §9.4 record, and require every one to pass: that is the `drafts.reference_cases` oracle, the cross-spec trace M1 found missing. The valid drafts hold the cases a rule could be misread to refuse:
      - a first thesis with a predecessor, recorded as ignored;
      - a revision without one, still a `ThesisRevised`;
      - a revision without an autopsy;
      - a thesis that fails checks 1 and 2, refused for check 1;
      - an uncorroborated thesis that an earlier check refused;
      - a thesis that cites no source and is corroborated by market data;
      - MC-N07's pair of sources, out of order and one off the allowlist;
      - a source cited twice;
      - a zero horizon whose instants agree.
4. **The vectors.**
    - **A new `research` section.** Drafts in `agent_stream` would fail `main`'s live Rust tests on unregistered types, the same reason DEC-403 item 7 gave for `risk_state`. Nothing in Rust reads `research` until the tests PR.
    - **The validator.** The schema and rules live in `control.py` beside §9.2's and §9.3's, so one validator judges every closed schema. `reference/journal/research.py` builds and checks the section.
    - **The stored mandate.** The research agent's mandate is the mandate reference cases' `research_equity`, with its one admitting model's `content_hash` set to the stored model content's. That base pins a placeholder hash no object re-hashes to, and `content_hash` is a `ref`, so §11 check 6 needs the object stored.
    - **The oracles.**
      - `documents.valid` checks that the stored mandate differs from the proven base at that one hash only.
      - `drafts.pinned_model` checks that every base and valid draft names the stored mandate's admitting model by id, version, and hash.
      - `drafts.mandate_checks` recomputes, from the stored document alone, the §8.5 checks the mandate decides (4, 5, 6, 10, and 16's revision cap). The policy overlay only tightens, so no reason may pass over a check the document fails first. Checks 5, 6, and 10 read the mandate alone, so a refusal at any of them must also fail by the document. Check 6 is among them only while `PolicyOverlay::effective_admission` raises `auto` to `ask` and never to `deny` (#490 round 1, minor 4); an overlay that could deny moves it out. Checks 4 and 16 stay out: the overlay can fail 4, and 16 also reads the folded `retired` flag.
      - `cases.listed` checks that the section lists every thesis record the mandate reference cases journal, and `drafts.reference_cases` checks that each, rebuilt as a §9.4 record, passes every rule.
      - Each oracle has its own vector mutant, and `drafts.mandate_checks` has one for each clause and one for check 6.
    - **The report order (#490 round 1, M3).** Rule 34, its autopsy clause, rules 35 to 37, and rule 38 report at four different paths, so their order is the reason code a caller sees. An invalid draft breaks each pair of the four, and one breaks all four, each expecting every violation in number order, and an `order.*` seeded bug swaps each pair. Rules 35 to 37 all report at `payload.reason`, so no fixture can tell their order apart, and §9.4 claims none.
    - **Every member type pinned.** Each of the 25 members has an invalid draft and a `loose.payload.*` validator mutant that the draft catches. Every rule and clause has its own mutant too: 45 validator mutants (six of them order swaps) and 13 vector mutants, all caught.
    - **The header's founder line.** journal.yaml's header says changing these vectors needs founder approval. This change alters no existing vector. It adds a section, as DEC-403's `risk_state` did, and every rule in it only refuses (DEC-176).
5. **Readings not taken, each with its reason.** Each would only refuse more, so each can be added later as a tightening.
    - **A required autopsy on a revision.** §8.6 says a revision names what the autopsy found, but no §8.5 check refuses one that does not. Requiring it here would leave such an output with no record, against §8.2's "ignored outputs are journaled". E17-9's loop story should decide whether a missing autopsy is a refusal reason. That would be a mandate spec change.
    - **`lineage_id` equals `thesis_id` at revision 0.** §8.4 states it, and `LineageId`'s doc repeats it, but no admission check refuses a thesis that breaks it. Rule 36's reason stands for the same.
    - **The predecessor's lineage.** No rule requires a predecessor to be in the record's lineage, or to differ from the thesis. Both need the predecessor's own record.
    - **§8.2's ranges.** `conviction` in [−1, 1] and `confidence` in [0, 1] are recorded as given, as on `ModelOutputRecorded`, because no §8.5 check refuses an out-of-range value. Whether one should be is a mandate spec question.
    - **Binding to the model events.** Nothing binds a thesis to its `ModelOutputRecorded` or `ModelInvocationRecorded`. `ModelInvocationRecorded` is not closed yet, and both are other events.
    - **The checks that read the mandate: not a §9.4 rule, but blocking the registration (#490 round 1, M2).** `append` does not resolve `config_refs.mandate_version`, so checks 4, 5, 6, 10, and 16's cap are not schema rules. But they are decidable from the stored mandate, and check 5 is MI-20 and check 6 is `autonomy.admission: deny`, both envelope fields the owner confirmed. So, as #470 round 2 minor 5 ruled for §9.3's classification, the `mandate-journal` registration must re-derive them, and that requirement blocks its acceptance:
      - it re-derives §8.5 checks 4, 5, 6, 10, and 16's cap from the mandate document the record's `config_refs.mandate_version` names, and refuses a record whose verdict passes over a check that mandate fails: an `admitted: true`, or a `reason` later than the first check the document fails;
      - the `man` ref on these two records means the mandate in force when the thesis was judged, and the tests PR pins that;
      - the tests PR comes first (DEC-77), and its cases include a pinned universe (MI-20) and `admission: deny`.
      The vectors' `drafts.mandate_checks` oracle already checks the same on every fixture.
    - **Check 14.** It needs the allowlist's contents, which no record carries. `allowlist_version` names it.
    - **Upper bounds.** `revision`, `horizon_s`, and `allowlist_version` are `u32` in the crate. The type refuses a negative, and a larger value fails closed at the mapping, as the 64-byte id cap does (DEC-403 item 5). The free-text members are unbounded: `model_id`, `model_version`, `direction`, `invalidation`, and each `evidence_sources` entry are §9.1's `text`, which has no maximum length, and the journal spec sets no maximum event size. This is inherited from `ModelOutputRecorded`, and whether journal `text` gets a maximum length is a later spec question (backlog).
6. **What follows.**
    - The registration in `mandate-journal` follows DEC-77: a tests PR with stubs and pending tests, then the implementation, carrying item 5's blocking re-derivation.
    - `ThesisEntry` holds the crate's members. The members the writer adds (the model's identity, the instants, the artifact references) are the writer's story, and so is the lineage fold's reading of these records.

## Rationale

`mandate-research` already returns these records, and mandate spec §8.5 has the executor name them as the `causation_id` of every admission's `UniverseChanged`. But their payloads were open, so nothing checked that a record's verdict was consistent with the thesis it recorded. Closing them from the crate's `ThesisEntry`, with rules that recompute what the record alone decides, keeps the journal the single record of what the research agent proposed. It also keeps a thesis from being journaled as admitted when its own record shows a failed check.

## Alternatives considered

- **Two schemas, one per event.** Rejected: the members are identical. Rule 34 states the one difference.
- **Drafts in `agent_stream`.** Rejected: that would fail `main`'s live Rust tests on unregistered types (item 4).
- **`instrument_id` as `text`, as on `ModelOutputRecorded`.** Rejected: the platform resolves the instrument before it writes the entry, so the asset ID's grammar fits `id`, which refuses more.
- **The research model's content hash as a bare digest, not a `ref`.** Rejected: §9.1 types the same member as a stored `ref` on `ModelOutputRecorded`, and §11 check 6 then verifies the content.
