## Context

The founder's paper trade from `web/` starts with connecting Alpaca paper, and the web app's
connections screen needs to read what is connected. Workspace API §4.5 lists `GET /connections` and
`GET /connections/{id}` with "opaque id, broker, environment, scopes, the 1× check, data profile,
restrictions, agents granted, loss carry", references only (API-11). No route serves them, and no
shape says which of those members the journal can answer today. The control stream holds every
connection record (journal spec §9.8): `ConnectionRequested`, `ConnectionEstablished` (versions 1
and 2), `ConnectionRefused`, `ConnectionCredentialRotated`, and `ConnectionRevoked` (versions 1 and
2). The 1× check, the data profile, the restrictions and the loss carry are not journaled there.

## Decision

1. **Two shapes.** `GET /connections` returns `read-models/connections`, every connection the
   control stream names, in the order its first record names it. `GET /connections/{id}` returns
   `read-models/connection`, that one connection; an id the control stream does not name is
   `not_found`. Both carry `as_of` with the control stream's watermark, and read nothing else
   (API-14).
2. **Members.** Each connection has:
   - `connection_id`, and `broker` and `environment` from the latest `ConnectionRequested`,
     `ConnectionEstablished`, or `ConnectionRefused` naming it (a revocation carries neither);
   - `state`, one of `connecting`, `established`, `refused`, `revoked` (item 3);
   - `scopes`: the latest `ConnectionEstablished`'s granted scopes, `null` before one;
   - `since`: the `recorded_at` of the record that set `state`;
   - `refusal`: for `refused`, the `ConnectionRefused`'s `check` (nullable) and `reason`;
     otherwise `null`;
   - `revoked_reason`: for `revoked`, version 2's `reason` (`owner` or `compromised`), `null` for a
     version-1 revocation, which names none (not reported, never read as `owner`); otherwise `null`;
   - `agents`: the ids of the agents whose latest `AgentDeployed` is version 2, names this
     connection, and is not followed by an `AgentStopped`, in first-deployment order. A version-1
     deployment names no connection (DEC-1171 item 1) and is not counted.
   The 1× check, the data profile, the restrictions, and the loss carry are planned as optional
   members (§3.2) and are not served.
3. **The state fold.** Rows in commit order; a body that does not parse, or a record without a
   `connection_id`, is skipped, as the agents read skips one (DEC-979).
   - `ConnectionRequested` names a new connection `connecting`. For a connection already named it
     changes nothing: a request never moves an established, refused, or revoked connection back.
   - `ConnectionEstablished`, at either version, sets `established` and `scopes`.
   - `ConnectionRefused` with occasion `connect` sets `refused`. A `reconnect` or `reauthorize`
     refusal leaves the state as it was: it refused a change, not the connection.
   - `ConnectionCredentialRotated` leaves the state as it was.
   - `ConnectionRevoked` sets `revoked`.
   - A connection is named by its first `ConnectionRequested`, `ConnectionEstablished`, or
     connect `ConnectionRefused`. A revocation, a rotation, or a `reconnect` or `reauthorize`
     refusal of an id not yet named names nothing: rules 66 to 68 and 131 never let one come first,
     and a view formed from it would have no broker or environment to show.
4. **Never served (API-11, CN-1, CN-10).** No member is a credential, a token, the authorization
   code, the PKCE verifier, the `state`, a vault path, an account number, or the fingerprint. The
   `account_ref`, the connecting `user`, the `step_up` evidence, and `existing_connection_id` are
   journaled but not served either: the screen needs none of them, and `account_ref` names a stream
   the caller has no route to read. Both schemas refuse a secret-shaped member name with the
   pattern `commands/oauth-start-response` uses.
5. **Order of the work.** Tests first (DEC-77): this decision, the spec text, the two schemas with
   their examples, and the fold's tests pending on its stub land first; the fold, then the routes
   with their authorization and a canary-secret scan of the responses, follow.

## Rationale

The fold reads only what is journaled, so a connection the screen shows is one the journal records,
and a member the journal cannot answer is planned, not guessed. Keeping `state` to the four
lifecycle states of connections spec §9.1 that the control stream decides (`closing_only` and the
health states are the account stream's, E7-13) leaves nothing to infer. A request that never moves
a connection backwards, and refusals that only close a connect, follow rule 131.

## Alternatives considered

- **Serve `account_ref`.** It is opaque, not an account number, but no read route takes it and the
  screen needs it for nothing; it can be added as an optional member when one does.
- **Read the account stream for health and `closing_only`.** That is E7-13's, and the account
  stream is not the connection manager's to read here; it joins as an optional member.
- **Count version-1 deployments as agents granted.** A version-1 `AgentDeployed` names no
  connection; reading one from the mandate document is the resolver DEC-1171 item 4 dropped.
