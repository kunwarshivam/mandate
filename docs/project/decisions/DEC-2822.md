# DEC-2822: The approval screen reads a refused grant as refused, in words, and sends nothing more

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79 and DEC-176. It only tightens what the approver is shown and offered: a refused grant no longer reads as recorded, and nothing more is sent after it) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane D1) |
| **Story or claim** | The coordinator's follow-up to [DEC-2818](DEC-2818.md); [DEC-2129](DEC-2129.md) item 7; [workspace API spec](../../specs/workspace-api.md) §5.2 and §5.5; journal spec rule 47 |

## Context

A grant can be refused in two places. The API refuses one from a user the request's mandate does
not list, `forbidden` (403), recording nothing (DEC-2129 item 7). The runtime judges every grant
the API recorded again, and journals `ApprovalResponded` refused with the first check that failed
(journal spec rule 47): `not_an_approver` among them, for an approver removed or a connection
revoked since the API checked (DEC-2818). `GET /commands/{event_id}` serves that as `refused`, with
the step's reason (§5.5).

The web app's approval screen (D6) read the API's `forbidden` as the generic "nothing was
recorded" and offered Approve again. It never read the runtime's `refused` at all: the screen went
on saying "Recorded in the journal: you approved", which reads as a success.

## Decision

1. **A refused answer is its own phase.** The client's approval response gains `refused`, taken
   when the command status settles `refused`, with the reason of its `ApprovalResponded` step (or of
   the first step that has one), whether the answer's delivery was recorded or unknown. It is never
   `decided`, the recorded sentence is replaced, and it is announced as an alert.
2. **In words, per reason.** Each of `ApprovalResponded`'s eleven reasons has its own sentence,
   which starts "Refused:" and says nothing was approved (`web/src/lib/grant-refusals.ts`). A
   reason without a sentence, or none, reads "Refused by your deployment. Nothing was approved."
   The code is never the text (C-6).
3. **Nothing is sent again after it.** A refused answer settles the screen: Approve and Skip are no
   longer offered, so no gesture re-sends the grant. The runtime treats a refusal as not terminal
   (the request stays pending until its deadline), and a fresh grant needs a new page load and a
   new confirmation. That is the conservative side: the screen never offers to repeat an answer it
   was told was refused.
4. **The API's approver refusal is final too.** `forbidden` on a response, the API's refusal of a
   person the mandate does not list or whose role does not answer requests, says the person is not
   an approver and settles the screen the same way. The step-up refusals an
   approve can meet (`step_up_missing` and the others) still leave Approve offered, as before: a
   confirmation the owner has not run yet can still be run and sent.
5. **No toast announces a grant before the runtime acts on it.** The journal toast for an
   approval fires once it is `decided`, never on `recorded`: a recorded grant may still be refused,
   and a toast cannot be taken back. A Skip is still announced once recorded.
6. **The fixture screen reads the same phase the same way.** The fixtures' runtime never refuses,
   but the screen and its progress steps show a refused answer as refused, never as approved.

## Consequences

- Tests: `web/src/lib/grant-refusals.test.ts` reads the reasons from the journal spec's own
  `ApprovalResponded` row, so a reason added there without words fails it;
  `web/src/components/api-screens/grant-refused.test.tsx` drives the screen over the API runtime for
  the runtime's refusals, the API's `forbidden`, and an admitted grant; and
  `web/e2e-api/api-source.spec.ts` drives the same refusal through the built app.
- No API, schema, or journal change.

## Alternatives considered

- **Offer Approve again after a refusal whose cause may pass, such as a stale confirmation.** It
  would let the screen re-send an answer the runtime refused, which the coordinator ruled out, and
  the owner can still answer afresh from a new load.
- **Show the reason code.** Refused: C-6 shows the sentence and records the code.
