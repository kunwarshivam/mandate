## Decision

Journal spec v0.12 added the notice stream `ntf:{workspace_id}` (§2) and its records, moved
`OwnerAlertSent` to the subject stream's owner, and left the payload schemas to E8-9's tests PR
(notifications spec §5.5). This decision closes them at schema version 1, as journal spec §9.6
closes its records: every listed member is present, `null` only where the type is nullable, and
any extra member is refused. Journal spec §9.1's types and its report order apply. The journal spec
takes these tables as a new section at its next free version (the journal spec queue); until then
this file is their text, and `crates/mandate-journal/tests/notices.rs` pins it.

None of the four records holds free text: every string is an identifier, a closed vocabulary, or a
provider's opaque token, so nothing about an order, a position, or a mandate can reach the notice
stream (`AGENTS.md` rule 6, notifications spec NT-1 and NT-2).

### 1. Types

| Type | Values | Refused as |
|---|---|---|
| `notice_id` | Exactly 32 lowercase hexadecimal digits: notifications spec §4.2's random notice id. Never an event id, which is a `ulid` and carries its creation time | As `id` |
| `stream_id` | A stream id in journal spec §2's grammar | As `id` |
| `opaque` | 1 to 256 characters, each U+0021 to U+007E: a provider's message id, which has no space and so cannot carry a sentence | As `id` |

`kind` is notifications spec §3.2's closed set. Its class is §3.2's: `action` for
`approval_requested` and `approval_reminder`; `info` for `daily_brief`, `delegation_ended`,
`model_status`, `research_status`, `spend_cap`, and `approval_closed`; `safety` for the other
24 (`risk_limit`, `kill_switch`, `agent_held`, `account_restriction`, `protection`,
`exit_stalled`, `reconciliation`, `external_activity`, `account_state`, `data_feed_down`,
`integrity_incident`, `credential_added`, `new_device`, `recovery_used`, `role_granted`,
`member_deactivated`, `deprovisioned`, `break_glass`, `version_risk_increasing`,
`delegation_added`, `connection_added`, `went_live`, `client_connected`, `channel_lost`).

### 2. `OwnerAlertSent`

On the agent, account, and control streams only, written by that stream's owner in the subject's
own batch (notifications spec §3.2, §5.1); `wrong_stream` on the scheduler and notice streams. It
names no configuration and is not a risk input, so it carries no `risk_clock`.

| Member | Type | Meaning |
|---|---|---|
| `subject` | `ulid` | The subject event: rules N1 and N12 |
| `kind` | `kind`, except `approval_requested`, `approval_reminder`, and `channel_lost` | No alert causes those three (notifications spec §3.4) |
| `owner_command` | `ulid?` | For a user's kill switch, the `OwnerCommandIssued` it carries out, on which the dispatcher de-duplicates (§3.4): rule N2 |

### 3. Notice-stream `StreamOpened`

| Member | Type | Meaning |
|---|---|---|
| `stream_type` | `notice` | |
| `workspace_id` | `id` | The subject: rule N3 |

### 4. `NoticeIssued` (notice stream, before the first send)

| Member | Type | Meaning |
|---|---|---|
| `notice` | `notice_id` | The id the payload and the link carry |
| `kind` | `kind` | |
| `class` | `action` \| `safety` \| `info` | Rule N4 |
| `cause` | `ulid` | The event the notice answers: an `OwnerAlertSent`, an `ApprovalRequested`, or for `channel_lost` this stream's own `NoticeAttempted` (§3.4). A kill switch's owner command is reached through its alert's `owner_command`, never named as a cause. Rule N6 |
| `cause_stream` | `stream_id` | The stream `cause` is on: rule N7 |
| `recipients` | `[id]` | Opaque user ids (NT-2): rule N5 |

### 5. `NoticeAttempted` (notice stream, one attempt's outcome on one push channel)

| Member | Type | Meaning |
|---|---|---|
| `notice` | `notice_id` | |
| `recipient` | `id` | The opaque user id; never an address (NT-2) |
| `channel` | `email` \| `phone` \| `slack` \| `sms` \| `telegram` \| `web_push` | The mandate schema's push channels (§4.1). The pull channels are never attempted: `ApprovalDelivered` and the journal itself are their record |
| `attempt` | `integer` | 1 for the first attempt on the channel: rule N8 |
| `status` | `delivered` \| `failed` \| `suppressed_quiet_hours` \| `deferred_quiet_hours` \| `abandoned` | `delivered` means the provider accepted it, not that anyone read it |
| `reason` | `timeout` \| `rate_limited` \| `provider_error` \| `address_rejected` \| `auth_failed` \| `too_large` \| `recipient_not_permitted` \| `bounced` \| `complained` \| `unsubscribed` \| `not_pending` \| `retry_window_ended` (nullable) | §5.2's closed enum, `recipient_not_permitted` included; the receipts `bounced`, `complained`, and `unsubscribed` (§5.6, §5.7); and §5.3's two stops, as #763 states them: rule N9 |
| `provider_message_id` | `opaque?` | The provider's id for the accepted message, which a later receipt names: rule N10 |
| `coalesced_into` | `opaque?` | For a notice combined into one message (§5.4), that message's provider id: rule N11 |

A `NoticeAttempted` whose `reason` is `address_rejected`, `auth_failed`, `bounced`, `complained`, or
`unsubscribed` is the record
that marks the address on that channel `unreachable` (§5.6) and causes its `channel_lost` notice;
it needs no member of its own, since a separate flag could only disagree with the reason.
`recipient_not_permitted` marks nothing (§5.2).

### 6. Rules

Reason `schema` unless stated; the path is the member named.

- **N1.** `OwnerAlertSent`: `causation_id` equals `subject` (`causation_id`).
- **N2.** `OwnerAlertSent`: `owner_command` is `null` unless `kind` is `kill_switch`
  (`payload.owner_command`). It is allowed on every alert stream: the v0.12 row lets a stream
  owner's alert name the command ("if any"), and refusing it would refuse the batch that holds the
  `KillSwitchActivated` beside it (`AGENTS.md` rule 13).
- **N3.** Notice-stream `StreamOpened`: `stream_id` equals `ntf:{workspace_id}` (`stream_mismatch`
  at `stream_id`).
- **N4.** `NoticeIssued`: `class` is the class of `kind` above (`payload.class`).
- **N5.** `NoticeIssued`: `recipients` is strictly ascending by bytes, so none is listed twice
  (`payload.recipients`). It may be empty: a recipient with no push address keeps the pull channels.
- **N6.** `NoticeIssued`: `causation_id` equals `cause` (`causation_id`).
- **N7.** `NoticeIssued`: `cause_stream` is a stream of this stream's workspace: an agent stream for
  `approval_requested` and `approval_reminder`, this notice stream for `channel_lost`, and an
  agent, account, or control stream for every other kind (`stream_mismatch` at
  `payload.cause_stream`), so a notice never answers another workspace's event (NT-10).
- **N8.** `NoticeAttempted`: `attempt` is at least 1 (`payload.attempt`).
- **N9.** `NoticeAttempted`: `reason` is non-null exactly when `status` is `failed` or
  `abandoned`. An `abandoned` attempt's reason is a stop: `not_pending` (an `action` notice whose
  approval stopped being pending) or `retry_window_ended` (a `safety` notice's 24 hours or an
  `info` notice's 6 hours ran out; §5.3); a `failed` one's is any other (`payload.reason`).
- **N10.** `NoticeAttempted`: `provider_message_id` is non-null exactly when `status` is
  `delivered` or `reason` is a receipt, `bounced`, `complained`, or `unsubscribed`
  (`payload.provider_message_id`).
- **N11.** `NoticeAttempted`: `coalesced_into` is `null` when `status` is
  `suppressed_quiet_hours` or `deferred_quiet_hours`, since nothing was sent
  (`payload.coalesced_into`). A combined message that failed or was abandoned keeps the link, so
  NT-6's oracle attributes every joined notice's outcome to its cause, recipient, and channel.
- **N12.** **Batch rule.** An `OwnerAlertSent`'s `subject` is the `event_id` of an earlier draft in
  the same `append` batch that is not itself an `OwnerAlertSent`, and no other `OwnerAlertSent` in
  the batch names the same subject (`payload.subject`, at the first alert that breaks it): §3.2's
  "in the subject's own batch" and §3.4's "one subject, one kind", checked at append.

The first violation is reported in journal spec §9.1's order: unlisted members, the listed members
in the order given, then N1, N2, N4 to N6, and N8 to N11 (only on a well-typed payload), then
`artifact_refs` and `pii_refs`, then the subject rules N3 and N7. N12 spans a batch, so it is
checked once every draft in the batch passes these.

### 8. Tightenings of current text (DEC-176)

Each reading below refuses something today's text allows or leaves open. None adds risk: a refused
record is one no conforming writer emits, and no trading path waits on the notice stream (NT-9).
The journal spec PR that absorbs this decision carries them.

1. **Journal spec §9, control stream table, `OwnerAlertSent` (`journal.md` line 531 on `main`):**
   "on any stream type" becomes "on the agent, account, or control stream". No §3.2 kind has a
   scheduler subject, and notifications spec §5.1 names those three streams.
2. **Journal spec §9, notice stream table, `NoticeIssued` (`journal.md` line 549):** the cause
   "the `OwnerAlertSent`, `ApprovalRequested`, or owner command it answers" becomes "the
   `OwnerAlertSent`, `ApprovalRequested`, or (for `channel_lost`) `NoticeAttempted` it answers". An
   owner command is never a cause itself; its alert's `owner_command` names it.
3. **Notifications spec §3.4 (`notifications.md` line 202),** "The command's `OwnerCommandIssued`
   is the cause", is read as: the cause is the `OwnerAlertSent` (`kill_switch`) that workspace
   services write with that command in its batch on the control stream, whose `subject` and
   `owner_command` name the command. So one user kill switch is still one notice, keyed on that
   alert, and the dispatcher de-duplicates any other alert naming the same `owner_command`. The
   journal spec PR proposes the matching wording in §3.4.

## Rationale

Until these close, `mandate-journal` cannot hold the notice stream at all: `StreamId::parse` refuses
`ntf:`, and `OwnerAlertSent` is control-only with no schema. The dispatcher (E8-10) and the stream
owners' alerts (E8-9) both need a closed shape to write. Every reading makes the journal refuse
more: none lets a record carry trading content, cross a workspace, or name a cause it did not read.

## Alternatives considered

- **`OwnerAlertSent` on any stream type**, as v0.12's row said: no kind has a scheduler subject
  (item 8.1).
- **A `ulid` notice id**: refused by notifications spec §4.2, since a ULID carries its creation time.
- **`provider_message_id` as `text`**: `text` admits a sentence a provider could echo (§5.2).
