## Decision

[DEC-446](DEC-446.md) settles what §9.5 closes; the vectors pin it. Implementing it left readings
the spec text does not settle outright. Each is recorded here, and each is pinned by a vector or a
test that fails if the reading moves.

1. **Rule 43 is one-directional.** "Stop and take_profit are null on every action but `intended`,
   `placed`, `passive_start`, and `unprotected_start`" refuses prices off those four; on them it
   forces nothing, so an `intended` record may carry a stop and no take-profit (crypto's), and
   `take_profit` is null whenever `stop` is, at `payload.take_profit` (§9.5). A `watchdog` that
   still carried prices is refused at `payload.stop`, and its stray `intent_id` at
   `payload.intent_id` after it.
2. **Rule 39 reports once.** "The first offending member in the order `order_class`,
   `take_profit`, `stop`" is the first adjacent pair whose two members disagree, reported at its
   first member: null-with-value at `payload.order_class`, value-with-null after it at
   `payload.take_profit`. One refusal, never one per pair.
3. **The fold's companion map.** Rule 45 pairs two drafts of one batch; the fold replays them one
   at a time. So `ExecutorState` holds each folded `OrderRequestRecorded` against its own event
   id, and the `OrderSubmitted` that names it as `causation_id` consumes it: the rebuilt request
   takes the executor-only members from the companion and the request members from the
   submission, and the order's agent and intent come from the companion. A submission naming
   nothing pending replays through the legacy rebuild, which is what a version-1 record — and a
   payload an older writer produced — replays through (DEC-446 item 7). The pending map is fold
   state, so a restart replays the same pairing from the journal alone.
4. **`rung` non-null says a ladder rung, and the fold infers lone from the sequence's absence.**
   There is no `laddered` member to read (DEC-446 item 2). A submission whose companion carries a
   `rung` updates the non-passive `ExitSequence` its intent names; when no sequence names it, the
   rung founds a lone ladder — a lone ladder's first rung writes `rung` 0, so a zero rung never
   means "not a ladder". A sequence's own first submission writes no rung at all, which folds as
   rung 0 at its sequence. The reference oracle infers the same way, from the sequence an
   `unprotected_start` trio opened and an `unprotected_end` closed.
5. **The companion carries every member (§4.2), nulls where empty.** `rung` and `at_floor` are
   null together (rule 40); an OCO's `qty` is not a companion member — the fold rebuilds it from
   the submission's `qty`, the same read `request_of` always made.
6. **Every submission is a pair.** `journal_rung` journals the companion then the
   causation-naming submission for the protective legs and the passive OCO too, so those drafts
   append cleanly from here on; they were refused at `append` exactly as DEC-360 item 3 found,
   and option (c)'s relaxation covers them. The leg and OCO ids name the `ProtectionChanged` that
   records them, which now sits two drafts after the point the writer derives the id at — the
   look-aheads move from `id_after(1)` to `id_after(2)`.
7. **The `intended` record follows its `IntentReceived` in the batch**, so the fold holds the
   restored prices before the gate reads the body — the same order at replay. Its null members
   are written, not omitted (§4.2). `IntentHandoff` carries the proposed `tif` (DEC-389 item 3);
   where no proposal has been wired yet — the tracer's double — it stands in with `day`, a
   regular-session limit (`AGENTS.md` rule 12), until E7-7 carries the proposal's own.
8. **The fold's `StreamOpened` environment read is tolerant of §9's schema shape.** The registered
   `STREAM_OPENED_V1` carries the stream's subject, not an `environment` member; the fold required
   one, so no schema-conforming opening could replay at all — the same kind of drift DEC-360 item
   1 found, on the one record DEC-447 left at version 1. The read stays for a payload that names
   one (the golden journal's), and a payload without it opens the stream and leaves the
   environment to the envelope's own field. No conforming record is refused that was accepted
   before, and the mismatch refusal is unchanged (DEC-176). `FOLD_VERSION` stays 1: the golden
   journal folds byte for byte as it did.

## Rationale

**Why the pending map and not a wider `OrderSubmitted` read.** The fold is effect-free and
one event at a time; the companion is a different event. Holding it against its event id, and
consuming it on the causation name, is the smallest state that reproduces rule 45's pairing at
replay, and it refuses nothing a conforming stream wrote.

**Why the oracle infers lone from the sequence, not from the submission.** The vector format
cannot carry a `laddered` flag that the schema does not declare, and the oracle reads the same
records the fold does. An `unprotected_start` trio is exactly what starts the fold's sequence, so
it is what the oracle tracks; an `unprotected_end` is what ends it.

**Why the environment read moves at all.** The acceptance test replays the vectors' own chain from
`StreamOpened` at seq 1. A required member the registered schema does not declare is the drift
DEC-360 exists for; leaving it would pin a replay that refuses the very streams the spec closes.
The reading only refuses less, and the golden journal's shape is untouched.

## Alternatives considered

- **Report both of rule 39's pairs.** Rejected: the spec reports at the first offending member,
  and a second path would tell the writer nothing the first did not.
- **Carry `laddered` on the companion and let the oracle read it.** Rejected: it widens a closed
  schema toward the code, the exact move option (c) exists to avoid.
- **Skip the `StreamOpened` in the replay test.** Rejected: the acceptance replay must cover the
  stream the vectors pin, from seq 1.
