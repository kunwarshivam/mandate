## Context

The run's walk stage (§4.8.1 "Coverage", T1b) takes the range's rows as data, the way the plan stage
takes the control snapshot. §4.8.1 says what the run reads — "The run reads the events of
`from_seq` to `to_seq` in that snapshot and walks them in `seq` order" — and DEC-787 item 1 folds
the folds' prefix and the segments' rows past `to_seq` into the same snapshot, but neither says
what the walk does when the rows it is handed are not rows of the stream it was asked to verify.
Under a genesis start, a cleanly chained foreign row passes every per-event check: check 2 compares
a row's columns with its own body, and check 3 and check 5 compare it with its own neighbours, so
nothing in §11 distinguishes another workspace's chain from the range's own.

## Decision

1. **The walk judges only rows of the stream it was asked to verify.** Every row of the input must
   name, in its `stream_id`, the request's own stream — another workspace's, another of the same
   workspace's, or a row whose `stream_id` does not parse, alone or among the range's own rows —
   or the run is refused the one `NotFound` of AU-1 and DEC-760 item 4 (the refusal the request's
   own `stream_id` gets at step 4), before any position is judged and with nothing recorded. This
   is AU-1's own sentence — "a verification reads only streams whose `stream_id` names the path's
   workspace" and "no byte of the other workspace appears in any response" — read onto the rows
   the walk is handed: walked, such a row would put another workspace's event hash into
   `to_hash`, a byte of the other workspace in a served response.
2. **The walk's rows parameter holds the stream's whole slice of the one snapshot**, from `seq` 1
   to the head it holds (DEC-787 item 1: "The range's events, the workspace's control-stream
   records the run reads, the trusted-start record, and the hold anchor and connection anchor
   below are all read in one database snapshot"). The walk judges the positions `from_seq` to
   `to_seq` of them and only those; the folds of the per-range steps read the rows before
   `from_seq`, and the segment checks read the rows after `to_seq`, which §4.8.1 says are
   "compared but not counted in `checked`" — so a range ending before the head walks its own
   positions only and the tail rows neither fail it nor count.

Each item is pinned by E12-3's walk-stage tests, in
`crates/mandate-audit/tests/verification_walk.rs`: item 1 by
`rows_of_another_stream_refuse_the_run_alike`, item 2 by
`a_clean_range_walks_every_event_but_never_its_tail`. No spec text changes: AU-1 already names
verification, and §4.8.1 already states the one snapshot and the counted range.

## Rationale

An input the walk cannot tie to the stream it was asked to verify is a bug in whatever assembled
the snapshot, and refusing it is the cheapest outcome for the caller: nothing is recorded, so no
false SEV-1 follows, and the refusal is retryable once the snapshot is right. A refusal also keeps
AU-1's "no byte of the other workspace appears in any response" true of the run's own answer, not
only of the reads the adapter made. Taking the whole snapshot slice as one parameter keeps
`walk`'s signature the one the per-range steps (T2, T3) and the run vectors (V2) finish against,
without a later change to a merged API.

## Alternatives considered

- **Walk the rows as they come (no stream check).** Rejected: the record would vouch for events
  the verifier was never asked about, and a genesis-started range would carry another workspace's
  `to_hash` into a served response.
- **Skip the foreign rows and let `seq_gap` fail the range.** Rejected: on a healthy stream it
  records a found fault that is no fault, a SEV-1 for nothing, and it names the wrong code for
  what went wrong.
- **Pass only the range's rows, sliced by the caller.** Rejected: the same snapshot must also
  serve the folds' prefix (DEC-892) and the segment checks' rows past `to_seq` (DEC-787 item 4),
  so the caller would slice three times from one snapshot and the run could not check that the
  slices agree.
