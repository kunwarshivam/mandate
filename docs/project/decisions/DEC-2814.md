# DEC-2814: Every account-restriction cause in force is journaled

| | |
|---|---|
| **Status** | Accepted (the coordinator, under DEC-176: it only tightens. Every record it adds is one the executor's state already implied, no restriction is lifted, and a record that leaves the account state unchanged moves no agent) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | `claude-code` (coordinator), on lane L1's proposal |
| **Story or claim** | Backlog E7-2v; [journal spec](../../specs/journal.md) §9.5; [trading spec](../../specs/trading-domain.md) §7.3; [DEC-2137](DEC-2137.md) item 6; [DEC-441](DEC-441.md) item 23 |

## Context

Trading spec §7.3 lifts each cause of an account restriction on its own evidence, so a broker's
clearance never lifts a restriction the connection still imposes. The executor journaled an
`AccountRestrictionChanged` only when the account state it set was stricter than the one in force
(DEC-2137 item 6), so a second cause raised while the account was restricted never reached the
stream, and no lift could name it. Nothing lifts a restriction yet either: the executor's account
state never returns to active, and no journaled acknowledgment can name a restriction.

## Decision

1. **A cause is in force** from the `AccountRestrictionChanged` that raised it, at the restriction
   that record set, until a lift names it. No lift exists yet, so every cause raised stays in force.
2. **Every cause in force is journaled.** The executor journals a restriction whenever its cause is
   not already in force at that restriction or a stricter one (`blocked` over `closing_only`),
   whether or not the account state changes. The account state is the strictest restriction any
   cause in force set.
3. **Rule 309** (journal spec v0.95, a stream rule on the account stream) refuses an
   `AccountRestrictionChanged` whose cause an earlier one of its stream raised at the same
   restriction or a stricter one (`payload.cause`).
4. **A record that leaves the account state unchanged moves no agent**, since every agent already
   holds the mode it would apply. The owner is still alerted, by the record's event id.
5. **Slices.** This decision journals the causes. The lift, §7.3's "Lifts when", is backlog E7-2y
   (lane L1, rules 310 to 312 held for it). The connection's restriction and its distinct alert
   are E7-2z (lane EX). Until E7-2y lands no restriction is lifted, which is the reading that adds
   no risk.

## Rationale

- Items 2 and 3 put on the stream each cause the lift will need to name, once, so a replay finds the
  causes in force from the records alone.
- Item 4 keeps one mode change per change of the account state.
- No item lifts or loosens anything, so DEC-176 lets an agent take it.

## Alternatives considered

- **Journal only a stricter state, as before, and derive the causes from other records.**
  Rejected: a reject run and a connection failure leave no record that says the account is
  restricted by them, so a lift could not tell which cause it clears.
- **Key a cause in force by cause alone, refusing the same cause at a stricter restriction.**
  Rejected: §7.3 rows 4 and 1 are both `broker_notice`, and a margin-call notice followed by a
  blocked status must block the account.
