# DEC-2039: The handoff carries the owner's confirmed bid, and the executor journals it beside the intent, so a confirmed owner exit sells outside the regular session

| | |
|---|---|
| **Status** | Accepted (agent, under DEC-176) |
| **Date** | 2026-10-19 (UTC) |
| **Decided by** | `claude-code` (builder of lane X, story E7-30) |
| **Story or claim** | E7-30, claim [#1498](https://github.com/kunwarshivam/mandate/issues/1498) (lane X); [trading spec §5.5](../../specs/trading-domain.md#55-kill-switch) and §5.6; journal spec §9.1 (`OwnerExitRequested`, `IntentProposed`) and §9.5; [DEC-2037](DEC-2037.md) item 6; `AGENTS.md` rule 13 |

## Context

Rule 13 lets an owner exit sell equities outside the regular session once the owner confirms the
displayed bid. Trading spec §5.5 adds that the exit price ladder then never prices below the floor
the owner confirmed. The core already does this for an owner kill switch's flatten: the switch
journals the floor, bid, and bid size on `KillSwitchActivated`, and `kill::floor_of` reads them.

An owner's exit of one instrument reaches the core as a handoff. That handoff carries no
confirmation, so the core treats every handed owner exit as unconfirmed, and it waits for the
regular session ([DEC-2037](DEC-2037.md) item 6). DEC-2033 item 4 also prices an owner's exit at
the market as a limit at the floor, because the core took only limits then. So the
`IntentReceived` it writes differs from the `IntentProposed` it copies, which journal spec §9.1
says it copies exactly.

## Decision

1. **The handoff carries the confirmation.** `IntentBody::Order` gains `confirmation`: the bid,
   bid size, and floor the owner confirmed on the `OwnerExitRequested` the intent follows from,
   and that record's event id. The core refuses, as non-canonical and before anything is
   journaled:
   - a confirmation on any purpose but `owner_exit`;
   - a bid, bid size, or floor that is not positive;
   - a limit below the floor.
2. **The executor journals it beside the intent.** A confirmed handoff journals
   `OwnerConfirmationReceived` immediately after its `IntentReceived`, in the same batch. It is a
   new account-stream record, journal spec v0.66 §9.5, with members `intent_id`, `bid`,
   `bid_size`, `floor`, `copied_from`, and `risk_clock`. The confirmation stays out of
   `IntentReceived` for the reason the protective prices do (DEC-446 item 5): the copy of the
   proposal stays exact. Two rules bind the new record:
   - **Rule 246:** its three prices are positive.
   - **Rule 247, a batch rule:** the record immediately before it is the `IntentReceived` of the
     same intent, with purpose `owner_exit` and a limit that is null or not below the floor.

   The fold reads the confirmation back, so a restart, a re-gate, a later rung, or a resubmission
   after a confirmed absence sees the same floor. Its vectors are the `owner_confirmations`
   section. `mandate-journal` registers the record and enforces both rules in its own DEC-77 pair,
   before the core writes the record.
3. **The core sells a confirmed owner exit as it sells a confirmed switch's flatten.**
   - The gate sees the confirmed bid as `owner_confirmed_bid`, so it does not defer the exit
     outside the regular session (`owner_confirmation_required`).
   - In pre-market and after-hours the exit goes as an extended-hours limit.
   - The ladder never prices below the floor. The floor is the higher of the intent's own floor
     and its switch's floor, where both exist.
   - Any remainder rests at the floor, then waits for the session, with the existing alert
     (§5.5).
   - In the regular session, on a fresh sane quote, an exit with no limit goes at the market
     (§5.1, [DEC-2037](DEC-2037.md) item 4), as a confirmed switch's flatten does. The floor binds
     only the ladder (§5.5: "The ladder never prices below the floor").

   An owner exit with no confirmation still waits for the regular session, unchanged.
4. **The executor process hands the proposal as proposed.** An owner's exit at the market is
   handed with no limit, plus the confirmation from the `OwnerExitRequested` on its causation chain
   for the same instrument, or none. This replaces DEC-2033 item 4's limit at the floor, so
   `IntentReceived` copies the proposal exactly again.
5. **DEC-2037 item 6's gap closes.** Item 6's check stands: the gate paces an owner exit only by
   the participation caps. What changes is that a confirmed owner exit is no longer held to the
   session.

## Rationale

The core already sells a confirmed owner flatten outside the session by this route. This decision
gives an owner's exit of one instrument the same route and the same floor, and changes nothing for
an unconfirmed exit. A separate record keeps `IntentReceived` the exact copy of the proposal and
gives replay the confirmation without reading the agent stream.

## Alternatives considered

- **`IntentReceived` version 3 with `floor`, `bid`, and `bid_size`.** Rejected: §9.5 keeps the
  intent record the exact copy of the proposal, and this would break that copy.
- **The executor process re-reads the agent stream on each restart.** Rejected: the core folds only
  its own stream, and a re-gate between restarts would see no confirmation.
- **Keep the floor binding in the regular session.** Rejected: §5.5 binds the floor to the ladder,
  a confirmed switch's flatten already goes at the market in the session, and a limit at the floor
  can leave a position unsold that a market order would close.
