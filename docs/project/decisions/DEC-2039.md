## Context

DEC-2038 found that nothing on `main` journals `AgentStopped`. The owner's Stop is an
`OwnerCommandIssued` that the agent's runtime judges (mandate spec §6.1). An agent whose runtime
never ran has no process to judge it:

- a version-1 deployment;
- a version-2 one that rule 201 refuses;
- one the manager has not yet started.

So such an agent is never retired, and its `deployment_unread` alert repeats on every manager
start.

`AgentStopped` carries `loss_added`, the agent's net dollar loss max(0, N − E) at retirement, which
joins its connection's loss carry for the lifetime floor (mandate spec §5.7, V-032). The deployment
manager folds no account risk state and cannot compute it. A 0 written for an agent that traded
would understate the carry and loosen the floor, so the manager must not write it.

"Never ran" cannot be read from the control stream alone. The manager journals every start before
it makes one, but a runtime started outside it (a founder's run of `mandate-daemon`) does not, and
the agent's stream cannot be pinned to the control stream's head in one append. So the writer
claims the agent's stream instead: whoever opens it first decides.

## Decision

1. **The workspace service that takes the owner's Stop writes `AgentStopped` itself, for an agent
   no process ran.** That is the CLI's `agent stop` and the workspace API's stop. The record has
   reason `owner_stop`, `loss_added` 0, and the connection the agent's deployment names (version 2)
   or its stored document names (version 1).
2. **It first claims the agent's stream.** It reads the stream's head and, if the stream is
   empty, appends its `StreamOpened` at expected head 0 under the writer epoch that head holds
   (journal spec §5.1), as its own actor (the owner, `user`, for the CLI). It takes no epoch of
   its own, so it never fences a runtime, a running one least of all. The append is the emptiness
   check: it commits only on a stream nothing has opened. Its outcomes:
   - **Committed:** the stream is claimed. The service appends the `AgentStopped`.
   - **HeadMismatch:** the service reads the stream's first record. If it is a claim (a
     `StreamOpened` whose actor is not an agent), the stream was claimed by an earlier Stop that
     did not finish, and the service resumes it: it appends the `AgentStopped`. Otherwise the
     agent's runtime opened it: the agent ran.
   - **Fenced:** a runtime took the stream's epoch after the service read the head, so it is
     starting: the agent may run.
3. **The claim is identified by actor kind, never by process instance.** Only a `StreamOpened`
   whose `actor.kind` is not `agent` is a claim. A runtime's own restart, a second launch of the
   same slot, or a crash-recovery launch replays a stream its kind opened and resumes it, as
   today.
4. **The runtime refuses a claimed stream.** At start, after it takes the stream's epoch and
   replays it, a runtime that finds a claim appends nothing, sends nothing, and exits with code 6,
   `stream_claimed`, a new `mandate-process` exit distinct from every other (0 drained, 2 refused,
   3 fenced, 4 cycle failed, 5 drain incomplete). A runtime that loses the race (its own
   `StreamOpened` at head 0 answered `HeadMismatch`, and the stream's first record a claim) has
   written nothing and exits the same way, with no order sent: it sends none before its stream is
   open. A claim takes no epoch, so a `Fenced` answer means another runtime took the stream, and
   that exit stays `fenced` (3).
5. **What the manager does with that exit.** The orchestrator reports a claimed exit apart from
   any other. The manager does not restart it and does not count it toward the crash-loop bound:
   it raises one opaque operator alert, `stream_claimed`, and waits for the agent's `AgentStopped`,
   which ends its want for the slot as any stop does. The claim and the `AgentStopped` are
   consecutive appends, so the wait lasts until the service's next append, or, if the service
   crashed between them, until the owner's next Stop resumes the claim. A manager restarted in
   that wait starts the slot once more, and that start exits the same way.
6. **Otherwise the Stop is committed as an `OwnerCommandIssued`, as today.** That covers an agent
   that ran, one never deployed, a version-1 deployment whose document cannot be read, and a
   control stream that keeps moving. The direct write is withheld, never the Stop. A Stop is a
   risk reduction, so it is never refused for this (`AGENTS.md` rule 13), and the fallback to the
   command path stays.
7. **Stream rule 246 is the writer's own.** An `AgentStopped` whose actor is not an agent has
   reason `owner_stop`, `loss_added` 0, and an agent stream that opens with a claim; a claimed
   stream holds nothing after its `StreamOpened`. `append` sees one record and does not check it.
   The writer appends the `AgentStopped` at the control head it read, so a deployment or stop
   appended in between is decided again: the CLI up to its bound, the API answering 503
   `journal_unavailable`, as for DEC-1171's deployments. The claim stands across those decisions.
8. **The kill switch is unaffected.**
   - It never depends on a runtime being alive: the manager starts a down or crash-looped process
     once per kill switch, and the executor applies its own copy (journal spec §9.21, DEC-1170).
   - The claim touches only the agent's own stream, never the account stream the executor
     writes. No kill switch waits on a Stop, and no Stop waits on a kill switch.
9. **A runtime that started and then crash-looped is a later slice.** Its Stop needs the runtime's
   own loss reading. The manager starting it once per owner Stop, as it does per kill switch, is a
   journal spec change (`ProcessStartIssued.cause`), so it follows as its own spec-then-code pair.

## Rationale

The append's head check is the only atomic test the journal offers, and it is per stream. Claiming
the agent's own stream turns "nothing ran" into a fact one append decides, with no window between
two reads. A runtime that holds the stream but has not yet opened it loses at its own head check,
and one that takes the stream after the service read its head fences the claim. No
loss is ever guessed: the direct write happens only where the claim proves the loss is 0, and every
other Stop keeps its existing path.

## Alternatives considered

- **The deployment manager writes it.** Rejected: it cannot compute `loss_added`.
- **Prove "never ran" from `ProcessStartIssued` and an empty agent stream, read in turn.**
  Rejected: an unmanaged runtime started between the two reads is not seen.
- **Identify the claim by process instance.** Rejected: a managed runtime's own restart would
  then refuse its own stream.
- **Refuse the Stop when the claim fails.** Rejected: a Stop is never refused (rule 13). The
  existing command path stays.
- **Write it for any agent whose runtime is down.** Rejected: an agent that ran may carry a loss.
