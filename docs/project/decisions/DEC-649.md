# DEC-649: A step-up presentation names its workspace and principal only through the request's context

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | Agent (lane L1 builder, claude-code), under DEC-176 (it only tightens ID-8: an honest caller's presentation is judged as before, and only a caller that names IDs it was not authorized for loses that ability) and DEC-79 (the DEC-77 staging is reversible engineering) |
| **Story or claim** | E9-4 (action-bound step-up), E9-8 (ID-8's layers); identity spec ID-8, §7.2 step 4; [DEC-665](DEC-665.md), [DEC-662](DEC-662.md) |

## Context

`mandate_passkey::stepup::Presentation` carried public `workspace_id` and `principal_id` fields,
and `consume` compared the challenge record with whatever the caller wrote there. A request
authorized in workspace B could fill in workspace A's IDs, and the step-up would be judged as
A's. Issuance already takes the `TenantContext` `authorize` returns (DEC-665); presentation did
not. ID-8 says no API accepts a bare workspace ID.

## Decision

1. **The request path is `Presentation::new(&TenantContext, Action, Proof)`.** It reads the
   context's `workspace()` and `principal()`. A challenge obtained under one workspace's or
   principal's context therefore never matches a presentation made under another's: `consume`
   refuses it `step_up_mismatch`, at the same place in DEC-662's order as before.
2. **`&TenantContext`, not `&impl Tenant`.** It matches `issue_challenge` (DEC-665 item 1), so a
   challenge is obtained and presented through the same kind of context. `Tenant` is also
   implemented by `demand::Permitted` (a read witness, DEC-655) and is open to future sealed
   contexts such as a system context (DEC-668); step-up proves a person's presence (§7.1), so no
   machine context may present one. An `own` row's context arrives through
   `PrincipalContext::into_tenant`, an org row's through `OrgContext::into_workspace`, as at
   issuance.
3. **The IDs are owned values.** `TenantContext`'s accessors return the `Copy` IDs by value, so
   the fields hold `WorkspaceId` and `PrincipalId` rather than references. `consume`'s checks and
   their order do not change.
4. **Staging under DEC-77.** The existing step-up fixture (`tests/stepup/mod.rs`, used by 14 live
   tests) builds a `Presentation` by literal. Making the fields private needs that fixture to call
   `new`, and while `new` is a stub every one of those tests would stop at it. DEC-77 item 2 lets
   an implementation PR change `tests/` only by deleting `#[ignore]` lines, so the fixture cannot
   move in the implementation PR either. The change therefore lands in four steps, none of which
   turns a live test pending:
   1. **Tests PR (this one).** `new` as a `todo!()` stub; the fields become owned (the fixture's
      literal changes with them); a live `compile_fail` doctest that `new` takes no bare
      `(WorkspaceId, PrincipalId)`; and two tests pending on E9-4 that stop at the stub:
      `a_step_up_challenge_from_another_workspace_never_counts` and the property
      `a_step_up_counts_only_under_the_context_its_challenge_was_issued_to`, over contexts from
      the real `authorize` with an oracle that compares the drawn indices.
   2. **Implementation PR.** `new`'s body; it deletes only the two `#[ignore]` lines.
   3. **Fixture PR (tests only).** The fixture builds each case's context with `authorize` over
      `mandate-identity-testkit` and presents through `new`. Every test stays live; no `src/`
      change.
   4. **Seal PR (code only).** The ID fields become private, with a `compile_fail,E0451` doctest
      that a `Presentation` cannot be built from bare IDs outside the crate. No `tests/` change.

   Until step 4 merges the public fields remain, and their documentation says so; no product
   crate builds a `Presentation` today (only the passkey crate's tests do).

## Rationale

Issuance takes the context, so the challenge record binds the authorized workspace and principal;
presentation must too, or the binding is checked against the caller's word. With the context in
the signature and the fields private (item 4's last step), a cross-workspace presentation cannot be
expressed, rather than being refused only when the caller is honest; until that step lands the
public fields still allow it, and no product crate builds a `Presentation` meanwhile.

## Alternatives considered

- **Make the fields private in the implementation PR and migrate the fixture there.** Rejected:
  DEC-77 item 2 forbids that `tests/` change.
- **Migrate the fixture in this PR and mark its 14 tests pending.** Rejected: it takes live
  coverage of `consume` off for the length of the sequence.
- **Land the constructor's body, the fixture, and private fields together in one PR.** Rejected:
  implementation before its tests on a safety-critical path (DEC-77, DEC-83).
- **A public `tenant: &TenantContext` field instead of a constructor.** Equivalent at the type,
  but the struct would carry the whole context (session, permission) into `consume`, which needs
  only the two IDs.
