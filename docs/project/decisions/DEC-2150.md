## Context

[DEC-2146](DEC-2146.md) item 1 lets only a `dev` or `ci` test cell waive a first passkey's 24-hour
enrolment cool-off at step-up. Staging keeps the 24 hours. The founder needs a working demo on
staging within two days. A demo owner enrols a fresh passkey there and must confirm, deploy, resume
and stop within minutes.

The founder's words, relayed to lane L1 by the coordinator on 2026-10-29, verbatim:

- the context: **"the deadline is two days, i need a working demo"**;
- the coordinator's offer: "waive it on staging for the demo only, with an end date";
- the founder's answer, accepting it: **"waive on staging"**.

No record of these words exists in the repository beyond this file. The founder reviews after the
fact and can revert this decision (DEC-79).

## Decision

1. **A staging cell may waive the cool-off, for the demo only, until a fixed expiry (the
   founder).**
   - This amends DEC-2146 item 1: `staging` joins `dev` and `ci`.
   - The expiry can be no later than **2026-11-05T00:00:00Z**.
   - **Production never waives it**, with or without an expiry, and neither does an unset or
     unknown tier, which reads as `production`.

2. **The expiry is a setting, and the server refuses it at start unless it is well formed.**
   - **The setting.** It is `MANDATE_API_STEP_UP_COOL_OFF_WAIVER_UNTIL`, written exactly as
     `YYYY-MM-DDTHH:MM:SSZ` in UTC. The chart renders it from `api.stepUpCoolOffWaiverUntil`. Like
     the waiver's own name, it holds no part DEC-978 item 2 refuses.
   - **What the server refuses at start, before it serves anything, beside DEC-2146 item 2's
     refusals:**
     - the waiver in `staging` without the expiry;
     - an expiry in any form but the one above;
     - an expiry without the waiver;
     - in `staging`, an expiry later than the ceiling of item 3.
   - **When the server starts anyway.** It starts with a staging expiry already past. That waiver
     is then inert from the first request, which fails closed (item 4).
   - **`dev` and `ci` are unchanged.** They need no expiry, and the ceiling does not apply to them.
     An expiry set there is honoured as in item 4, since it can only end a waiver.

3. **The ceiling is compiled into the server, so a values edit alone cannot extend the waiver.**
   - The API server holds the const `STAGING_WAIVER_CEILING`, 2026-11-05T00:00:00Z, and refuses at
     start any staging expiry later than it.
   - Moving the expiry past the ceiling needs a code change and a new founder decision. The chart's
     values cannot do it, and neither can any other setting.

4. **The clock can only end the waiver, never start it.**
   - The verifier judges the expiry against its own judging instant, `judged.now`. That is the
     instant DEC-2146 item 4 already writes as both records' `event_time`.
   - A step-up judged before the expiry is waived as DEC-2146 item 3 says. One judged at or after
     the expiry is not: its cooling credential refuses `step_up_missing`, and nothing is appended.
   - No clock reading turns a waiver on: without the setting, and outside `dev`, `ci` and
     `staging`, there is no waiver for any instant to count.
   - The expiry is judged at each step-up, not only at start. So a server started before the expiry
     stops waiving at the expiry without a restart.

5. **`StepUpCoolOffWaived` names `tier` `staging` (journal spec v0.116).** The record's `tier`
   type admits `staging` beside `dev` and `ci`, and `production` stays invalid. Rules 316 to 318
   are unchanged. The journal cannot check the tier, as DEC-2146 item 4 says, but an auditor reads
   a staging waiver's `event_time` against that cell's expiry.

6. **The chart refuses it everywhere else.**
   - Its schema and its render refuse `api.stepUpCoolOffWaiver: true` in `production`. They refuse
     it in `staging` without `api.stepUpCoolOffWaiverUntil`.
   - The schema also refuses an expiry without the waiver, and an expiry in any other form.
   - The render sets both variables in a staging cell.
   - Staging's own values set the waiver and the expiry in the implementation change, and nowhere
     else.

7. **It is removed after the demo.** The backlog row
   `docs/project/backlog/E9-4-remove-staging-cool-off-waiver.md` takes the waiver out of staging's
   values, and then the `staging` tier out of the server and the chart, once the demo is over. The
   ceiling and the expiry make it end even if that row waits.

8. **How it lands (ES-22, DEC-77).**
   - **This change:** the decision, journal spec v0.116 with its vectors and fixtures, and the
     identity and workspace API notes. It also carries the chart's schema, the backlog row, and
     DEC-2146's status line. In `mandate-journal`'s `cool_off_waivers` tests, the valid staging
     draft becomes a pending test with its behaviour-only row, as DEC-2857's change did.
   - **Then a tests change**, pending tests and a stub:
     - production with the waiver refuses to start;
     - staging with the waiver but no expiry refuses;
     - staging with an expiry past the ceiling refuses;
     - a staging waived confirmation before the expiry commits with its `StepUpCoolOffWaived`
       naming `staging`;
     - at or after the expiry, the same step-up is `step_up_missing` with nothing appended;
     - `dev` and `ci` are unchanged;
     - the chart renders staging's two variables, and refuses production in its schema and its
       render.
   - **Then the implementation**, with staging's values, planted bugs, and mutants to 0 missed.

## Rationale

- **Item 1** is the founder's: a demo on staging, with an end.
- **Items 2 and 3** make the end hard to move. A staging cell cannot start waiving without an
  expiry, and cannot start with one later than the ceiling the code is built with. So extending the
  waiver takes a code change that a reviewer sees, not a values edit.
- **Item 4** makes the clock fail closed. A wrong or skewed clock can end the waiver early, but it
  cannot start one or keep one going past an expiry the verifier has reached.
- **Items 5 and 6** keep each waiver visible in the journal, and keep production refused at three
  points: the schema, the render, and the start.

## Alternatives considered

- **No expiry: waive on staging until someone turns it off.** Rejected. The founder accepted "with
  an end date".
- **The expiry as a setting alone, with no compiled ceiling.** Rejected. A values edit could then
  extend the waiver without a decision.
- **Judge the expiry only at start.** Rejected. A server started before the expiry would keep
  waiving after it until restarted.
- **Waive at enrolment on staging by shortening rule 249's 24 hours.** Rejected for DEC-2146's
  reason: the record would hide that the passkey was new.

## Adversary notes

- **An insider who sets a staging pod's environment** can set any expiry up to the ceiling, and
  can set the tier. That is DEC-2146 item 2's residual, now with an end no later than 2026-11-05.
- **A staging clock set back** could keep a waiver counting past the real expiry, until the
  ceiling-capped expiry by that clock is reached. The journal's `event_time`s then show the waiver
  at instants the auditor can check against the cell's other clocks.
- **A demo user's sign-in channel taken over** within the demo window could add a passkey and step
  up at once. Staging is paper only (DEC-2146 item 3's scope), so no money moves. That window is
  the cost the founder accepted for the demo.
