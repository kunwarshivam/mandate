# DEC-2820: An abandonment names the client order id its intent derives (rule 303)

| | |

| **Date** | 2026-10-26 (UTC) |

## Context

DEC-2803 closed `OrderAbandoned` but left its `client_order_id` unbound to its `intent_id`. Trading
spec §2.3 then stated `"{intent_ulid}-{attempt}"`, which the executor never writes, so a rule would
have made the wrong form normative. DEC-2807 (v0.21) brought §2.3 to the form the executor derives:
an intent's own order is `md-` followed by its intent id, the watchdog's and a kill switch's exits
(`w-…`, `k-…`) alike.

## Decision

1. **Rule 303** (journal spec §9.5, v0.99): an `OrderAbandoned`'s `client_order_id` is `md-`
   followed by its `intent_id`, exactly; otherwise refused `schema` at `payload.client_order_id`.
   An abandonment can then name no other intent's order, and no rung, protective order or
   replacement of its own.
2. **No executor change.** The executor's only writer, `abandon_record`, writes
   `ClientOrderId::for_intent(intent)`, which is this form, so every abandonment it drafts already
   holds; its tests parse those drafts through the journal's own checks.
3. Rule 304 stays unused.

## Rationale

- A record that names an order and the intent it abandons should not be able to name two that do
  not belong together; the fold and every reader would otherwise have to choose between them.

## Alternatives considered

- **Admit a rung's or protective order's id too.** Rejected: the executor abandons an intent, not
  one of its orders' later forms, and admitting them would let a malformed record pass.
