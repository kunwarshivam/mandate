## Context

DEC-2392 lets a stored news item or filing on an instrument with an active thesis bring a
`monitor` run forward, and the research core (#2558) decides it. The cell has no live news source
yet (the Alpaca reader of DEC-2394 is wiring to come), and its recorded bundle (DEC-2210) stamps
every item at an age before each read's cut-off. An item read that way has different bytes on
every pass, and is always newer than the last research call. So it cannot be the trigger: rule 271
dedupes an item by its stored bytes (`data_ref`), and §5.3 refuses an item older than the last
call.

While testing, a restarted daemon was found to start a second run on an item that had already
started one. The process replayed the agent stream into the runtime's state on start, but never
into the research state.

## Decision

1. **A recorded feed.** A recorded bundle may hold `feed.json`, an array of news items with the
   fields of `news.json`, except that `arrives_s` replaces the two ages. An item arrives
   `arrives_s` seconds after the agent's latest `AgentDeployed` in the environment, on the whole
   second. It is known and published at its arrival. Its bytes therefore hang on a journaled
   instant, and are the same in every pass and every process.
2. **Optional, read strictly.** This narrows DEC-2210 item 1 for this one file. A bundle without
   `feed.json` has an empty feed, so no existing bundle changes. A `feed.json` that exists but
   cannot be read, is not strict JSON, or has a row missing a member refuses the load. So does a
   directory whose entry cannot be checked. Nothing else is defaulted.
3. **Offered every pass, in arrival order.** The cell's source gives the pass the items arrived by
   its risk clock, and only when the version sets `behavior.research.event_triggers`. The pass
   offers them before its scheduled poll, earliest arrival first. For each item it:
   - captures the item as of its arrival;
   - stores the record (once a process, by digest), so the `ObservationRecorded` an event run
     starts with names stored bytes;
   - hands it to the core.

   The core alone decides. It refuses an item whose run is already journaled (rule 271), one no
   newer than the last research call, and one the debounce, the day's cap, the cost cap, or a run
   in flight holds. A refused item journals nothing. The next pass offers it again, so the
   debounce and a run in flight only delay it. An item becomes inert once a research call is
   later than it, which is §5.3's "a later run reads it like any other item". An item whose
   record cannot be stored is not offered on that pass.
4. **Research state is replayed on start.** The daemon folds every replayed agent-stream row into
   the core's research state as well as into the runtime's state. A row the research fold refuses
   fails the start, as one the runtime fold refuses already does. A restarted process therefore
   keeps:
   - the last research call;
   - the debounce;
   - the day's event runs;
   - the items that started runs.

   This is agent harness spec §5.3's restart row. A run in flight is not restored; as that row
   says, the restarted process starts afresh. Before this, a restart forgot all of these for
   scheduled research too.
5. **No live source.** The feed is recorded data only, and CI and the demo use nothing else. The
   Alpaca reader (DEC-2394) offers its stored items through the same pass once it is wired.

## Consequences

- The demo bundle (`deploy/cell/demo/research/`, lane DR's) gains a `feed.json` item and the
  research mandate gains `event_triggers` in a later change. The demo shows the agent acting on
  news only once the research agent's runtime runs in the cell and its position fills.
- Adversaries:
  - **A burst of feed items:** bounded by the debounce, `max_runs_per_day`, the cost cap, and
    one run in flight.
  - **An item replayed after a restart:** it carries the same bytes, so rule 271 refuses it.
  - **An item no thesis covers:** it journals nothing, and goes inert after the next research
    call.
