# DEC-2127: The fixture's token refusals are written to standard error as their code and cause alone

| **Date** | 2026-10-25 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane D1, claim [#1901](https://github.com/kunwarshivam/mandate/issues/1901)) |
| **Story or claim** | E10-23; [DEC-2625](DEC-2625.md) items 4 and 6; [DEC-2100](DEC-2100.md) item 7; `AGENTS.md` rule 7 |

## Context

In the cell's connect drill, the token-exchange process reports `endpoint_failed` against the
fixture provider's `POST /alpaca/oauth/token`, and nothing says why. The fixture answers RFC 6749
§5.2's `error` alone, and `invalid_grant` covers four different checks (an unknown code, an expired
code, another redirect URI, another verifier). The exchange process may not log the answer's body,
and the fixture logged nothing, so a refused exchange could not be told from any other.

## Decision

1. **The line.** For each refusal of `POST /alpaca/oauth/token`, the fixture writes one line to
   standard error: `token_refused`, the answer's `error`, and the word of the check that refused it,
   separated by single spaces. The words are `form` (not exactly DEC-2625 item 4's form, or not
   UTF-8), `grant_type`, `client` (another client id or secret), `code_unknown`, `code_expired`,
   `redirect_uri`, `code_verifier`, and `store_full` (the token store is full or the random source
   failed). For example: `token_refused invalid_grant redirect_uri`.
2. **Before the provider.** A body that is not a form is written as `token_refused
   unsupported_media_type`, and one over the body limit as `token_refused payload_too_large`.
3. **No request value.** A line holds only those fixed words: never the client id or secret, the
   code, the redirect URI, the verifier, a token, a header, or any other value the request carried
   (`AGENTS.md` rule 7). A test asserts the lines byte for byte, and that none of a refused
   request's values appears in them.
4. **The wire is unchanged.** The status and body each refusal answers stay DEC-2625 item 4's. The
   checks run in the same order, so a request that fails two checks is written with the first, as
   it is answered.
5. **Nothing else.** Issued tokens, the authorize route, and the account route write nothing, and
   standard output keeps the announce line alone.

## Rationale

The cause is what a drill needs to tell a race (the code not yet written, or spent) from a
misconfiguration (another redirect URI or client secret). Fixed words carry the cause without
carrying a credential. The stub runs only in `dev` and `ci` and holds only the fixture's own
client, so naming which check failed discloses nothing a production provider would hide.

## Alternatives considered

- **A separate `error` code per cause on the wire.** Rejected: the fixture answers as Alpaca's
  provider does, and RFC 6749 §5.2 fixes the codes.
- **Logging the request with its secrets redacted.** Rejected: a redaction that misses a field
  leaks it, and fixed words cannot.
- **Logging in the token-exchange process instead.** Rejected for this change: the exchange sees
  only the `error`, which does not separate the four `invalid_grant` checks.
