# DEC-955: The paper run books its own unbooked fills before the flat-account check

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-16 (UTC) |
| **Decided by** | Claude (builder agent), under DEC-79 (reversible engineering decisions) and DEC-176 (each reading tightens a rule or closes a gap by the reading that adds no risk, and weakens no safety invariant or non-negotiable) |
| **Story or claim** | E2, the first paper trade; claim #1393; the gap #1388 recorded (runbook §11, "§8 run"); DEC-921 (one PR, tests first) |

## Context

The first paper order (1 SPY at 763.75, broker id `68099755-…`) filled, but its run stopped on
the journal refusal #1369 fixed before it booked the fill. The account stream holds the entry
`filled` and no `FillApplied` or `LateFillApplied`. Every later run is refused at Validate by
DEC-470 item 1 (`a paper account with no position and no open order`), which runs before the
cycle's startup reconciliation, so no run could ever book the fill. The journal and the broker
disagreed with no path to converge.

## Decision

1. **Where.** A placing run and a `--reconcile-only` run on a paper connection perform one
   own-fill reconciliation after the credentials are read and before the preflight, so before
   DEC-470 item 1's flat-account check. That check is unchanged: it still refuses while any
   position or open order exists, so after the fill is booked the E2 run is refused at Validate
   exactly as before, with nothing sent. A dry run keeps nothing (DEC-157 item 6) and books
   nothing. A live connection keeps DEC-529 item 3's lapse and books nothing; booking for the live
   arm is backlog.
2. **What it may touch.** Only orders the account stream already owns: every order it journaled
   `OrderSubmitted` for whose booked quantity is below its own (`mandate_executor::owed_orders`).
   When there are none, nothing is read from the broker and nothing is owned or written. Otherwise
   it takes the stream's ownership and reads, with GETs only, each owed order by its own client
   order id and the account's `FILL` activities from the stream's last checkpoint on (at most 20
   pages). A fill that names no owned order is left alone: nothing is adopted, and no
   `ExternalActivityIngested` is written.
3. **How a fill is matched to its order.** By our client order id, or, where the fill carries
   none, by the broker's own id for the order as the broker's lookup of our id answered it.
   Alpaca's `FILL` activity carries `order_id` and no `client_order_id`, so `BrokerFill` gains
   `broker_order_id`, read from `order_id`. A fill that names the order by one id and another order
   by the other is a mismatch.
4. **What it books, and when it stops.** For each owed order the broker answered, what it filled
   beyond what the stream booked must be made up exactly by the unbooked fills that name it, in
   the same instrument and side, and the order must not be filled beyond its own quantity. Each
   such fill is drafted by the executor's own fill path at the broker's price and fees:
   `LateFillApplied` where the stream holds the order terminal (trading spec §5.7, DEC-938
   item 3), otherwise `FillApplied` and the order's state change. Any disagreement
   (`not_ours`, `order_twice`, `order_differs`, `overfilled`, `broker_filled_less`,
   `fill_differs`, `fill_names_another_order`, `fills_short`, `fills_exceed`) drafts nothing and
   stops the run at Reconcile with `own_fill_mismatch`, naming the order's opaque client order id
   and the reason code only (rules 3 and 6). The drafts are appended at the head the pass read,
   all at once; any other append answer stops the run. No `ReconciliationRun` is written: this
   pass compares no position, cash or open order, so it never claims the §11 coverage that would
   release the runtime's hold on openings (DEC-458).
5. **Nothing it carries can send.** The pass builds its executor from
   `mandate_shell::paper::reconcile_context`, whose binding gate answers no request, and the
   executor returns journal records only: any other effect is refused before the append. Its
   broker requests are the two reads in item 2, nothing else.
6. **`mandate-paper --reconcile-only`.** Books as above, then runs the pass again over the journal
   it wrote, which must find nothing more owed, and exits printing
   `booked <n> fill record(s); nothing sent`. It reads no market data, runs no model and no cycle,
   and never places. It needs `--journal` and is refused beside `--place-one-order`.

## Rationale

The fill already happened at the broker; booking it records a fact, and adds no order, quantity
or owner. Every reading here refuses where the evidence is short: a mismatch stops the run, a
fill nobody owns is left for the full reconciliation, and the flat-account check that refuses
the second run is unchanged. So DEC-470 item 1 is not loosened in any way, and the item tightens
the journal toward the broker without adding risk (DEC-176).

## Alternatives considered

- **Run the full startup reconciliation before the flat check.** On the E2 state it would meet
  the take-profit leg Alpaca lists at top level under its own id and ingest it as external
  activity (`ExternalActivityIngested` has no registered schema), and it adopts open orders.
  Refused: it adopts what the journal does not own.
- **Book from the order's `filled_avg_price` alone.** That needs a fill id, and an invented one
  would be booked again when the activity is later read. Refused.
- **Let the dry run book.** A dry run keeps nothing (DEC-157 item 6). Refused.

## Not decided here (backlog)

- The executor's own fill path (`BrokerUpdate::Fill` and the full reconciliation) still matches
  a fill to its order by `client_order_id` alone, which Alpaca's `FILL` never carries, so a real
  fill read there is external activity. Matching by `broker_order_id` there needs the broker id
  in the fold (DEC-869's `OrderStateChanged` version 2 carries it).
- A fill of a bracket leg (the take-profit or the stop) names an order Alpaca named, which no
  `OrderSubmitted` owns, so this pass leaves it alone; booking it is the leg-reconciliation slice.
- The live arm's booking.
