| **Amends** | DEC-2265 item 6 and DEC-2272 item 7 (the gateway's artifact-store access) |

## Context

The research path stores the artifacts its journal records cite before it journals them (DEC-2208
item 5):
- the observations it retrieved;
- each model call's prompt and response;
- each tool result;
- the run's summary.

The cell's research runtime stores them through `MANDATE_ARTIFACTS`. The chart mounts that store
read-only for the runtime, and must keep doing so: DEC-2385 item 5 and DEC-1016 say so, and the
deployment manager's admission policy admits a managed pod's claim only read-only. So every put
fails. The writer refuses the first batch `artifact_unstored`, and research halts with the alert
`research_halted`. The local cell's capture on main b76a3a1 (2026-10-26 16:28Z) shows this.
The runtime made no call and journaled nothing for research.

## Decision

1. **The gateway is the research runtime's artifact writer.** A runtime started with `--gateway`
   sends each research artifact's bytes to the model-gateway service. The service is the one
   service that runtime already reaches (DEC-2397 items 5 and 6).
   - The request is a `put` frame on the existing framed canonical-JSON exchange (DEC-2265),
     bounded by the request frame's limit.
   - It names the workspace. A put naming another workspace is refused `foreign_workspace`, as a
     call naming one is (DEC-2265 item 7).
   - The service stores the bytes in its workspace's artifact store and answers the reference it
     computed from them.
2. **Create-only, content-addressed, checked on the server.**
   - The service recomputes the reference from the bytes it received; it never takes one from the
     runtime.
   - It writes through the store's create-only path: a new object is linked into place, and an
     existing name is never replaced. Bytes already stored change nothing and answer the same
     reference.
   - The service gains no read, list, delete or overwrite of any artifact. The only new code path
     is that put. Its reads stay item 1 of DEC-2272's, the deployed mandate's research cap.
3. **The runtime checks the answer, and a failed put fails closed.**
   - The runtime's research sinks count a put as stored only when the answer is the reference of
     the bytes it sent. Those are both the core's draft artifacts and the worker's retrieval,
     prompt and response.
   - An answer that is lost, refused, or names any other reference is a failed put. The writer
     then refuses the batch `artifact_unstored`, and research halts exactly as DEC-2208 items 5
     and 6 say.
   - Nothing is ever journaled citing an artifact that was not stored.
4. **A fixed store cap.**
   - The service refuses `store_full` any put that would take the workspace's artifact store
     past 512 MiB.
   - At start it counts the bytes of every stored object, so the count survives a restart. It
     then adds each put's length.
   - The cap is a fixed constant of the service, not a value. It is half the store volume's
     1 GiB, so the other writers keep room (the control runs and the data process).
   - A refused put fails closed as item 3 says.
5. **The mounts.**
   - The chart mounts the artifacts volume read-write for `model-gateway`, as a fixed entry in its
     per-process access map ("rw", as the data process's is), so no value widens it.
   - The runtime's mount stays read-only, and the admission policy is unchanged.
   - No port, Service, NetworkPolicy or egress is added. The gateway's ingress still admits only
     same-namespace pods labelled for it.
6. **Amendments.** This amends DEC-2265 item 6 ("the gateway has no artifact-store egress") and
   DEC-2272 item 7 ("the service writes no artifact"). Both stay in force for everything else.

## Safety

- **Integrity.** Every artifact the core, the executor or a verifier reads is reached through a
  hash the journal holds, and read with `get_artifact`, which re-hashes the bytes and answers
  `Corrupt` unless they match (journal spec §4).
  - So a gateway that is wrong or compromised can add bytes to the store, but it cannot change what
    any journaled decision, record or mandate cites.
  - Altered or deleted bytes are refused on read, so the reader fails closed: no decision is made
    from them, and the journal's verifier reports them.
- **Availability.** The rw mount lets a compromised gateway process damage files outside its code
  path, by deleting them or breaking a stored object. That costs availability, not safety:
  - a deployment whose mandate document no longer reads resolves to nothing;
  - research halts;
  - every read fails closed.

  The data process already holds the same access (DEC-2385 item 3).
- **Store filling.** A compromised research runtime could send many distinct puts. Each is bounded
  by the frame, item 4's cap bounds the whole, and only that workspace's runtime can reach the
  service. Filling to the cap halts research, and leaves half the volume for the other writers.
- **Rules.** No rule of `AGENTS.md` changes:
  - the runtime holds no credential and reaches no broker;
  - an LLM still produces opinions only;
  - every order still goes through the journal and the gate;
  - nothing here adds risk, and every failure path halts research.

## Rejected

- **Making the runtime's mount read-write.** This weakens DEC-2385 item 5 and DEC-1016, and the
  manager's admission policy, so it is founder territory.
- **The data process as the writer.** It is the market-data service, with no listener, and it
  reaches nothing but its data host. A research put would add an ingress and a second role to it.
- **A new artifact-writer process.** It would add an image, a Service, a NetworkPolicy and an ADR
  for the same capability, beside a service the research runtime already reaches.

## Consequences

- With the gateway's put and the runtime's remote sink, the research runtime in the cell can store
  what it journals, so its research runs past the first batch.
- The gateway's store access is now rw. The chart's invariant tests hold the access map fixed, and
  hold the runtime's mount read-only, over both deployment managers.
