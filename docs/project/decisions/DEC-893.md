## Context

`mandate_journal::resolve_trusted_start` (§9.14, DEC-767) does not check the row it finds. It
filters on the row's columns and reads the payload from the body, so a row whose `stream_id` column
names this workspace while its body is another workspace's passes; and it returns a manifest start
that only the hot store vouches for, which DEC-787 items 3 and 5 refuse.

## Decision

1. **The start row is checked before it is used.** After §9.14's lookup finds the record (by the
   row's columns and its body's `payload`, as today), its row must pass journal spec §11 check 1
   (`non_canonical`), check 2 (`column_mismatch`, every column §11 lists, `stream_id` and so the
   workspace included), and check 4 (`rehash_mismatch`), in that order. A `SegmentExported` must
   then also satisfy rule 117: its `manifest_hash` is its own six fields' hash. Any failure refuses
   the start. Genesis has no record and is not checked.
2. **No check 6, and no other per-event check.** DEC-787 item 3 names checks 1, 2, and 4 only.
   Check 3 (`seq_gap`) and check 5 (`prev_hash_mismatch`) relate a row to its neighbours, which a
   lone start record does not have, and check 6 (artifacts) is the range walk's. The range walk
   still runs every check on the range itself.
3. **Check 2 closes the column and body workspace mismatch.** Because the lookup reads the
   columns, a row of another workspace stored under this workspace's `stream_id` column would be
   found; check 2 then refuses it. A row of this workspace stored under another workspace's column
   is not found at all, which is the same refusal (DEC-767).
4. **A manifest start is a type-state.** The resolver returns a manifest start as `ManifestStart`,
   which is not a `TrustedStart`. It becomes one only through `ManifestStart::confirm(cold_bytes)`,
   which requires `Digest::of(cold_bytes) == manifest_hash`, the bytes being the segment's manifest
   object as the cold store returns it (§6.2). A hot-only manifest start is therefore
   unrepresentable: no code path can use one without the cold bytes. This is rung 1 of the trust
   ladder, the same approach as DEC-892's verified prefix (pending).
5. **The error is `TrustedStartError { Refused, ColdUnreadable, Unimplemented }`.** `Refused`
   covers no usable record, a record that fails item 1, and cold bytes whose digest differs
   (DEC-894 item 1); `ColdUnreadable` covers a manifest object that is absent or cannot be read
   (DEC-787 item 5); `Unimplemented` stays for the crate's stubs (DEC-77). Both map to 422
   `trusted_start` with nothing recorded; `ColdUnreadable` is kept apart because it is retryable and
   raises no alert (E12-7).
6. **The reference vectors catch up.** `cold_records.trusted_starts.rows` holds real control-stream
   rows and `row_cases` the cases of items 1 to 5, answered by `control.py`'s `start_from_rows`,
   recomputed by `cold.py`'s own oracle, and each seeded bug caught; `records` and `cases` are
   unchanged.

## Rationale

A start record that is not canonical, disagrees with its columns, or does not re-hash vouches for
nothing, and checking it costs one row. A type, unlike a step, cannot be forgotten by a later
caller. Refusing adds no risk: nothing changes state, and the caller can retry.

## Alternatives considered

- **A `confirmed: bool` on `TrustedStart`.** Rejected: a flag can be ignored, a type cannot.
