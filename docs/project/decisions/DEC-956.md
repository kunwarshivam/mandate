DEC-946 was the highest number on `main` when this was reserved; the dispatch named DEC-956.

## Decision

1. **The ticker (supersedes DEC-941 item 1's "`symbol` the listing's instrument id").** The
   executor names an equity by its asset id (mandate spec §3); Robinhood's tools name it by its
   ticker, the registered instrument snapshot's `symbol` (DEC-523). `RobinhoodConnector::new`
   and `restore` take `Tickers`, built by `Tickers::registered` from `(asset id, symbol)` pairs:
   an empty symbol is `NoSymbol`, and an asset under two symbols or a symbol under two assets is
   `AmbiguousSymbol`, so nothing is mapped. Every call names the instrument by its ticker:
   review, place, the listing's `symbol` filter, tradability and quotes. Every answer reads back
   as the asset id, and an answer naming another ticker than the one asked about is never read
   as that instrument's:
   - **Place:** an order record for another ticker is `Unknown` and never re-sent (LT-6).
   - **Cancel:** the cancel goes by `order_id` alone, so it is sent even for an order whose
     ticker is not registered (`AGENTS.md` rule 13); an answer for another ticker, or with no
     registered ticker to compare, is `Unreadable` (`cancel`).
   - **List:** a record of another ticker is `Unknown` (`Ambiguous`) for the whole listing.
   - **Preflight and quote:** `preflight_facts` and `equity_quote` of an instrument with no
     ticker refuse `NoSymbol` before any read; tradability and the quote must name the ticker.
   - **Snapshot:** a position or working order in a registered ticker names its asset id; any
     other ticker stays as the broker spelled it, so an instrument the run does not trade is
     never taken for one it does (as DEC-938 item 1 does for Alpaca).
   - **No ticker:** a `Submit` is `NotSent` (`no_symbol`), and a listing is `Unknown`, with
     nothing called. Nothing guesses a ticker, a protective order's included: an instrument the
     run trades is always registered, so this refuses only a wiring fault.
2. **Proposed: an adopted order stays adopted (would supersede DEC-869 item 4's "the
   executor's fold … are unchanged" in part). Not implemented; `main`'s behavior stands.** A Robinhood record never carries our key (U-R2), so after a restart's
   listing adopts an order, the startup reconciliation found no record for it, marked it
   `Unknown` again and drafted `ExternalActivityIngested` for the broker's record. The fold now
   keeps, per order, every non-null `broker_order_id` its version-2 `OrderStateChanged` records
   carried (journal spec §9.16). Reconciliation step 1 (trading spec §11) still matches by
   client order id first. Only a record naming no client order id is matched by broker id, and
   only to the one order whose records carried exactly that id and no other, for the record's
   own instrument and side. An id two orders carried, an order that carried two ids, or another
   instrument or side matches nothing, as before. Such a matched record is ours, never external
   activity. No risk input would read the ids: replay with any ids gives the same orders,
   reservations, positions, modes and account. This was built and tested in #1394 (commits
   `31bf63f`, `555663c`, `8658ec8`, `424c259`, `9183f59`) and reverted there after its independent
   review: until the founder decides, an adopted order fails closed at the startup reconciliation,
   as on `main`, and DEC-869 item 4 stands.
3. **Pages (supersedes DEC-941 item 3's "a whole answer or none" and item 2's refused `cursor`).**
   A listing reads `get_equity_orders` page by page, each page behind a fresh account check
   (CN-8), with the same filters and the `cursor` the page before named, until a page names
   none. The next page is named by `next_cursor`: non-empty text, or `null` or absent on the last
   page. The contract names the input `cursor` but not the output member, so the name is assumed
   (DEC-875 item 4). The guess cannot read part of an answer as the whole: any other member
   beside `orders` still refuses the page, so a broker that spells the cursor otherwise leaves
   the order `Unknown` (DEC-941's objection to guessing). At most ten pages are read; a listing
   still naming a page after ten, any page lost, refused or garbled, a cursor that is not
   non-empty text, or a cursor the broker refuses is `Unknown` (`Ambiguous`), and no record of
   an earlier page is handed over. The preflight's and the reconciler's reads stay one whole
   answer (`read_sole_member`), so a paged snapshot still refuses. The simulator gains
   `Event::PageSize(n)`: at most `n` orders a page, named by cursors only it issues, and a
   cursor without a page size refused.
4. **Found, not fixed: the binding gate is not handed the account's working orders.** With item
   2's proposal applied, a restart that opens a new cycle on the same rising
   closes places a second SPY opening while the adopted one still works: the shell's
   `gate_template` (`crates/mandate-shell/src/paper/gate.rs`) gives the gate empty
   `working_orders`. So trading spec §5.3 rule 6 (`working_order_limit`) and §9.3's open opening
   orders in gross exposure go unchecked there. The live run cannot reach it, because its
   preflight refuses an account with any open order (DEC-470 item 1, `paper/judge.rs`), and the
   adopted order stops at the reconciliation on `main` anyway. It has its own backlog row and
   needs its own fix in the risk gate's inputs, before item 2 lands.
5. **`ExternalActivityIngested`.** It has no registered schema (journal spec §9's catalogue row
   lists no closed members), so the journal refuses the executor's draft as `unknown_schema`
   whatever its members say. That refusal stays fail closed: no schema is registered without its
   spec, and the draft is not reshaped to a shape that does not exist. Genuinely external
   activity, and an adopted Robinhood order until item 2 is decided, still stop the run at the
   journal.

## For the founder

Item 2 is yours to decide. Journal spec §9.16 says "The executor's fold does not read the member:
no risk state, limit, or order state depends on it". Matching an adopted order by its journaled
broker id keeps every risk state and limit independent of the id, but makes one order state depend
on it: whether the startup reconciliation keeps an adopted order or marks it `Unknown` again. That
loosens a fail-closed path: if a look-alike adoption (DEC-863) were wrong, the next reconciliation
would no longer flag it. The independent review (Sonnet) held it to be founder-reserved, and this
change takes the most conservative option meanwhile: nothing is matched by broker id, and a restart
after an adoption stops at its reconciliation (DEC-529 item 3 refuses such a run anyway). The
recommendation: accept item 2 with a spec PR amending §9.16 to "no risk state or limit depends on
it; reconciliation step 1 matches a record naming no key by it", after item 4's gate inputs are
fixed, and restore the reverted commits.

## Rationale

Item 1 is the defect #1370 reported: the asset UUID reached Robinhood as a symbol, which a real
broker would refuse or, worse, resolve to nothing the run registered. Checking each answer's
ticker means a record about another instrument can never be booked as the run's. Item 2's proposal is what
DEC-529 item 4's adoption is for: an adoption that the next reconciliation undoes leaves every
restart after a lost answer stopped. Item 3 takes the reading that can only leave an order
`Unknown`, never adopt from part of an answer. Ten pages is a fixed bound because a listing spans
five minutes of one symbol on one agentic account.

## Alternatives considered

- **Map tickers in the shell, as `BrokerSymbols` does for Alpaca:** it translates answers only;
  the request would still need the ticker, and the preflight reads bypass the shell's `Connector`.
- **Match in the connector, by its restored `order_id` map:** the map is rebuilt at start from
  the journal, before the restart's own listing adopts, so it never knows the adoption it needs
  to match.
- **Match by broker id only when the record's instrument is unknown, or any record whatever its
  side:** rejected; a record whose instrument or side differs is not that order.
- **Register an `ExternalActivityIngested` schema here:** rejected; it needs its spec first.
- **No page bound, or stopping at a repeated cursor only:** rejected; a broker that keeps naming
  pages would keep the listing reading, and a fixed bound is simpler to verify.
