# DEC-2519: The approval read names its decision's deferred checks, and a disagreement is unreadable

## Context

Journal spec rule 292 requires an `ApprovalRequested`'s `content.deferred_to_binding` to equal its
`DecisionMade`'s, an absent member read as empty, but only when both are in one `append` batch. The
runtime writes them together, so its own requests always agree. A writer that split them could write a
version 1 or 2 request, which names no deferral, for a decision that deferred checks, or a version 3
request whose list differs from its decision's. DEC-2518 made the read name the request's version, but
such a request's own content is valid for its version, so the web app still read it as the request said:
"nothing deferred" for the first case. DEC-2518 item 5 disclosed that gap.

## Decision

1. **The single read serves `decision_deferred_to_binding`:** the `payload.deferred_to_binding` of the
   `DecisionMade` the request's `causation_id` names on the same agent stream, as journaled; an empty
   list when that decision names none (versions 1 and 2); `null` when the request names no causation or
   no `DecisionMade` by that id is on the stream. The inbox carries none of it.
2. **The schema requires it** on `read-models/approval`: `null`, or a list of non-empty names. It does
   not require it to equal the request's list, so a read can report a disagreement for the client to
   refuse.
3. **The web app shows a request's checks only when they are exactly its decision's**, in order: the
   request's own list (empty for versions 1 and 2) against the decision's. Any other request is
   unreadable and offers Skip only, never Approve. That covers a decision that cannot be found, a
   decision list that cannot be read, a request that hides a deferral, and one that invents one. The
   read model accepts any list there, and the screen judges it, so a bad item never hides the approval
   from its owner.
4. **The test oracle is the vectors' `approval_deferrals.batches`:** every pairing the journal refuses
   within a batch reads as unreadable, and every pairing it admits reads as the request says.

## Rationale

An approval that disagrees with its decision about which checks were not run cannot be presented
truthfully. Skip adds no risk, and the request stays visible, so its owner can end it rather than let
it time out unseen. The decision is on the same stream as its request, so the read needs no other
stream. Rule 292 makes the runtime's own requests always agree, so no real approval loses Approve.

## Alternatives considered

- **Check it only in `mandate journal verify` (§11).** That records the disagreement but leaves the
  screen offering Approve until someone runs it. It stays useful as a record and remains backlog debt
  (`E21-30-approval-deferral-range-check`), now without the gap at the read.
- **The server judges and serves a verdict.** Refused. The web app already judges the request's own
  list (DEC-2518), and serving both lists keeps the read a plain projection of the journal, with one
  place for the rule.
- **A missing decision reads as agreeing.** Refused: ambiguity resolves to the safe default
  (non-negotiable 3).
