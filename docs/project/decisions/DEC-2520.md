## Context

Trading spec §7.3 restricts the account to closing when the connection is `degraded` or
`suspended` (row 5), under the cause `connection_unavailable`. Its cause table promises a distinct
alert: the platform cannot reach or use the connection, and the broker has not restricted the
account. Notifications spec §3.2 has one kind, `account_restriction`, for every
`AccountRestrictionChanged`. The two causes differ in what the owner must do. A broker's
restriction is lifted by the broker, then an acknowledgment. A connection's is lifted when the
connection's own condition clears, often by re-authorizing, then an acknowledgment. One kind for
both would tell the owner the broker restricted the account when it did not.

## Decision

1. **A kind of its own.** Notifications spec §3.2 gains `connection_unavailable`:
   - **Class and text key:** class `safety`, text key `attention_needed`.
   - **Recipients:** the owners of every agent on the account, as for `account_restriction`.
   - **Trigger:** an `AccountRestrictionChanged` whose cause is `connection_unavailable`.
   - **Where the alert goes:** the executor writes its `OwnerAlertSent` in that record's batch, as
     DEC-2514 places every core alert.

   `account_restriction` keeps the broker's causes, `broker_notice` and `broker_reject`. The
   payload is unchanged: a notice id and the generic text key (NT-1), so nothing in a notice says
   which kind it is.
2. **The closed sets follow.** Journal spec §9.15's kind set grows from 35 to 36 kinds, with
   `connection_unavailable` among the safety kinds, after `account_restriction`. An
   `OwnerAlertSent` may name it. The alerts read serves it (DEC-2141 item 2: §3.2 sends it to an
   account's owners), and the client names it from its own closed table.
3. **What the alert does not decide.** Nothing here changes when the restriction is journaled, what
   it blocks, or how it lifts. Those are trading spec §7.3, connections spec CN-6 and §9.1, and
   DEC-2816. A cause already in force journals no second record (DEC-2816 item 2), so it raises no
   second alert.

## Consequences

- E7-2z's later slices implement it:
  - **B:** the kind in `mandate-notify` (`NoticeKind`, `OwnerAlertKind`), `mandate-journal`'s notice
    classes, the alerts read schema and server list, and the web's table.
  - **C:** the executor writing the restriction and this alert when its connection goes `degraded`
    or `suspended`, with `ConnectionStateChanged` following and folded.
  - **D:** executord turning the connector's failures into that input.
- `mandate-notify` and `mandate-journal` today hold 33 kinds against the spec's 35: they lack
  `kill_switch_unapplied` and `retirement_held`. Slice B adds this kind and closes that gap, or
  records it as a backlog row.
