# DEC-2832: The executor process counts the broker's answers per class and reports an unusable connection

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79 and DEC-176. It only adds a restriction the specs already require, reads every ambiguous answer toward it, and lifts or loosens nothing) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane EX) |
| **Story or claim** | E7-2z (backlog `E7-2-connection-restriction.md`), slice D: `mandate-executord` maps connector errors to `Input::Connection`. Connections spec §8.2, §9.1, §9.2; DEC-687; DEC-2826; DEC-2821; DEC-85 |

## Context

DEC-2826 gave the executor's core `Input::Connection`, which restricts the account first and then
records the state change. Nothing sent it: `mandate-executord` passed a lost answer to the core
as an unknown outcome and stopped on anything else it could not use. Connections spec §8.2 counts
health signals per class and makes the connection `degraded` after 3 network failures in a row
and `suspended` after 2 authorization failures in a row (both Proposed). The coordinator's
direction for this slice: an ambiguous connector error counts as degraded, never as healthy.

## Decision

1. **A refused credential is an unknown outcome.**
   - **The change:** the Alpaca connector now answers HTTP `401` as
     `ConnectorError::Unknown(BrokerUnknown::Unauthorized)`, on every path: reads, order-bearing
     requests, cancels and their read-backs, and account-wide calls.
   - **What it fixes:** before, it answered `401` as `Rejected` on order paths, and as
     `Unreadable` on reads, which stops the process (DEC-85).
   - **Why:** connections spec §5.4 says one authorization failure "is treated as a possible
     transient: the request's outcome is `Unknown` if it was a submit, and is resolved by query".
     A `Rejected` answer settled an order, and released its reservation, that may be live at the
     broker. So this is the reading that adds no risk (DEC-176).
   - **What the process does with it:** it hands the unknown outcome to the core, which queries, as
     it does for a lost answer. A read refused this way is left due for a later pass, never a stop.
2. **Counted from every answer.** Every broker request the process makes, and a one-read broker's
   account reads, feed one counter per class (`src/health.rs`). A count resets only on a good
   result of its own class (DEC-687).
   - **Network:** a lost answer (`Unknown`: a timeout, a dropped connection, a `429` or `5xx`) and
     an answer the connector could not read (`Unreadable`) are failures, since an ambiguous answer
     is never read as healthy. Any answer the broker gave is good, a rejection or a refused
     credential included. Counting a `429` here, where §8.2 has a headroom class of its own, only
     restricts sooner.
   - **Authorization:** `Unknown(Unauthorized)`, and a `Rejected` with HTTP `401` from a connector
     that answers it so, are failures. Any other answer the broker gave is good, except a `403`.
     A `403` is the broker's refusal of the request, which trading spec §7.3's reject rows read
     (DEC-2137), and it counts neither way. It is not ambiguous, so the coordinator's direction
     that an ambiguous error is never healthy does not reach it.
   - **Neither:** a request that never left the process (`NotSent`).
3. **Reported where it cannot be behind.** While a count is at its threshold, the process hands
   the core `Input::Connection`, network first:
   - after the pass's kill switches, so none waits on it (`AGENTS.md` rule 13);
   - again before each proposal it takes, so a count that crossed its threshold earlier in the pass
     restricts the account before the next opening is taken (connections spec §9.1: the
     restriction before anything else is sent).

   The core journals each restriction and state change once (DEC-2826). A core error on the input
   is held like a broker input's, never a stop (DEC-2821).
4. **What a restart loses.** The counts live only in the process. What they led to is on the
   stream, so a restart neither lifts nor repeats a restriction, but it starts counting again. An
   unreadable answer still stops the process (DEC-85), so it counts toward `degraded` only when
   later answers keep the process up.
5. **Out of scope** (on the backlog row):
   - **Robinhood:** its connector folds every account-snapshot error into one `Unreadable`, so a
     refused credential there neither counts as an authorization failure nor keeps the process up.
   - **No probe yet:** the scheduled health probe, so an idle executor with nothing to read still
     notices, and the quote feed's answers, which are not counted.
   - **Other signals:** headroom and contract drift; a failed later permission check, and a token's
     refresh failure or expiry, as suspending causes.
   - **E7-2y:** the recovery count (3 good probes) that leads to `condition_cleared`.
   - **ES-22:** journal spec §9.5's sentence that leaves this restriction to E7-2z is a protected
     path and goes in its own change.

## Consequences

- A broker that keeps losing answers, or refuses the credential, now restricts the account to
  closing and moves every agent to `exits_only`, with the owner told by `connection_unavailable`.
- A single `401` no longer settles an order as rejected. The order stays in doubt and is resolved
  by query once a credential works again.
- An executor that reads nothing (no order working) notices nothing until the probe lands.
