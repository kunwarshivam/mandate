## Question

E8-9 replaces the free-text `message_key` of `NotificationRef` in `mandate-runtime` and
`mandate-executor` with the closed notice kind of spec §3.2. The runtime emits one such alert:
`message_key: "decision_skipped"` (`crates/mandate-runtime/src/step.rs:538`), when the risk gate's dry
run denies a decision. Spec §10 counts it as "one runtime key". No row of §3.2's closed catalogue
has a dry-run deny as its cause, and no decision maps it. Today the alert reaches only the paper
tracer's report: no dispatcher exists yet, so no owner receives it.

## Options

- **(a) Map it to no kind.** A dry-run deny is a pull-only record: `DecisionMade` already journals
  the refusal, and the activity view and the next brief show it. This fits §3.1 ("an `info`
  notice: nothing the agent may do has changed") and the `ask_suppressed` precedent (DEC-195). The
  runtime stops emitting `Effect::Notify` for it, and spec §10's "one runtime key" becomes none.
  It removes an alert from the owner's push channels before any channel carries it.
- **(b) Add an `info` kind to §3.2,** for example `decision_refused`, with no text key: an `info`
  kind goes only to the pull channels and the next brief (§3.1), so nothing more is pushed. This
  changes the closed `NoticeKind` in `mandate-notify` (33 → 34) and DEC-720's `OwnerAlertSent`
  kind set, and needs a notifications spec and journal spec change.
- **(c) Reuse an existing kind.** Not recommended: no row's cause is a gate refusal (`risk_limit`
  needs a `RiskLimitTriggered`).

## Recommendation

(b), on reflection over the lead's first preference of (a). It keeps the refusal visible to the
owner as an attributed `info` notice, with the same reach as (a) (pull channels and the brief,
never a push), and removes no record the owner might rely on. (a) is simpler and leaves the record
in `DecisionMade`. Both add no trading risk, and neither pushes anything new.

## Interim (conservative, until the founder decides)

The runtime keeps emitting `decision_skipped` as it does today. E8-9 S3's tests pin neither
reading: they cover the other kinds and leave this one alert's mapping pending this decision.

## Rationale

Spec §10 names the alert and §3.2 does not catalogue it, so the code and the spec disagree. Under
`AGENTS.md` ("if code and docs disagree, stop and ask") and DEC-176, a reading that removes an
owner-facing alert loosens what the owner is told rather than tightening it, so it is the
founder's call.
