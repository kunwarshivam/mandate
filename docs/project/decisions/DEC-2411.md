# DEC-2411: A test cell's browser tries a cooling-off passkey, and the server decides

| | |
|---|---|
| **Status** | Accepted; amended by [DEC-2155](DEC-2155.md) (a second, staging flag beside this one) |
| **Date** | 2026-10-28 (UTC) |
| **Decided by** | The agent (lane W), with the coordinator's agreement, under DEC-79: a reversible engineering choice that only drops a client pre-check, never founder-reserved |
| **Story or claim** | E11-9 (the cell demo's step 2 from web/). Follows DEC-2146 |

## Decision

1. **A build flag, for test cells only.** `NEXT_PUBLIC_OWLHEAD_COOL_OFF_WAIVED=1` makes `web/`'s
   `usablePasskeys` admit a passkey still in its first 24 hours (DEC-2108 item 5). Any other value,
   or none, keeps today's pre-check, which holds the action in words and sends nothing.
2. **Only the local cell's Playwright config sets it**, on its `next dev`, to `1` only when the
   driver passes `OWLHEAD_CELL_COOL_OFF_WAIVED=1`, which it does exactly when the cell was started
   with `api.stepUpCoolOffWaiver: true` (DEC-2146), and to `0` otherwise, so a value exported in the
   runner's shell never reaches `next dev`. Two guards hold it there:
   - **In the build.** `web/next.config.ts` refuses anything but `next dev` (`NODE_ENV=development`)
     in which the flag is `1`, whatever set it: a shell, Workers Builds or GitHub variables, a
     `.env` file. `next build` inlines `NEXT_PUBLIC_*` into the client bundle under any `NODE_ENV`,
     so the guard allows the one environment the cell uses and refuses every other, an unforeseen
     one included.
   - **In the repository.** `web/src/test/cool-off-waiver-static.test.ts` fails if any tracked file
     other than the cell config, its one reader (`web/src/api/passkey.ts`), the build's refusal
     (`web/next.config.ts`, `web/src/lib/cool-off-build.ts`) and Markdown, or a `web/.env*` on disk,
     names the flag. It cannot see a build's own environment; the build guard covers that.
3. **It changes nothing else.** No new screen copy. The other refusals (no WebAuthn, no passkey)
   are unchanged. The server stays the only judge: where it does not waive the cool-off it answers
   `step_up_missing`, which the screens already show.

## Rationale

DEC-2146's waiver lives in the server's check 6 alone: its replies are unchanged, and
`GET /passkeys` still serves `cool_off_ends` 24 hours ahead (workspace API spec §3.6). `web/`
refuses a cooling-off passkey before it asks for a challenge, so without this flag a waived cell's
browser would still hold confirm, deploy, resume and Stop, and DEC-2146 could not be shown from
`web/`. A flag that only drops the pre-check adds no risk: a deployed build that somehow carried it
would still be refused by its server, as it is today when the pre-check and the server disagree.

## Alternatives

- **Serve the waiver on `GET /passkeys`** (a `cool_off_waived` member). Rejected for now: a schema
  and server change for a test-cell convenience, which DEC-2146 kept out of every reply on purpose.
- **Drop the pre-check everywhere.** Rejected: in a deployment the owner would be asked for a
  passkey the server is sure to refuse, instead of being told in words why the action waits.
