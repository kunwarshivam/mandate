## Context

The signal models and the liquidity check read daily bars from the workspace's store (DEC-846,
DEC-470 item 4). Only the local cell's data process has any: a recording of synthetic closes that
only dev and CI cells may list (DEC-2385 item 4). On a hosted cell the crossover agent therefore
has nothing to decide on. DEC-2385 item 7 left the real source to a later slice, read "over the
account's connection". The data process has no connection of its own, though, and a connection's
token is the executor's alone. The platform already holds one data-only paper key in the vault,
for news (DEC-2277).

## Decision

1. **A second source for the data process.** `mandate-datad` gets a source `alpaca-iex` beside the
   recording. It stores each instrument's US-equity `iex` daily bars, unadjusted, in the DEC-89
   layout under the root `alpaca-iex/`, through `Store::put_day`. Every reader and its trust check
   stay as they are (`mandate-bars`, DEC-2385 item 1). The recording becomes a fixture the chart
   refuses on any tier but `dev` and `ci`, by its own check, no longer only because no other tier
   lists instruments.
2. **One key for news and bars (founder, F2).** The data process reads the platform's data-only
   paper key, `platform/news-data-key`, as a new identity, `Identity::BarsReader` (role
   `bars-reader`), with read access to that path only. `policy::holders` gains one reader:

   | Secret | Read | Write | Delete |
   |---|---|---|---|
   | The platform data key | News reader, bars reader | Secret import | — |

   DEC-2277's guards carry over unchanged:
   - it is read once at start into memory, its `Debug` redacted, and its headers marked sensitive;
   - a key whose id does not begin `PK` is refused, with `NotPaper`;
   - the transport accepts only the data host's `/v2/stocks/bars` path.

   The key never reaches the environment, a chart value, a log, the journal, or any agent or
   runtime. Without it the process stores nothing new, so the trust check refuses the next session.
   The vault path keeps its name, so nothing already provisioned moves.
3. **The instruments.** These are the symbols of the latest `instrument_snapshot` registered on
   the control stream for each US-equity asset id, read as the runtime's composer reads them and
   as DEC-2280 item 1 bounds the news reader. The executor refuses any instrument without a
   registered snapshot, so this covers every pinned and working-universe instrument. The process
   gets a read-only journal role over the control stream and the registrations' artifacts, and
   appends nothing.
4. **Settled sessions only, never a guess.**
   - A session's bar is stored only once that date's last calendar session span, extended hours
     included, has ended plus 15 minutes (`SETTLE`).
   - A day the vendor answers with no bar is stored as fetched and empty. The trust check then
     refuses the span until that day leaves it.
   - Nothing is filled in, carried forward or adjusted.
   - A refetch of a stored day that differs is refused as `put_day` refuses it, logged as
     `bar_revised` with no symbol or price, and the process goes on.
   - Between a session's regular close and its settle time, and after any such gap, there are no
     closes, so there is no signal (MI-10).
5. **Batched and paced.** One request asks every instrument due for a day (`symbols=` with several
   symbols, split by symbol on receipt), through the E2-1 client's pacing: 200 a minute, `429` waits
   for the window, server errors back off. A first start asks 30 requests, one a session of the
   span, whatever the instrument count; after that, one a settled session. This answers
   E7-2zq's lesson for bars.
6. **Closes object.** After each store the process puts each instrument's trusted closes object,
   with source `alpaca_iex_daily_bars` (DEC-846 item 3), byte for byte what the composer derives.
   The runtime's `ObservationRecorded` then names an object that is there (DEC-2385 item 5). The
   composer wires the signal models for an `alpaca-iex` root as it does for the recording's root.
7. **Liquidity.** The executor's daily figures come from the same root and trust check. Its
   trailing five minutes of volume are read at gate time over the workspace's own connection
   (`recent_minute_bars`), as the shell's paper path already reads them. The data process stores
   no minute bars, because a stored day is never rewritten and the current day's minutes grow. An
   empty or unread window refuses the opening, as it does today.
8. **Order of work.** Each piece lands separately, tests first. The connector and the readers are
   safety-critical.
   1. This spec and decision.
   2. The multi-symbol fetch in `mandate-marketdata`.
   3. The data process's source, the composer's root, and the executor's trailing minutes.
   4. The vault identity, its provisioning, and the chart's `data.source`, with lane IAC.
9. **Other workspaces may use it (founder, F1, a compliance risk accepted).** The bars are served
   to every workspace's data process, customers' included, not only the founder's own.
   - **The risk, plainly:** IEX bars fetched with one platform key and served to many workspaces
     are likely redistribution under Alpaca's market-data terms. That holds until a data license
     is recorded, or until each workspace fetches with its own data key.
   - This is an exception to data-plane spec item 3, §1.3, and DP-11, for these stored IEX bars
     alone.
   - Quotes, marks, news to other workspaces, and every other datum stay as they were: the shared
     plane holds no market data, and nothing else is widened on this decision's strength.
   - Backlog row E2-20 obtains the license, or moves each workspace onto its own data key.

## Consequences

- A hosted cell's crossover agent decides on real IEX daily closes. They are IEX's prints only, so
  thin names may have days with no bar, which hold the signal (item 4). IEX volume understates
  consolidated volume, which errs toward the tighter liquidity limit (DEC-470 item 4).
- Every workspace shares one key's request budget. A first start costs 30 requests; steady state
  is one request a settled session for all instruments. A `429` delays storing and adds no risk.
- One wrong daily close can drive one signal until it leaves the slow window. The signal is an
  opinion, sized and admitted by deterministic code under the owner's caps (rule 4).
- Founder steps (lane IAC relays, DEC-79):
  1. Confirm `ALPACA_NEWS_KEY_ID` and `ALPACA_NEWS_SECRET` are set in `infra-staging`.
  2. Run the infra apply once the bars-reader AppRole lands.
  3. Set the staging cell's `images.data` and `data.source: alpaca-iex`.
