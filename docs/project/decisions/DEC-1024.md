# DEC-1024: The cell runs the workspace API server on its pod's loopback, with a session key made in pod memory at each start

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and DEC-176. It exposes the API to nothing new, stores no key at rest, and weakens no safety rule) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (lane A1, claim [#1444](https://github.com/kunwarshivam/mandate/issues/1444)) |
| **Story or claim** | E21-31; [workspace API spec](../../specs/workspace-api.md) §3.11 items 1, 2 and 7; [DEC-978](DEC-978.md); [DEC-1023](DEC-1023.md); infrastructure design §3.1 |

## Context

The workspace chart (E21-36) had no process for the API server, so `cargo xtask cell demo` could
not serve `/v1`. Running it in the cell needs four choices that the spec leaves to the deployment:
- where it listens;
- where its session signing key comes from;
- how its subject links reach the fixed path;
- which workspace it hosts in the local cell.

The cell's one ingress, cloudflared, has no route to it yet. The chart renders no Service, and
`deploy/tests/test_cell.py` refuses any.

## Decision

1. **Loopback only.** In the chart and the Compose file, `--bind` and `--probe-bind` are
   `127.0.0.1:8080` and `127.0.0.1:8081`, which §3.11 item 1 allows. No pod or node reaches the
   server, and it has no ingress policy. The local demo reaches it with `kubectl port-forward`. The
   tunnel's route to it, and probes the orchestrator can read, are a later change, which revisits
   this item.
2. **The session signing key lives in pod memory.**
   - An init container writes 32 random bytes, owner-only (`umask 077`), into a memory-backed
     `emptyDir`. That directory is the server's `CREDENTIALS_DIRECTORY`, mounted read-only into the
     server.
   - The key never exists at rest or outside the pod, and the chart holds no Secret for it.
   - Sessions live in the one replica's memory too (item 6), so a restart that makes a new key
     loses nothing the restart did not already lose.
   - When sessions move to Postgres, the key must outlive the pod. That change supersedes this
     item.
   - The Compose file has no init step, so there the key is a secret file the host provides (mode
     0600).
3. **Subject links are an operator's ConfigMap.**
   - `api.subjectLinks` names a ConfigMap whose `subject-links` key is mounted read-only, mode
     0444, at `/etc/mandate/subject-links` (DEC-1023). The mounted file is owned by root and
     writable by nobody, which the reader's checks accept.
   - With no ConfigMap named, nothing is mounted, the file is absent, and every sign-in is refused.
   - The local cell names none until lane SI's stub issuer (DEC-2100) can sign a token for a
     linked subject.
4. **The demo workspace is a ULID.** The API server hosts one workspace by ULID
   (`MANDATE_API_WORKSPACE`). So `cargo xtask cell demo` opens `01KDEM0000000000000000000W`, the
   workspace the local cell's `api.workspace` names, instead of `demo`. A test checks that the two
   agree.
5. **Settings are values, checked at render time.**
   - The chart's `api` block holds the issuer, audience, key-set URL, app origin, organization,
     workspace and tier.
   - Each is required once `images.api` is named.
   - The schema refuses a non-ULID id, a tier outside `dev`, `ci`, `staging` and `production`, and
     an `http` key-set URL that is not loopback.
   - None is a secret.
6. **The interim image carries TLS roots.** The local `api` image is the static binary on an empty
   base, plus a CA bundle found on the building host (`SSL_CERT_FILE`, else the usual Debian, Fedora,
   openSUSE or Alpine path), placed at `/etc/ssl/certs/ca-certificates.crt`.
   - Without roots, the server cannot build its key-set client and refuses to start, even for the
     loopback `http` stub issuer. That fail-closed refusal is correct, so the image changes and the
     server does not.
   - Lane R2's signed API image must carry roots too.

## Rationale

- **Item 1** gives the cell the server's process without deciding the tunnel's routing: a Service,
  a cloudflared sidecar, or a fixed pod address are each a design choice of their own. Until then
  the server is reachable from nowhere, which adds no exposure.
- **Item 2** keeps a credential out of the chart, the values and the cluster's Secrets altogether,
  and matches what the server's in-memory sessions already imply.

## Alternatives considered

- **A Secret holding the session key.** It would need an operator step and a key at rest, for no
  gain while sessions die with the pod.
- **Binding to the pod's address.** It needs an ingress policy and a caller, and the cell has
  neither yet.
- **Mounting the subject links from a Secret.** They hold digests and principal ids, not
  credentials. A ConfigMap states that, and is just as read-only.
