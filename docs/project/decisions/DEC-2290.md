## Context

The reader asks the vendor from the news stream's last `knowledge_at` (journal spec §9.37).
`knowledge_at` is a receipt time. So an item the vendor indexes late, with a publication time before
that instant, is never fetched. DEC-2281 item 3 recorded it as a limit. The same review asked that
`future_dated` refusals be counted, and that §9.37 say what of the stream never starts a run.

## Decision

1. **A round asks from `POLL_OVERLAP_S` (15 minutes) before the stream's last `knowledge_at`.**
   An empty stream still asks from 48 hours back (DEC-1130 item 5).
   - Rule 284's `item_id` dedupe makes the overlap safe. An item the stream holds, fetched again, is
     counted as `held` and never stored twice.
   - A late item that is fetched is known at its receipt. That is never before what the stream
     already knew (rule 285), so the overlap moves no `knowledge_at` back.
   - An item indexed more than 15 minutes late is still not fetched. That limit stays, narrowed.
2. **`future_dated` refusals are counted.** They are already counted in the reader's
   `Counts::refused`, by the parser's code (`tests/reader.rs`). No change is needed.
3. **§9.37 discloses what never starts a run.**
   - An item with no ticker or more than 32 is never stored, so it never starts a run, even when one
     of its tickers carries an active thesis.
   - A run's own trimmed read (`news_get`) of a stored item journals its own
     `ObservationRecorded`, whose `data_ref` is that read's record. Rule 271 counts only an event
     run's cause, so that observation neither starts a run nor counts as one.
4. **Order of changes.** The spec change (journal spec v0.114) lands first. The reader's change
   follows in its own PR (spec guard), stacked on DEC-2289's.

## Rationale

Fifteen minutes covers the vendor's usual indexing delay at a small cost. Each round re-fetches at
most 15 minutes of items, which the page cap already bounds, and the dedupe discards them. A longer
overlap would cost more re-fetches for items rarely that late. Missing a late item adds no risk:
news reaches only a `monitor` run, which can only invalidate (DEC-2392 item 3).

## Alternatives considered

- **No overlap:** the limit DEC-2281 recorded.
- **An overlap as long as the first poll's 48 hours:** every round would re-fetch two days of items.
- **Deduplicating by publication time instead of `item_id`:** rule 284 already dedupes by
  `item_id`, which is the vendor's id and version, so a later version is its own item.
