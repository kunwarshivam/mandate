## Context

`mandate-connections` holds the start's rules (`plan_start`, `connect_digest`, `PendingStates`),
and no route uses them. Three things it fixes do not fit a deployment other than production: the
redirect URI is a constant on `api.owlhead.ai`, while staging's API is `api-staging.owlhead.ai`
(DEC-2057) and the cell's fixture provider redirects to loopback; the `state`'s binding does not
name the pending connection, so the callback could not tell which connection's vault entry the code
belongs to; and nothing drops a `state` that is never redeemed. The spec does not say how the
route answers each of `plan_start`'s refusals.

## Decision

1. **The route.** `POST /v1/workspaces/{ws}/connections/oauth/start`, body
   `commands/oauth-start-request`: `broker` (`alpaca`), `environment` (`paper` | `live`),
   `disclosure` (`{document, version}`, DEC-2621 item 4), and `step_up` (§3.6's evidence or
   `null`). It answers `201` with `commands/oauth-start-response`: `authorization_url`,
   `expires_at`, and `connection_id`, so the web app can follow the connection in `GET
   /connections/{id}` (DEC-2620).
2. **The redirect URI is the deployment's.** `RedirectUri` accepts an `https` origin, or `http` on
   `localhost`, `127.0.0.1`, or `[::1]` for the cell's fixture provider, followed by exactly
   `/v1/oauth/alpaca/callback`, with no user information, query, fragment, or other path, a
   lowercase DNS host, and a port from 1 to 65535 if any. `OAuthClient` pairs it with the client id.
   The start's authorization URL and the token exchange send the same one (RFC 6749 §4.1.3).
   Production's is `RedirectUri::production()`; each deployment registers its own with the broker
   (connections spec §13 question 5). Both are API settings, not secrets.
3. **The binding names the connection.** `Binding` carries the pending `connection_id`, so the
   callback writes the code under that connection's vault entry and no other.
4. **Where the `state` is held.** In the API process's memory, in `PendingStates`, for its
   600-second lifetime (connections spec §5.2 step 1), and dropped by `prune` at each start once
   expired. The cell's chart runs one API replica. A restart drops every pending `state`: the
   callback then refuses it, and the deadline's teardown closes the open request, as connections
   spec §5.2 step 6 already says. Before the API runs more than one replica, the `state` needs a
   store the replicas share; the backlog records it.
5. **The ids.** The `connection_id` (`conn_` and a ULID) and the `account_ref` (a ULID) are derived
   from the request's idempotency key, as §3.4 derives event ids, so a retry names the same pending
   connection.
6. **The order and the codes** (one code per response, §3.5):
   1. session, CSRF mark, key, and body, as every write checks them (§3.4); a broker other than
      `alpaca` is `invalid` at `/broker`;
   2. authorization: the `BrokerConnection` permission of identity spec §5; a `live` workspace is
      `live_unavailable`;
   3. a disclosure other than the current version of `alpaca_oauth_token_breadth` is `invalid` at
      `/disclosure` (DEC-2621 item 4);
   4. the step-up, judged for the connect digest with that disclosure: §3.5's step-up codes;
   5. `plan_start`, in DEC-883's order after step-up: `live` is `live_unavailable`; a control-stream
      fold that cannot answer is `journal_unavailable`; a request already open, an establishment,
      or a used `account_ref` for the derived ids is `idempotency_conflict`, since only a key reused
      for another request can reach them.

   A refused start appends nothing, so no step-up is spent (journal spec §9.8).
7. **The commit.** `ConnectionRequested` version 2 (DEC-2621 item 1), `credential` `oauth`, with the
   step-up as evidence, appended on the control stream as §3.4's writes are. Then the `state` and
   PKCE verifier are drawn from the operating system's random source, 32 bytes each, base64url
   without padding, the challenge is the S256 of the verifier, and the `state` is issued.
8. **A retry.** The same key and body, while the `state` is held and unredeemed, answers the same
   `201`. Once it is redeemed or expired, the key's start is spent: `idempotency_conflict`, and the
   owner starts again under a new key.
9. **Not offered.** A deployment whose settings name no OAuth client answers the route `not_found`:
   it offers no connect.

## Rationale

Each value that differs by deployment is a setting with a checked form, so no deployment can send
the browser, or the code, anywhere but its own API's callback. Deriving the ids from the key makes a
retry land on the same pending connection, and a spent `state` is never re-issued for it, so one
request never has two codes. Holding the `state` in memory keeps the code, the verifier, and the
`state` out of every store, and a restart fails closed.

## Alternatives considered

- **Keep the redirect URI a constant and register production's for staging too.** Alpaca would
  then send staging's codes to production's API.
- **Store the `state` in the journal or a database.** It would put a value that redeems a code
  into a durable store, for a ten-minute lifetime and one replica.
- **Re-issue a new `state` on a retry after expiry.** One request could then hold two codes.
