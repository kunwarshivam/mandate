## Decision

1. **Ports.** `mandate-paper` is a library whose `run` takes the process's three effects as a
   `Ports` value: the workspace control stream's records, read once; the paper credentials and the
   one transport (`connect`), called at most once and only after every check that needs no
   credential; and the clock and timer (`Pause`), whose `now` is the run's one clock read and the
   binding gate's clock. The binary supplies the Postgres reader, `Credentials::from_env` with
   `AlpacaPaperHttp`, and `TokioPause`; tests script all three. Nothing else reaches the process:
   no file but the store and the stored bars, and no environment variable but the host refusal's.
2. **Where the host's closes come from.** The closes handed to `mandate_modelhost::evaluate` are
   read by the shell's existing trust check over the stored daily bars, the one `liquidity_facts`
   uses, through a new `mandate_shell::paper::daily_closes` that returns each close with its
   session. The paper adapter has no second reader of the dataset, so the closes the host sees and
   the liquidity facts the gate sees are one trusted span. Part 2 of the tests adds its stub.
3. **The observation's data.** The adapter stores exactly the closes it handed the host, the full
   span `daily_closes` returns and not a trailing window of it, as the
   canonical JSON object `{"closes":[["<session date>","<close>"],…],"instrument_id":"<asset id>"}`,
   oldest first, the close in canonical decimal text and the asset id the mandate pins (the shape
   H3's tests store). It puts the bytes in the deployment's `mandate-artifacts-fs` store (write,
   fsync, hard link) and only then hands `ProductionCycle::run_observed` the observation whose
   `data_ref` is their digest, with source `alpaca_iex_daily_bars` and `as_of` the host's output's
   `as_of` (DEC-503 items 5 and 6, journal spec §9.1, §11 check 6). A `Flat` or `Undecided` run
   stores nothing.
4. **No mandate file.** The production stages still take the mandate as a path. The adapter passes
   the stored document's own content-addressed path in the store (`object_path` of the deployed
   version), which E19-11's phase 1 has just re-hashed, never a file the founder names (FT-3).
5. **Order of a run.** The host is evaluated after the GET-only preflight and E19-11's phase 2, so a
   "no output" report is only ever given for a deployment that every V-rule, V-002 on the broker's
   equity included, accepts. The brief's order holds around it: every FT-3 check before the
   credential read, V-002 after the preflight and before any decision.
6. **The journal on a dry run.** `--journal` names the Postgres journal the control stream is read
   from. Only a run with `--place-one-order` hands that DSN to the cycle; a dry run's cycle appends
   to a scratch in-memory journal (DEC-157 item 6). `None` in `Args` is the scratch journal for
   both, which only tests construct: the argument parser (part 2) requires `--journal` with
   `--place-one-order`, refuses a flag given twice, and never echoes a value, since the DSN may
   hold a password (`AGENTS.md` rule 7).
7. **The tests PR is two parts** (ES-13's 400 lines). Part 1, this PR: the crate, the founder-owned
   layer, CODEOWNERS and workspace entries, the `run` API, the harness, and the pending tests for
   FT-1, FT-4 and FT-6. Part 2: the refusals before any credential (FT-3, FT-10), the argument
   parser and its stub (no mandate, configuration, output or host argument), two equities that
   differ only in journaled inputs (FT-2), a held position (FT-7), untrusted bars (FT-8), the
   closing window (FT-9), the `daily_closes` stub, and a dry run given a journal DSN that hands
   the cycle none (item 6). Part 3: the pending tests that call `daily_closes` directly (the full
   span, its order, and untrusted bars refused). The binary's `main`, which holds no logic,
   lands with the implementation PR.
8. **Shared fixtures.** The tests reuse `mandate-shell`'s `tests/common` module and recorded broker
   answers by path rather than copying them, so the SPY deployment the paper adapter is tested on
   is the one the shell's Q1 and H3 tests deploy.

## Rationale

Each item fills a gap the brief leaves to the slice, and each picks the reading that adds no
risk: one credential read after every credential-free check, one trusted dataset reader, the
observation's data stored before the record that names it, the stored document rather than a file,
and no journal for a run that places nothing. No limit, rule or safety invariant changes.

## Alternatives considered

- **The adapter reads the dataset itself for the host.** Rejected: a second reader could admit
  bars the shell's trust check refuses, and the host and the gate would see different spans.
- **The host before the credentials.** It needs no credential, but its "no output" report would
  then be shown for a deployment V-002 may refuse; the brief orders V-002 before any decision.
- **The adapter writes the stored document to a temporary mandate file.** Rejected: a second copy
  the stages read, which could differ from the version phase 1 re-hashed.
