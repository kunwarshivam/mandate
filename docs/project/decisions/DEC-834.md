# DEC-834: Whether route 2's rate limits may exempt a member who holds a valid key

## Decision

The question the founder decided: DEC-816 item 6 rate-limits both route-2 routes per address and per device. A
sustained flood from the member's own address and device can hold both limits and deny the member
route 2, the kill switch's and pause's path during an identity-provider outage, for as long as the
flood lasts. Another network or device and, on hybrid and on-prem deployments, the host CLI
(route 3) remain, and route 1 once the identity provider is back. Should the limits change so that a member who holds a valid key gets through?

1. **Interim until the decision (superseded by item 2):** the limits as DEC-816 item 6 writes
   them, with the residual stated.
2. **Decided (the founder chose this option):**
   - The assertion route verifies a signature only against an outstanding challenge it issued. It
     consumes every presented challenge on first presentation, whether the assertion verifies or
     not, so verification work is bounded by the challenge limit.
   - The assertion route's limit counts failed assertions only. An assertion that verifies against
     an outstanding challenge is never refused for a limit.
   - The challenge route's limit counts a challenge only while it is outstanding.
   - Over a limit, a failure is still the same 401 `unauthenticated` (DEC-816 item 6).
   - Even then, an attacker who requests a new challenge whenever a slot frees can keep the
     challenge route's limit full while the flood lasts. The option narrows the residual but does
     not remove it. Closing it fully needs a path not keyed on address or device alone, for example
     a per-credential challenge budget, which would need the client to name a credential before
     verification and so touches DEC-816 item 6's "nothing is enumerable".
   - Tests owed to E9-1:
     - `a_verified_assertion_is_never_refused_for_a_rate_limit`;
     - `over_limit_requests_verify_only_against_an_outstanding_challenge_consumed_on_first_use`.

## Rationale

Rule 13 says the kill switch is always available. Route 2 is its path during an identity-provider
outage, and an unauthenticated route needs rate limits. Every option trades one against the
other: counting every request lets an attacker on the member's network lock them out; exempting
verified traffic costs signature verification under flood unless it is bounded by outstanding
challenges; a per-credential budget leaks which credentials exist unless designed carefully. That
trade is the founder's under DEC-79.

## Alternatives considered

- **Exempt route 2 from rate limits.** Not recommended: unlimited assertion verification on an
  unauthenticated route is a cheap denial of service against the deployment.
- **Keep DEC-816 item 6 as written and only disclose the residual.** This was the interim, superseded by item 2.
- **A per-credential challenge budget.** Closes the residual, but the client must name a
  credential before verification; it needs its own design so that the budget is no oracle.
