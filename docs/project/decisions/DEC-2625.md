## Context

The connect flow sends the owner's browser to Alpaca's authorization page and has the
token-exchange process redeem the code at Alpaca's token endpoint. Agents never reach Alpaca
(`AGENTS.md` rule 8), and a dev or CI cell has no registered Alpaca OAuth client, so the flow needs
a provider that answers as Alpaca's does, for the cell and for tests. The stub issuer (DEC-2100) is
already the cell's stand-in for an external provider, with the gates such a stand-in needs: debug
builds only, the `dev` and `ci` tiers only, loopback only, its own `Host` only, and no state across
restarts.

## Decision

1. **Where.** A module `alpaca` in `mandate-stub-issuer`, compiled only with debug assertions, like
   `issuer` and `serve` (DEC-2100 item 2). It is served only when started with all three of
   `--alpaca-client-id`, `--alpaca-client-secret-file`, and `--alpaca-redirect-uri`; with none,
   its routes answer 404 as any other path does; with some but not all, the stub refuses to start.
2. **Settings.** The client id; the client secret, read from a regular file only its owner can read
   or write (no group or other bits), never from an environment variable or an argument; and the
   exact registered redirect URI, which must pass `RedirectUri::parse` (DEC-2623 item 2: `https`,
   or `http` on a loopback host, exactly `/v1/oauth/alpaca/callback`, no user information, query,
   or fragment), or the stub refuses to start. Requests must then carry it byte for byte.
3. **`GET /alpaca/oauth/authorize`.** It requires exactly the parameters connections spec §5.2 step 2
   names, each once: `response_type=code`, the client id, the registered `redirect_uri`, a
   non-empty `state`, a `code_challenge` with `code_challenge_method=S256`, `scope` exactly
   `trading data` (as `start::REQUESTED_SCOPES` sends it), and `env=paper`. It answers `302` to the
   redirect URI with `code` and `state`, with no consent page. Any other request is `400` with
   `{"error":"invalid_request"}` and no `Location`: it never redirects anywhere on a refusal.
4. **`POST /alpaca/oauth/token`** (`application/x-www-form-urlencoded`): exactly `grant_type`
   (`authorization_code`), `code`, `client_id`, `client_secret`, `redirect_uri`, and
   `code_verifier`, each once. A code is taken out of the store when it is first presented, so a
   code that was tried is spent whatever the answer. It answers `200` with
   `{"access_token":<token>,"scope":"trading data","token_type":"bearer"}` and `Cache-Control:
   no-store` only when the client id and secret are the configured ones (the secret compared in
   constant time), the code was issued less than 600 seconds before (connections spec §5.5) to the
   same client and redirect URI, and the S256 of the verifier is the code's challenge (RFC 7636).
   Otherwise `400` with RFC 6749 §5.2's `invalid_request` (a malformed form), `invalid_client`
   (the client id or secret), or `invalid_grant` (the code, its expiry, its redirect URI, or the
   verifier).
5. **What it holds.** Codes and tokens are 32 bytes from the operating system's random source,
   base64url without padding, so each is in DEC-2624's token alphabet. Codes live in memory only,
   at most 4,096; an expired one is dropped before a new one is refused, and a full store answers
   `503` `temporarily_unavailable`. Tokens are not kept: the fixture broker, not this provider,
   serves the account. Nothing is logged.
6. **Amends DEC-2100.** Item 7's routes gain these two, under the same `Host` and HTTP/1.1 checks
   and with no CORS header. Item 11 gains: it issues no refresh token and no ID token here either,
   and its OAuth tokens authorize nothing but the cell's fixture broker.

## Rationale

The provider is a stand-in that stays: the cell and the tests need it for as long as the connect
flow exists, and no real Alpaca client may run there. Putting it behind the stub issuer's gates
gives it, without new code, every property a stand-in must have. Refusing exactly what Alpaca's
documentation would not accept, and redirecting only to the one registered URI, keeps the flow it
tests the flow production runs.

## Alternatives considered

- **A crate and image of its own.** Another binary, image, and chart entry with the same gates.
- **Mock the token endpoint inside each test.** The browser half of the flow, and the cell's
  end-to-end run, would have nothing to talk to.
