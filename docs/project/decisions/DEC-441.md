|---|---|

| **Date** | 2026-10-03 |
| **Decided by** | The agent drafting the connections spec (`claude-code`), under DEC-79 and DEC-176 for items 1 to 14; items 15 to 20 involve vendor terms, live accounts, or legal text and are the founder's |

## Decision

The [connections spec](../../specs/connections.md) v0.1 is a draft. Items 1 to 14 each tighten a
rule or resolve a gap by the reading that adds no risk (DEC-176). Items 15 to 20 stay Proposed;
work continues on the conservative option each names.

1. **Precedence.** The connections spec adds no risk-gate rule. Where it overlaps the trading
   domain, mandate, or journal spec, those win.
2. **References only.** A connection is a reference: opaque id, broker, environment, scopes,
   account reference, and a keyed account fingerprint. The credential lives only in the vault and
   in the one executor using it (CN-1).
3. **Alpaca API keys are paper only.** Alpaca keys cannot be narrowed or have their permissions
   read, so no live key can be shown to lack fund-movement rights. Live Alpaca is OAuth only.
4. **A live credential whose fund-movement permission cannot be shown absent is refused.** This
   tightens infrastructure §5.3, which recorded and disclosed the limit; that sentence is amended in
   the same change. Paper and demo keys keep the record-and-disclose reading.
5. **Alpaca scopes are `trading` and `data` only,** never `account:write`; a grant that differs
   from the request is refused. U-A1 to U-A5 are confirmed from Alpaca's documentation before M8
   builds.
6. **One connection per broker account per environment in a deployment,** found by a keyed
   fingerprint; a second is refused. A reconnect of the same account reuses its `connection_id`,
   `account_ref`, stream, and loss carry, so revoking and reconnecting cannot reset V-032.
7. **Connection states** `connecting`, `active`, `degraded`, `suspended`, `revoked`. `degraded`
   and `suspended` set the existing account state `closing_only` (trading §7.3, reason
   `account_restricted`), the most restrictive opening block that never holds an exit, journaled
   as `AccountRestrictionChanged` and `AgentModeApplied` before the executor acts; it lifts on the
   owner's acknowledgment with the account refreshed. A dedicated connection restriction that
   lifts on its own is a separate spec-first change (ES-22; E7-13). Exits continue while any call
   succeeds (rule 13). (Amended in round 1 of #563: v0.1 named a `connection_degraded`
   restriction that no spec defines, which would have failed open.)
8. **Broker MCP hardening.** The connector calls only an allowlist of tools pinned by a contract
   hash; tool metadata, descriptions, and error text reach no model, prompt, notification, or
   journal text; contract drift halts openings; the host is pinned and redirects refused.
9. **Data minimization.** Data about any account other than the connected one is dropped inside
   the connector before redaction, hashing, or storage.
10. **No Robinhood order path without idempotency.** If Robinhood's tools do not accept a client
    order id with idempotent retry and query by it (U-R1, U-R2), E7-6's order path is not built and
    the question returns to the founder. Journal before acting cannot be made crash-safe otherwise.
11. **No live Robinhood call by any agent.** Robinhood has no test environment, so every agent test
    uses fixtures synthesized from the published contract and the simulated broker with Robinhood's
    rules (DEC-124); `AGENTS.md` rule 8.
12. **Switching connection is a new agent.** V-031 stands; the new agent starts with that
    connection's loss carry.
13. **Backlog.** E7-6 refined; E7-11 to E7-18 added under E7, tests first (DEC-77).
14. **Health defaults** (Proposed values, reversible): a probe every 60 seconds while deployed;
    3 network errors `degraded`; 2 authorization failures `suspended`; 3 good probes recover;
    rate-limit headroom under 20% `degraded`. The probe draws from the read budget, never the
    reserved exit budget; contract drift alerts the owner at once.
21. **A token that reaches both paper and live is refused** for either kind of connection until
    Alpaca's documentation shows tokens are bound to one environment (U-A4), and the other
    environment's host is never probed to find out (CN-3). Accepted as a tightening (DEC-176).

**Proposed for the founder:**

15. **Robinhood platform terms.** Whether one platform may act for many customers, data use, and
    attribution (OD-12, ADR-0002 "Monitor"). *Recommendation:* get Robinhood's written answer before
    E7-6 builds; no Robinhood connection in any environment until then.
16. **Robinhood fixtures.** *Recommendation:* synthesize them from the published tool contract. Any
    recording from a real account is the founder's own act, on the founder's own account, after counsel signs
    off (DEC-98).
17. **Robinhood equity protection without OCO or bracket.** Trading spec §5.4 requires OCO or
    bracket legs for equities. *Recommendation:* if Robinhood offers a resting GTC stop-limit but no
    OCO, accept one stop-limit for the whole position, as crypto does (DEC-36); if it offers no
    resting stop, no protected equity mandate deploys on Robinhood.
18. **Alpaca OAuth app registration** and its terms. *Recommendation:* register at M8 after the
    founder reads Alpaca's app terms; no registration before.
19. **Account-holder verification.** *Recommendation:* no name matching in v1 (it would process
    more personal data); the owner attests ownership with step-up; counsel confirms.
20. **Robinhood disclosures**: the customer-responsibility statement and that the token can read
    every Robinhood account of the customer. *Recommendation:* counsel drafts the text (compliance
    question 32) before any Robinhood connection.

22. **(Proposed) If item 21 blocks Alpaca OAuth entirely** because every token reaches both
    environments. *Recommendation* (the round-1 reviewer's): accept such a token with the executor
    bound to its own environment's host, no live host compiled outside production (ES-23), egress
    limited to that host, and the token's breadth journaled with the connection and disclosed to the
    owner. This loosens item 21, so it is the founder's.

## Rationale

Broker connections are where a mistake moves real money, so every reading takes the side that
holds fewer permissions and stops openings sooner, while leaving risk reduction alone (rules 3, 7,
8, 12, 13). Items 3 and 4 close a gap between HLD §6 A, which assumes key permissions can be read,
and Alpaca, whose keys cannot be read. Item 6 closes a loophole the mandate spec's per-connection
loss carry would otherwise leave open. Items 8 to 11 answer ADR-0002's top risk (prompt injection)
and OD-12's unknowns without guessing. Items 15 to 20 are vendor terms, live accounts, or legal
text, which DEC-79 reserves.

## Alternatives considered

- Accept live Alpaca API keys with a disclosure: rejected, since HLD §6 A promises the platform never
  holds a fund-moving permission.
- Give a reconnect a new `connection_id` and inherit the carry by fingerprint: equivalent in effect,
  but it changes mandate spec §5.7's computation; reusing the id changes nothing there.
- Build the Robinhood connector now with order matching by instrument, side, quantity, and time
  instead of a client order id: rejected as unsafe after a crash (duplicates possible).
- Let tool descriptions inform an LLM-based connector: rejected (rule 4, CN-9).
