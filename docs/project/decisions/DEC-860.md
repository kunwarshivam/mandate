# DEC-860: The Robinhood connector's `ref_id`, tool seam, state spelling and place readings (C1)

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The E7-6 C1 builder (Claude Code), under DEC-79 and DEC-176: each item fixes a value the brief or the spec leaves open, or takes the reading that adds no risk, and none loosens a rule |
| **Story or claim** | E7-6, the [first live trade brief](../tasks/first-live-trade.md)'s C1; connections spec §6.2; DEC-529 item 4; DEC-849 item 4 |

## Decision

1. **`ref_id`.** The brief fixes "a UUID version 8 from SHA-256 of the intent's idempotency key".
   Exactly: SHA-256 (`mandate-canon`) over the UTF-8 bytes of the `ClientOrderId` text
   (`md-<intent>`, and its protective and rung forms alike); the first 16 bytes; the version
   nibble set to 8 and the variant bits to `10` (RFC 9562 §5.8); lower-case 8-4-4-4-12 text.
2. **The tool seam.** The connector is generic over `Tools`, one `tools/call`. In production it
   is `McpClient` (allowlist, pin, drift halt), adapted with the runner (G1a) or after DEC-849
   item 4; the tests use `mandate-rh-sim` over loopback through the wire format (DEC-849 item 2).
3. **State spelling.** `BrokerOrder.status` carries the spelling the executor's §5.7 table reads,
   as the connector maps `gfd` to `day` (DEC-630 item 5): `new`, `queued`, `confirmed` and
   `unconfirmed` are `accepted`; `partially_filled` and `filled` are themselves; `cancelled` and
   `voided` are `canceled`; `rejected` and `failed` are `rejected`. Any other value is unmapped.
   §6.2's one re-read by `order_id` of a `rejected`, `failed` or `voided` order before its
   intent closes is C3's; the live run is gated on it.
4. **What a place answer is.** Only a tool result without `isError` whose `structuredContent`
   is an order record with an `id`, a mapped `state` and decimal-text numbers is an answer.
   Anything else to a place, an `isError` result included, is `ConnectorError::Unknown`, never
   `Rejected`: the contract publishes no error shapes, so an error may follow a created order
   (DEC-529 items 4 and 6). A connector never places one `ref_id` twice; a second `Submit` of an
   order in doubt is `Unknown` with nothing called. An `Unknown` protective or exit order is
   escalated to the owner by a prompt (C3), never left silent.
5. **The profile.** Version 1, one row (US equities, regular session), as trading spec §5.2
   reads: `market` whole, fractional and notional; `limit`, `stop` and `stop_limit` whole only;
   `day` and `gtc` in every cell, the spec stating no narrower set; the whole-share stop-limit
   the one protective form; `ref_id` sent, `retry` `unknown`, no query by it.
6. **Call classes.** An opening's or an increase's review and place draw on `Ordinary`; every
   other purpose's calls, and every cancel, on `RiskReducing`, so a drift halt in `McpClient`
   holds openings only (`AGENTS.md` rule 13).
7. **Refused before any call.** A `Submit` the profile does not offer (a bracket, an OCO,
   extended hours, `ioc`) is `NotSent`. `Cancel` carries only our `ClientOrderId`, so:
   - the broker `order_id` of every place answer is journaled, and the connector's
     `ClientOrderId` → `order_id` map is rebuilt from the journal at start, never held only in
     memory, so a cancel after a restart, the kill switch's order-by-order ones included, finds
     its order;
   - a cancel with no recoverable `order_id` is never dropped: it is `NotSent`
     (`no_order_id`), which the shell stops and alerts the owner on (DEC-85); the order stays
     live in the executor's view, never assumed cancelled, and the connector never cancels or
     adopts by guess (CN-7);
   - owed, and gating the live run: a journal spec field for the `order_id` if one is needed
     (its own journal-spec PR), and the rebuild with its test,
     `a_cancel_after_a_restart_finds_its_order_id_from_the_journal` (C1 part 3 or C3), beside
     C3's list-and-match.

## Rationale

Items 1, 3, 5 and 6 spell out what the brief and the spec name; item 2 keeps `mandate-mcp`'s
refusal of plain `http`. Items 4 and 7 add no risk: a false `Unknown` blocks an instrument until
the founder looks, a false `Rejected` could let a second order out, and a cancel that cannot
find its order is escalated, never dropped (`AGENTS.md` rule 13).

## Alternatives considered

`isError` read as `Rejected`; a test seam in `mandate-mcp` (the founder's, DEC-849 item 4).
