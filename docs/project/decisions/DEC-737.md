## Decision

1. **The mandate version is its own read, in an interim shape.** `GET /mandate-versions/{hash}`
   (spec §4.1) supplies the agent's `mandate` and `provenance`. No read-model schema for it exists
   yet, so S3's tests assume this shape:
   - the envelope;
   - `mandate_version`, a `sha256:` ref;
   - `mandate`, a document of `schemas/mandate.schema.json`;
   - `provenance`, as `[{path, provenance, quote?}]` (mandate spec §2.1).

   When that schema lands, its PR supersedes this item.
2. **Five reads make one `Agent`, and the screens keep their contract** (spec §4.9).
   `assembleAgent` builds the existing `web/src/fixtures/types.ts` `Agent` from five reads:
   - `GET /agents/{id}`
   - `.../positions`
   - `.../orders`
   - `.../pnl`
   - the mandate version

   Every fixture agent in every fixture scenario round-trips to the same `Agent`, with times in
   their canonical form.
3. **Reads that disagree are refused, never merged.** The source becomes unreachable, with
   nothing shown, when any of these hold:
   - a positions, orders, or P&L read names a different agent (`agent_mismatch`);
   - a read names a different environment (`environment_mismatch`);
   - the version read is not the agent's current `mandate_version` (`version_mismatch`).
4. **What `Agent` has no member for travels beside it, in `AgentDetails`.**
   - Each position's mark and broker freshness.
   - Whether the ledger and broker quantities disagree. Both quantities are shown, and neither is
     picked.
   - The unprotected interval, measured from `unprotected_since` to `served_at`, or `null` while
     protected.
   - The limit state's freshness: headroom on stale limit state shows stale.
   - The marks' freshness.
   - The paper label.
   - The working orders in `Unknown`, which stay `Unknown` in the `Agent` and are listed as
     unknown, never guessed (trading spec §5.7).
5. **A version is read once per hash.** A mandate version is content-addressed, so a `/changes`
   notice never refetches it. A new `mandate_version` on the agent read makes the source read the
   new hash once.

   Every other view is refetched only when a notice is newer than its own `as_of` (DEC-736 item 8).
6. **No cached content** (DEC-736 item 6). Any one of the five reads failing, or failing to
   decode, makes the agent unreachable. Nothing from an earlier load survives.

## Rationale

The screens already render a full `Agent` from the fixtures. Assembling the same type from the API
keeps every screen and its tests as they are, and the round-trip test proves the mapping is
lossless.

The tightening items share one rule: a value the owner cannot trust is not shown. That covers
reads that disagree, an `Unknown` order guessed as known, and a stale value presented as current
(brief P6).

## Alternatives considered

- **A new view type per screen.** Rejected: every agent screen and its tests would change at
  once, with no gain over assembling the existing type.
- **Show what loaded when one read fails.** Rejected: a position list without its orders, or
  P&L without its marks, reads as complete when it is not (G4).
- **Refetch the mandate version on every agent change.** Rejected: the hash names the content.
  Re-reading the same hash only costs a request.
