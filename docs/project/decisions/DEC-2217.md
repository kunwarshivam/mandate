## Context

DEC-2216 put the whole gate inside the gateway service. A faithful gate runs each probe run through
the research loop that production uses: the runtime core's run, its tool dispatch over readers, and
its checks on the final output (agent harness spec §6.5, §6.9 to §6.11). That loop lives in the
research runtime, and `mandate-gatewayd` may not depend on `mandate-runtime`
(`xtask/layers.toml`).

So the runtime drives the runs. The service still:
- holds the only key;
- meters every call on its streams;
- decides the gate, from what it saw on the wire, never from what the runtime claims.

## Decision

1. **A gate-only listener.**
   - **Where it opens.** A live service opens a second TCP listener, `--gate-listen <addr>`, beside
     its call listener. The recorded mode opens none.
   - **Who can reach it.** The gate Job runs under its own ServiceAccount, and its pods carry a
     label only the chart's gate CronJobs set. NetworkPolicy selects by that label: it admits
     ingress to the gate port from those pods alone, and it gives those pods egress to the gate port
     (and DNS) alone. No workspace runtime's policy reaches the port. A chart test asserts the
     ingress rule, the Job's egress rule, and that no runtime's egress names the port.
   - **What the call listener keeps refusing.** It refuses `evaluation` as today: its decoder admits
     no such purpose, and #2837's test holds.
   - **What the gate listener admits.** It admits only `evaluation` calls with no agent, inside an
     open gate session (item 2). Every other purpose, an agent id, or a call outside a session is
     refused with no record. A test covers each listener.
2. **A gate session.** The gate Job's first frame on the gate listener opens a session for one
   entry of the live registry file. The frame names the entry and the probe set's digest. The
   session belongs to that connection alone: no other connection can join it, and the connection
   dropping ends it at once.
   - **When the service refuses it.** Before any call, nothing spent, it refuses when:
     - the entry is unknown or the registry refuses it;
     - the probe set's digest is not the one built into the service's image;
     - another session is open;
     - either monthly cap's room is below the gate's whole maximum (DEC-2216 item 7);
     - the store holds a passing report for the same entry, probe set, endpoint and price table.
   - **The gate's own registry.** For the session, the service registers the entry in a registry of
     the gate's own, gives it its endpoint, and probes its identity first. Research calls never
     resolve in that registry.
   - **What each call is.** Each call the Job then sends is checked against the session's shape
     (item 4) before anything is reserved. A call that fits is reserved and settled on the service's
     two meter streams like every call, so the workspace's and the deployment's monthly caps both
     bind it, with purpose `evaluation` and `agent_id` `null` (DEC-2216 item 1). A call that does
     not fit is refused unreserved and ends the session `unmatched`. So a session sends at most the
     probe set's runs times the entry's `max_turns` calls, each at most its maximum cost: the
     maximum the room check reserved room for.
   - **How a session ends, and its report.** Every session that called ends with a report (item 4).
     The `stopped` codes are DEC-2216's (`identity_mismatch`, `cap_refused`, `provider_failed`,
     `checks_failed`), plus:
     - `unmatched`: a call outside the shape;
     - `incomplete`: the Job closed before every run ended;
     - `aborted`: the connection dropped;
     - `timed_out`: the session outlived its bound, the probe set's runs times the entry's
       `max_run_s`.

     When several hold, the report names the first that occurred. The service answers a close with
     the report's reference and verdict. A call in flight when a session ends keeps its reservation
     counted at its maximum, as every call's does (inference spec §7.3).
   - **When the report cannot be written.** If the research store refuses it (DEC-2279's cap), the
     service logs `report_unwritten`, and no reference exists for any file to name. The gate
     therefore cannot pass.
   - **Restarts.** A restart ends a session with no report, as DEC-2216 item 2 says. Nothing
     resumes it, and a reservation made before it stays counted at its maximum (inference spec
     §7.3).
3. **The gate-mode runtime.** The research runtime's binary takes a `gate` mode, run only as the
   one-shot gate Job. It reads the probe set and the fixture corpus baked into its image, and drives
   each of the probe set's 15 runs through the runtime core's research run and the worker's
   dispatch, unchanged but for its calls' purpose (`evaluation`) and their missing agent. Its
   constraints:
   - **Readers:** fixture readers over the corpus only. It has no broker, no account, and no
     network but the gate listener.
   - **Store:** an in-memory store, discarded at exit. It never connects to the journal database
     and writes no agent stream.
   - **Tools:** none but the probe set's entry's tools, served from the corpus.
   - **Order:** it opens the session, runs the runs in the probe set's order, and closes.
4. **The gateway computes the report from what it saw.** The runtime's claims are never read.
   - **What the service holds.** The probe set and corpus are built into the service's image as
     into the runtime's, with one digest. The prompt's fixed text, the tool declarations and the
     sampling are the pinned entry's, which the service renders itself; a call carries none of them.
   - **The session's shape.** The service holds the run each call belongs to:
     - A call whose transcript is empty opens the next run, in the probe set's order.
     - A call whose transcript is not empty extends the current run by exactly one turn.
     - A run ends when the service's reply to it is a final output, or at the entry's `max_turns`.
       A run that ends at `max_turns` with no final output fails the schema and output checks.

     Anything else does not fit and ends the session `unmatched`: a call before the open, a second
     call for a turn, a run out of order, a call after the last run, or a call once the run has
     ended. So the first reply to each turn binds, and no call can be resent until a reply suits.
   - **Every member of each call is checked.** The service checks it against its own record of the
     session:
     - `run_kind` and `as_of` are the run's;
     - `inputs` are the run's seed inputs, which the service recomputes from the corpus by the
       entry's retrieval plan;
     - each earlier turn's `response` is byte for byte the service's own reply to that turn;
     - each earlier turn's `results` are the service's own dispatch over the corpus of that reply's
       tool calls, in reply order;
     - `tools` is the menu agent harness spec §6.9 offers for the run kind and the turn;
     - the deadline and the spend ceiling are within the entry's bounds.

     A call that differs in any of them does not fit.
   - **The §4.3 checks, each the service's own:**
     - **Identity:** each response's reported model and provider equal the pin's.
     - **Schema conformance:** each final output validates against the entry's output schema for
       its run kind, as the gateway already checks.
     - **Output limits:** the harness's §6.5 checks, run by the service over each final output,
       as `mandate-research-run`'s functions, with the run's corpus items as their evidence.
     - **Latency:** as the service measured it.
     - **Injection:** each injection run's final output names no evidence or source that is not an
       item of its own corpus slice.
     - **Cost bound:** from the entry's bounds and price table.
   - **When it passes.** `passed` holds only if every one of the 15 runs ended, in order, and every
     check passed. A runtime that lies, skips, reorders, replays or resends can only end the session
     early, never pass it.
   - **What the report holds.** DEC-2216 item 3's members, with each run's verdict and the
     `stopped` code when it did not pass.
5. **The steps after the founder's apply**, replacing DEC-2216 item 6 step 3:
   1. The founder puts the OpenRouter key in the cell's vault (the existing runbook step).
   2. IAC applies the chart with the live registry values. The service starts live, offers nothing,
      and stays ready.
   3. IAC runs the gate for Sonnet:
      `kubectl create job --from=cronjob/mandate-research-gate-sonnet gate-sonnet-<yyyymmdd>`.
      Then the same for `-haiku`.

      The chart renders each vetted entry's gate as a suspended CronJob that never fires on its own.
      The Job's log ends with the report's reference and `passed`, or the `stopped` code.
   4. IAC sets each passing entry's `gate_report` in the values and applies. The service restarts,
      verifies each report's bindings, probes identity, and offers the gated entries.
6. **What else stands.** The costs of DEC-2216 item 7 stand: at most $7.20 for Sonnet and $0.36 for
   Haiku. So do its journaling gaps (item 8, backlog E21-62u, v and w). The probe socket answers
   `livez` and `readyz` only, as DEC-994 item 5 says.

## Rejected

- **Why the Job is not the separate Job DEC-2216 rejected.** That Job would have held the key and
  written the meter streams. This one holds no key, writes no stream, and reaches only the gate
  listener. The service stays the one key holder and meter writer, and it decides the gate.
- **The gate inside the service (DEC-2216's item 2).** It would need the runtime core in
  `mandate-gatewayd`, against its layering, or a second, thinner loop that is not production's.
- **A thinner driver in the service (option C).** It skips the runtime's checks, so it is less
  faithful to §4.3's output-limits and injection rows.
- **Trusting the runtime's own report.** A compromised or buggy runtime could pass a model. The
  service recomputes every input, result and check instead.
- **Admitting `evaluation` on the call listener behind a flag.** The runtime that serves owners would
  then hold a path to the gate's spend. A separate listener, reachable only by the gate Job, keeps
  the two apart.
