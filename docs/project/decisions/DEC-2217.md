## Context

DEC-2216 put the whole gate inside the gateway service. A faithful gate runs each probe run through
the research loop that production uses: the runtime core's run, its tool dispatch over readers, and
its checks on the final output (agent harness spec §6.5, §6.9 to §6.11). That loop lives in the
research runtime, and `mandate-gatewayd` may not depend on `mandate-runtime`
(`xtask/layers.toml`).

So the runtime drives the runs. The service still:
- holds the only key;
- meters every call on its streams;
- decides the gate, from what it saw on the wire, never from what the runtime claims.

## Decision

1. **A gate-only listener.**
   - **Where it opens.** A live service opens a second TCP listener, `--gate-listen <addr>`, beside
     its call listener. The recorded mode opens none.
   - **Who can reach it.** The chart's NetworkPolicy admits ingress to that port only from pods
     labelled as the gate Job, which runs under its own ServiceAccount. No workspace runtime's
     network policy reaches it, and a chart test asserts both.
   - **What the call listener keeps refusing.** It refuses `evaluation` as today: its decoder admits
     no such purpose, and #2837's test holds.
   - **What the gate listener admits.** It admits only `evaluation` calls with no agent, inside an
     open gate session (item 2). Every other purpose, an agent id, or a call outside a session is
     refused with no record. A test covers each listener.
2. **A gate session.** The gate Job's first frame on the gate listener opens a session for one
   entry of the live registry file.
   - **When the service refuses it.** Before any call, nothing spent, it refuses when:
     - the entry is unknown or the registry refuses it;
     - another session is open;
     - either monthly cap's room is below the gate's whole maximum (DEC-2216 item 7);
     - the store holds a passing report for the same entry, probe set, endpoint and price table.
   - **The gate's own registry.** For the session, the service registers the entry in a registry of
     the gate's own, gives it its endpoint, and probes its identity first. Research calls never
     resolve in that registry.
   - **What each call is.** Each call the Job then sends is reserved and settled on the service's
     meter streams like every call, with purpose `evaluation` and `agent_id` `null` (DEC-2216 item
     1).
   - **How a session ends.** It ends when the Job closes it, when the service stops it, or when its
     time bound passes. The bound is the probe set's runs times the entry's `max_run_s`.
   - **What it writes.** The service writes the report (item 4) for every session that called, and
     answers the close with the report's reference and verdict. A restart ends a session with no
     report, as DEC-2216 item 2 says.
3. **The gate-mode runtime.** The research runtime's binary takes a `gate` mode, run only as the
   one-shot gate Job. It reads the probe set and the fixture corpus baked into its image, and drives
   each of the probe set's 15 runs through the runtime core's research run and the worker's
   dispatch, unchanged. Its constraints:
   - **Readers:** fixture readers over the corpus only. It has no broker, no account, and no
     network but the gate listener.
   - **Store:** an in-memory store, discarded at exit. It never connects to the journal database
     and writes no agent stream.
   - **Tools:** none but the probe set's entry's tools, served from the corpus.
   - **Order:** it opens the session, runs the runs in the probe set's order, and closes.
4. **The gateway computes the report from what it saw.** The runtime's claims are never read.
   - **What the service holds.** The probe set and corpus are built into the service's image as
     into the runtime's, with one digest.
   - **Matching each call.** For each call on the session, the service recomputes:
     - the run it belongs to, from its `run_kind`, its cut-off and its place in the session;
     - that run's seed inputs, from the corpus by the entry's retrieval plan;
     - each tool result in the call's transcript, from its own dispatch of that tool call over the
       corpus.

     A call whose inputs or results differ from the service's own is `unmatched`, and so is a run
     the session never reached.
   - **The §4.3 checks, each the service's own:**
     - **Identity:** each response's reported model and provider equal the pin's.
     - **Schema conformance:** each final output validates against the entry's output schema for
       its run kind, as the gateway already checks.
     - **Output limits:** the harness's §6.5 language checks, run by the service over each final
       output, as pure functions of `mandate-research-run`.
     - **Latency:** as the service measured it.
     - **Injection:** each injection run's final output names no evidence or source that is not an
       item of its own corpus slice.
     - **Cost bound:** from the entry's bounds and price table.
   - **When it passes.** `passed` holds only if every run matched and every check passed. A lying
     runtime can make a gate fail, never pass.
   - **What the report holds.** DEC-2216 item 3's members, with each run's `matched` verdict.
5. **The steps after the founder's apply**, replacing DEC-2216 item 6 step 3:
   1. The founder puts the OpenRouter key in the cell's vault (the existing runbook step).
   2. IAC applies the chart with the live registry values. The service starts live, offers nothing,
      and stays ready.
   3. IAC runs the gate for Sonnet:
      `kubectl create job --from=cronjob/mandate-research-gate-sonnet gate-sonnet-<yyyymmdd>`.
      Then the same for `-haiku`.

      The chart renders each vetted entry's gate as a suspended CronJob that never fires on its own.
      The Job's log ends with the report's reference and `passed`, or the `stopped` code.
   4. IAC sets each passing entry's `gate_report` in the values and applies. The service restarts,
      verifies each report's bindings, probes identity, and offers the gated entries.
6. **What else stands.** The costs of DEC-2216 item 7 stand: at most $7.20 for Sonnet and $0.36 for
   Haiku. So do its journaling gaps (item 8, backlog E21-62u, v and w). The probe socket answers
   `livez` and `readyz` only, as DEC-994 item 5 says.

## Rejected

- **The gate inside the service (DEC-2216's item 2).** It would need the runtime core in
  `mandate-gatewayd`, against its layering, or a second, thinner loop that is not production's.
- **A thinner driver in the service (option C).** It skips the runtime's checks, so it is less
  faithful to §4.3's output-limits and injection rows.
- **Trusting the runtime's own report.** A compromised or buggy runtime could pass a model. The
  service recomputes every input, result and check instead.
- **Admitting `evaluation` on the call listener behind a flag.** The runtime that serves owners would
  then hold a path to the gate's spend. A separate listener, reachable only by the gate Job, keeps
  the two apart.
