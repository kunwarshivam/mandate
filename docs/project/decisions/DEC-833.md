# DEC-833: Whether the workspace-local passkey route (identity §6.4 route 2) serves discoverable credentials only

| | |
|---|---|
| **Status** | Accepted (the founder, 2026-10-09): route 2 serves both discoverable and non-discoverable credentials; the narrowing is not taken |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The founder (DEC-79), 2026-10-09, choosing item 1. Raised by the lane L1 builder on the review of PR #811 |
| **Story or claim** | E9-1 (claim #758); [identity spec](../../specs/identity.md) v0.3 §6.4 route 2, ID-10; [DEC-816](DEC-816.md) item 6 |

## Decision

The question the founder decided: should `POST /v1/reduction-sessions/challenges` and `POST /v1/reduction-sessions`
serve **discoverable (resident) credentials only**, so that a member whose only key is a
non-discoverable security key can no longer open a reduction-only session during an identity-provider
outage?

1. **Decided (the founder chose this):** route 2 serves every key the workspace holds, discoverable or not,
   exactly as before identity spec v0.3. A non-discoverable key's credential ID is supplied by the
   client with the assertion; the challenge route takes nothing and returns nothing
   workspace-specific. The kill switch and pause stay reachable for every member (rule 13).
2. **Not taken (the narrowing):** had the founder accepted it, a non-discoverable key's owner would have had only route 1, the host
   CLI where one exists (managed mode has none), and the broker (OPS-4). The identity spec's ID-10 and
   §6.4 would then have said so.

## Rationale

The question arises because a challenge that must name credentials (an `allowCredentials` list for a
non-discoverable key) would let an unauthenticated caller learn which credentials exist. The interim
avoids that by having the client hold and supply its own credential ID, so nothing is enumerable
before the assertion verifies, and every failure of the assertion route returns one identical answer
(401 `unauthenticated`, same body, headers and timing), so it is no oracle for whether a credential
exists or its member was deactivated (owed to E9-1: `reduction_session_failures_are_indistinguishable`). The founder judged that a simpler discoverable-only route is not worth removing the outage path
from members with non-discoverable keys.

## Alternatives considered

- **Discoverable only (the narrowing).** Smaller surface and a simpler challenge, but a member whose
  only key is non-discoverable loses the outage kill switch and pause, against rule 13.
- **Serve both (decided).** Keeps every member's risk-reduction path. The cost is that the client
  must hold its credential ID, and the assertion route must look credentials up by ID.
- **Serve both and return `allowCredentials` from the challenge route.** Rejected: it enumerates
  credentials to unauthenticated callers.
