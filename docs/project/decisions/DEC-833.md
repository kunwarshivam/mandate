## Decision

Proposed question: should `POST /v1/reduction-sessions/challenges` and `POST /v1/reduction-sessions`
serve **discoverable (resident) credentials only**, so that a member whose only key is a
non-discoverable security key can no longer open a reduction-only session during an identity-provider
outage?

1. **Interim, in force now:** route 2 serves every key the workspace holds, discoverable or not,
   exactly as before identity spec v0.3. A non-discoverable key's credential ID is supplied by the
   client with the assertion; the challenge route takes nothing and returns nothing
   workspace-specific. The kill switch and pause stay reachable for every member (rule 13).
2. **If the founder accepts the narrowing:** a non-discoverable key's owner has only route 1, the host
   CLI where one exists (managed mode has none), and the broker (OPS-4). The identity spec's ID-10 and
   §6.4 then say so, in a change that cites this decision.

## Rationale

The question arises because a challenge that must name credentials (an `allowCredentials` list for a
non-discoverable key) would let an unauthenticated caller learn which credentials exist. The interim
avoids that by having the client hold and supply its own credential ID, so nothing is enumerable
before the assertion verifies. What remains for the founder is whether a simpler discoverable-only
route is worth removing the outage path from members with non-discoverable keys.

## Alternatives considered

- **Discoverable only (the narrowing).** Smaller surface and a simpler challenge, but a member whose
  only key is non-discoverable loses the outage kill switch and pause, against rule 13.
- **Serve both (the interim).** Keeps every member's risk-reduction path. The cost is that the client
  must hold its credential ID, and the assertion route must look credentials up by ID.
- **Serve both and return `allowCredentials` from the challenge route.** Rejected: it enumerates
  credentials to unauthenticated callers.
