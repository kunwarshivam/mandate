# DEC-498: thirty-two mutation shards, because the external oracles raised the cost of a mutant

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-07 (UTC) |
| **Decided by** | The merge coordinator (agent), under DEC-79: a reversible scheduling decision of the same kind DEC-464 and DEC-473 made, which the founder may overturn |
| **Story or claim** | [#652](https://github.com/kunwarshivam/mandate/pull/652) review round 3, major 2; supersedes DEC-473's shard count; DEC-464's ten-minute budget, DEC-497 |

## Decision

1. Supersede DEC-473's twenty-four mutation shards with **thirty-two** deterministic, zero-based
   slice shards.
2. Keep everything DEC-473 kept: the ten-minute timeout, the complete source diff, the selected
   packages, the live-test preflight, the unmutated baseline, the test command, and the
   zero-survivor rule. `cargo xtask check` stays unsharded as the complete local oracle.
3. **When a shard times out, expand the matrix; never the job's ten-minute limit, the diff, or the
   tests.** That is what DEC-464 made the hard limit for and what DEC-473 did when E6-13 outgrew
   twelve shards.
4. **Set cargo-mutants' per-mutant test timeout explicitly, to 180 seconds**
   (`MUTANT_TEST_TIMEOUT` in `xtask/src/main.rs`), instead of taking the value cargo-mutants
   derives. This is not item 3's job timeout; it is the cap on one mutant's test run, and the
   derived value is unusable here for the reason the measurement below found.

## Rationale

DEC-497 runs the whole reference harness for any mutation of a crate it is built on, so a mutant
of a core crate now costs its own package's tests plus the whole of `mandate-refcases`. That raises
the worst case, and #652's review asked for the arithmetic rather than the assurance that layer-0
crates change rarely.

The reference package, measured at `d8b99df` on this four-core box with two test threads, is 62
seconds, concentrated in three of the twelve suites (`mandate_harness` 19.7s,
`mandate_lifecycle_harness` 13.5s, `refcases` 10.7s). Any mutation of a crate under the harness
pays all of it, so 62 seconds a mutant is the per-mutant worst case.

`--sharding slice` cuts the mutant list into contiguous slices whose sizes differ by at most one,
so the largest shard of `N` mutants holds `ceil(N / 32)`, and the budget is
`ceil(N / 32) × 62 + 120 ≤ 600`, with 120 seconds for the baseline build and setup DEC-473
measured. That gives `ceil(N / 32) ≤ 7`, so thirty-two shards hold up to `32 × 7 = 224` mutants.
The largest safety-critical diff so far is E6-13's 169, which DEC-473 measured: `ceil(169 / 32) = 6`
mutants a shard, `6 × 62 + 120 = 492` seconds. At twenty-four shards the same diff needs
`ceil(169 / 24) = 8`, and `8 × 62 + 120 = 616` seconds, over the limit — which is why the count
goes up.

The 224 bound is an estimate from a four-core box, not from the runner. The measurement from
`ubuntu-24.04` is in the measured worst case below.

### Measured on the runner, and what the measurement found

#652's round-4 review asked for the slowest shard measured on `ubuntu-24.04` rather than a shard
count inferred from a four-core box, so [#657](https://github.com/kunwarshivam/mandate/pull/657)
was pushed to produce one: three untested `pub fn`s in `mandate-canon`, nine mutants, none of them
caught, all in a single shard — one more than the eight that would break the budget and two more
than the seven a 224-mutant diff puts in its largest shard. Nine uncaught mutants each run the
whole reference harness to completion, which is the per-mutant worst case, because a caught mutant
stops at nextest's first failure.

The job took **5m26s**, inside the ten minutes, with a baseline of 11s build + 0s test and
per-mutant costs of 28–72s build plus 20s test.

The 20s is the finding. Every one of the nine was reported `TIMEOUT`, not missed. cargo-mutants
sets its per-mutant test timeout to five times the unmutated baseline's test phase, floored at
twenty seconds, and it runs that baseline over **the mutated package alone**: the
`--test-package=mandate-refcases` that DEC-497 adds applies to the mutants and not to the
baseline. So the baseline measured a second of `mandate-canon` tests, the floor gave twenty
seconds, and every mutant that reached the reference harness blew through it.

That is fail-closed — `cargo mutants` exits 3, which `mutants_outcome` refuses outright rather
than reading as a verdict — but it would fail every honest change whose mutants the harness
catches slowly, so item 4 sets the timeout here instead: 180 seconds, about three times the whole
reference package, reached only by a mutation that actually hangs, and not a function of what some
baseline happened to cover.

The budget stands with it. A caught mutant is bounded by time-to-first-failure, not by the
timeout, so the 62-second figure is still the per-mutant worst case; 180 is the cap on a
pathological one, and a shard that meets one fails loudly under item 3.

A diff past that bound fails loudly and never quietly: the shard hits GitHub's hard timeout, the
job fails, the `full` aggregate fails, and the PR cannot merge. No mutant is ever reported caught
because its shard ran out of time. So the cost of this bound being wrong is a red check and this
decision's item 3, not a gap in the gate.

## Alternatives considered

- **Raise the ten-minute job timeout.** Refused for the reason DEC-473 refused it: it weakens the
  latency gate DEC-464 made enforceable, and a limit tuned to today's suite is a number that rots.
- **Leave the per-mutant timeout derived and let the baseline run the reference package too.** It
  would make the derived number honest, but it charges every run a full harness pass before the
  first mutant, for a number an explicit constant states more clearly and more deterministically.
- **Keep twenty-four shards and accept the overflow.** It is loud rather than silent, but it
  spends a reviewer's round and a full CI run to discover something this arithmetic already
  shows.
- **Narrow the external oracles so a core mutation does not run every suite.** Tried in three
  shapes and withdrawn in DEC-497: it saves about fourteen seconds a mutant and buys a failure mode
  that reports a mutant caught when no oracle ran.
- **Make the expensive suites cheaper.** Worth doing on its own merits and nothing to do with this
  change; it belongs in the backlog, not in a PR about configuration references.
- **Larger runners or an external CI service.** Refused for DEC-473's reason: it introduces
  spending or a new service, which DEC-79 reserves to the founder, when the native matrix holds.
