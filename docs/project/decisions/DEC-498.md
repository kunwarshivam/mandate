## Decision

1. Supersede DEC-473's twenty-four mutation shards with **forty-eight** deterministic, zero-based
   slice shards.
2. **Run one mutant at a time** (`MUTANT_JOBS` in `xtask/src/main.rs`, `cargo mutants --jobs 1`),
   not two. A shard's critical path is then its mutants in a row, with nothing to bound by waves.
3. **Set cargo-mutants' per-mutant test timeout explicitly, to 180 seconds**
   (`MUTANT_TEST_TIMEOUT`), instead of taking the value cargo-mutants derives. This is the cap on
   one mutant's test run, not the job's ten-minute limit.
4. Keep everything DEC-473 kept: the ten-minute job limit, the complete source diff, the selected
   packages, the live-test preflight, the unmutated baseline, the test command, and the
   zero-survivor rule. `cargo xtask check` stays unsharded as the complete local oracle.
5. **When a shard runs out of time, expand the matrix; never the job's ten-minute limit, the diff,
   or the tests.** That is what DEC-464 made the hard limit for and what DEC-473 did when E6-13
   outgrew twelve shards.
6. **A shard budget is measured on `ubuntu-24.04`, over repeated runs, and bounded by the slowest
   observation rather than the mean.** Every number here comes from such runs, because the two
   drafts before it did neither and were wrong both times: the first scaled from a four-core
   developer box and was out by a factor of two and a half, the second divided a nine-mutant
   total by nine and priced a shard at its average mutant instead of its critical path.

## Rationale

DEC-497 runs the whole reference harness for any mutation of a crate it is built on, so a mutant
of a core crate costs its own package's tests plus the whole of `mandate-refcases`. #652's review
asked for the arithmetic, then for it to be measured, then for it to be measured properly.

### What the runner measured

[#657](https://github.com/kunwarshivam/mandate/pull/657) is a throwaway branch built to produce
these numbers: three untested `pub fn`s in `mandate-canon`, nine mutants, none caught, all in a
single shard. An uncaught mutant runs the whole harness to completion, which is the per-mutant
worst case, because a caught mutant stops at nextest's first failure. The same nine mutants ran
four times, twice at one worker and twice at two, with the timeout lifted so nothing was cut off.

| Workers | Run | Test phase | Build | Per mutant, total | Wall clock per mutant | Nine mutants |
|---|---|---|---|---|---|---|
| 1 | a | 77–83s | 16–27s | 93–107s | 99s | 14m49s |
| 1 | b | 63–66s | 16–25s | 79–90s | 82s | 12m17s |
| 2 | a | 133–139s | 25–55s | — | 83s | 12m29s |
| 2 | b | 165–181s | 24–71s | — | 108s | 16m15s |

Two things follow, and they decide items 2 and 3.

**The second worker buys nothing.** Wall clock per mutant is 82–99 seconds at one worker and
83–108 at two: the runner's cores are already saturated by a single nextest process, so the
second copy only takes turns with the first. What it does change is how long any one mutant
takes, because the two contend for the same cores — 133–181 seconds of test phase against 63–83.
So item 2 runs one at a time. It costs no throughput and it makes a shard's duration the sum of
its mutants rather than a sequence of waves whose length has to be bounded by the worst pair in
each.

**At two workers the timeout would have fired on a healthy run.** The slowest test phase measured
was 181 seconds, against the 180-second cap of item 3 — a mutant the harness judges perfectly
well, reported `TIMEOUT`, failing a green PR. At one worker the slowest was 83 seconds, so the
same cap sits at 2.2 times the slowest thing ever observed, and only a mutation that actually
hangs reaches it. Item 2 is what makes item 3 safe.

### The budget

At one worker a shard of `k` mutants takes `k × C + S`, with `C` the slowest per-mutant total and
`S` setup plus baseline. The slowest mutant observed across both one-worker runs was 107 seconds;
`C = 120` carries a twelve per cent margin on top. `S` was 57 seconds, measured from job start to
the baseline finishing; call it 60.

`k × 120 + 60 ≤ 600` gives **`k ≤ 4`**. `--sharding slice` cuts the mutant list into contiguous
slices whose sizes differ by at most one, so `S` shards hold `4 × S` mutants.

Forty-eight shards therefore hold **192**. The largest safety-critical diff so far is E6-13's 169,
which DEC-473 measured: `ceil(169 / 48) = 4` mutants in its largest shard, `4 × 120 + 60 = 540`
seconds. Thirty-two shards would need `ceil(169 / 32) = 6`, and `6 × 120 + 60 = 780` seconds, well
over — which is why the count goes up.

### What the measurement found on the way

The first #657 run reported nine `TIMEOUT`s, every one at a twenty-second cap, and no verdicts at
all. cargo-mutants sets its per-mutant test timeout to five times the unmutated baseline's test
phase, floored at twenty seconds, and it runs that baseline over **the mutated package alone**:
the `--test-package=mandate-refcases` that DEC-497 adds applies to the mutants and not to the
baseline. The baseline measured a second of `mandate-canon` tests, the floor gave twenty seconds,
and every mutant that reached the reference harness blew through it.

That failure is closed, not silent — `cargo mutants` exits 3, which `mutants_outcome` refuses
outright rather than reading as a verdict — but it would have failed every honest change whose
mutants the harness catches slowly. Hence item 3.

### When the bound is wrong

A diff past 192 mutants fails loudly and never quietly: the shard hits GitHub's hard timeout, the
job fails, the `full` aggregate fails, and the PR cannot merge. No mutant is ever reported caught
because its shard ran out of time. So the cost of this bound being wrong is a red check and item
5, not a gap in the gate.

The bound is also pessimistic by construction. It prices every mutant as if the harness ran to
completion, which happens when a mutant *survives* — and a surviving mutant fails the PR anyway. A
mutant that is caught costs time-to-first-failure: #652's own forty-eight shards, one caught
mutant each, finished in 30 to 58 seconds including setup.

## Alternatives considered

- **Raise the ten-minute job limit.** Refused for the reason DEC-473 refused it: it weakens the
  latency gate DEC-464 made enforceable, and a limit tuned to today's suite is a number that rots.
- **Keep two workers and bound the critical path by waves.** `ceil(k / 2)` waves, each as long as
  its slowest mutant, is the correct arithmetic for two workers, and #652's round-5 review was
  right that the draft before this one did not use it. But the measurement says two workers return
  no throughput for the doubled per-mutant latency, so the right fix is to remove the waves rather
  than to bound them.
- **Keep thirty-two shards.** They hold 128 mutants under this budget, fewer than the largest diff
  the repository has already produced.
- **Leave the per-mutant timeout derived, and run the reference package in the baseline too.** It
  would make the derived number honest, but it charges every run a full harness pass before the
  first mutant, for a value an explicit constant states more clearly and deterministically.
- **Narrow the external oracles so a core mutation does not run every suite.** Tried in three
  shapes and withdrawn in DEC-497: it saves little and buys a failure mode that reports a mutant
  caught when no oracle ran.
- **Make the expensive suites cheaper.** The one change here that would shrink the worst case for
  every PR rather than redistribute it, and worth doing on its own merits. It belongs in the
  backlog, not in a PR about configuration references.
- **Larger runners or an external CI service.** Refused for DEC-473's reason: it introduces
  spending or a new service, which DEC-79 reserves to the founder, when the native matrix holds.
