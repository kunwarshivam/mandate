# DEC-498: thirty-two mutation shards, because the external oracles raised the cost of a mutant

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-07 (UTC) |
| **Decided by** | The merge coordinator (agent), under DEC-79: a reversible scheduling decision of the same kind DEC-464 and DEC-473 made, which the founder may overturn |
| **Story or claim** | [#652](https://github.com/kunwarshivam/mandate/pull/652) review round 3, major 2; supersedes DEC-473's shard count; DEC-464's ten-minute budget, DEC-497 |

## Decision

1. Supersede DEC-473's twenty-four mutation shards with **thirty-two** deterministic, zero-based
   slice shards.
2. Keep everything DEC-473 kept: the ten-minute timeout, the complete source diff, the selected
   packages, the live-test preflight, the unmutated baseline, the test command, and the
   zero-survivor rule. `cargo xtask check` stays unsharded as the complete local oracle.
3. **When a shard times out, expand the matrix; never the timeout, the diff, or the tests.** That
   is what DEC-464 made the hard limit for and what DEC-473 did when E6-13 outgrew twelve shards.

## Rationale

DEC-497 gives a mutation run the reference suites that judge what it mutates, so a mutant now
costs its packages' own tests plus those suites. That raises the worst case, and #652's review
asked for the arithmetic rather than the assurance that layer-0 crates change rarely.

The reference suites, measured at `d8b99df` on four cores with two test threads: the whole package
is 62 seconds, and three suites are 44 of them (`mandate_harness` 19.7s,
`mandate_lifecycle_harness` 13.5s, `refcases` 10.7s). Every suite declares a driver built on the
layer-0 crates, so a `mandate-num`, `mandate-time` or `mandate-canon` mutation selects all of
them: 62 seconds a mutant, the worst case there is.

DEC-473 measured the largest safety-critical diff so far, E6-13's 169 mutants, and baselines of
one to two minutes. At twenty-four shards that is eight mutants a shard, and
`8 × 62 + 120 = 616` seconds, over the limit. At thirty-two it is six, and
`6 × 62 + 120 = 492` seconds, inside it. Stated as a bound: thirty-two shards hold a
worst-case-selection diff of up to about `32 × (600 - 120) / 62 ≈ 247` mutants, against the 169
of the largest diff measured.

A diff past that bound fails loudly and never quietly: the shard hits GitHub's hard timeout, the
job fails, the `full` aggregate fails, and the PR cannot merge. No mutant is ever reported caught
because its shard ran out of time. So the cost of this bound being wrong is a red check and this
decision's item 3, not a gap in the gate.

## Alternatives considered

- **Raise the ten-minute timeout.** Refused for the reason DEC-473 refused it: it weakens the
  latency gate DEC-464 made enforceable, and a timeout tuned to today's suite is a number that
  rots.
- **Keep twenty-four shards and accept the overflow.** It is loud rather than silent, but it
  spends a reviewer's round and a full CI run to discover something this arithmetic already
  shows.
- **Narrow the external oracles so layer-0 mutations do not select every suite.** That is
  precisely the coverage DEC-497 exists to restore; a `mandate-num` bug can fail any of them.
- **Make the expensive suites cheaper.** Worth doing on its own merits and nothing to do with this
  change; it belongs in the backlog, not in a PR about configuration references.
- **Larger runners or an external CI service.** Refused for DEC-473's reason: it introduces
  spending or a new service, which DEC-79 reserves to the founder, when the native matrix holds.
