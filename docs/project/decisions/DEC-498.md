# DEC-498: forty-eight mutation shards and an explicit per-mutant timeout, both measured on the runner

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-07 (UTC) |
| **Decided by** | The merge coordinator (agent), under DEC-79: a reversible scheduling decision of the same kind DEC-464 and DEC-473 made, which the founder may overturn |
| **Story or claim** | [#652](https://github.com/kunwarshivam/mandate/pull/652) review rounds 3 and 4; supersedes DEC-473's shard count; DEC-464's ten-minute budget, DEC-497; measured by [#657](https://github.com/kunwarshivam/mandate/pull/657) |

## Decision

1. Supersede DEC-473's twenty-four mutation shards with **forty-eight** deterministic, zero-based
   slice shards.
2. **Set cargo-mutants' per-mutant test timeout explicitly, to 180 seconds**
   (`MUTANT_TEST_TIMEOUT` in `xtask/src/main.rs`), instead of taking the value cargo-mutants
   derives. This is the cap on one mutant's test run, not the job's ten-minute limit.
3. Keep everything DEC-473 kept: the ten-minute job limit, the complete source diff, the selected
   packages, the live-test preflight, the unmutated baseline, the test command, and the
   zero-survivor rule. `cargo xtask check` stays unsharded as the complete local oracle.
4. **When a shard runs out of time, expand the matrix; never the job's ten-minute limit, the diff,
   or the tests.** That is what DEC-464 made the hard limit for and what DEC-473 did when E6-13
   outgrew twelve shards.
5. **A shard budget is measured on `ubuntu-24.04`, not extrapolated from a developer's machine.**
   Both numbers above come from a run on the runner, and the first attempt at this decision shows
   why: its arithmetic, scaled from a four-core box, was wrong by a factor of two and a half.

## Rationale

DEC-497 runs the whole reference harness for any mutation of a crate it is built on, so a mutant
of a core crate now costs its own package's tests plus the whole of `mandate-refcases`. That raises
the worst case, and #652's review asked for the arithmetic, then for the arithmetic to be measured
rather than scaled.

### What the runner measured

#657 is a throwaway branch built to produce one number: three untested `pub fn`s in
`mandate-canon`, nine mutants, none caught, all in a single shard. An uncaught mutant runs the
whole harness to completion, which is the per-mutant worst case, because a caught mutant stops at
nextest's first failure.

| | |
|---|---|
| Job, nine worst-case mutants in one shard | **15m17s** |
| Setup before `cargo mutants` | 42s |
| Unmutated baseline | 11s build + 0s test |
| Per mutant | 23–66s build + 151–158s test |
| Per mutant, wall clock at `--jobs 2` | **96s** |

So the budget is `k × 96 + 56 ≤ 600` for `k` mutants in the largest shard, which gives `k ≤ 5`.
`--sharding slice` cuts the list into contiguous slices whose sizes differ by at most one, so the
largest shard of `N` mutants over `S` shards holds `ceil(N / S)`, and a matrix of `S` shards holds
`5 × S` mutants.

Thirty-two shards hold 160. The largest safety-critical diff so far is E6-13's 169, so
thirty-two is not enough and **forty-eight** is: it holds 240, and E6-13's 169 puts
`ceil(169 / 48) = 4` mutants in its largest shard, `4 × 96 + 56 = 440` seconds.

This is two and a half times the per-mutant cost the previous version of this decision assumed. It
had the whole reference package at 62 seconds, measured locally on four cores with two test
threads; on the runner the same package under two concurrent mutant jobs takes 151–158. Scaling a
CI budget from a developer's machine was the mistake, and item 5 records it.

### What the measurement found on the way

The first #657 run reported nine `TIMEOUT`s, every one at a twenty-second cap, and no verdicts at
all. cargo-mutants sets its per-mutant test timeout to five times the unmutated baseline's test
phase, floored at twenty seconds, and it runs that baseline over **the mutated package alone**:
the `--test-package=mandate-refcases` that DEC-497 adds applies to the mutants and not to the
baseline. The baseline measured a second of `mandate-canon` tests, the floor gave twenty seconds,
and every mutant that reached the reference harness blew through it.

That failure is closed, not silent — `cargo mutants` exits 3, which `mutants_outcome` refuses
outright rather than reading as a verdict — but it would have failed every honest change whose
mutants the harness catches slowly. Hence item 2. 180 seconds is a little above the 158 the
harness took at its slowest here, so a mutant the harness catches at all is judged, and a mutation
that actually hangs is still cut off. With it set, the same nine mutants were correctly reported
missed.

### When the bound is wrong

A diff past 240 mutants fails loudly and never quietly: the shard hits GitHub's hard timeout, the
job fails, the `full` aggregate fails, and the PR cannot merge. No mutant is ever reported caught
because its shard ran out of time. So the cost of this bound being wrong is a red check and item
4, not a gap in the gate.

The bound is also pessimistic by construction. It prices every mutant as if the harness ran to
completion, which happens when a mutant survives — and a surviving mutant fails the PR anyway. A
mutant that is caught costs time-to-first-failure: #652's own shards, one caught mutant each,
finished in 30 to 58 seconds including setup.

## Alternatives considered

- **Raise the ten-minute job limit.** Refused for the reason DEC-473 refused it: it weakens the
  latency gate DEC-464 made enforceable, and a limit tuned to today's suite is a number that rots.
- **Keep thirty-two shards and accept that the largest diff so far does not fit.** It is loud
  rather than silent, but it spends a reviewer's round and a full CI run to discover something this
  measurement already shows.
- **Leave the per-mutant timeout derived, and run the reference package in the baseline too.** It
  would make the derived number honest, but it charges every run a full harness pass before the
  first mutant, for a value an explicit constant states more clearly and deterministically.
- **Narrow the external oracles so a core mutation does not run every suite.** Tried in three
  shapes and withdrawn in DEC-497: it saves little and buys a failure mode that reports a mutant
  caught when no oracle ran.
- **Run the mutants with `--jobs 1` to remove the contention that makes the harness take 155
  seconds instead of 62.** It removes the contention and the parallelism together, so the wall
  clock per mutant lands in the same place; it would need its own measurement to claim otherwise.
- **Make the expensive suites cheaper.** The one change here that would shrink the worst case for
  every PR rather than redistribute it, and worth doing on its own merits. It belongs in the
  backlog, not in a PR about configuration references.
- **Larger runners or an external CI service.** Refused for DEC-473's reason: it introduces
  spending or a new service, which DEC-79 reserves to the founder, when the native matrix holds.
