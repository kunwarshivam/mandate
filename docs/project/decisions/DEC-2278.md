## Context

DEC-2394 lets the agent read Alpaca news: read-only, with a paper credential from the vault that is
never logged, each item journaled before use, allowlisted egress, and recorded items only in CI.
DEC-2277 gives the reader its own paper data key, read only by `Identity::NewsReader`. The research
core already brings a `monitor` run forward when a journaled item matches an active thesis
(DEC-2392). The cell's daemon already offers it items, so far from a recorded `feed.json`
(DEC-2275).

Two things are still undecided:
- which process fetches the live news;
- how its items reach the runtime.

The runtime holds no credential, ever (CN-4), so it cannot fetch.

## Decision

1. **A news-reader process of its own**, one per workspace: `news-reader` in the workspace chart.
   - It holds the `news-reader` AppRole, and nothing else in the vault.
   - Its only egress is the vault, Postgres, and `data.alpaca.markets`.
   - It runs only in the founder's workspace (DEC-2277 item 6).
   - It reads the key once at start. With no key, or a key refused `NotPaper`, it starts, writes
     nothing, and reports not ready with that reason. It never crashes and never retries the read
     in a loop.
2. **What it reads.** It polls news for the symbols of the agent's active theses and held
   instruments, read from the journal, through `mandate-sources`' fetcher under allowlist version
   3, paced as the allowlist says.
3. **Journal-only writes.** For each new item, the reader:
   - stores the raw response bytes and the item's typed record in the artifact store;
   - appends `NewsItemStored` to its own stream, `news:{workspace_id}` (journal spec §9.37,
     rules 283 to 285).

   It writes no other stream, and holds no text of an item in the record. The record's `item_ref`
   is the bytes the runtime stores and names as `ObservationRecorded.data_ref`. So an item is the
   same item to the reader and to the runtime, and rule 271's one item, one run holds across them.
4. **How the runtime uses it.** The daemon's research source reads the news stream as it reads
   the meter stream, and gives the pass each recorded item whose `knowledge_at` the risk clock has
   reached. The pass offers those items exactly as it offers the recorded feed's (DEC-2275 item 3).
   The core alone decides whether a `monitor` run starts, and the run only ever produces opinions.
5. **Not a risk input.** No stream's owner copies from the news stream, and no gate or fold of a
   limit reads it.
6. **CI and the demo** use recorded items only: a recorded transport answers the fetcher, and the
   key comes from a fake vault. No test reaches Alpaca.

## Consequences

- **The work, in order:**
  1. this spec slice (journal spec v0.96);
  2. `NewsItemStored`'s registration in `mandate-journal`, with vectors;
  3. the reader crate, its process, and its recorded tests;
  4. the daemon reading the stream;
  5. the chart, with the process, its image, NetworkPolicy, egress, and vault binding, and a
     `test_cell.py` invariant that it reaches nothing else.
- **Adversaries:**
  - An injected or hostile news item can at most lead a monitor run to invalidate a thesis. That
    sells a position, which only reduces risk, and is never denied (rule 13). It can never open
    one (DEC-2392 item 3).
  - A burst of items is bounded by the debounce, `max_runs_per_day`, the cost cap, and one run in
    flight.
  - A stolen news key reaches only the news-only paper account (DEC-2277 item 1).
