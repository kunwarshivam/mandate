## Context

DEC-2394 lets the agent read Alpaca news: read-only, with a paper credential from the vault that is
never logged, each item journaled before use, allowlisted egress, and recorded items only in CI.
DEC-2277 gives the reader its own paper data key, read only by `Identity::NewsReader`. The research
core already brings a `monitor` run forward when a journaled item matches an active thesis
(DEC-2392). The cell's daemon already offers it items, so far from a recorded `feed.json`
(DEC-2275).

Two things are still undecided:
- which process fetches the live news;
- how its items reach the runtime.

The runtime holds no credential, ever (CN-4), so it cannot fetch.

## Decision

1. **A news-reader process of its own**, one per workspace: `news-reader` in the workspace chart.
   - It holds the `news-reader` AppRole, and nothing else in the vault.
   - Its only egress is the vault, Postgres, and `data.alpaca.markets`.
   - It runs only in the founder's workspace (DEC-2277 item 6).
   - It reads the key once at start. With no key, or a key refused `NotPaper`, it starts, writes
     nothing, and reports not ready with that reason. It never crashes and never retries the read
     in a loop.
2. **What it reads.** It polls news for the symbols of the agent's active theses and held
   instruments, through `mandate-sources`' fetcher, under the allowlist version in effect (3 today),
   paced as the allowlist says.
   - It reads those symbols from the agent and account streams, which it may only read. Its
     Postgres role may write only the news stream.
   - A thesis that ends drops its symbol from the next poll.
   - Each poll asks from the stream's last `knowledge_at`, or from 48 hours back for an empty stream
     (DEC-1130 item 5). So news published before a thesis began can still be read, within that
     bound.
3. **Journal-only writes.** For each new item, the reader:
   - stores the raw response bytes in the data plane's store, which no journal record names. Their
     retention is data-plane spec §4.5's and DEC-433 item 20's, which stays open with counsel;
   - stores the item's typed record in the artifact store: `RetrievedItem::record` of the whole,
     untrimmed item, which for a licensed item holds no text;
   - appends `NewsItemStored` naming that record as `item_ref` to its own stream,
     `news:{workspace_id}` (journal spec v0.97 §9.37, rules 283 to 286).

   It writes no other stream. One item is stored once, by its `item_id` (rule 284): a later fetch,
   a restart, or a failover stores nothing again. The reader folds the stream at start for that.
   An item it cannot store (no ticker, or more than 32) is counted by id in its metrics, not
   journaled. A refused append stops the reader, not ready, and the next process folds again.
4. **How the runtime uses it.** The daemon's research source reads the news stream as it reads
   the meter stream, and gives the pass each recorded item whose `knowledge_at` the risk clock has
   reached, from a source in the allowlist version in effect. The pass offers each item as
   DEC-2275 item 3 offers the recorded feed's, with one difference: it builds the offer from the
   record's members and takes `item_ref` as the `data_ref` as it is. It never rebuilds the item,
   so the reader's digest and the runtime's are the same bytes, and rule 271's one item, one run
   holds across them. The core alone decides whether a `monitor` run starts, and the run only ever
   produces opinions.
5. **Not a risk input.** No stream copies a record from the news stream, and no gate or fold of a
   limit reads it.
6. **CI and the demo** use recorded items only: a recorded transport answers the fetcher, and the
   key comes from a fake vault. No test reaches Alpaca.
7. **A correction to agent harness spec §5.3.** It said an event run's `ObservationRecorded`
   names "the item's raw bytes as stored". The code (#2558) and the journal name the item's typed
   record, which holds no licensed text where raw bytes would. §5.3 now says so. This keeps
   licensed text out of every record the journal verifies.

## Consequences

- **The work, in order:**
  1. this spec slice (journal spec v0.97);
  2. `NewsItemStored`'s registration in `mandate-journal`, with vectors;
  3. the reader crate, its process, and its recorded tests;
  4. the daemon reading the stream;
  5. the chart, with the process, its image, NetworkPolicy, egress, and vault binding, a
     `test_cell.py` invariant that it reaches nothing else, and its Postgres role.
- **Adversaries:**
  - An injected or hostile news item can at most lead a monitor run to invalidate a thesis. That
    sells a position, which only reduces risk, and is never denied (rule 13). It can never open
    one (DEC-2392 item 3).
  - A burst of items is bounded by the debounce, `max_runs_per_day`, the cost cap, and one run in
    flight.
  - A stolen news key reaches only the news-only paper account (DEC-2277 item 1).
