## Context

The journal spec's catalogue row for `OwnerAcknowledged` names the acknowledging user, the user who
requested the lift, and the independence requirement as it stood at the request (mandate spec §6.7,
DEC-351). No payload schema was registered, so a real journal refused every acknowledgment as
`unknown_schema`. The sources disagreed on what to register:

- DEC-279 item 7's members, which the CLI writes and DEC-2102 item 4 copies for the workspace API,
  are `agent`, `event`, `user`, `risk_clock`, `submitted_at` and `step_up`. They lack the requester
  and the independence requirement, so every acknowledgment that needs an independent user fails
  closed.
- The executor's fold reads `subject`, which no writer emits, and treats `step_up` as text. The
  mandate reference cases name the tripwire, not an event.
- The CLI writes `risk_clock` in integer seconds, which §9.2's `risk_clock` type refuses.
- No event recorded who requested a lift, so nothing could supply the requester.

## Decision

1. **The members** (coordinator's ruling (a)). `OwnerAcknowledged` carries:
   - `agent` and `event`: the acknowledged `RiskLimitTriggered`'s `event_id`. This is the name the CLI and the API already write; the executor's `subject` becomes `event`.
   - `user`, `requested_by`, `independent_required`, and `request`.
   - `submitted_at`, as an integer.
   - `risk_clock`, as §9.2's timestamp. The CLI changes from integer seconds.
   - `step_up`: §9.7's nullable object. The authentication method is `step_up.method`, with no second member.
2. **A separate request event** (coordinator's ruling (b)). Where an independent user is required,
   the requester records `OwnerAcknowledgmentRequested`, and a different user acknowledges, naming
   it in `request`. So an `OwnerAcknowledged` is always an acknowledgment that takes effect when it
   passes, never a request. With the other option, a prior acknowledgment serving as the request,
   the fold would have to decide from policy whether an acknowledgment took effect, and a policy
   misread on replay could lift a limit.
3. **The rules.**
   - Rule 239: a request carries `independent_required` `true`. An acknowledgment that requires independence names a request and a different user; one that does not names no request and its own user as requester.
   - Stream rule 240: the request exists earlier on the stream and matches the acknowledgment's `agent`, `event`, `requested_by` and `independent_required`.
   - Stream rule 241: one acknowledgment per request.

   Writers check all three before appending, and `append` checks rule 239.
4. **The executor judges at processing, from its own stream.** It copies the request as well as the
   acknowledgment, so its account-stream fold holds every input it judges from, and a replay
   decides the same way. It refuses as `not_independent`:
   - an acknowledgment that, under the stricter of the requirement it carries and the overlay's, breaks rules 239 to 241 on the copies;
   - one whose trigger was superseded: `event` is not the latest `RiskLimitTriggered` of its `limit`, or a `RiskLimitLifted` of that `limit` follows it.

   A stale request never lifts a later latch. The existing `not_independent` reason is reused, so
   `OwnerCommandRefused`'s closed reasons do not change.
5. **The step-up type is §9.7's**, with integer seconds. That is what the CLI writes for every
   control-stream owner command. The executor's account-stream records that repeat it, such as
   §9.27's `HighWaterMarkReset`, convert it to §9.3's timestamp form when they write it.

## Rationale

Items 1 and 3 close the record the spec already described, plus the member that names what is
acknowledged. Item 2 keeps each event's meaning fixed, so no replay depends on policy. Item 4 puts
the judgment where the lift happens, on inputs the account stream holds. Every rule only refuses an
acknowledgment, which only adds risk when it passes.

## Alternatives considered

- **A prior acknowledgment as the request.** Rejected for item 2's replay risk.
- **A new `OwnerCommandRefused` reason for a superseded trigger.** It would change a closed schema.
  `not_independent` already means "no independent acknowledgment of this trigger".
- **A §11 range check for rules 240 and 241 now.** It needs a new `VerificationRun` check code, so
  it comes as its own change. Until then the writers and the executor hold the rules, and the
  executor fails closed.

## Follow-ups

- **The registration change (M7 S2):** `mandate-journal` registers both schemas and rule 239, with the vectors §9.28 lists.
- **The CLI (M7 S2):** `mandate agent request-ack` and `mandate agent acknowledge` write these members, with `risk_clock` as a timestamp, and check rules 239 to 241 before appending.
- **The workspace API (DEC-2102 item 4, lane L1):** add `requested_by`, `independent_required`, `request` and the timestamp `risk_clock` before its route mounts.
- **The executor (E7-4, lane X):** fold `event` instead of `subject`, copy the request, and judge item 4.
- **§11:** a range check for rules 240 and 241, with its check code.
