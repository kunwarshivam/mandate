# DEC-1006: A working order is read by the profile's listing, and one opening works per instrument (R0 R18)

| | |
|---|---|
| **Status** | Accepted (agent: reversible engineering readings under DEC-79, each under DEC-176. Each one refuses or holds more, or fills a gap by the reading that adds no risk; none touches live money, spending, legal text or a safety rule) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The R18 builder (Claude Code), under DEC-79 and DEC-176; one PR with its tests first (DEC-921) |
| **Story or claim** | E7-26, E7-23; the [R0 rehearsal](../tasks/r0-rehearsal.md)'s R18 and its second ask; claim #1428 |

On the Tuesday rehearsal clock, the entry was sent to the simulator and accepted
(`rh-sim-000001`). The run then stopped with `the tracer stopped at Connector: the request was
not sent (not_offered)`, because something asked the Robinhood connector for
`GetOrderByClientId`, which it does not serve: Robinhood's profile cannot query by client order
id. The R0 record first blamed the executor's `query_unknown`. Reading the code showed that the
request that stopped the run was the shell's LT-10 watch, which polled the entry by its client
order id on every wake (`crates/mandate-shell/src/tracer.rs`, `watch`). The executor's
`query_unknown` had the same gap for a working order. In the same run, the runtime asked a second
time for the same instrument while the first opening worked. These are the readings that close
both gaps.

## Decision

1. **The executor asks after a working order by the profile's listing.** On a profile with
   `query_by_client_order_id: false`, an order in any state other than `Unknown`, which the
   broker has already described, is asked after by one `ListOrders` listing. The listing covers
   its instrument and agentic origin, from DEC-862 item 2's margin before its `OrderSubmitted`.
   No query the connector refuses unsent is asked. Unlike an `Unknown` order, this needs no
   dedicated account, because item 2 adopts only a record naming the order by our own id.
   - An `Unknown` order keeps DEC-862's listing on a dedicated account and nothing on a shared one.
   - A profile that can query by client order id still asks by it.
   - An order with no folded submission is asked after by nothing, and stays as it is.
2. **A working order adopts only the record naming it.** A listing's answer for a working order is
   folded through §5.7's table only when exactly one record names the order by our own client
   order id and matches it as sent (DEC-862 item 4's members). Robinhood's records name our
   `ref_id` exactly (DEC-941 item 4). The following leave the order as it was, with nothing sent:
   - a record naming no id (DEC-863's look-alike, which only an `Unknown` order may adopt);
   - a record naming another id;
   - two records naming ours;
   - no record at all.

   So a working order is never taken as filled or gone on a guess. The broker's own order id is
   not the key: journal spec §9.16 says the executor's fold never reads `broker_order_id`, and our
   id carried as `ref_id` is the same identity, already in the fold.
3. **The watch reads its entry the way the profile offers.** The shell's watch asks by client
   order id when the connector's profile can, and otherwise by the same listing, from the run's
   start less the margin. It reads the LT-10 status only from the one record naming the entry. A
   listing with none or several such records reads nothing, and the watch reads again on the
   next wake. The answer goes to the executor as every broker answer does, so item 2 decides
   what it describes. A profile the connector cannot give is read as one that can query by id,
   which the connector then refuses unsent, and the run stops (fail closed).
4. **The runtime follows its own openings on the account stream.** From the journal alone:
   - **Linking.** `OrderRequestRecorded` names the intent (`intent_id`). `OrderSubmitted` names
     its order (`client_order_id`), and its `causation_id` is that request (rule 45), or the
     intent itself on the legacy shape a test double writes. A `replaced` order passes the intent
     to its successor (`replaced_by`).
   - **What ends one.** A `GateDecided` with verdict `deny`; an `OrderAbandoned`; or an
     `OrderStateChanged` of its own order to `filled`, `canceled`, `rejected`, `expired` or
     `abandoned`.
   - **What ends nothing.** A record missing any of these members, or naming an order the runtime
     did not submit. The hold therefore never lifts on a guess; the only cost is holding longer,
     which adds no risk.

   All of it is rebuilt by replay (ES-21). `FOLD_VERSION` stays 1, because these records were
   folded as inert before and no committed fold output changes.
5. **One working opening per instrument.** While an opening or increase the runtime proposed in an
   instrument still works (item 4), another opening or increase there is denied in the runtime's
   dry run as `working_order_limit`, trading spec §5.3 rule 6's code: "At most one working
   non-protective order per instrument per account". This happens before the gate is asked,
   journaled as the `DecisionMade` deny, and the same holds at a grant's re-validation (mandate
   spec §6.4 check 11). The R0 run's second ask would now be held. The binding gate keeps its own
   checks. An exit, a protective order and a kill switch are never read against it (`AGENTS.md`
   rule 13). Mandate spec §8.3 step 3, the size net of working openings, is the builder's and is
   not changed here.
6. **Two tests move with item 5.**
   - The fail-closed suite's `--new-cycle` test fills its first order before starting the second
     cycle. Without the fill, rule 6 holds the second opening, which is the reading this decision
     takes.
   - The rh-sim restart test's opening behind an `Unknown` order is now held by the runtime's dry
     run, before the gate, and the test asserts exactly that: a `DecisionMade` denied
     `working_order_limit` and no new `GateDecided`. The opening was blocked before as well, by
     the binding gate's `unknown_order_in_flight`.

## Rationale

The watch is how a placing run learns of its fill. On a profile that cannot query by id, the only
honest read is the listing the profile offers, matched by our own id. A record matched by guess
could book a fill that never happened. Following the opening through the journal lets the runtime
apply rule 6 the same way live and on replay, without trusting the run context's
`working_opening_cost` of zero.

## Alternatives considered

- **Store the broker's order id in the executor's fold, and match it**: journal spec §9.16 rules
  this out; the fold does not read it.
- **Hold while any intent is outstanding**: the runtime never retires an outstanding intent, so
  this would hold every opening after the first, forever.
- **Fix the run context's `working_opening_cost` instead**: that is the builder's sizing (§8.3), a
  larger change, and it would not stop an ask the builder still proposes.
