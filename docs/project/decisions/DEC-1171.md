# DEC-1171: `AgentDeployed` version 2 names its connection, and the deployment manager reads a deployment's account from the journal alone

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and DEC-176; it adds a member and two checks, tightens the CLI's paper deployment, and loosens nothing) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (lane D1 of the managed-cells plan, DEC-967, DEC-990), under DEC-79 and DEC-176 |
| **Story or claim** | E21-33; journal spec v0.52, §9.2, §9.21, §9.24, §11; supersedes DEC-1170 item 5's and item 9's resolver over stored mandates |

## Context

The deployment manager (journal spec §9.21, DEC-1170) runs an executor for the account of each
deployed agent. `AgentDeployed` version 1 names only the mandate version, so DEC-1170 item 5 had the
manager ask a resolver over the stored mandate documents for the connection, then read that
connection's `account_ref`. The cell has no artifact store the manager shares with the workspace
services, so that resolver has nothing to read. Everything else the manager needs is on the control
stream already: a connection kill switch's scope is read from the connection's own version-2
`ConnectionEstablished`, and `AgentStopped` already names its connection.

## Decision

1. **`AgentDeployed` version 2 (journal spec v0.52, §9.24).** Version 1's members (`agent_id`,
   `mandate_version`, `record_ref`), then `connection_id` (`id`): the `connection_id` of the stored
   mandate document `mandate_version` names. The connection never changes across a mandate's
   versions (mandate spec V-031). Version 1 stays registered, replayable, and unchanged. Rule 22
   applies to both versions. A writer that deploys a stored version writes version 2, taking the
   member from the document; until the CLI and the workspace API move, in the code change that
   follows, they write version 1.
2. **Rule 200, judged by the writer and where the document is read.** A version-2 record's
   `connection_id` equals the document's. Each writer of version 2 (the CLI's `agent deploy`, the
   workspace API's deployment) checks it before appending, against the stored document it already
   holds, and refuses the draft on a mismatch. §9.2's mapping to `AgentVersionActive`, which reads
   the document, refuses a mismatch as malformed at `payload.connection_id`, as it refuses a record
   whose document is not stored; so every `ValidationContext::from_journal` reader (the writers'
   checks, the runner's control fold, replay) refuses the control stream at that record. The fact is
   the same for both versions, from the document. `append` does not judge it (it reads stored
   objects only for configuration references, journal spec §9, rules 21a and 21b, and a mandate
   document is not one); §11 cannot see it, since it never reads a document's members; and the
   deployment manager acts on the record alone. A mismatch stored anyway fails closed: the manager
   would start the record's account's executor and a runtime for the agent, but the runtime reads
   its deployment through the mapping and refuses it, so the agent proposes nothing; the executor
   adds no exposure and is one slot per account. The deployment does not run until it is corrected.
3. **Rule 201, a stream rule, kept as a tightening under DEC-176.** A version-2 `AgentDeployed`
   follows, on the same control stream, a version-2 `ConnectionEstablished` of its
   `connection_id`, and that connection's latest earlier establishment or revocation is an
   establishment. Held and checked as rules 66 to 68 are: the writer checks it against its fold
   before appending, and §11's `connection_lifecycle_mismatch` judges it, from the connection
   anchor, which already holds each id's first establishment and its latest establishment or
   revocation, or failing closed at a version-2 `AgentDeployed` without one. A version-1
   deployment is not judged, so every stream written before v0.52 still verifies. It refuses only
   deployments, which add risk, so it never holds risk reduction, and what it refuses fails closed.
   It is not what every writer does today:
   - a live deployment meets it already: the CLI's `admitted()` requires the connection's latest
     establishment or revocation to be a version-2 establishment that `connection record`
     committed (DEC-529 item 3);
   - a paper deployment does not: `admitted()` returns early for paper and never reads the
     connection, and when the stream records nothing about the connection the CLI's V-rule check
     clears its environment (so V-001 does not fire) and tolerates V-002. Phase 1's paper
     connections journal no establishment, and the CLI's `agent deploy` deploys a paper agent on
     such a connection today. Under rule 201 a paper deployment needs the connection's version-2
     establishment from `connection record` first. **The CLI is the writer whose behaviour
     changes**, in the code change that follows; the workspace API's deployment clears the
     environment the same way, though it refuses V-002 for a deployment;
   - a revoked connection is known to the fold, so V-001 already refuses a paper deployment on it
     and `admitted()` a live one.
4. **The manager's reading (§9.21).** A deployment's account is the `account_ref` of its version-2
   `connection_id`'s version-2 `ConnectionEstablished` earlier on the stream. A version-1 deployment
   names no account, and a version-2 one that rule 201 refuses has none: the manager starts nothing
   for either (`AGENTS.md` rule 3), and a later establishment revives neither. It never reads the
   mandate document, so no store outside the journal stands between a deployment and its
   processes, and the resolver of DEC-1170 items 5 and 9 is dropped.
5. **Every other reader is unchanged.** The folds that read only `agent_id` and `mandate_version`
   (the runner's control fold, the CLI's and the workspace API's active-deployment reads, §9.4's,
   §9.17's and §9.18's references) read them the same at both versions.
6. **Vectors and order.** A new generated `agent_deployed` section of the journal vectors holds the
   base drafts, an invalid draft for every member type of version 2 and for rule 22 at version 2,
   valid drafts (a mismatch `append` admits among them), mapping cases for rule 200, control streams
   for rule 201 with the processes the manager runs for each, and anchored and unanchored ranges,
   with seeded bugs in the validator, the mapping, the stream rule, the range reading, the
   manager's reading, and the vectors, each caught. No other section changes. The Rust registration,
   the mapping's rule 200, the writers, rule 201's check, §11's verifier, and the manager's reading
   follow in one code change.

## Rationale

The journal is the only channel between the workspace services and the cell's processes (DEC-986),
and the manager already reads a connection's account from the control stream for kill switches.
Restating the connection, with a rule that binds it to the document, gives the manager the same
path for deployments with no new store, no new dependency, and nothing that can be unavailable
while a kill switch waits. Version 1 failing closed costs nothing today: the manager's process is
not yet deployed, and the code change that ships it moves the writers to version 2. Rule 201 asks a
paper owner to record the connection before deploying, a step a live owner already takes; it
refuses a deployment, never an exit, so the cost is a refused gesture with a clear code, not risk.

## Alternatives considered

- **A resolver over the stored mandate documents (DEC-1170 item 5).** Needs an artifact store the
  cell does not have, and a store outage would defer deployments.
- **Restate the `account_ref` on `AgentDeployed`.** The account belongs to the connection, which the
  control stream already binds (rule 66); a second copy could disagree with the binding, and the
  writer would need a second rule to keep them equal.
- **Judge rule 200 at `append`.** It would put the mandate document's shape into `append`, which
  today reads stored objects only for configuration references, and refuse every deployment where
  no artifact source is passed.
- **Read a version-1 deployment by the document when one is at hand.** Two paths to one answer, one
  of them through a store the manager cannot rely on; failing closed is the safer default.
