# DEC-676: Connections check 1 shares the MCP client's fund-movement rule, and checks 1 and 7 fail closed

## Context

Two places decide whether a name can move funds out (CN-2):

- the MCP client (E7-16), under [DEC-839](DEC-839.md) item 3;
- connections check 1 (E7-12), over key permissions, OAuth scopes, and MCP tools.

[DEC-839](DEC-839.md) item 3 is the rule, as #888 (the live lane's M2 tests, part 2) amends it.
This decision does not restate or change that rule. It records which code implements the rule, and
that check 1 uses that code.

#883's review also found two inputs to the checks with no stated outcome:

- a later contract check with no stored pin;
- a grant whose kind does not match the credential.

## Decision

1. **One shared implementation.** `mandate_domain::fund_movement` implements
   [DEC-839](DEC-839.md) item 3, as #888 amends it. Both `mandate-mcp` and `mandate-connections`
   use it. E7-12's check 1 applies it to every key permission, OAuth scope, and MCP tool name. So
   the MCP client and check 1 refuse the same names, and a name one of them refuses can never pass
   the other.
2. **Check 7 fails closed without a pin.** A contract is pinned at the first connect only. At any
   other occasion (`reconnect`, `reauthorize`, `executor_start`, `daily`), a contract check with no
   stored pin fails as `contract_drift`, never as a pass. A connect with no pin still passes,
   because it makes the pin. This is `AGENTS.md` rule 3: ambiguity resolves to the safe default.
3. **Check 1 fails closed on a grant of the wrong kind.** What the broker reported must be the kind
   the credential is:
   - an API key's permissions for `api_key`;
   - OAuth scopes for `oauth`;
   - MCP tools for `mcp_oauth`.

   Any other pairing fails check 1 as `scope_mismatch`. That includes a Robinhood MCP credential
   given key permissions or scopes, an Alpaca OAuth credential given key permissions or tools, and
   an API key given scopes or tools. The check never judges one kind's grant by another kind's
   rules.
4. **Where check 1 applies the rule.** Check 1 calls
   `mandate_domain::fund_movement::is_fund_movement_name` on every key permission, every OAuth
   scope, and every MCP tool name. The rule it applies is [DEC-839](DEC-839.md) item 3 as #888
   amends it; this decision does not restate it.

## Rationale

Every item here refuses more, and none accepts anything that [DEC-839](DEC-839.md) or #825
refused, so DEC-176 lets an agent take each one.

- **Item 1** gives both refusal points one rule. One list cannot drift from another, so a name
  refused at one point cannot pass the other.
- **Items 2 and 3** give a stated, safe outcome to inputs that had none, as rule 3 requires.

## Consequences

- #825 depends on #888: #888 must merge first, because it carries the amended
  [DEC-839](DEC-839.md) item 3 that #825's check 1 tests pin.
- #883 implements check 1 and check 7 against these tests, and calls the shared function rather
  than keeping a list of its own.

## Alternatives considered

- **Separate rules for the MCP client and check 1.** Rejected. Two lists drift apart, and then a
  name refused at one point passes the other.
- **Passing a later check with no pin, or judging a mismatched grant by its own kind's rules.**
  Rejected. Either one turns an input that should never happen into a pass.
