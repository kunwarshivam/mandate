# DEC-676: One fund-movement rule for the MCP client and connections check 1, and two checks that fail closed

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The L2 lead, under DEC-176 (every item only refuses more), on the coordinator's ruling of #883's review |
| **Story or claim** | E7-12, claim [#764](https://github.com/kunwarshivam/mandate/issues/764); tests [#825](https://github.com/kunwarshivam/mandate/pull/825), implementation #883; amends DEC-839 item 3 |

## Context

Two places decide whether a name can move funds out (CN-2):

- the MCP client (E7-16), under DEC-839 item 3;
- connections check 1 (E7-12), over key permissions, OAuth scopes, and MCP tools.

DEC-839 item 3 splits a tool's name into tokens. It refuses a name with a token in `transfer`,
`transfers`, `withdraw`, `withdrawal`, `withdrawals`, `wire`, `ach`, `send`, `payout`, `disburse`.
#825's tests for check 1 also refused `deposit`, `funding`, and `transfer_funds`, but none of them
said how a name is matched. #883's review found that a substring match and the token rule give
different answers: `get_fundamentals`, `wireless`, and `resend` contain a listed word but are
other words.

The same review found two more places where an input the checks do not expect had no stated
outcome. One is a later contract check with no stored pin. The other is a grant whose kind does
not match the credential.

## Decision

1. **One rule, one function.** A name is fund movement exactly when DEC-839 item 3's tokenization
   yields a token in this set: DEC-839's ten words, plus `deposit`, `deposits`, `fund`, `funds`,
   and `funding`. The tokenization splits the name at every character that is not a letter or a
   digit and at each lower-to-upper case change, then lower-cases each token. This amends DEC-839
   item 3's set.
   - The rule lives in one shared function, `mandate_domain::fund_movement`.
   - The MCP client (E7-16) and connections check 1 (E7-12) both call it, so both refuse the same
     names. Check 1 applies it to every key permission, OAuth scope, and MCP tool name.
2. **What the shared rule changes.**
   - **On the MCP client, a read can now be over-refused,** for example `get_deposits`. It
     behaves as DEC-839 items 4 and 5 say for any fund-movement tool. At the first connect, no
     client is returned. On a reconnect or a session start, a halted client is returned:
     openings stop and exits go on (`AGENTS.md` rule 13).
   - **`get_fundamentals` is no longer refused,** as it would be under a substring match. Its
     token is `fundamentals`, a different word from `fund`. Accepting it is not a loosening: the
     rule names words, and `fundamentals` was never one of them.
3. **Check 7 fails closed without a pin.** A contract is pinned at the first connect only. At any
   other occasion (`reconnect`, `reauthorize`, `executor_start`, `daily`), a contract check with no
   stored pin fails as `contract_drift`, never as a pass. A connect with no pin still passes,
   because it makes the pin. This applies `AGENTS.md` rule 3: ambiguity resolves to the safe
   default.
4. **Check 1 fails closed on a grant of the wrong kind.** What the broker reported must be the kind
   the credential is:
   - an API key's permissions for `api_key`;
   - OAuth scopes for `oauth`;
   - MCP tools for `mcp_oauth`.

   Any other pairing fails check 1 as `scope_mismatch`. That includes a Robinhood MCP credential
   given key permissions, and an Alpaca OAuth credential given key permissions or tools. The
   check never judges one kind's grant by another kind's rules.

## Rationale

Every item refuses more and accepts nothing that #825 or DEC-839 refused, apart from words that
were never on the list. DEC-176 lets an agent take that reading. Item 1 gives both refusal points
one rule, so a tool the MCP client refuses can never pass check 1, and the reverse cannot happen
either. Items 3 and 4 give a stated, safe outcome to inputs that had none, as rule 3 requires.

## Alternatives considered

- **Substring matching.** Rejected. It refuses `get_fundamentals`, `wireless`, and `resend`. It
  also refuses `teacher` once `ach` is in the set. A rule that refuses ordinary words invites
  allowlist exceptions, and those are where a real fund tool would slip through.
- **Separate rules for the MCP client and check 1.** Rejected. Two lists drift apart, and then a
  name refused at one point passes the other.
- **Passing a later check with no pin, or judging a mismatched grant by its own kind's rules.**
  Rejected. Either one turns an input that should never happen into a pass.
