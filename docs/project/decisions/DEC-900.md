## Context

DEC-886 item 1 drops an unknown member inside the kill switch's hard `scope` and lists it at
`/scope/<name>`. Item 6 refuses a duplicate hard member `duplicate_member`. #1204's
`decode_lenient` reads the whole `scope` through the strict decoder's duplicate scan before it
drops anything, so a duplicate nested inside an unknown member refuses the whole stop. #1204's
review found:

```json
{"scope": {"kind": "agent", "id": "x", "zz": {"a": 1, "a": 2}}}
```

which #1204 refuses `duplicate_member` at `/scope/zz/a`, though `zz` applies nothing.

The two readings:

- **(a) Refuse.** Treat the scope as hard all the way down, so any duplicate inside it refuses the
  stop, as #1204 does.
- **(b) Drop.** Drop the unknown member whole, whatever it holds, keep `kind` and `id`, and let the
  stop go through.

## Decision

1. **Option (b).** An unknown member inside the kill switch's `scope` is dropped whole and listed
   once at `/scope/<name>`, whatever it holds: a duplicate inside it at any depth, a value of any
   type, a nested object naming `kind`, `id` or a workspace, or the member itself named twice
   (DEC-886 item 6 for a non-hard member). `kind` and `id` are kept as the scope without it would
   keep them. Nothing else changes.
2. **Guard: a duplicate hard member is still refused.** `kind` or `id` named twice inside the
   scope is refused `duplicate_member` (DEC-886 item 6), with or without an unknown member beside
   it. Which agent, connection or workspace was meant cannot be resolved, so the stop's target is
   never guessed, widened, or narrowed.
3. **Guard: a dropped member never moves the target.** For every body, the kept target (`kind`,
   `id`) equals the target of the same body with the unknown member removed. Nothing inside a
   dropped member is read, so it can never change which agent, connection or workspace the stop
   applies to.
4. **Order.** This decision, then a tests-correction PR that pins items 1 to 3 (pending, with
   `xtask/behaviour-only` rows), then the implementation fix, after #1204 merges.

## Rationale

The merge coordinator ruled (b), citing `AGENTS.md` rule 13: the kill switch is always available,
and risk reduction is never denied. Under (a), a client that adds a malformed member the platform
never reads loses its stop. DEC-886 item 1 already says an unknown scope member applies nothing,
and item 6 refuses duplicates only where the meant value cannot be told: `kind` and `id`. A
duplicate inside a dropped member leaves no such doubt, since nothing in it is read. The guards
keep what item 6 protects: the stop never acts on a guessed or widened target.

## Alternatives considered

- **(a) Refuse any duplicate inside the scope.** Refuses a stop over a member that applies
  nothing, against rule 13.
- **Drop the whole scope on a malformed unknown member.** Leaves no target, or defaults to the
  workspace, which widens the stop.
- **Read `kind` or `id` from inside the unknown member, or keep the last duplicate `id`.** Guesses
  or redirects the target.
