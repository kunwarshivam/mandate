## Context

§11's `held_mismatch` anchors on the stored chain before a range: the verifier is given "one of
no version-2 `AgentModeChanged` before it, or the `held` the last one before it carried (from a
hold, a lift, or a carried copy), or none when the caller cannot read that chain". DEC-787 item 7
and workspace API §4.8.1 "Inputs" say the run folds that hold anchor from the stored chain, `seq` 1
to `from_seq − 1`, in the run's snapshot, never from a read model. Nothing derives it yet:
`HeldAnchor` (`mandate-journal`, `agent.rs`) is built by hand in tests and passed as `Unknown` by
the CLI.

The specs do not say what a prefix gives when its own records break `held_mismatch`: a hold or a
lift whose `held` contradicts its reason, a copy whose `held` differs from the carried one, or a
version 1 after a version 2. Three readings were open: (a) fold the expected hold regardless,
(b) carry the last `held` written, (c) anchor nothing.

## Decision

1. **A valid prefix gives the hold §11 carries.** The fold reads only the prefix's
   `AgentModeChanged` records, in `seq` order, by §11's expected-hold rule: `owner_hold` sets the
   hold, `owner_lift_hold` clears it, and every other record keeps it whatever it wrote (DEC-673).
   - With no version-2 `AgentModeChanged` in the prefix, the anchor is `HeldAnchor::NoVersionTwo`.
     An empty prefix (a range from `seq` 1) gives it too, and a full chain is anchored on nothing
     before it whatever the anchor says (§11).
   - Otherwise it is `HeldAnchor::Carried { seq, held }`: the `seq` of the last version-2
     `AgentModeChanged` and the expected hold after it.
2. **A prefix that itself breaks `held_mismatch` gives `HeldAnchor::Unknown`** (option (c)), so
   the range fails closed at its first version-2 record that is not a hold or a lift, as §11 says
   for a range with no anchor. A prefix breaks it exactly when the full-chain run, from `seq` 1,
   would report `held_mismatch` inside it. This mirrors DEC-885 I5 for the connection anchor: a
   chain that breaks a rule before the range anchors nothing, and the full-chain run reports the
   record that broke it.
3. **A prefix that is not the stream's own `seq` 1 to `k`, in order, gives `HeldAnchor::Unknown`
   too**: rows of more than one stream, a stream that is not an agent stream, a gap, a repeat, or
   a reorder, and an `AgentModeChanged` whose body does not parse. Such a prefix is not a chain the
   fold can read, which is §11's "none when the caller cannot read that chain".
4. **The fold judges only the hold.** It does not re-run §11's checks 1 to 6 or the other
   agent-stream checks on the prefix; the weekly full-chain run judges those (§11).

## Rationale

The anchor exists so that a range and the full chain agree (as DEC-885 I1 says of the connection
anchor). With a valid prefix, item 1's anchor is the full-chain run's own hold state at the
trusted start, so every split agrees. With a broken prefix, no anchor makes them agree: the full
chain stops at the break before the range, so whatever the range reports is a second verdict.
Reading (a) would pass ranges after a break as if the chain were sound, and (b) would carry a
value the full chain already refused. Anchoring nothing reports no rule the range does not hold
and passes no record a hold could make wrong; the range still fails closed, which is SEV-1 on a
chain that is already broken, so it raises nothing the full-chain run would not.

## Alternatives considered

- **(a) Fold the expected hold whatever the prefix wrote.** Rejected: a range after a broken
  prefix would be judged as if the chain were sound.
- **(b) Carry the last `held` written.** Rejected: it trusts the very value the full chain
  refused.
- **Refuse a non-prefix input with an error instead of `Unknown`.** Rejected: the caller would
  need a second outcome for a chain it cannot read, which §11 already names as having no anchor.
