## Context

§11's `held_mismatch` and `connection_lifecycle_mismatch` anchor on the stored chain before a
range. DEC-787 item 7 and §4.8.1 "Inputs" say the run folds both anchors from that chain, `seq` 1
to `from_seq − 1`, in the run's snapshot, and never from a read model. Nothing derives the hold
anchor yet. `HeldAnchor` is built by hand in tests, and the CLI passes `Unknown`.

Three questions were open:

- **What a prefix gives when its own records break `held_mismatch`.** The candidates were a hold
  or lift whose `held` contradicts its reason, a copy whose `held` differs from the carried one,
  and a version 1 after a version 2. The readings were (a) fold the expected hold regardless,
  (b) carry the last `held` written, or (c) anchor nothing.
- **Whether the prefix itself is verified.** §4.8.1's checks 1 to 6 cover only the range; outside
  it only the trusted-start record is checked. An anchor folded from an unverified prefix is open
  to the hot-store rewrite the threat table's "Forged trusted start" row puts in scope. Suppose a
  writer rewrites the body of an earlier `AgentModeChanged` from `owner_hold` to
  `owner_lift_hold` with `held: false` and leaves its hash columns. The fold then carries
  `held: false`, and a range that drops the hold passes: a false pass.
- **Whether the prefix is bound to the range.** An empty or truncated prefix looks like a valid
  one, and gives an anchor for a point in the chain that is not the range's trusted start.

## Decision

1. **The run verifies the prefix once, through `VerifiedPrefix::bind`.** `mandate_journal::VerifiedPrefix`
   holds the stored rows `seq` 1 to `from_seq − 1`. Its only constructor,
   `bind(rows, start, artifacts)`, refuses the rows unless all of these hold:
   - they pass §11's checks 1 to 6 from genesis, with no gap;
   - they are empty when `start.from_seq` is 1;
   - otherwise, the last row's `seq` is `from_seq − 1` and its `hash` is `start.prev_hash`.

   Its refusals are `PrefixError::Unverified` (the first failure) and `PrefixError::Unbound`. The
   prefix is read in the run's snapshot (DEC-787 item 1).
2. **Every anchor fold takes only a `VerifiedPrefix`.** `held_anchor` takes one now, and L2's
   `ConnectionAnchor::fold` will take one in its own change. The type makes an unverified fold
   impossible to write.
3. **A failed `bind` gives no anchor, so the range fails closed.** The caller passes
   `HeldAnchor::Unknown`, or `ConnectionStart::Unanchored`. The range then fails at its first
   record that needs the anchor, as §11 says for a range with none (DEC-885 item 4), and the
   full-chain run reports what broke the prefix.
4. **A valid prefix gives the hold §11 carries.** `held_anchor` reads only the prefix's
   `AgentModeChanged` records, in `seq` order, by §11's expected-hold rule: `owner_hold` sets the
   hold, `owner_lift_hold` clears it, and every other record keeps it whatever it wrote (DEC-673).
   - With no version-2 `AgentModeChanged` in the prefix, the anchor is
     `HeldAnchor::NoVersionTwo`. This includes the empty prefix of a range from `seq` 1, and a full
     chain is anchored on nothing before it whatever the anchor says (§11).
   - Otherwise it is `HeldAnchor::Carried { seq, held }`: the `seq` of the last version-2
     `AgentModeChanged`, and the expected hold after it.
5. **A prefix that itself breaks `held_mismatch` gives `HeldAnchor::Unknown`** (option (c)), so
   the range fails closed. The prefix breaks it exactly when the full-chain run, from `seq` 1,
   would report `held_mismatch` inside it. This mirrors DEC-885 I5: a chain that breaks a rule
   before the range anchors nothing.
6. **A prefix that is not one agent stream's gives `HeldAnchor::Unknown` too.** That covers rows of
   more than one stream, a stream that is not an agent stream, and an `AgentModeChanged` whose body
   does not parse. Such a prefix is not a chain the fold can read, which is §11's "none when the
   caller cannot read that chain".

## Rationale

The anchor exists so that a range and the full chain agree, as DEC-885 I1 says of the connection
anchor. That holds only if the anchor describes the same chain the range continues.

- **Verification.** A fold of unverified history would let a hot-store body rewrite hide a dropped
  hold, because the range's own checks start after the rewrite. Verifying the prefix from genesis
  makes such a rewrite fail `bind`. Binding the last row to `start.prev_hash` ties the prefix to
  the range's trusted start, which is itself checked (DEC-787 item 3), so a truncated, empty, or
  foreign prefix cannot stand in for the real one.
- **The cost** is linear in the prefix, which the fold reads anyway. §4.8.1's 1,000,000-event
  bound covers the range, not the prefix, so a range late in a long stream verifies more events
  than it reports. That is the price of an anchor that can be trusted, and the weekly full-chain
  run already walks the same events.
- **Option (c).** With a valid prefix, item 4's anchor is the full-chain run's own hold state at
  the trusted start, so every split agrees. With a broken prefix, no anchor makes them agree,
  because the full chain stops at the break before the range. Reading (a) would judge a range
  after a break as if the chain were sound, and (b) would carry a value the full chain already
  refused. Anchoring nothing reports no rule the range does not hold and passes no record a hold
  could make wrong.

## Alternatives considered

- **(a) Fold the expected hold whatever the prefix wrote.** Rejected: a range after a broken
  prefix would be judged as if the chain were sound.
- **(b) Carry the last `held` written.** Rejected: it trusts the very value the full chain
  refused.
- **Fold the prefix unverified, leaving it to the weekly full-chain run.** Rejected: a requested
  run would pass a range whose anchor a hot-store rewrite forged, and the full-chain run catches it
  only days later.
- **Verify inside each fold.** Rejected: two folds would each re-verify, and nothing would stop a
  third fold from forgetting to. One type with one constructor makes it impossible.
