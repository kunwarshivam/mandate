## Context

DEC-2342's pass appends a refusal only once its first delete has succeeded, so a vault outage
holds the close (item 3). That is safe, since the request stays open and nothing can use its code,
but it is silent: nothing tells an operator that a connect is stuck past its deadline, or that a
closed one still holds its code and token. The pass also has no fingerprint release yet, and
nothing runs it.

## Decision

1. **The alert.** The pass raises the opaque operator alert `connect_teardown_stalled`, with the
   runbook [RB-19](../../runbooks/RB-19-connect-teardown.md) and nothing else: no connection id,
   account reference, workspace or user (rule 6). It raises it when a delete the teardown owes a
   request fails at or after that request's deadline (DEC-2342 item 2: its `recorded_at` plus 660
   seconds; a `recorded_at` that cannot be read counts as past it, so such a request alerts on
   its first failed delete). The delete is either the first delete of a refusal the pass is
   holding, or a delete still owed for a request a refusal or a revoke closed. It raises it once
   per request per process: a restarted finish reads the control stream again and raises it again
   while the delete still fails. The alert changes nothing the pass does, and is SEV-2, since a
   code and a token outlive the connect they were for.
2. **The release.** The `Fingerprints` port gains `release`, called with a closed request's
   connection id and `account_ref` once that request's deletes have succeeded, once per request
   per process. A restarted pass calls it again, so a backing must treat it as idempotent. The
   release follows the deletes, so an account is never free to connect again while a code or token
   of its last connect may remain. `Unbacked` releases nothing, so the wiring does not wait for
   V2's fingerprint backing (F3).
   - The port is asynchronous, as F3's vault calls are, and a release can fail. A closed request
     is cleared only once its deletes and its release have both succeeded. Until then each pass
     deletes and releases it again, both idempotent, and a failure at or past the request's
     deadline raises item 1's alert, once per request per process.
3. **The wiring** (a second pair, after DEC-2338's #2235): the vault-backed `Teardown` logs in
   fresh as `Identity::ConnectionManager`, deletes the connection's `Code` and `Token`, counts an
   absent entry as deleted, and runs off the async runtime. The pass runs every five seconds
   (DEC-2342 item 10) and writes each alert to stderr as `operator_alert <code> <runbook>`, as
   the deployment manager does.
   - The finish is the connection manager (DEC-694 item 2), so it holds the connection manager's
     vault identity, for these deletes and for item 4's calls. The coordinator chose this over
     widening `Identity::Api`'s policy, which stays the callback's write of a code and nothing
     more. W2 first logged in as the API; the fingerprint adapter's pair moved it.
   - **The finish runs in its own process** (the conservative option, AGENTS rule 9; the founder
     asked not to be waited on). `mandate-api-server finish` holds only the connection manager's
     AppRole. It reads `MANDATE_API_DATABASE_URL`, `MANDATE_API_WORKSPACE`,
     `MANDATE_FINISH_VAULT_ADDRESS` and `MANDATE_FINISH_VAULT_DIR`, the last holding `ca.crt`,
     `connection-manager.role-id` and `connection-manager.secret-id`. Without all four, valid, it
     refuses to start with one line naming them; a directory without the connection manager's own
     pair is invalid, and no other identity's pair is read in its place. SIGTERM drains it: the
     wait between passes ends at once, a pass in flight gets five seconds to end, and the process
     exits 0. A pass still running then is abandoned, which is safe: every pass reads the control
     stream again, appends at the head it read, and deletes and releases idempotently. Its
     runtime is then shut down without waiting, since a vault call the abandoned pass made still
     runs on a blocking thread, up to a login and two deletes at ten seconds each, and the exit
     must come within the pod's 30-second grace, which the chart sets explicitly. The API process no
     longer runs the pass and holds the API's identity alone, so a compromised API container
     reaches no connection manager credential. The chart gives the finish its own Deployment with `api.connectFinish`, one
     replica from the API's image, holding the connection manager's AppRole alone, and takes that
     AppRole out of the API pod (#2269's `api.connectionManagerBinding` is gone).
   - **Considered and not taken:** both AppRoles in the API pod, for staging only, with the split
     before production. It widened the blast radius on a credential path (#2269's review, N2), a
     DEC-79 call, so it stayed Proposed until this option replaced it.
4. **The fingerprint port over the vault** (DEC-2345). For a request whose connect check passed,
   `VaultFingerprints` logs in fresh as the connection manager, reads the request's fingerprint
   entry by its connection id and `account_ref`, and requires the entry's reference to equal the
   check's `account_pii_ref`. It then claims the hash: `Claimed` judges the account unique, and
   `HeldBy` another connection judges it already connected to that one. A mismatched reference,
   a missing entry, a rotating key, an outage, a failed login, an identity that is not the
   connection manager's, or a clock that cannot be read claims nothing and cannot answer, so
   the connect waits for its deadline and is torn down. The port never judges
   `AccountMismatch`: DEC-2345 gives no signal for it, and a connection's own earlier claim
   answers `Claimed`. `release` gives back the request's claim, and any failure is item 2's
   failed release. The finish process passes this port, never `Unbacked`.

## Rationale

DEC-2342 item 3 trades a prompt close for a safe one during a vault outage. The alert makes that
trade visible without making it unsafe: it reports, and decides nothing.

## Alternatives considered

- **Append the refusal anyway after a deadline's worth of failed deletes.** That would journal a
  close the vault had not honoured, which §9.8 forbids, and leave the code usable.
- **Alert on the first failed delete.** A vault restart would page for nothing; before the deadline
  the request is still within its own time.
- **Release the fingerprint with the refusal, before the deletes.** The account could then be
  connected again while the old code was still in the vault.
