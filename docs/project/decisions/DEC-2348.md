## Context

DEC-2342's pass appends a refusal only once its first delete has succeeded, so a vault outage
holds the close (item 3). That is safe, since the request stays open and nothing can use its code,
but it is silent: nothing tells an operator that a connect is stuck past its deadline, or that a
closed one still holds its code and token. The pass also has no fingerprint release yet, and
nothing runs it.

## Decision

1. **The alert.** The pass raises the opaque operator alert `connect_teardown_stalled`, with the
   runbook [RB-19](../../runbooks/RB-19-connect-teardown.md) and nothing else: no connection id,
   account reference, workspace or user (rule 6). It raises it when a delete the teardown owes a
   request fails at or after that request's deadline (DEC-2342 item 2: its `recorded_at` plus 660
   seconds; a `recorded_at` that cannot be read counts as past it, so such a request alerts on
   its first failed delete). The delete is either the first delete of a refusal the pass is
   holding, or a delete still owed for a request a refusal or a revoke closed. It raises it once
   per request per process: a restarted API reads the control stream again and raises it again
   while the delete still fails. The alert changes nothing the pass does, and is SEV-2, since a
   code and a token outlive the connect they were for.
2. **The release.** The `Fingerprints` port gains `release`, called with a closed request's
   connection id and `account_ref` once that request's deletes have succeeded, once per request
   per process. A restarted pass calls it again, so a backing must treat it as idempotent. The
   release follows the deletes, so an account is never free to connect again while a code or token
   of its last connect may remain. `Unbacked` releases nothing, so the wiring does not wait for
   V2's fingerprint backing (F3).
   - The port is asynchronous, as F3's vault calls are, and a release can fail. A closed request
     is cleared only once its deletes and its release have both succeeded. Until then each pass
     deletes and releases it again, both idempotent, and a failure at or past the request's
     deadline raises item 1's alert, once per request per process.
3. **The wiring** (a second pair, after DEC-2338's #2235): the vault-backed `Teardown` logs in
   fresh as `Identity::Api`, deletes the connection's `Code` and `Token`, counts an absent entry as
   deleted, and runs off the async runtime. `main.rs` spawns the pass every five seconds (DEC-2342
   item 10) only when the connect is bound, and writes each alert to stderr as
   `operator_alert <code> <runbook>`, as the deployment manager does.

## Rationale

DEC-2342 item 3 trades a prompt close for a safe one during a vault outage. The alert makes that
trade visible without making it unsafe: it reports, and decides nothing.

## Alternatives considered

- **Append the refusal anyway after a deadline's worth of failed deletes.** That would journal a
  close the vault had not honoured, which §9.8 forbids, and leave the code usable.
- **Alert on the first failed delete.** A vault restart would page for nothing; before the deadline
  the request is still within its own time.
- **Release the fingerprint with the refusal, before the deletes.** The account could then be
  connected again while the old code was still in the vault.
