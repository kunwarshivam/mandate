# DEC-994: `mandate db migrate`: one ledger, the takeover from `deploy/`, and the command's interface

| | |
|---|---|
| **Status** | Accepted (agent; reversible engineering under DEC-79, readings under DEC-176) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (lane K0 builder) |
| **Story or claim** | E21-50, claim #1452; [managed-cells plan](../tasks/managed-cells.md) lane K0; ADR-0001 ES-08; infrastructure OPS-13 and §7.2 |

## Decision

1. **The interface K1 and S2 consume** is `mandate db migrate --journal <DSN> [--schema <name>]`,
   nothing more. `--schema` defaults to `journal`, the schema `deploy/bootstrap.sh` and the cell
   use. The DSN is a `SecretString`; prefer one without a password (`PGPASSWORD` or a mounted
   `PGPASSFILE`, so the secret stays a mounted file, DEC-822 item 4). No output or refusal shows
   any part of it, and a DSN that does not parse is refused like one that does not connect.
   Standard output is one line per file (`already applied <file>` or `applied <file>`), preceded by
   `took over <n> files from deploy.migrations` when that happens, and ended by
   `schema <name> at version <n>`. The exit status is 0 only when the schema is at this build's
   version. A refusal exits non-zero with `db migrate refused: <code>: <message>` on standard error
   and nothing on standard output. The codes are `schema_invalid`, `unavailable`,
   `privilege_missing` (the connecting role may not create a missing role or the schema),
   `owner_role_not_held`, `schema_not_owned`, `schema_unrecorded`, `schema_newer`,
   `migration_changed`, `migration_out_of_order` and `migration_failed` (with the file and
   Postgres's SQLSTATE, never the driver's text).
2. **What one run does,** in one transaction under one advisory lock, so two Jobs never
   interleave and any refusal or failing file rolls back everything, roles and schema included:
   create `mandate_journal_owner` and `mandate_journal_app` `NOLOGIN` when missing (tolerating a
   concurrent run in another database creating the same one); refuse unless the connecting role
   can `SET ROLE mandate_journal_owner`; create the schema owned by the owner role, or refuse one
   another role owns; then, acting as the owner, grant the application role `USAGE` on the schema
   and apply each unapplied file in order. The connecting role needs to create roles (when
   missing) and schemas and to `SET ROLE` the owner: the cell's Postgres superuser, as
   `deploy/bootstrap.sh` uses `postgres`. Login roles for the processes, and their `search_path`,
   stay the deployment's job (the chart's, or the bootstrap's).
3. **One ledger:** `<schema>.schema_migrations` (`version`, `file`, `sha256` in lowercase hex as
   `sha256sum` prints it, `source`, `applied_at`), owned by the owner role and readable by no
   other (`REVOKE ALL FROM PUBLIC`). It replaces the sqlx embedded migrator (`migrator()` and its
   `_sqlx_migrations` table are gone; the Postgres tests migrate through the same runner), and it
   lives in the migrated schema, so tests can migrate a schema each in one database.
4. **Taking over `deploy/`:** on the first run against `journal`, when the ledger does not exist
   and `deploy.migrations` does, its rows are vouched for by the same check as the ledger (each
   file's version is the number its name starts with) and copied in with `source`
   `deploy.migrations`; nothing is applied again. A row the build does not know, or whose digest
   differs, refuses the run with nothing created. From then on `deploy/bootstrap.sh` skips its own
   migration loop whenever `journal.schema_migrations` exists, so the two never run beside each
   other; on a fresh host the bootstrap still applies `migrations/` (the binary is not on the host
   yet) and the command takes it over later. `deploy.migrations` is left in place, unread.
5. **Refusals, all before anything is applied** (the readings that only tighten, DEC-176): a
   ledger holding a version beyond this build's is `schema_newer`, checked first, so a downgrade
   is always named as one, and the newest such version is the one named; a ledger that is not
   exactly versions 1 to n is `migration_out_of_order`; a recorded file whose name or SHA-256
   differs is `migration_changed`; and a schema holding any relation, function or type with no
   ledger (or no `deploy.migrations` rows vouching for it) is `schema_unrecorded`. An empty schema
   the owner role owns counts as fresh.
6. **"The existing xtask lint" ES-08 and OPS-13 name did not exist.** It is now a clippy
   `disallowed-methods` entry in `clippy.toml`, run by `cargo xtask`'s lint job (`clippy -D
   warnings`): `mandate_journal_pg::migrate::{migrate, migrate_dsn, migrate_known}` and sqlx's
   `Migrator::run` and `run_direct` are refused everywhere except where an `#[allow]` with a
   reason says why: `mandate db migrate`'s one call site, the runner's own entry points, and the
   tests. A process that tried to migrate at start fails the lint. This only tightens (DEC-176).
7. **For K1 (#1432) and S2 (#1435):** run the command as a Job before any process rolls (Helm
   `pre-install,pre-upgrade` hooks, or the Compose service every process `depends_on` with
   `condition: service_completed_successfully`), with `backoffLimit` retries for a database that
   is still starting. Do not run it on `helm rollback` (no `pre-rollback` hook): migrations are
   expand-only (infrastructure §7.2), so an older release runs on a newer schema, but the older
   command refuses that schema `schema_newer` by design.

## Rationale

One transaction makes "refuse, having changed nothing" true by construction rather than by care,
and Postgres's transactional DDL allows it. Keeping the ledger beside the schema it describes,
and taking over `deploy.migrations` once rather than writing both, gives one record without
asking the founder to change the demo host's bootstrap order. The ledger check is a pure function,
fuzzed against an oracle of its own, so its rules can be read and tested apart from the database.

## Alternatives considered

- **Keep sqlx's migrator behind the command:** a second ledger beside `deploy.migrations`, which
  the backlog row rules out, and sqlx's checksum (SHA-384) is not the digest the host recorded.
- **Use `deploy.migrations` itself as the ledger:** no copy, but one table per database cannot
  describe a schema per test, and the name ties the cell to the demo host's script.
- **Make `deploy/bootstrap.sh` call the command:** one code path, but the bootstrap runs before
  the binary is on the host (`deploy/FOUNDER-STEPS.md`), so it would change the founder's steps.
- **Let the older command accept a newer schema on rollback:** convenient for a rollback Job,
  but it is exactly the downgrade the lane must refuse; the chart simply does not run it then.
