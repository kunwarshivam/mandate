## Decision

1. **The session.** With sign-in on (DEC-211), the browser trades the sign-in client's access token
   for the API's own cookie with `POST /v1/sessions` before its first read
   (`web/src/api/session.ts`, `web/src/lib/api-session.ts`). It refreshes the cookie every four
   minutes, one minute inside the five-minute access lifetime, with `POST /v1/sessions/refresh` and
   a fresh token, or `null` when the sign-in provider does not answer, which the API reads as an
   outage that keeps only pause and the kill switch. A read answered 401 opens the session again
   once and reads again. `DELETE /v1/sessions/current` signs out.
2. **One tab at a time.** A refresh rotates the cookie's secret, and a rotated secret presented again
   ends the session (§3.11 item 6). So a refresh holds one exclusive Web Lock that every tab shares,
   reads hold the same lock shared and never run during a refresh, and commands take no lock and
   never wait (API-7). A `BroadcastChannel` carries only the time of the last refresh, so a tab
   that learns another refreshed within the last two minutes does not refresh again. A browser
   without Web Locks serializes within the tab.
3. **Nothing stored.** The token stays with the sign-in client; the keeper puts it only in a request
   body, never in browser storage or a URL.
4. **Signed out shows nothing.** No session can be opened (no token, or the API refuses it): every
   screen says "Sign in to see your workspace" with a link to sign in, and nothing is read.
5. **An unread membership is its own state.** A read answered 503 `membership_unavailable` (§3.5)
   shows "Your membership could not be read" and no data, not the deployment unreachable. Stop still
   opens and still sends its request; the API answers for itself whether it records it (DEC-1007
   item 8, Proposed).
6. **No session without sign-in.** With sign-in off (the fixtures, the e2e build's mock API at
   `/v1`), the runtime opens none.

## Rationale

Lane A1 relayed the session routes on 2026-10-17. The cookie is host-only on the API's host, so only
the browser can hold it (DEC-975 item 1). Serializing refreshes is what keeps one owner with several
tabs from ending their own session by reuse; letting commands skip the lock keeps Stop from waiting
on a slow refresh. Showing the two new answers as their own states keeps rule 3: neither is shown as
data, and neither is mistaken for a deployment that is down.

## Alternatives considered

- **Refreshing in every tab on its own timer.** Two tabs would present the same rotated secret and
  end the session.
- **Holding commands behind the lock too.** A refresh that hangs would hold Stop; refused (API-7).
- **Keeping the token or the refresh time in `localStorage` to share it.** Puts a credential in
  browser storage (brief §5, rule 6 row); the lock and a channel that carries only a time do the job.
