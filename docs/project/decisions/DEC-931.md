# DEC-931: the mutation job optimises what no mutant rebuilds, so a `mandate-executor` shard's tests fit their cap

| | |

| **Date** | 2026-10-16 (UTC) |
| **Decided by** | The mutants-executor-timeout builder (agent), on the coordinator's choice of option 1, under DEC-79 and DEC-176 |
| **Story or claim** | CI correction for [#1337](https://github.com/kunwarshivam/mandate/pull/1337)'s `mutants (k/21)` timeouts; [DEC-464](DEC-464.md), [DEC-498](DEC-498.md), [DEC-519](DEC-519.md), [DEC-538](DEC-538.md), [DEC-873](DEC-873.md) item 5 |

## Decision

1. **Every build the mutation job makes is at `opt-level = 1`**, for the `dev` profile and the
   `test` profile that inherits it, except in the packages named in item 2. xtask adds
   `CARGO_PROFILE_DEV_OPT_LEVEL=1` and `CARGO_PROFILE_TEST_OPT_LEVEL=1` to `MUTANT_BUILD_PROFILE`,
   beside DEC-519's no-debuginfo settings. The `mutants` matrix sets the same two values, so they
   are part of rust-cache's key, as DEC-519 does for debuginfo.
2. **The packages a mutant can make cargo rebuild stay at `opt-level = 0`.** These are each
   package with a mutant in the run, and each workspace package built on one of them through any
   kind of dependency (`unoptimised_packages`, from the `workspace_closure` DEC-497 already uses).
   xtask passes `--config=profile.{dev,test}.package.<name>.opt-level=0` for each one. It goes to
   the pre-flight's `cargo nextest list` and, as `--cargo-arg`, to every cargo invocation of
   `cargo mutants`: the baseline's and each mutant's, build and test alike. A mutant therefore
   rebuilds what it rebuilt before, at the cost it had. Cargo has no environment form for a
   package override, so this part is arguments, not environment.
3. **Debug assertions and overflow checks stay on.** Cargo's `dev` profile enables both whatever
   its `opt-level` is. `the_mutants_job_keeps_assertions_and_overflow_checks` holds that the
   workspace `Cargo.toml` turns neither off for `dev` or `test`, and it was shown to catch a
   manifest that does. Optimisation changes how fast a test runs, not what it asserts.
4. **DEC-498's caps and budget stand unchanged.** The caps are `MUTANT_TEST_TIMEOUT` 180 s (it
   also caps the baseline's tests) and `MUTANT_BUILD_TIMEOUT` 60 s, so the three capped phases
   still cost at most 420 of a shard's 600 seconds. The matrix, one mutant per shard, one worker,
   the tested packages, the baseline, the pre-flight and the zero-survivor rule are untouched.
5. **DEC-873 item 5's closed world admits exactly two more names**, `CARGO_PROFILE_DEV_OPT_LEVEL`
   and `CARGO_PROFILE_TEST_OPT_LEVEL`, so seven in all. An optimisation level selects no feature,
   dependency or `cfg`, so the live-build check reads it as it reads the debuginfo names. The
   release profile's level stays refused, and so does every name that could turn debug assertions
   or overflow checks off: `every_cargo_name_but_the_seven_cannot_be_read` names them. That is the
   one edit this decision makes to DEC-873, recorded on its status line.

## Rationale

### What failed

#1337 (E7-6, touching `mandate-journal` and `mandate-executor`) failed 14 of its 21 shards in run
[38866039803](https://github.com/kunwarshivam/mandate/actions/runs/38866039803). Its mutants
were never the problem. The **unmutated baseline** timed out: `TIMEOUT Unmutated baseline in 26s
build + 180s test`. Nextest ran 648 of the 709 `mandate-executor` tests, all passing, in 179.6
seconds, then sent SIGTERM. The runner ran two tests at a time. The finished tests' times add up
to 346 seconds, mostly the `properties` suite (8 to 24 s each) and `rule_13_holds_over_random_scripts`
(41 s), with about twenty properties still to run. The same failure was seen before #1345's
profile fix, so it comes from the suite, not from the diff. No `mandate-executor` mutant could
be judged at all, so the gate failed every PR that changes that crate.

### Why not raise the cap

DEC-498 item 5 prices the baseline's tests and a mutant's tests at one cap each. An unoptimised
executor phase of roughly 285 seconds would need the baseline cap and the mutant cap together to
use more than the ten-minute limit before any remainder (DEC-464). Fewer proptest cases or bigger
runners were ruled out: the first judges mutants by less evidence, and the second is spending.

### Why not optimise everything

Run [38870140804](https://github.com/kunwarshivam/mandate/actions/runs/38870140804) (a
`workflow_dispatch` of #1337's head with every build at `opt-level = 1`, from a cold cache)
brought the executor baselines down to **21 to 40 s** of test. But every viable mutant it reached
ran out of its build, `TIMEOUT … in 60s build`, because the mutated crate and everything built on
it were now compiled optimised. Four of its shards never started: "recent account payments have
failed or your spending limit needs to be increased". So CI was not run again (below).

### What this decision measured

Measured locally on #1337's head (4 cores, nextest at 2 test threads as on CI's runner,
`CARGO_INCREMENTAL=0`, debuginfo off). The mixed profile is items 1 and 2: optimised, with
`mandate-executor`, `mandate-journal` and `mandate-refcases` kept at 0.

| Phase | Unoptimised | Mixed profile |
|---|---|---|
| `cargo nextest run -p mandate-executor`, all 709 passing | 163 s | 41 to 43 s (86 s at one test thread) |
| Rebuild of the three tested packages after a `mandate-executor` edit | 19 s | 19 s |
| The same after a `mandate-journal` edit | 25 s | 26 s |
| Cold build of the three tested packages, `-j2` | 39 s | 59 s |

The test phase is about four times shorter and the mutant rebuild is unchanged. Scaled to CI by
the unoptimised ratio (285 s on CI against 163 s here), the executor baseline should take about
75 s of its 180-second cap. The suite's hot code is in the layers under the executor and in
dependencies (`sha2`, `ruint`, `rust_decimal`, `proptest`), which this profile optimises.

End to end, `MANDATE_MUTANT_SHARD=0/21 cargo xtask ci mutants` on #1337's head with this change
reported `ok Unmutated baseline in 30s build + 43s test` and `1 mutant tested in 2m: 1 caught`,
in 179 seconds. That shard's mutant (`schema_version -> u64 with 0`) was a 60-second build
timeout under the all-optimised profile.

### The remainder (DEC-498 item 6, item 9)

Not measured on CI, because billing stopped the second run: the cold-cache cost. Changing the
matrix's environment changes rust-cache's key, and optimised dependencies take about half as long
again to build from cold (39 s against 59 s here). A PR's first run after this merges therefore
builds its dependencies from nothing. The all-optimised cold run spent 4m10s in the pre-flight
and 85 to 132 s in the baseline build. A shard there that judged one mutant at the build cap took
9m27s, and this profile compiles the mutated layers unoptimised, which is cheaper than that run.
This term is named, not bounded. If it overruns, the failure is loud (a cancelled job at ten
minutes, which `full` refuses), and DEC-498 item 8 applies: the matrix is not the answer.

## What holds it

- `the_mutants_job_builds_without_debuginfo` requires the four `MUTANT_BUILD_PROFILE` settings on
  the job's building children and in the matrix's environment.
- `only_what_a_mutant_rebuilds_stays_unoptimised` checks `unoptimised_packages` on a fixture graph
  and on the repository's own. A `mandate-executor` mutant keeps `mandate-executor`,
  `mandate-refcases` and `mandate-shell` unoptimised and optimises `mandate-journal`,
  `mandate-canon` and `mandate-num`. The test also requires the configuration on the pre-flight
  and, as `--cargo-arg`, on the run. It fails on a seeded bug that keeps only the mutated
  packages themselves unoptimised.
- `the_mutants_job_keeps_assertions_and_overflow_checks` covers item 3.
- `every_cargo_name_but_the_seven_cannot_be_read` and
  `a_repository_shaped_workflow_passes_the_closed_world` cover item 5.
