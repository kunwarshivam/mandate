# DEC-662: Action-bound step-up: how each failed check is reported, and in what order

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | Agent (lane L1 builder), accepted by the lane L1 lead under DEC-79 and DEC-176: each item refuses, and none loosens a rule |
| **Story or claim** | E9-4, claim [#759](https://github.com/kunwarshivam/mandate/issues/759); identity spec §7.2, §7.3, §10.1; mandate spec §6.1 |

## Decision

Identity spec §7.2 step 6 names five refusal codes but does not map every check of step 4 to one.
`mandate_passkey::stepup::consume` reads them as follows.

1. **A challenge for another principal or workspace is `step_up_mismatch`.** It is bound to
   another subject, as a challenge for another action digest is.
2. **A credential that is not the principal's, or is still in its enrolment cool-off (§10.1), is
   `step_up_missing`.** Mandate spec §6.1 counts evidence that does not count as missing.
3. **An assertion that does not verify is `step_up_missing`.** That covers the signature, user
   verification, the counter, the origin, the RP ID, and the challenge. The passkey refusal
   (`mandate_passkey::Refusal`) is kept as its detail.
4. **`cli_confirm` in a `live` environment is `step_up_method`** (§7.3). `passkey` is accepted in
   both environments. Live `cli_confirm` on the founder's own Robinhood connection (mandate spec
   §6.1, DEC-529 item 3) is judged by E7-11's path, not by this crate, so refusing it here only
   tightens.
5. **A challenge is usable from its `issued_at` until just before its `expires_at`.** Expiry is
   exclusive. Presenting it at a time before `issued_at` is stale, so clock skew fails closed, as
   mandate spec §6.1 does for `authenticated_at`.
6. **Order.** The method is checked first (§7.3), before anything is read. Then §7.2 step 4's
   checks run in the spec's order:
   1. the challenge exists;
   2. it is unused;
   3. it is not expired;
   4. it names this principal and workspace;
   5. the credential is the principal's and past its cool-off;
   6. the assertion verifies;
   7. the submitted action, both its kind and its digest, equals the challenge's.

   The first failure names the refusal, so each code is deterministic. A test that combines two
   failures pins the order, and so does a property over every combination.

   Step 6 runs in `mandate_passkey::verify`'s order (DEC-660): the credential ID, then
   `clientDataJSON`, then the authenticator data (RP ID hash, user presence, then user
   verification), then the backup flags, then the signature, then the counter. §7.2 step 4 lists
   the signature, user verification, and the counter; that list is read as what step 6 must all
   hold, not as an order inside one verification. Each of them is refused as `step_up_missing`
   (item 3), so the step-ups refused and the API's answer are the same under either order, and
   only the passkey detail kept differs. That adds no risk, and accepts nothing §7.2 would refuse
   (the lane L1 lead's ruling, DEC-176).
7. **Consumed in the same transaction.** `consume` is pure. It returns the evidence
   `{assertion_id, authenticated_at, method}` and the used marker together, and the caller commits
   both with the action's event (§7.2 step 5). `assertion_id` is the challenge ID, and
   `authenticated_at` is the challenge record's `issued_at`. The gesture happened somewhere
   between `issued_at` and the instant `consume` judges it, up to 300 s later, and nothing
   `consume` reads says when. Stamping the judging instant would let the runtime honour the
   evidence up to about 600 s after the gesture under mandate spec §6.1's 300 s window, against
   identity spec §7.1's "within the last 300 seconds". `issued_at` is the earliest bound on the
   gesture, so the window can only close early, never late: it fails closed (DEC-176, ruled by
   the lane L1 lead). The lower bound costs nothing: the effective time the runtime judges at is
   never before the server's `submitted_at`, set at receipt (workspace API spec), which follows
   the gesture and so `issued_at`. Only `consume` builds `Consumed` and `Used`, and only
   `ChallengeRecord::issue` builds a record, deriving `expires_at` itself, so no caller can
   forge evidence or stretch a challenge's lifetime.
8. **Re-verification.** `reverify` checks a stored raw assertion against the record and the stored
   public key, judging everything except the counter, which has moved on since (§7.2 step 5).

## Rationale

Every reading refuses, so none can let an action commit that the spec would refuse. Fixing the
order makes the API's reason code and the journal's the same whatever combination of faults a
request carries.

## Alternatives considered

- **`step_up_missing` for a challenge bound to another principal.** That would hide a binding
  failure behind the code for absent evidence, and the API would tell the caller less.
- **Judging the action digest first.** The spec lists it last. Running the cheap binding checks
  before the signature matters little in a pure function, and following the spec's order keeps
  the codes the spec's.
