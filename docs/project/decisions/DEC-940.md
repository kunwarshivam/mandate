# DEC-940: The live cycle hands each wake's answers to the runtime and waits for the grant

| | |
|---|---|
| **Status** | Accepted (agent: reversible engineering readings under DEC-79, each one under DEC-176 — every reading holds, refuses or sends nothing where the code before it sent nothing too) |
| **Date** | 2026-10-16 (UTC) |
| **Decided by** | `claude-code` (builder, the G1b grant-cycle lane), under DEC-79, DEC-176 and DEC-921 |
| **Story or claim** | E7-26; G1b and LT-10 of the [first live trade brief](../tasks/first-live-trade.md); claim [#1365](https://github.com/kunwarshivam/mandate/issues/1365); DEC-912, DEC-914, DEC-920, DEC-923 |

Before this, `wait_for_the_grant`, `answers`, `cross_check_the_opening`, `watched` and `lt10` in
`mandate-paper` had no production caller. A cycle whose classifier said `ask` journaled its
request and stopped with `autonomy_not_auto`, and the shell tailed the control stream only at a
cycle's open. Nothing in a run handed a later answer to the runtime, so an `ask` opening could
only die at its deadline. These are the readings the call sites take.

## Decision

1. **An asked cycle stays open (`ProductionCycle::run_observed_asked_watched`).** The shell opens
   the cycle as before. When the cycle never asks, the run is the run it was: the wait is never
   called and the watch asks the shell's own `watch_may_end`. When it asks:
   - a dry run (no `--place-one-order`) stops at the ask as before, because it appends to no
     journal an answer could reach;
   - a placing run hands its open session to the runner's wait as an `AskedCycle`.
   The session stays private to the shell (DEC-475); the runner reads, wakes and releases through
   three calls only: `agent_rows`, `wake`, and `submit`.
2. **The opening is held until the runner releases it.** While the wait runs, a risk-adding
   submission stops at the shell's broker door after its `OrderSubmitted` is journaled, exactly
   where a dry run's `would_place` stops, and is held. Only `AskedCycle::submit` sends it, once.
   A wait that stops, or returns with the opening still held, sends nothing and the run refuses
   (`Cause::Absent`, "the held opening the grant wait released"). The held order's journaled
   `OrderSubmitted` is then an unsent submission, which the next start's reconciliation resolves
   as it resolves a crash between the journal and the send. Exits and protective orders are
   never held (rule 13): the hold applies only to a purpose that adds risk.
3. **Each wake hands the answers to the runtime.** `wake(now)` moves the session's event time to
   `now`, reads the workspace control stream whole, hands every row to the runtime as
   `Input::Journal` in journal order (the runtime's copy fold makes repeats inert, EI-3), ticks
   the risk clock to `now`, and returns both streams as the journal reads them. The runtime then
   writes its own `ApprovalResponded` and `ApprovalRevalidated` (DEC-920 item 1). During a wake
   the classifier's `ask` is not a stop: re-validation re-classifies the bound order, and an
   `ask` by the same trigger is what the grant answered. The runtime's `ApprovalRevalidated`
   decides, and the runner's fold reads it. Every other refusal stops the wait.
4. **The runner's frame (`granted_opening`).** It binds the ask off the agent stream (DEC-914
   item 1), then `wait_for_the_grant` re-reads per wake through `AskedCycle::wake` at the watch's
   poll interval, so the release is `answers`/`grant` over the runtime's admitted, re-validated
   records and never a raw answer. Then `cross_check_the_opening` runs, and only then `submit`.
   The cross-check reads the registered gate's own collar members, the pinned instrument's asset
   class and 20-day median dollar volume, the preflight's IEX ask as the independent quote, and
   the broker's own ask from a new port, `Session::broker_ask`. For Alpaca that is the same IEX
   quote, so the check passes trivially on the paper path. For Robinhood it is `None` until the
   MCP session reads a quote (O2), so a live asked opening refuses `quote_absent` and nothing is
   sent.
5. **The asked run's watch ends through `watched` and `lt10`.** After the submit, the shell's
   watch asks `lt10_end`, which is `watch_may_end` (the cap, `watched`, `lt10`) in the shell's
   terms: settled ends the run, unsettled reads on, the cap fails closed with the shell's own
   `cancel_unconfirmed`, a bound no session holds refuses, and any other answer fails closed.
   A paper `auto` run keeps the shell's own `watch_may_end`; the two answer the same facts the
   same way.
6. **Gaps found, not fixed here.** Each fails closed: the opening is refused and nothing is
   sent. Until all three are fixed, no grant can open a position in any build:
   - **No mark reaches the runtime.** No production code journals `MarkUpdated`, so an ask
     records `reference_mark: null`, drift cannot be computed, and re-validation skips every
     grant with reason `drift` (DEC-156 item 3). Pinned by
     `a_grant_with_no_mark_is_skipped_and_never_released`.
   - **A granted intent has no execution policy.** `mandate-runtime`'s `bound_proposal` sets
     `execution: None`, and the production `ExecutorSink` refuses an order intent without one.
     Pinned by `a_granted_intent_without_its_policy_stops_at_the_sink`. The shell probes use a
     test-only sink that supplies the fixture's policy, so they can test the hold behind it.
   - **The grant is judged against the preflight's quote.** The binding gate judges the
     preflight quote's age at the executor's hand (`judge_submission_time`,
     `iex_quote_max_age_s`), so a grant answered later than that bound is refused there.
7. **No runtime tick at or past the deadline.** A wake at or after the ask's deadline hands the
   runtime nothing; the fold denies `approval_timed_out` with no read. The runtime's own timeout
   record, `ApprovalTimedOut`, is catalogued but has no registered payload schema, so its append
   is refused as `Invalid`. The approval stays pending on the journal for the runtime's own fold
   (DEC-912 item 1).

## Rationale

The wait has to hold the submit while the runtime does the admitting, and the runtime hands its
intent and the executor submits inside one step. So the hold sits at the one place every
submission already passes: the shell's broker door, where the write-ahead check and the
one-order door are. Holding there needs no change to the runtime or the executor, and it keeps
the release where DEC-920 put it: on the runtime's own records, read back by the runner's fold.
Reading the answers in the wake rather than in a second tail keeps one path into the runtime.

Each gap in item 6 is outside this lane's crates (runtime, executor, journal), and each refuses
rather than sends, so the wiring lands as a stop that is correct today. Fixing any of them is a
safety-critical change of its own.

## Alternatives considered

- **Check the grant inside the shell before handing the answer to the runtime.** Rejected: it
  is a second admission, which DEC-912 and DEC-920 reject.
- **Have the runner hold the intent rather than the submission.** Rejected: the intent is the
  runtime's handoff inside one step, so the runner could only see it after the executor had
  already asked to submit.
- **Wait in a dry run too.** Rejected: a dry run appends to an in-memory journal no answer can
  reach, so it could only time out after up to `timeout_s`.
- **Tick the runtime at the deadline so it journals its own timeout.** Rejected for now: the
  journal refuses `ApprovalTimedOut`'s payload, which would turn a clean deny into a journal
  refusal.
