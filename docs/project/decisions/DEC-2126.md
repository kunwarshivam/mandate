| **Story or claim** | E9-4 S4; claim #759; [workspace API spec](../../specs/workspace-api.md) §3.6 and §4.5; [identity spec](../../specs/identity.md) §7.2 and §7.3; [journal spec](../../specs/journal.md) §9.8 and §9.32; [DEC-2108](DEC-2108.md) items 3, 7 and 8; DEC-2125 (lane X) |

## Context

A paper connect's start (`POST /connections/oauth/start`) needs step-up of kind `connection`
([DEC-2621](DEC-2621.md) item 4). The server binds only DEC-2104's `cli_confirm` verifier, which
admits `approve` alone, so every connect is refused `step_up_method`. DEC-2125 (lane X, accepted by
the founder on 2026-10-25) lets `cli_confirm` also confirm `connection` in paper, as an interim
until passkey step-up serves it. DEC-2108 items 7 and 8 already decide the passkey wire and its
verifier for every kind the challenge route issues. This decision applies them to the connect's
start, the first route that serves them, and ends the interim.

## Decision

1. **The wire.** `commands/oauth-start-request` gains `step_up_assertion`, DEC-2108 item 7's object
   (its id member is `passkey_id`, the API's name for journal §9.31's `credential_id`, which
   DEC-2108 item 7 calls `credential_id`; DEC-2115) (`envelope.schema.json#/$defs/StepUpAssertion`)
   or `null`. It is optional, so a `cli_confirm` start written before it still decodes, and an
   absent member reads as `null`.
   - `step_up` of method `passkey` with no assertion is `step_up_missing`: there is nothing to
     judge.
   - `step_up` of method `cli_confirm` with an assertion is `invalid` at `/step_up_assertion`, one
     violation, among §3.4's body checks: a request never carries an assertion it does not rest on.
   - A `null` `step_up` with an assertion is `invalid` at the same path, before `step_up_required`.
2. **The verifier is DEC-2108 item 8's**, bound once at the server's step-up port and serving every
   kind the challenge route issues. The port dispatches on `step_up.method`: `passkey` to the
   passkey verifier, `cli_confirm` to DEC-2104's. The passkey verifier:
   - takes the held challenge (`Challenges::take`) and folds the member's credentials from the
     control stream as the request read it (`mandate_passkey::credentials::CredentialFold`, with
     each credential's last counter from its `StepUpAsserted` records);
   - judges the assertion with `mandate_passkey::stepup::consume` in its order, environment
     `paper`, and maps its refusal to the §3.5 code `StepUpRefusal::code` names;
   - on success, drops the challenge (DEC-2108 item 8: if the commit then fails, the challenge is
     gone and the owner signs again) and returns the `StepUpAsserted` draft: the challenge, the
     credential, the counter the assertion carried, and the assertion's canonical bytes to store.
   A credential fold that cannot answer is `journal_unavailable`, never a pass.
3. **The commit.** A start under passkey step-up stores the assertion's canonical bytes as an
   artifact, then appends `ConnectionRequested` and `StepUpAsserted` in one batch, in that order,
   with the assertion's `causation_id` the request (journal spec §9.32 rules 253 and 254). A start
   under `cli_confirm` appends `ConnectionRequested` alone, as today. A refused start appends
   nothing, whichever method it carried.
4. **The port grows without moving `cli_confirm`.** The step-up trait gains one method that takes
   the evidence and the assertion together and returns the draft to append, with a default that
   refuses any assertion and otherwise calls today's `verify`. DEC-2104's verifier keeps its one
   method, so lane X's DEC-2125 change and this one touch different code.
5. **Order of the changes.** The request type gains its optional member and the port its method in
   the tests change, listed as ahead of the schema in `mandate-api`'s schema test, a list that
   tolerates the schema naming it so the schema change carries no code (ES-22). The schema, its
   examples and the spec text follow in their own change. The implementation then empties the list,
   so the struct's members are checked exactly again.
6. **The interim ends per member.** Once the passkey verifier is bound for `connection`,
   DEC-2125's `cli_confirm` for `connection` ends for each member who holds a passkey past its
   cool-off: for them `cli_confirm` admits paper `approve` alone again, as DEC-2104 says, and a
   paper connect needs a passkey. For a member who holds no such passkey, `cli_confirm` for
   `connection` stays as DEC-2125 says. It only tightens: a member with no enrolled passkey enrols
   one first (DEC-2108 item 5). A first passkey waits out its 24-hour cool-off before it can step
   up (DEC-2108 item 5, rule 249), so the interim ends only once S4 has landed *and* the member
   holds a passkey past its cool-off; until both hold, paper `cli_confirm` for `connection` stays
   as DEC-2125 says.
   The change that ends it is its own small one, after S4: `CliConfirm` refuses `connection` as
   `step_up_method` exactly when the request's member holds a passkey past its cool-off in the
   control stream's credential fold as the request read it, and admits it as DEC-2125 says
   otherwise. "A passkey past its cool-off" is judged as the step-up verifier counts one: a
   `CredentialEnrolled` version 2 passkey the fold holds, past its cool-off, so a member whose only
   passkey is a version 1 enrolment, which never counts (DEC-2122 item 3), keeps `cli_confirm` and
   is never left with no method. `live` stays `live_unavailable` throughout.
7. **Scope.** This covers a connect's start. A connection's change and revoke carry the same
   member when their routes serve passkey step-up, in their own slices; a revoke with
   `compromised: true` reduces risk and never waits on step-up (identity spec §7.3).

## Rationale

- Items 1 to 3 add no rule: DEC-2108 decided the wire, the verifier, and the record for every kind,
  and §9.32 the batch. They fix only what one route does with them.
- Item 1's optional member keeps the interim's clients working while both methods are served, and
  refusing an assertion that nothing rests on keeps the request honest about what it proves.
- Item 6 is a tightening the coordinator asked for: an interim that outlived its reason would leave
  a second, weaker method for a risk-increasing action. It ends per member because a member's first
  passkey cannot step up until its cool-off ends, and ending it for everyone at once would leave
  such a member no way to connect for that day.

## Consequences

- An assertion whose members pass the wire's base64url pattern but do not decode (a length of 1
  mod 4) is answered `step_up_missing` before `consume` runs, so it reports neither
  `step_up_stale` nor `step_up_mismatch` even when those would also apply. It fails safe: no
  malformed assertion is ever accepted, and `consume` needs the decoded bytes to judge anything
  (#2403's review).

## Alternatives considered

- **A required, nullable member, as `passkey_enrol` has.** Rejected for this route: it would break
  every `cli_confirm` start written under DEC-2125 for the life of the interim.
- **A verifier per kind.** Rejected by DEC-2108 item 8.
- **Keeping `cli_confirm` for `connection` after passkeys serve it.** Rejected by item 6.
