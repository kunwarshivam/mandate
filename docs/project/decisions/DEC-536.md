| **Story or claim** | E7-19 slice 4 remainder (the first paper trade brief's J3 and D4d); [DEC-534](DEC-534.md); [first paper trade brief](../tasks/first-paper-trade.md) |

## Decision

1. **Where the overlay applies.** Mandate spec §6.2 gains step 5c, the policy overlay of §4.3. It
   applies last, after the review ceiling, so it only tightens.
   - While the confirmed version is `policy_nonconforming`, the decision becomes `deny`
     ([DEC-534](DEC-534.md) item 2).
   - Otherwise, if the effective `auto_allowed` is false, the decision becomes the stricter of the
     result so far and `ask`. This includes an `auto` that a delegation produced.
   - Step 3 has already decided every exit as AUTO, so the step never reaches an exit.
2. **The label.** Journal spec v0.18 adds `policy_overlay` to §9.1's closed `decided_by` labels.
   Mandate spec §6.4 adds it to the approval content's `trigger.decided_by`, where `trigger.rule`
   is `null`.
   - Like the three ceilings before it, the step names itself only when it changed the decision.
   - An `ask` or `deny` that a rule or an earlier ceiling had already decided keeps that source's
     label.
3. **What the record refuses.**
   - Rule 7: a decision whose `decided_by` is `policy_overlay` is never `auto`.
   - Rule 5 already refuses the label on a decision that is not an opening or an increase, and on
     a decision with no classification.
   - Neither `DecisionMade` version changes its payload: only the closed set of labels grows.
4. **The vectors.** The vectors gain a generated, additive `policy_overlay` section of
   `DecisionMade` drafts built on `agent_stream`'s chain, and stay at version 3.
   - The `agent_stream` cases and their counts are unchanged. `mandate-journal`'s live tests count
     those cases, so the new cases cannot join `agent_stream` without a code change, and ES-22 keeps
     code out of a spec PR.
   - The generator checks the section with its own validator rule `7.policy_overlay_label`. It also
     plants four validator mutants and two vector mutants, and every one must be caught.
5. **Sequence.** This is a spec PR under ES-22. Next come the J3 tests and implementation PRs, so
   that `mandate-journal` accepts the label. After them, D4d records the shell's two overlay cases
   with it.

## Rationale

The journal must say why a decision was taken. Without its own label, an overlay `ask` would have to
claim `default` or the rule that said `auto`. A DEC-534 `deny` would have to claim a rule that
never denied. Both are false records. The approver would also be shown the wrong reason for the
`ask` (§6.4's `trigger`), and an audit or replay could not tell an owner's rule from a policy.

The label only names a tightening that §4.3 and DEC-534 already require. The record cannot use it to
run anything unasked. No safety rule is loosened, which is why an agent may accept it under
DEC-176.

## Alternatives considered

- **Reuse `review_ceiling` or `default`.** Rejected: either label would name a step that did not
  decide, and every audit and replay would read it wrongly.
- **One label per cause (`policy_ask`, `policy_nonconforming`).** Rejected for now: `autonomy`
  already tells the two apart, because `ask` is the narrowing and `deny` is the nonconformance.
  One label keeps the closed set small.
- **Add the cases to `agent_stream`.** Rejected: it changes counts that live code tests assert, so
  the spec PR would need code (ES-22).
