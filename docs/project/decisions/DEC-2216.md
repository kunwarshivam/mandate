## Context

DEC-2282 says an entry is `offered` only once, on the day it is mounted, its upstream is in
OpenRouter's zero-retention list, its §4.3 identity probe passes, its prices are re-read, and its
snapshot meets INF-1. Inference spec §4.2 adds that the whole §4.3 gate passes, recorded with the
entry's content hash, before an entry is offered.

The pieces that exist (#2832):
- the registry refuses an undated non-Anthropic snapshot and a role's mismatched harness;
- `live_registry` gives an entry an endpoint only once it is offered and its probe passes.

Nothing yet:
- runs the gate;
- records the gate's result;
- probes an endpoint for real.

The model-gateway service still refuses a live start (`live_not_built`).

The gate has to call the model, and every call spends. Three constraints shape where it runs:
- Only the gateway service holds the provider key (DEC-2020).
- Only it writes the meter streams; each stream has one writer (journal spec §2, inference spec §7.3).
- No agent may call a provider with a real key.

## Decision

1. **A new purpose, `evaluation`.** A gateway call the platform makes to evaluate a registry entry
   has purpose `evaluation`:
   - It has no agent (`agent_id` `null`, as for `compiler`) and is paid by the platform's key.
   - It is reserved and settled like every call on the service's own two meter streams:
     `meter:{workspace}` for the one workspace the service is configured for (`config.workspace`,
     staging's research workspace) and `dmeter:{deployment}`. The service is the one writer of
     both. So that workspace's monthly cap and the deployment's bind it, and its spend counts
     against the same month the workspace's research draws on.
   - No daily research cap or run ceiling applies, since it has no agent and no run.
   - The journal spec's `MeterReserved` admits it (rule 156: `agent_id` is `null` exactly for
     `compiler` and `evaluation`).
2. **The gate runs inside the running service.** The command `mandate-gatewayd gate <model_id>
   --probe <socket>` asks the running service, over its probe socket, to run §4.3 on one entry of
   its live registry file. So the gate uses the service's one key and its one meter writer. The
   service:
   - registers the entry in a registry of the gate's own, apart from the one research calls
     resolve in, and probes its endpoint (item 4). So the endpoint the gate calls is never one a
     research call can reach while the entry is `evaluating`;
   - runs the probe set (item 3) as agentic research runs. The model calls go through the gateway
     with purpose `evaluation`. The tool reads are served from the probe set's fixture corpus, never
     from live data;
   - checks each §4.3 row;
   - writes the gate report to its research artifact store (DEC-2279), create-only, and prints the
     report's reference (`sha256:…`).

   It refuses with a code, spending nothing and writing no report, when:
   - the entry is unknown or not registrable;
   - either monthly cap's room is below the gate's whole maximum (item 7), so a gate never starts
     that a cap could cut off for lack of room;
   - a gate already runs;
   - the store already holds a passing report for this entry's content hash, probe set, endpoint
     and price table, so a passed gate is never paid for twice.

   Once it has called, every end writes a report. A pass sets `passed`; any other end sets `passed`
   false with a `stopped` code naming why:
   - `identity_mismatch`, at the first reported identity that differs from the pin;
   - `cap_refused`, when the meter refuses a call (another workload spent the room meanwhile);
   - `provider_failed`, when a call ends `credential_invalid`, or `provider_unavailable` or
     `deadline_exceeded` after the gateway's retries;
   - `checks_failed`, when every run ended and a check fails.

   The operator's disconnect does not stop it, since it runs in the service. A restart during a gate
   ends it with no report. Nothing resumes it, and its in-flight reservation stays counted at its
   maximum for the month, as any call's does (inference spec §7.3). **Re-runs are the operator's to
   decide.** Each costs at most item 7's maximum, and the room check above refuses one that the
   month cannot hold whole.
3. **The probe set is versioned, in the repository, and the same for every entry of the role.**
   The file is `fixtures/gate/research-probe-set.json`, with 15 runs:
   - 5 `ideate`;
   - 5 `monitor`;
   - 5 runs over the prompt-injection fixtures (RAID R-05).

   Each run names its cut-off, its seed inputs and the fixture corpus its tools read. The pass
   conditions are §4.3's. With 10 schema-checked runs, "at least 99%" means all 10. The report
   holds:
   - the entry's pin, the probe set's digest, and the endpoint and price table the gate ran
     against;
   - each call's request digest, reported identity, outcome, tokens and cost;
   - each check's verdict;
   - `passed`, and `stopped` when it did not pass.

   The probe set's current digest is the one built into the service's image. A change to the probe
   set therefore demotes every gated entry at the next start, whatever restarted it. That is
   intended: a report on another probe set is not a pass on this one. Until a new gate passes,
   research naming those entries has no output, the safe default (rule 3).
4. **The live start probes identity only.** `--registry <file>` starts the service live (DEC-2326
   item 3).
   - **What the file adds.** Beside DEC-2282's members, each entry may name `gate_report`, the
     reference of a passing report.
   - **Who is offered.** An entry the file offers is offered only if all of these hold:
     - its report reads back from the store;
     - the report names this entry's content hash, the probe set's current digest, and the
       endpoint and price table the file now names, so a changed endpoint or price needs a new
       gate;
     - the report says `passed`;
     - one `evaluation` call (the identity probe: a fixed one-line prompt, at most 16 output
       tokens) ends `ok` and reports exactly the pin's model and the endpoint's provider. A probe
       that errs, times out, is refused by a cap, or reports anything else offers nothing.

     Every other entry stays `evaluating` with no endpoint, so research calls naming it refuse
     (`policy_denied`, missing output). That holds until a gate passes, the file names the report,
     and the service restarts.
   - **Start-up checks.** The start refuses, by code, when:
     - the registry file is missing or malformed;
     - either cap is unset;
     - the key cannot be read.

     A start that offers nothing still starts, so the deployment stays ready and research waits.
     The owner's picker then lists no research model, and a running agent's research calls are
     refused `policy_denied`, so its research has no output, the safe default (rule 3).
   - **Who can write a report.** Only the service: it mounts the research artifact store
     read-write, and every other reader mounts it read-only (DEC-2279). A report is
     content-addressed and create-only, and the start re-reads `passed` and every binding from the
     report itself, never from the file's say-so.
5. **Who writes the file.** The chart renders the live registry file from its values. Those values
   list DEC-2282's vetted entries, their prices and endpoints, re-read on the day by the agent that
   opens the change (DEC-2396 item 3), and each entry's `gate_report` once a gate passes. Rendering
   it is now allowed: DEC-2326 item 1 kept it unrendered only until the founder chose, and the
   founder chose with DEC-2282. C's entry is listed, and the registry refuses it while it is
   undated.
6. **The steps after the founder's apply** (the chart's runbook, which IAC follows):
   1. The founder puts the OpenRouter key in the cell's vault (the existing runbook step).
   2. IAC applies the chart with the live registry values. The service starts live, offers
      nothing, and stays ready.
   3. IAC runs `kubectl exec deploy/mandate-gatewayd -- mandate-gatewayd gate llm.research_sonnet
      --probe /run/mandate/probe.sock`, then the same command for `llm.research_haiku`. Each prints
      its report reference and `passed` or the failing check.
   4. IAC sets each passing entry's `gate_report` in the values, applies, and the service restarts.
      It probes identity and offers the gated entries.
7. **Expected cost.** Each gate is at most 15 runs of 8 turns, each turn at most 20k tokens in and 2k
   out, so 2.4M input and 240k output tokens in total.
   - **Sonnet 5.5** (2 / 10 per million): at most $4.80 + $2.40 = **$7.20**.
   - **Haiku 5.5** (0.10 / 0.50, pinned at its highest listed tier): at most **$0.36**.
   - **Each start's identity probe:** under $0.001 per entry.
   - **Both gates:** at most about $7.56 of the deployment's $50 month. These are upper bounds; the
     meter reserves each call's maximum, so the caps hold whatever the provider bills.
8. **What is not journaled yet.** An `evaluation` call has no agent stream, and journal spec
   §9.19's `ModelInvocationRecorded` admits no `evaluation` purpose. So inference spec §3.6
   exempts evaluation calls from the call record until a record of their own is added (backlog
   E21-62w). The gate's calls are recorded in its report, an artifact named by reference. The
   start's identity probe writes no report, so its call is recorded only by its spend on the meter
   streams until E21-62w lands. Every evaluation call's spend is journaled there like every
   call's. An entry's change to `offered` is
   configuration, read from the file at start. Journaling registry status changes on the control
   stream waits for `PlatformOperatorAction` to close (journal spec §9, DEC-261 item 9). It is a
   backlog row (E21-62v), as is refusing a non-offered entry in the call path, which today holds no
   endpoint (E21-62u, #2832's review).
9. **The probe socket gains one command.** DEC-994 item 5's socket answers `livez` and `readyz`.
   It now also takes `gate <model_id>`. The socket is a Unix socket inside the pod, reachable only
   by `kubectl exec` with the namespace's exec rights, and a gate spends only under item 2's room
   check and the caps. The build is under E21-62. The code change adds the probe set
   `fixtures/gate/research-probe-set.json`, the gate command, the live start, and the chart's
   registry values, with tests first.

## Rejected

- **Running the gate as a separate Job.** It would be a second writer on the meter streams and a
  second holder of the key.
- **A lighter gate for staging,** such as the identity probe alone. The coordinator declined it.
- **Offering on the identity probe alone and gating later.** Inference spec §4.2 offers only after
  the gate.
