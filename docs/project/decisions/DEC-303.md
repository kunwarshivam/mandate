## Decision

1. **The journal's stub.** `mandate-journal` gains a `control` module. `Draft::parse` routes to it every type §9.2 closes on its stream: the control stream's nine, and `OwnerCommandRefused` on the agent and account streams. Its two entry points, `payload` and `subject_and_copy`, answer `InvalidReason::Unimplemented` (`unimplemented`), which comes back for this PR and goes with the implementation, as E7-9's did. Every draft it refuses was refused before: as `unknown_schema`, or a control stream's `StreamOpened` as `schema` (it took the account schema). **`AccountSnapshotRecorded` is not routed** (DEC-261 item 7, DEC-302): it stays `unknown_schema` until stream K's writer conforms.
2. **The mapping lives in `mandate-spec`**, as `JournaledFact::from_record(event_type, payload, documents, account_connection)`, beside the enum it builds. It reads a canonical `Value` and needs no `mandate-journal` dependency, which DEC-128 item 1 keeps out of `mandate-spec`. `documents` returns the stored document a version names, which a deployment is read from, and the mapping refuses one that is missing or does not hash to its version. `account_connection` is DEC-261 item 10's argument. A record the mapping cannot read is `Err(InvalidInput)`, never skipped, because a dropped `ConnectionRevoked` would leave a connection looking established. The stub answers `SpecError::Unimplemented`.
3. **The vectors are driven directly,** by integration tests in `crates/mandate-refcases/tests/control_stream.rs`, one per §9.2 family plus the chain and the mapping. No `src/` harness is added (E7-9 added one), so no harness code needs live tests of its own to pass the mutation gate. No `journal::control_stream::*` reference cases are added either, so `status.toml` is untouched. The implementation PR adds in-crate tests that read the vectors, as E7-9's did.
4. **The ordering pins are live, not pending.** The coordinator asked for a pending test that keeps `AccountSnapshotRecorded` unregistered before stream K's fee-step writer conforms. A pending test must fail at its own story's stub (DEC-137), but this condition holds today and must keep holding, so it is pinned by three live tests. `mandate-journal`'s `account_snapshot_recorded_waits_for_the_fee_step_writer` checks the type is still `unknown_schema`. `mandate-executor`'s `the_fee_steps_snapshot_is_never_refused_for_its_members` parses the executor's own fee-step and cash-step snapshot payloads and fails the moment a registered schema refuses one for a member. `mandate-refcases`' `snapshot_drafts_stay_unregistered` checks every snapshot draft in the vectors is refused for want of a schema. Planting the registration early (the 14 members of v0.7, before the writer fix) fails the first two; the executor's refusal came at `payload.risk_clock`, which is how DEC-302 was found. The executor test is test-only code in stream K's crate.
5. **17 pending tests** (`#[ignore = "pending E7-10"]`, plain `fn`s): 9 in `mandate-refcases`, 7 in `mandate-spec`, and 1 in `mandate-journal`. Two live tests come with them: `a_closed_control_stream_event_is_never_an_unknown_schema` and the catalogue test, which leaves the eleven (type, stream) pairs to the pending test. Each family holds a draft to accept and one to refuse, and each mapping test constructs a fact, so neither do-nothing passes any of them
6. **§9.2 leaves `MandateVersionApplied` and `UniverseChanged` to their own story** (#429 round 1, M1). §9.2 closes neither, so `from_record` maps both to none, and the fold fails closed: a deployed agent's later version and its admitted instruments are not seen. The `ValidationContext::from_journal` backlog row, which named E7-10 for them, and `JournaledFact::AgentVersionActive`'s doc comment now say so. Both name the new backlog row "account-stream risk-state records" that carries them.
7. **Every depth of a closed schema is pinned** (#429 round 1, B1). Three pending hand-written tests in `mandate-journal`'s `catalogue.rs` cover it. `step_up` with an unlisted member is refused as `schema` at `payload.step_up.<member>`. `step_up.authenticated_at` off the §4.7 form is refused as `non_canonical` there. A `provenance` entry with an unlisted member is refused at `payload.provenance[0].<member>`. On the throwaway implementation, the reviewer's three plants each fail one: `step_up` open, `authenticated_at` as text, and the `provenance[]` entry open. The ruling also asked for the same cases as `control_stream` invalid drafts, with a generator mutant for each of `step_up`'s member types. That is a tightening under DEC-176 (1), but it changes `reference/`, `docs/specs/` and `fixtures/refcases/`, which ES-22 keeps out of a PR with crate code; the spec guard would fail this PR's CI. So it ships as its own spec PR, as DEC-302 did, and the Rust tests here pin the behaviour meanwhile
8. **The implementation** (E7-10, DEC-77 stage 3). `mandate-journal`'s `control::payload` normalizes each payload against its §9.2 schema, then applies consistency rules 17 to 23 in number order. Each rule is reported only on a well-typed payload. `control::subject_and_copy` applies subject rules 25 and 26 and copy rule 27 after `artifact_refs` and `pii_refs`, which is §9.1's order. `schema.rs` gains the `pointer` type: a non-empty RFC 6901 pointer whose `~` appears only in `~0` or `~1`. `InvalidReason::Unimplemented` goes, and the tests PR's 20 `#[ignore]` lines are deleted, the only change to any test file. `AccountSnapshotRecorded` is still not routed, and rule 24 lands with its registration (item 4, DEC-261 item 7).
9. **Rule 23 reads the normalized decimal's sign.** `loss_added` is normalized on the way in (§4.6), and normalization turns `-0` into `0`. So the rule refuses exactly the strictly negative values, and the boundary `0` is accepted, as the `stopped_with_no_loss` vector requires.
10. **The mapping's errors.** `from_record` reads each member under its own name and refuses one it cannot read as `SpecError::InvalidInput { what }`, naming the member. That includes a decimal or date it cannot parse, so a parse failure never surfaces as another code. The tests PR's round-1 review found that pinned. A deployment's version becomes a `MandateVersion` only after its stored document parses and hashes to it, through a crate-private `MandateVersion::named`. The mandate records' versions name the document they are about. `mandate-spec` still has no `mandate-journal` dependency.
11. **In-crate vector tests.** `control.rs` has a `tests` module that reads `fixtures/refcases/journal.json`'s `control_stream` section: every chain event and valid draft parses, and every invalid draft is refused with its reason at its path, with snapshot drafts left out. The mutation gate runs only the mutated crate's own tests, so §9.2's rules are judged inside `mandate-journal` as well as by `mandate-refcases`, as E7-9's implementation did.

## Rationale

The tests-first stage of DEC-77 for E7-10, with DEC-261 item 7's ordering made checkable rather than only written

## Alternatives considered

A pending ordering test (cannot fail at a stub); the mapping in `mandate-journal` (layer 2 cannot see `mandate-spec`'s types) or in the executor (a second home for the fold's input); a `src/` harness in `mandate-refcases` (needs its own live tests for the mutation gate)
