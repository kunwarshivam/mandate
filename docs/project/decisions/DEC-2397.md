## Context

`mandate-gatewayd` serves DEC-2265's framed calls, and only it may call a provider (DEC-2257
item 1). The runtime's research worker still holds a `Gateway` in its own process, over the recorded
transport, with its own `CellMeter` writing `meter:{workspace}` (DEC-2259 item 1). To route the
runtime through the service, four questions are open:
- what the worker calls;
- what a lost exchange is, since DEC-2265 item 4 calls it the caller's `deadline_exceeded` but the
  caller has no record to journal;
- who writes the meter stream;
- how the runtime is told where the service is.

## Decision

1. **One port, two sides.** `mandate-research-run` gains a port, `ModelCalls`: `now()`, the
   instant a call is built at, and `call(&CallRequest) -> Result<CallRecord, RequestError>`.
   `Gateway` implements it in-process, as today. `RemoteGateway`, in `mandate-daemon`, implements it
   over `std::net` and `mandate_gateway::frame::call`:
   - one connection per call;
   - socket read and write timeouts run to the request's absolute `deadline`;
   - a reply frame bounded at `MAX_REPLY_FRAME`;
   - the host clock as `now()`.

   `research_run::call` and `turn::call` take the port, not a `Gateway`. Neither crate gains a
   dependency.
2. **A lost exchange is a refusal.** `RequestError` gains `GatewayUnreachable`
   (`gateway_unreachable`). `RemoteGateway` returns it when any of these happens:
   - the connect is refused or times out;
   - the deadline passes before the whole reply is read;
   - the reply is cut short, over its bound, or does not decode;
   - the reply is a record for another `call_id`.

   The gateway itself never returns it, so its place in `RequestError::ALL` is last, after every
   refusal the gateway checks. The core already ends a refused call's run with no output (inference
   spec §3.1), so no thesis, no proposal and no order follows: a model outage, the safe default,
   which never enlarges an order (`AGENTS.md` rule 3). It reads as a refusal, not as a
   `deadline_exceeded` record, because the caller holds no prompt or response to give a record:
   - The service has already journaled its `MeterReserved` if it reserved, and that counts at its
     maximum until settled (DEC-2265 item 3).
   - The call is never retried, under the same `call_id` or another, within the run (DEC-2265
     items 3 and 4).
   - This supersedes DEC-2265 item 4's "is the caller's `deadline_exceeded`" for the remote
     caller. The rest of item 4 stands.
3. **The service writes the meter; the runtime only reads it.** With a service address, the runtime
   builds no `Gateway` and opens no meter writer. Its research source reads `meter:{workspace}`
   through a read-only `MeterStore` that never takes the stream's writer epoch. If it took the
   epoch, it would fence the service. That read gives DEC-2259 item 2's cross-check and item 3's
   last reservation. Any append through it is refused `Unavailable`, which no path reaches.
4. **The address is explicit.** The runtime is told the service with `--gateway <host:port>` beside
   `--research`; a `--gateway` without `--research`, or with an address that does not parse, refuses
   the start (`gateway_address_invalid`). Without `--gateway` the runtime keeps today's in-process
   recorded fake (DEC-2257 item 6, DEC-2210 item 3). The chart passes `--gateway model-gateway:8080`
   to a researching runtime only when `images.model-gateway` is named.
5. **The runtime's egress is unchanged.** It already reaches only `model-gateway:8080` for models
   (inference §8.2), and the chart's policy already allows exactly that.

## Delivery

| Item | Slice | Tests |
|---|---|---|
| 1, 2 | The port and `RemoteGateway` (tests first) | a call crosses the service whole; a refused connect, a stalled reply past the deadline, a cut, oversized or malformed frame, and another call's record each read `gateway_unreachable`; no second exchange after a loss; `gateway_unreachable` crosses the wire as itself and is last in `ALL` |
| 3 | The read-only meter | a read never takes the epoch, so the service's next append is not fenced; every append refused |
| 4 | The daemon's flag and the chart | each refusal's code; without `--gateway` the in-process fake; with it, no `Gateway` and no meter writer |

## Rationale

A refusal is the one answer the core already turns into "no output", with nothing to journal on
the agent stream that the runtime cannot back with artifacts. The service's own meter record keeps
the spend counted. A read-only meter keeps one writer per stream, the journal's own rule.

## Alternatives considered

- **A `deadline_exceeded` record built by the caller.** Refused: it would have no prompt or
  response ref, which journal spec rule 148 allows only for a guard refusal.
- **Retry once on a fresh connection.** Refused: a lost reply may already have spent (DEC-2265
  item 3).
- **The runtime keeps writing the meter.** Refused: two writers on one stream fence each other.
