## Context

`mandate-gatewayd` serves DEC-2265's framed calls, and only it may call a provider (DEC-2257
item 1). The runtime's research worker still holds a `Gateway` in its own process, over the recorded
transport, with its own `CellMeter` writing `meter:{workspace}` (DEC-2259 item 1). Routing the
runtime through the service leaves five questions open:
- what the worker calls;
- what a lost exchange is;
- who writes the meter stream;
- which workspace each service serves;
- how the runtime finds the service.

On the lost exchange: DEC-2265 item 4 calls it "the caller's `deadline_exceeded`", but the caller
holds no prompt or response, so it cannot give the record journal spec rule 148 requires.

## Decision

1. **One port, two sides.** `mandate-research-run` gains `ModelCalls`: `now()`, the instant a call
   is built at, and `call(&CallRequest) -> Result<CallRecord, RequestError>`. `Gateway` implements
   it in-process, as today. `RemoteGateway`, in `mandate-daemon`, implements it over `std::net` and
   `mandate_gateway::frame::call`:
   - one connection per call;
   - the connect and every write bounded by the time left to the request's `deadline`, so a call
     already past it is never sent;
   - every read bounded by that time plus a fixed grace of two seconds, so a reply trickled a byte
     at a time still ends;
   - the host clock as `now()`.

   The grace covers the service's own deadline (`request.deadline`, inference §3.4): a reply the
   service finishes at the deadline is still read, not lost to a race between two clocks.
   `research_run::call` and `turn::call_turn` take the port. No crate gains a dependency.
2. **A lost exchange is the caller's `gateway_unreachable`.** `RequestError` gains
   `GatewayUnreachable`, code `gateway_unreachable`. `RemoteGateway` returns it when any of these
   happens:
   - the connect is refused or does not finish in time;
   - the bound passes before the whole reply is read;
   - the reply is cut short, over its bound, or does not decode;
   - the reply is a record for another `call_id`.

   It is last in `RequestError::ALL`. The service never sends it: `mandate-gatewayd` answers only
   with the gateway's own replies, and a reply frame naming it from anywhere reads as the code it
   is, the same answer. It is a refusal at the caller in this sense: there is no record on the
   agent stream, because the caller holds no prompt or response to give one (rule 148). Unlike the
   gateway's refusals, it may have cost money, up to the call's reservation, which the service
   journaled before sending and which counts at its maximum until settled (DEC-2265 item 3).
   The inference spec says so in §1.2, §3.3 and §9.
3. **What the core does with it.**
   - The run ends with no output, as for any refusal, so no thesis, no proposal and no order
     follows: a model outage, the safe default (`AGENTS.md` rule 3).
   - The call is never sent again, neither within the run nor under its `call_id`.
   - Unlike the gateway's refusals, the pin is **not** withdrawn: research stays on schedule, and
     the next run calls afresh with a new `call_id`, so an outage ends when the service answers.
   - Each one is visible to the operator, since it may have cost money (agent harness §7.3):
     - the runtime logs it by its code alone;
     - when the run journaled a record, the core alerts the operator with the opaque key
       `research_gateway_unreachable`, naming the run's latest journaled record (rule 6): an
       agentic run's `RunStarted` or a later record of it, or a single call's last
       `ObservationRecorded`;
     - a single call that read no item journaled nothing for the alert to name, so the log line is
       its only trace beside the service's meter record.
4. **The service writes the meter; the runtime only reads it.** With a service address, the runtime
   builds no `Gateway` and opens no meter writer. Its research source reads `meter:{workspace}`
   through a read-only `MeterStore` that never takes the stream's writer epoch: `JournalMeter::open`
   takes it, and that would fence the service. That read gives DEC-2259 item 2's cross-check and
   item 3's last reservation. Any append through it is refused `Unavailable`, and no path makes one.
5. **One service per researching workspace.** A service serves one workspace (DEC-2265 item 7). In
   the local cell it serves the research agent's workspace, `<workspace>r` (DEC-2247 item 2,
   DEC-2070), the only workspace with a researching agent. `cargo xtask cell demo` points
   `modelGateway.workspace` there, as it points the managers. The demo's own workspace runs
   deterministic `quant.` models only (DEC-2383), which make no model call, so no service serves it,
   and its runtime is given no `--gateway`. A runtime of another workspace that calls the service
   is refused `foreign_workspace`, with nothing reserved or sent.
6. **The address is explicit.** A runtime is told the service with `--gateway <host:port>` beside
   `--research`. A `--gateway` without `--research`, or with an address that does not parse,
   refuses the start (`gateway_address_invalid`). Without `--gateway` the runtime keeps today's
   in-process recorded fake (DEC-2257 item 6, DEC-2210 item 3). The chart hands `--gateway
   model-gateway:8080` only to runtimes of the workspace `modelGateway.workspace` names.
7. **Restarts.** A restarted runtime re-plans its next run with new call ids (INF-10: no model call
   during replay), so it never re-sends a lost call. A call id the service has already reserved is
   refused at the meter's append (inference §3.6), so even a re-sent id could not spend twice.
8. **The runtime's egress is unchanged.** It already reaches only `model-gateway:8080` for models
   (inference §8.2), and the chart's policy already allows exactly that.

## What this changes

- **DEC-2265 item 4's "is the caller's `deadline_exceeded`"** becomes item 2's
  `gateway_unreachable`, for the remote caller. The rest of item 4 stands: the deadline holds on
  both sides, with the grace above on the caller's, and nothing is retried.
- **Inference spec v0.7:**
  - §1.2's "a refused call costs nothing" names its one exception;
  - §3.3 gains the row;
  - §9 gains "Gateway service unreachable".
- **Agent harness §7.3** gains the row. The new alert is stricter than the treatment of a gateway
  refusal, which alerts no one, and not withdrawing the pin changes only whether research resumes:
  nothing is enlarged, and the next call is metered like any other.

## Rationale

The caller cannot honestly fill a call record it never received, so the lost exchange is the one
answer the core already turns into "no output". The service's meter record keeps the spend
counted, and the alert makes the outage visible rather than silent. A read-only meter keeps one
writer per stream, the journal's own rule.

## Alternatives considered

- **A `deadline_exceeded` record built by the caller.** Refused: it would carry no prompt, request
  digest or price table, which rule 148 allows only for a guard refusal, and it would invent fields.
- **Retry once on a fresh connection.** Refused: a lost reply may already have spent (DEC-2265
  item 3).
- **Withdraw the pin, as for the gateway's refusals.** Refused: one restart of the service would end
  research silently until the runtime restarts.
- **The runtime keeps writing the meter.** Refused: two writers on one stream fence each other.
