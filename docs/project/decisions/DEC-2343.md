## Context

The executor process learns of a kill switch only through the runtime's copy on each agent's stream
([DEC-2003](DEC-2003.md) item 4). It follows the account's agents as DEC-2003 item 3 reads them,
from the control stream's latest state: an agent is followed while its connection's latest
establishment or revocation is a version-2 `ConnectionEstablished` naming this account. Any
`ConnectionRevoked` ends the following at once, for every row of the agent's stream, whenever it
was written.

On a compromise revocation (workspace API §5.6), the API commits one batch: `OwnerCommandIssued`
`kill_switch` at the connection's scope, then `ConnectionRevoked`. The runtime copies the switch
onto each agent's stream only after that batch has committed, so after the revocation. The executor,
running or restarted, folds the revocation, stops reading the agent's stream, and never applies the
switch. No order is cancelled and nothing is closed, while the owner's alert says the switch ran
(lane D1's finding on `main` 57355d40: `crates/mandate-executord/src/follow.rs` `agents_of`,
`process.rs` `switches`).

The existing test `process.rs::a_revoked_connection_is_followed_again_once_established_again`
asserts that defect: a switch written after the revocation is not applied. This decision rewrites
it.

## Invariants first

1. Every kill switch the journal holds for an agent the executor follows, journaled before a
   revocation of that agent's connection, is applied exactly once, as the executor's own
   agent-scoped switch (`AGENTS.md` rule 13).
2. A revocation never adds risk: an agent on a revoked connection gets no opening handed from then
   on.
3. A revocation never removes risk reduction the executor would otherwise do: the agent's exits and
   protective re-placements are still handed.
4. A kill switch never reaches an account-wide endpoint from an owner's connection or workspace
   command before DEC-2333's slice A2b (DEC-2333 item 7).
5. Every reading is a pure function of journaled rows, in `seq` order, so a running executor and a
   restarted one apply the same switches.

## Decision

1. **A revocation does not end the following of an agent deployed before it.** An agent the executor
   follows, whose version-2 `AgentDeployed` named a connection this account established, stays
   followed after that connection's `ConnectionRevoked`. The executor keeps reading the agent's
   kill-switch copies and its risk-reducing proposals (exits, protective re-placement), as it does
   for a stopped agent. It hands none of the agent's openings or increases from then on, and writes
   no record for them: no `IntentReceived` exists to refuse. This supersedes DEC-2003 item 3's
   reading, whose latest establishment or revocation now decides openings only. A later
   establishment of the same connection naming this account follows the agent fully again, as
   before.
2. **Every connection an agent was deployed on counts.** The agent is followed on this account if
   any of its version-2 deployments named a connection this account established, not only the
   latest one. Mandate rule V-031 and journal §9.24 already keep an agent on one connection; this
   makes the executor fail safe if a writer ever slips.
3. **The executor reads a revoked connection's kill switch itself.** It reads the control stream's
   `OwnerCommandIssued` `kill_switch` of `connection` scope (its subject a connection this account
   established, revoked since included) or `workspace` scope (its subject this workspace), in
   `seq` order. For each agent it follows that the command covers and whose connection has a
   `ConnectionRevoked` at or after the command, it applies the core's agent-scoped
   `Command::KillSwitch`, `cause` the command, with no owner confirmation, since the executor does
   not judge step-up. Every other covered agent waits for the runtime's copy, as today.
4. **Applied once.** A runtime copy whose `causation_id` names a command the executor already applied
   for that agent counts as applied. A command whose copy the executor already applied is not read
   again. Both orders are tested.
5. **Agent by agent until A2b.** The switch is the agent-scoped switch of each covered agent:
   its orders cancelled by id and its sub-ledger sold, never `cancel-all` or `close-position`. An
   order on the connection that no agent's ledger holds is not cancelled by it until A2b, and §5.6's
   confirmation and alert must not say or imply that it was.

## Consequences

- Workspace API §5.6 step 1 names the executor's own read and the agent-by-agent form, and step 3
  what the owner may be told.
- `mandate-executord`'s `agents_of` keeps the followed agents and the set of them whose connection is
  revoked; `switches` adds the commands of item 3 and filters copies by item 4; `take` hands no
  opening of a revoked agent.
- The tests PR rewrites the test named in Context, and adds a property test over interleavings of
  deployments, kill-switch commands, runtime copies (written, late, or never), ordinary and
  compromise revocations, re-establishments, `AgentStopped`, and restarts. Its oracle computes
  invariant 1 from the journaled rows, and seeded bugs (the drop on revocation, and the latest
  deployment replacing an earlier one) are shown caught.
- Lane X orders the credential's destruction after the executor applies the switch.

## Not covered

- **A stopped agent with no revocation.** `AgentStopped` stops the agent's runtime, the only writer
  of the copy, so a kill switch issued afterwards reaches the executor only through item 3, and only
  when a revocation follows. The deployment manager also stops the executor once no running agent
  remains on the account. The backlog holds the row.

## Alternatives considered

- **(1) Read every connection and workspace kill switch directly, with no confirmation.** This makes
  the executor independent of the runtime for every such switch (rule 13), but an owner's confirmed
  bid would no longer sell an equity outside the regular session. That changes what the owner gets,
  so it goes to the founder as its own proposal. The backlog holds the row.
- **(3) The executor judges step-up itself.** This would keep the confirmed bid under option (1), but
  it moves step-up judgement into the executor's layer, which is too large a change for this fix.
- **Keep the latest-state reading and order the runtime's copy before the revocation.** Rejected:
  the copy cannot be written before the API's batch commits, and a restarted executor would still
  read the latest state.
