## Context

The executor's binding gate answers an opening only while nothing has traded on the account
(DEC-2380 item 2). After the first order, every opening is held (`account_traded`, DEC-2143) until
the account risk view reads the agent's risk. So in the cell, once the agent has opened and exited
SPY once, it never opens again. R4b's risk book (DEC-2804) now gives the gate the agent's
`RiskSnapshot`, mode and instrument restrictions through `Deployment::risk`. The gate also reads
facts the risk book does not keep: the market-conduct counters of trading spec §9.6, mandate spec
§5.3's orders per day and re-entry cooldown, and the day-trade ledger. The rest is the account's
positions and working orders. No production code folds any of these. The coordinator split the
work: this slice answers an opening on an account that has traded but is flat now, and an account
that holds a position or works an order stays held until the multi-instrument risk state
(E6-15m).

## Decision

1. **When the gate answers.** An opening of a pinned agent is answered from the account's journal
   only when:
   - nothing has traded on the account (as today); or
   - the account is **flat**: no instrument nets to a position in the account stream's fills,
     every order any agent submitted on the account has reached a terminal state, the workspace has
     no other account to relate to (item 4), and R4b's `Deployment::risk` reads the agent's risk.

   Anything else holds the opening, as `account_traded` does today. An unpinned agent stays held
   (DEC-2819 item 4, E6-15m).
2. **The agent's risk.** It is R4b's `GateRisk`: the snapshot, the mode, and the bound instrument's
   restrictions. `None`, whether the fold is not open, is unreadable or is unpriced (DEC-2834),
   holds the opening.
3. **The counters.** One pure fold in `mandate-gate-context`, beside `Journaled::opening_hold`,
   reads them from the account stream's rows. It reads only the agent's own orders, each known by
   the `OrderRequestRecorded` before its `OrderSubmitted` (journal spec rule 45), with its purpose
   and instrument from that request. "Today" is the risk day, 00:00 to 00:00 America/New_York
   (mandate spec §5.3), of the gate's `now`.
   - `orders_today` (mandate §5.3): the agent's orders with an opening or increasing purpose
     submitted today, each `client_order_id` once, rejected and abandoned ones included.
   - `orders_today_per_instrument` (§9.6): the agent's orders of any purpose submitted today, per
     instrument, each once, a replacement counted as an order of its own. The specs exclude orders an exit sequence or a kill switch canceled.
     The journal names no such cause on `OrderStateChanged`, so none is excluded (DEC-176: the
     reading that counts more).
   - `filled_today` (§9.6): per instrument, the agent's orders with a fill today. Here counting
     more would loosen the order-to-fill ratio, so a fill counts only when both its `trade_date`
     and its `risk_clock` fall on today.
   - `last_opposite_fill_at` (§9.6): per instrument and side, the latest fill on the account by any
     agent or none.
   - `participation_today` (§9.6): per instrument, the quantity filled today on both sides on the
     account by every agent and by none. A fill counts as today when its `trade_date`, its
     `risk_clock` or its `recorded_at` is today. A flat account works no order, so none is
     added.
   - `last_exit_fill_at` (mandate §5.3): per instrument, the latest sell fill on the account, of
     any order or none. v1 holds no short position, so every sell reduces a long position. A
     protective leg the broker created holds a `client_order_id` no request names, so a fill of it
     would be missed if only the agent's own requests counted. Counting every sell can only start a
     cooldown, never skip one (DEC-176).
   - **Each fill's instant.** For the last two, it is the later of the fill's `risk_clock` and the
     instant the store recorded the row (`recorded_at`). A fill is recorded only after it happened,
     and the gate's `now` is the risk clock, which never runs ahead of the host's. So the time the
     gate counts since a fill is never more than the time that has passed (DEC-176). A row with no
     readable `recorded_at` holds the opening.
   - **The day of an order or a fill.** It counts as today when either its `risk_clock` or its
     `recorded_at` falls on today, except for `filled_today` as said above. An order whose row
     carries neither counts as today.
   - **Flat.** The account holds no position: every instrument's fills net to zero. And every
     order seen on the account is ended: any `client_order_id` an `OrderSubmitted`, a replacement or
     an `OrderStateChanged` names, of any agent or a broker-created leg, until a terminal state or
     an `OrderAbandoned` ends it.
4. **Related accounts.** §9.6's opposite-fill, participation and self-trade controls read every
   account of the related-accounts group, which by default is the whole workspace. The executor
   follows one account. So the gate answers only while the workspace's control stream has
   established exactly one connection that no revocation ended. A second connection holds the
   opening until the counters read every account of the group (backlog row
   `E6-15-related-account-counters.md`).
5. **Day trades.** The gate already answers only where the account's day trades cannot bind
   (trading spec §9.2): under `intraday_margin` with no maintenance deficit, or under the legacy
   regime with a prior close at or above the threshold. Mandate-risk's day-trade check reads the
   ledger only in the other case, which the gate never answers. So the ledger is passed empty, and
   a test shows that a legacy account below the threshold is still held.
6. **Exits are untouched.** No exit, protective order or kill switch reads the risk, the counters or
   the flatness (`AGENTS.md` rule 13). A counter that does not read holds only openings.
7. **One fold for the gate and the workspace read.** `Journaled::opening_hold` keeps its meaning,
   and the counters are a method of the same fold. A reader that has each row's `recorded_at` folds
   with it (`Journaled::fold_recorded`). One that folds without it reads the same facts, but no
   counter: a fill with no `recorded_at` leaves the counters unread, which holds the opening.

## Rationale

This is the smallest slice that lets the demo agent open again after a round trip. It reads every
fact the gate needs and assumes none. Wherever the specs leave a reading open, the stricter one is
taken and recorded here (DEC-176). The time base is the one that can only lengthen a cooldown,
never shorten it.

## Alternatives considered

- **Keep `account_traded` until E6-15m.** Rejected: the demo agent could never open twice. The
  coordinator named this slice demo-critical.
- **Count from `risk_clock` alone.** Rejected: a fill can land up to a tick after the last
  `risk_clock`, so a cooldown counted from it could end up to a tick early.
- **Fold the counters in `mandate-executord`.** Rejected: the workspace API's agent read would need
  a second reader of the same rows.
