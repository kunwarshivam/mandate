## Context

`mandate-api-server` serves `GET /v1/workspaces/{ws}/backtests/{id}` and `…/evaluations/{id}` from
the control stream's `BacktestRunRecorded` and `EvaluationRunRecorded` (journal spec §9.18), with
each report read from the content-addressed store. Four things are not stated:

- §4.7 and DEC-1002 item 6 serve an evaluation "only in the team's internal paper workspaces
  (DEC-103); elsewhere `not_found`", and nothing in the code or the configuration marks a workspace
  internal. DEC-1141 item 2 leaves the same check off the record.
- The server is configured with no journal environment; each row carries its own.
- §4.2 and DEC-1001 item 5 say a completed run's `report` is the artifact's object, and do not say
  what the read answers when the store lacks it or it fails its digest check.
- Nothing says what a second record with the same `backtest_id` or `evaluation_id` means.

## Decision

1. **The setting.** `MANDATE_API_INTERNAL_PAPER_WORKSPACE` marks the deployment's one hosted
   workspace an internal paper workspace. It is off when absent or empty, on only for exactly
   `true`, off for exactly `false`, and any other value refuses start naming the setting
   (`config::internal_paper_workspace`). It is carried as `Hosted::internal_paper`.
2. **Paper, shown at start and on every read.** With the setting on, the process reads the hosted
   control stream before it listens, within five seconds, and refuses to start, exit status 2,
   unless the stream has a row and every row's `environment` is `paper`. An unreadable, empty, or
   mixed stream refuses (`config::check_internal_paper`): the setting is never taken on trust, so
   it is turned on only after the stream is opened. The evaluation read checks the same of the rows
   it reads, so a live row appended later closes the route again.
3. **Elsewhere, the one 404.** With the setting off, or the stream not paper throughout, every
   evaluation id answers the 404 an absent id answers, a recorded one included, after the request
   is authenticated and authorized as any read is. The route does not say that it exists.
4. **A completed run's report, or 503.** `read-models/backtest` requires a completed run's `report`
   to be an object, so a completed record whose report the store lacks, that fails its digest check
   (logged by name, with no content), that is not a JSON object of its `kind` and `report_version`
   (2 for a backtest, 1 for an evaluation), or, for a backtest, that names another mandate version,
   answers `journal_unavailable`, as does a deployment with no store. A failed read is never an
   empty result, and `report: null` would make a completed run look like a refused one. A refused
   run needs no store.
5. **One record, or none served.** Exactly one schema-version-1 record must name the id. A second
   record with the same id, identical or not, and a record that breaks §9.18's shape (the marker,
   `report_version`, `result`, rule 143's `report` and `refusal`, a `refusal` outside ES-09's code
   grammar, a reference that does not parse) answer `journal_unavailable`: the journal holds no
   single answer, and serving the first or the last would show the go-live screen a report the
   journal does not settle. A row whose body does not parse is skipped, as the other reads skip it.
   An id outside the id grammar names nothing.
6. **No `running`.** Nothing journals a backtest in flight (`POST /backtests` is not built), so a
   backtest is absent until its record commits and `state: running` is never served.
7. **The permission row.** Neither identity spec §4.2's matrix nor §3.7's copy names a row for these
   reads. Both use "View agents, positions, decisions", the row every §4.7 read uses: no row is
   stricter for a backtest, and "Read records, verification; export" is not, since it admits a
   service account that the view row refuses. A backtest answers only in the workspace whose control
   stream records it (API-9).

## Rationale

Every item narrows what is served and loosens nothing. Item 1 and 2 make the internal workspace an
explicit, checked act of the deployment's configuration rather than an inference, so a mistake
closes the route; item 3 keeps an owner's workspace from learning the route exists, as DEC-1002
item 6 intends. Items 4 and 5 follow rule 3 of `AGENTS.md`: an ambiguous or unreadable journal
resolves to no answer, and the schema itself forbids the `null` report. Item 7 takes the matrix as
it stands; a stricter row is a change to the identity spec.

## Alternatives considered

- **Serve `report: null` for a missing artifact.** Rejected: the schema refuses it for a completed
  run, and it reads as no report rather than a failed read.
- **The first or the latest record wins.** Rejected: either serves a report the journal does not
  settle; the writer is single, so a duplicate is a defect to surface, not to resolve.
- **Mark internal workspaces in the journal.** Deferred: it needs a record type and a spec change;
  this setting can be read from such a record later without changing the route.
- **Trust the setting without reading the stream.** Rejected: one wrong setting would show the
  founder's evaluation in an owner's live workspace.
