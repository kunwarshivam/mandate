# DEC-1022: A cookie a refresh just rotated away still admits calls for 30 seconds; only the refresh route treats it as reuse

## Context

§3.11 item 6 rotates the session cookie's secret at each granted refresh and ends the session when
a rotated secret is presented again. The web app sends commands without waiting on its refresh
(W2, #1497), so a pause or a kill switch can be in flight with the old cookie while a refresh
rotates it. Ending the session then would refuse risk reduction and sign the owner out at the
worst moment (`AGENTS.md` rules 3 and 13).

## Decision

1. **Only the refresh route treats a rotated secret as reuse** and ends the session
   (`refresh_reuse`), as identity spec §6.2's refresh-token rotation does.
2. **On every other route**, the secret the last granted refresh rotated away admits the call for
   30 seconds after that refresh, as the current one would, except that it never triggers the
   server-recorded outage refresh (which needs the current secret; within 30 seconds of a grant
   the access is live anyway). After that, and for any secret older than the last one, the call
   gets the one 401 and the session is kept.
3. A grant always rotates, so a stolen cookie's window is the 30 seconds after the owner's own
   refresh, and its use on the refresh route still revokes the whole session.

## Rationale

A command in flight across a refresh is the web app's normal case, not an attack, and it is the
risk-reducing commands that most need to land. Thirty seconds covers a slow request; the refresh
route keeps reuse detection where identity spec §6.2 puts it.

## Alternatives considered

- **Refuse 401 without a grace.** Safe for the session, but a kill switch in flight across a
  refresh fails and must be resent, which the owner may not notice.
- **Accept every rotated secret on other routes.** A stolen old cookie would act until the session
  ends.
