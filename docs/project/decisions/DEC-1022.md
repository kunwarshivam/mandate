## Context

§3.11 item 6 rotates the session cookie's secret at each granted refresh and ends the session when
a rotated secret is presented again. The web app sends commands without waiting on its refresh
(W2, #1497), so a pause or a kill switch can be in flight with the old cookie while a refresh
rotates it. Ending the session then would refuse risk reduction and sign the owner out at the
worst moment (`AGENTS.md` rules 3 and 13).

## Decision

1. **Reuse still ends the session**, as identity spec §6.2 says: a rotated secret presented on
   any route ends it (`refresh_reuse`), with the one exception below.
2. **The exception.** For 30 seconds after a granted refresh, the secret that refresh rotated away
   (and no older one) serves a pause and a kill switch as the current one would, except that it
   never triggers the server-recorded outage refresh, which needs the current secret (within 30
   seconds of a grant the access is live anyway). Any other call with it in that window gets the
   one 401 and the session is kept, so a read in flight across the refresh does not sign the
   owner out. The refresh route treats it as reuse even within the window.
3. **What it costs.** A thief holding the cookie the owner's own granted refresh just rotated away
   can pause or engage the kill switch for 30 seconds, which adds no risk (`AGENTS.md` rule 2), and
   nothing else; any other use is refused, and any use after the window revokes the session. An
   outage refresh does not rotate, so it opens no window.
4. **Out of scope.** Two refreshes racing on one cookie (two tabs) still meet as reuse; the web
   app serializes its refreshes (W2).
5. **Spec text.** Identity spec §6.2 and workspace API spec §3.11 item 6 say this, pointing here.

## Rationale

A command in flight across a refresh is the web app's normal case, not an attack, and it is the
risk-reducing commands that most need to land (`AGENTS.md` rule 13). Admitting only those keeps
the window harmless; keeping reuse detection everywhere else keeps identity spec §6.2's
stolen-token signal. Narrowing that rule is the founder's call, so this stays Proposed.

## Alternatives considered

- **No exception (§6.2 as written).** A kill switch in flight across a refresh would end the
  session and be refused, and a read in flight would sign the owner out.
- **Admit every call in the window.** A stolen cookie could act on risk-increasing routes for 30
  seconds.
- **Refuse 401 without ending the session, forever.** It would remove stolen-token detection on
  every route but refresh.
