## Context

DEC-2108 settles the enrolment ceremony. The workspace API spec's routes for it still need their
check order, the codes their refusals use, a read of one's own passkeys, and a wire name for a
credential that the response schemas' member-name guard allows.

## Decision

1. **Check order.** Both mutating routes check, in this order: the session (`reduction_only` for a
   reduction-only session), the CSRF mark, `Idempotency-Key`, the strict body, §3.7's "Enrol or
   remove one's own passkey" `own` cell, and then a `live` workspace (`live_unavailable`), as the
   step-up challenge route does (DEC-2103). The enrol route then judges the registration challenge,
   the step-up, and the authenticator's response, in that order, and commits only after all pass.
2. **No new error code.**
   - A registration challenge that is not held, has expired, or names another principal or
     workspace is `invalid` at `/challenge_id`. The submit drops it whatever follows.
   - A response `mandate_passkey::enrol` rejects is `invalid`, and a passkey id the stream has ever
     enrolled is `invalid` at `/passkey_id`.
   - A first enrolment whose session was opened more than 300 s before is `step_up_stale`: the
     fresh session is that call's evidence, and it is too old. The registration challenge route
     refuses it too, so the client signs in again before the ceremony, not after.
   - A later enrolment is judged by §3.5's step-up order, so a member whose every passkey is still
     cooling off gets `step_up_missing`.
3. **The list.** `GET /v1/workspaces/{ws}/passkeys` serves the member's own enrolled passkeys under
   the same row's `own` cell, without step-up: it returns opaque ids, algorithms and instants, the
   ids a step-up's `allowCredentials` needs anyway, and grants nothing. No public key is served.
4. **`passkey_id` on the wire.** A response member's name never contains "credential" (the
   schemas' `propertyNames` guard), so the API names a credential id `passkey_id` in requests and
   responses alike, including DEC-2108 item 7's `step_up_assertion`. It is the journal's
   `credential_id`, the same unpadded base64url string.
5. **Limits.** Registration challenges are counted with the step-up challenges, at most 32
   unexpired per principal and 4,096 in all (`rate_limited` past either).

## Rationale

Reusing the existing codes keeps the problem schema and every client unchanged; each refusal
already has a code whose client action is right (resubmit with a fresh challenge, or run a new
ceremony, where a first enrolment's ceremony is a new sign-in). The list exposes nothing the step-up
ceremony does not already expose to the same member.

## Alternatives considered

- **A new code for a first enrolment from an old session.** Rejected: `step_up_stale` already tells
  the client its evidence is too old, and a code would grow the problem schema for one case.
- **Step-up for the list.** Rejected: it would need a passkey to see one's passkeys, and the read
  grants nothing.
- **`credential_id` on the wire.** Rejected: the member-name guard forbids it, and loosening the
  guard weakens a safety check.
