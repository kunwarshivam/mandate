| **Decided by** | the builder of lanes K1 and C1 (Claude Code), under DEC-79 and DEC-176 |
| **Story or claim** | E21-36, E21-37 (first slice); claim #1432; [managed-cells plan](../tasks/managed-cells.md) lanes K and C; DEC-967, DEC-990 |

## Decision

1. **One process list, two renderings.** `deploy/cell/charts/workspace/processes.json` lists every
   process type of infrastructure §3.1 with its kind, image, database role, egress column,
   placement and resources. The Helm chart reads it with `.Files.Get`; `cargo xtask cell generate`
   writes the Compose file and the journal's roles file from it, and the lint job fails when
   either drifts. A process renders in the chart only when `values.images` names its image, and
   in the Compose file only when the list marks it `built`, so a process lane adds its process by
   building its image and flipping one field.
2. **The chart emits JSON.** Every manifest is written as YAML in a named template and emitted
   through `fromYaml | toJson`, which fails the render on a template that does not parse. The
   rendered chart is then machine-readable without a YAML parser, so the invariant tests
   (`deploy/tests/test_cell.py`) and the drills read it with the standard library and
   `serde_json`, and no dependency is added for them.
3. **helm comes from get.helm.sh.** D-4 says GitHub releases only, but Helm attaches no binaries
   to its GitHub releases; its only official binaries are on `get.helm.sh`. CI and
   `.cursor/install.sh` download helm 4.3.0 from there, checked against a SHA-256 pinned in both
   files. `install.sh` fetches it best effort, as it does PostgreSQL, so a session behind a proxy
   that allows only the listed hosts still installs everything else, and the cell's checks skip
   there. k3d and kubeconform come from their GitHub releases.
4. **k3d, not kind.** k3d runs on GitHub's `ubuntu-24.04` runners, so the kind fallback is not
   built. kubectl is the one inside the k3s node (`docker exec`), so the cell needs no fourth tool.
   On a cgroup v1 host, k3s 1.35's kubelet is started with `fail-cgroupv1=false`;
   `MANDATE_CELL_CA_BUNDLE` mounts a CA bundle into the node for a machine behind a TLS-inspecting
   proxy.
5. **The journal's Postgres is its own release.** The workspace chart's migration Job is a
   pre-install and pre-upgrade hook, so it finishes before any process is created or rolled
   (OPS-13); on a first install a Postgres in the same release would not exist yet. So the
   journal's CloudNativePG cluster, its roles and one credential Secret per process type are a
   second chart, `deploy/cell/charts/journal-db`, installed first; lane S2 (E21-41) grows it.
   Passwords are generated by that chart in the cluster and kept across upgrades by reading the
   Secret back; no password is a value or in git. Each process type logs in as its own role, a
   member of `mandate_journal_app`; the migration Job logs in as `mandate_migrator`, the only role
   that may become `mandate_journal_owner`.
6. **The migration Job mirrors `deploy/bootstrap.sh`.** No `mandate db migrate` command exists, and
   `mandate-cli`'s entry point is an R0 file, so the Job applies `migrations/` with `psql` from
   CloudNativePG's PostgreSQL image, each file once, recorded with its SHA-256 in
   `deploy.migrations`, refusing an applied file that changed: the demo host's procedure. When a
   migration command ships, it takes over from that table.
7. **Secrets are files, and pgpass is copied.** Each role's Secret holds a `pgpass` line, mounted
   group-readable for `fsGroup`; libpq and sqlx both refuse a pgpass file any group can read, so an
   init container copies it to a memory-backed directory as 0600 under the process's user, and
   `PGPASSFILE` names it. The DSN has no password and is `verify-full` against the cluster's CA.
   In the Compose file every service runs as the library Postgres image's non-root user (999), so
   its first-start script and each process read the same 0600 files; that script reads each
   password inside `psql`, never on a command line.
8. **Network policy.** A namespace-wide default-deny, then one policy per rendered process type
   allowing exactly its infrastructure §3.1 egress: DNS when it has any destination, Postgres, the
   vault and the model gateway by pod label and port, and each external destination's CIDRs from
   values, empty by default so nothing external is allowed until a lane sets it. Values take only
   CIDRs of /24 or narrower (/32, at most four, for DEC-821's token host), and `cargo xtask ci
   cell` refuses any rendering whose policies contain a live trading host's resolved address. No
   process accepts ingress but the model gateway, from the processes that name it. The first CI
   run of the egress drill showed that k3s's policy controller filters a new pod only seconds
   after it starts, and in that window every probe reached every live trading host. So every pod
   starts with an `egress-gate` init container that lets nothing else run until the pod's own
   egress is shown filtered (the API server, which no policy allows, stops answering), and fails
   closed after a minute; the drill's probes sit behind the same gate. Residual: an API server
   that is down in that same window reads as filtered. The journal's
   pods accept only the labelled Postgres clients, the operator and each other; their egress stays
   open in this slice, which S2 narrows. NetworkPolicy filters addresses, not names; the residual
   is the one DEC-821 item 4 discloses. Reading §3.1 to its letter added three destinations the
   first draft left out: the runtime's artifact store, the control services' identity provider and
   vault, and the model gateway's own replicas (the meter holder). The tests hold §3.1's column as
   their own table, not read from the process list.
9. **The interim image.** Until lane R2 (E21-35) builds reproducible, signed images, `cargo xtask
   cell up` builds `mandate.local/mandate:<commit>`: `mandate-cli` from this checkout, linked
   statically (`+crt-static`), on an empty base (`FROM scratch`), never with the `live` feature.
   No base image is added. The chart accepts a `mandate.local/` name only where `localImages` is
   set, which only the local cell's values do; every other cluster takes digests only.
10. **Where the checks run.** The chart's invariants (`deploy/tests/test_cell.py`) run in the
    required `fast` check, in `fast-python` with helm installed and required. The cluster itself
    runs in the `cell` job on every pull request, not yet in `full`, so a new job's start-up
    flakiness cannot block every other lane; it joins `full` once it has passed on ten consecutive
    runs, by a later change. The local-cell gate (DEC-967 item 16, DEC-990 item 2) reads its result
    on `main`.
11. **The first drills.** `boot` (the release is installed as rendered, the migration hook's own
    policy and files included, and the hook succeeded), `journal` (the CLI opens a control stream
    in the cell and a Job exports and verifies it by journal spec §11), `egress` (from a pod of
    every process type, each live trading host fails at the network layer, tried at once and ten
    seconds later, and the journal is reachable exactly from the rendered processes whose egress
    names Postgres; OPS-5), and `compose` (the Compose file on the host's docker, from first start
    to a verified export). `cargo xtask cell drill --seeded` plants each drill's bug, and a seeded
    run counts as caught only when its report names that bug's symptom. The kill-switch, restart,
    two-executor, upgrade and restore drills join as their processes land.

## Rationale

Each item is the smallest structure that holds a safety property for every later lane: one list
keeps the chart and the Compose file from diverging, JSON output keeps the tests and drills free of
new dependencies, and a separate journal release is what lets the migration hook run before any
process on the first install as well as on every upgrade.

## Alternatives considered

- A YAML parser (PyYAML in the uv workspace, or `serde_yaml` in xtask) to read `helm template`:
  a new dependency outside D-1 to D-7.
- Postgres in the workspace release with the migration as a post-install hook: processes would
  start before migrations on a first install.
- `kind`: k3d runs on the runners and is cell #1's own distribution (k3s).
- Making `cell` part of `full` at once: a new job's flakiness would block every lane.
- A `distroless` base for the interim image: not among DEC-990's image kinds, and a static
  binary needs none.
