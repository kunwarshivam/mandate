## Context

The account risk fold binds one instrument (DEC-2308 item 4). [DEC-2804](DEC-2804.md) item 8
fails closed at the fold: the executor opens no fold, so it holds every opening, for an agent whose
confirmed version's `universe.max_instruments` is above 1, and for every agent on an account where
more than one agent that has not stopped is followed. That is safe, but the owner learns it only as
held openings, after the agent runs. Item 8 left refusing such a deployment before it runs to its
own decision, because what it refuses touches DEC-117's proposed default and the local cell's two
demo agents on one account. The coordinator ruled on 2026-10-26:

- the web draft caps `max_instruments` at 1 (lane WB);
- `second_instrument` lands now;
- the cell moves its second demo agent onto its own paper connection and account (lane DR), and
  `second_agent_on_account` lands only after that, so the cell never goes red in between.

## Invariants first

- No deployment the executor's fold could not read runs unrefused: what item 8 holds at the fold is
  refused at deploy first, with a reason the owner sees.
- Nothing here changes what may be confirmed. A version with `max_instruments` above 1 stays a valid
  envelope (DEC-117's proposal), and is refused only where it would run.
- A refusal commits nothing (workspace API §4.2): the control stream holds no `AgentDeployed`, so
  nothing starts.
- Neither refusal holds an exit, a protective order, a risk exit or a kill switch: both judge only a
  new deployment.

## Decision

1. **`second_instrument`.** A deployment of a version whose `universe.max_instruments` is above 1 is
   refused, by the CLI's `agent deploy` and by the workspace API's Deploy alike, until the
   multi-instrument risk state lands (DEC-2308 item 5). It is judged after the checks on the agent
   (DEC-530 item 9's `agent_active` and DEC-1173's `agent_stopped`, so a re-run of a deployment that
   already ran still answers with its `AgentDeployed`) and before the V-rules:
   - the CLI's code is `second_instrument`, added to DEC-530 item 10's closed list;
   - the workspace API answers `invalid` at `/mandate_version` with code `second_instrument`.
2. **`second_agent_on_account`.** A deployment is refused when the account its version's connection
   names already has a deployed agent other than this one that has not stopped: a version-2 or
   version-3 `AgentDeployed` naming a connection whose version-2 `ConnectionEstablished` names the
   same `account_ref` in the same environment, with no `AgentStopped` for that agent. Judged after
   item 1:
   - the CLI's code is `second_agent_on_account`, added to DEC-530 item 10's closed list;
   - the workspace API answers `invalid` at `/agent_id` with code `second_agent_on_account`.

   It lands only after lane DR has moved the cell's second demo agent onto its own paper
   connection and account and said so.
3. **A stopped agent frees the account** at its `AgentStopped`, which is final (DEC-1173). Its
   leftover position, working orders and protective orders are still the executor's to manage, and
   the executor still marks its instrument. If that is another instrument, the next agent's fold is
   unreadable while those marks go on (DEC-2804 item 8): its openings are held and its exits are not.
   The deployment is not refused for it: holding is safe, and item 9 of DEC-2804, if the founder
   accepts it, removes the hold.
4. **Not journaled.** As every deploy refusal (workspace API §4.2), a refusal commits nothing.
   `DeploymentRejected` waits for the deployment manager to journal its own refusals. The refusal
   reaches the owner as the CLI's code or the API's `invalid`, with the path and code above.
5. **Withdrawal.** When the multi-instrument risk state lands, item 1 is withdrawn by the decision
   that lands it. If the founder accepts DEC-2804 item 9, item 2 is withdrawn by a new decision.

## Consequences

- R4c code: the CLI's `agent deploy` and the workspace API's Deploy judge item 1, tests first. The
  web draft's cap is lane WB's.
- Item 2's code lands after lane DR's move.

## Alternatives considered

- **A V-rule (V-048).** Refused: a V-rule also refuses confirmation, which would make DEC-117's
  proposed `max_instruments` of 5 unconfirmable everywhere (the DEC-2804 review's B1). The executor
  needs the refusal only where a version runs.
- **Hold at the fold only (DEC-2804 item 8).** Kept as the backstop, but the owner would learn of it
  only as held openings after the agent ran.
- **Journal the refusal.** Refused here: no deploy refusal is journaled today (workspace API §4.2), and
  one record type for this alone would precede the deployment manager's.
