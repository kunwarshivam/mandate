## Decision

Every answer comes from Alpaca's public documentation, read on 2026-10-08. Nothing comes from
signing in, calling an Alpaca API, or a credential. Connections spec §5.5 quotes each source with
its URL. The main source is "Using OAuth2 and Trading API",
<https://docs.alpaca.markets/docs/using-oauth2-and-trading-api> (page `updatedAt` 2026-03-02).

1. **The API never calls a broker, at connect included** (agent-accepted under DEC-79: a reversible
   engineering decision that narrows exposure relative to `main`). Workspace API spec §1.4 already
   said so, but connections spec §5.2 had the API process do the code exchange and run the §8.1
   checks, and infrastructure §3.1 gives that process no broker egress. It is not a DEC-176
   tightening, because it adds a custody path (below). Connect now splits between the two
   processes:
   - **The API process (connection manager)** checks `state`, writes the authorization code (or a
     key) straight to the vault, and starts the pending connection's executor. It writes the
     pending connection record, including the fingerprint the executor returns. It runs check 4
     (uniqueness), because only it sees every fingerprint. Then it either appends
     `ConnectionEstablished`, with its causation citing the executor's passing `ConnectionChecked`,
     or tears the connection down.
   - **The account executor**, which holds that one connection's lease and broker hosts, exchanges
     the code and runs checks 1, 2, 3, and 7. It appends their results on its account stream
     as `ConnectionChecked` (E7-17); checks 5 and 6 come from `AccountStateObserved` and never
     refuse a connect. While `connecting` it does nothing else. It acts on the account
     only after it reads `ConnectionEstablished`.
   - **Teardown and restarts** are connections spec §5.2 step 6.

   **Custody.** The platform's OAuth client secret is read by a connecting executor through a
   single-use grant. The vault binds the grant to that executor's workload identity, limits it to
   10 minutes, and revokes it at `ConnectionEstablished` or teardown (infrastructure §3.5, §5.1,
   §5.2). An active executor has no read of it, so no refresh exists without a new decision.
   DEC-821 item 2 (pending on PR #762, not in force until it merges) authorizes the token call;
   it does not by itself authorize this custody. The custody is this item's reading, and it
   applies only once DEC-821 is in force.

   The alternative was one connection-manager identity holding the secret for every exchange. It
   would expose the secret in fewer processes. But that identity would carry every token in its
   memory, which CN-1 forbids, and DEC-821 item 2 places the token call in "the connection's own
   process". The per-executor single-use grant is the narrower option.
2. **U-A1 is answered** (Accepted). The scopes are `account:write`, `trading`, and `data`. "Read-only
   endpoint access is assumed by default", so reading the account needs no scope. The request stays
   `trading data` (DEC-441 item 5). The token response's `scope` must equal the request.
3. **`env` is always sent, set to the connection's environment** (Accepted, a tightening). Without
   it Alpaca prompts for a live and a paper account together, which would give a token CN-3
   refuses.
4. **U-A2 is open** (Accepted reading). The documentation maps no OAuth scope to an endpoint. The
   Trading API's crypto withdrawal (`POST /v2/wallets/transfers`, deprecated, sunset 2026-10-09)
   and whitelist (`POST /v2/wallets/whitelists`) endpoints live on the same hosts. Fund movement
   therefore cannot be shown absent, and under CN-2 and DEC-441 item 4 every **live** Alpaca OAuth
   grant is refused, for every asset class, not only crypto. A paper grant records and discloses
   the limit (infrastructure §5.3).
5. **U-A3 is open** (Accepted reading). Nothing is documented about token lifetime, refresh tokens,
   or revocation. A token is valid until a call fails authorization (connections §5.4), and no
   refresh is built. A forum post from Alpaca staff says authorization codes live 10 minutes, so
   the executor exchanges the code at once. A platform revoke tells the owner to remove the app at
   Alpaca as well, because no revoke call is documented.
6. **(Proposed) Whether an `env`-scoped grant satisfies U-A4.** Two statements in the
   documentation bear on it:
   - "An single Alpaca OAuth token may authorize access to either: One live account; One paper
     account; One live account and one paper account".
   - "If you specify a value for the `env` parameter when redirecting to us, we will ask the user to
     authorize only a live or a paper account".

   These describe what the owner authorizes. They do not say the live host refuses a token granted
   with `env=paper`, and the token response names no environment. Alpaca's only explicit public
   statement (forum, staff, 2020-02-18) says a token "belongs to the user instead of a specific
   account and can be used for both paper and live accounts".

   **Agent reading, in force:** U-A4 is not settled. DEC-441 item 21 keeps refusing every Alpaca
   OAuth grant, paper included, and the live host is never probed.

   **Recommendation:** get Alpaca's written statement that a token granted with `env=paper` is
   refused by `api.alpaca.markets` for trading and account calls. With that statement, accept
   `env`-scoped grants for their own environment only. Without it, DEC-441 item 22 is the
   remaining path.
7. **(Proposed) The token endpoint is on the live host.** The exchange is
   `POST https://api.alpaca.markets/oauth/token` for a paper grant too. ES-23 compiles only paper
   hosts into every non-production build, so no paper OAuth connection can be completed outside
   production, even once item 6 is decided.

   **Agent reading, in force:** no exception. Alpaca OAuth is not built outside production.

   **Recommendation:** allow exactly one live-host request, `POST /oauth/token` on
   `api.alpaca.markets`, from an executor in `connecting` only, behind the egress allow-list:
   - no other path or method on that host;
   - no redirects;
   - the build test that "no live trading host is compiled in" extended to name the single
     exception.

   This loosens ES-23, so it is the founder's.
8. **U-A5 is answered** (Accepted). `GET /v2/account` returns `multiplier` and
   `GET /v2/account/configurations` returns `max_margin_multiplier`. Both are reads, so they fall
   under the documented default for read-only endpoints; no page names them for OAuth. If a read
   is refused, §8.1 check 5 fails closed and agents are not deployable.
   Changing them needs `account:write`, which is never requested. FR-2.6 is checked by reading; the
   owner changes the setting at Alpaca (trading §15 q3).
9. **PKCE is sent but never relied on** (Accepted). Alpaca documents no `code_challenge` and
   authenticates the exchange with `client_secret` from the backend. The controls are the client
   secret (item 1) and the single-use `state`.
10. **What the founder registers and asks, under DEC-441 item 18** (Accepted as a list; the
    registration itself stays the founder's, item 18). Sources: "Registering Your App"
    (<https://docs.alpaca.markets/docs/registering-your-app>) and "About Connect API"
    (<https://docs.alpaca.markets/us/docs/about-connect-api>).
    - **Where:** an OAuth app is created from the founder's own Alpaca dashboard: Alpaca Connect,
      then "My Developed Apps", then "Submit Your App", completing the Alpaca Connect Application.
      Alpaca then issues a Client ID and Client Secret and reviews the app by email. Both go
      straight into the cell vault (item 1), never into the repository or a chat.
    - **Redirect URI:** exactly `https://api.owlhead.ai/v1/oauth/alpaca/callback`, on the domain of
      DEC-820 and DEC-822, both pending on PR #762 (workspace API §4.5). It is fixed because a
      registered URI cannot carry a workspace id: the workspace, user, environment, and PKCE
      verifier are bound to the single-use `state`, and the environment is also sent as `env`. HTTPS
      only, with no wildcard and no localhost. Hybrid and on-prem hosts would each need their own
      registered URI, which is still open.
    - **Secrets the founder enters** into the environment's secret store. The values never go
      into the repository, a chat, or a log:
      - `ALPACA_OAUTH_CLIENT_ID`
      - `ALPACA_OAUTH_CLIENT_SECRET`

      Only the connection's executor in `connecting` reads them (item 1).
    - **Scopes requested:** `trading` and `data` only, never `account:write`. Scopes are chosen per
      request, and the documentation shows no scope setting at registration.
    - **Terms to read before registering:**
      - The "Terms of Access and Use" on About Connect API. They require registration, OAuth 2.0
        for all clients, and no implication that Alpaca built the app.
      - A commercial application "must disclose it in the registration form and receive written
        approval".
      - "To allow live trading for other users, the app needs to be approved by Alpaca".
      - Alpaca's Terms and Conditions, which the Trading API reference names
        (<https://s3.amazonaws.com/files.alpaca.markets/disclosures/library/TermsAndConditions.pdf>).
    - **Ask Alpaca in writing:**
      - U-A4: does `api.alpaca.markets` refuse a token granted with `env=paper`, and the reverse?
      - U-A2: which endpoints can a `trading`-scoped token reach? Does it reach
        `/v2/wallets/transfers`, `/v2/wallets/whitelists`, or any successor?
      - U-A3: token lifetime, refresh, a revoke call, and how revocation is signalled.
      - Is PKCE supported?
      - May a non-production deployment call the token endpoint?

## Rationale

The demo needs "connect Alpaca paper by OAuth". Its blockers come from Alpaca's own design, not
from our specs:

- Alpaca documents what the owner authorizes, not what its hosts enforce.
- Its token endpoint is on its live host.

Treating either as settled would let a paper connection hold a token that might reach a live
account, and would compile a live host into a paper build. Both weaken rule 8 and CN-3, so they
wait for the founder (DEC-79). Items 1 to 5 and 8 to 10 only tighten a rule or record a fact, and
they change no outcome a test checks today. The paper API-key path (connections §5.1) is
unaffected.

## Alternatives considered

- **Read the `env` note as settling U-A4:** rejected as the agent reading. It is a statement about
  the consent screen, and a staff statement contradicts it; whether it is enough is item 6, for the
  founder.
- **Probe the live host with a paper token to find out:** forbidden by CN-3 and rule 8.
- **Let the API process do the exchange through a broker-egress exception:** rejected. It would
  give the process that faces users a broker credential and a broker route.
- **Rely on PKCE:** rejected while it is undocumented.
