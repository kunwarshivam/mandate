# DEC-681: How `mandate-api` reads the workspace API spec where its text leaves a choice

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The L2 builder (Claude Code), under DEC-79 and DEC-176. Each item tightens the spec, or settles a gap by the reading that adds no risk; none loosens a rule or touches one DEC-79 reserves |
| **Story or claim** | E10-10, claim [#750](https://github.com/kunwarshivam/mandate/issues/750); [workspace API spec](../../specs/workspace-api.md) §3.1, §3.2, §3.4, §3.5, §3.8, §5; DEC-436 |

## Decision

1. **`code` is closed on the server.** The lead's dispatch asks for `ProblemCode` to be a closed
   enum. §3.2 names `code` as an open set for clients.
   - Both hold. The server can emit only the codes the enum lists, so it can never send one the
     spec does not name. A client still handles an unknown code by its `status` and `effect`,
     as §3.2 requires.
   - An operation's own codes join the enum in that operation's story, with its spec row.
2. **Decimals are refused unless canonical.** §3.1 requires journal spec §4.6's canonical form.
   - A JSON number is refused as `invalid`.
   - So is text that only normalizes to the canonical form (`"1.50"`, `"+1"`, `"1e2"`). The API
     never normalizes a value the owner did not type, so what is journaled is byte for byte what
     the client sent.
3. **Opaque ids** are journal spec §9.3's `id`, `[A-Za-z0-9_-]+`, bounded here to 64 characters.
   - Every id the platform mints is a ULID (26) or a random id well under 64.
   - The bound refuses only oversized input.
4. **No principal type here.** By the coordinator's ruling of 2026-10-08, roles, client scopes,
   principals, and `authorize` are `mandate-identity`'s (L1), and the `Authenticate` trait is
   `mandate-api-server`'s. This crate defines none of them, so there is one copy to keep right.
5. **§3.4's hash input is a canonical JSON object.**
   - The object is `{"key", "operation", "principal", "workspace"}`, plus `"position"` (an
     integer from 0) for each event of a multi-event call. It is hashed in journal spec §4's
     canonical form. The ULID is the first 128 bits of its SHA-256.
   - Plain concatenation would be ambiguous (`"ab" + "c"` is `"a" + "bc"`). The canonical form is
     already the journal's hashing form.
   - `principal` is the actor's own id: a client's id, never its user's. So a client and its user
     can never collide on one event.
   - `operation` is the route table's operation name.
   - DEC-290's CLI derivation hashes a different object (stream, event type, choice, step-up, head).
     It is not reused; only its ULID encoder is shared, moved into `mandate-canon` by the
     implementation PR.
6. **Request bodies refuse members their shape does not name** (`additionalProperties: false`,
   the coordinator's schema convention of 2026-10-08).
   - A body carrying `requested_by` is refused as `invalid`, so it is never journaled at all, let
     alone as `owner`. API-6's stated test expects such a client request journaled as `client`.
     Refusing it is the tighter reading: no owner value can come from a body either way.
     `requested_by` has no member in any request shape; it comes only from the authenticated
     channel.
   - API-6's text is amended to say so in the spec's own change (the schemas PR, under ES-22), not
     here.
   - A new optional request member (§3.2) therefore ships to the server before any client sends it.
7. **An action card has no free-text member** (API-18). The gate's reason is a code (an `id`),
   quantities are decimals, and the outcome is a closed enum. Model text appears only in quoted
   content, whose `author` is one of two wire codes: `owner_selected` (shown as "Output of software
   you selected") and `platform_authored` (shown as "Platform-authored"), the journal's two display
   labels (`common.schema.json`'s `QuotedContent`, DEC-740 item 8).
8. **Member names the spec leaves open.**
   - A Stop carries `release` and `warning_shown`, as DEC-290 item 2 journals them.
   - An acknowledgment names its event as `acknowledged`.
   - A revoke's `compromised` defaults to `false` when absent, the ordinary revoke of §4.5.
   - The delegation preview's own §6.5 members join with E8-15, which builds the preview.
9. **`retryable` is true for `journal_unavailable`, `rate_limited`, and `membership_unavailable`
   only** (the last as identity spec §4.5 and §3.5's row say).
   - §3.5 states it for `journal_unavailable` and `membership_unavailable`. A `rate_limited` call
     also committed nothing (`effect: none`), and resending it under the same key commits at most
     once (API-4).
   - `rate_limited`'s `true` goes beyond §3.5's text; it is the reading that commits at most once
     either way.
   - Every other code needs a different request (evidence, a new base, a valid body) or cannot
     succeed by resending, so it is `false`. On `unknown` the client polls §5.5 and never retries
     blindly.

10. **How `decode` reports a refused body.** Each refusal is one `schema` violation with a JSON
    pointer and a code:
    - `malformed` at `""`: not JSON, empty, or bytes after the value;
    - `duplicate_member`: one member named twice, at any depth (serde_json alone keeps the last);
    - `unknown_member`: at the member;
    - `type`, `non_canonical`, `missing`, `enum`: at the member, where serde can name it.
11. **A problem's type URI and its effects.**
    - `type` is `https://mandate.dev/problems/<code>`, and the title is fixed per code.
    - Every code is refused before anything is written (`effect: none`), with two exceptions:
      `step_up_required` and `control_stream_frozen` may also carry `recorded`, for §5.6's batch,
      whose kill switch is recorded before its revocation is refused.
    - Identity spec §4.5's six refusals (`own_roles`, `owner_role_reserved`, `last_owner`,
      `last_admin`, `reduction_only`, `membership_unavailable`; DEC-643) are served codes: #766
      added them to §3.5's table without a `(planned: …)` marker, so they are variants now, not
      later. The authorization step commits nothing, so each carries only `none`;
      `membership_unavailable` is never sent for a risk-reducing row, and where it is sent nothing
      was authorized.
    - §3.5 names no code for an append whose outcome is unknown. The schemas PR (#788) adds
      `outcome_unknown` (503, `effect: unknown`, not retryable), marked `(planned: E10-10)`. This
      crate's enum gains the variant with E10-10's implementation, after #788's row lands, so the
      drift test stays green on both sides (DEC-683 item 6). The tests already pin its behaviour
      (it carries `unknown` and nothing else), and the drift tests' in-flight list names E10-10.
      Every other code refuses `unknown`.
    - The title is the one `envelope.schema.json#/$defs/Problem` pins for the code, or item 14's
      for the identity codes; the tests list all nineteen.
12. **A problem's members as a client reads them** (`envelope.schema.json#/$defs/Problem`).
    - `event_id` is required, `null` when `effect` is `none`. A body without the member is
      refused rather than read as `null`.
    - `current_base` is the base now in force, a content reference or an id. It is present exactly
      for `stale_base` (§3.5: "the body names the current base", API-19), and `Problem::of` refuses
      it missing for that code or present for any other.
13. **A policy violation's two levels are distinct types.** The looser `level` is
    `organization`, `workspace`, or `mandate`. The `ancestor_level` is `platform`,
    `organization`, or `workspace`. The platform has no ancestor and the mandate is never one, so
    neither type can spell a finding §4.3 cannot produce.
14. **The identity codes' titles.** Neither §3.5 nor identity spec §4.5 titles its codes, so this
    item fixes them, generic like the rest and naming no content (rule 6, API-10):
    - `own_roles`: "Cannot change own roles";
    - `owner_role_reserved`: "Owner role reserved";
    - `last_owner`: "Owner must remain";
    - `last_admin`: "Admin must remain";
    - `reduction_only`: "Risk reduction only";
    - `membership_unavailable`: "Membership unavailable".

    The schemas PR (#788) must add a per-code branch for each to `envelope.schema.json#/$defs/Problem`
    with these titles, its §3.5 status, `effect: none`, and `retryable` (true only for
    `membership_unavailable`), so the schema and this crate pin the same values.

## Rationale

The spec was written before any of its types existed. Each item fixes the one spelling the code
must pick, and in every case the choice either refuses more input or exposes nothing new. None
changes what the runtime, the executor, or the gate decides, and §1.4 already says the API adds no
trading rule.

## Alternatives considered

- **An open `code` with an `Other(String)` variant.** That would let the server emit an unlisted
  code.
- **Normalizing decimals.** The journal would then hold a value the owner never saw.
- **SHA-256 over concatenated parts** (`Digest::of_parts`). Ambiguous, as item 5 shows.
- **Ignoring unknown request members.** It matches API-6's stated test literally, but it lets a
  misspelled member (`step_upp`) pass silently, and it differs from the schemas' convention.
- **A principal and `Authenticate` seam in this crate.** It would duplicate L1's `mandate-identity`.
