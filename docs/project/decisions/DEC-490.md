## Decision

1. **A sibling subcommand, `mandate journal verify-cold <dir>`**, not a mode of E5-4's `verify`.
   `verify` takes one segment file and `verify-cold` a directory; a `--cold` flag on `verify`
   would make the positional path mean two things, and reading the path's type to pick the mode
   would switch verifiers on an auditor without being told. The two commands share their flags
   where they mean the same: `--store <dir>` (DEC-115 item 7, without it every reference is
   `artifact_missing`), `--anchor <file>` (DEC-115 item 6's JSON), and the trusted start as
   `--from-seq` with `--trusted-prev-hash`, together or not at all, default the genesis start
   (DEC-115 item 5: never read from the export, which would let a rewritten segment vouch for
   itself). `verify-cold` adds `--token <file>`, the anchor's RFC 3161 token as stored, which
   requires `--anchor`. The library call is `mandate_cli::journal::cold::verify(&VerifyColdArgs,
   &mut impl Write) -> anyhow::Result<ColdOutcome>`, tested without a process spawn (ADR-0001).
2. **The directory's layout, which E5-7's export job must write:** each segment is `<name>.jsonl`,
   §6.2's JSON Lines as `mandate_journal::export_segment` writes them, beside `<name>.manifest.json`,
   the manifest's canonical bytes (DEC-263's six fields). The command pairs the two by `<name>`
   and reads nothing else in the directory. **Segments are walked in the order of their
   manifests' `(first_seq, last_seq)`, then their names**, whatever the names are: the manifest
   is §6.2's record of what a segment holds, and a file name is not. A manifest that does not
   parse claims no place and is walked last, so `mandate-journal-cold` reports it as
   `segment_manifest_mismatch` at the `seq` the range expected after everything it could read
   (DEC-264 item 1), which names where the chain stopped. The order cannot hide anything: DEC-264
   item 3 refuses a segment that begins anywhere but where the previous ended, in both
   directions, so a stale or overlapping copy fails `segment_gap` wherever it sorts.
3. **An export the command cannot cover is refused, never reported.** A directory holding no
   segment, a `.jsonl` without its manifest, or a manifest without its `.jsonl` is the refusal
   `cold_export_incomplete`: the export is not what §6.2 says a cold store holds, and a walk
   over the pairs that exist would print `verified` over a range the auditor did not ask about.
   Unlike E5-4's `verified, no events` for an empty segment file, an empty directory is not a
   range at all. Every manifest must name one stream, else `export_mixes_streams` (DEC-115
   item 8's refusal, reused), checked once the walk has passed: the cold crate pins each
   segment's rows to its own manifest's stream, and the command pins the segments to each other.
4. **Every path has a code** (the tracker's known issue, for this path): the export directory,
   each segment and manifest file, the anchor and the token are read before anything runs, and
   an I/O failure or an export path that is not a directory is the refusal `path_unreadable`.
   The other refusals are E5-4's own words: `trusted_start_invalid`, `artifact_store_unusable`,
   `anchor_invalid`, `anchor_covers_another_stream`. A refusal is reported through the error
   with its code first and writes no report line (DEC-115 item 11).
5. **The checks and their order:** `mandate_journal_cold::verify_range` from the trusted start
   over the segments (DEC-264: manifest, file, chain, then the per-event checks, segment by
   segment), whose failure surfaces unchanged as `ColdOutcome::Cold`; then, with `--anchor`, the
   anchor must name a leaf for the export's stream (else `anchor_covers_another_stream`) and
   `mandate_journal::verify_anchor` runs over the rows the range walked — the events at or after
   `from_seq` in every walked segment, read back through `mandate_journal_cold::import_line` — so
   an anchored head the
   range did not verify, before the trusted start or past the last segment, is
   `anchor_head_mismatch` (DEC-115 item 10: an anchor never vouches for what was not checked),
   then `anchor_root_mismatch`; then, with `--token`, `mandate_journal_cold::verify_tsa`. The
   anchor and token checks come after the walk because they are checks over verified events, and
   the token's check needs the anchor; §11 lists the per-range checks without an order, and
   DEC-264 fixed the segment checks' own.
6. **A token is never reported verified.** `verify_tsa` fails closed (DEC-265 item 1): a token
   without the anchor's imprint is `tsa_token_invalid`, and one with it is
   `ColdFailure::TsaVerificationIncomplete`, which the command reports as
   `result: failed, tsa_verification_incomplete` with a non-zero exit. The word is the command's
   own, not a §11 code — §11 has no word for a check that cannot finish — and it goes when the
   crypto half lands and `verify_tsa` can answer `Ok`. A run with `--token` therefore never ends
   on `verified` until then, which is what the story's acceptance says.
7. **The report is seven lines, in this order and nothing else**, so two runs over the same
   bytes are byte-identical:

   ```text
   export: <directory as given>
   segments: <n>
   trusted start: seq <n>, prev_hash <64 hex>
   artifact store: <path as given> | none given
   anchor: <path as given> | none given
   token: <path as given> | none given
   result: verified, stream <id>, seq <first> to <last>, last hash <64 hex>
   ```

   with `result: failed, seq <n>, <code>` for a per-event failure and for a segment check, which
   `mandate-journal-cold` reports at the `seq` the range expected, and `result: failed, <code>`
   for the anchor's and the token's checks. `<first>` is the trusted start's `seq` and `<last>`
   the last event walked. The process exits non-zero whenever `ColdOutcome::failed`, with the
   result text on standard error, as E5-4's command does.
8. **The stubs report `ControlError::Unimplemented { story: "E5-8" }`** (DEC-77, DEC-137): the
   one `Unimplemented` the crate already carries, so every pending test fails with its story's
   report and the implementation PR removes nothing but the stub body.
9. **Three of the journal vectors' tamper cases are re-expressed by a cold export**, each
   asserted by its test: `whitespace_inserted_and_rehashed` (check 1, `non_canonical` at seq 2)
   is `segment_manifest_mismatch` at the segment's first `seq`, because a body that is not
   canonical makes its line not an export line, and DEC-264 item 2's segment check — the
   manifest against the file's own lines — runs before item 4's per-event walk; the export still
   fails, earlier, with a §11 code, which only tightens. `seq_values_swapped` is `seq_gap` at
   the line claiming seq 3, and `column_altered` has no cold input at all, both as DEC-115 item 3
   found for E5-4's export. The other six replay through a cold export with the vector's own
   `seq` and code.

## Rationale

The story's acceptance is that the command never vouches for an export it cannot cover and never
answers `Ok` for a token. Each item resolves a gap §6.2, §11 and §12 leave — the directory's
layout, the walk order, what an incomplete directory means, where the anchor is checked, how an
unfinished check is reported — in the direction that cannot produce a false pass, and reuses
E5-4's words and shapes where the two commands do the same thing, so an auditor's script reads one
vocabulary. The cold crate's checks are called, not copied (DEC-263 item 1): the command reads the
directory, orders the segments, and prints the crate's verdict.

## Alternatives considered

- A `--cold <dir>` mode of `verify`, or picking the mode from the path's type (two meanings for
  one positional, or a silent switch of verifier).
- Walking the segments in file-name order (a name is a claim the manifest does not make; an
  exporter's padding choice would decide the verdict).
- Walking a manifest that does not parse first (reported at `from_seq`, naming nothing about where
  the chain stopped) or refusing it as input (DEC-264 item 1 already gives it a §11 code).
- Reporting `verified, no events` for an empty directory, as E5-4 does for an empty file (a
  directory with no segment is a mistyped path or an empty bucket, not a range).
- Skipping an anchored head outside the verified range as "not this range's business" (true of
  §11's reference rule, but the report would carry `anchor: <path>` as though checked; DEC-115
  item 10 already refused that reading).
- Reporting the incomplete token as `verified` with a note, or as an input refusal (the first
  overstates what was proven; the second hides that every other check passed).
- Checking the token before the walk (its check needs the anchor, and the anchor's needs the walk).
