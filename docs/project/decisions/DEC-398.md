# DEC-398: CI's `full` job may run for 60 minutes, up from 30

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-02 (UTC) |
| **Decided by** | The merge coordinator, under DEC-79 (a reversible engineering and process decision) |
| **Story or claim** | E8-3, [#440](https://github.com/kunwarshivam/mandate/pull/440); ADR-0001 ES-12 |

## Decision

1. The `full` job in `.github/workflows/ci.yml` has `timeout-minutes: 60`. It was 30.
2. Nothing else about the job changes: the same commands run, the mutation gate still fails on a
   missed mutant, and `fast` keeps its 15 minutes.
3. A diff whose mutation run does not finish in 60 minutes is too large for one PR, and is split
   (ES-13), not given a longer limit.
4. This overtakes DEC-366 item 3 in two places: its condition that each PR is sized so `full`
   finishes inside a 30-minute timeout, and its "No PR raises the cap". The rest of DEC-366 stands,
   and its rule of 0 missed mutants is unchanged. #440 carries DEC-366 and updates item 3 to cite
   this decision when it merges `main`.

## Rationale

The mutation gate runs every mutant of a PR's diff against the package's tests. On #440, a diff
of 672 non-test lines under its recorded exception to ES-13 (DEC-366) produced 76 mutants in
`mandate-refcases`, and then 61 after the author cut code to fit. Both runs were cancelled at the
30-minute limit with no test failing and the mutation run unfinished, after 27 and 26 minutes of
mutants. So the measured time is more than half an hour, not up to it, and 60 minutes is a limit
with a known floor, not double headroom. The package's baseline test run grows as `main` gains tests, so the same number of
mutants takes longer each week.

A limit that cancels a correct run does two kinds of harm. It blocks the PR, and it pushes authors
to shape code around the clock: #440 removed a guard and moved an assertion to a later slice to
get under it, and its third slice was to be split in two for the same reason. The size of a PR
should follow from what a reviewer can read in one sitting (ES-13), not from how long the mutants
take.

On cost: a job cancelled at its limit uses its full 30 minutes and gives no verdict. #440 spent
three such runs, 90 minutes, and had none. One run that finishes costs less than that under any
budget, so this decision does not depend on how Actions minutes are billed. Today they are not
billed: DEC-256 planned a private repository with 3,000 minutes a month from 2026-10-01, and the
founder made the repository public again on that date. If it goes private again, the argument
above still holds, and DEC-256's budget already carries a 90-minute nightly job.

ES-12 asks that every job has a timeout, which `full` still has, and sets a median target under 10
minutes for the required checks. The median is untouched: a typical `full` run takes 5 to 25
minutes, and a 60-minute run is the tail.

There is a precedent: `nightly.yml` raised its own limit from 30 to 90 minutes in #428 for the
same reason, that a cap must clear the workload and not cancel it.

## Alternatives considered

- **Keep 30 minutes and split every driver PR further.** This is what #440 was doing. It costs a
  review round per extra PR and lets a CI limit decide the design.
- **Run mutants in parallel, or shard them across jobs.** This is the better long-term fix and is
  left to the backlog. It changes `cargo xtask ci mutants`, which is safety-critical tooling, and
  needs its own story and review.
- **Exempt large diffs from the mutation gate.** Rejected: it weakens the gate (AGENTS.md, safety-
  critical paths).
