# DEC-855: The founder's OAuth login uses fresh PKCE, a single-use exact `state`, and a strict callback (O1b)

|---|---|

| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The E7-24 lane, under DEC-176. Each item reads the published flow the way that accepts less, and none adds risk. The founder approves the `getrandom` row (F-6) |
| **Story or claim** | E7-24 (the first live trade brief's O1b); claim #859; the O1b tests PRs |

## Decision

1. **One callback per login.** `PendingLogin::callback` takes the login by value and it is not
   `Clone`, so any callback spends it, whether accepted or refused (DEC-691 item 6's rule).
   `compile_fail` doctests pin both properties.
2. **`state` exact, and first.** `state` must appear exactly once and, percent-decoded, equal the
   login's own byte for byte, case included. Otherwise the callback is `state_mismatch`. It is
   checked before any other member, so no code and no `error` of another login is ever read.
3. **The callback, strictly.**
   - The path must be exactly `/callback`, in origin form.
   - `code` must appear exactly once, as visible ASCII `0x21` to `0x7e`. This is narrower than
     RFC 6749's `VSCHAR`, as DEC-847 item 6 is for `client_id`. Either failure is `malformed`.
   - An `error` member is `authorization_denied`, its text unread. Other members, such as RFC
     9207's `iss`, are not read.
   - No error carries the state, the code or the target's text (LT-9, CN-9).
4. **Fresh secrets.** The verifier and the `state` are 32 bytes each from the operating system
   (`getrandom` 0.2, already in `Cargo.lock` through `ring`), as 43 characters of unpadded
   base64url (RFC 7636 §4.1). If the generator fails, the result is `random_unavailable`. The
   challenge is `S256` only, hashed with `mandate-canon`'s `Digest`, so no hash crate is added.
   All three secrets are `SecretString`s only.
5. **The request.**
   - It carries exactly `response_type`, `client_id`, `redirect_uri`, `code_challenge`,
     `code_challenge_method`, `state` and `resource`, which is the MCP endpoint (RFC 8707, as MCP
     2025-06-18 requires).
   - It sends no `scope`, since none is published. If one is required, the founder's R0 login
     refuses, and that is a new decision.
   - An authorization endpoint with any query is `endpoint_shape`, stricter than RFC 6749 §3.1.
6. **Two parts.** Part 2 adds the loopback listener (`tokio`'s `net`), the code exchange, the
   token as a `SecretString`, and LT-9's canary scan.

## Rationale

Every refusal ends the login before a token exists (rule 3). Checking `state` first is RFC 6749
§10.12's CSRF defence.

## Alternatives considered

- **A run-time `spent` flag.** Rejected: weaker than the type.
- **`rustls`'s `SecureRandom`.** Rejected: the brief names `getrandom`.
