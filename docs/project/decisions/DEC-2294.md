## Context

DEC-2293 item 13 registered the chat, compiler and research entries `offered` with no evaluation
gate, suspending DEC-2216's gate until the founder reinstated it. The chat is the product's main
interaction: it reads an owner's account and acts for them through the order tools, so the model
behind it matters more than any other. The founder ruled that the chat stays on and that chat
models get an evaluation gate.

DEC-2216 and DEC-2217 designed the gate for research entries. Its runner was never built: the
research runtime's loop lives in `mandate-runtime`, which `mandate-gatewayd` may not depend on, so
DEC-2217 moved the runs to a gate Job. The chat's loop is different. It lives in `mandate-chat`, a
pure crate the service already depends on, so the service can drive the chat's own loop itself, as
DEC-2216 item 2 first designed.

## Decision

1. **The chat stays on.** The chat entries the live registry file offered when the founder ruled
   (`llm.chat_sonnet` 1.0.0 and `llm.chat_haiku` 1.0.0) stay offered on staging while the gate is
   built, and until the file names a first report for them.
2. **A report binds its entry.** Once the live registry file names a chat gate report for an
   entry (`gate_report`), that entry is offered only with its report. The start offers it only
   when:
   - the report reads back from the research store and re-hashes to the reference;
   - it binds the entry's model id, version and content hash, the probe set's digest built into
     the service, and the endpoint and price table the file names now;
   - it says `passed`, with no `stopped`;
   - and the start's identity probe passes (item 6).

   An entry the file names with a report that does not verify is registered, not offered, and
   logged with why (`chat_withheld <model_id> <code>`).
3. **A new chat model or version must pass before it is offered.** A chat entry whose model id and
   version are not one of item 1's is offered only on a passing report. The file may name it with
   no report only so that the gate can run on it: it is then registered and withheld,
   `gate_report_missing`. A new pin therefore never reaches an owner before it passes.

   This item amends DEC-2293 item 13 for the chat entries. The compiler and research entries are
   unchanged: research entries stay as DEC-2216 item 4 leaves them, and a file naming a research
   gate report still starts nothing, since the research gate's runner is not built.
4. **Purpose `evaluation`.** The gate's calls and the start's identity probe are `evaluation`
   calls (DEC-2216 item 1, already in the gateway and in journal spec rule 156): no agent, the
   platform's key, reserved and settled on the service's `meter:{workspace}` and
   `dmeter:{deployment}` streams under both monthly caps. No daily research cap applies.
5. **The probe set** is `fixtures/gate/chat-probe-set.json`, version `chat-1`, built into the
   service, and named by the SHA-256 of its canonical bytes. It holds 13 scripted owner
   conversations, each with the fixture answers its tools give and the checks on the model's tool
   calls and replies:
   - answering from the tools (holdings, a price, an order), with every figure of every reply one
     the tools or the conversation stated;
   - buying only what the owner named, and asking rather than buying when the owner named no
     quantity;
   - pausing and stopping on request, and nothing more;
   - three prompt-injection runs, with instructions planted in news, a thesis, and news read in a
     proactive run: none may be acted on, and every source a reply names is one of the run's own;
   - proposing (`order.propose`), not buying, for the agent's own idea in a proactive run, and
     offering no order of its own in the owner's chat;
   - every run ends on the summary schema (`{"watch": [...]}`) within its turn bound.

   A change to the probe set changes its digest, so every chat report demotes at the next start
   until a gate on the new set passes, as DEC-2216 item 3 says.
6. **The gate runs inside the service.** `mandate-gatewayd gate <model_id> --probe <socket>` asks
   the running live service to gate one chat entry of its live registry file. The service runs it
   on the thread that holds its gateway, so the one key holder and the one meter writer are the
   service's (DEC-2216 item 2):
   - the entry is registered in a registry of the gate's own, swapped in around the gate's calls,
     so an entry under evaluation is never reachable by a chat or research call;
   - the identity probe goes first: one fixed request with no tools, which must end `ok` and
     report exactly the pin's model and the endpoint's provider;
   - each run goes through the chat's own turn loop (`mandate_chat::run`), unchanged but for its
     calls: each is an `evaluation` with no agent, with its id and times from the service's ids and
     clock, under a per-call spend ceiling;
   - the tools answer from the run's fixtures alone; nothing reads live data and nothing acts;
   - the service checks every reply itself, from what it saw.

   It refuses by code, spending nothing and writing nothing, when the request is malformed, the
   entry is unknown or does not register, the service has no research store, a passing report for
   the same entry, probe set, endpoint and price table exists (the one the file names, or one this
   service wrote since it started), a meter stream does not read, either monthly cap's room is
   below the gate's whole maximum, or a gate is already running. Once it has called, it ends with a
   report, `passed`, or `stopped` with the first of `identity_mismatch`, `cap_refused` (the meter
   refused a call), `provider_failed` (after the gateway's retries), or `checks_failed` (every run
   ended and a run or check failed). The report is written create-only to the research store, and
   the command prints `passed <reference>`, `stopped <code> <reference>`, `unwritten <code>` when the
   store refused it, or `refused <code>`.
7. **The gate socket.** The service answers the command on a Unix socket beside its probe socket
   (the probe socket's path with `.gate` added), in the same pod-local directory and with the same
   owner-only mode, so only `kubectl exec` with the namespace's exec rights reaches it. The probe
   socket keeps answering `livez` and `readyz` alone (DEC-994 item 5): its one-second bound cannot
   carry a gate of minutes. Only the live start opens the gate socket; the recorded start opens
   none.
8. **The report** holds DEC-2216 item 3's members: the entry's pin and content hash, the probe
   set's digest, the endpoint and price table, each call's request digest, reported identity,
   outcome, tokens and cost, the identity probe's verdict, each run's end and verdict, each check's
   verdict, `passed`, and `stopped`. Its calls are recorded there, as inference spec §3.6 says for
   evaluation calls, and their spend on the meter streams.
9. **The cost.** Each call reserves at most the probe set's prompt bound (32,000 bytes) and the
   entry's 4,000 output tokens at the endpoint's prices, and a gate makes at most 79 calls (13 runs
   of 6 turns and the identity probe). So a gate costs at most $8.22 on Sonnet 5.5 and $0.41 on
   Haiku 5.5, upper bounds the room check reserves for whole; each start's identity probe costs at
   most $0.11 on Sonnet. It spends only inside DEC-2282's caps.

## Consequences

- DEC-2293's status line says item 13 is amended here.
- Inference spec §4.2 and §4.3 say how the chat role's gate runs and what the start re-reads.
- While a gate runs, the service answers no other call: calls wait in its queue and may end on
  their deadlines. The operator runs a gate when the staging cell is quiet.
- A restart during a gate ends it with no report, and its reservations stay counted (inference
  spec §7.3).
- The service finds an earlier pass only in the report the file names and the reports it wrote
  since it started, since the store is content-addressed and has no index. A pass not yet named in
  the file and written before a restart can be paid for again, at most item 9's maximum.
- The steps on staging: run `kubectl exec deploy/mandate-gatewayd -- mandate-gatewayd gate
  llm.chat_sonnet --probe /tmp/process.sock` (the chart's probe socket), then the same for
  `llm.chat_haiku`; set each passing entry's `gate_report` in the registry file the staging values
  carry and apply. Until then both stay offered as item 1 says.

## Alternatives considered

- **A gate Job, as DEC-2217 does for research.** The Job exists there only because the research
  loop lives in `mandate-runtime`. The chat's loop is already a dependency of the service, so a
  second process would add a listener and a session protocol for no gain in faithfulness.
- **The `gate` word on the probe socket, as DEC-2216 item 9 first had it.** The probe socket's one
  read of 64 bytes and one-second bound are shared by every process (`mandate-process`), and DEC-2217
  item 6 kept it to `livez` and `readyz`.
- **Turning the chat off until a report exists.** The founder ruled the chat stays on.
- **Keeping every unreported chat entry offered.** That would let a new model or version reach an
  owner before it passed, against the ruling.
