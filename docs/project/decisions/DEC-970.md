# DEC-970: The web app reads and commands through the workspace API behind one server-side data-source switch, with a provisional read contract until the read-model schemas land

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The `claude-code` builder of lane W2 (the demo lane of the managed-cells plan, DEC-967), under DEC-79 and DEC-176: every item is a reversible engineering choice inside `web/`, and each reading taken where the spec is silent is the one that adds no risk |
| **Story or claim** | E11-9, claim [#1443](https://github.com/kunwarshivam/mandate/issues/1443); supports E21-45; workspace API spec §3, §4.3, §4.5, §4.7, §4.9, §5.2, §5.4, §5.5, §6.3 |

## Decision

1. **One switch, on the server.** `web/src/lib/data-source.ts` reads `OWLHEAD_DATA_SOURCE`
   (`fixtures`, the default when unset or empty, or `api`), `OWLHEAD_API_ORIGIN` and
   `OWLHEAD_WORKSPACE_ID` from the server's environment when a request is served (`connection()`),
   never from a `NEXT_PUBLIC_` variable and never inlined at build (ES-12). Neither value is a
   secret: the browser reaches the API with its own session cookie (spec §3.3 item 5,
   `credentials: "include"`). The origin must be `https`, or `http` on a loopback host for
   development and the e2e suite, with no path, query or credentials.
2. **Fail closed.** Any other value of `OWLHEAD_DATA_SOURCE`, or an `api` choice whose origin or
   workspace does not parse, is `misconfigured`: the app shows the deployment unreachable and holds
   no data. It never falls back to the fixtures, so fixture figures never pass for a record (rule 3).
3. **Fixtures stay the default** for `npm run dev`, the unit and e2e suites, and the landing page's
   live demo: `/demo` builds its workspace from the fixtures directly and never reads the switch
   (DEC-906 item 4).
4. **The web app calls only documented operations** (DEC-967 item 13). `web/src/api/operations.ts`
   lists each read and command the app uses with the spec section that documents it;
   `contract.test.ts` fails an entry the spec's operation tables do not list, a query member the
   spec does not name, a request made while loading the workspace and sending every command that no
   entry matches, a command body with a member its request schema does not allow or without one it
   requires, and a `/v1/` path written anywhere in `web/src` outside `src/api/` and the mock route.
   This is E21-45's check from the web side until the OpenAPI document is published.
5. **A provisional read contract, until `schemas/workspace-api/read-models/` lands.** The spec
   names each read's route (§4.7, §4.9) but not its body. Until the schemas do, each body is the
   envelope (§3.2, §6.1) plus the `web/src/fixtures/types.ts` shape §4.9 maps to it, as
   `web/src/api/mock-server.ts` serves it:

   | Route | Body members |
   |---|---|
   | `GET /health` | `served_at`, and `market_data`, `broker`, `deployment`, `relay`, each `{state, freshness: {observed_at, stale, age_seconds, limit_source}}` |
   | `GET /dashboard` | `decisions` (`GateDecision[]`), `external_positions` |
   | `GET /agents` | `agents: [{agent_id}]` |
   | `GET /agents/{id}` | `agent`: `Agent` without `positions`, `orders`, `past_orders`, `fills`, with the mandate in force inline |
   | `GET /agents/{id}/positions` | `positions` |
   | `GET /agents/{id}/orders` | `orders`, `past_orders`, `fills` |
   | `GET /agents/{id}/timeline` | `events` (`TimelineEvent[]`) |
   | `GET /approvals?state=pending\|resolved` | `approvals: [{approval_id}]` |
   | `GET /approvals/{id}` | `approval`: `Approval` with `content_hash` |
   | `GET /connections` | `connections`: `Connection` with `environment` |

   The decoders (`web/src/api/reads.ts`) refuse, as an unreadable answer the screens show as
   unreachable: a JSON number anywhere but a count member (a decimal sent as a float); a value a
   closed enum the screens branch on does not list (agent mode, startup, restriction code, order
   state and purpose, approval status, gate verdict and reason, timeline kind, health state,
   environment, broker); an approval without its `content_hash` (API-12); and a read without its
   watermarks (API-14). When the schemas land, their generated decoders replace these and this item
   is superseded; the server lane (E21-31) serves these bodies or the schemas, whichever is first.
6. **What the app does not know, it reads at its conservative value.** Over the API the number of
   approvers is 0 and `independent_approval_required` is `null` (required, V-047) until a members and
   policy read is wired; the account's equity and price history are not drawn (the charts render
   nothing) and the sample headlines are hidden, since no route serves them and seeded bars beside a
   deployment's figures would read as a record; the "Fixture data" tags that mark the workspace's
   own figures are hidden, and the ones that mark sample content stay.
7. **Commands go through the API's idempotent write routes** (spec §5.2, §5.4): one key per
   gesture, the same key and body on every resend (API-4), at most four sends with backoff while the
   API does not answer, then `unknown`, never success and never "nothing happened" (API-13). A
   recorded command is followed through `GET /commands/{id}` to `applied`, `refused` or `ended`,
   and the workspace is read again (§6.3). Commands are sent whatever the reads say (API-8). The
   mapping: pause, resume and stop to the agent's routes; release to stop with `release: true` and
   the SHA-256 of the warning lines shown as `warning_shown`; the kill switch at the agent's scope;
   pause-all as one pause per agent not stopped; stop-all and close-all as the kill switch at the
   connection's scope, or the workspace's when no connection has been read; an answer to
   `POST /approvals/{id}/responses` with the content hash the read gave.
8. **Step-up and records, until their routes exist.** `step_up` is `null` on every command: the
   browser's step-up ceremony (E9-4) and the artifact upload a `record` names are not built. The API
   forwards a missing step-up for the stream owner to refuse (§5.4), or answers an approve with
   `step_up_required` and records nothing (§5.2); the screen then says "Not recorded" and that
   nothing was approved. `record` is `null` wherever its schema allows; an answer's required
   `record` is the SHA-256 of the screen's lines as shown, with the web build named `owlhead-web/E11-9`.
9. **Not sent in this slice:** setting up an agent and changing a mandate (drafts, versions,
   confirmation, deploy; spec §4.1, §4.2). Over the API they send nothing and say so.
10. **The mock API at `/v1` is development and e2e only** (`web/src/app/v1/`): a production build
    answers 404 there, which `scripts/no-scenarios.mjs` checks after every build. The e2e suite
    `npm run test:e2e:api` runs the e2e build with the API as its data source against it, and runs
    against the API server instead once E21-31's routes are on `main`
    (`OWLHEAD_API_E2E_ORIGIN`, `OWLHEAD_API_E2E_WORKSPACE`).

## Rationale

The demo of 2026-10-26 shows the web app on a hosted cell's paper workspace (DEC-969), and the
plan makes the web app one client of the public API (DEC-967 item 13). A switch on the server keeps
every test and the landing page on fixtures, puts nothing in the bundle, and lets one build serve
either. Failing closed is rule 3: an unreadable configuration or answer is shown as unreachable, not
as figures. The read bodies are a gap in the spec; pinning them to §4.9's own mapping changes no
screen contract, which is what §4.9 says replacing fixtures with calls should do, and the strict
decoders keep a mismatch from rendering as something it is not.

## Alternatives considered

- **A `NEXT_PUBLIC_` switch.** Inlined at build, so one build could not serve both, and the choice
  would sit in the bundle; refused by ES-12's rule for the bundle.
- **Reading through the Next server** (server components fetching the API and passing data down).
  The session cookie is host-only on the API's host (§3.3 item 5), so the app's server cannot hold
  it, and a server-side path into the cell is what DEC-967 item 13 refuses.
- **Falling back to fixtures when the API is misconfigured or down.** Shows fixture figures as a
  deployment's; refused (rule 3).
- **Waiting for the read-model schemas.** They are not scheduled before the demo; the provisional
  contract is superseded by them without a screen change.
- **Faking step-up in the browser.** A mock passkey's "verified" would be evidence of nothing;
  sending `null` lets the API and the stream owner refuse it where the spec says they do.
