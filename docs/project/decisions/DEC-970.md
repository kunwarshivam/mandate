On the Tuesday rehearsal clock the founder's `cli_confirm` grant was committed on the control
stream and then refused by the runtime `step_up_method`, because the shell built its mandate view
with `live_cli_confirm: None` (R16). Verify of the control and agent streams failed
`artifact_missing`, because the `ApprovalRequested` lists its `content_hash` in `artifact_refs` and
nothing put the content object in the store (R17). These are the readings that close them.

## Decision

1. **Where the scope comes from.** DEC-923's `LiveScope` is read by the run exactly as
   `mandate approvals approve` reads it (`crates/mandate-cli/src/approvals.rs`, `live_scope`).
   The record is the mandate connection's latest `ConnectionEstablished` or `ConnectionRevoked` by
   `seq`, a revocation outranking an establishment at the same `seq`. That record must be an
   establishment whose `environment` is `live`. Its `broker` gives the scope's broker:
   `robinhood` is `Robinhood`, and anything else is `Other`, which DEC-923 never admits. The
   confirmed mandate (the version the run deployed, DEC-957) gives `risk.max_order_usd` and the
   pinned instruments' asset ids. The owner is the one `mandate_shell::approvers::members`
   already reads for DEC-953, so a membership record the run does not fold, or a record naming no
   user, gives no scope. The function is `mandate_shell::approvers::live_cli_confirm`.
2. **Only a live run.** The scope is read only when the connection the live door chose is
   `live`. A paper run gives none, and the runtime admits `cli_confirm` on paper anyway (DEC-155
   item 4). The runtime still reads the scope only on a `live` mandate view
   (`crates/mandate-runtime/src/escalation.rs`, `answered`). `mandate-approval`'s
   `live_cli_confirm` still checks every DEC-923 condition at each grant: Robinhood, a mandate cap
   of at most 100 USD, one pinned instrument, a US equity, an order of at most 100 USD, and the
   owner as approver. This change decides none of them and widens none.
3. **How it reaches the runtime.** `RunContext` gains `live_cli_confirm`, which `run_context`
   leaves `None` and the runner sets from item 1 after `load_contexts_with_clock`. The shell's
   `runtime_view` hands it to `ApprovalSettings::live_cli_confirm`. With no scope, every live
   `cli_confirm` grant is refused `step_up_method` as before, and nothing is sent (`AGENTS.md`
   rule 3).
4. **R17: store the content object, never stop listing it.** Journal spec §9.7 types
   `ApprovalRequested.content_hash` as a `ref`. §3 lists every `ref` in `artifact_refs`, and the
   type table says "the object must be stored and re-hashes (§11 check 6)". So the strict reading
   is to store the object, not to drop the hash from `artifact_refs`. The placing run's journal
   (`StoreJournal`, given the run's store as `Sources.content_store`) puts each `ApprovalRequested`
   draft's canonical `content` in the store under its `content_hash`, before the append. If the
   content is missing, if the hash does not name exactly that content, or if the store refuses the
   put, the batch is not appended (`Unavailable`). No record then names an object the store does
   not hold, and the ask is never made. The CLI's `ApprovalResponseSubmitted` cites the same hash
   and finds the same object, since the run and the CLI share the store. A run with no content
   store (the dry run's scratch journal, the booking pass, and the tests' journals) puts nothing,
   as before.

## Rationale

DEC-923 was accepted for exactly this deployment, and the CLI already checks it locally before it
commits a grant. The runtime refused only because the run never told it the scope. Reading the
scope from the same records, by the same rule, keeps the CLI's local check and the runtime's
admission in agreement. Storing the content object keeps verification strict: an exported stream
verifies against the store it was written with, or fails.

## Alternatives considered

- **A constant scope in the live build**: it would admit a grant whatever the records say, which
  DEC-923 forbids.
- **Reading the scope in `mandate-paper` from the door's `Connection`**: the door holds no owner,
  and the owner rule is already the shell's (DEC-953). Two readers of one rule would drift.
- **Dropping the inline content's hash from `artifact_refs`**: smaller, but it contradicts §3's
  "every `sha256:` reference" and §9.7's `ref` type. That would be a spec change (ES-22) that
  loosens verification.
