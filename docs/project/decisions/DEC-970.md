## Context

Four lanes of the managed-cells plan (DEC-967) build long-running processes: the scheduler and
the runtime and executor processes (P2, P3), the API server (A1), the vault (V2), and the
deployment manager (D1). Each needs the same answers: when it is live, when it is ready, what it
may do while it is not, how long a drain may take, and when restarts have become a crash loop
(design §3.4, §7.3). `mandate-agentd` (E21-2 slice 1, DEC-968) proved a lease, reconciliation
before start, loopback health, and a SIGTERM drain for one deployment. E21-28 puts the shared
part in one crate that lands first, with a small interface the other lanes import.

## Decision

1. **A new pure safety-critical crate, `mandate-process`, at layer 3.** It depends only on
   `mandate-journal` (the `Fenced` outcome) and `mandate-time` (`UtcNanos`), with no external
   crate. It reads no clock and draws no randomness: every input arrives with its time, so the
   same inputs give the same states. Its one I/O is the probe socket of item 5, `std` only.
2. **The lifecycle is a fold.** `Lifecycle::new(kind, liveness, at)` then `observe(at, input)`
   returns the state, one of `Starting`, `Replaying`, `Ready`, `NotReady`, `Draining` and
   `Exited(exit)`. The inputs are `Heartbeat`, `StartupPassed` (design §3.4's start-up checks),
   `EpochTaken`, `Replayed { position, head }`, `Reconciled { passed }` (the executor's
   reconciliation, the runtime's mode known), `Fenced` (`Input::from_append` maps an append's
   `Fenced` outcome to it), `DrainRequested`, `Settled` and `Failed`. The `Kind` says which gates
   readiness asks: `Executor` and `Runtime` the epoch, the replay at the head and the
   reconciliation; `Writer` (the scheduler, any single writer) the epoch and the replay; `Service`
   none past its start-up checks. The state is derived from the facts folded so far:
   - `Exited` once any of: `Fenced`, in every state; `Failed`, which exits `Refused` before the
     process was up under its epoch, `CycleFailed` once it was, and `DrainIncomplete` while
     draining; `Settled` while draining, `Drained`; a drain past its bound (item 4). An exited
     process ignores every later input.
   - else `Draining` once a drain was requested, else `Starting` until the start-up checks pass,
     else `Replaying` until the process holds its epoch and has replayed to the head under it,
     else `Ready` while every gate holds and `NotReady` otherwise.
   States only move forward in that order, except `Ready` and `NotReady`, which alternate as the
   replay falls behind the head or a reconciliation fails and recovers.
3. **What a process may do follows from the state, never from readiness alone (design §3.4).**
   `permits(Action::Open)` (a new cycle or opening) only while `Ready`. `Action::RiskExit` (risk
   exits and protective re-placement) once started, holding the epoch and replayed under it,
   whether ready or not, draining included, as design §3.4 and §7.3 require of an executor that
   is not ready. `Action::KillSwitch` whenever the process is up, in every state but `Exited`: it
   is never gated on readiness, the epoch or the replay; the journal's fence still refuses an
   append of a process without its epoch. An exited process is permitted nothing, so a `Fenced`
   append is always followed by no further side effect. Stricter reading (DEC-176): a replay
   position or a reconciliation observed before `EpochTaken` does not count toward readiness or
   risk exits, since the old writer may have appended after it; design §7.3 step 3 has the new
   process replay and reconcile after it takes the epoch.
4. **The bounds, as design §3.4 and §7.3 propose them.**
   - **Drain:** `DRAIN_BOUND`, 90 seconds from the first `DrainRequested`. An input observed past
     it exits `DrainIncomplete` before the input applies: the drain is abandoned, never forced,
     and the next process recovers as after a crash. A repeated request never extends it.
   - **Liveness:** live while not exited and the last input is within the process's own bound,
     given at `new`, since §3.4 sets no number. Every input is a heartbeat.
   - **Time:** the fold's time is the latest `at` it has seen, so a clock that steps back neither
     extends a drain nor moves liveness back.
   - **Crash loop:** `crash_loop(restarts, now)` is true when `CRASH_LOOP_RESTARTS` (5) restarts
     fall within `CRASH_LOOP_WINDOW` (10 minutes) before `now`, both ends included; a restart
     after `now` counts, so a clock behind the journal never hides a loop. Its inputs are
     journaled restarts, which the caller reads from the journal, never the orchestrator's count.
     Which journal fact records a restart is the deployment manager's to choose (E21-33, lane D1,
     with a journal spec change first if it needs a new event); this crate takes only the
     instants.
5. **Probes go over a Unix socket, asked by `exec` probes; no HTTP server crate (D-1 is not
   taken here).** `probe::serve(path, status, clock)` binds a Unix socket and answers one request
   line, `livez` or `readyz`, with `ok <word>` or `fail <word>`, from the `Snapshot` the process
   last published into its `Status`, judged at the caller's `clock()`. `probe::query(path, probe)`
   is what each binary's probe subcommand runs; `Answer::exit_status` is 0 when it passed and 1
   otherwise. The words are fixed: `live`, `stalled`, `stopped`, `ready`, `not_ready`,
   `not_found`, with no id, symbol, price, quantity, or mandate content (`AGENTS.md` rule 6).
   Readiness also needs liveness, so a stalled process is not ready. A socket left at the path by
   an earlier process is replaced; any other file there is refused. A peer may send at most 64
   bytes and stay silent for one second, so no client can hold the socket from the probes. In
   Kubernetes the socket lives on a pod-local `emptyDir` (the root file system is read-only) and
   the probe is `exec` of the process's own binary, which needs no shell in the image; Compose
   runs the same command as a `CMD` health check.
6. **Readiness is also judged at probe time.** A published snapshot carries the time until which
   the process counts as live; a probe after it answers `stalled` and `not_ready`, so a loop that
   stops publishing is restarted even though its last snapshot said ready.
7. **`mandate-agentd` shares it without changing behaviour.** Its `Stop` is now
   `mandate_process::Exit`, with the same variants, codes and exit statuses, and its
   `health::answer` maps each phase to the shared state and answers through `probe::answer`, with
   no heartbeat bound yet (DEC-968 item 7). Its loopback HTTP listener and its tests are
   unchanged. It moves onto the full lifecycle and the socket when E21-30 (lane P3) hosts the
   runtime and executor as processes.
8. **Proposed, for the founder: one PR, over ES-13's line limit.** The dispatch asked for one PR
   with the tests in their own first commit, failing on stubs (DEC-921). The crate's `src/` is
   about 500 lines with its doc comments, over ES-13's 400 for a safety-critical crate. Every
   other gate is kept: independent review on a different model, every mutant on the diff killed,
   CI green. If the founder prefers, the probe socket splits from the lifecycle as a stacked PR.

## Rationale

The fold keeps the lifecycle's rules in one place that four lanes share, so readiness, the kill
switch's independence from it, the drain bound and the crash-loop bound cannot drift between
processes. Making it pure and fed with injected time is what lets its property test compare it
with an independent oracle over random input sequences, including clocks that step back and
drains that cross their bound to the nanosecond.

A Unix socket keeps every data-plane pod without an inbound port: the kubelet cannot reach a
loopback listener with an `httpGet` probe, so HTTP probes would need a listener on the pod's
address, which K1's default-deny network policy (E21-36, "no inbound to the data plane") would
have to open for each process. `exec` probes over a socket open nothing, need no new crate, and
work the same under Compose. The choice is reversible: `probe::answer` is independent of the
transport, so moving to HTTP probes later changes only the listener.

## Alternatives considered

- **HTTP probes on axum (D-1, pre-approved by DEC-969).** Rejected for probes: an inbound port on
  every process and a large dependency tree for two fixed answers. The API server (A1) still takes
  D-1 for its own routes.
- **`mandate-agentd`'s loopback HTTP listener for every process.** Rejected: the kubelet cannot
  reach loopback. It stays in `mandate-agentd` until P3 replaces it.
- **TCP socket probes.** Rejected: they show only that a port is open, not readiness.
- **A clock read inside the probe socket.** Rejected: the crate reads no clock; the binary hands
  `serve` its clock.
- **The crash-loop bound over the orchestrator's restart count.** Rejected by the story: the
  orchestrator's count resets with a pod's replacement, and the journal's does not.
