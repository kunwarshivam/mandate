# DEC-786: The run order of `POST /verifications`, and `first_failure.seq` as rule 111 reports it

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | An agent (Claude Code, lane L5's spec author) under DEC-79 and DEC-176: each item tightens workspace API §4.8.1 to journal spec §11 and rule 111, or orders checks §11 leaves unordered, and adds no risk |
| **Story or claim** | E12-3 ([#748](https://github.com/kunwarshivam/mandate/issues/748)); workspace API spec §4.8.1 row J4; journal spec v0.36 |

## Context

Workspace API §4.8.1 listed the per-range checks of a requested verification, but:

- it reported `anchor_root_mismatch` and `tsa_token_invalid` at `from_seq − 1` (the trusted-start
  anchor's `seq`), `segment_manifest_mismatch` at a segment's first `seq`, and `segment_gap` at the
  first missing `seq`, while journal spec rule 111 records those four with `seq` `null`, and a
  non-null `seq` only inside `[from_seq, to_seq]`, which `from_seq − 1` is not;
- its run order named only `intent_action_mismatch` and `mode_event_mismatch` of §11's stream
  checks, leaving out `anchor_self_mismatch`, `break_glass_cause_mismatch`, `held_mismatch`, and
  `connection_lifecycle_mismatch`, so a range could pass the API while §11 fails it.

## Decision

1. **`first_failure.seq` is nullable, and `null` exactly for `anchor_root_mismatch`,
   `tsa_token_invalid`, `segment_manifest_mismatch`, and `segment_gap`.** Every other code is
   reported at an event inside the range. This is rule 111's classing; §4.8.1 had no other
   source, and a value outside the range could not be recorded at all.
2. **The run order.** Checks 1 to 6 on every event; then, only when none failed, in this order:
   `anchor_head_mismatch` (lowest anchored `seq` first); `anchor_root_mismatch` then the token
   check, per anchor in ascending anchor `seq`, the trusted-start anchor included;
   `segment_manifest_mismatch`, in ascending `first_seq`; `segment_gap`; then **the stream type's
   own checks**, judged together, the lowest `seq` reported and ties broken by §11's listing order:
   - `ctl:{ws}`: `anchor_self_mismatch`, `break_glass_cause_mismatch`,
     `connection_lifecycle_mismatch`;
   - an agent stream: `intent_action_mismatch`, `mode_event_mismatch`, `held_mismatch`;
   - an account stream: `connection_lifecycle_mismatch`.
   The first failure ends the run. An incomplete token check does not ([DEC-789](DEC-789.md)).
3. **`connection_cause_mismatch` never runs in a request.** §11 makes it the full-chain run's
   only, since it reads the control stream and its account streams together, and a request names
   one stream.
4. **This order deliberately differs from the CLI's** ([DEC-782](DEC-782.md) item 1, which runs
   the stream checks before `--anchor` and `--token`). The API keeps the order DEC-767 and §4.8.1
   already gave it, anchors and segments first, and slots the stream checks where §4.8.1 had its
   agent checks.

## Rationale

Every order gives the same verdict: a range that fails any check fails. Order decides only which
code a range with several faults shows. For the API, whose answer is recorded and alerts on call,
the anchor and segment checks come first because they compare the hot store with what was fixed
outside it (the anchor root, the cold-store manifest); a mismatch there is the direct evidence of
tampering, and a rewritten range can be made to break or satisfy a stream rule at will. The CLI
reads files an auditor hands it, where DEC-782's reason (an anchor vouches for checked events)
fits; changing either to match the other buys nothing. Lowest `seq` first within the stream
checks is DEC-782 item 2's rule and `verify_agent_stream_anchored`'s behaviour, so the library
serves both.

## Alternatives considered

- **Adopt DEC-782's order for the API.** Rejected: it reorders a contract DEC-767 already set,
  for no change in verdict.
- **Keep reporting the four range codes at a `seq`.** Rejected: rule 111 refuses it, so the API
  could not record its own result.
- **Run `connection_cause_mismatch` against the account streams too.** Rejected: a request is
  one stream by §4.8.1's shape; §11's weekly full-chain run covers it.
