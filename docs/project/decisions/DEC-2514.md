## Context

Both cores raised alerts as `NotificationRef { subject_event, message_key: &'static str }`. A
string can be any literal, and the executor built some keys at runtime: a restriction's reason,
a park's reason. Nothing wrote `OwnerAlertSent`, the dispatcher's cause, so no alert could reach
an owner even once a dispatcher runs. The coordinator chose the spec's plan over a process-layer
map whose unknown keys would need a fallback.

## Decision

1. **A closed set of owner kinds.** `mandate_notify::OwnerAlertKind` is every §3.2 kind a stream
   owner may raise: the catalogue less `approval_requested`, `approval_reminder` and
   `channel_lost`, which journal spec §9.15 refuses on an `OwnerAlertSent`. So no core can build an
   alert record that refuses its batch, and no alert without a kind can be raised.
2. **The executor's alerts carry a kind.** `NotificationRef` holds `kind: OwnerAlertKind`. Each
   site maps by spec §3.2's table:
   - `protection`: the stop watchdog, an interval at its bound, and protection expiring.
   - `exit_stalled`: the ladder at its floor, an exit held past its bound, with nothing to price
     from, released, parked for the session, and a kill switch's cancel retries spent.
   - `reconciliation`: a mismatch, cash drift, and a fee difference.
   - `agent_held`: an unmapped broker status.
   - `account_restriction`: any restriction the broker's account or a reject causes, whatever its
     reason.
   - `external_activity`.
   - `kill_switch`: every switch the executor applies, as it alerted every one before. §3.4 makes a
     user's switch one notice, written by the workspace services with the command, but nothing
     writes that yet (backlog E8-9k). Dropping the executor's alert first would leave a user's
     switch with none, and removing an owner-facing alert is the founder's call (DEC-723's
     reasoning). E8-9k removes the executor's alert for a user's and an operator's switch when it
     lands, so §3.4's one notice holds then.
3. **The executor records each alert.** `Batch::notify` journals
   `OwnerAlertSent { subject, kind, owner_command: null }`, `causation_id` the subject, right
   where it is raised, so it is in the subject's own run of drafts, which a shell that appends each
   run separately (the paper runner's tracer) keeps in one append, as rule 130 requires.
   - **One per subject.** The first kind wins (§3.4, rule 130). Where a reconciliation's cash drift
     and its fee difference name one snapshot, the owner gets one `reconciliation` notice.
   - **No id moves.** The record's id is derived at ordinal 900,000 and up, never from the drafts'
     own ordinals, so no id an earlier draft predicted for a later one (`Batch::id_after`, a
     protective order's client order id) moves. A version that took the next ordinal sent a cancel
     for an order that did not exist.
   - **Never fails the batch.** A subject the batch did not draft gets the effect alone, since its
     record would refuse the batch (`AGENTS.md` rule 13). One alert is raised that way today: a
     kill switch's cancel whose retries are spent, which a tick raises about the cancel's earlier
     record. It needs an account-stream record of its own to be a journaled cause (backlog
     E7-2v); until then it reaches the process's report and not the dispatcher.
   - Both folds take `OwnerAlertSent` as a record that changes nothing, ahead of the executor's
     `risk_clock` read, which it does not carry.
4. **The runtime's alerts are closed too, and none is an owner kind.** `RuntimeAlert` is
   `DecisionSkipped` (a dry run's deny: DEC-723 is the founder's, so its interim, raising the
   alert as before, is kept), `ResearchCallRefused` and `ResearchDeadlineStreak` (operator alerts).
   The runtime journals no `OwnerAlertSent` until a §3.2 row is its own.
5. **The report keeps LT-10's key.** The paper runner releases an uncovered run only on the
   unprotected interval's own alert, and `protection` is shared with the stop watchdog. So the
   tracer reports `unprotected_interval_limit` exactly for a `protection` alert whose subject is a
   `ProtectionChanged` `interval_limit` record. It reads that record from every account draft it
   appends, so every path that reports an alert, the watch's included, sees it.
6. **The catalogue's rows name what they cover.** §3.2's `protection`, `exit_stalled` and
   `reconciliation` rows now list the executor keys this decision maps to them: protection that can
   no longer be re-placed before expiry, an exit parked for a closed or unknown session, a kill
   switch's spent cancel retries, and a persistent cash drift's pause. The executor raised each
   before; they now have a named row. `OwnerAlertKind` follows `NoticeKind`, which lacks §3.2's
   `kill_switch_unapplied` and `retirement_held` (written by the manager and the runtime); adding
   them is their writers' change.

## Consequences

- Every executor owner alert in the cell but one (E7-2v) is now a journaled cause the dispatcher
  can read (X8 part 2 builds the dispatcher process). No alert is removed: every key the executor
  raised is still raised, under its §3.2 kind, and §3.2's rows now name the keys they cover.
- Two gaps found on the way are backlog rows: `AccountRestrictionChanged` has no registered
  journal schema, so the real journal refuses that batch (E7-2u); and the user kill switch's
  `OwnerAlertSent` is not yet written by the workspace services (E8-9k).
