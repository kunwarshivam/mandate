# DEC-2514: `ApprovalRequested` version 3 names the checks the dry run deferred

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and DEC-176, and the coordinator's ruling on option (a), 2026-10-26. It only tightens: the approver is told which checks have not run, and a request that hides one is refused) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane D1) |
| **Story or claim** | E21-30; [DEC-2378](DEC-2378.md) item 11 condition 4; [DEC-2388](DEC-2388.md) items 10, 12 and 13 |

## Context

Since DEC-2388 item 13, the cell's runtime asks the owner about an opening whose dry run deferred
checks to the executor's binding gate. `DecisionMade` version 3 names each deferral, and the
`ApprovalRequested` that asks names that decision as its cause. But the content the approver is
shown, and whose hash the grant repeats, said nothing about them. DEC-2378 item 11 condition 4
asks only that the request never claim the checks passed, and an empty `risk_impact` claims
nothing. Still, an approver who is not told can read silence as a pass. The coordinator chose
option (a): put the names inside the hashed content, with a fixed sentence shown to the approver.

## Decision

1. **`ApprovalRequested` version 3 (journal spec v0.88).**
   - **Members:** version 2's content, then `deferred_to_binding`, last and required, in
     `DecisionMade` version 3's names.
   - **Hashed:** the list sits inside the content hash, so a grant approves the order knowing
     exactly which checks are still to run.
   - **Versions 1 and 2** refuse the member.
   - **When it is used:** exactly when the decision that asks is version 3 and defers a check.
   - **A deferring ask without a builder plan** has no version: the journal refuses it, so the
     runtime asks no one rather than hide the deferral. This is an accepted gap, like
     `DecisionMade` version 3 with version 2's references.
2. **Rule 291, on the request:** the list is strictly ascending by bytes (`non_canonical`), never
   empty, and names `liquidity_floor` and `participation` both or neither (`schema`), as rule 270
   has the decision do.
3. **Rule 292, on the batch, at every version:** when the `DecisionMade` a request names is in its
   `append` batch, the request's list equals the decision's, an absent member read as empty on
   either side, or the batch is refused whole. So no request hides a deferral, and none invents
   one.
4. **Across batches:** nothing is checked yet. The runtime writes both in one batch. A §11
   per-range check is debt: `docs/project/backlog/E21-30-approval-deferral-range-check.md`.
5. **What the approver is shown** (mandate spec v0.12 §6.4), exactly:
   - the sentence "These checks have not been run yet. They run when the order is placed, and may
     still refuse it:";
   - then each check by name.

   A deferred check is never shown as passed. Lane W renders it. The wording is the platform's,
   not advice: it tells the approver what has not happened, and it describes no trade or outcome.
6. **§6.2 step 5c (mandate spec v0.12)** now says what DEC-2388 item 12 does: a dry run that
   deferred a check turns an `auto` into `ask`, labelled `policy_overlay` when that changed the
   decision.
7. **Rule numbers:** 291 and 292 are the coordinator's block for D1. They were renumbered from 271
   and 272 after lane NE's v0.87 took 271.
8. **Delivery:** this spec and vectors first (the spec guard). Then `mandate-journal` (the version 3
   schema, rule 291, rule 292 in `check_batch`). Then the runtime writes version 3, and the shell's
   and the daemon's `EventDraft::schema_version` answers 3. Then lane W renders the sentence.

## Rationale

The record the approver grants on should carry what the approver must know. Naming the deferrals
in the hashed content makes the grant's meaning exact: the owner approved this order with these
checks still to run, and the binding gate runs them (DEC-2378 item 11 condition 3). Putting the
check in the batch means the runtime cannot write a request that disagrees with its own decision.

## Alternatives considered

- **Leave the names on the decision only (DEC-2388 item 10's reading).** It meets condition 4's
  letter. But the approver is shown the content, not the decision, so it is told nothing.
- **A fixed sentence inside the content, beside the names.** It would bind the wording to every
  request's hash, so any change to the wording would need a new version. The sentence is fixed in
  the mandate spec instead, and the content carries only the names.
