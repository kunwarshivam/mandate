# DEC-781: A control-stream freeze has no carve-outs, and no break-glass access before the operator service spec

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The founder, on 2026-10-09, answering the two freeze questions DEC-774 left open and DEC-261 item 9; relayed by the coordinator and recorded by the L5 lane lead (`claude-code`) |
| **Story or claim** | E12-3 ([#748](https://github.com/kunwarshivam/mandate/issues/748)); follows [DEC-774](DEC-774.md) item 5; DEC-261 item 9 in the [decision log](../04-decision-log.md#decisions) |

## Decision

1. **No carve-outs from the freeze.** While a control-stream verification failure holds the
   control stream frozen (journal spec §11, a SEV-1), these stay frozen and are refused
   `control_stream_frozen`:
   - confirming a mandate version, even one whose change only tightens. It is still a mandate
     change, which §11 freezes, though outside a freeze a tightening applies at once;
   - Stop.

   Pause, holding new openings, the kill switch at any scope, and owner exits stay available, as
   the workspace API's API-7 operations and `AGENTS.md` rule 13 require. Risk exits and
   protective orders are never held by the freeze (DEC-774 item 5).
2. **The specs already say this.**
   - Workspace API §5.1, confirming a mandate version, says "every confirm is refused with
     `control_stream_frozen`" while the control stream is frozen.
   - API-7's operation list does not name Stop, and its test column says Stop is not risk
     reduction.
   - Journal spec §11, as DEC-774 item 5 left it, lists only risk exits, protective orders, owner
     exits, and the kill switch as what the freeze never holds.

   So no spec text changes for this. One wording is loose: the workspace API's "Control stream
   frozen" row says the API-7 operations stay recorded because "otherwise a tampering incident
   would disable Stop", and there "Stop" means the kill switch. That is a wording fix for the
   workspace API's owner, not a rule change.
3. **The tests land with the freeze.** No code enforces the freeze yet: `ControlStreamFrozen` is
   only an error code. The change that implements it adds these cases to API-7's per-operation
   matrix:
   - a tightening-only confirm and a Stop, each refused `control_stream_frozen` and journaling
     nothing;
   - pause, hold, the kill switch at each scope, and an owner exit, each still committing.
4. **No break-glass access yet (DEC-261 item 9).** The founder ruled that the operator service
   spec (E17-6) is written before the platform ever uses break-glass access, and that until then
   no break-glass is used. DEC-261 item 9 stays open until that spec. Meanwhile:
   - `PlatformOperatorAction` stays unregistered;
   - DEC-774 item 2's fail-closed check stands: every operator read fails
     `break_glass_cause_mismatch`, now implemented in Rust (#1099).

## Rationale

The freeze answers a possible tampering incident on the control stream, the stream that records
mandate versions, memberships and operator actions. The founder chose to hold every change to what
an agent may do there, even a tightening, and to keep only the operations that take risk off.
Those are pause, hold, the kill switch, and owner exits, and none of them depends on the control
stream's integrity. Stop is not on that list: it ends a deployment, which is a deployment change,
and an owner who needs the agent to stop trading still has pause and the kill switch.

## Alternatives considered

- **A carve-out for tightening-only versions, which apply at once outside a freeze.** The founder
  declined it.
- **A carve-out for Stop.** The founder declined it.
