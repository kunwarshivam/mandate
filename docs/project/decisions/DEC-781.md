## Decision

1. **No carve-outs from the freeze.** While a control-stream verification failure holds the
   control stream frozen (journal spec §11, a SEV-1), these stay frozen and are refused
   `control_stream_frozen`:
   - confirming a mandate version through workspace API §5.1, even one whose change only tightens.
     It is still a mandate change, which §11 freezes, though outside a freeze a tightening applies
     at once;
   - Stop.

   Pause, holding new openings, the kill switch at any scope, and owner exits stay available.

   **Scope.** The ruling did not name the other API-7 operations. These are:
   - §4.4's reducing shortcuts, ending a delegation and away mode, which create and confirm a
     version of their own;
   - Skip on an approval.

   API-7 says none of them is ever refused for a frozen control stream. §5.1 says the shortcuts are
   still recorded while frozen. This decision does not change that: they stay available. That is
   the reading that never blocks risk reduction (`AGENTS.md` rules 2 and 13). It goes back to the
   founder to confirm. Risk exits and protective orders are never held by the freeze (DEC-774
   item 5).
2. **The specs agree, with one loose wording.**
   - Workspace API §5.1 says "every confirm is refused with `control_stream_frozen`" while the
     control stream is frozen, and that the API-7 operations, its reducing shortcuts included, are
     still recorded.
   - API-7's operation list does not name Stop, and its test column says Stop is not risk
     reduction.
   - Journal spec §11, as DEC-774 item 5 left it, lists only risk exits, protective orders, owner
     exits, and the kill switch as what the freeze never holds.

   No spec says Stop is refused while frozen, but none says it stays available either, so the
   ruling closes that silence. One wording reads against the ruling: the workspace API's "Control
   stream frozen" row says the API-7 operations stay recorded because "otherwise a tampering
   incident would disable Stop". There "Stop" can only mean the kill switch. Changing it to name
   the kill switch is for the workspace API's owner. It changes no rule.
3. **The tests land with the freeze.** No code enforces the freeze yet: `ControlStreamFrozen` is
   only an error code. The change that implements it adds these cases to API-7's per-operation
   matrix:
   - a tightening-only §5.1 confirm and a Stop, each refused `control_stream_frozen` and journaling
     nothing;
   - each API-7 operation still committing: pause, hold, the kill switch at each scope, an owner
     exit, Skip, ending a delegation, and away mode.
4. **No break-glass access yet (DEC-261 item 9).** The founder ruled that the operator service's
   specification is written before the platform ever uses break-glass access. DEC-261 item 9 places
   that specification in E17-6's later slice. Until then no break-glass is used, and DEC-261
   item 9 stays open. Meanwhile:
   - `PlatformOperatorAction` stays unregistered;
   - DEC-774 item 2's fail-closed check stands: every operator read fails
     `break_glass_cause_mismatch`, now implemented in Rust (#1099).

## Rationale

The founder chose no carve-outs. What follows is the recorder's account of why the result is
consistent with the rest of the specs, not the founder's reasoning.

The freeze answers a possible tampering incident on the control stream, the stream that records
mandate versions, memberships and operator actions. Holding ordinary mandate changes and Stop there
still leaves the owner every operation that takes risk off, which API-7 and `AGENTS.md` rule 13
require: pause, hold, the kill switch, owner exits, and the API-7 shortcuts.

## Alternatives considered

- **A carve-out for tightening-only versions, which apply at once outside a freeze.** The founder
  declined it.
- **A carve-out for Stop.** The founder declined it.
- **Reading the ruling as freezing the reducing shortcuts too.** The recorder rejected this: it
  would contradict API-7, which is binding, and block risk reduction, so it needs the founder's
  explicit word.
