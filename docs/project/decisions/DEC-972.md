## Decision

1. **What a release is.** `cargo xtask release build <out>` builds, from the checked-out commit
   with `--locked`, the binaries `mandate` (`mandate-cli`), `mandate-agentd` and `mandate-rh-sim`
   (the loopback test double the local cell runs beside an executor, DEC-124; never a broker) for
   `x86_64-unknown-linux-musl`, statically linked (`-C target-feature=+crt-static`), in the
   `release` profile. It names no feature, so no release build holds `live` (DEC-529 item 3); a
   test checks that no shipped package is the crate `xtask/layers.toml` marks `live_feature`. The
   live executor image is B3's (E21-48) and is not built here.
2. **What makes it reproducible.** Every machine path rustc could write into a binary is
   remapped to a fixed prefix (`--remap-path-prefix`: the checkout to `/mandate`, `CARGO_HOME` to
   `/cargo`, `RUSTUP_HOME` to `/rustup`); `SOURCE_DATE_EPOCH` is the commit's time; incremental
   compilation is off; the build's environment is cleared to the home, terminal, proxy and
   certificate settings plus its own, so no `RUSTC_WRAPPER`, inherited rustflags or `cargo run`
   variable reaches it; the toolchain is `rust-toolchain.toml`'s; and the musl target's C code
   (`ring`) is built with the runner's `gcc`, named rather than searched for. The build keeps its
   own target directory (`target/release-build`), so its flags never rebuild the workspace's.
   **Residual:** `gcc` and the linker are the runner image's, not pinned. If the `ubuntu-24.04`
   image changes them between the two jobs, the builds can differ and `compare` fails: loudly, and
   never by passing a build it should not. Each build logs `rustc -vV`, `gcc --version` and
   `ld --version` so such a failure can be told from a real one.
3. **The proof is two builds in CI.** `.github/workflows/release.yml` builds each `main` commit
   twice, on two runners, in two checkout paths, with no cache, and fails unless both print the
   same digest of their `SHA256SUMS`, which lists every binary's SHA-256. A pull request that
   changes the release build runs the same jobs and keeps nothing; only `main` and a manual run
   keep `build-a`'s output as the run's artifact (ES-12). The workflow runs only `cargo xtask`, so
   the tools' pins and the build's flags live in one place, `xtask/src/release.rs`.
4. **The build digest is the binary's SHA-256.** `mandate-release`'s `BuildDigest` is the SHA-256
   of an executable's bytes, the same digest `SHA256SUMS` lists, written `sha256:<hex>` as the
   envelope's `actor.build` admits (journal spec §3). A process takes its own from
   `/proc/self/exe` on Linux, which names the running file even after its path is replaced, so a
   release installed over a running one cannot make the old process journal the new digest. The
   digest is what R2 signs and checks at start (OPS-15, E21-35), so the release's identity, its
   signature and what the journal names are one value.
5. **The SBOM comes from the binary.** `cargo-auditable` embeds each binary's resolved dependency
   list in the binary; `syft` reads it back and writes one CycloneDX JSON SBOM a binary
   (`sbom/<binary>.cdx.json`), offline. The SBOMs carry a generation time, so they are not
   compared; the binaries are.
6. **Tools.** `cargo-auditable` 0.7.7 and `syft` 1.52.0, each the x86_64 Linux asset of its
   GitHub release, checked against a pinned SHA-256 (checked against the project's own published
   checksums when pinned), installed by `cargo xtask release tools` under `$CARGO_HOME/mandate-release-tools`, never
   inside the checkout: cargo hashes the path of `cargo-auditable`, its `RUSTC_WORKSPACE_WRAPPER`,
   into every workspace crate's metadata, so a tool inside each checkout made two checkouts'
   binaries differ (found by the first two-checkout run).
   They are not in `.cursor/install.sh` or `cargo xtask check`, which never build a release.
7. **Wiring the digest into each writer is its own slice.** The writers that journal today name
   a placeholder `build` (a digest of the crate's name and version): `mandate-shell`'s
   `envelope.rs`, on R0's run path, and `mandate-cli`'s `control.rs`, the CLI's control-stream
   writer, which R0's rehearsal drives. Neither is touched until R0 closes (DEC-967 item 2);
   switching both to `BuildDigest::running()` is queued **after R0**. The long-running processes
   (`mandate-agentd`'s hosts, E21-30's runtime and executor) take it at start when they first
   journal, and E21-35's start-up check reads the same value.

## Rationale

The infrastructure design (§7.1 step 2) already chose static Linux binaries, `--locked`,
`SOURCE_DATE_EPOCH`, a double-build diff, an SBOM and cargo-auditable metadata; this records how.
Remapping paths and pinning the compiler are what keep two checkouts byte-identical: two local
builds of one commit from two checkout paths and two target directories gave identical
`SHA256SUMS` before this was written. Hashing the file a process runs, rather than embedding a
hash at build time, is the only build digest a binary can know about itself without a second
build, and it is the value a signature over the binary signs.

## Alternatives considered

- **glibc binaries on a distroless base:** the image then carries a libc to patch; musl static
  binaries run on an empty base (E21-35).
- **`cargo-cyclonedx` for the SBOM:** it writes one SBOM a workspace crate from the manifests,
  not one a shipped binary from what was linked; `cargo-sbom` likewise. Syft reading the
  auditable data describes exactly the artifact that ships.
- **One job building twice:** the same runner and the same disk would share whatever made the
  first build; two runners share nothing but the commit.
- **An embedded build ID as the digest:** a value compiled in cannot be the hash of the file that
  contains it, and would not match `SHA256SUMS` or the signature.
- **Switching the writers now:** R0's run and rehearsal journal through them this week; a change
  to every event's `actor.build` belongs after R0 closes.
