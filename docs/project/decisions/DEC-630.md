DEC-531 names the profile's categories. It leaves its exact fields open, and SP1 had not yet
written them. B1 could not start until they were fixed, so the coordinator ruled on the open
points, and this decision records the result.

## Decision

1. **Times in force and protection are keyed by order type and quantity form.** A row is one
   asset class in one session. It holds cells, one per order type and quantity form, and each
   cell lists its times in force and its protection forms. DEC-531 keyed both by asset class
   and session, which cannot state trading spec §5.2's rule for Alpaca: fractional and notional
   orders are `day` only and are not allowed in an OCO or bracket. Keying by cell keeps that
   rule, so LT-14 holds.

   **A cell lists a protection form when an order of that type and quantity form may be
   submitted as that form**, that is, as the order whose `type` the submission carries:
   - a bracket's entry;
   - an OCO's parent, which is its take-profit;
   - the one resting stop-limit itself.

   It never lists the forms an order may appear in only as a leg. Each form fixes its own
   legs: a bracket's and an OCO's are a limit take-profit and a stop or stop-limit stop-loss.
   So the builder and protection ask one question of one cell: "may this order be sent as a
   bracket, as an OCO, or as the resting stop-limit?"

   **Alpaca's cells come from its public order documentation**
   ([Orders at Alpaca](https://docs.alpaca.markets/docs/orders-at-alpaca), read on
   2026-10-08). Where the documentation is unclear, the tighter set is taken (DEC-176):
   - **Bracket:** a whole-share market or limit order. The documentation's example entry is a
     market order, and it gives `limit_price` as "the limit price of the entry order, for
     bracket or OTO orders if the entry type is limit". It names no stop or stop-limit entry,
     so neither is listed.
   - **OCO:** a whole-share limit order only. The documentation says "the type parameter must
     always be 'limit'".
   - **Resting stop-limit:** none on equities. DEC-36 gives it to crypto only, whose row
     comes with B2a.
   - **Times in force:** whole shares take `day` and `gtc`, which are §5.2's values and the
     only ones the documentation's whole-quantity table gives without "contact the sales
     team". Fractional and notional orders take `day` only: the fractional table answers
     "No" for every other time in force.
   - **Fractional and notional orders take no protection form.** This is §5.2's "not allowed
     in OCO or bracket orders".
2. **Idempotency has three members:**
   - `client_order_id`: whether an order carries an id the client chooses.
   - `retry`: `idempotent`, `not_idempotent`, or `unknown`.
   - `query_by_client_order_id`: whether orders can be looked up by that id.

   **`unknown` is read exactly as `not_idempotent`: never a blind re-send.** A lost answer is
   queried. When the query cannot resolve it, the order stays `Unknown`, which blocks the
   instrument (DEC-160, DEC-529). The rule is a type, not a convention:
   `Retry::may_resend_blindly` is true for `idempotent` alone, and nothing else reads `retry`
   to decide a re-send.

   A profile without a client order id must say `not_idempotent` and must not offer a query
   by it; any other combination is refused.

   Alpaca's values come from the connector as it stands:
   - `client_order_id` is true: our id goes on the wire (`wire::submission_body`).
   - `retry` is `idempotent`: a second order with an id Alpaca holds is refused with a 422
     (`client.rs` `DUPLICATE_CLIENT_ORDER_ID`, the recorded `submit_duplicate_client_order_id`).
   - `query_by_client_order_id` is true (`/v2/orders:by_client_order_id`,
     `TradingClient::order_by_client_id`).
3. **Version 1 of the type has no GTC-expiry field and no pre-trade-check field.** Both rows
   in the brief's Robinhood table are recorded as later, additive fields. A later version
   that adds either is a new `profile_version` and a new hash.
4. **Rows: Alpaca declares US equities in the regular session only** (DEC-531 item 6). Its
   crypto row comes with B2a, which moves the executor's crypto stop-limit choice onto the
   profile.
5. **One `day` value.** Robinhood's `gfd` and Alpaca's `day` are one domain value, `day`,
   because both expire at the end of the session in which the order was placed. Each
   connector maps its own spelling.
6. **The hashed object** is canonical JSON (journal spec §4) built through `mandate-canon`.
   Its keys are snake_case:
   - `kind` is `"broker_profile"`.
   - `profile_version` is an integer, starting at 1.
   - `rows` is an array of `{asset_class, session, cells}`. Each cell is
     `{order_type, quantity_form, times_in_force, protection_forms}`.
   - `idempotency` is `{client_order_id, retry, query_by_client_order_id}`.

   Enums are spelled as trading spec §5.2 and the schemas spell them:
   - `order_type`: `market`, `limit`, `stop` (Robinhood's `stop_market`), `stop_limit`.
   - `quantity_form`: `whole`, `fractional`, `notional`.
   - `times_in_force`: `day`, `gtc`, `ioc`.
   - `protection_forms`: `bracket`, `oco`, `stop_limit`.
   - `asset_class` and `session` use `mandate-domain`'s spellings.

   Arrays are sorted, so the order a connector declares in is not part of the profile:
   - rows by asset class, then session (so `us_equity`'s `after_hours` row comes before its
     `regular` row, and both come after any `crypto` row);
   - cells by order type, then quantity form;
   - each set by its spelling.

   The profile hash is the SHA-256 of the canonical bytes.
7. **Refusals.** A profile is refused when:
   - its version is 0;
   - it has no rows, or a row has no cells;
   - two rows name the same asset class and session;
   - two cells in a row name the same order type and quantity form;
   - a cell has no time in force;
   - it claims deduplication or a query without a client order id.

   Each refusal has its own stable code.
8. **Journal registration is not in B1.** The `broker_profile` kind is not in journal spec
   §9.2's closed `ConfigSnapshotRegistered` vocabulary. The coordinator gave that change to
   the SP1 builder as a journal spec PR. B1 exposes `CapabilityProfile::KIND`, the canonical
   object and its hash for that registration to use.
9. **Typed reads.** Readers never parse the canonical object. A profile answers:
   - `idempotency()`, the three idempotency members;
   - `cell(asset_class, session, order_type, quantity_form)`, the one cell for an order.
     An order the profile does not list is refused `profile_not_offered`, so a missing
     cell can never be read as "anything goes".

## Rationale

These are the smallest fields that state, as data, every rule the first live order reads,
together with the rule Alpaca already has. LT-14 needs Alpaca's fractional rule to survive the
move, and only per-cell keying can carry it. The third idempotency state records what the
Robinhood contract leaves open, instead of guessing. Reading that state as `not_idempotent`
adds no risk (DEC-176).

## Alternatives considered

- **Times in force and protection per row, as DEC-531 first listed them:** these cannot state
  Alpaca's fractional rule, so they would break LT-14.
- **Listing a form wherever the order may be a leg of it:** a stop could then say "bracket"
  because it can be a bracket's stop-loss, and the reader could not tell that from "may enter
  a bracket". The legs are fixed by the form, so listing them adds nothing a reader needs.
- **A boolean retry:** this would force the Robinhood profile to claim something its contract
  does not say.
- **Hashing in declaration order:** two connectors declaring the same rules in a different
  order would get different hashes, so a reordering would look like a contract change.
