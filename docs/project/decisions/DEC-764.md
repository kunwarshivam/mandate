# DEC-764: Timeline: which account-stream events are an agent's, a k-way merge, and one cursor per stream

| **Story or claim** | E12-6 ([#756](https://github.com/kunwarshivam/mandate/issues/756)); E12-1 (#745), E12-2 (#747), E12-3 (#748); workspace API spec §4.8.1 |

## Decision

1. A timeline merges `agent:{ws}:{agent_id}` with the account stream of each connection the agent
   was deployed on.
2. An account-stream event is the agent's when its `agent_id` (or `agent`) is the agent or `*`, its
   `intent_id` is an intent whose `IntentReceived` names the agent, its `client_order_id` is an
   order whose `OrderRequestRecorded` names the agent, its `causation_id` names an event of the
   agent's stream, or it is `AccountRestrictionChanged` or a connection- or workspace-scope
   `KillSwitchActivated`.
3. Order is a k-way merge: each stream in `seq` order, the next event the head with the least
   `(recorded_at, stream_id)`. A stream's own events never leave `seq` order.
4. One cursor per stream, `after=<stream_id>:<seq>`. Events a `types`, `from` (inclusive), or `to`
   (exclusive, on `recorded_at`) filter excludes are consumed, so pages stay complete. At most
   10,000 events consumed per stream per page; `more: true` says the page stopped early.

## Rationale

`recorded_at` comes from a host clock that may step back, so sorting by it alone could reorder one
stream's events and break a per-stream cursor. The merge keeps the readability order the spec asks
for and makes completeness provable. The membership rules use only links the records carry.

## Alternatives considered

- **Sort by `(recorded_at, stream_id, seq)` strictly.** Rejected: under a clock step the per-stream
  cursor would skip or repeat events.
- **Every account-stream event.** Rejected: marks, fees, and settlement are the account's, not the
  agent's, and would bury the agent's history; they stay one stream page away.
