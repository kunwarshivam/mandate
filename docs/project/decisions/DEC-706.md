## Context

Journal spec §9.15 closes `NoticeAttempted` at schema version 1 ([DEC-720](DEC-720.md)): a
`failed` attempt carries its `reason` (rule 127), not the provider's verdict. Notifications spec
§5.2's `send` returns `retryable { reason }` or `permanent { reason }`, and
[DEC-725](DEC-725.md) item 6.3 says the verdict decides whether that channel is tried again, not
the reason. Under accepted decisions two reasons occur both ways:

- `provider_error` is `permanent` for a relay refusal of the deployment's own request
  ([DEC-728](DEC-728.md) item 1) and for a push service's `400`, `401`, or `403`
  ([DEC-729](DEC-729.md) item 4 and its interim), and `retryable` for a `5xx` and any status the
  spec does not name (DEC-729 items 7 and 8);
- `too_large` is `permanent` for a push `413` (DEC-729 item 5), and `retryable { too_large }` retries
  (DEC-725 item 6.3).

The dispatcher keeps no state outside the journal: on every step, and after a restart, it re-reads
the notice stream, and "a notice with no terminal attempt is due again" (notifications spec §5.1
step 4). NT-8's oracle reads only the journal too. From a version-1 record neither can tell a
`failed` attempt to retry from one that ended its channel.

## Decision

1. **`NoticeAttempted` version 2.** Version 1's members in their order, and `verdict` last:
   `retryable` | `permanent`, nullable. It is a closed enum of strings, as every other closed value
   in §9.15 (`status`, `reason`, `channel`) and §9.1's `a` | `b` type are, and it uses §5.2's own
   words, so the record names the outcome the adapter returned; a boolean such as `final` would
   need a reading of its own and would blur with the "terminal attempt" of item 5, which other
   statuses also reach.
2. **Present on every record, non-null exactly when `status` is `failed`** (rule 134). This is
   DEC-720's closed-schema form: every listed member is present and `null` only where the type is
   nullable, as rule 127 does for `reason`. So for `delivered`, `suppressed_quiet_hours`,
   `deferred_quiet_hours`, and `abandoned` it is `null`.
3. **Refused on append** with §9.1's reasons and order: an absent `verdict`, or an unlisted member
   beside it, is `schema` at that member; a non-string is `schema` and a string outside the two
   values `non_canonical` at `payload.verdict`; a `null` on a `failed` attempt, or a value on any
   other, is `schema` at `payload.verdict` (rule 134, after rule 129 in the report order).
4. **Which outcome gives which verdict.** §5.2's `permanent { reason }` is `permanent`. Its
   `retryable { reason }`, and a timeout with no answer (the caller's `retryable { timeout }`,
   DEC-725 item 6.3), are `retryable`. A receipt's `failed` record (`bounced`, `complained`,
   `unsubscribed`) is `permanent`. Where §5.2 to §5.4 fix a reason's verdict, rule 134 holds the
   record to it: `permanent` for `address_rejected`, `auth_failed`, `recipient_not_permitted`,
   `address_missing`, and the three receipts; `retryable` for `timeout` and `rate_limited`. Only
   `provider_error` and `too_large` take either. So a record never marks an address `unreachable`
   while its channel is still retried, and never stops a channel on a timeout or a rate limit.
5. **A terminal attempt** on a recipient's channel is `delivered`, `suppressed_quiet_hours`,
   `abandoned`, or `failed` with the verdict `permanent`; `deferred_quiet_hours` and a `failed`
   attempt with the verdict `retryable` leave that channel due. This is notifications spec §7's
   diagram, now stated in journal spec §9.15's Lifecycle and §5.1 step 4.
6. **Version 1.** It is not edited (journal spec §8) and still replays. A stored version-1 `failed`
   attempt reads as `permanent`: that channel is finished for that notice, and nothing is sent
   again on a guess. From journal spec v0.40, `append` refuses `NoticeAttempted` at version 1 as
   `unknown_schema` at `payload`, and every writer appends version 2, so a writer cannot leave the
   verdict out by writing the older shape. This differs on purpose from `VerificationRun`'s
   version 1, which stayed appendable (v0.36): there no member could be skipped by it, and here
   the older shape is exactly the record without the verdict.
7. **No deployment holds a version-1 record.** The only writer is `mandate_dispatcher::step`
   (slice D2), a library whose only callers are its own tests (`step/tests.rs`, `step/tests/crash.rs`)
   over an in-memory journal; no crate depends on `mandate-dispatcher`, and the dispatcher process
   (slice D10) is not built. `reference/journal` and `docs/specs/reference-cases/journal.yaml` do
   not model §9.15, and `fixtures/refcases/` holds no notice record.
8. **Notifications spec §7's provider-down row** said "after the window, `failed`"; §5.3 and
   journal rule 127 record the end of the window as `abandoned` with reason `retry_window_ended`
   (`not_pending` for an `action` notice). The row now says so, and records each attempt as
   `failed` with the verdict `retryable`.
9. **DEC-720 and DEC-725 are not amended.** DEC-720 closed version 1, which this leaves as written;
   version 2 extends it. DEC-725 item 6.3's policy is unchanged; this records its input. Neither
   status line changes.

## Rationale

The verdict is already known when the attempt is journaled (`Outcome::Retryable` or
`Outcome::Permanent` in `mandate-notify`), and dropping it at the journal boundary leaves the
dispatcher's restart, and NT-8's oracle, to guess. Recording it adds information and changes no
send, no mark, and no `channel_lost`: those follow `reason` exactly as before (§5.6). Rule 134 and
the refusal of version 1 only refuse more. A refused append stops the step before its next send
(DEC-704 item 3), the safe default the journal-first rule gives every other refusal. It changes
nothing the owner is told (DEC-723), touches no trading path (NT-9), and weakens no invariant, so
DEC-176 lets an agent accept it, as the coordinator's ruling R3 said.

Reading an old `failed` record as `permanent` is the coordinator's default. It matches what the
step does today (any attempt ends that channel), it never re-sends a deterministic refusal for 24
hours (DEC-728's reason), and no deployment can hold such a record (item 7).

**Consequences.** `crates/mandate-journal/tests/notices.rs` gains the pending tests of version 2,
rule 134, and the refusal of version 1 (DEC-77); the implementation then registers version 2 in
`notices.rs`, stops admitting version 1, and moves the step's writer (`step.rs`'s `attempt`) to
version 2 in the same change, so `main` never holds a writer the journal refuses. Slice D4
(retries) then reads `verdict` to decide whether a channel is due, through
`mandate_notify::next_attempt`'s schedule.

## Alternatives considered

- **`final: bool`.** Rejected: §9.15 writes every closed value as an enum of names, and §5.2 names
  the two outcomes; a boolean would need its own reading and would be easy to confuse with a
  terminal attempt, which `delivered` and `abandoned` also are.
- **Add the member to version 1 in place.** Rejected: §8 never edits a stored schema, and the
  journal has added members only at a new version (`OrderStateChanged` at v0.34, `VerificationRun`
  at v0.36), even where no writer had appended version 1.
- **Keep version 1 appendable.** Rejected: a writer could then journal a `failed` attempt with no
  verdict, which item 6 must read as a stop; refusing it closes that path at no cost, since no
  deployment writes it.
- **Read a version-1 `failed` attempt from its reason** (`timeout` and `rate_limited` retry).
  Rejected: it guesses for the two reasons that occur both ways, and none of these records exists.
- **No rule tying the verdict to the reason.** Rejected: journal §9.15 already notes that a
  separate flag "could only disagree with the reason"; rule 134 holds it to §5.2 to §5.4 wherever
  they fix the verdict, and leaves it free only where accepted decisions do.
