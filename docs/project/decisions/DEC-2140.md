# DEC-2140: The workspace API's alerts read (`GET /alerts`)

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79 and DEC-176. It serves records the journal already holds, adds no write, and narrows what a member sees, never widens it) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane EX), on the coordinator's assignment |
| **Story or claim** | G5 alerts center over the API (workspace API spec §4.7, E11-9), the web alerts screen for the 2026-10-26 demo; notifications spec §1.3, §3.2, §4.1, §5.9; journal spec §9.15 |

## Context

Workspace API spec §4.7 lists `GET /alerts`, "G5, from `OwnerAlertSent` and the events it names",
with no shape, and nothing serves it, so the web alerts screen shows "not available from your
deployment yet" over the API. The notifications spec makes the web inbox a pull channel whose list
is the journal itself (§1.3, §4.1). Since DEC-2514 every core alert is an `OwnerAlertSent` in its
subject's batch, and since DEC-2516 the cell's dispatcher journals a notice and its attempts for
each.

## Decision

1. **`GET /alerts` returns `read-models/alerts`, users only until client tokens land (E10-14).**
   It reads the streams the dispatcher follows (DEC-2516 item 1): the control stream, every agent
   stream `AgentDeployed` names, and every account stream `ConnectionRequested` or
   `ConnectionEstablished` names, with the notice stream. Using the same streams means the inbox
   and the dispatcher agree on what an alert is. Alerts are served most recent first (`raised_at`,
   then `alert_id`, both descending), at most `limit` (1 to 200, default 50; anything else is
   `invalid`), with `truncated`.
2. **Only the alerts about agents and accounts.** The read serves the kinds notifications spec
   §3.2 sends to an agent's or an account's owners, with workspace admins or not. It never serves
   the nine kinds about members and access: `credential_added`, `new_device`,
   `notification_address_changed`, `recovery_used`, `role_granted`, `member_deactivated`,
   `deprovisioned`, `break_glass` and `client_connected`. §3.2 sends those to one member or to
   admins alone, and they are about members and access rather than any agent or account, so
   serving them under the view row would widen what a viewer sees. The control-stream kinds that
   are served (`integrity_incident`, `version_risk_increasing`, `delegation_added`,
   `connection_added`, `went_live`) are ones §3.2 sends to owners, about the agents, accounts and
   streams the view row already shows.
3. **Each alert serves its records, not words.** It serves:
   - `alert_id`, `kind` and `raised_at`, as journaled;
   - `class`, from §3.2;
   - the stream it is on, with the agent or account its id names;
   - the subject's id and the `event_type` of that event on the alert's own stream;
   - `owner_command`.

   No text is served. The client renders the kind from its own closed table (API-10, AGENTS.md
   rule 6).
4. **A member sees only their own deliveries.** `notice` serves the `NoticeIssued` whose `cause` is
   the alert: its `issued_at`, and the asking member's own latest `NoticeAttempted` on each push
   channel, which is the highest notice-stream `seq` among that member's attempts on the channel.
   The member is matched by notifications spec §5.9's recipient: `p_` and the member's ULID in
   lowercase. Web push's several addresses therefore show as one channel. Another member's
   attempts, recipients, addresses and provider message ids are never served, and neither is the
   notice id. `notice` is `null` while no notice names the alert, which covers two cases: the
   dispatcher has not reached it yet, or it is the second alert of one user's kill switch, which
   §3.4 gives a single notice.
5. **The view row.** The read needs `ViewAgents`, the row the approvals inbox already needs (§3.8).
   Every kind it serves is about an agent or an account that row already shows. §3.3's recipient
   rows govern push, not this list.
6. **Fail closed.** A stream the store holds no row for reads as empty. A read the store fails is
   `journal_unavailable`. So is an alert that does not read, names a kind §9.15 does not admit, or
   names a subject its stream does not hold (rule 130). The read never answers with a shorter
   list.

## Consequences

- `schemas/workspace-api/read-models/alerts.schema.json` closes the shape, with examples covering
  every served kind and its class, every delivery status, and each refusal. The schema mutation sweep
  marks three survivors deliberate, each with its reason.
- The route in `mandate-api-server` and the web alerts screen follow in lane EX's next change.
- The nine member and access kinds need their own read, served to the member and the admins §3.2
  names. Until then they reach those members by push alone.
- A per-role narrowing of the pull list, if the founder wants viewers to see only `info` alerts, is
  a new decision; this one serves every member with the view row the same list.
