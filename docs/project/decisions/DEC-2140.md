# DEC-2140: The workspace API's alerts read (`GET /alerts`)

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79 and DEC-176. It serves records the journal already holds, adds no write, and narrows what a member sees, never widens it) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane EX), on the coordinator's assignment |
| **Story or claim** | G5 alerts center over the API (workspace API spec §4.7, E11-9), the web alerts screen for the 2026-10-26 demo; notifications spec §1.3, §3.2, §4.1, §5.9; journal spec §9.15 |

## Context

Workspace API spec §4.7 lists `GET /alerts`, "G5, from `OwnerAlertSent` and the events it names",
with no shape, and nothing serves it, so the web alerts screen shows "not available from your
deployment yet" over the API. The notifications spec makes the web inbox a pull channel whose list
is the journal itself (§1.3, §4.1). Since DEC-2514 every core alert is an `OwnerAlertSent` in its
subject's batch, and since DEC-2516 the cell's dispatcher journals a notice and its attempts for
each.

## Decision

1. **`GET /alerts` returns `read-models/alerts`.** The alerts are the `OwnerAlertSent` events on
   the streams the dispatcher follows (DEC-2516 item 1): the control stream, every agent stream
   `AgentDeployed` names, and every account stream `ConnectionRequested` or `ConnectionEstablished`
   names, in the deployment's environment. They are served most recent first, at most `limit`
   (1 to 200, default 50), with `truncated`. The same streams mean the inbox and the dispatcher
   agree on what an alert is.
2. **Each alert serves its records, not words.** It serves:
   - `alert_id`, `kind` and `raised_at`, as journaled;
   - `class`, from notifications spec §3.2's table (`safety` or `info`; the journal refuses the
     three kinds no alert causes);
   - the stream it is on, with the agent or account its id names;
   - the subject's id and `event_type` from the same stream;
   - `owner_command` for a user's kill switch.

   No text is served. The client renders the kind from its own closed table, so the read can carry
   nothing an alert's records do not hold (API-10, AGENTS.md rule 6).
3. **A member sees only their own deliveries.** `notice` is `null` until a `NoticeIssued` names the
   alert as its `cause`. Then it serves `issued_at` and the asking member's own latest
   `NoticeAttempted` per push channel. The member is matched by the recipient id notifications spec
   §5.9 derives: `p_` and the member's ULID in lowercase. Another member's attempts, recipients,
   addresses, and provider message ids are never served, and neither is the notice id: the read
   needs none of them.
4. **The view row.** The read needs `ViewAgents`, the row the approvals inbox already needs (§3.8).
   Notifications spec §3.3's recipient rows say who is pushed which class. They do not narrow the
   pull list, which is the journal a viewer can already read through the agents and approvals
   reads.
5. **Fail closed.** A read of any of those streams that fails is `journal_unavailable`, never a
   shorter list. A notice stream not yet written is not a failure: every `notice` is `null`.
   `as_of` names every stream read.

## Consequences

- `schemas/workspace-api/read-models/alerts.schema.json` closes the shape, with examples covering
  every kind and its class, every delivery status, and each refusal. The schema mutation sweep
  marks two survivors deliberate, each with its reason.
- The route in `mandate-api-server` and the web alerts screen follow in lane EX's next change.
- A per-role narrowing of the pull list, if the founder wants viewers to see only `info` alerts, is
  a new decision; this one serves every member with the view row the same list.
