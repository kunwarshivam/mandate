# DEC-800: Journal spec v0.23 journals a connection's history and binds an account stream to its connection

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 |
| **Decided by** | Lane L2 builder (`claude-code`), under DEC-79 and DEC-176: every item adds records or rules that only refuse drafts, and none applies to an exit, a protective order, or a kill switch |
| **Story or claim** | E7-17, claim #764 |

## Decision

[Journal spec](../../specs/journal.md) v0.23 adds §9.11, the connection records the
[connections spec](../../specs/connections.md) CN-10 asks for.

1. **`ConnectionEstablished` version 2**: version 1's four members, then `account_ref` (`ulid`),
   `user`, and `step_up` (never `null`). Version 1 stays registered and closed. A writer that has an
   `account_ref` writes version 2.
2. **The binding** (closes DEC-261 item 10). An account stream `acct:{workspace_id}:{account_ref}`
   belongs to the connection whose version-2 establishment names that `account_ref`. One
   `account_ref` belongs to one `connection_id` (CN-5). §9.2's mapping still takes the account
   stream's connection as an argument; its owner now reads it from the binding.
3. **The connecting user and step-up** that DEC-261 item 8 assigned to E7-1 ride in the same
   version. A second version within one story would only add an upcaster; identity spec ID-4
   requires step-up to connect, so the member can never be `null`.
4. **Who writes what.** The control services write `ConnectionRefused` and
   `ConnectionCredentialRotated` on the control stream. The executor writes `ConnectionChecked`,
   `ConnectionStateChanged`, and `ConnectionCredentialRefreshed` on the account stream, each with
   `risk_clock` (DEC-447) and the `connection_id` they act for.
4a. **The connect sequence** (#769's blocker 1, agreed with the L2 S4 builder). The connection
   manager assigns `connection_id` and `account_ref` when the connect starts. The connecting
   executor opens the account stream and journals `ConnectionChecked` (occasion `connect`) there.
   The control services run check 4, then append `ConnectionEstablished` version 2 with that
   check as its `causation_id` (rule 62), having confirmed it is on the bound stream, for the same
   connection, and passed every check. A reconnect (`reconnect`) and a credential replacement
   (`reauthorize`, `ConnectionCredentialRotated`) run the same sequence. A refused connect leaves an
   account stream that is never bound.
5. **A suspended connection recovers by re-authorization, not by reconnect.** Connections spec §9.1
   says a `suspended` connection ends when "the owner reconnects the same account". §3's reconnect
   needs a `ConnectionRevoked` first, and the workspace API refuses a revocation while an agent
   holds positions (§4.5), so that reading would leave a suspended account with positions no way
   back but the compromise path. The reading taken: replacing the credential of a connection that
   is not revoked is `ConnectionCredentialRotated`; a reconnect (second `ConnectionEstablished`) is
   only for a revoked connection. So that this is no loosening, the replacement is held to what a
   reconnect is held to: it names a `reauthorize` `ConnectionChecked` in which every §8.1 check
   passed (rule 62), check 3 shows it reaches the same account by fingerprint, and it keeps the
   connection's `connection_id`, and with it the same `broker`, `environment`, and `account_ref`
   (rule 64 refuses it on a revoked or never-established connection). It does not itself leave
   `suspended`: rule 65 requires a `condition_cleared` that names a passing check, and then the
   owner's acknowledgment lifts the restriction.
6. **The state machine on the account stream.** `active`, `degraded`, `suspended`, with the
   reasons of connections spec §8.2 and §9.1 (and §9.2's vault outage as `lease_expired`).
   `condition_cleared` records that the cause cleared while the state stays; `acknowledged`
   returns to `active`, names the copied `OwnerAcknowledged` as its cause (rule 61), and only
   follows a `condition_cleared` (rule 65); out of `suspended`, that `condition_cleared` names a
   check in which every result passed. A reconnect continues the account stream and its state, and
   one account stream names one `connection_id` for life (rule 65, CN-5).
7. **The halt is never behind these records.** Into `degraded` or `suspended`, the executor
   commits `AccountRestrictionChanged` and `AgentModeApplied` first (CN-6, trading spec §7.3), and
   the check and state records in a later batch. Out of it, the `acknowledged` record is committed
   no later than the batch that lifts the restriction. A refused append of a §9.11 record therefore
   keeps openings halted (`AGENTS.md` rule 3).
8. **Checks 5 and 6 are not journaled here.** `AccountStateObserved` already records the multiplier
   and the account status they read.
9. **Stream rules 63 to 65 are the owner's and §11's, not `append`'s.** `append` folds no stream.
   The connection manager and the executor check them against their own fold before appending, and
   the new per-range check `connection_lifecycle_mismatch` verifies every range. A version-1 first
   establishment has no `account_ref`, so it is never re-established. No rule refuses a
   `ConnectionRevoked`, so the compromised revocation of workspace API §5.6, whose kill switch shares
   its batch, is never held by one.
10. **What the journal cannot see.** The fingerprint is never journaled (connections spec §3.1), so
    that a new connect to an account whose connection was revoked must be a reconnect of that
    connection (CN-12) is the connection manager's to enforce (E7-11, E7-14). Rule 62 makes the
    binding unable to drift once it does.
11. **Vectors.** A generated, additive `connections` section of `journal.yaml`, built by
    `reference/journal/connections.py`: 6 base drafts, 125 invalid and 10 valid drafts, and 25
    stream sequences. 40 validator, 14 stream, and 7 vector mutants are each caught. The vectors
    stay version 3.
12. **Version and numbers.** The journal queue is α's E10-15 changes at v0.19 (#775), v0.20
    (#792, `ConnectionRevoked` version 2 with its `reason`, last rule 74) and v0.21, then L3's
    notice schemas at v0.22 (§9.10). This change is v0.23 and §9.11, and adds nothing to
    `ConnectionRevoked`; the stream rules count a revocation of either version. Its rules are
    numbered provisionally from 54 and renumbered after the last rule before it when it merges
    `main`.
13. **Vault credential events** for the minimal local vault (the L2 lane's V1) are a separate,
    following spec change, so that this one stays reviewable.

## Rationale

CN-10 requires every connection change journaled before it takes effect, and E7-12 and E7-14 wait
on these schemas. Every member traces to the connections spec (§3's fields, §8.1's checks, §8.2's
signals, §9.1's states) or to the identity spec (ID-4's step-up). The rules only refuse drafts,
and the ordering in item 7 keeps a refusal from ever lifting a halt.

## Alternatives considered

- **`account_ref` alone in version 2**, the user and step-up in a version 3 with E7-1: two
  upcasters for one story's records, and a version-2 record E7-1 would supersede at once.
- **Suspended ends by revoke and reconnect**, as §9.1 reads literally: traps positions, since a
  revocation is refused while an agent holds them.
- **Connection state on the control stream**: the executor detects health and owns the account
  stream; a control-stream copy would add a cross-stream writer for a fact only the executor has.
- **Stream rules enforced at `append`**: the journal would have to fold control-stream records it
  otherwise treats as opaque; §11 already verifies cross-record rules (`mode_event_mismatch`).
