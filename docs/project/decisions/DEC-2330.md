## Context

The token-exchange process (`mandate-token-exchange`) checks its settings and then stops: it has
no vault. The exchange itself (`run`: the client secret, the take, the one request, the token
write) is written against `mandate_connections::vault::Vault` and a `ClientSecretSource`, with
nothing in the process implementing either. This decision binds them to the vault.

## Decision

1. **The layer.** `mandate-token-exchange` moves from layer 7 to layer 9, so it can link
   `mandate-vault` (layer 8). It needs `OpenBaoSource` for the Kubernetes login of
   `Identity::TokenExchange(<its connection>)` (DEC-2060), the client-secret read (DEC-2636
   item 2), the take (DEC-2061) and the token write (DEC-821 item 2). Nothing may depend on it,
   as before.
2. **The adapter.** `ExchangeVault` holds one session and its connection. It refuses a session
   that is not that connection's exchange, and every key but that connection's own:
   - the take is the session's single-use `take_code`, and the bytes it returns are read as the
     code entry, format 1 (DEC-2338 item 2), so a code the API did not write that way is
     `code_entry_invalid`;
   - the token is written as the token entry, format 1 (DEC-2624), at `SecretPath::Token`;
   - the client secret is the bytes `vault put alpaca-oauth-client-secret` wrote, one line of
     visible ASCII. Anything else is `vault_unavailable`, before any code is taken;
   - the exchange never writes a code and never deletes anything (the take already spent it), so
     those calls are refused;
   - every vault failure is `vault_unavailable` and names nothing it read.

   Each call runs on the adapter's own current-thread runtime, as the HTTP adapter does.
3. **The command line, exactly `run --vault-address <address> --vault-dir <dir>`.** Lane D1's
   chart pins it, with the binary at `/mandate-token-exchange`:
   - `<address>` is the vault's `https://host:port`;
   - `<dir>` holds `ca.crt`, read by `mandate_vault::mounted::read_mounted_ca` (DEC-2340);
   - the projected ServiceAccount token and the namespace are read from
     `mandate_vault::mounted::SERVICE_ACCOUNT_TOKEN_DIR` (`/run/mandate/vault-token`) at the one
     login.

   The settings in the environment are judged first, as today, and then the arguments; any
   other argument refuses the start.
4. **The subject's account is self-reported.** `MANDATE_SUBJECT_ACCOUNT` is checked against the
   subject only to catch a misconfigured pod early. The binding that holds is the Kubernetes-auth
   login: the vault admits only the one ServiceAccount the connection's exchange role binds,
   whose name the deployment manager's admission policy (D1) pins to the subject. No second
   login gate, debug-only or other, is added.
5. **The proof.**
   - A crate-level chain test runs `run` through `ExchangeVault` over a scripted session and the
     real HTTP adapter against the loopback fixture provider.
   - A spawn test of the binary covers its settings, its arguments, its refusals and their exit
     codes up to the vault login.
   - The end-to-end proof is a cell drill: the real exchange pod against `oauth-fixture` and the
     cell vault exits 0 with the token written. It is backlog row E10-22, which lands with or
     after D1's K1, and it gates the founder's staging connect.

## Rationale

The exchange already says what it needs from a vault; this binds those needs to the one product
that holds the secrets, as the narrowest identity the vault knows. Reading every entry by one
byte form keeps the hand-off between the API, the exchange and the executor a comparison.

## Alternatives considered

- **An AppRole grant from the connection manager** (DEC-821 item 2's first reading). Retired with
  DEC-2060's Kubernetes auth, which needs no secret handed to the pod.
- **A debug-only login gate on `MANDATE_SUBJECT_ACCOUNT`.** It would check nothing the vault's
  login does not, and add a path that exists only in tests.
- **Read the CA by `read_mounted`.** It refuses the 0444 ConfigMap mount the CA arrives as
  (DEC-2340).
