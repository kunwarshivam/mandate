# DEC-369: E7-3's corporate-action tests correction: the expected difference, the applied action, and the reconciliation's cash

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-02 |
| **Decided by** | The stream K builder (`claude-code`) under DEC-79, DEC-77 and DEC-176: each item tightens a test toward the spec or corrects a fixture so the test can check what its title claims |
| **Story or claim** | E7-3 and E7-4 slice 5 (corporate actions), claim [#137](https://github.com/kunwarshivam/mandate/issues/137), umbrella [#174](https://github.com/kunwarshivam/mandate/pull/174) |

## Decision

1. **The pending split explains the expected difference only** (trading-domain spec §8.5, §11).
   §8.5 says reconciliation treats "the expected difference" as `pending_corporate_action`. §11's
   tolerance column names the same exception. `hand::a_pending_corporate_action_difference_is_not_a_mismatch`
   held no position: the model had 0, the broker reported 40, and a 4-for-1 split was pending. Zero
   split four for one is zero, so 40 is not the split's difference. A test that expects it excepted
   would need reconciliation to except any quantity in an instrument while a split is pending. That
   reading hides a real mismatch for as long as the split is pending. The test now holds the 10
   shares its comparison implies, folded before the startup reconciliation as `coverage::holding`
   does, so 40 is exactly the split's difference and the test checks what its title claims.
2. **An applied action names itself** (journal spec §9's catalogue row for `CorporateActionPrepared`
   and `CorporateActionApplied`: instrument, action, ratio or amount, ex-date).
   `coverage::a_split_multiplies_the_position_and_ends_the_pending_action` folded an applied split
   with no `action`. The fold refuses a payload missing a field the journal names (DEC-85), rather
   than inferring a split from a ratio. The test now names `action: split`.
3. **A reconciliation step reports the step's own cash** (DEC-347 item 3's rule, extended to every
   reconciliation step). The harness's `snapshot` for a `reconciliation` or `broker_position_update`
   step took the shared default account, whose cash is not the case's. A case such as RC-04 then
   fails on a cash difference that the case never states, and that would hide whether its position
   tolerance holds. Each snapshot now reports `account_after(step)`, the case's settled cash.

## Rationale

Items 1 and 2 make each test assert what its title claims under the spec's narrower wording.
Item 3 makes the harness meet a case with the account the case describes. None loosens an
assertion: every one of the four tests still fails at its stub on `main`, and each is caught by a
plant in the implementation it waits for.

## Alternatives considered

- **Keep the hand test and except every difference while a split is pending.** That is the looser
  reading, and it hides a real mismatch for the life of the split. Rejected; were it wanted, it
  would be the founder's to decide, not a tests correction's.
- **Let the fold infer `split` from a `ratio`.** That reads a field the journal names as optional,
  and it guesses. Rejected (DEC-85).
