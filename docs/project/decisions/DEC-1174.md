## Context

E2-5 is the live market-data stream on the workspace's own Alpaca connection (PRD FR-2.7). The
data-plane spec asks that the channels each feed carries be checked against the vendor's
documentation before E2-5 starts (§11 question 1). This decision records what the documentation
says and splits the story so that the protocol, which needs no new dependency, lands first.

## Decision

1. **What the vendor documents** (Alpaca, "Real-time Stock Data" and "Streaming Market Data",
   read 2026-10-19):
   - The feeds are `wss://stream.data.alpaca.markets/v2/iex` and `/v2/sip`.
   - Authentication is `{"action":"auth","key":…,"secret":…}` within 10 seconds of connecting. It
     is answered `[{"T":"success","msg":"connected"}]`, then `…"authenticated"`.
   - A subscription is `{"action":"subscribe", "trades":[…], "quotes":[…], "bars":[…],
     "updatedBars":[…], "dailyBars":[…], "statuses":[…], "lulds":[…]}`. It is confirmed by a
     `{"T":"subscription",…}` message listing every channel. Corrections and cancel errors come with
     a trades subscription.
   - The message types are `q`, `t`, `b`, `u`, `d`, `s`, `l`, `c` and `x`, with the fields the page
     lists.
   - The error codes are 400 to 410 and 500. Among them: 402 auth failed, 404 auth timeout,
     405 symbol limit exceeded, 406 connection limit exceeded, 407 slow client, 409 insufficient
     subscription, and 410 invalid subscribe action for this feed.
   - The connection limit per endpoint is often 1.
   - **The documentation does not say whether `iex` carries `statuses` or `lulds`.** It says only
     that status access "depends on your subscription".
2. **Absent until received.** A status or LULD channel is treated as absent until a message of
   that type arrives. Until then, every instrument on the connection has no status after
   resubscription, so §3.2's `resyncing` never ends for it and openings stay blocked (DP-5). Whether
   paper may open without a status channel is DEC-433 item 18, which stays the founder's.
3. **The protocol first, in `mandate-alpaca`.** The protocol module is pure: it builds the
   messages to send and reads each received text frame into typed messages.
   - Prices and sizes are read as raw text through `mandate-num` (ES-23).
   - Times are UTC nanoseconds.
   - A zero-price side is absent (DEC-116).
   - Any message that cannot be read exactly, or of an unknown type, is refused and counted, never
     completed (§3.1).
   - The connection states and the reconnect of §3.2 are the module's next slice, over an injected
     frame transport and clock. Both are tested on recorded frames with no network.
4. **The stream host joins ES-23's compiled-in set as a data host.** `stream.data.alpaca.markets`
   is a market-data host, as `data.alpaca.markets` is. It is kept apart by type from the trading
   host: a stream frame is not an HTTP request, so no trading call can reach it. The sandbox host is
   not compiled in.
5. **The errors that end the stream without a loop.**
   - 402 and 409 mean a rejected credential or plan. They end in a paused connection with an alert,
     never a retry loop (§3.2).
   - 406 means connection limit exceeded. It goes `down` and backs off, since another connection of
     the same key may still hold the one slot.
   - 405 means symbol limit exceeded. It drops the overflow by §3.2's priority, and the owner is
     told.
   - 410 means a channel the feed does not carry. It narrows the subscription to the channels
     every feed carries, dropping statuses and LULD bands, and sends it again. Going down would only
     reconnect and ask again, which takes the quotes down with it. Narrowing happens once: a 410
     with nothing left to narrow, or a subscription with no channel left, pauses with an alert
     (`stream_subscription_invalid`) rather than resubscribing in a loop (#1955's review).
   - An `error` message that cannot be read goes `down`, as an unreadable status or band does
     while subscribed.
   - Every other error goes `down`.
   - A pause, a narrow or an error arriving while the link is already `down` comes from the lost
     socket and changes nothing. A pause opens the gap at the last message received, and the
     `stream_down` alert counts from the first loss of an outage, not from each failed
     reconnect. An outage ends only when the link is `live` again, so a link that resubscribes
     and is lost again before it resyncs is still one outage (#1955's re-review).
6. **Proposed, for the founder: a WebSocket crate.** The transport slice needs a WebSocket client
   over the workspace's rustls (`tokio-tungstenite` with `rustls-tls-webpki-roots` off and the
   process's own rustls config). That is a new row in `docs/dependencies.md`, which the founder
   approves. The protocol and the state machine land without it.

7. **An ES-13 exception for slice 1.** The protocol is one pure module of about 975 lines with
   its tests, over ES-13's 400 for a safety-critical crate. It lands as one PR on the
   coordinator's recorded exception:
   - the tests come first in its history, shown failing at the stub;
   - it has zero missed mutants;
   - the reviewer noted that it would split by message family (control, quotes and trades, bars,
     statuses and bands, corrections) if a later change needs it.

8. **A repeated key in a message keeps its last copy.** The reader takes each message's members
   through `serde_json`, which keeps the last copy of a repeated key; it does not refuse one.
   - Refusing would need a serde visitor whose expecting text no test can observe. That is an
     equivalent mutant, and `.cargo/mutants.toml` exclusions are the founder's.
   - The coordinator judged last-wins on a duplicate key in a broker frame not worth such an
     exclusion (#1908's review).

9. **A quote resyncs its instrument only with both sides.** A quote whose bid or ask is absent
   (zero priced, DEC-116) is read and kept, but it is not the live quote §3.2's `resyncing` waits
   for: the gate's mark needs both sides, so openings stay blocked until a two-sided quote arrives
   (#1955's review). This only tightens.

## Rationale

The documentation leaves the `iex` status question open. The reading that adds no risk is to
count a channel only once it is seen: openings stay blocked, and exits are untouched.

Splitting the protocol from the transport lets the parsing, the refusals and the state machine
be proven on recorded frames now, which E2-5's acceptance asks for. The one founder question, the
dependency, waits until the transport is all that remains.

## Alternatives considered

- **Assume `iex` carries statuses.** Rejected: it would open on an unknown halt state.
- **Write a WebSocket client by hand on `tokio`.** Rejected: a framing and TLS surface of our own
  on a safety-critical path.
- **Read market data by polling the REST latest-quote read (E7-8).** Rejected for the live mark:
  it is DEC-168's read for one decision, not a stream, and it cannot give statuses or LULD bands.
