## Context

DEC-695 items 6 and 7 define `loss_answer_fields` and `proposed_ladder`, but neither they nor §7
give an outcome for some inputs. These are an allocation of 0 or less, a negative answer, and a
drawdown D of 0 or less, or of 1 or more. #1199's review left these open. The merge coordinator made
pinning them a condition of the S1b implementation.

On some of these inputs `reference/mandate/ref.py` drafted, and on others it raised:

- **It drafted for:**
  - a fraction answer of 0.1 of an allocation of 0, or of -10000;
  - a USD answer of -100 of an allocation of -10000, which gives F = 0.01;
  - `proposed_ladder` with D = 1, 1.5, or 2.
- **It raised:**
  - `DivisionByZero` for a USD answer of 100 of an allocation of 0;
  - `InvalidOperation` for a USD answer of 0 of an allocation of 0.

## Decision

1. `loss_answer_fields` never drafts for an allocation of 0 or less, or for a negative answer, given
   as a fraction or in dollars.
2. `proposed_ladder` never drafts for a drawdown D of 0 or less, or of 1 or more.
3. For each of these inputs, either function returns a typed error or `AskAgain`, and never panics.
   Which of the two is left to the implementation.
4. `reference/mandate/ref.py` is aligned with items 1 to 3: both functions return `None`, the
   reference's "ask again", for every one of these inputs instead of drafting or raising.

## Rationale

This records consistency with the schema, not a new reading. The schema already excludes every one
of these inputs:

- `capital.allocation_usd` is `positive_decimal`.
- `capital.max_loss_from_allocation` and `risk.max_drawdown` are `open_fraction`
  (`^0\.[0-9]{0,27}[1-9]$`), which is strictly between 0 and 1.
- V-014 requires `max_loss_from_allocation ≥ max_drawdown`.

A draft for any of these inputs could therefore never be a valid mandate. Refusing it, or asking
again, only refuses what validation would refuse later.

## Alternatives considered

- **Keep `ref.py`'s drafts.** It would propose fields the schema rejects, from an allocation the
  schema rejects.
- **Let the functions raise or panic.** It would turn a caller's mistake into a crash on the
  onboarding path, against `AGENTS.md`'s rule that trading paths return typed errors.
- **Fix one outcome, typed error or `AskAgain`.** Nothing needs it yet. Leaving it to the
  implementation keeps this decision to what the schema already says.

## Consequences

- PR #1216's pending tests pin items 1 to 3 for both functions:
  - `a_loss_answer_without_a_positive_allocation_or_amount_is_never_drafted`;
  - `a_drawdown_outside_zero_to_one_proposes_no_ladder`, which covers D = 0, -0.08, -1, 1, 1.5,
    and 2.
- Item 4 ships in its own PR, on branch `claude/l2-e10-7-ref-dec-901`. ES-22's spec guard refuses
  a change under `reference/` in the same PR as code under `crates/`.
- `reference/mandate/fuzz.py` checks the same inputs against `ref.py`.
- `reference/mandate/mutants.py` seeds two bugs: dropping the allocation guard, and proposing a
  ladder beneath D ≥ 1. The fuzz catches both.
- No reference case or fixture changes: none drafted any of these inputs.
