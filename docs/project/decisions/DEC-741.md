# DEC-741: Read-model response shapes, part 1 (workspace API §4.10)

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The L4 builder, under DEC-79 and DEC-176. It is a reversible engineering reading: it adds no trading rule, removes nothing from the spec, and only narrows what a response may carry |
| **Story or claim** | E11-9, with E10-10's response contract; claim #746; lane L4 slice S0a part 2. It builds on [DEC-740](DEC-740.md) (common value types) and L2's `envelope.schema.json` |

## Decision

1. **Shapes.** The response bodies of these routes are the JSON Schema 2020-12 documents under
   `schemas/workspace-api/read-models/` that workspace API spec §4.10 lists:
   - `GET /health`, `/dashboard`, and `/agents`;
   - `/agents/{id}` and its `positions`, `orders`, and `pnl`.

   Each body is L2's `Envelope` plus its own members. Each has a valid example taken from the web
   app's BTC fixture agent, cases that must be accepted, and cases that must be refused, all run by
   DEC-740's checker.
2. **Closed bodies.**
   - The root is closed with `unevaluatedProperties: false`, so that it composes with the envelope.
   - Every nested object is closed with `additionalProperties: false`.
   - As a result, no account number, key, token, scorecard, or model text outside `QuotedContent`
     can appear (API-11, FR-8.4, API-18). Each of those has a refused case.
3. **Paper is labeled simulated.** Every agent-scoped body and agent summary carries `environment`
   and `simulated`. The schema requires `simulated` to be `true` exactly when `environment` is
   `paper`.
4. **Freshness.** These values carry DEC-740's `Freshness`:
   - a position's mark and broker quantity;
   - the limit state;
   - the P&L's oldest mark;
   - each health component.

   An `ok` health component is never stale.
5. **Order states.** Working orders take only trading-domain spec §5.7's non-final states, and
   `Unknown` is one of them. It is served and shown as unknown and never mapped to another state.
   Finished orders take only the final states.
6. **Conventions** (for L2's drift check):
   - a union is a `oneOf` with a `kind` tag (the fixture's `VersionApplication.result` becomes
     `kind`);
   - a nullable member is `"type": [..., "null"]`, or `oneOf: [{$ref}, {type: "null"}]` for a
     reference;
   - a nullable member is always present (`ActiveRestriction.symbol`), as journal spec §4.2's
     presence rule has it.
7. **Additive members** beyond the fixtures, each named in §4.7 already:
   - `broker_freshness`, `mark_freshness`, `state.freshness`, and `marks_freshness`;
   - `protection.unprotected_since`;
   - `positions_count`;
   - `disclosures`, by document and version.
8. **Client-derived values:**
   - what a restriction blocks and how it lifts;
   - limit headroom;
   - the fixture-only `Workspace.now`, `status`, `scenario`, and `journal`.

   `Agent.mandate` and `Agent.provenance` come from §4.1's version read, whose shape is E10-11's.
9. **Labels.** `label` matches `Agent <n>`, the platform-assigned form (PX-6 (c)), so a mandate's
   name cannot travel in it.

## Rationale

E11-9 moves the web app off fixtures. Fixing the shapes first lets the client's tests be written
against the contract before the projections exist. Using the fixture's own values as examples
shows the screens need no new contract. Closing every body turns the spec's "never" rules into
refused cases rather than review items. Each choice either narrows what a response may carry or
names a value §4.7 already lists. None changes a trading rule, so DEC-176 lets an agent accept it,
and a later schema change can revise it.

## Alternatives considered

- **Open bodies.** These would match §3.2's "clients ignore unknown members", but a secret, a
  scorecard, or model text could ride in an unnamed member. Additive change still works by
  changing the schema.
- **One agent body carrying positions, orders, and P&L,** as the fixture's `Agent` type does.
  §4.7 already gives each its own route, and separate routes let each body carry only the
  watermarks it read.
- **Restriction text from the server.** Serving the closed code keeps the safety enum closed
  (§3.2) and keeps the brief §4.3 wording in one place, the client.
- **A `mandate-version` read model here** for `Agent.mandate` and `Agent.provenance`. §4.1's route
  belongs to E10-11; shaping part of it here would fix members that story has not designed.
