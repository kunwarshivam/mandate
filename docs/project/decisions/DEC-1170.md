## Context

E21-33's acceptance asks that, before its tests, the stream and event that record the deployment
manager's pause be named, with a journal spec change first if the catalogue has none. DEC-994 item
4 left to this lane which journal fact records a restart, since `mandate_process::crash_loop` takes
journaled instants and never the orchestrator's count. The catalogue has neither: no record says a
process was started or restarted, and the only pause records are the owner's (`OwnerCommandIssued`
with `pause`, which names the human who asked) and the runtime's own `AgentModeChanged`.

## Decision

1. **Three new records on the workspace control stream, closed at schema version 1 (journal spec
   v0.48, §9.21, rules 165 to 168):**
   - `ProcessStartIssued`: the manager is about to start one process: `process` (`runtime` or
     `executor`), `subject` (the agent, or the account's `account_ref`), `generation` (1 for the
     slot's first start, one more for each start after it) and `cause` (`deployed`, `restart`, or
     `kill_switch`).
   - `ProcessStopIssued`: the manager is about to stop one running process: `process`, `subject`,
     the `generation` it stops, and `cause` (`agent_stopped`).
   - `ProcessCrashLooped`: the crash-loop bound was reached and the manager stops restarting the
     process: `process`, `subject`, the last `generation`, the `restarts` counted and the
     `window_seconds` they were counted in.

   Workspace control services write them, the control stream's writer (§2), as a `system` actor
   (rule 165). No member is text: an ID, a closed enumeration or an integer, so no record can carry
   an instrument, a quantity, a price or mandate content (`AGENTS.md` rule 6).
2. **A restart is a `ProcessStartIssued` with `cause` `restart`.** The crash-loop bound
   (`mandate_process::crash_loop`, five in ten minutes, design §3.4 Proposed) counts the
   `recorded_at` of those records for the slot, never the orchestrator's restart count, which
   resets when a pod is replaced. A start for a kill switch is not counted: it is never a reason to
   stop starting (item 5). The manager starts every process itself: the orchestrator is told never
   to restart one on its own (in Kubernetes, bare pods with `restartPolicy: Never`), so no restart
   escapes the journal.
3. **The pause is `ProcessCrashLooped`.** After it the manager starts no process for that slot
   except for a kill switch (item 5), and raises one opaque operator alert: the reason code
   `crash_loop` and the runbook RB-14 (design §8.2, OPS-10), no ID and no content. It does not use
   the owner's `pause` command, which names a human who did not ask. The agent is left `Paused` in
   the sense of the HLD lifecycle (`Recovering` → `Paused`): nothing runs for it; protection rests at
   the broker. **What ends it, at this version, is only the agent's `AgentStopped`** (for an
   executor, every agent of its account stopped). That is the conservative reading (`AGENTS.md`
   rule 3): an owner's resume cannot lift it yet, because the runtime does not copy the
   manager's pause into the agent stream, so a restarted runtime would not be paused there and the
   resume's step-up would protect nothing. Lifting it by the owner's resume comes with the runtime
   that copies the pause (lane P3, E21-30), recorded in the backlog.
4. **Journal before every effect, and never two writers.** Each start and stop is appended, and
   only after `Committed` or `AlreadyCommitted` does the manager call the orchestrator; a call that
   fails is retried with the same generation, and a stop or start is never issued unjournaled. A
   slot's next generation is started only once every earlier instance is observed exited or gone;
   while one is running, starting or in an unknown state (a lost node), the manager waits. Each
   process still takes its stream's writer epoch when it starts (journal §5.1, design §3.4), so a
   copy the manager could not see is fenced before it acts.
5. **The manager never gates or delays the kill switch** (design §3.4, §3.6). A kill switch
   (`OwnerCommandIssued` with `kill_switch`) never makes it stop, drain or replace a process, and
   readiness never gates anything: a process that is not ready keeps running and acts on the switch
   itself. A process in the switch's scope that is down (between restarts, or after a crash loop)
   is started at once, without back-off, once per switch, with `cause` `kill_switch` and the
   switch's `OwnerCommandIssued` as its `causation_id`. An agent that is stopped is never started
   again, for a kill switch or anything else. Starting a crash-looped runtime for a switch is safe
   only because a runtime reads the kill switch first and applies it before anything else (ES-06,
   design §3.6): lane P3 (E21-30) keeps that, and the restart drill checks it. A connection switch reads
   its account from the control stream's own version-2 `ConnectionEstablished`, never from a store
   outside the journal, so the switch's path needs nothing design §3.6 does not list; a connection
   the stream never established covers nothing, so a switch never starts a process outside its
   scope. Only a deployment asks the resolver for its account (from the stored mandate): one it
   cannot answer now is deferred, the read position stays before it, and every other row, kill
   switches included, is still folded and acted on, so an outage loses and delays no switch.
6. **What runs.** The desired processes come only from the control stream: a runtime for each
   agent with an `AgentDeployed` and no `AgentStopped`, and an executor for each account with such
   an agent. An `AgentStopped` is final: a later `AgentDeployed` for the same agent starts nothing.
   The manager appends only the three records above, so it never writes a mandate, an envelope, a
   deployment or a command.

7. **One crate, `mandate-deploy-manager`, safety-critical, at layer 4, a workspace service**
   (E21-42's `workspace_services` group). A pure fold and decision (`Manager`) that reads no clock;
   a driver (`Deployer`) that journals before every effect; the orchestrator port with a fake; and
   the Kubernetes adapter. Its `forbidden_internal` list keeps it off the runtime, the executor,
   the connectors, the shell, the CLI, the order builder, the risk gate and `mandate-spec`, so it
   cannot send an order, hold a broker credential or edit a mandate. After a start commits it
   reads the stream again and does not carry the start out if the agent was stopped meanwhile.
   The crash-loop alert is raised when the pause is journaled and again once by each manager
   process that finds the slot still paused, so a restart between the record and the alert loses
   no alert; de-duplicating is the alert path's (DEC-988 item 6). A generation the orchestrator
   does not list is retried unjournaled only by the manager process that journaled it and saw its
   start fail; after a restart it counts as exited, so its successor is journaled and counted, and
   a crash-looped process is never brought back by a replay. Each record's `event_id` is
   derived from the stream, the record, the slot and the generation, so a retried draft, or a second
   manager's draft of the same step, is the same event and the journal commits it once.
8. **The Kubernetes adapter is plain HTTPS to the API server through the existing `reqwest` and
   `rustls`** (D-3's second option; no new crate, so no `docs/dependencies.md` row). It reads the
   service account's token and CA from their mounted files, trusts that CA only, follows no
   redirect and uses no proxy. Each instance is a bare pod named by the slot and generation, from
   the chart's pod template for its process, with `restartPolicy: Never`, the manager's labels,
   and the process's workspace, subject and generation in its environment (none is a secret). A
   pod being deleted, or in phase `Unknown`, counts as possibly running. A pod of the manager's
   that cannot be read makes the whole list unavailable, so nothing is decided while an instance
   might be hidden.
9. **What this first slice leaves to the next.** The process binary (the loop, its probes over
   `mandate-process`, the Postgres journal port and the resolver over the stored mandate
   documents), the chart's templates, RBAC and the manager's Deployment, the Compose adapter, and
   the k3d drill through `cargo xtask cell drill`, once lane C adds the restart drill. Lifting a
   crash-loop pause by the owner's resume waits on the runtime copying the pause (item 3). Also
   left, and recorded in the backlog: an alert for an instance stuck `Pending` or `Unknown` (the
   manager waits, never starting beside it), deleting exited pods (the cluster's garbage collection
   does today), and a check that the chart's pod templates mount no service-account token.
10. **Proposed, for the founder: one PR, over ES-13's line limit.** The crate's `src/` is about
    1,400 lines with its doc comments, the fake orchestrator included, over ES-13's 400 for a safety-critical crate. Every other gate
    is kept: tests first, independent review on a different model, every mutant on the diff
    killed, CI green. If the founder prefers, the Kubernetes adapter splits out as a stacked PR.

## Rationale

The journal is the only record that survives a pod's replacement and the only channel between
workspace services and agent processes (DEC-986). Writing the start before the orchestrator call
is rule 5's write-before-acting for the manager's own effects, and it gives the crash-loop bound
its input with no new reader. Leaving a crash-looped process down until its agent is stopped can
cost an owner a deployment, but it can never add risk; the kill-switch exemption keeps rule 13 and
design §3.6 whole while it lasts.

## Alternatives considered

- **Record the pause as an owner `pause` command from a `system` actor.** The runtime would copy it
  without change, but the record names a user who never asked, and the audit trail would say the
  owner paused the agent.
- **Count restarts from the orchestrator** (the pod's `restartCount`). Rejected by DEC-994 item 4:
  it resets with the pod.
- **Count restarts from each process's writer epochs.** A process that crashes before it takes its
  epoch would leave no trace, which is exactly the crash loop of a bad release.
- **Let the owner's resume lift the crash-loop pause now.** Not taken, for the reason in item 3.
