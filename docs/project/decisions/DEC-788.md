# DEC-788: `VerificationRun` version 2, the verification's id, and the order of `POST /verifications`'s refusals

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | An agent (Claude Code, lane L5's spec author) under DEC-79 and DEC-176: each item records more or refuses more than the specs said, and adds no risk |
| **Story or claim** | E12-3 ([#748](https://github.com/kunwarshivam/mandate/issues/748)); journal spec v0.36 §9.13; workspace API spec §4.8.1 |

## Context

`GET /verifications/{id}` must return a result holding `trusted_start` and `checked`, but journal
spec §9.13's `VerificationRun` version 1 records neither, so the API could not rebuild its own
result from the journal. The spec did not say what `verification_id` is, whether `phase` can be
`running`, or in which order the route's refusals come.

## Decision

1. **`VerificationRun` version 2.** Each range adds:
   - `start: {kind: genesis | manifest | anchor, manifest_hash: digest?, anchor_event_id: ulid?}`,
     the member matching `kind` non-null and the other `null`;
   - `checked: integer`;
   - `incomplete` ([DEC-789](DEC-789.md)).

   Rule 132 checks, per range: the start names exactly its own record; `genesis` has `from_seq` 1
   (and so, by rule 107, a `prev_hash` of 64 zeros); `anchor` has `from_seq` at least 2;
   `checked ≤ to_seq − from_seq + 1` (§4.4 keeps it from 0); `checked = to_seq − from_seq + 1`
   when `failure` is null; a failed range records no incomplete check; and, while the token cannot
   be proven, an anchor start's range never passes. Rule 133 is the three-way result (DEC-789).
   These are new rule numbers after rule 131, because rule 111 judges both versions and its
   number is cited by version 1's tests; no rule is renumbered.

   **A new version, not an edit of version 1.** §8 and the changelog's settled reading (v0.13,
   v0.34) are that a closed schema is never edited in place: a member joins at a new version.
   Nothing appends version 1 today, but `mandate-journal` registers it, its tests pin it, and an
   edit in place would turn them red in a spec-only change. Version 1 stays registered and
   replays; every writer appends version 2. The anchor-start-never-passes clause, which encodes
   DEC-789's state, goes with the change that lets the token check answer.
2. **The verification's id is its `VerificationRun`'s `event_id`,** derived from the
   `Idempotency-Key` as workspace API §3.4 derives every event id, as an export's id is its
   `ExportCreated`'s.
3. **`phase` is always `recorded` in v1.** A run is synchronous within the 1,000,000-event bound,
   so the response comes after the record; `running` is reserved for an asynchronous run and never
   sent.
4. **The order of refusals:** role 403; the members that are not ids, 422; the idempotent replay
   (the recorded result, or 409 `idempotency_conflict`); `stream_id`, 404; then `range`,
   `trusted_start`, and the size bound, each 422 (the size bound with violation `range`). None
   records anything. **A replay returns the stored result and never runs again**, so a head that
   has moved since cannot change it.
5. **`GET /verifications/{id}` serves only a version-2 `VerificationRun` with `trigger` `request`**
   of the path's workspace; any other id is the 404.

## Rationale

A result the API cannot rebuild from the journal is a result served from memory, which AU-6 and
the journal-first rule forbid. Recording the start's record rather than a copy of the request lets
a reader re-resolve it. The refusal order follows §4.8.1's own pattern (role, then non-id members,
then ids) so a refusal leaks nothing about an id before the caller is allowed to ask; putting the
replay before the stream lookup keeps a retry from depending on state that moved.

## Alternatives considered

- **Amend version 1 in place.** Rejected: §8, and it breaks `main` in a spec-only change.
- **Fold the new clauses into rule 111.** Rejected: rule 111 judges both versions; separate
  numbers let version 1's tests keep citing it unchanged.
- **Return `running` and poll.** Rejected: there is no asynchronous run in v1 to report.
