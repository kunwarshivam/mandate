# DEC-2144: The workspace API serves the owner's acknowledgment of a hold, and lists the holds to acknowledge

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | `claude-code` (lane GL), paired with lane WB: a reversible engineering decision under DEC-79; no founder-reserved choice is touched |
| **Story or claim** | E10-12; workspace API spec §3.11 item 12, §3.5, §4.2, §5.5; journal spec §9.28 (DEC-2509, DEC-2824, DEC-2830, [DEC-2523](DEC-2523.md)); lane WB's acknowledgment screen; lane L1's CLI acknowledgment (E7-4b) |

## Context

Journal spec §9.28 defines `OwnerAcknowledged` and `OwnerAcknowledgmentRequested` version 2, with a
`subject` of `limit`, `restriction`, or `reconciliation`, and the executor's four checks that judge them.
Only the CLI could write them. Lane WB's screen needs the same records from a browser, and a read of the
holds there are to acknowledge. DEC-2523 (journal spec v0.106) made `passkey` step-up valid for an
acknowledgment in every environment, so the executor can accept what a browser sends.

An acknowledgment adds risk back: it lifts a latched limit, or with `AgentModeApplied` a reconciliation
hold. So it must never be easier from the API than from the CLI, and a refusal must commit nothing.

## Decision

1. **Routes.** `POST /agents/{agent_id}/acknowledgments` commits `OwnerAcknowledged` version 2, and
   `POST /agents/{agent_id}/acknowledgment-requests` commits `OwnerAcknowledgmentRequested` version 2,
   each with the verified `step_up` and then `StepUpAsserted` in one batch (DEC-2140). The records'
   members are §9.28's: the users come from the authenticated principal, never the body (API-6), and
   `requested_by`, `independent_required`, `submitted_at`, and `risk_clock` are set as §9.28 and the CLI
   set them. The API writes version 2 with `subject` always; the CLI writes version 2 with
   `--subject` since #2739, and version 1, read as `limit`, without it. A named request matches only
   when its `subject` equals the acknowledgment's, a version 1 request read as `limit`, the reading
   lane L1 takes for the CLI ([DEC-2838](DEC-2838.md)).
2. **Checks, first failure wins, nothing committed** (workspace API spec §3.11 item 12): strict decode;
   the `Acknowledge` role, users only; the agent deployed here; `paper` only, else `live_unavailable`; the
   hold served by the list now with this `subject`, else `409` `acknowledgment_unavailable`; a named
   request unspent, matching, and not the caller's, else `409` `acknowledgment_request_invalid`; and
   `passkey` step-up with its assertion, judged by the port. The executor judges every acknowledgment
   again by §9.28's four checks; the API's checks only keep out what it would refuse.
3. **Unverified step-up is refused, not recorded.** Unlike a resume, which reduces nothing and so may
   wait, an acknowledgment only lifts a hold: refusing it never delays risk reduction, and it spends no
   challenge. A `null` step-up is `step_up_required`; another method, `cli_confirm` in `paper`
   included, is `step_up_method`: the API accepts passkey only, and `cli_confirm` stays the CLI's.
4. **Live stays the CLI's.** The API refuses a live workspace with `live_unavailable`, as it does a
   grant. The founder's live acknowledgment, by `cli_confirm` on the founder's own connection (DEC-529
   item 3, DEC-923), is unchanged.
5. **The digest** is DEC-279 item 1's canonical object, as a resume's, with `confirms` `acknowledge` or
   `request_ack`, `event`, `subject`, and, only when named, `request`. `control_head` binds the control
   stream's head, so a stream that moved answers `step_up_mismatch`. Three worked vectors are in the spec.
6. **The list.** `GET /acknowledgments?state=open[&agent=]` serves each standing hold with `event`,
   `subject`, the `agent_id` to post to, `account`, `reason`, `mode`, `raised_at`,
   `independent_required` (`null` until the server reads the policy), and the unspent `request`. An
   unreadable account stream fails the read `journal_unavailable` rather than serve a short list.
7. **Status.** `GET /commands/{key}` gains a planned phase `accepted`, for a restriction acknowledgment
   that the executor accepts and that lifts nothing by itself; `applied` includes `RiskLimitLifted` and
   the lifting `AgentModeApplied`. The two refusal codes and `accepted` are `x-planned` E10-12 until the
   server serves them.
8. **Order (ES-22, DEC-2643).** The request type gains its optional members first, in its own pull
   request, checked with `members_ahead` (DEC-2126, DEC-2128); this spec and its schemas follow, with
   test-only exceptions for the server's not-yet-written request decoder; the server, the list, and the
   codes come last and remove the exceptions.

9. **Residual: two acknowledgments of one request at once.** The record is appended at the head it
   finds, as a resume's is, not pinned to the head its checks read. Two acknowledgments naming one
   request, under different keys and challenges bound to the same head, can both pass check 6 and
   both commit. Rule 241 then holds at the executor, not the writer: it refuses the second
   `request_invalid` and lifts nothing more. Pinning would answer the loser `outcome_unknown`, which
   says less than the executor's refusal; it is revisited if a writer-side refusal is wanted.

## Rationale

The API writes nothing the CLI could not, and its checks are a subset of the executor's, so the route
adds a channel without adding a way past §9.28. Refusing unverified step-up rather than recording it
costs nothing for safety, since only risk-adding actions pass here, and keeps a refused acknowledgment
out of the journal. Paper only keeps the live path where DEC-529 put it.

## Alternatives considered

- **Record unverified evidence and let the executor refuse it, as a resume does.** Refused: the resume
  records because it must not lose an owner's intent to restart; an acknowledgment loses nothing by
  being asked again, and a journaled refusal is only noise.
- **Serve live too, by passkey.** Not now: DEC-2523 lets the executor accept it, but serving live from
  the API is the founder's (DEC-79, live money). The CLI path stands.
- **Let the client compute `independent_required`.** Refused: the client cannot read the policy, and a
  wrong `false` would hide the request route; `null` makes it ask and show the executor's answer.
