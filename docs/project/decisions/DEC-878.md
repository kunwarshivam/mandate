# DEC-878: Reconciliation finds a filled bracket's legs under their entry, because Alpaca names each leg itself

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-10 (UTC) |
| **Decided by** | the agent, under DEC-176: it resolves a gap between trading-domain spec §2.3 and §11 and the broker by the reading that adds no risk, and weakens no safety invariant or non-negotiable |
| **Story or claim** | E7-4, the slice that reconciles protective legs (backlog); first paper trade FT-11 and E2; the finding in #1245 |

## Context

Once a bracket entry fills completely, the executor records its legs `placed` under the platform's
name for them, `{entry}-p{record}` (§2.3, §5.4, DEC-346 item 4), and that name joins the order set
as a live protective sell (DEC-160 item 3). Reconciliation's step 1 (§11) then matches every live
order to the broker's open orders by `client_order_id`. No broker order carries that name:

- A bracket is one Alpaca order. Its parent is the entry, under the entry's own `client_order_id`,
  and the POST that creates it has no field for a leg's id.
- Alpaca names each leg with its own `client_order_id`, a UUID. The recorded
  `submit_bracket_accepted` scenario shows it: legs `86942a5e-…` and `94969c96-…` under the parent
  `md-daea915c1fc0042bcc19a4caed`. §2.3's `…-tp` and `…-sl` name no order Alpaca holds, and the
  hand-built `submit_oco_accepted` scenario, which gives its legs those names, is not what Alpaca
  returns.

So every reconciliation after a complete fill adopted the placement `Unknown`, wrote a
`CompensatingEvent` for it, and asked the broker for it by a name that always answers 404. An
`Unknown` order in the instrument then held every exit there (`unknown_order_in_flight`): a risk
exit right after the fill was journaled `hold`. That breaks FT-11 in the founder's paper run (E2),
and it holds exits on a false doubt, which `AGENTS.md` rule 13 allows only for a real one.

## Decision

1. **The placement's name is the platform's handle, never a broker id.** A filled bracket's
   `{entry}-p{record}` names the pair of legs Alpaca created. It is compared with no broker
   `client_order_id`, and nothing derives a leg's broker id from it.
2. **Step 1 finds such a placement through its entry.** A live protective order that no
   `OrderSubmitted` recorded, whose id names an entry (§2.3, everything before the last `-p`) that
   was sent as a bracket, is present when the snapshot lists an open order whose `client_order_id`
   is that entry with at least one leg nested under it that is a **sell** and whose status §5.7's
   table maps to a live state (`Becomes` a non-terminal state, or `accepted` flagged restricted).
   Present, it keeps its own state: nothing is adopted, no `CompensatingEvent` is written, and no
   lookup is asked.
3. **The leg's own `client_order_id` is never compared**, whatever it holds. The broker names it.
4. **Legs nested under one of our orders are never external activity.** A top-level order whose
   `client_order_id` is not ours still is (§7.1): if Alpaca lists a filled bracket's legs at the
   top level rather than nested under the entry, every agent on the account goes `exits_only`
   rather than the platform guessing an owner. That fails closed. E2 records the open-orders read
   after its fill to settle which shape Alpaca sends.
5. **Anything else is unchanged.** With the entry not listed, listed with no legs, with every leg
   done, or with only buying legs, the placement is adopted `Unknown` with its `CompensatingEvent`
   and asked after, as §11 adopts any order the broker does not list (rule 3).
6. **Rule 13.** A reconciliation that finds the legs under their entry leaves no order in doubt, so
   it holds no exit: a risk exit right after it passes the gate, and its sequence starts by
   cancelling the placement (§5.4).
7. **`BrokerOrder.legs` holds each leg whole** (`Vec<BrokerOrder>`: side, prices, status, and the
   broker's `client_order_id`), read from the nested open-orders answer. This is the type change
   the backlog's leg-reconciliation slice named; its own tests correction rides with it (the
   executor tests' `ready()` and the Alpaca hostile-leg-id test now build whole legs).
8. **Three behaviour-only rows.** The pending tests reach no stub: step 1 is implemented and adopts
   the placement, so they fail on that adoption. A stub on step 1 would make every reconciliation
   that meets a filled bracket refuse on `main`, which would stop the paper path rather than pin
   it. So, as DEC-260 (19) and DEC-532 did, this decision adds three rows to
   `xtask/behaviour-only/` for E7-4, an exception to DEC-160 item 2's shrink-only rule. The code
   PR deletes each with its test's `#[ignore]` line.

## Rationale

Nothing here keeps an order the broker does not show live: a placement is kept only on a live
sell leg the broker nests under that very entry, which is the broker's own statement that the
protection rests. It adds no order, no quantity and no owner, and it never reads a leg id. It
removes a false `Unknown` that held exits and asked for a name that cannot be found. Where the
evidence is missing, the old fail-safe path stands. That is the reading that adds no risk, so
DEC-176 lets an agent take it; nothing in it loosens a rule.

## Not decided here (backlog)

- **The cancel of a bracket's placement at Alpaca.** `BrokerRequest::Cancel` names the placement,
  and the connector cancels by looking the order up by that `client_order_id`, which answers 404 for
  `{entry}-p{record}`. The exit sequence's first step therefore cannot be confirmed at Alpaca. The
  connector has to resolve such a cancel through the entry's legs (cancelling a bracket leg at
  Alpaca cancels its sibling). E2 places one share and exits nothing inside the run, so it does not
  block E2, but it must land before any exit runs against a filled bracket.
- **The in-doubt lookup** (item 5) still asks by `{entry}-p{record}`, which Alpaca answers 404. Asking
  by the entry's id and reading its nested legs would settle the doubt; until then the placement
  stays `Unknown`, which is safe.
- **The OCO.** An OCO's parent carries our `{entry}-p{record}` and is found by it. Its stop leg is
  nested under it with a broker-named id, so it needs no change. The hand-built
  `submit_oco_accepted` scenario's leg ids should be made Alpaca's.

## Alternatives considered

- **Keep each leg's `client_order_id` and match it to `…-tp` and `…-sl`**, as the backlog item
  planned. Alpaca never gives a leg one of our ids (the recording), so this would never match.
  Planted bug B5 in the tests PR is exactly this and is caught.
- **Treat the placement as present while the entry is listed at all.** That would keep protection
  that the broker has already cancelled or filled. Refused: only a live sell leg counts.
- **Leave the adoption and stop `Unknown` protective orders from holding exits.** That would loosen
  rule 13's hold on a real doubt. Refused.
