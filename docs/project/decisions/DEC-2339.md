# DEC-2339: a connection's broker account id is kept in the personal-data vault at its own entry, which the executor creates once and never reads

| **Status** | Accepted |
| **Date** | 2026-10-22 (UTC) |
| **Decided by** | an agent (Claude Code, lane V2), under DEC-79, at the coordinator's direction; it gives one process one create on one entry of its own connection, and no read |
| **Story or claim** | E21-32, claim [#1442](https://github.com/kunwarshivam/mandate/issues/1442); E10-13 (the exchanged executor's connect check); connections spec §5.2 step 4, §3.1; journal spec §3, §6.4, §9.8 rule 62; E5-5 |

## Context

On a connect, the executor "stores the broker's account id in the personal-data vault and records
only that reference (`account_pii_ref`, §6.4), never the id" (journal spec §9.8; connections spec
§5.2 step 4). A reference is a random id, never a hash of the value (journal spec §3). The control
side then has the vault compute the account's fingerprint from that reference (connections spec
§3.1). No personal-data vault existed in code: no path, no policy, no writer. The account id must
outlive the connection: it stays until its retention ends, and is erased only then, with no legal
hold, journaled as `PersonalDataErased` (connections spec §5.2 step 6; journal spec §6.4).

## Decision

1. **The entry.** A connection's broker account id is kept at `personal/accounts/x<hex>`, under the
   KV mount, `x<hex>` being the connection's segment (DEC-2060 item 3)
   (`SecretPath::AccountId`). It holds the account id and the reference `pii_<ULID>` the executor
   mints for it, at random, when it creates the entry.
2. **Create once, never read.** The connection's executor may create that one entry, and only when
   it is not there (`Access::Create`): it can neither read it, overwrite it, nor delete it, and no
   other connection's entry. Its templated Kubernetes policy gains `create` on
   `personal/accounts/x{its own name}` alone. The create is a check-and-set write at version 0, so
   a second create is refused even where a policy allowed update.
3. **Who reads.** The account fingerprint is the vault's keyed hash of the entry's account id, as
   connections spec §3.1 says: the key never leaves the vault, and the connection manager (the
   API, lane X) asks the vault to compute the hash and receives only the result, never the account
   id. The manager checks that the hash was computed over the entry whose reference is the
   `account_pii_ref` of the connection's `ConnectionChecked`. The hash operation and the
   fingerprint registry are F3's, under their own decision; until it lands, the manager's read of
   the entry is the interim, and F3 replaces it with the hash alone.
4. **Retention, not revoke.** The entry is outside `connections/`, and no identity may delete it,
   so revoking a connection, which deletes its code and token, leaves it, and a test pins that. Its
   erasure at retention end, journaled as `PersonalDataErased`, is a follow-up (E5-5).
5. **An unreadable account** creates no entry, and its `ConnectionChecked` carries a null
   `account_pii_ref` (journal spec rule 62).
6. **A refused create fails closed.** Create-once with no read is not idempotent: an executor that
   created the entry and crashed before journaling its reference finds its retry's create
   `Denied`, and cannot read back what is there. A `Denied` create is therefore treated as an
   unreadable account: `ConnectionChecked` carries a null `account_pii_ref` (rule 62), the API
   refuses the connect, and step 6 tears it down by its deadline. The owner reconnects, and a new
   connect has a new connection id and so a new entry. The executor is never given `read` to
   recover the old one. E1b's connect check implements this, with a crash-then-retry test.

## Residuals, disclosed

- **Per-person keys are not met yet.** Journal spec §6.4 keeps personal data "under per-person
  keys". This entry is encrypted only under the vault's own barrier key, like every KV entry, not
  under a key of the connecting person's. Encrypting it under the connecting user's key, the `user`
  of `ConnectionRequested`, is E5-5's work, which already names the per-person key; until then this
  is the interim reading, and erasure means deleting the entry, not destroying a key.
- A compromised executor could create its own connection's entry with a wrong account id before a
  correct one. The control side compares the fingerprint with the connection's record (check 3), so
  a wrong id refuses the connect; it never establishes it.

## Rationale

The connection's own segment makes the policy one templated block, keyed by the executor's own
name, so it can write no other connection's entry; a separate `personal/` prefix keeps the entry
out of every path the revoke deletes, which is the retention the specs ask for.

## Alternatives considered

- **The entry under `connections/x<hex>/`.** Rejected: it sits beside the code and token that a
  revoke deletes, so a later change to the revoke could sweep it.
- **One shared `personal/` path keyed by the reference.** Rejected: an executor's policy could then
  not be limited to its own connection, since the reference is not its name.
- **The reference handed to the executor.** Rejected: the specs have the executor store the id and
  record the reference it gets for it.
