# DEC-920: The live run's grant wait releases only on the runtime's admitted, re-validated grant

| | |
|---|---|

| **Date** | 2026-10-16 (UTC) |
| **Decided by** | An agent (Claude Code, the grant-wait admission builder), under DEC-79 and DEC-176 |
| **Story or claim** | E7-26; [#1336](https://github.com/kunwarshivam/mandate/issues/1336); DEC-912 item 1; DEC-914 item 2; mandate spec §6.4; journal spec §3, §9.7 (rules 46 to 53); workspace API spec API-12 |

DEC-912 item 1 says the runner's grant wait releases the `ask` opening's submit on the first
answer naming the ask's approval, and that "Admission — mandate spec §6.4's checks 1 to 7 and
re-validation — stays the runtime's". As merged, `grant()` and `answers()` in `mandate-paper`
released on a raw control-stream `ApprovalResponseSubmitted` matched by approval, content hash and
verdict alone: the record mapping dropped the envelope's actor, so no check — the actor a `user`
in the approver set (check 3) among them — tied the release to the runtime's admission. Nothing
live called the wait yet. The journal names no `ApprovalGranted`; the runtime's record of an
answer is `ApprovalResponded` (result `admitted`, `counted` or `refused`) and of its re-validation
`ApprovalRevalidated` (`act` or `skip`), both on the agent stream. These are the readings the wait
now takes.

## Decision

1. **The release is the runtime's admitted, re-validated grant.** An `approved` answer repeating
   the ask's content hash is never a release by itself. The wait reads the runtime's own records
   on the agent stream the run appends to: the answer's copy is the `ApprovalResponded` whose
   `causation_id` is the answer's event id (journal spec §9.7 rule 50); its re-validation is the
   `ApprovalRevalidated` whose `causation_id` is the copy's event id (the workspace API spec's
   trace, `ApprovalRevalidated` → `ApprovalResponded` → `ApprovalResponseSubmitted`). The submit is
   released only when the copy is `admitted` and the re-validation is `act`, and the run's clock is
   still before the ask's deadline. With no copy yet, or an admitted copy with no re-validation
   yet, the wait holds, and the timeout denies at the deadline. A `refused` or `counted` copy is
   not terminal (mandate spec §6.4's lifecycle), so the fold reads on to the ask's next answer;
   a re-validation `skip` denies. The runner re-implements none of checks 1 to 12 (DEC-912's
   rejected alternative of two admissions): what it adds is only the binding of the release to
   the answer that repeated the ask's hash (LT-4), so the runtime stays the single source of
   admission truth and API-12's "only the runtime's `ApprovalResponded` and `ApprovalRevalidated`
   say what happened" holds for the runner too. The wait re-reads both streams on every wake.
2. **A deny stays a deny.** A `skipped` answer repeating the ask's hash denies whenever it is
   read, whatever the runtime made of it, and an answer repeating another content hash, or one
   the run cannot read, still refuses as a difference whatever its admission (DEC-912 item 1).
   Ending the run on an answer the runtime may refuse sends nothing; the approval stays pending on
   the journal for the runtime's own fold.
3. **A runtime record the wait cannot read refuses.** A copy of the answer naming another approval
   or another verdict, a copy whose result is none of the three, a re-validation naming another
   approval, and one whose result is neither `act` nor `skip` each refuse as a difference
   (`AGENTS.md` rule 3). A `causation_id` that is absent, `null` or not text links nothing, so it
   can only hold the wait.
4. **An unreadable row refuses only where the fold reads it.** The row's own `event_type` column
   scopes the refusal: a row of a type the fold reads (`ApprovalResponseSubmitted` on the control
   stream, `ApprovalResponded` and `ApprovalRevalidated` on the agent stream) whose body cannot be
   read could be this ask's, so it refuses as a difference with nothing sent; a row of any other
   type is handed in its place with a `null` payload and no `causation_id`, because the fold reads
   nothing of it. One malformed unrelated row no longer refuses every ask behind it. The rows are
   still handed verbatim, in journal order, never filtered (DEC-914 item 2).

## Rationale

The wait existed to hold the one live order until the founder's grant; a raw answer is the owner's
input, not a grant, until the runtime has judged it (mandate spec §6.4: "An answer reaches the
runtime only as an `ApprovalResponseSubmitted`"). Reading the runtime's own records keeps one
admission and cannot drift from it; the second check the runner keeps, the hash the answer
repeated, is LT-4's own sentence. Requiring the re-validation as well as the admission is the
stricter reading of "admission ... and re-validation stay the runtime's": an admitted grant that
re-validation skips sends nothing in the runtime, and now sends nothing in the runner either.
Every reading only holds, denies or refuses where the merged seam released.

## Alternatives considered

- **Check the actor kind and approver membership in the runner.** Rejected: it duplicates check 3
  beside the runtime's, needs the bound mandate's approver set in the runner, and still leaves
  checks 1, 2 and 4 to 12 unread — two admissions to drift, the alternative DEC-912 rejected.
- **Release on the admitted `ApprovalResponded` alone.** Rejected: re-validation can still skip
  an admitted grant (checks 8 to 12), and API-12 reports a grant as acting only on `act`.
- **Let a non-approver's skip or differing hash be ignored rather than end the run.** Rejected for
  now: ending the run sends nothing and leaves the approval pending, so it adds no risk; a wait
  that kept running would rest on a read DEC-912 already chose to refuse.
- **Keep refusing on any unreadable row.** Rejected: a row of a type the fold never reads cannot
  release or deny the ask, and refusing on it let one unrelated malformed row end every live run.
