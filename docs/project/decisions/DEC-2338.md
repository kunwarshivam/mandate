## Context

The callback (DEC-2626) hands a redeemed code and its verifier to the API's `CodeVault` port, but
the API process binds no port at all, so no deployment offers a connect. Three things were open:
what bytes the code entry holds, so the API's write and the token exchange's take (DEC-2061) read
them the same way; how the API reaches the vault, a crate two layers above it; and what the
binary reads to bind a connect.

## Decision

1. **`mandate-api-server` moves from layer 7 to layer 9**, so it can link `mandate-vault` (layer
   8). Its `forbidden_internal` list stays as it is: `mandate-vault` and everything it links
   (`mandate-connections`, `mandate-time`, `mandate-vault-local`) are outside it. Only
   `mandate-stub-issuer`, a `tool` crate, depends on the API server, so no layer above it moves.
2. **The code entry, format 1.** Exactly the canonical JSON (journal spec §4)
   `{"code":"<code>","format":1,"verifier":"<verifier>"}` at `connections/x<hex>/code`:
   - `code`: Alpaca's code as the callback admitted it, 1 to 512 bytes from `!` to `~`, none of
     them `"` or `\`, so it needs no escape and the entry has one byte form. The callback admits
     those two bytes (DEC-2626 item 2.4); a code holding either cannot be written, so the write
     fails, nothing starts, and the deadline's teardown closes the request;
   - `format`: the integer `1`; a later shape is format 2, never an optional member;
   - `verifier`: the PKCE verifier, 43 to 128 bytes of RFC 7636's unreserved characters
     (`A`-`Z`, `a`-`z`, `0`-`9`, `-`, `.`, `_`, `~`).

   `mandate_connections::code_entry::encode` writes it and refuses anything outside the form;
   `decode` reads it and refuses any other bytes as `code_entry_invalid`, which names nothing of
   them. Decoding compares the bytes with the form around the two values, so nothing else is
   copied out, and those only into `SecretString`s (OPS-1). The API is the only writer; the token
   exchange is the only reader (5b-3b-2, DEC-2330).
3. **The API's vault port.** `VaultCodes` implements `CodeVault`:
   1. A binding for a live connection is refused as `environment_refused` before anything is
      read: Alpaca OAuth is paper only (DEC-821), so no live code is ever written.
   2. The code and verifier are encoded (item 2) before any login.
   3. Each write logs in afresh as `Identity::Api` with the AppRole role id and secret id read
      from the mounted files `api.role-id` and `api.secret-id`
      (`mandate_vault::mounted::read_mounted_credentials`), never from the environment or argv.
      A connect is rare, so no session is held between writes, and nothing is left to renew.
   4. A session that is not `Identity::Api` writes nothing.
   5. The one call is `put` at `SecretPath::Code(<connection>)`. The port calls nothing else.
   6. Every failure is `vault_unavailable`, with no detail (API-11).

   The write runs on its own current-thread runtime, and the callback calls the port through
   `tokio::task::spawn_blocking`, so a slow vault holds one blocking thread, never the server's
   runtime. The session's token is not revoked after the write: `mandate-vault` exposes no revoke
   for an AppRole login, and the token can only write codes and delete entries, so it lapses with
   the `api` role's token TTL.
4. **Nothing in the API can read a token.** The vault's policy table (`mandate_vault::policy::allows`)
   gives `Identity::Api` writing codes and deleting codes and tokens, nothing else; a test pins
   every access to every path kind for it. The port's own test pins that its session sees one
   `put` and no other call.
5. **The binding (the next pair of this slice).** `connect` is bound only when
   `MANDATE_ALPACA_CLIENT_ID`, `MANDATE_ALPACA_REDIRECT_URI`, `MANDATE_API_VAULT_ADDRESS` and
   `MANDATE_API_VAULT_DIR` are all set and valid, and the authorize page passes DEC-2633 item 3's
   gate. The vault directory holds `ca.crt` and the two AppRole files, each readable by the
   process alone, because `mandate_vault::mounted::read_mounted` refuses any group or other bit.
   Lane D1's chart ([#2227](https://github.com/kunwarshivam/mandate/pull/2227), which depends on
   this decision) projects the `vault-approle-api` Secret, as `api.role-id` and `api.secret-id`,
   and `vault-ca`'s `ca.crt` at 0440. An init container copies them at 0600 into a Memory
   `emptyDir`, which the api mounts read-only as that directory. D1 also opens the api pod's
   egress to the vault on 8200. `ca.crt` leaves the copy once DEC-2340's public-CA reader lands.
   Any other combination leaves `connect` off,
   the callback answering `not_found` (DEC-2626 item 7), so a deployment fails closed. A
   missing piece does not refuse the start: the API also serves risk reduction, which a broken
   connect setting must never take down (`AGENTS.md` rule 13). Two conditions hold with it:
   - **The off state is visible.** When `connect` is off with some but not all of the settings
     set, the start writes one line naming each missing or invalid setting by name, never its
     value. An API with none of them set offers no connect, as today, and writes nothing.
   - **A cell override still refuses.** A `MANDATE_ALPACA_AUTHORIZE_URL` set where DEC-2633 item 3
     refuses it (any build without debug assertions, or a tier other than `dev` or `ci`) refuses
     the start, as it does without this decision. Only the four connect settings fail soft.
   - **The release build.** This pair gives `config::authorize_page` its first production caller,
     so it also commits a release-build pin in the form of the stub issuer's `cargo xtask ci
     stub-release`. The pin runs the API binary built without debug assertions and shows that every
     tier, `dev` and `ci` included, refuses to start with any `MANDATE_ALPACA_AUTHORIZE_URL` set.
     That pin, not a unit test, covers `authorize_page`'s `#[cfg(not(debug_assertions))]` arm.

## Rationale

The code is a secret that crosses two processes built by two slices. One byte form, written and
read by one module, makes the hand-off a comparison. Logging in per write keeps no credential or
token in the API's memory between the rare connects. Moving the API server above the vault is the
smallest change that lets it hold the one port it needs, and the policy table, not the API's code,
is what stops it reading a token.

## Alternatives considered

- **vault-local's two-byte length fields.** A second format for the same entry, not canonical,
  and not what the token entry chose.
- **A session held for the process's life.** It would need renewal and keep a vault token in
  memory for days to serve a write made a few times.
- **Make `CodeVault` async.** An async trait method cannot be called through `dyn`, and the
  callback already holds the port as `Arc<dyn CodeVault>`; `spawn_blocking` keeps the port as it
  is.
- **Refuse the start when only some connect settings are set.** Louder, but it would take down the
  API's risk-reduction routes over a connect setting.
