## Context

The deployment signs every web push's VAPID header with its own application server key (RFC 8292,
DEC-726), and DEC-438 item 22 makes the keys our own. `mandate_webpush::VapidSigner` keeps the key
out of the pure crate: it asks for the public key and an ES256 `r || s` signature. Nothing yet says
where the private key lives, who may write or read it, or how it changes. A browser subscription is
bound to the public key it was made with, so a key change also strands every subscription made
under the old key.

## Decision

1. **One key set per workspace, in that workspace's vault namespace.** Each workspace has its own
   VAPID keys, at the new `SecretPath` `workspaces/{workspace}/web-push/vapid/{key_id}`, where
   `key_id` is the first 16 lowercase hex digits of the SHA-256 of the key's public point. A
   compromise of one workspace's dispatcher exposes no other workspace's key. In hybrid and on-prem
   the customer's vault holds it, as for every credential (infrastructure §5.2).
2. **Generated in place, never imported.** A new key is made only by a keygen command (`mandate
   vault vapid-keygen --workspace <id>`) under a write-only vault identity, `VapidKeygen`, which
   can create a key entry and read nothing. The command draws the P-256 key from the operating
   system's source (`ring`'s `EcdsaKeyPair::generate_pkcs8`), writes the PKCS #8 document
   put-if-absent, and prints only the key id and the public key (unpadded base64url of the
   uncompressed point, 87 characters). It never prints, logs, or writes the private key anywhere
   else, so no copy ever exists outside the vault. There is no import path: a key made elsewhere
   is a key someone else has seen.
3. **Read once, at start, by the dispatcher alone.** The workspace's dispatcher identity
   (`Dispatcher(workspace)`) may read that workspace's key entries and nothing else of them; no
   other identity reads them, the API and the operator included (OPS-1, infrastructure §5.2's "no
   wildcard"). The dispatcher reads every key of its workspace at start, as a start-up check while
   web push is on (DEC-2500 item 4), holds each as a `ring::signature::EcdsaKeyPair` behind its
   `VapidSigner`, and drops the PKCS #8 bytes, held as a `secrecy` value, once parsed. A vault
   outage after start stops no send; one at start keeps the dispatcher from becoming ready, and the
   orchestrator retries it. The pull channels are not affected (§5.1), nor is trading (NT-9).
4. **Signing in process.** `sign_es256` is `ring`'s `ECDSA_P256_SHA256_FIXED_SIGNING`, which gives
   the 64-octet `r || s` RFC 8292 needs, with the process's secure random source. The key never
   leaves the process: not in a log, a metric, a trace, the journal, an error, a panic message, a
   `Debug` or `Display` output, an environment variable, or a file. The process runs with core
   dumps off, and the pod has no swap (infrastructure §3.3). Residual, disclosed: `ring` does not
   zero a key pair's memory when it is dropped.
5. **Each address records its key.** The web client subscribes with the workspace's current public
   key, which it fetches from the workspace API, and sends that key's id with the subscription; the
   API stores it in the address entry as `key_id` (DEC-2502 item 1) and refuses an id the workspace
   does not hold as current. The dispatcher signs each send with the key its address names. An
   address whose key the dispatcher does not hold is a fault of the deployment, not of the address:
   `permanent { provider_error }`, which marks nothing (DEC-728's reading).
6. **The subject is a role mailbox on every route.** DEC-727's rule (exactly
   `mailto:<role>@<domain>`, `<role>` one of `push`, `notifications`, `postmaster`, `abuse`,
   `security`) applies to direct sends too, not only relayed ones, so no push service is ever given
   a person's address. The deployment value `mailto:push@notify.owlhead.ai` (DEC-790 item 4)
   already meets it. This tightens DEC-790 item 4, which allowed any `mailto:` or `https:` URI on a
   direct send.
7. **Rotation.**
   - *Planned* (a schedule, or a key nearing an age the operator sets): keygen makes a new key; the
     workspace API starts serving it as current; the dispatcher, restarted, holds both. A browser
     whose subscription names the old key re-subscribes under the new one the next time the member
     opens the app (with the step-up `PUT /me/channels/web_push` already needs), and the API
     replaces the old address with the new in one batch, as it replaces an unreachable one
     (workspace API §5.7; the replacement by key is lane A1's change). The old key is deleted only
     when no active address names it, however long that takes. Nothing is dropped: until then every
     address is signed with the key it was made under.
   - *On compromise*: the key is deleted at once and the dispatcher restarted, because a stolen key
     must stop signing. Addresses still on it can no longer be signed for (item 5,
     `permanent { provider_error }`), and a push service's `403` for a mismatched key is DEC-729
     item 4's question, whose conservative interim marks nothing. The member keeps the pull channels
     and re-subscribes when they next open the app. Whether such an address should instead be
     marked and raise `channel_lost` is the same founder question as DEC-729 item 4, not a new one.
8. **The stricter alternative, deferred: OpenBao's transit engine.** A transit key never leaves the
   vault, and the dispatcher would ask the vault to sign each header. It is deferred, not rejected:
   it puts the vault in every send's path (a vault outage stops web push, where item 3 stops only a
   start), adds a round trip per attempt, and returns DER signatures that need conversion. It
   becomes the better choice if the vault is made highly available (E21-32's follow-ups) or a
   dispatcher compromise is judged likelier than a vault outage.

## Owed by other changes

- **Infrastructure §5.1 and §5.2** (follow-up): a row for the VAPID private key (used by the
  dispatcher of its workspace; custody the workspace's vault namespace, generated there) and the
  dispatcher's and `VapidKeygen`'s identities.
- **The vault policy rows** (L3, the E21-32 follow-up over [#1458](https://github.com/kunwarshivam/mandate/pull/1458)'s
  closed table): `SecretPath::VapidKey`, `Identity::Dispatcher`, `Identity::VapidKeygen`.
- **Workspace API** (lane A1): the route that serves the current public key and its id, and the
  `key_id` in `PUT /me/channels/web_push`. **The web client** (lane W2): subscribe with the served
  key and re-subscribe when it changes.

## Rationale

Every item narrows who can see the key: one workspace's, made where it is kept, read by one
identity, used only in one process's memory, and never shown. Item 5 makes rotation possible without
a flag day, and item 7 states what a forced rotation costs instead of hiding it. Item 6 extends a
rule that already holds on the relayed route to the direct one, which only sends less.

## Alternatives considered

- **One key per deployment or per cell.** Rejected: one compromised dispatcher would expose every
  workspace's key.
- **An import command beside keygen.** Rejected: a key generated outside the vault has had a copy
  outside it.
- **The key in an environment variable or a mounted Secret file.** Rejected by OPS-1 and ES-23.
- **Transit signing now:** item 8.
