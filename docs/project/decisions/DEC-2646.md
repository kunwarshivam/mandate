# DEC-2646: A closed pull request's runs are cancelled, so they stop holding CI's slots

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-27 (UTC) |
| **Decided by** | An agent (Claude Code, lane RN), under DEC-79: a reversible CI scheduling change the coordinator asked for. It cancels only runs whose pull request has closed, and weakens no check |
| **Story or claim** | CI throughput; [DEC-610](DEC-610.md), [DEC-2610](DEC-2610.md), [DEC-2065](DEC-2065.md) |

## Context

On 2026-10-27 GitHub's runners started nothing for more than four hours. The coordinator found
about 200 queued runs, and 15 still in progress, from pull requests merged the day before. Once
they were cancelled, `main`'s run started at once.

`ci`, `CodeQL`, `release-check` and `web` already cancel a pull request's older run when a newer
one starts, because each workflow's concurrency group is keyed on the pull request's ref
(`refs/pull/<n>/merge`). A pull request that closes never starts a newer run, so its last runs
stayed queued or running, holding slots no later run of it could free.

## Decision

1. **`.github/workflows/cancel-closed.yml` runs when a pull request closes**, merged or not. It
   has one job per workflow above. Each job joins that workflow's concurrency group for the pull
   request's ref with `cancel-in-progress: true`, which cancels the workflow's queued or running
   run, and then only echoes. Concurrency groups are shared across workflows, so no token or
   `actions: write` permission is needed, and the workflow grants none.
2. **Pushes to `main` are untouched.** Their runs use the groups `ci-refs/heads/main` and
   `codeql-refs/heads/main`, which no closed pull request's ref can name, so DEC-2610's
   post-merge runs are never cancelled.
3. **Cost:** four one-second jobs on GitHub's runners per closed pull request. Each releases at
   least one run that would otherwise wait for a slot.

## Rationale

The stall was ours, not GitHub's. Superseded runs cancel themselves today; this closes the one
case that never gets superseded.

## Alternatives considered

- **Cancel through the API on close.** It needs a token with `actions: write` in a workflow that
  a pull request triggers, which is more power than a concurrency group needs.
- **Add `closed` to each workflow's own triggers**, with every job skipping on it. Every job of
  `ci` would need the new condition, and the required `fast` and `full`, which run on `always()`,
  would report on a closed pull request.
