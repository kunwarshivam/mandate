# DEC-671: Journal spec v0.22 adds the client actor and closes ConnectionRevoked's reason and the client records

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The L2 builder agent, under DEC-79 and DEC-176. Each item records what DEC-436 items 9 and 20 and DEC-437 item 10 already settled, or refuses more. None loosens a rule or touches a founder-reserved area |
| **Story or claim** | E10-15, claim #749; DEC-436 items 9, 14, 20; workspace API spec §3.3, §3.8, §4.5, §5.6; identity spec §12.1, §12.2 |

## Decision

1. **The `client` actor is one shape, defined in journal §3:** `{kind: "client", id, version,
   build: null, on_behalf_of}`. Every record a client may write uses it, including L5's
   `RecordsAccessed` and L1's identity events. `on_behalf_of` is a member of a client actor only.
   It is absent from every other kind rather than `null`, so no recorded event's bytes or hash
   change and `envelope_version` stays 1 (rule 81).
2. **The human of an actor** is `on_behalf_of` for a client and `id` for anyone else. Mandate spec
   §6.4 check 7 (already amended under DEC-436 item 19), §5.8's requester, and identity spec ID-6
   compare humans. Check 3 needs no change: it requires a `user`, which a client never is.
3. **A client is external** (rule 82: `build` is `null`).
4. **A client writes only what its scopes allow** (rule 83). That is the control stream's
   `MandateDraftSaved` (propose), `OwnerRequestSubmitted` (request), and `RecordsAccessed` (read,
   dry run). Everything identity spec ID-11 forbids it is refused at append, before its payload is
   read. An approval answer from a client is therefore refused twice: at append, and by check 3 at
   the runtime. A client's `RecordsAccessed` is admitted at append, but cannot be journaled until
   the audit lane (L5) closes that record's schema, so E10-14's "every client call, reads included,
   is journaled" waits on L5. L5's schema must use the §3 client actor and carry a valid client
   vector. The `hold` scope's command joins the list with DEC-672, which closes
   `hold_openings`. Until then a client's hold is refused, which costs only an action the owner can
   still take.
5. **The host CLI keeps `system` with no `on_behalf_of`** in this version. Identity spec §6.4 gives
   it one, but `HostCliRegistered` is not in the journal yet. The change that adds it widens rule
   81, and identity spec §12.2 says so.
6. **`ConnectionRevoked` version 2** adds `reason` (`owner`, `compromised`) and `step_up` (never
   `null`, identity ID-4). Version 1 is never edited and stays registered. Rule 84: a
   `compromised` revocation names its kill switch as `causation_id`, and an ordinary one has none.
   The coordinator's review tightened it to a batch check, on rule 45's precedent: the cause is a
   `kill_switch` `OwnerCommandIssued` earlier in the same batch, at `connection` scope, for the
   revoked connection, read from the members the CLI writes today.
   This makes workspace API §5.6's order, kill switch first and then revocation, visible in the
   record. Rule 85: the actor is a user. E7-17 (builder δ) adds connection state at a later version
   and does not touch these members. Its fold counts either version as a revocation.
7. **`ClientConnected`:** `client_id`, `user`, `scopes` (workspace API §3.8's closed list), `agents`,
   and `step_up` (never `null`). Rules 86 to 88: both lists are non-empty and strictly ascending,
   and the actor is the user the client acts for.
8. **`ClientRevoked`:** `client_id`, `user`, and `reason` (`owner`, `admin`, `member_deactivated`,
   `deprovisioned`, `compromised`), with no step-up (ID-5). The reason is identity's lead's ask, so a
   reader can tell who ended a client and why. Rule 89 pins the actor to the reason: a user for
   `owner` (and that user is the client's) and `admin` (another user), the `system` for
   deprovisioning, and either a user (the deactivating admin, identity spec §5.2) or the `system` for
   `member_deactivated` and `compromised`. Revocation only removes access, so admitting the admin adds
   no risk (DEC-176); the journal cannot see roles, so it checks none.

### Invariants

- **INV-1. A client is never a person.** No record carries a client as `user`, and every rule that
  compares people reads the human (items 1 and 2).
- **INV-2. A client never does what ID-11 forbids,** checked at append (rule 83).
- **INV-3. Who acted is the authenticated principal.** `requested_by`, `client_id`, and
  `ClientConnected.user` agree with the actor (rules 79 and 88).
- **INV-4. A compromised revocation follows its kill switch** (rule 84).
- **INV-5. Nothing recorded before v0.22 changes.**

The vectors' `client_actor` section has an invalid draft for every rule. Its valid drafts include
the client branches of §9.9's rules 70 and 79, which v0.21 could only refuse. The generator checks
two oracles of its own:

- the human behind every accepted record, computed from ID-6 and ID-11 rather than from the rules;
- the compromised revocation's link to its kill switch.

All 32 validator mutants, 5 batch mutants, and 6 vector mutants are caught.

### Lifecycle walk

- **Client.** Connected by its user with step-up. It then acts only through rule 83's records.
  Revoked by its user, an admin, or deprovisioning, which needs no step-up. After revocation the
  API refuses its next call (ID-11). The journal does not check that a client acts only between
  its two records: that is a cross-event, stateful check, and the API's token is the authority.
- **Connection.** An ordinary revoke is refused by the API while any agent on the connection is
  exposed. A compromised one commits the kill switch and then the revocation in one batch. If the
  step-up is missing, only the kill switch commits (workspace API §5.6), so the revocation never
  exists without its step-up.

### Adversary

- **A prompt-injected client:** it tries to approve, confirm, revoke a connection, or connect
  another client. Rule 83 refuses each at append.
- **A client claiming to be its user:** it cannot. The actor is set from the token, and rule 79
  ties `requested_by` to it.
- **A user approving their own client's proposal as the second party:** check 7 compares humans.

## Rationale

DEC-436 item 14 requires these records in the journal spec before the API writes them. Making the
shape a §3 definition, not part of one event, is what lets the audit lane (L5) and the identity
lane (L1) reference it without redefining it (the coordinator's scope note).

## Alternatives considered

- **`on_behalf_of` always present, `null` for non-clients:** this changes every recorded event's
  canonical bytes, and so breaks every hash chain.
- **Refuse a client's approval only at check 3:** that works, but leaves the journal accepting a
  record the product never permits. Refusing at append as well is cheaper to audit.
- **Admit the host CLI's `on_behalf_of` now:** its registration record does not exist yet, so the
  journal could not tell a host CLI from any other `system` actor.
