# DEC-458: Journal the reconciled broker account before releasing startup

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-05 (UTC) |
| **Decided by** | The implementing agent under DEC-79 and DEC-176 |
| **Story or claim** | E7-7 and E6-9 integration; claim [#171](https://github.com/kunwarshivam/mandate/issues/171); [PR #598](https://github.com/kunwarshivam/mandate/pull/598) |

## Decision

1. `AccountStateObserved` schema version 1 is the executor's existing complete broker-account
   record: `status`, `crypto_status`, the three blocking flags, `multiplier`, `equity`, `cash`,
   `buying_power`, `non_marginable_buying_power`, `accrued_fees`, and `risk_clock`.
2. Startup reconciliation journals and folds that account record before `ReconciliationRun`.
   An opening is released only after both records from the same gathered snapshot commit.
3. The record remains free of broker account numbers, broker account IDs, credentials, and
   personal data. The schema is closed; missing or extra fields fail the append.

## Rationale

The executor already writes and folds this exact record for a broker account update, and its
startup hold deliberately requires both an observed account and a completed reconciliation.
The shell's gathered startup snapshot contains the same typed `BrokerAccount`; failing to pass it
through the existing writer left every opening held forever. Registering the writer's exact shape
and recording it before the run resolves the integration gap without inventing state or weakening
the hold.

## Alternatives considered

- Treat `ReconciliationRun` alone as an account observation: rejected because it carries no
  account status, flags, balances, or buying power and would weaken the startup hold.
- Fold the gathered account only in memory: rejected because restart and audit would lose the fact.
- Use `AccountSnapshotRecorded`: rejected because that event is the daily/fee reconciliation
  snapshot with a different closed payload and lifecycle.
