# DEC-2335: The deployment manager starts an OAuth connect's executor on its exchange's success, and keeps it until the connection closes

## Context

DEC-2627 item 5 has the deployment manager start the pending connection's executor, with the
request's `account_ref`, once the connect's token exchange succeeds. The connections spec has that
executor run checks while the connection is `connecting` and, after `ConnectionEstablished`, act on
the account starting with its first reconciliation, until the connection is disconnected. Journal
spec §9.21 has no record for that start: rule 167 admits `deployed` or `requested` at generation 1
and rule 256 keeps `requested` to the token exchange; and the manager wants an executor only while
an agent is deployed on its account.

## Decision

1. **The start is journaled as `exchanged`** (journal spec v0.74). When the request's token
   exchange exits successfully while the request is open, the manager journals the executor's
   `ProcessStartIssued` for the request's `account_ref` at generation 1 with cause `exchanged`,
   before it acts. Rule 167 reads `deployed`, `requested` or `exchanged` exactly at generation 1,
   and rule 257 keeps `exchanged` to `executor`. A failed exchange, or none by the deadline, starts
   nothing; the API's teardown closes the request (DEC-2627 item 5).
2. **The executor is wanted until its connection closes.** From that start, through `connecting`
   and after `ConnectionEstablished`, whether or not an agent is deployed on it (the coordinator's
   choice (a), 2026-10-22: connections spec §5.2 step 5, and the kill switch reaches an established
   account before any agent). It restarts and answers kill switches as any executor does.
3. **Without an agent it places no order of its own.** An executor with no deployed agent only
   runs its checks, reconciles the account, and acts on a kill switch: nothing proposes an order
   to it, and this decision gives it none.
4. **The stop is `connection_closed`, journaled first.** A `ConnectionRefused` with occasion
   `connect`, or a `ConnectionRevoked`, ends it: the manager journals `ProcessStopIssued` with
   cause `connection_closed` before it acts, unless a deployed agent of its account still wants it
   (§9.24: a revocation stops no deployment). Rule 257 keeps `connection_closed` to `executor`; rule
   256's `request_closed` stays the token exchange's alone.
5. **API-key connections are unchanged.** A connection with no OAuth request (the CLI's
   `connection record`) keeps today's rule: its executor is wanted while an agent is deployed on its
   account.
6. **J2 lands atomically.** The new vectors are refused by the old `deployment.rs` and the new
   parser by the old spec's `reference` and `refcases` gates, as J1's were (DEC-2635), so the spec,
   its reference and vectors, and the parser ship in one pull request under one
   `ATOMIC_EXCEPTIONS` entry naming it.

## Rationale

Journaling the start before it acts keeps the manager's one rule: every process it runs is
recovered from the journal after a restart, so a restarted manager neither starts a second
executor for the connect nor loses the one it started. Keeping the executor to the connection's
own lifetime is what the connections spec describes, and it keeps the kill switch's reach.

## Alternatives considered

- **Reuse `deployed`.** Rejected: it would claim an agent's deployment that never happened.
- **Reuse `request_closed` for the executor's stop.** Rejected: it would loosen rule 256, which
  ties it to the token exchange both ways.
- **Stop the executor at establishment when no agent is deployed** (choice (b)). Rejected by the
  coordinator: the spec has it act on the account from establishment, and the kill switch would not
  reach an account with no agent.
