# DEC-2148: An agent's mandate versions fail closed on an application that contradicts its entry

| | |
|---|---|
| **Status** | Accepted (agent: two tightenings DEC-176 lets an agent take. Each only refuses a read that DEC-2147 would have served, and adds no risk: the route writes nothing, and a refusal is `journal_unavailable`, retryable, never a version in effect read past a contradiction) |
| **Date** | 2026-10-29 (UTC) |
| **Decided by** | `claude-code` (lane L1, builder 4), on R3's review of #2903 and R1's review of #2916 |
| **Story or claim** | E10-27; amends [DEC-2147](DEC-2147.md) items 4 and 6; #2914, #2916 |

## Context

DEC-2147 item 4 put a version in effect on any `MandateVersionApplied` `applied` for the agent, and
item 6 matched each later version to the first application whose `causation_id` is its
confirmation. Neither said what to do with an application that disagrees with the entry it
answers. R1 found that a second application answering one confirmation could put a version in
effect that the history does not list.

## Decision

1. **In effect only through a listed confirmation.** Item 4 counts an `applied` application only
   when its `causation_id` is a confirmation the history lists. So `in_effect` is always a listed
   version, or `null`; an application no listed confirmation caused moves nothing.
2. **A contradicting application fails the read.** An application answering a listed confirmation
   that names another `new_version` than the entry's, another `old_version` than its
   `base_version`, or another classification than the one the server computes from the stored
   documents (when it computes one), or that gives a `reason` exactly when it is not `rejected`
   (journal spec §9.3 rule 30), answers `journal_unavailable`. Rule 33 is not checked again here:
   append refuses a record that breaks it, and a read that re-checks it is backlog row E10-28.
3. **A second application of one confirmation fails the read.** Two applications whose
   `causation_id` is the same listed confirmation answer `journal_unavailable`, whatever they say.
4. **The account stream is the workspace's own.** The application records are read only from
   `acct:{workspace_id}:…` under the path's workspace; an agent of the same id in another
   workspace changes nothing (API-9).

## Known consequences

R3 reviewed the read after it landed and found three behaviours this decision records rather than
changes; each fails closed or holds by another decision.

1. **One agent's unreadable record fails its account's other agents.** The read checks the
   members of every `MandateVersionApplied` on the account stream before it filters by
   `agent_id`, so an unreadable record of one agent makes every agent's read on that account
   `journal_unavailable`. That fails closed but couples their availability. Filtering by
   `agent_id` first, and refusing only the agent's own unreadable records, is backlog row E10-29
   (Could).
2. **A classification the server cannot compute checks nothing.** When the store cannot give
   either document, the entry's `classification` is `null` and item 2 accepts whatever
   classification the application records; the version, base, reason and one-application checks
   still apply.
3. **A stop is never undone.** Once an `AgentStopped` names the agent, `in_effect` stays `null`
   even if a later `AgentDeployed` names the same id. That holds because an agent id is deployed
   once ([DEC-1173](DEC-1173.md) item 1); if ids ever become reusable, this read must reset its
   stop at each deployment.

## Rationale

Each item refuses or narrows what DEC-2147 served, and none serves anything new. The journal's own
rules already refuse a contradicting application at append, so a read that meets one is reading a
journal that is not what the writers wrote, and the safe answer is to say so rather than choose a
version.

## Alternatives considered

- **Serve the first application and ignore the rest.** Refused: the version in effect would then
  depend on which record the reader happened to keep, and could be one the owner never confirmed.
- **Serve the contradiction with a flag.** Refused: a client would have to judge the journal's
  consistency, which is the server's to judge.
