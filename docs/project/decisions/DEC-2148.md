# DEC-2148: The acknowledgment refusal codes are served, and a one-agent reconciliation hold is acknowledged through its own agent alone

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79. Item 1 records what shipped. Item 2 is the reading DEC-176 lets an agent take: it only narrows who may acknowledge, so it adds no risk) |
| **Date** | 2026-10-29 (UTC) |
| **Decided by** | `claude-code` (lane L1, builder 3), for R2's follow-up on #2912 |
| **Story or claim** | E10-12; workspace API spec §3.11 item 12, §3.5; journal spec §9.28; [DEC-2144](DEC-2144.md) item 7; [DEC-2830](DEC-2830.md) item 1 |

## Context

[DEC-2144](DEC-2144.md) item 7 says the two refusal codes `acknowledgment_unavailable` and
`acknowledgment_request_invalid`, and the status phase `accepted`, are `x-planned` E10-12 until the
server serves them. #2925 serves both codes, and #2912 dropped their markers. Since the
decisions README lets a PR edit only its own decision files, this decision records that and leaves
DEC-2144 as it stands.

Workspace API §3.11 item 12's check 5 refuses an acknowledgment unless the hold is one the list
serves now for the agent in the path. #2912 added a note there that cites DEC-176, but no decision
recorded the reading it names.

## Decision

1. **The two codes are served.** `acknowledgment_unavailable` and `acknowledgment_request_invalid`
   have been served since #2925, and #2912 removed their `x-planned` E10-12 markers. DEC-2144 item 7's
   "until the server serves them" is met for these two. The status phase `accepted` stays `x-planned`
   E10-12 until the server serves it.
2. **A reconciliation hold of one agent is acknowledged through that agent alone.** Journal spec
   §9.28 and [DEC-2830](DEC-2830.md) item 1 let an acknowledgment of a reconciliation hold name any
   agent of the account. The workspace API's check 5 reads a hold whose `agent` is one agent as
   standing for that agent only. An acknowledgment of it posted through another agent of the same
   account is therefore refused `409` `acknowledgment_unavailable`, and nothing is committed
   (`Hold::blocks`; `versions_http::another_agents_limit_is_not_acknowledged_through_this_agent`
   for a limit). A hold of every agent (`*`) still blocks, and can be acknowledged through, every
   agent of its account. This is the note under check 5. The narrower reading only removes a way to
   lift a hold, so it adds no risk (DEC-176). The CLI and the executor keep §9.28's reading.

## Rationale

Item 1 closes a status line DEC-2144 left open, so a reader does not take the codes as still
planned. Item 2 gives check 5's note a decision to cite. The API lists each hold under the agent
the owner sees it on, so letting another agent's page acknowledge it would act on a hold the owner
was not shown there.

## Alternatives considered

- **Edit DEC-2144 item 7 in place.** The decisions README forbids it: a PR edits only its own
  decision files.
- **Supersede DEC-2144.** Rejected: the rest of DEC-2144 stands. Only item 7's status note and one
  reading are new.
- **Widen the API to §9.28's reading.** Rejected for now: it loosens the API, and nothing asks for
  it. A later decision can widen it if the web app needs it.
