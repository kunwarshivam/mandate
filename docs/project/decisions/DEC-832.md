## Context

DEC-642 item 1 says an org-scope authorization yields no `TenantContext`, and items 3 and 8 say
every data API takes only a `TenantContext` or a `SystemContext` and the request path never holds a
`SystemContext`. Yet identity spec §12.1 writes organization-scope events (ownership, SSO, org
policy, the org-scope kill switch) into each workspace's control stream. No type let the request
path make those writes, so the org-scope kill switch, which `AGENTS.md` rule 13 says is always
available, had no lawful path. The `own` rows of §4.2 (one's own passkey) and the leave row had the
same gap from the other side: nothing in the types bound "one's own" to the authenticated principal.

## Decision

1. **`OrgContext`.** An authorization at an organization's scope yields an `OrgContext`, sealed as
   `TenantContext` is: private fields, built only by `authorize`, no public constructor, no
   `Default`, no deserializer, no `Clone`, never stored or serialized, and alive for one request. It
   carries the organization, the authenticated principal (ID and kind), the `session_ref`, the one
   permission authorized, `membership_unverified` (DEC-642 item 10), and the organization's
   workspaces. It does not implement `Tenant`, so no data API takes it.
2. **The workspaces come from the store, never from the caller.** `authorize` enumerates the
   organization's workspaces (those not archived) that this deployment hosts, at authorization
   time, through the same sealed membership lookup it reads memberships with (DEC-642 item 4), from
   the fold of the organization's events in this deployment's store. No body field or argument
   names the set.
3. **From an `OrgContext` to workspace data.** It is consumed into `TenantContext`s, each carrying
   one workspace of the enumerated set, the organization, and the same principal, permission,
   `session_ref`, and `membership_unverified`. Two ways, and no other:
   - **one workspace:** the workspace the route names, and only when it is in the enumerated set;
     otherwise `no_membership` (404, workspace API-9);
   - **every workspace:** one context per workspace of the set, for a write that one request makes
     to all of them.

   Each event written through such a context is attributed to the authenticated principal (ID-1),
   with an idempotency key derived from the request's `Idempotency-Key` and the workspace, so a
   retry commits at most one event per workspace (workspace API-4).
4. **The organization kill switch** (the only org-scope write workspace services' request path
   makes today; the other org-scope rows belong to the global control plane's API, workspace API
   §1.4, gap 8). DEC-436 item 13 stands: the client issues one workspace-scope call per workspace,
   each journaled on its own and reported per workspace. Each call is authorized at the
   organization's scope through the row "Kill switch, org scope: engage", and its `OrgContext`
   yields the one `TenantContext` of item 3 for the route's workspace. **Partial failure is never a
   denial:** each call is independent, refused only as API-7 allows, and the client retries each
   workspace not yet reported committed, with the same idempotency key, until every workspace of
   the set is, showing the owner which are pending. During a membership-store outage the call is
   authorized from the session's roles snapshot (DEC-642 item 10), and the set check is replaced by
   the route workspace's own record naming the snapshot's organization. If that record cannot be
   read either, the call is **pending, never refused**: `OrgContext::into_workspace` answers
   `OneWorkspace::Pending`, not a `Refusal`, and the client retries it with the same idempotency
   key and shows it pending, as for a workspace not yet committed. It is not granted unchecked
   either: nothing would then establish the route's workspace as the organization's, and one
   organization's kill switch could reach another's workspace.
5. **One request writing to every workspace** (item 3's second way; no route uses it today, and
   none may call it until a route story decides it). `OrgContext::into_every_workspace` yields
   `EveryWorkspace::Contexts`, exactly the enumerated set, or, for a context built during a
   membership-store outage (no set enumerated), `EveryWorkspace::NoSetYet`: never a caller-named or
   partial set, and not a `Refusal`; the caller treats it as pending and retries, never as a
   denial. Then:
   - a risk-reducing write (the risk-reducing set of identity spec §4.5) is never denied: a
     workspace whose append fails is retried until it commits, and the response reports each
     workspace as committed or pending;
   - any other write commits in one database transaction across every target workspace's control
     stream, or not at all, refused `journal_unavailable`, retryable.
6. **Organization events from the global control plane** (ownership, SSO, org policy, org
   memberships) are not request-path writes. A separate process of the workspace deployment, with a
   `SystemContext` per workspace, commits each into every workspace of the organization it hosts,
   attributed to the principal the origin event names (ID-1), under item 5's rules: tightening org
   policy is retried until every workspace holds it; every other one commits to all or none. The
   origin event's authentication and the relayed event's shape are gap 8's, owed before the global
   control plane writes any.
7. **`PrincipalContext`, for one's own data.** An authorization of a row whose cell is `own` (enrol
   or remove one's own passkey) or of the leave row yields a `PrincipalContext`, sealed the same way.
   It binds the authenticated `PrincipalId` and the scope of the membership the row is used through.
   The credential-store APIs for one's own passkeys and the leave operation take only a
   `PrincipalContext` and read the subject from it; none takes a principal ID, a credential owner, or
   a member as an argument, so "own data only" holds by type. Its control-stream writes go through
   the `TenantContext` of its workspace, bound to the same principal; leaving an org membership is
   an org-scope change, item 6's.
8. **Hybrid and on-prem.** Each deployment enumerates only the workspaces it hosts. How the owner
   reaches a workspace hosted by another deployment that is offline is identity spec §16 open
   question 5, not decided here.
9. **The tests it owes** (identity spec ID-8 and ID-16; E9-2 for `authorize`, E9-8 for the
   isolation and compile-fail tests):
   - compile-fail: `org_context_cannot_be_constructed_outside_authorize`,
     `principal_context_cannot_be_constructed_outside_authorize`, `org_context_is_not_a_tenant`
     (passing an `OrgContext` to a data API fails to compile), and
     `own_credential_api_takes_no_principal_id`;
   - `an_unreadable_workspace_record_never_refuses_risk_reduction` (item 10),
     `an_org_route_with_no_set_and_no_record_is_pending_never_refused` (item 4), and
     `every_workspace_has_no_set_during_an_outage_and_the_full_set_live` (item 5), E9-2's;
   - `org_fanout_workspaces_come_from_the_store`: a call whose route names a workspace of another
     organization, or one this deployment does not host, is refused `no_membership`, and an
     every-workspace fan-out reaches exactly the store's set;
   - `org_fanout_events_are_attributed_to_the_principal`: the ID-1 fuzz extended to org-scope
     writes; every per-workspace event's actor and `session_ref` equal the oracle's record of who
     authenticated;
   - `org_kill_switch_reaches_every_workspace_through_append_failures`: with injected
     per-workspace append failures and a membership-store outage, the client's per-workspace retries
     end with the oracle (a fold of each workspace's control stream) finding exactly one kill-switch
     command per workspace of the set, attributed to the principal, and no call refused for a reason
     API-7 forbids; and the same for item 5's risk-reducing writes;
   - `org_risk_adding_write_is_all_or_nothing`: with one workspace's append failing, no workspace
     holds the event and the request is refused `journal_unavailable`;
   - `own_rows_reach_only_the_principals_own_data`: principal A can neither remove B's passkey nor
     deactivate B's membership through the `own` or leave rows.

10. **A workspace scope's pair, and an unreadable record** (amended under DEC-176). A
    `Scope::Workspace { org, workspace }` is the route's pair, so `authorize` checks it against the
    workspace's own record in the store (`MembershipLookup::workspace_org`), in this order: an
    inactive row is refused `inactive_permission`; then a pair the record does not hold (another
    organization's workspace, or one this deployment does not host) is refused `no_membership` for
    every principal kind; then `reduction_only`, `no_membership`, and `forbidden` as identity spec
    §4.5 says. When the record cannot be read, the pair cannot be checked: a row that is not
    risk-reducing is refused `membership_unavailable` for every principal kind, and a risk-reducing
    row (DEC-642 item 10's set) is never refused for it (`AGENTS.md` rule 13). A user or a client is
    authorized from its session's roles snapshot as DEC-642 item 10 says, the snapshot entry's own
    pair, which the store folded, standing in for the record, so a pair the snapshot does not hold
    reaches nothing; a service account, the host CLI, and a platform operator are authorized by
    their columns, whose workspace their own issuance, registration, or window names; each context
    is flagged `membership_unverified`, which the committed event records. A reduction-only session
    still reaches only its four rows.

## Rationale

The `OrgContext` keeps ID-8's one rule (a workspace's data is reached only through a context the
authorization step built, for a workspace the store, not the caller, named) while giving the
org-scope kill switch a lawful path that no outage of one workspace can deny. It keeps DEC-436 item
13's client fan-out, so no new route or global dependency enters the kill-switch path (API-8).
All-or-nothing for the other writes means no workspace runs under a loosened org policy another
workspace of the same organization did not record.

## Alternatives considered

- **A server-side fan-out with an outbox for the kill switch.** It would survive the client going
  away, but it supersedes DEC-436 item 13 and adds a new kill-switch route and a principal-attributed
  write from a `SystemContext` on the kill-switch path; a candidate for gap 8, not for this gap.
- **Let `authorize` take a list of workspaces.** The caller would choose the tenants, which ID-8
  forbids.
- **Authorize each per-workspace call at the workspace's scope.** An org owner holds no workspace
  role (identity spec §4.1, no inheritance), so the org-scope row would have no route.
