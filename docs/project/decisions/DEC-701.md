# DEC-701: Notification code layout: a pure `mandate-notify` and a process `mandate-dispatcher`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The L3 builder agent under DEC-79 (a reversible engineering decision) and DEC-176 (it only bars dependencies NT-3 already forbids) |
| **Story or claim** | E8-16, claim [#753](https://github.com/kunwarshivam/mandate/issues/753); [notifications spec](../../specs/notifications.md) §10; E8-9, E8-10 |

## Decision

1. **`mandate-notify`**, layer 1, pure, safety-critical: the notice id and its source trait
   (DEC-702), the kinds, the classes, the text keys, the payload, the channel templates, the
   quiet-hours rule by class, the retry schedule, the coalescing fold, and the provider trait. No
   I/O, no impure crate. The quiet-hours window arithmetic stays `mandate_approval::deliver_now`'s
   (DEC-165 item 12); `mandate-notify` maps a class and the window's verdict to send, suppress, or
   defer.
2. **`mandate-dispatcher`**, a process crate, safety-critical: tails the journal, mints notice ids,
   resolves recipients, reads addresses through the vault client, drives the adapters, and appends
   to the notice stream. Its layer is set in the change that creates it, above `mandate-journal`.
3. **NT-3 at rung 1.** `mandate-dispatcher`'s `forbidden_internal` in `xtask/layers.toml` names
   every crate that writes an agent, account, or control stream: `mandate-runtime`,
   `mandate-executor`, `mandate-mcp`, `mandate-shell`, `mandate-cli`, `mandate-paper`, and the
   broker connectors (`mandate-alpaca` and any later one). Because `mandate-journal` also builds
   control-stream drafts, the dispatcher appends only through a writer that accepts only an `ntf:`
   stream id, pinned by E8-10's tests.
4. Each crate gets its `xtask/layers.toml` entry, CODEOWNERS line, and lint header in the change
   that creates it.

## Rationale

Splitting the pure rules from the process keeps every rule that decides what a payload holds, when
a send happens, and how notices coalesce mutation-testable and free of I/O, and puts the one crate
that talks to providers where the layering check can bar it from every trading writer.

## Alternatives considered

- **Extend `mandate-approval`.** Rejected: it would carry alerts, the brief, and identity notices
  that are not approvals, and a crate at layer 1 cannot also hold a process.
- **One dispatcher crate holding the rules too.** Rejected: the rules would sit beside the provider
  I/O and the vault client, so a mutant run could not exercise them on their own.
