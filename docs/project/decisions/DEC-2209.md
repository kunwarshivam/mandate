# DEC-2209: The runtime process tails its deployment's account stream

| | |
|---|---|
| **Status** | Accepted (agent; reversible engineering decisions under DEC-79, each at least as strict as the rule it implements) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | An agent (Claude Code, intelligence lane I2), under DEC-79, with lane P, which owns the process |
| **Story or claim** | E2E lane gap 3 (research in the runtime process, DEC-2208), E21-30; [claim #1531](https://github.com/kunwarshivam/mandate/issues/1531) |

## Context

`mandate-daemon` (E21-30 slice 1, DEC-1012) reads only the control and clock streams. The runtime
core lifts its startup hold only once it has folded a clean `ReconciliationRun`, and copies the
account's restrictions only from `AgentModeApplied` (DEC-131 items 13 and 22). Both are account-stream
records. So the process's core stays `paused` for ever. Neither research (DEC-2208) nor trading can
ever run in it.

The shell (`mandate-shell`'s `Session`) folds the agent stream, then the account stream, and only then
hands `Input::Started`.

## Decision

1. **The wiring names the account.** `Wiring` gains `account: Option<String>`: the account the
   deployment's connection names, whose stream is `acct:{workspace}:{account}` (journal spec §2).
   `fixture::wiring` leaves it `None`. With `None` the process reads no account stream, and the core
   keeps its startup hold, as before this change. An account that makes no valid stream id refuses
   the process at start, before it takes anything, as a non-paper environment does (`refused`).
2. **At start, the account stream is folded after the agent stream and before `Input::Started`**, as
   the shell does. So the startup hold is taken with the broker's last known truth. An account stream
   that cannot be read, or whose rows cannot be folded, stops the process at start (`cycle_failed`),
   as an unreadable agent stream does (DEC-1012 item 7); the restart replays.
3. **Each pass reads the account stream after the control stream and before the clock stream.** The
   owner's kill switch is still read first (DEC-1012 item 4, ES-06), and a tick is handed only after
   the account rows it may depend on.
4. **Only the rows past the core's own head for the stream are folded**, each once, in journal order,
   with `mandate_runtime::fold`, as the shell folds the account rows it commits. The core acts on
   them at the next input, the tick that follows in the same pass: it settles its startup hold and
   journals any change of mode then (MI-6). The core's head is folded state, so no bookkeeping of what
   was read can drift from the journal, and `fold` itself refuses a row out of sequence. Unlike a
   control row (DEC-914 item 2), an account row is never offered twice: the core would re-apply an
   earlier restriction.
5. **An account stream that cannot be read during a pass folds nothing and holds nothing.** The
   clock pass still runs, on the core's last folded view of the account. A tick is what expires
   approvals and proposes exits, and an account-stream outage is none of the holds `AGENTS.md` rule
   13 allows an exit; every opening still meets the gate on the account stream. A row the core cannot
   fold stops the process (`cycle_failed`), as an agent-stream row it cannot fold does at start, so
   an account row of a type the core does not interpret keeps the runtime down until the core
   interprets it, exactly as such an agent-stream row would.
6. **What a fold does not do, as in the shell.** The core cancels pending approvals on
   `MandateVersionApplied` only when it is handed that record as input (`applied`), and neither the
   shell nor this process hands account rows; both fold them. Parity with the shell is kept here; a
   version applied while an approval is pending is a follow-up for the post-R0 hook (E21-30 slice 2,
   with the executor's process).

## Rationale

The core decides what each account record means. The process only decides when each is offered, and
offers it in the shell's order. A deployment without the account named runs exactly as before.

## Alternatives considered

- **Hand the account stream whole each time its head grows, as the control stream is.** Rejected:
  item 4's spurious mode changes.
- **Hand account rows as `Input::Journal`.** Rejected: the core folds no row it is handed that way
  unless it is owner input. Its account-stream reactions run from its own folded state at the next
  input, which is the shell's order too.
- **Start without the account stream when it cannot be read.** Rejected: the core would take the
  startup hold, and the process would run on no view of the broker's truth until the stream came
  back. Failing the start and replaying keeps one path.
