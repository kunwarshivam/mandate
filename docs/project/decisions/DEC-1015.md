# DEC-1015: A runtime process started by the deployment manager takes its deployment from the pod's variables

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and DEC-176, agreed with lane D1; it adds a way to name a deployment and loosens nothing) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (builder of lane P3 of the managed-cells plan, DEC-967, DEC-990), with lane D1 (E21-33) |
| **Story or claim** | E21-30 slice 1, E21-33 slice 2; DEC-1012, DEC-1013 |

## Context

The deployment manager (`mandate-deploy-manager`, E21-33) starts one pod per runtime from a chart
template. It sets `MANDATE_WORKSPACE`, `MANDATE_PROCESS` (`runtime` or `executor`),
`MANDATE_SUBJECT` (the agent for a runtime, the account's `account_ref` for an executor) and
`MANDATE_GENERATION`. It passes ids only, never a secret, and does not know an agent's connection
or owner. `mandate-daemon run` took its whole deployment as flags.

## Decision

1. **The manager's template runs `mandate-daemon run --probe <socket>`.** The process takes its
   workspace from `MANDATE_WORKSPACE` and its agent from `MANDATE_SUBJECT`.
2. **A pod for another process is refused.** `MANDATE_PROCESS` other than `runtime` refuses
   `process_not_runtime`.
3. **The flags still work, and never override the manager.** Without `MANDATE_PROCESS`, the
   workspace and agent come from `--workspace` and `--agent`. With it, a flag that names a different
   workspace or agent refuses `deployment_conflict` rather than being guessed between (`AGENTS.md`
   rule 3). A launch with no workspace or agent refuses `deployment_missing`.
4. **`MANDATE_GENERATION` is the manager's alone.** The agent stream's writer epoch is what fences
   an earlier process (DEC-1012).
5. **The connection and the owner are read from the agent's deployment, not passed.** They are in
   the mandate document the latest `AgentDeployed` of the agent names (journal spec §9.2: the
   record carries the version, never the connection). Until the process reads that document, a
   launch that names no `--connection` and `--owner` refuses `deployment_unresolved` before it is
   ready. That reading is the next change of lane P. The cell's static runtime Deployment (DEC-1013)
   keeps naming them by flag.

## Rationale

One source for the deployment: the journal and the documents it names. The manager stays a
starter of processes that passes ids, and cannot start a runtime against a connection the
deployment does not name.

## Alternatives considered

- **The manager passes `--connection` and `--owner`.** Its resolver would duplicate what the
  mandate document holds, and a stale copy could start a runtime against the wrong connection.
