# DEC-497: every reference suite declares the crates it drives, and a mutation run uses the suites that reach what it mutates

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-07 (UTC) |
| **Decided by** | The merge coordinator (agent), under DEC-79: a reversible engineering decision about the gate's own reach and cost, which the founder may overturn |
| **Story or claim** | E7-19 follow-up to [#644](https://github.com/kunwarshivam/mandate/pull/644), round 2 finding 1; [#652](https://github.com/kunwarshivam/mandate/pull/652) review rounds 1 and 2; ES-11's mutation gate, DEC-137, DEC-139, DEC-253, DEC-464's ten-minute budget |

## Decision

1. **Every reference suite declares the crates it drives**, in `crates/mandate-refcases/oracles.toml`:
   one entry per `crates/mandate-refcases/tests/<name>.rs`, naming the workspace crates that suite
   calls. Only the crates it calls: an entry says nothing about which call reaches which layer.
2. **A suite judges the crates under the ones it drives, from cargo's own graph.** A test that
   exercises a crate exercises everything that crate is built on, so a suite driving
   `mandate-journal` judges mutants of `mandate-canon`, `mandate-time` and `mandate-num` as well,
   with nothing written down. `workspace_closure` in `xtask/src/main.rs` computes the transitive
   workspace dependencies of each package from `cargo metadata`.
3. **A mutation run executes the suites that reach the packages it mutates.**
   `cargo xtask ci mutants` takes the union of the suites whose closure contains any mutated
   package, adds `--test-package=mandate-refcases` and the nextest filter
   `package(<mutated>) | … | binary(<suite>) | …`, and so runs every test the mutated packages own
   plus exactly those suites. With no suite reaching any of them the run is what it was.
4. **A suite the change edits runs whatever it declares**, so a new or reworked suite judges the
   mutants of the change that writes it, before its entry has been through a review.
5. **A suite the change deleted names no binary.** Only paths that still exist are collected: a
   deleted suite would contribute a `binary(<name>)` term matching nothing, and could leave a
   filter that selects no test at all, which DEC-139 then reports as a mutated package no live
   test judges.
6. **`cargo xtask oracles`, which `cargo xtask ci lint` runs, holds the table to the suites**:
   every suite file has an entry, every entry names a suite that exists and workspace packages
   that exist, and no entry is empty. A suite cannot join the harness without saying what it
   drives.
7. **The rule is `external_oracles` in `xtask/src/main.rs`,** a pure function with its own unit
   test, `the_external_oracle_runs_for_the_suites_that_judge_the_mutated_packages`, beside
   `every_reference_suite_declares_the_packages_it_judges` and
   `a_suite_judges_the_crates_under_the_ones_it_drives`, which read the real table and the real
   dependency graph.

## Rationale

A mutant is judged only by the tests cargo-mutants runs, and cargo-mutants runs the tests of the
mutated package. Several crates' oracles are not there: they live in `mandate-refcases`, a package
the mutated crate does not depend on, so nothing discovers them. E7-19 showed the hole directly —
`validate_config_artifacts` replaced by `Ok(())` was caught only by two `production_config_refs`
cases, and the gate as it stood never ran them.

The first fix for that, and this decision's first shape, keyed the choice on the diff: run a suite
when the change edits it. #652's review refused it, rightly. DEC-77 lands the tests and the
implementation of a story in two PRs, so an implementation PR legitimately changes only
`crates/mandate-journal/src` and edits no suite; under the diff rule its mutants were judged
without the one oracle that could catch them, which is the DEC-79 zero-missed-mutants assurance
quietly not holding on a safety-critical path. "The paved path usually edits the suite too" is not
an assurance.

What a run needs follows from what it mutates, so that is what the gate now reads. The table makes
the relation explicit and reviewable where the dependency graph cannot carry it: the harness
depends on the core, never the reverse, so nothing in Cargo's graph says which suite covers which
crate. `cargo xtask oracles` keeps it from rotting on the side that silently loses coverage — a
suite with no entry is an error, so a new suite must declare itself.

The first table asked each entry to name every package the suite can fail on, "indirectly
included", and #652's second review found two entries already wrong by that rule: `agent_stream`
and `asset_id` both call `Draft::parse`, which validates timestamps through
`mandate_time::UtcNanos::parse`, and `agent_stream` generates malformed timestamps on purpose, so
a `mandate-time` mutant escaped the very suites written to catch it. The finding is not two typos.
Asking a human or an agent to trace, per suite, which call reaches which crate is the kind of
audit that is wrong the day it is written and wronger every month after, and its failures are
silent. So the entry now claims only what a suite calls, which its own header already says, and
cargo's graph supplies the rest. A test that exercises a crate exercises what that crate is built
on; that is not a judgement call, and it cannot rot.

The closure over-selects, deliberately. A `mandate-num` mutation now reaches every suite, since
every crate is built on it, and pays the whole 62 seconds. That is the correct answer — every
suite can fail on a `mandate-num` bug — and it falls on the layer-0 crates, which change rarely.

Naming the whole of `mandate-refcases` instead would be sound with no table at all, and was tried:
it makes every mutant of every PR pay the whole harness. Measured at `d8b99df`, on this four-core
box with two test threads, the suite is 62 seconds per mutant, and it is concentrated in three of
the twelve: `mandate_harness` 19.7s, `mandate_lifecycle_harness` 13.5s, `refcases` 10.7s, against
`production_config_refs` 0.34s, `risk_state` 0.32s, `control_stream` 0.36s. A `mandate-journal`
change now pays `refcases` and the five journal suites, about 13 seconds a mutant, and never the
two mandate harnesses that judge nothing of it. On CI's two-core runners that difference is the
one between fitting DEC-464's ten minutes and the shard timeouts the first shape hit.

The residual risk is an entry that leaves out a crate the suite calls directly. That is a much
smaller surface than the first table's: it is one line beside the suite's own header, which says
what it drives, and the `oracles` check refuses a suite that declares nothing at all. The cost of
naming one crate too many is bounded by that suite's own run time, so an entry should err wide.

## Alternatives considered

- **Key the suites on the change's diff** (this decision's first shape). Cheap and wrong: an
  implementation PR that edits no suite runs no external oracle, which DEC-77 makes an ordinary
  case rather than an edge one.
- **Name `mandate-refcases` on every mutation run.** Sound and needs no table, but it charges every
  mutant of every PR the three harness suites that are most of the run time and none of most
  changes' oracle, and it timed the CI shards out.
- **Derive the mapping from the suites' source, by the crate names each file mentions.** Automatic,
  but unsound in the direction that matters: a suite that reaches a crate only through
  `mandate_refcases`'s own harness mentions it nowhere, so the derivation would quietly drop
  exactly the indirect coverage the table exists to record.
- **Keep the declaration exhaustive and audit the entries** (#652 round 2's literal fix: add
  `mandate-time` and `mandate-canon` to the two entries, then trace every suite that reaches
  `Draft::parse`). It closes the two instances and leaves the rule that produced them, whose
  failures are silent and whose correctness decays with every call a crate adds. The closure
  removes the question instead.
- **Make the mutated crates depend on `mandate-refcases` so cargo-mutants finds the oracles.**
  Refused: it inverts the layering (`xtask/layers.toml` puts the harness above the core) and would
  put a test harness in the dependency graph of shipped crates.
- **Move the oracles into each crate's own tests.** The reference cases are one approved corpus
  read by one harness (DEC-253); splitting it per crate would duplicate the corpus and lose the
  single place that proves every case is covered.
