# DEC-1014: The runtime process folds the account stream its connection's establishment names

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and DEC-176; it lets the runtime process take the account stream's facts the shell already folds, every reading it takes is the stricter one, and item 6 tightens the core's startup hold) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (builder of lane P3 of the managed-cells plan, DEC-967, DEC-990), under DEC-79 and DEC-176 |
| **Story or claim** | E21-30 slice 1; trading spec §11 (the startup hold); journal spec §2, §9.8; DEC-131 items 13 and 22; DEC-914 item 2; DEC-1012 |

## Context

`mandate-daemon`'s runtime process (DEC-1012) read the control and clock streams and never the
account stream. The core's startup hold lifts only on a clean `ReconciliationRun` folded from the
account stream (DEC-131 item 13), so its effective mode stayed `paused` for good: no research run
could start and no proposal could be made. The executor's `AgentModeApplied`, and every other
account-stream fact the shell's copy fold takes, never reached it either.

The account stream is `acct:{workspace}:{account_ref}`, and `account_ref` is not the connection id:
an account stream belongs to the connection whose version-2 `ConnectionEstablished` on the control
stream names its `account_ref` (journal spec §9.8).

## Decision

1. **Each pass folds the account stream after the control stream and before the clock stream.**
   The rows past the core's head for that stream are folded with `mandate_runtime::fold`, as the
   shell folds them, so a row is folded once and the core's own sequence check refuses a gap. The
   next input the core takes (each pass's tick) settles the startup hold and journals the mode
   change. The owner's kill switch is still read first (ES-06).
2. **The start folds it too, before `Input::Started`,** as the shell's open replays the account
   stream before the start, so the hold is taken or not on the whole fold.
3. **The account is the one the latest version-2 `ConnectionEstablished` of the deployment's
   connection, in the process's environment, names.** Another connection's establishment, another
   environment's, and a version-1 record name nothing. Until one names it, the process follows no
   account, and the hold stays. A later `ConnectionRevoked` is not read: a revoked connection's
   executor is torn down and writes nothing more, and what its account stream already holds can
   only tighten the runtime or lift its hold on a reconciliation the executor did run.
4. **It fails closed.**
   - A start that cannot read the control stream, or the account stream it names, is never ready.
   - A pass that cannot read the account stream folds nothing from it and still hands the control
     stream and the tick, so neither the owner's kill switch (ES-06) nor a risk exit or deadline
     waits on it (`AGENTS.md` rule 13). An opening decided on a mode that may be stale still meets
     the executor's gate, which applies the account's restrictions itself (rule 1).
   - A record the core cannot fold, or an account row journaled for another environment, stops
     the process (DEC-85, `AGENTS.md` rule 8), as an unfoldable control or agent row already does.
   - A running process never changes the account it follows. A later establishment that names
     another account stops it, and the next process follows the new account from its start.
5. **The runtime only reads the account stream.** It never takes ownership of it or writes it. The
   account's executor stays its single writer (journal spec §2).
6. **A startup hold waits for a reconciliation after the start.** When `Input::Started` takes the
   hold, the core forgets the reconciliation its replay folded, so only a clean `ReconciliationRun`
   folded after that start lifts it. The hold is taken exactly when that earlier reconciliation was
   judged not enough (an intent outstanding, or a submission after it), so it cannot be what lifts
   it. Without this, `settle_startup_hold`'s looser test (no "nothing outstanding") would lift the
   hold on the next input after a restart with an intent still outstanding. The shell never hit
   this, because it runs a fresh reconciliation right after `Started`, and its outcomes are
   unchanged. This tightens `mandate-runtime` and loosens nothing.
   A runtime process restarted while held therefore waits for the executor's next clean
   reconciliation, so the executor process (E21-30 slice 2) must reconcile periodically or when a
   runtime restarts. That is one of its acceptance criteria, with a test of a copied
   `ConnectionEstablished` on the account stream (item 7).
7. **The executor's connection records still stop the process.** The account stream will carry
   the executor's `ConnectionStateChanged` and `ConnectionCredentialRefreshed` and its copies of
   `ConnectionEstablished` and `ConnectionCredentialRotated` (journal spec §9.8). The core still
   refuses them `not_interpreted`, as DEC-969 item 5 keeps them until their writer exists, so a
   runtime that meets one fails closed. The executor process (E21-30 slice 2), their first writer,
   decides how the runtime folds them. Connections spec §9 already says a connection's state
   reaches the mode machine only through the executor's `AccountRestrictionChanged` and
   `AgentModeApplied`.

## Rationale

The shell's in-process run already folds the account stream beside the agent stream. The runtime
process is the same core on the journal alone (DEC-1012), so it takes the same facts the same way.
What the shell got from its sequencing, a reconciliation run after every start, the runtime
process cannot: its executor reconciles on its own schedule. Item 6 puts that ordering into the
core instead, so neither process can lift a hold on knowledge from before the start.

## Alternatives considered

- **A `--account` flag.** One more thing to keep in step with the journal, and a wrong value would
  let another account's reconciliation lift this agent's hold.
- **Hand the account rows as `Input::Journal`, as the control rows are.** The core folds account
  facts rather than taking them as input, and refuses a row it has already folded, so handing the
  stream whole each pass would stop the process.
- **Follow a new account without a restart.** The core keeps one reconciliation state, so an old
  account's reconciliation could lift the hold for the new one.
- **Fold the executor's connection records as inert here.** That supersedes DEC-969 item 5 from a
  lane that does not write them; their writer's lane decides it (item 7).

## Consequences

- In the local cell nothing changes yet: the cell's demo deployment's connection is never
  established on the control stream, so the runtime follows no account and stays held.
- Research (lane I2) and trading can run in the process once the executor reconciles after the
  runtime's start, and once item 7's records are folded or absent.
