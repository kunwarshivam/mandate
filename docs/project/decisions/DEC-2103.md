## Context

The demo cell's owner should approve an ask in web/ (`cargo xtask cell demo`, step 4). The
server's step-up port verifies nothing yet (DEC-2101 item 2), so every grant through the API is
refused. `mandate_passkey::stepup` holds the core on main: `issue_challenge` behind `authorize`'s
`TenantContext` (DEC-665), `Presentation::new` (DEC-649), and `consume`. Workspace API spec §3.6
names the route that issues a challenge, `POST /v1/workspaces/{ws}/step-up/challenges` with
`{action: {kind, digest}}`, but not its checks, its answer, where a challenge is kept, or whether a
retry issues another.

## Decision

1. **The route.** `POST /v1/workspaces/{ws}/step-up/challenges`, operation name
   `step_up_challenge` for §3.4's derivation. The checks run in DEC-1007 item 1's order: the
   session (the one 401, or `reduction_only`, identity spec §7.2 step 1 and §7.3), the CSRF mark (403), then
   `Idempotency-Key` (422 `invalid` when missing, repeated, or malformed), the body, decoded
   strictly (`commands/step-up-challenge-request`; 422), and authorization by the §4.2 row the
   kind needs, the one `issue_challenge` checks (identity spec §7.2 step 1, DEC-665 item 2). A
   principal that may not perform the action gets that row's refusal and no challenge. The two
   kinds whose row is `own` (`credential_enrol`, `notification_address`) are answered the one 404
   until their own routes land: the server authorizes at the workspace's scope only, and an
   `own` row's context comes from `PrincipalContext::into_tenant`, which those routes will use.
2. **The challenge id is the key's.** The challenge id is §3.4's derived ULID for the key, the
   operation, the principal, and the workspace. A retry with the same key and the same action
   answers the challenge already issued, unchanged; the same key with another action is 409
   `idempotency_conflict`. A challenge is never journaled when issued: identity spec §7.2 step 5
   records it once, as the evidence of the event it authorizes.
3. **The answer.** `201` with `commands/step-up-challenge`: `challenge_id`, `webauthn_challenge`
   (the base64url, unpadded, of `ChallengeRecord::webauthn_challenge`'s 32 bytes, identity spec
   §7.2 step 2), `action` as requested, `issued_at` (the server's clock at receipt), and
   `expires_at` (300 s later), with the envelope's `api_version` and `build` and an empty `as_of`.
   It carries no workspace or principal id: both are the session's. It is sent with
   `Cache-Control: no-store`, and the server never logs its body.
4. **Live is refused, after the row.** Once the row is granted, a workspace whose control
   stream is `live` is refused 409
   `live_unavailable` (§3.6: the API refuses every `live` step-up until counsel signs off).
5. **Where a challenge is kept.** The server keeps issued challenges in its own memory, at most
   32 unexpired per principal and 4,096 in all; an expired one is dropped when the store is next
   touched. A request past either bound is refused 429 `rate_limited`, and no challenge is issued.
   A restart or a second replica loses or does not hold a challenge, and a step-up whose challenge
   is not held counts as missing (`step_up_missing`), so a lost challenge can only refuse a step-up, never pass one. A
   challenge is used once per workspace, judged from the control stream's recorded evidence, not
   from this store (API-17, DEC-173 item 3).
6. **What this changes for verification.** Nothing yet: the port stays `Unbound` until a later
   E9-4 slice binds a passkey verifier over this store, and the raw-assertion carriage that slice
   needs (identity spec §7.2 steps 4 and 5) is decided with it.
7. **Which methods the API verifies (decided by the founder, DEC-2605 row 5).** Asked "when
   you approve a paper-trading grant in the web app, may the API accept a step-up confirmed in
   the CLI (`cli_confirm`) instead of your passkey?", the founder answered "Allow cli_confirm
   too". The API verifies `passkey`, and `cli_confirm` within these bounds, each a tightening of
   that answer (DEC-2605 item 3), and each refused with the code named:
   - **A paper grant only.** The action is `approve`; `cli_confirm` for any other kind is
     `step_up_method`. The workspace is paper by every control-stream row, not the first
     (DEC-1143 item 2); a `live` workspace is refused `live_unavailable` before any evidence is
     read (item 4), and `cli_confirm` in `live` is `step_up_method` (identity spec §7.3).
   - **Bound to a challenge this server issued.** The evidence names a challenge from item 1's
     route for the same principal, workspace, action kind, and action digest; another is
     `step_up_mismatch`, and one the server does not hold is `step_up_missing` (item 5).
   - **Within the challenge's 300 s.** Confirmed after `expires_at`, or before `issued_at`, is
     `step_up_stale`.
   - **Used once.** A challenge already recorded as evidence on the control stream is
     `step_up_reused` (item 5; API-17).
   - **Confirmed in the CLI, not in the browser.** The confirmation comes from the CLI, signed in
     as the same principal, never from the web session that asked for the challenge: identity
     spec §7.3 says recent sign-in is not step-up, so a confirmation typed into that session
     proves only the session and is `step_up_missing`.
   How the CLI's confirmation reaches the server is decided with the verifier slice (item 6),
   which lands each bound above with its own pending test first. Until it lands the port stays
   `Unbound`, and every grant through the API is still refused.
8. **How a new request schema lands (a process reading, agent-accepted).** A schema change
   ships without code (ES-22, the spec guard), and `mandate-api`'s
   `the_decoders_cover_every_request_schema_and_request_type` requires every
   `commands/*-request` schema to have a request type and a decoder row, so neither can land
   first. The test gains a const, `SCHEMA_AHEAD_OF_TYPE`: a stem listed there has no request type
   and no row, and every other request schema still needs both. A new request shape lands in three
   changes: the stem is listed, then its schema lands, then its type and row land and empty the
   list. Every check the test made before still holds for every unlisted stem, and a listed stem
   that gains its type fails the test until it is removed, so the list cannot outlive the type.
   A listed stem with neither a schema nor a type is permitted, as between the first change and
   the second.
   The list holds `step-up-challenge-request` from the first change until the third.
9. **The example challenges are allowed in gitleaks, by exact value (a DEC-176 reading).**
   `generic-api-key` reads the examples' `webauthn_challenge` strings as keys. They are fixed
   base64url of example bytes, and a WebAuthn challenge is public by design. `.gitleaks.toml`
   allows exactly those five values, and only in the challenge response's example files, as
   [DEC-2603](process.md#dec-2603) allows its fixtures; the same value elsewhere, or another value there,
   is still reported. A spec PR carries no code, so xtask's `gitleaks_plants` gains the three
   cases (allowed there, reported in a stray file, a near miss reported there) in the first code
   change after it.

## Rationale

Items 1 to 4 apply the routes' existing order and §3.4's derivation to a call the spec names but
does not detail; each refuses at least what the spec refuses. Deriving the id from the key makes a
retried request harmless without a second store. Item 5 keeps an unjournaled, short-lived record
where the only failure is a refused step-up (rule 3), and leaves single use to the journal, which
already holds every recorded assertion.

## Alternatives considered

- **Journal the challenge when issued.** Rejected for now: no event type exists for it, and
  identity spec §7.2 step 5 records the challenge with the action it authorizes.
- **A random challenge id, no key.** Rejected: every retry would issue a new challenge, and
  §3.4 asks a key of every mutating call.
- **Accept `cli_confirm` typed into the web session that asked.** Rejected under item 7: it
  proves only the session (identity spec §7.3). The founder's answer allows a confirmation made
  in the CLI.
- **Keep `passkey` only.** Item 7's former conservative course, loosened by the founder
  (DEC-2605 row 5).
