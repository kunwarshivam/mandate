## Context

Identity spec §6.4 route 2 keeps pause and the kill switch reachable when the identity provider is
down: a member opens a reduction-only session with a passkey the workspace deployment already holds.
DEC-816 item 6 names the two routes and the no-oracle rule, and DEC-834 (the founder's) sets how the
limits treat a valid key. The workspace API listed both routes only as owed: no request or response
shape, no cookie, no limit numbers, and no meaning for "address" or "device" on a route that has no
session yet.

## Decision

1. **Shapes.** `POST /v1/reduction-sessions/challenges` takes an empty object and answers `201`
   with `{challenge_id, webauthn_challenge, rp_id, issued_at, expires_at}`: 32 random bytes, 300 s.
   `POST /v1/reduction-sessions` takes `{challenge_id, passkey_id, authenticator_data,
   client_data_json, signature}`, in [DEC-2115](DEC-2115.md)'s `PasskeyId` and `Base64url` terms,
   and answers `201` with `{kind: "reduction_only", expires_at, workspaces}` and the session cookie.
   Both are browser-only, as `POST /v1/sessions` is. Neither answer names a principal, passkey,
   member, or token, and the challenge names no workspace and lists no passkey to allow. The
   challenge is held in memory, consumed on its first presentation, and never journaled. Opening the
   session journals nothing, as opening a browser session does not.
2. **The session.** It is the browser session record, of kind `reduction_only`, for the passkey's
   member, counted toward that principal's 16. It lives 15 minutes from its opening, absolute, with
   no idle limit, and is never refreshed, extended, or turned into a full session: the refresh route
   refuses it `reduction_only` and keeps it.
3. **Limits.**
   - **Challenges:** at most 4 outstanding per device, 32 per address, and 4,096 in all. Past any
     of them the route answers 429 `rate_limited` with `Retry-After`. A challenge counts only while
     it is outstanding (DEC-834).
   - **Failed assertions:** at most 10 per device and 100 per address in any 15 minutes. Over
     either, the route still judges every request whose challenge is outstanding, and a request
     naming none fails without verifying. An assertion that verifies is never refused for a limit
     (DEC-834).
4. **Address and device.**
   - **Address:** the TCP peer of the API listener. When the peer is one the deployment lists in
     `MANDATE_API_INGRESS_PEERS`, it is the last `X-Forwarded-For` entry instead, the one that
     ingress appended. Any other peer's forwarded header is ignored, as DEC-822 item 4 requires
     for lockout.
   - **Device:** the `__Host-mandate_device` cookie, 32 random bytes the challenge route sets,
     `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, 30 days. It carries no workspace, member,
     principal, passkey or session. The server never links it to one, keeps only its digest, and
     keeps that only while it counts something.
5. **The one 401.** Every refusal of the opening route after the browser check is 401
   `unauthenticated` with the same body and headers, and no cookie set or cleared. An unknown
   passkey is judged against a fixed decoy key of the same algorithm, so timing tells no refusal
   apart.
6. **What verifies.**
   - The passkey is found by its id among those the control stream holds enrolled and not removed,
     so a discoverable passkey and a non-discoverable one both serve, as DEC-833 keeps them. Its
     member must hold an `active` membership.
   - A subject the provider refused since the member's last sign-in is refused.
   - An enrolment cool-off does not bar the route. The cool-off guards step-up, which can add
     risk, while this session reaches only pause and the kill switch.
7. **Reach.** The session covers each workspace of the member's `active` memberships when it opens,
   with the roles in effect then as its snapshot. It authorizes pause and the kill switch only, and
   only where those roles grant them. Every other route is refused `reduction_only`: owner exits,
   resume, Stop, approvals, confirm, deploy, step-up, enrolment, and every workspace read. `GET
   /v1/me/session` answers it with `kind: "reduction_only"` and the same `workspaces`.

## Rationale

The shapes reuse what the passkey routes already define, so the web app runs one WebAuthn ceremony
for both. A route reached before anyone is known must not become an oracle. That is why the
challenge names nothing, every failure is one answer, and the device key is random and linked to
nothing.

The numbers leave a member room for a few retries on one device. They hold an address-wide flood
to a small, fixed amount of memory and verification. DEC-834 keeps a valid key from ever being
refused.

Reading the address from a forwarded header only when the peer is the named ingress keeps the
address limit per client behind the cell's ingress. It stops anyone else from choosing their own
address. Without the setting, every client behind one ingress shares the TCP peer's budget, so a
flood from anywhere can hold the address limit. That widens the residual DEC-834 states from one
network to every network. A deployment behind an ingress therefore sets `MANDATE_API_INGRESS_PEERS`;
the workspace chart's value for it is owed with E9-1's implementation.

Item 6's cool-off reading follows rule 13: reducing risk never needs approval. The cool-off is
defined for step-up (identity spec §7).

## Alternatives considered

- **Answer the challenge route's over-limit with the one 401.** Refused: the route holds nothing
  to protect, and 429 with `Retry-After` lets the web app tell the member when to try again.
- **Sign the device cookie.** Refused: a random 32-byte key cannot be guessed. A signature would
  stop no one from minting fresh keys, and the address limit still binds those.
- **Bar passkeys in their enrolment cool-off.** Refused for now: it would deny a newly enrolled
  member the outage kill switch for 24 hours, against rule 13. If the founder wants the cool-off
  here, that is a narrowing for them to take.
- **Let the session reach owner exits.** Refused: identity spec §6.4 and DEC-816 item 6 allow
  pause and the kill switch only, and exits need step-up (ID-4).
