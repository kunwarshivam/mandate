# DEC-640: Interim reading of DEC-437 item 15: the managed sign-in provider is one OIDC issuer verified by asymmetric keys only, and workspace services are the WebAuthn relying party

## Decision

While DEC-437 item 15 stays Proposed, code is written to this reading:

1. **One OIDC issuer.** The managed sign-in provider (Supabase Auth, DEC-211) is one OIDC issuer
   among those an organization may configure. Workspace services verify its tokens against the
   keys the issuer publishes (its JWKS), selected by `kid` from the configured issuer only.
2. **Asymmetric algorithms only.** A token is accepted only when signed with RS256, PS256, ES256,
   or EdDSA, and only when the selected key's own type matches that algorithm. `none`, every
   `HS*` algorithm, and a key the token carries itself (`jwk`, `jku`, `x5u`, `x5c` headers) are
   refused, whatever the token's header says.
3. **Workspace services are the WebAuthn relying party** for passkey sign-in, step-up (§7), and
   the risk-reduction path's route 2 (§6.4). They hold each member's passkey public keys and
   verify assertions themselves; no passkey held only by the sign-in provider presents step-up.
4. **No spending.** Nothing here buys a plan or a service; a paid plan stays item 15's question.
   Item 15's interim holds: every environment stays `paper`, and a `live` step-up is refused
   (`live_unavailable`, workspace API §3.6).
5. **Tests** use an in-memory issuer and a software authenticator only (identity spec §1.3).

## Rationale

The code for E9-1 and E9-4 needs to know which tokens it verifies and who holds the passkeys. The
spec's §6.1 already has workspace services act as the relying party for step-up and §6.4; this
reading extends that to passkey sign-in, so a member enrols a passkey once, with the workspace,
and nothing hosted sits in the core path (HLD §4, ID-10). Refusing symmetric and embedded keys
closes the `alg` confusion attacks of identity spec §13's OIDC row.

## Alternatives considered

- **Wait for item 15.** Blocks E9-1 and every lane that codes against sign-in.
- **Verify with whatever algorithm the header names.** The classic `none` and HS256-with-the-public-key attacks.
- **Leave passkey sign-in with the provider.** Two enrolments, and sign-in would depend on a hosted service.
