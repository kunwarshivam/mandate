## Decision

1. **One OIDC issuer.** The managed sign-in provider (Supabase Auth, DEC-211; the free tier, so
   no spending) is one OIDC issuer among those an organization may configure. Workspace services
   verify its tokens against the keys the issuer publishes (its JWKS), selected by `kid` from the
   configured issuer only.
2. **Asymmetric algorithms only.** For every configured OIDC issuer, a token is accepted only when
   signed with RS256, PS256, ES256, or EdDSA, and only when the selected key's own type matches
   that algorithm. `none`, every `HS*` algorithm, and a key the token carries itself (`jwk`,
   `jku`, `x5u`, `x5c` headers) are refused, whatever the token's header says. Each issuer's
   configuration may narrow the list further.
3. **The managed issuer's configuration.** These are public values, and configuration supplies
   them, not code. The repository never holds a key, a secret, or a token.
   - The issuer has the form `https://<ref>.supabase.co/auth/v1`. Today it is
     `https://wyyxngmblqqokcvraflx.supabase.co/auth/v1`; the ref came from the founder through
     the lane lead.
   - Its keys are at `<issuer>/.well-known/jwks.json`. As the coordinator observed it on
     2026-10-08, it published one EC P-256 signing key; that is an observation, not a
     requirement.
   - The audience is `authenticated`.
   - It accepts **ES256 only**. This narrows item 2's list for this issuer, and it is the
     agent's own narrowing, not DEC-820's.
4. **Workspace services are the WebAuthn relying party** for step-up (§7) and the
   risk-reduction path's route 2 (§6.4), as DEC-820 item 2 decides, and, by this file's own
   reading, for passkey sign-in too. They hold each member's passkey public keys and verify
   assertions themselves; no passkey held only by the sign-in provider presents step-up.
   - **Per-deployment configuration.** The RP ID and the one accepted origin are configuration,
     never code, like item 3's values. Each deployment accepts exactly one origin, and its RP ID
     matches that origin's host.
   - **The managed deployment's values.** RP ID `app.owlhead.ai`, origin exactly
     `https://app.owlhead.ai`; the API is at `api.owlhead.ai`. DEC-820 item 1 makes `owlhead.ai`
     the base of the RP ID; `app.owlhead.ai` narrows it, a tightening DEC-820 leaves open, so
     passkeys are scoped to the web app alone.
   - **Hybrid and on-prem deployments** configure their own RP ID and origin on their own domain.
5. **Environments are not item 15's.** Item 15 chooses the provider. A `live` step-up stays
   refused for the reasons that already hold (workspace API §3.5 `live_unavailable`, `AGENTS.md`
   rule 8), not because of the provider.
6. **Tests** use only an in-memory issuer and a software authenticator (identity spec §1.3). No
   test reaches the managed issuer.

## Rationale

The code for E9-1 and E9-4 needs to know which tokens it verifies and who holds the passkeys.
This file records the exact values and the verifier's rules, so every lane builds the same thing.
A member enrols a passkey once, with the workspace, and nothing hosted sits in the core path
(HLD §4, ID-10). Refusing symmetric and embedded keys closes the `alg` confusion attacks in the
OIDC row of identity spec §13.

## Alternatives considered

- **Verify with whatever algorithm the token's header names.** This allows the classic `none`
  attack and the HS256-with-the-public-key attack.
- **RP ID `owlhead.ai`.** Any subdomain could then use the passkeys. The narrower ID costs nothing
  today.
- **Leave passkey sign-in with the provider.** Members would enrol twice, and sign-in would depend
  on a hosted service.
