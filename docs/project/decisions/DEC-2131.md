# DEC-2131: `MandateConfirmed` and `AgentDeployed` version 3 carry the step-up evidence rule 253 reads

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79 and DEC-176; it adds members and a writer rule, and leaves rule 253 as strict as it is) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | `claude-code` (coordinator) |
| **Story or claim** | E9-4 S5; claim #759; [DEC-2128](DEC-2128.md) item 3; [journal spec](../../specs/journal.md) §9.9, §9.24 and §9.32 rule 253; the review of #2475 |

## Context

[DEC-2128](DEC-2128.md) item 3 has a confirmation or a deployment under passkey step-up append its
one control-stream event (`MandateConfirmed`, or `AgentDeployed`) and the `StepUpAsserted` in one
batch, as journal spec §9.32 rule 253 names. Rule 253 reads the authorized event's
`payload.step_up`: its `method` must be `passkey` and its `assertion_id` the assertion's
`challenge`. §9.32 assumed that "no event that carries step-up changes", but `MandateConfirmed`
(versions 1 and 2) and `AgentDeployed` (versions 1 and 2) carry no `step_up` member: their step-up
evidence sits in the record artifact `record_ref` names. So `append` refuses every such batch at
`payload.step_up`, and #2475's confirmation could never commit on a real journal. Its tests passed
because the test journal never runs the batch rule.

Rule 253 cannot read the evidence through `record_ref` instead: the batch rule is pure, judged over
the drafts alone, and opens no artifact. Dropping the `payload.step_up` clause for these two events
would leave an assertion bound to its event by causation and actor alone, which weakens a safety
rule and is the founder's (DEC-79).

## Decision

1. **`MandateConfirmed` version 3**: version 2's members, then `step_up`, §9.2's
   `{assertion_id, authenticated_at, method}`, never `null`. Rules 18, 77 and 78 and §9.2's
   mapping apply to it as to version 2.
2. **`AgentDeployed` version 3**: version 2's members, then `step_up` as in item 1, never `null`.
   Rules 22, 200 and 201 and §9.2's mapping apply to it as to version 2.
3. **Who writes which version.** The workspace API writes version 3 exactly when it commits the
   event under step-up, with the evidence it judged, which is also the evidence its record
   artifact holds; otherwise it writes version 2 as today. The CLI is unchanged. Rule 253 is
   unchanged, so a passkey `StepUpAsserted` follows only a version-3 record whose `step_up` names
   its challenge.
4. **Readers.** Every reader of version 2 reads version 3 as version 2 and ignores `step_up`; the
   evidence it needs is still the record's. A reader that has not moved refuses version 3 as an
   unknown version, so it fails closed: for `AgentDeployed`, the deployment manager starts nothing
   for it.
5. **Order of the changes.**
   1. The journal spec (v0.84, rules 267 and 268 for the two versions' consistency), the
      reference implementation and its vectors, and `mandate-journal`'s registry, in one change,
      since the Rust tests reproduce the vectors.
   2. The readers, tests first: the journal mapping in `mandate-spec`, the deployment manager, the
      executor's follow, the daemon, the API's reads, and the paper run.
   3. #2475 writes `MandateConfirmed` version 3 under passkey step-up, and its commit test runs the
      route's drafts through the journal's batch check. The test journal runs the batch check on
      every append, so no batch rule can again pass a route's tests and fail on the real journal.
   4. DEC-2128's deploy slice writes `AgentDeployed` version 3 the same way.

## Rationale

- Items 1 and 2 follow `ConnectionRequested` and `DisclosureAccepted`, which already carry their
  step-up evidence as a member, so rule 253 reads every authorized event the same way.
- Items 3 and 4 leave every record written today valid and unchanged (§8), and a reader that has
  not moved fails closed.
- Rule 253 stays as strict as it is: no assertion commits apart from an event that names it.
