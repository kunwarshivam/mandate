## Context

Mandate spec §8.6 removes an instrument at once when its thesis's invalidation condition holds
(MI-19). The condition is the model's own text, so the harness takes the verdict from the research
call's response (agent harness spec §6.7). The executor writes the removal as `UniverseChanged`
(`removed`, `thesis_invalidated`), whose `causation_id` must name a journaled cause. No record
carried one, so agent harness spec §6.2 keeps every research run from starting (HI-19).

Backlog E19-5 asks for a journal spec change first:
- the agent-stream invalidation verdict and the executor's `UniverseChanged` (`thesis_invalidated`)
  copy from it, with vectors;
- DEC-433 item 19's revoked source covered too;
- `exits_only` runs review-only;
- an invalidation never admits, never adds risk, and is journaled before the removal;
- MI-19 and HI-19 hold under a fuzz of random invalidations and renewals.

Journal spec v0.46 §9.19 (DEC-998) already journals each candidate's verdict in the call record's
`verdicts` (rule 151). A `judged` invalidation verdict hands the candidate "to its invalidation
record (E19-5, not yet catalogued)".

The versions in use when this change was drafted are v0.47, §9.20, and rule 164 (DEC-1010). This
change takes v0.49, §9.22, and rules 184 to 187.

## Decision

1. **The record.** `ThesisInvalidated`, on the agent stream, at schema version 1, with required
   `config_refs` `mandate_version`. Its members:
   - `thesis_id`, `lineage_id`, and `instrument_id`, as the admitting thesis record states them;
   - `cause`, either `model` or `source_revoked`;
   - `candidate` (`integer?`), the verdict's index in the call record's `verdicts`;
   - `evidence` (`[text]`), the item ids the output cited, as given;
   - `source` (`text?`), the revoked source.

   It is a separate event, not a member of the call record, for two reasons. A revoked source
   invalidates with no call. And the executor's copy needs one record per removal to name as its
   cause, as it names `ThesisProposed` for an admission. `mandate_version` is required because the
   executor's `UniverseChanged` requires it, and the record states which mandate version the
   removal ran under. No `model_version` is required: a model's invalidation names its call record,
   which binds the model (rule 146).
2. **Rule 184, the pairing.**
   - A `model` invalidation names its verdict (`candidate`) and no source.
   - A `source_revoked` one names a source, no verdict, and no evidence.
   - Both name a cause in `causation_id`.

   Each clause is reported at its member, the first that fails, in a fixed order.
3. **Rule 185.** The actor is an `agent`: the runtime that owns the stream, as rule 147 for the call
   record.
4. **Rule 186, a batch rule** like rules 10 and 84.
   - A `model` invalidation names a `ModelInvocationRecorded` earlier in its batch. That record's
     verdict at `candidate` must be an `invalidation` with result `judged`, and no earlier record
     of the batch may name the same verdict.
   - Every judged invalidation verdict of a call record in the batch must be named by a later
     `ThesisInvalidated` of the batch.

   **A reading beyond the brief, which refuses more but no removal a correct writer makes:** the second clause makes the pairing
   exactly one record per judged verdict, so a dropped removal is refused at append rather than
   found by the verifier (HI-22). It refuses a call record with a judged invalidation verdict
   appended without its record. Nothing writes such a batch: no run starts before this record is
   registered (§6.2). The harness writes the call record, its thesis records, and its
   invalidations in one batch (DEC-1120 item 6), so the rule fits the writer.
5. **The `source_revoked` cause.** `causation_id` names the control stream's
   `ConfigSnapshotRegistered` of the first source-allowlist version that no longer lists `source`.
   The allowlist is versioned platform configuration registered that way (DEC-101, agent harness
   spec §8.4). No source-revocation event exists. The causation crosses streams, so `append` checks
   only that it is present (rule 184) and the verifier owns the rest.
6. **Rule 187, a stream rule** like rule 153. A `ThesisInvalidated` names a thesis that:
   - no earlier record of the stream invalidated;
   - an earlier `ThesisProposed` or `ThesisRevised` of the stream admitted, with the same
     `lineage_id` and `instrument_id`;
   - is the latest admitted thesis for its instrument on the stream.

   The first that fails is reported, each at its member. **A reading beyond the brief, which only
   refuses more:** the last clause refuses invalidating a thesis that a revision or a renewal has
   superseded. The new thesis would otherwise lose its instrument through its predecessor's verdict.
   Mandate spec §8.6 keeps a renewal and a revision as new theses that hold the instrument.
7. **The executor's copy.** §9.3 now says it outright:
   - for `thesis_invalidated`, `UniverseChanged`'s `causation_id` names the `ThesisInvalidated`;
   - the copy is written after the record is stored;
   - it has the same instrument, thesis, and lineage, and the stream's agent.

   §9.4's closing paragraph says the same, and §9.19's `verdicts` row names the record. The copy is
   on another stream, so no rule checks it at append; the verifier owns it, with the
   `source_revoked` cause's allowlist and the thesis's currency (not expired, retired, or removed),
   which the agent stream alone cannot show.
8. **What the record does not do.** It never admits: rule 31 already keeps `thesis_invalidated` a
   removal. It needs no approval or corroboration (`AGENTS.md` rule 2, agent harness spec §6.7). In
   `exits_only` a run is review-only and its invalidations are the only candidates it hands on, as
   agent harness spec §6.7 says. The record changes no envelope field.
9. **Vectors.** A generated `thesis_invalidation` section (`reference/journal/invalidation.py`) holds:
   - six base drafts;
   - 31 invalid drafts (every member type, rules 184 and 185, the catalogue's stream, version, and
     reference) and 5 valid drafts;
   - 15 batches for rule 186;
   - 17 agent streams for rule 187, each a list of `append` batches that each pass rule 186, with
     every call record passing rules 151 and 153.

   21 validator mutants and 9 vector mutants are each shown caught by their check. The vectors stay
   version 3.
10. **Agent harness spec.** §6.2's invalidation precondition now names the record, and holds once
    `mandate-journal` registers it. Also updated: §6.6's records row, §6.7's record bullet, §10's
    executor and journal bullets (§10.3), and §13 open question 4, now answered.
11. **One response that invalidates a thesis twice.** §6.7 now reads that invalidations are judged
    in response order, and an accepted one ends its thesis at once. So the second is
    `unknown_thesis`: it names no active thesis. It refuses only a duplicate of a removal already journaled. Without it the harness
    would judge both, and rule 187 would refuse the batch's second record, and with it the
    whole judging batch, including the call record.

12. **Invalidations are judged before theses, and journaled before them.** Refusing a removal is not
    risk-neutral, so the readings above must never refuse one a correct writer makes. Under a
    response-order reading they could: with thesis A active on X, one response that proposes B on X
    (a renewal, since A is active) and invalidates A would journal B first, then rule 187's current
    clause would refuse A's record, rule 186 would refuse the batch without it, and the invalidation
    would be lost, against MI-19 and HI-19. So agent harness spec §6.7 now says the harness judges a
    response's invalidations first, against the run's active theses, and its theses second, against
    those left; and journal spec §9.22 puts the `ThesisInvalidated` records after the call record and
    before its thesis records. B is then a new thesis in a new lineage, facing every admission check
    and the autonomy rules (mandate spec §8.5), and the removal happens first. This is safe: removal
    adds no risk and comes first, and B adds risk only through the checks any new thesis passes. The
    `verdicts` array keeps rule 151's index order; it is the record's order, not the judging order.
    **Residual, disclosed:** if `append` refuses a judging batch, that is a writer defect. Nothing in
    the batch is used, the runtime raises an operator alert, and the thesis stays active until a
    later run invalidates it again; it is never a silent drop.

## Attacks considered

- **A duplicate invalidation**, so one verdict removes twice or a second record churns the book. Rule
  186 refuses a second record of one verdict in a batch. Rule 187 refuses a second invalidation of
  one thesis on the stream, whatever its cause.
- **Invalidating a thesis never admitted**, or one the admission refused or ignored. Rule 187 needs
  an admitting record, with `admitted` `true`, earlier on the stream.
- **A substituted instrument or lineage.** The record could name a real thesis but another
  instrument, to remove a position the thesis never held. Rule 187 needs the admitting record's
  instrument and lineage, and the verifier checks the executor's copy against the record (§9.3).
- **A forged causation.** The record could name another event, a refused verdict, a thesis verdict,
  another call's verdict, or no verdict. Rule 186 refuses each. A `source_revoked` record's
  allowlist link crosses streams and is the verifier's (disclosed).
- **Superseding by stale verdict.** A model could invalidate an old thesis id after a renewal, to
  remove the renewed instrument. Rule 187's last clause refuses it.
- **A dropped removal.** A writer could journal a judged verdict but never its record, so the
  instrument stays tradable after the model said the thesis is wrong. Rule 186's second clause
  refuses the batch.
- **Residual.** An invalidation of a thesis that already expired, retired, or was removed passes
  `append`. The agent stream alone does not show it. Removing an instrument already removed changes
  nothing, so it adds no risk, and the harness judges `unknown_thesis` for any thesis that is not
  active (agent harness spec §6.5).

## Follow-ups

- `mandate-journal`'s registration of the record, rules 184 to 187, with tests first. Rule 187
  joins `append`'s stream rules (DEC-2201) and reads the stream's thesis records too. With it,
  `JournalCatalog`'s invalidation answer reads the registration.
- The runtime's invalidation path. It writes the records in the judging batch, and folds them with
  the thesis records so the active set excludes invalidated theses. The executor's copy follows.
  MI-19 and HI-19's property test, a fuzz of random theses, invalidations, and renewals checked by an
  independent oracle that replays the verdicts, belongs to that implementation, not to this spec
  change.
- §11's verifier checks named in §9.22's "Checked by no rule at append".
- The `source_revoked` writer, once the founder decides DEC-433 item 19.
