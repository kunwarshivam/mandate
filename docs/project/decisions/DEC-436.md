## Decision

The [workspace services API spec](../../specs/workspace-api.md) v0.1 is the draft contract between
the backend and the web app, the CLI, and owner-connected agents. It adds no trading rule.

**Accepted (agent):**

1. **Precedence and authority.** The API records owner input on the control stream and serves read
   models; it never writes an agent or account stream, calls a broker, or calls a runtime. The
   runtime and executor judge every command, response, and step-up as mandate spec §6.1 and §6.4
   say. The API's own checks are authentication, authorization, and refusals that only stop risk
   from being added (spec §1.4, §6.2).
2. **Transport.** JSON over HTTPS with an OpenAPI 3.1 contract generated from the Rust types, paths
   under `/v1`, decimals and timestamps in the journal's canonical string forms, and server-sent
   events carrying watermarks only. Not gRPC at the edge: browsers, the MCP adapter, and approval
   links are plain HTTP, and string decimals avoid float encodings (spec §3.1). Safety enums are
   closed within a major version (spec §3.2).
3. **The control stream's writer.** From M8 the API process holds the control stream's writer epoch,
   and the CLI calls the API in managed deployments. The CLI's direct append (DEC-155) stays for
   Phase 1 and for on-site operators with database access, as a kill-switch path when the API is
   down; the writer epoch fences whichever writer is stale (journal spec §5.1).
4. **Idempotency.** Every mutating call carries `Idempotency-Key`. The control-stream `event_id` is
   derived from SHA-256 over the workspace, the principal, the operation, and the key, extending
   DEC-290 to the API. A repeat returns the first outcome; a different body is
   `idempotency_conflict` (spec §3.4).
5. **Command phases.** A command is `recorded` once its control-stream event is committed, `taken`
   when its owning stream copies it, then `applied`, `refused`, or `ended`. An ambiguous append is
   reported as `effect: unknown`, never as success or as "nothing happened" (spec §5.5, API-13).
6. **Read models.** Projections from journal tailing, each response stamped with per-stream
   watermarks; never authority for trading; rebuildable from the journal alone (spec §6).
7. **Errors.** RFC 9457 problem documents with a stable `code` and an `effect` member (`none`,
   `recorded`, `unknown`), so the UI can always say whether anything changed (spec §3.5).
8. **Step-up is bound to one action.** A challenge names one action digest; evidence is accepted only
   on that action's call and is single-use (DEC-173 item 3). This tightens step-up: a stolen
   assertion cannot be spent on another action (spec §3.6, API-17).
9. **Client scopes are a closed list:** `read`, `request`, `propose`, `dry_run`, and `hold`
   (DEC-141, DEC-185, DEC-190, DEC-191). `requested_by` comes from the token. Client events carry a
   new actor kind `client`, never `user`, with the human named beside it as `on_behalf_of`
   (settlement X2; the identity spec, #556, amends its §12.2, ID-11, and DEC-437 item 10 to match).
   The runtime's check 3 refuses any client answer from the record alone, and every rule that
   compares humans (check 7's author, mandate spec §5.8's requester, identity ID-6) counts a client
   as its `on_behalf_of` user; mandate spec §6.4 says so in this change (item 19). Client, CLI, and
   service-account tokens are sender-constrained (DPoP, RFC 9449), never plain bearer tokens
   (settlement X5; spec §3.3). Every client call, reads included, is journaled (DEC-141 item 5).
10. **The kill-switch path.** Pause and the kill switch read no read model and run on a reserved
    worker and connection pool, with no rate limit or quota (API-7, API-8). The kill switch is never
    refused for step-up; missing evidence costs only the owner-exit privilege (DEC-158 option (c)).
    The kill switch's `submitted_at` is the server's receipt time.
11. **Drafts are journaled.** Each explicit draft save is a `MandateDraftSaved` event on the control
    stream, with the draft as an artifact; this tightens "journal every state change" for a state
    that has no effect on any agent (spec §4.1).
12. **Foreign ids are 404.** An id in another workspace and an id that does not exist get the same
    response (API-9).
13. **The organization kill switch fans out from the client,** one workspace-scope call per
    workspace, each journaled on its own and reported per workspace. It never routes through the
    global control plane (HLD §4).
14. **Journal changes this spec needs** are made in the journal spec before the operations that use
    them ship (E10-15): `MandateDraftSaved`; the compiler's `ModelInvocationRecorded` on the control
    stream; `agent_id` and `base_version` on `MandateConfirmed`, so a confirmed version names the
    agent it is for; `OwnerRequestSubmitted`; the `hold_openings` and `lift_hold` commands; the
    `client` actor kind; and `ClientConnected` and `ClientRevoked`. Until then those operations are
    not offered.
15. **Backlog placement.** The stories continue existing epics (E8-15, E10-10 to E10-15, E11-9,
    E12-6) instead of taking a new epic number, because sibling specs drafted in parallel may take
    E20 and later. The approval row is E8-15 because the notifications spec (#558) holds E8-9 to E8-14.
16. **An ordinary revoke is not risk reduction.** It is refused while any agent on the connection
    holds positions or is not stopped, because without the connection nothing can exit or re-place
    protection. A suspected compromise uses item 20 instead (spec §4.5).

19. **Mandate spec §6.4 is tightened in this change** (DEC-176): the notification payload is a
    random notice id the deployment maps to the request, never the request's event id (settlement
    X3; the notifications spec, #558, aligns its NT-4, §4.2, §4.3, and DEC-438 item 10), and check 7
    counts a client as its `on_behalf_of` user. `mandate_approval::ApprovalRef::of_requested_event`
    becomes a notice-id lookup in E8-15.
20. **Revoke now, on a compromised broker credential** (the coordinator's ruling on M2). One
    command commits the connection-scope kill switch and then `ConnectionRevoked` (reason
    `compromised`) in one batch. Revocation never waits on positions. The kill switch's cancel and
    close requests go first with the current lease, and whatever the broker accepts stands; then
    the credential is destroyed and, where the broker offers it, revoked there. Exits the executor
    would have deferred are not re-driven, and the owner is told which positions remain at the
    broker and to revoke the key there too. The kill-switch half is never refused for step-up or a
    frozen stream (spec §5.6).
21. **Roles and step-up kinds come from the identity spec.** Spec §3.7 prints identity spec §4.2's
    matrix exactly and enforces no other (settlement X1); the org-admin-as-workspace-admin note is
    gone. The step-up `kind` set is identity spec ID-4's list and grows with it (the ruling on M3).

**Proposed (founder):**

17. **Pause on a session past its absolute lifetime while the identity provider is unreachable.**
    Identity spec §6.4 already keeps pause and the kill switch on a session whose refresh failed,
    until its absolute lifetime. Recommended beyond that: allow pause only (never the kill switch,
    resume, or anything else), up to 12 hours after the last successful authentication, never after
    revocation or deprovisioning, journaled with the distinct authentication method `session_grace`
    so the audit explorer can filter it. Pause never adds risk and
    can be undone, and it keeps the owner able to stop new orders through an outage. **Until
    decided:** no grace; pause needs a valid session, and the kill switch a passkey the deployment
    verifies itself. This loosens an authentication check on a safety-critical path, so it is the
    founder's (DEC-79).
18. **Third-party access to the API** (DEC-149, E18). Recommended: first-party only in v1: the web
    app, the CLI, and the Owlhead MCP server. Opening it brings terms, pricing, and support duties.
    **Until decided:** first-party only.

## Rationale

The specs already say who judges owner input: the runtime and the executor, from the control stream
(mandate spec §6.1, journal spec §2). The CLI proves the shape in M7. The API keeps that shape and
adds what a multi-user, networked surface needs: authentication, roles, client scopes,
idempotency across retries, an honest error model, and read models that say how old they are.
Every reading either adds no rule or tightens one.

## Alternatives considered

- **gRPC at the edge:** rejected for browsers and links (item 2).
- **A request-scoped idempotency table instead of derived ids:** workable, but derived ids reuse the
  journal's own idempotency check and the CLI's rule (item 4).
- **Let the API judge step-up and deadlines:** rejected; two judges could disagree, and the stream
  owners are the authority (item 1).
- **Record client calls as the owner's:** rejected; it would let a bug make a client look like a
  person to the approval checks (item 9).
- **A new epic E20:** rejected to avoid colliding with parallel specs (item 15).
