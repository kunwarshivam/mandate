## Context

Connections spec §5.2 step 1 and §9.1 say the connection manager creates a pending record
(`connecting`) when a connect starts. That record has a `connection_id` and an `account_ref`. Journal
spec §9.8 had no event for it. The first control-stream record of a connect was its
`ConnectionEstablished` (version 2) or its `ConnectionRefused`, and §9.8 said "`connecting` leaves
no record but a `ConnectionRefused`". Identity spec §7.2 step 5 marks a step-up challenge used in
the transaction that commits the action's control-stream event, and the start committed none.

## Invariants

The design was written against these, and each is a vector:

- **I1.** Every connect that leaves `connecting` (established, refused by a check, or torn down)
  closes exactly one `ConnectionRequested` of its own `connection_id`, on its own control stream.
- **I2.** At most one request per connection is open at a time, and a request is closed once.
- **I3.** An `account_ref` is assigned once per control stream: a retry gets a new account stream,
  and an orphan's is never used again (connections spec §5.2 step 6).
- **I4.** The record that closes a request repeats its broker, environment, user, and step-up, and
  an establishment also repeats its `account_ref`. The step-up a connect spent is the one its
  outcome carries.
- **I5.** No member carries a secret, the code, the verifier, the `state`, the vault path, an
  account number, or the fingerprint (CN-1, CN-10, `AGENTS.md` rule 7).
- **I6.** No new rule refuses a `ConnectionRevoked`, an exit, a protective order, or a kill switch
  (`AGENTS.md` rule 13).

## Decision

1. **`ConnectionRequested`**, a control-stream record at schema version 1. Its members are
   `connection_id` (`id`), `account_ref` (`ulid`), `broker`, `environment` (`paper` | `live`),
   `user`, and `step_up` (never `null`). It maps to no `JournaledFact`.
   - The name follows §9.8's records: the owner requested a connection.
   - `environment` is typed as `ConnectionRefused`'s. The start route connects paper only
     (connections §5.2, DEC-693 item 2), but the CLI's `connection record` (DEC-529 item 3) may
     record the founder's live Robinhood connection. Its establishment must close a request
     (item 3), so a paper-only type would make rule 131 refuse that connection. A live start of
     Alpaca OAuth is still refused before anything commits.
2. **It commits with the step-up.** The connection manager commits it when the connect starts. It
   commits in the transaction that marks the step-up challenge used (identity §7.2 step 5), before
   the redirect, any vault write, or any process start. A start refused before that commits
   nothing. The closing record repeats the request's `user` and `step_up`: that is the evidence
   of one action written again, not a second use.
3. **Stream rule 131** (control stream). It is checked after rules 66 and 67 on the same record,
   so every earlier case keeps its rule.
   - **Opening.** A request names a `connection_id` with no open request and no earlier
     `ConnectionEstablished` on its stream (I2), and an `account_ref` that no earlier request or
     establishment there names (I3).
   - **Closing.** A connect's version-2 `ConnectionEstablished` (no earlier establishment of the
     id) and a `ConnectionRefused` with occasion `connect` each close the id's open request. One
     must exist, and the record repeats its members (I1, I4). A request is closed once.
   - **What closes none.** A reconnect, a credential replacement, a version-1 establishment, and a
     `ConnectionRevoked` close none.
   - §11's `connection_lifecycle_mismatch` reports rule 131. A request still open at a range's
     end is a connect in progress, not a mismatch.
   - A refused id may start again with a new request and a new `account_ref`, as rule 67 already
     admits. The reference's `a_refused_id_connects_later` keeps its answer.
4. **Every state walked to its exit.**
   - **Success** closes the request with the establishment.
   - **Refusal** closes it with the `ConnectionRefused` of a check, or with step 6's teardown
     (`timeout`, `restart_past_deadline`, `executor_stopped`, `start_failed`).
   - **A refused callback, or a failed vault write,** starts nothing. The deadline's teardown
     closes the request.
   - **After an API restart,** the open requests are the `connecting` records the manager
     re-reads (connections §5.2 step 6), so the fold gives the manager its pending set.
   - **The deadline bounds an open request.** An open request is not a defect.
   - **One-step writers.** A writer that records a connect in one step, as the CLI's
     `connection record` does, commits the request and the establishment in one batch.
5. **A `ConnectionRevoked` closes no request.** Connections §9.1 has no revoke out of
   `connecting`, and a pending connection is not established. **Not decided here:** whether the
   owner may end a pending connect early. Today a `ConnectionRevoked` journaled for a pending id
   makes the teardown's `ConnectionRefused` (occasion `connect`) break rule 67. A route that
   allowed it would need a teardown reason or a rule change. That is a separate decision; until
   it is made, the deadline's teardown ends the connect, and the revoke route has nothing to revoke.
6. **The sentences reconciled.**
   - Journal §9.8: the `ConnectionStateChanged` paragraph's "`connecting` leaves no record but a
     `ConnectionRefused`", and `ConnectionRefused`'s "Nothing else is kept of a refused connect".
   - Connections §9.1: "no record kept beyond the refusal event".
   - Connections §5.2 step 1 and step 6, and §9.2's walk, now name the request.
7. **Vectors and order (ES-22).**
   - The `connections` section's control-stream sequences gain the request that each of their
     connects closes. Every case keeps its answer, at an index one later where a request comes
     before the mismatch.
   - A new generated section, `connection_requests`, holds the record's drafts and the rule-131
     sequences, with their validator, stream, and vector mutants.
   - The E7-17 fold (`crates/mandate-journal/src/connection_fold.rs`) does not check rule 131 yet,
     and its tests read `connections`, where it skips the new record type. Its code change, tests
     first, follows this one and reads the new section. So does the registration of
     `ConnectionRequested` in `mandate-journal`, which refuses it today as an unknown event type.

## Not covered here

- **A reconnect and a credential replacement** also spend a step-up at their start, with no
  start event. DEC-694 item 4 asks for the connect only; the same gap for the other two occasions
  is left for a follow-up.
- **Workspace API spec §4.5** names only `ConnectionEstablished` as the connect row's event. The
  row should also name `ConnectionRequested` at the start and `ConnectionRefused`. That edit waits
  for L2's open revoke change to the same table, so the two do not conflict.

## Rationale

The request is what DEC-694 item 4 asks for. It puts the start of every connect, and the step-up
spent on it, in the journal (rule 5: journal before acting). It also makes the connection manager's
`connecting` set a fold of the journal rather than state of its own. Every rule refuses more and
nothing it already admitted. The record carries no member a secret could sit in.

## Alternatives considered

- **Make closing optional,** checking the members only when a request exists. Rejected: DEC-694
  item 4 requires every connect's outcome to follow its request, and an optional rule would not
  prove I1.
- **Require a new `connection_id` for every attempt.** Rejected: it would change the answer of a
  case rule 67 admits today, and I1 to I3 hold without it.
- **Type `environment` as `paper` only.** Rejected for the reason in item 1.
- **Add the vectors to the `connections` section.** Rejected: the E7-17 fold's tests read that
  section and would fail until the fold's code change lands.
