## Context

A first passkey enrolls with a 24-hour cool-off (journal spec rule 249, identity spec §10.1).
Until the cool-off ends, the passkey verifier refuses every step-up made with it as
`step_up_missing` (workspace API §3.6 check 6). That rule is right for a real owner, because an
attacker who takes over a sign-in channel cannot add risk for a day. But the browser proofs of
resume, stop, version confirmation and deployment run in throwaway `dev` and `ci` cells. Each such
cell enrols a fresh passkey and needs step-up within minutes, so none of those proofs can run.

The founder was asked whether a test cell may waive the cool-off. The answer, 2026-10-28, was:
**"Yes, test cells only."**

## Decision

1. **A `dev` or `ci` cell may waive a first passkey's enrolment cool-off at step-up (the
   founder).** Staging and production keep the 24 hours, and so does every cell whose tier is not
   `dev` or `ci`.

2. **The tier and the waiver come from the deployment's own configuration, and nowhere else.**
   - **The tier.** It is `MANDATE_DEPLOYMENT_TIER`, which the cell chart sets on every process from
     `deploymentTier` alone (DEC-971 item 2). It is the same setting DEC-2100's stub issuer is
     gated on, and the API server already reads it at start.
   - **The waiver.** It is the API server's setting `MANDATE_API_STEP_UP_COOL_OFF_WAIVER`, which
     the chart renders from the value `api.stepUpCoolOffWaiver: true`.
     Its name holds no part DEC-978 item 2 refuses in the API server's environment (`KEY` among
     them), so it is `STEP_UP`, not `PASSKEY`: a variable named `..._PASSKEY_...` stops the server
     before this check is reached.
   - **What the server refuses at start, before it serves anything:**
     - any value of the setting other than unset or exactly `true`;
     - `true` with any tier but `dev` or `ci`. An unset or unknown tier reads as `production`
       (`mandate_release::startup::Tier`), so it is refused too.
   - **What the chart refuses at render.** It refuses `api.stepUpCoolOffWaiver: true` unless
     `deploymentTier` is `dev` or `ci`, as `mandate.stubIssuer` refuses the stub issuer.
   - **What never turns it on.** No request member, header, query or session state does, and
     neither do the clock or any other environment variable. The setting is read once at start.
   - **The residual (an adversary note).** An insider who can set a production pod's environment
     can set both `MANDATE_DEPLOYMENT_TIER=dev` and the waiver, and the server will start with it.
     That is the residual DEC-971 and DEC-2100 already accept: whoever sets a pod's environment
     already controls the pod. What stays visible is a `StepUpCoolOffWaived` naming `tier` `dev` or
     `ci` in a production cell's journal, which an auditor sees and the journal cannot refuse,
     because it does not know the deployment's tier.

3. **The waiver lives in the API's passkey verifier, at the cool-off check, and nowhere else.**
   - **What it changes.** At identity spec §7.2 step 4 and workspace API §3.6 check 6, a passkey
     whose `cool_off_ends` is after the verifier's `now` counts as past its cool-off. That holds
     only while the server started with the waiver in a `dev` or `ci` tier.
   - **What it leaves alone.** Every other check keeps its order and code:
     - the challenge, and its 300-second window;
     - the credential being the principal's own, enrolled and not removed;
     - the signature;
     - user verification;
     - the counter;
     - the digest.
   - **Enrolment is unchanged.** `CredentialEnrolled` still records `cool_off_ends` as rule 249
     fixes it, so the record keeps saying the passkey was cooling off.
   - **Scope.** It is passkey evidence only, never `cli_confirm`, and paper only: a `live` step-up
     is refused `live_unavailable` before evidence is read.
   - **Only a route that journals the assertion can count a waiver.** The verifier does not just
     report a step-up as counted. It returns the waiver as part of the typed outcome that carries
     the `StepUpAsserted` to append, and only a caller holding the writer of that pair (the
     assertion, then its waiver) can consume it.
     - A route that judges without appending an assertion treats a cooling credential as cooling,
       which gives `step_up_missing`. So does the port's plain `verify`, which carries no
       assertion. No route can waive with nothing journaled.
     - The routes that append an assertion today, and so can carry a waiver, are:
       - a version's confirmation (`MandateConfirmed` version 3);
       - a deployment (`AgentDeployed` version 3);
       - resume and stop (`OwnerCommandIssued`);
       - an OAuth connect's start (`ConnectionRequested`).
     - An approval grant passes no assertion until the passkey grant lands, so it stays cooling.
       So does a second passkey's enrolment, whose step-up is not yet judged (E9-4 S3.3b).
     - An acknowledgment carries the waiver once it lands with its assertion (#2754). A later route
       that appends its assertion through the same writer carries it with no other change.

4. **Each waived step-up is journaled as its own record, `StepUpCoolOffWaived`, not as a
   `StepUpAsserted` version 2 (journal spec §9.38, rules 316 to 318).**
   - **Where it goes.** The API appends it immediately after the `StepUpAsserted` of the step-up it
     waived, in the same batch, with the same `causation_id`. Both records carry the same
     `event_time`: the instant the verifier judged the step-up at. So a step-up judged within a
     tick of `cool_off_ends` is judged by one instant throughout. Rule 318 never refuses a waiver
     its own verifier granted. A step-up judged at or after the end needs no waiver, and a race
     there is a retry, not a lockout.
   - **What it holds.** The challenge, the credential, the `cool_off_ends` it waived, and the tier,
     `dev` or `ci`.
   - **Why a new record.** It is purely additive. `StepUpAsserted` version 1 and every reader of it
     are unchanged: the verifier's counter fold, rules 253 and 254, and the deployment manager's
     and runtime's readers of the authorized events.
   - **The rules.**
     - Rule 316 (consistency) keeps it paper-only and a user's.
     - Rule 317 (batch) ties it to the assertion it waived.
     - Rule 318 (stream) ties it to the credential's own enrolment, and adds the converse. A
       `StepUpAsserted` whose credential is still cooling off at its `event_time` must be followed
       by a waiver. That converse is a tightening, so the journal itself shows every early step-up
       and why.
   - **Why the tier is recorded.** It is the writer's word, from its configuration. The journal
     cannot check it, but the record says which kind of test cell waived. What holds it is item 2:
     the API's refusal at start, and the chart's refusal at render, of the waiver in any tier but
     `dev` or `ci`.
   - **The reply is unchanged.** A waived step-up's route answers exactly as an unwaived one does,
     with the same status and body. Only the journal record shows the waiver.
   - **The shared instant is a rule.** Rule 317 requires the waiver's `event_time` to equal its
     assertion's.

5. **What this never changes.**
   - The 24 hours, and rule 249.
   - The cool-off of a membership (identity spec §8.3).
   - The reduction-only path's own enrolment and step-up rules.
   - The runtime's and executor's judgement of step-up evidence.
   - Any tier but `dev` and `ci`.

   A test cell's journal stays a test cell's. Staging and production never start with the setting,
   so they never write the record.

6. **How it lands (ES-22, DEC-77).**
   - **This spec change.** It carries the DEC, journal spec v0.112 with §9.38, the identity and
     workspace API notes, the reference module `reference/journal/cool_off_waivers.py`, its
     vectors, and the regenerated fixtures.
   - **Then a tests change**, pending tests first:
     - `mandate-journal` registers `StepUpCoolOffWaived` and rules 316 to 318.
     - The API server refuses to start with the setting in `staging`, `production` or an unset
       tier, and with a value other than `true`.
     - In a `ci` cell with the waiver, each route of item 3 that appends an assertion commits with a
       fresh passkey, with its `StepUpCoolOffWaived`. That is one test each for a version's
       confirmation, a deployment, resume, stop, and an OAuth connect's start.
     - Without the waiver, the same cell still answers `step_up_missing`.
     - No header or request member turns the waiver on.
     - A route that appends no assertion keeps the cool-off even with the waiver: an approval
       grant's passkey evidence, and the port's `verify`.
   - **Then the implementation.** It includes the chart's render refusal.

## Rationale

- **Item 1** is the founder's: it lets the browser proofs run in the cells built for them.
- **Item 2** puts the waiver behind the one tier setting the chart alone sets. It also refuses the
  waiver at both ends, at render and at start, as DEC-2100 gates the stub issuer, so a
  misconfigured staging cell fails closed rather than quietly waiving.
- **Item 3** waives only what the founder named and only at use. The enrolment record and its
  `cool_off_ends` stay true, and every other step-up check still stands.
- **Item 4** makes each waiver visible in the journal. Rule 318's converse means a step-up inside a
  cool-off without one is refused, so a waiver cannot happen silently.

## Alternatives considered

- **Waive at enrolment by writing `cool_off_ends` `null`.** Rejected, because rule 249 fixes it and
  the record would hide that the passkey was new.
- **`StepUpAsserted` version 2 with a `cool_off_waived` member.** Rejected for item 4's reason:
  every reader of the assertion would change for a member only test cells set.
- **A request header or query flag for test runs.** Rejected, because anything a request carries,
  a request can forge.
- **Waive in `staging` too.** Rejected, because the founder said test cells only.
