## Context

The specs said an address is active while its last `NotificationAddressChanged` is `added`, and that
a deactivation appends a `removed` for each active address inside its own commit. Two cases were
left open. If the one active-set fold (L3's `ActiveAddresses` in `mandate-notify`) cannot read the
history, the deactivation cannot compute its removals; blocking it would keep a departing member's
access. And if the removals are missing, nothing in the old definition stops a reactivated member's
old browsers from receiving again, or lets the sweep delete their entries.

## Decision

1. **Serving: one fail-closed definition.** An address is active if and only if all of these hold:
   1. the member has a start (`MemberActivated` or `MemberReactivated`);
   2. the `added` seq is greater than the member's latest start seq;
   3. no end (`MemberDeactivated` or `MemberRemoved`) has a seq above that start;
   4. no matching `removed` (same member and `address_ref`) follows the `added`.

   With no start, nothing is active. A `removed` naming an `address_ref` that is not active, or
   another member's, changes nothing. `cooling_off` has no end record, so a cooling-off member's
   addresses stay active. The fold takes four parse-only tuple types in `seq` order: `added` and
   `removed` as `(seq, member, action, address_ref)`, a start as `(seq, member)`, and an end as
   `(seq, member)`. It joins them on `member`, the user principal's ULID that journal §9.12's
   membership records carry too, so the join is the same id by definition. The dispatcher, the workspace API (the 10-address limit, an
   endpoint already held, the listing, and 404 against 200 on removal), and E9-7's
   `removals_on_deactivation` all use it, through L3's one fold. Disregarding an address is the
   reversible tightening: the address is ignored, never destroyed.
2. **Erasing: positive evidence only.** The sweep erases an entry only on positive evidence from a
   fold that succeeded and covers the entry's `written_at`:
   1. a matching `removed`, after any last send ends, or 24 hours after the `removed`;
   2. the member's latest start followed by a `MemberDeactivated` or `MemberRemoved`;
   3. the `added` seq before the member's latest start;
   4. no `added` at all, for an entry whose `written_at` and file are both more than 24 hours old.

   Evidence 2 and 3 waits a further 7-day grace: evidence 2 from the end record's time, evidence 3
   from the later start's time (a reactivation after the membership that added the address
   ended). A member
   with no start, a fold that fails, or a journal read that fails keeps the entry and raises one
   operator alert carrying opaque ids only (item 7).
3. **A fold error never blocks a deactivation.** When the fold fails, E9-7's writer commits the
   `MemberDeactivated` or `MemberRemoved` without the removals and raises one operator alert with
   opaque ids only (item 7). By item 1, the member's addresses are no longer active once it commits,
   so the dispatcher sends them nothing; the sweep erases their entries on evidence 2 after the
   grace. E9-7 owes two tests: `deactivation_removes_the_workspace_notification_addresses_in_one_transaction`
   and `a_deactivation_whose_fold_fails_commits_without_removals_and_alerts_once`.
4. **Removing a dead address.** A removal of an address that is not active only because a
   membership ended, with no `removed` of its own, answers `200` with the watermark of the
   `MemberDeactivated` or `MemberRemoved` that ended it. A reactivated member is told to add an
   address again by identity spec §5.2 step 3's in-app notice (`web_inbox`), never by push.
5. **The specs.** Workspace API §4.11 ("Active addresses", "Deactivation", the removal route's
   row) and §5.7 ("The sweep", removing step 2), identity spec §5.2 step 3, journal spec §9.15's
   "The active set" (v0.73), and notifications spec §5.1, §5.3, and §9's failure-mode row say so.
6. **The dispatcher's stop needs evidence too** (journal rule 216). A pending web-push send to an
   address that stops being active for any reason, its `removed` or a membership that ended, is
   journaled `abandoned` with `address_retired`. When the fold fails, the dispatcher sends nothing
   and does not journal `address_retired`, since that stop claims the address left the active set,
   which a failed read cannot show. The pending send waits and, if the fold stays down, ends
   `retry_window_ended`. As in items 1 and 2, serving fails closed, and recording a stop needs
   evidence.
7. **The operator alert.** Both the deactivation that commits without its removals (item 3) and
   the sweep that keeps an entry for want of evidence (item 2) raise the opaque operator alert of
   kind `address_fold_unreadable`, carrying the workspace id and the member's or entry's opaque id
   only. The kind joins infrastructure design §8.2's alert table and `mandate-alerts`' closed
   `AlertKind` (a backlog row).

## Rationale

A deactivation must end access whether or not the history reads, so blocking on the fold is the
unsafe choice; anchoring "active" to the latest start makes the missing removals harmless, since an
address can only be served after the membership that added it began and before it ended. Serving
less is reversible and deleting is not, so the two take different evidence: the dispatcher fails
closed on any doubt, and the sweep acts only on a record that says the address is gone.

## Alternatives considered

- **Block the deactivation until the fold reads.** Rejected by the coordinator: a departing member
  keeps access while the history is unreadable.
- **One predicate for serving and erasing.** Rejected: with "no start, nothing active", a missing or
  unreadable start record would let the sweep destroy every address, irreversibly.
- **Read reactivation as restoring the old addresses.** Rejected: an attacker's browser added before
  a deactivation would resume receiving the member's notices.
