## Decision

1. **E1b is split in two.** The earlier E1b builder found two blockers in `mandate-paper`:
   - `crates/mandate-shell/src/tracer.rs`, `execute_cycle`, opens the session, feeds the model
     output and one `Input::Tick`, and returns `Ok(session.report)`. The session is dropped after
     one tick, so nothing can tick the executor again or wait for the entry.
   - `mandate_executor::Command` had only `KillSwitch` and `Reconcile`. Nothing could cancel one
     agent's working openings in one instrument. The agent kill switch flattens the position. A
     direct `BrokerRequest::Cancel` from the adapter would break `AGENTS.md` rule 12 and FT-1.

   **E1b-0** adds the command to `mandate-executor`. **E1b** then makes `ProductionCycle` in
   `mandate-shell` keep its session and run the bounded watch, and `mandate-paper` drives it.
2. **The command.** `Command::CancelOpenings { agent, instrument }` cancels exactly the orders
   `cancel_openings` already cancels for an exit (trading-domain spec §5.3 rule 5) and for a
   stricter mode (mandate spec §5.9). Those are the `open` and `increase` orders of that agent in
   that instrument that the broker holds as `accepted` or `partially_filled`. It never touches a
   protective order, an exit, another agent's order, or another instrument's order, and never
   names an account-wide endpoint. Each cancel is journaled as `OrderStateChanged` to
   `pending_cancel` with `cancel_requested` before the request leaves (rule 5, journal spec §9's
   closed `OrderStateChanged`). A cancel already asked and not yet confirmed is not asked again.
   The event ids are the executor's (epoch, head, ordinal) derivation.
3. **It is never denied, and with nothing working it changes nothing.** The command only reduces
   risk, so no gate, conduct, budget, session or mode rule applies (rule 13). It needs no binding
   gate snapshot. Mandate spec §5.9 says "On entering `exits_only` or stricter, the executor
   cancels the agent's working opening orders", so `paused` and `stopped` do not block it. With
   nothing to cancel it answers `Ok` with no effect and no journal event. **This reads the
   dispatch's "journaled no-op"** as a no-op that leaves the journal as it is: no account-stream event records a command that changes no order, and adding one is a journal
   spec change. The no-op therefore journals nothing, like every executor step that changes no
   state. Why an order was cancelled is the paper run's report's to say (E1b).
4. **An `Unknown` opening is left to its query.** The command adds no behaviour of its own here.
   `cancel_openings` cancels only resting openings: an `Unknown` order is queried by id and never
   cancelled blind (§5.7). The `Unknown` order still holds every new order in the instrument
   (§5.3 rule 9). E1b's watch keeps ticking, so the lookups resolve it, and it issues the command
   again once the order is resting.
5. **E1b's bound.** The watch's bound is the start of the close window of the regular session the
   run is in: that session's end less `close_window_minutes` × 60 s. This is 15:50 New York on a
   full day, and ten minutes before an early close. `close_window_minutes` is the registered rule set's gate
   member, which the preflight already reads. The session's end comes from the calendar the
   judge's `regular_session_outside_close_window` reads (`mandate_time::ExchangeCalendar`), so
   the preflight's "before the close window" and the watch's bound are the same instant. The
   registered `trading-calendar.json` names only `first`, `last`, `holidays` and
   `special_sessions`, with no session times, so it cannot give the end by itself. E1b pins that
   the run refuses before any `POST` when the calendar cannot place the run inside the regular
   session (FT-8). At the bound the watch issues `CancelOpenings` for the deployment's agent and
   instrument.
6. **E1b's poll interval** is derived from the registered rule set's `executor` members. It is
   the least of: `exit_step_s`; `unknown_absent_window_s` divided by `unknown_absent_lookups`
   (whole seconds, rounded down, at least 1), so the query discipline of §5.7 can complete inside
   its window; `bracket_partial_fill_timeout_s`; and `max_unprotected_s`. The divisor is never 0:
   the paper rule set's reader takes `unknown_absent_lookups` with `required_positive_u32`, so a
   rule set naming 0 is refused before any run, and no term is skipped. With the reviewed
   values (5, 15 / 3, 60, 60) it is 5 s. The watch also wakes at any timer the executor arms
   before the next poll. What it does after the bound, until the cancel is confirmed and any
   partial fill covered or its interval journaled (FT-11), is E1b's to pin.
7. **The founder reviews this after the fact** (DEC-79). Reverting it means removing the variant
   and its tests, and leaving E1b blocked on the two findings in item 1.

## Rationale

The executor is the account stream's only writer, and it already has one cancel path (§5.3 rule
5, §5.9). Reusing it keeps rule 5, the type-level ban on account-wide endpoints in agent scope,
and the `Unknown` handling unchanged, and gives neither the shell nor the adapter a second door to
the broker (FT-1).

## Alternatives considered

- **The agent kill switch at the bound.** Rejected: it flattens the position and engages the
  mode, which is far more than cancelling a working entry.
- **A `BrokerRequest::Cancel` sent by `mandate-paper`.** Rejected: the cancel is journaled by
  nobody, the executor's state goes stale, and it breaks rule 12 and FT-1.
- **A new account-stream event for the command, so the no-op is journaled.** Deferred: it is a
  journal spec change, and those are queued one at a time. Item 3's reading needs none.
