## Context

DEC-437 item 9 owes journal §9 the identity spec's §12.1 control-stream records, with schemas, in
E9-7's tests PR. Journal §9 had none, so `append` refuses each as `unknown_event_type`, and nothing
can fold the memberships that `workspace_users` (identity spec §5.3, ID-7) is derived from.

Closing all of §12.1 at once is several thousand lines of spec and vectors. E9-7's fold needs only
the membership records. §12.1 also leaves three gaps that the fold of identity spec §5.1 needs
filled.

## Decision

1. **Journal spec v0.25 catalogues every §12.1 record** in §9's control-stream table, with the
   members §12.1 names. `ScopeHalted` and `ScopeReenabled` are left out while DEC-437 item 21 is
   Proposed, and `ClientConnected` and `ClientRevoked` keep the row journal spec v0.22 gave them, closed in
   §9.10 with the `client` actor ([DEC-671](DEC-671.md)).
2. **§9.12 closes the seven membership records** at schema version 1, with rules 96 to 106:
   `MemberInvited`, `MemberInvitationRevoked`, `MemberActivated`, `MemberRoleChanged`,
   `MemberDeactivated`, `MemberReactivated`, and `MemberRemoved`. The credential, session,
   service-account, host-CLI, and break-glass records close in a later change under E9-7. Until
   then `append` refuses them as it does today.
3. **Three gaps in §12.1 are filled.** Each journals a state change identity spec §5 already
   defines:
   - `MemberInvitationRevoked`, for §5.1's `invited` to `revoked` transition, which had no record.
   - The accepted `invitation` on `MemberActivated`, so the fold can tie a membership to the
     invitation and roles it accepted. It is `null` exactly for the founding grant.
   - `cool_off_ends_at` on `MemberReactivated`. §8.3 says a reactivation can start a cool-off.
     `MemberReactivated` also carries step-up evidence in place of a reason code, because §5.1
     requires step-up and an admin is its only cause.
4. **Instants are timestamps, and a record's own instant is its envelope's `event_time`.** The
   instants are `invited_at`, `expires_at`, `activated_at`, `changed_at`, `reactivated_at`, and each
   cool-off end, because the identity spec's cool-off and expiry are wall-clock times.
   `MemberInvited` carries `invited_at`, which §12.1 did not list, so that the 7-day expiry can be
   checked from the record. Each own instant must equal the envelope's `event_time` exactly
   (rule 106, the review of #789), and every cool-off end and step-up window is computed from
   `event_time`. Otherwise a writer could date a grant into the past to escape its cool-off, or to
   make a stale step-up look fresh. Step-up evidence is §9.2's type, with a timestamp `authenticated_at`, not
   §9.7's integer form (DEC-533 item 2).
5. **Each grant records the effective `independent_approval_required` at the grant**
   (`MemberActivated`, `MemberRoleChanged`, `MemberReactivated`), and `MemberReactivated` names the
   kept roles it restores, so the cool-off is decided by the record alone. **The record checks what it
   can on its own:**
   - Role lists are sorted.
   - The writer is the recorded admin (ID-1).
   - Who may write each record: a `user`, or the system for the founding grant and for directory
     and organization-deletion effects. A client or a platform operator never writes one (ID-11,
     ID-12).
   - Nobody changes their own membership except by leaving (ID-13).
   - A founding grant includes `workspace_admin`.
   - A grant carries step-up and a removal does not.
   - The step-up evidence is mandate spec §6.1's: its method suits the environment, and it was
     authenticated no more than 300 seconds before the record's own instant and never after it.
     Whether its assertion was used before is a check across records, so it is the identity
     crate's.
   - An invitation lasts exactly 7 days.
   - A record names its session exactly when a user wrote it (item 8).
   - Each cool-off is exact (§8.3). It is 24 hours when the record's
     `independent_approval_required` is true and the grant adds operator or approver to an existing
     workspace, and zero otherwise. The founding grant never cools off.
6. **Members are user principals' ULIDs.** No payload carries an address, a name, an identity-provider
   subject, or a token. The invited address is a vault reference in `pii_refs` (rule 6, ID-9).
7. **The fold.** §9.12 states which record moves which state, and leaves the cross-record checks to
   the identity crate. `removed`, `expired`, and `revoked` are terminal. A removed member comes back
   only through a new invitation, which starts a new membership with none of the old roles. An
   invitation activates at most once and only while `invited`: `activated_at` < `expires_at`, so an
   activation at the expiry instant is refused. If the fold meets a record that does not fit the state it finds, it reads the
   membership as unreadable, so `workspace_users` reads as 1 (identity spec §5.3, rule 3).
   - **Offboarding a deactivated member** ([DEC-654](DEC-654.md) item 7). `change_roles` accepts
     removing a role from a `deactivated` member, so the fold accepts a `MemberRoleChanged` with no
     `added` for one, removing roles it keeps; without this an accepted change could not be
     journaled. A grant to a `deactivated` member stays refused, as DEC-654 item 7 refuses it
     `forbidden`. A member whose kept roles are all removed cannot be reactivated, because rule 100
     refuses an empty `roles`; they return only by removal and a new invitation.
   - **The cross-record checks are the identity crate's:** the author is an `active` workspace
     admin whose role is effective (DEC-654 item 2); the last owner and last admin rules; step-up
     assertion reuse; that the record's `independent_approval_required` equals the workspace's
     effective policy at `event_time`; and that workspace services never commit an entry that
     changes nothing. DEC-654 item 6 lets `change_roles` pass such an entry, but the fold refuses
     granting a held role or removing one not held, and rule 100 refuses a record left with no
     entry, so the writer drops such entries before committing and commits nothing when none is
     left.
8. **`session_ref` is a payload member of the membership records, for now.** Identity spec §12.2
   says every committed event names its session. On the envelope, that changes the field set frozen
   at `envelope_version` 1 (journal §8), which moves every writer and every vector. Until that
   change lands, each membership record carries `session_ref` (`text?`) in its payload, non-null
   exactly when a `user` wrote it (rule 105). **The envelope-level `session_ref` is owed by a
   separate change**, which the L1 lead raises with the coordinator.

## Rationale

Every item narrows what `append` accepts, or records a transition the identity spec already
requires. The new `membership` vectors are additive, so the version-3 vectors and every existing
test are unchanged. `mandate-journal` gains the catalogue entries and schemas in E9-7's tests PR
and then its implementation PR (DEC-77).

## Alternatives considered

- **Close all of §12.1 in one change.** Too large to review in one sitting, and the session,
  client, and host-CLI records depend on E9-1, E9-9, and the `session_ref` question.
- **Defer `session_ref` entirely until the envelope change.** Rejected by the lead: the membership
  records would then name no session at all, and the identity crate could not list a revoked
  session's membership changes.
- **Revoke an invitation with `MemberRemoved`.** Rejected: an invitation is not a member, and
  reusing the record would make the fold guess which one it names.
- **Leave the 24-hour choice unchecked.** Rejected: the journal can refuse every end other than the
  two the rule allows without knowing the policy.
