| **Story or claim** | E21-40 (lane S1 of the [managed-cells plan](../tasks/managed-cells.md), DEC-967 item 9), claim [#1434](https://github.com/kunwarshivam/mandate/issues/1434) |

## Decision

1. **A new safety-critical crate, `mandate-objectstore`, layer 6** beside `mandate-artifacts-fs`,
   impure, reaches storage only through a plain S3 endpoint named in configuration. Its lock check
   judges what the store reports about itself and refuses anything weaker than journal spec §6.2
   before the cold exporter or the artifact writer may start.
2. **What the check accepts, for a standard S3 store.** All of: versioning enabled; object lock
   enabled; a bucket default rule in **compliance** mode of at least six years; and a probe version,
   written by the writer's own credential, in compliance mode retained at least six years from its
   creation, which that credential could neither shorten (`PutObjectRetention` to an earlier date),
   nor delete (`DeleteObject` of the version, with the governance bypass header), nor unlock by
   writing the bucket's own lock configuration back (`PutObjectLockConfiguration`). Every failure
   is a named refusal, and the check reports all of them, not only the first.
3. **Six years is 2192 days** (six years of 365 days and two leap days) wherever a period is in
   days or seconds, so no six-year span from any creation date is longer; a default rule in years
   needs at least 6. This only tightens §6.2's "creation + 6 years".
4. **The bucket default is required as well as each object's own retention.** The writer always
   sets compliance retention on each object it writes; the default rule protects anything written
   without it. This only tightens §6.2.
5. **The finding on Cloudflare R2**, from its documentation as of 2026-10-17 (the bucket-locks page
   last updated 2026-04-30, and the S3 API compatibility page):
   - R2's S3 API does **not** support per-object Object Lock: `x-amz-object-lock-mode`,
     `x-amz-object-lock-retain-until-date` and `x-amz-object-lock-legal-hold` on `PutObject`,
     `CopyObject` and `CreateMultipartUpload` are listed as not supported;
     `GetObjectLockConfiguration`, `PutObjectLockConfiguration`, `GetBucketVersioning` and
     `PutBucketVersioning` are unimplemented; `x-amz-bucket-object-lock-enabled` on `CreateBucket`
     is not supported.
   - R2 offers **bucket lock rules** only, through Cloudflare's API
     (`GET`/`PUT /accounts/{account_id}/r2/buckets/{bucket}/lock`) and Wrangler, not the S3 API:
     up to 1,000 rules, each covering a key prefix, with an age, a fixed date, or indefinite
     retention; the strictest covering rule wins; rules apply to existing objects too; while any
     rule exists the bucket cannot be emptied.
   - What a rule **prevents:** deleting and overwriting a covered object while it is retained.
     What it **cannot prevent:** removing or shortening the rule itself. Any API token with
     permission to edit the bucket's configuration can delete a rule (the dashboard, `wrangler r2
     bucket lock remove`, or a `PUT` without it), which unlocks every object it covered, existing
     ones included. There is no compliance mode and no per-object retention date.
   - So R2's strongest lock is **governance-equivalent**, and §6.2 requires compliance mode "(not
     governance mode)". The check refuses R2's bucket lock rules for every §6.2 object (segments,
     manifests, artifacts, configuration objects, timestamp tokens, verifier releases), whatever
     the rules say, with `objectstore_governance_only`, plus `objectstore_no_lock` when no enabled
     rule covers the prefix and `objectstore_retention_too_short` when the strictest covering rule
     is a fixed date or shorter than six years.
   - The finding is from documentation. The run against R2 itself (the plan's H3 test) is a
     documented command the founder runs the day R2 is bought (DEC-969); it is expected to confirm
     this finding, and a result that differs reopens this decision rather than being taken
     silently.
6. **R2 stays the endpoint for what §6.2 does not cover:** the journal Postgres's WAL archive and
   base backups (E21-41), which the plan sends to the S1 endpoint. Nothing that §6.2 lists is
   written to R2. Where the §6.2 objects go instead is [DEC-974](DEC-974.md).
7. **A provider swap is configuration.** The same check, the same refusals, and the same
   conformance suite run against any S3-compatible endpoint; only the endpoint, the bucket and the
   kind of lock evidence (S3 Object Lock or R2 rules) are configured.

## Rationale

§6.2 is the journal's tamper-evidence of last resort: the hash chain shows that a record changed,
and compliance-mode retention is what keeps the evidence that it did. A lock that a credential can
lift protects against accidents, not against the insider or the stolen admin token §6.2 exists
for. Reading the provider's real setting at start, and probing it with the writer's own credential,
is what keeps a provider swap or a mis-set bucket from silently weakening it (E21-40's purpose).

## Alternatives considered

- **Accept R2's indefinite bucket lock rule as good enough.** Refused: it is removable by a
  bucket-configuration token, which is governance mode by another name; accepting it loosens §6.2
  toward the provider, which only the founder could decide.
- **Trust the configuration without a probe.** Refused: it would accept a store that reports
  compliance but lets the writer delete (a misconfigured gateway or fake), and could not see a
  writer credential able to rewrite the bucket's rule.
- **A fresh probe object on every start.** Refused: each would be locked for six years. The probe
  reuses one key and writes a new version only when the old one is gone or its retention lapsed.
