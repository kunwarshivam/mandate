# DEC-944: `ApprovalTimedOut` is closed at schema version 1 as `{approval, on_timeout: skip}`, caused by its ask

| **Status** | Accepted (agent: a reversible engineering reading under DEC-79, taken under DEC-176. It admits a record that was impossible, adds a refusal, and loosens nothing) |
| **Date** | 2026-10-16 (UTC) |
| **Decided by** | `claude-code` (builder, the grant-gap timeout lane), under DEC-79, DEC-176 and DEC-921 |
| **Story or claim** | E7-26; DEC-940 item 7 (gap 4 of [#1367](https://github.com/kunwarshivam/mandate/pull/1367)); claim [#1376](https://github.com/kunwarshivam/mandate/issues/1376) |

Before this decision, `ApprovalTimedOut` was catalogued on the agent stream but had no registered
payload. `append` refused every draft of it as `unknown_schema`. When an ask's deadline passed,
the runtime's record of the skip could not be journaled, and the approval stayed pending on the
journal (DEC-940 item 7). These are the readings this lane takes.

## Decision

1. **Members.** Journal spec v0.41 §9.7 closes `ApprovalTimedOut` at schema version 1 with exactly
   the two members its §9 row and mandate spec §6.4 name:
   - `approval` (`ulid`): the ask's `ApprovalRequested` `event_id`;
   - `on_timeout` (`skip`): the safe default that applied.

   It requires `mandate_version` in `config_refs`, as its catalogue entry already does. It carries
   no content, instrument, owner identity, or free text, so nothing sensitive can reach it
   (`AGENTS.md` rule 6).
2. **No `deadline` member.** The deadline is the ask's `ApprovalRequested.deadline`. The record
   names that ask twice, through `approval` and through its cause, so a reader joins one record to
   find it. Repeating it would add a second copy that could disagree with the first. It would also
   change what the runtime writes, which the mandate reference cases pin: MC-E03 states the
   timeout's members, and its harness refuses a member a case does not state. So `mandate.yaml`,
   `reference/mandate`, the harness and the runtime would all have to change in one PR, and ES-22's
   spec guard refuses that. A later version can add the member if a reader needs it.
3. **Rule 135, the cause.** `causation_id` is non-null and equals `payload.approval`. Both clauses
   are refused `schema` at `causation_id`. The timeout is tied to the ask it ends, as rule 50 ties
   `ApprovalResponded` to its answer. The rule is checked after `artifact_refs` and `pii_refs`,
   where rule 50 is checked. The runtime's `expire` passes the approval's id as the cause; before
   this, it passed none.
4. **Two PRs, not one.** DEC-921 lets tests and implementation share a PR. It does not lift ES-22's
   spec guard, which refuses changes under `docs/specs/`, `reference/` or `fixtures/refcases/` in
   the same PR as code under `crates/` (DEC-901 split the same way). So:
   - the spec PR carries the spec text, the reference, the vectors and the regenerated fixtures,
     and this file;
   - the code PR carries `mandate-journal`'s registration and rule 135, and the runtime's cause.
     Its tests are written first and shown failing before the fix.

   Each PR is green on its own. The new vectors are a separate `approval_timeouts` section, so the
   existing `approval_answers` tests, which count that section's drafts, are unaffected until the
   code lands. After both merge, a Rust test that reads `approval_timeouts` can follow.
5. **Out of scope.** `ApprovalCanceled` has the same gap: it is catalogued and unregistered. It is
   left for its own row, and it fails closed the same way.

## Rationale

The gap fails closed: the runtime cannot record its skip, and nothing is sent. But it also leaves
an ask pending on the journal past its deadline, and the live cycle avoids ticking the runtime at
or after the deadline only to stay clear of the refused append (DEC-940 item 7). Closing the
schema with the members already written, and requiring the cause, admits exactly the runtime's
record and nothing else.

## Alternatives considered

- **Add `deadline` (integer risk-clock seconds).** The dispatch suggested it. Refused here for item
  2's reasons; the cost is one join.
- **Leave `causation_id` free.** A timeout could then name an approval while being caused by some
  other event. Requiring the cause costs one argument in the runtime, and it lets §11's readers
  follow the chain.
- **One PR.** CI's `fast` check would stay red on the spec guard. Refused.
