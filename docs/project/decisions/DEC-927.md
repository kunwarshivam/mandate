## Decision

1. **One judge.** `mandate_approval::live_cli_confirm` is the only place DEC-923's conditions are
   written. The runtime's admission check 6 and `mandate approvals approve` both call it, so the
   two cannot drift. It checks, in this order, and the first failure names the refusal: a scope is
   known (`live_scope_unknown`); the connection's broker is Robinhood (`live_not_robinhood`); the
   confirmed mandate's `max_order_usd` is at most 100 USD (`live_mandate_cap_above_limit`); the
   mandate pins exactly one instrument (`live_not_one_instrument`); the bound order is on it
   (`live_other_instrument`); the bound order is a US equity (`live_not_equity`, DEC-529 item 13);
   the bound order's value, quantity times limit, is at most 100 USD
   (`live_order_above_limit`); and the approver is the workspace owner (`live_not_owner`).
2. **"The one instrument DEC-529 names."** DEC-529 names no ticker (its item 2 leaves the ticker
   to the founder's confirmed mandate). The reading: the confirmed mandate pins exactly one
   instrument and the bound order is on it. Both caps are checked: the mandate's own
   `max_order_usd`, and the bound order's value, so a mandate edited above the cap and an order
   sized above it are each refused even if the gate would have caught them.
3. **Only the method is admitted.** On `live`, a grant whose `cli_confirm` evidence fails only for
   its method counts when the judge admits it. Missing, stale, and reused evidence are refused as
   before, and every other check (1 to 5, and 7) is unchanged. A refusal is journaled with the
   existing reason `step_up_method`, so no journal schema changes. A skip needs no step-up on
   `live` either (PX-7).
4. **Where the scope comes from.**
   - *Runtime:* `ApprovalSettings::live_cli_confirm`, set by the trusted run context: the
     connection's broker, the confirmed mandate's `max_order_usd` and pinned instruments, and the
     workspace owner. `None` keeps refusing. The shell's adapters set `None` today; the live
     runner (DEC-529 item 1) fills it from the connection record and the mandate when it is wired,
     and until then no live grant is admitted, which is the conservative reading.
   - *CLI:* on a request whose agent-stream envelope is `live`, `approve` reads the bound mandate
     version from the store and the control stream's latest record for its `connection_id`. Only a
     `ConnectionEstablished` with `environment` `live` gives a scope; a revoked, missing, or paper
     record gives none. The workspace owner is the user who recorded that connection with
     `cli_confirm` (DEC-529 items 3 and 11), so the owner running `approve` must be that user. This
     is the least-risk reading under DEC-929: it admits at most the one user who attested the
     account. A later re-record by another user moves it; E9-4's identity replaces it. A request
     whose envelope does not say `paper` is judged as `live`, so a missing environment fails
     closed; a `paper` request is judged as before.
   - *Backtest:* the runtime passes the scope to admission only when the stream is `live`, so a
     backtest view never admits `cli_confirm`, whatever scope it carries.
5. **Journal before release (DEC-923 item 2).** The admission is the `ApprovalResponded` with
   `result` `admitted`, whose `responder` is the approver and whose `step_up.method` is
   `cli_confirm`; it is written in the same batch as, and before, the `ApprovalRevalidated` and
   the `IntentProposed` it releases, and the intent is journaled before it is handed (rule 5). The
   grant is the control stream's `ApprovalResponseSubmitted` with the same members, committed
   before the runtime reads it. No new event or member is needed.
6. **Risk reduction is untouched (DEC-923 item 4, rule 13).** An exit is never asked, so it never
   reaches admission. Owner commands and the kill switch keep their existing step-up judgment;
   this decision does not extend DEC-923 to them.
7. **Lapse.** DEC-923 item 3: when E9-4's step-up lands, a later decision retires the judge and
   the `live_cli_confirm` field.

## Rationale

DEC-923 states conditions, not a mechanism. One pure judge in the layer-1 approval core keeps the
runtime and the CLI on one reading, and keeping the refusal reason `step_up_method` means the
narrowing needs no protected-path spec change. Leaving the shell's scope `None` until the live
runner is wired means nothing becomes admissible by accident.

## Alternatives considered

- A new `Environment` variant for the scoped live stream: it would leak DEC-923 into every
  environment match, owner commands and the kill switch included, which DEC-923 does not cover.
- A new refusal reason per condition in `ApprovalResponded`: a journal spec change, and the
  refusal is already recorded as the method's.
- Taking the workspace owner from a CLI flag: an untrusted surface naming its own owner.
