# DEC-2218: The gate holds the runtime's own journal ids to their form and constancy, and every other member to the service's record

| **Date** | 2026-10-28 (UTC) |

## Context

DEC-2217 item 4 has the model-gateway service check every member of a gate call against its own
record. Most members are pure functions of the probe set, the pinned entry and the service's own
replies: the run's kind and cut-off, the seed inputs retrieved from the corpus slice, each earlier
turn's response and results, the turn's menu and its spend ceiling.

Two kinds of member are not. The rendered `items` input names each item's `observation`, and the
`memory` input names each active thesis's `thesis_id`. Both are the runtime's own journal event ids,
assigned by its in-memory journal (agent harness spec §6.4). The service cannot compute them.

## Decision

1. **The service builds the expected call with the runtime's ids.** For each call it takes the
   call's observation ids and memory thesis ids, holds them to the rules in item 2, and builds the
   call it expects with exactly those ids. Every other member must then equal the expected call's,
   byte for byte. That covers the full `inputs`, so every item's body, source and kind, and every
   thesis's symbol and expiry. A call that differs is `unmatched` (DEC-2217 item 4).
2. **The rules for the ids:**
   - Each id is a ULID, so it carries no text but its own 26 characters.
   - On the first turn there is one observation per seed item. On each later turn the earlier
     turn's observations come first, unchanged, then one new observation per item the last
     dispatch read for the first time. No two observations in a call are the same.
   - There is one memory thesis per probe thesis, in order. Each thesis keeps its id from the
     first turn to the last.
3. **Why this adds no risk.** An id cannot carry an instruction to the model, since it is 26
   characters of a fixed alphabet. A runtime that chooses its ids still cannot change what the model
   reads, nor reorder, drop or add an item, nor give one item two ids or two items one. The gate's
   checks never read an id's value.
4. **Where the record lives.** The service's record of a run is `mandate-research-run`'s `Shadow`:
   the same pure steps the research worker and the runtime core take, which are retrieval, the run's
   loop state, dispatch over the corpus, and the turn's call. So an honest runtime fits by
   construction, and any drift between the two is caught as `unmatched`.

## Rejected

- **Requiring the runtime to use ids the service computes.** The runtime's journal assigns its ids
  itself. Forcing a scheme on it would change the production core for the gate's sake, against
  DEC-2217 item 3's "unchanged".
- **Ignoring the ids.** A call could then name one observation for two items, or change a thesis's
  id between turns, which the model would read as a different thesis.
