[Control-plane design](../../design/control-plane.md) §3.1, §3.2 and §3.4 describe enrollment, the
directory and fleet health; E21-43 asks for them as the plane's first slice, running as its own
deployment. These are the readings this lane takes.

## Decision

1. **A pure core first.** `mandate-cp` holds the behaviour (`ControlPlane`) over a `Store` port it
   declares, with time and randomness handed in, and an in-memory store. The HTTP server (axum,
   D-1, DEC-990), the plane's own Postgres store, and the binary are the next slice; its Helm
   release follows K1's chart skeleton (E21-36). Licensing, metering, the relay, distribution and
   the anchor witness are absent, not stubbed (E21-43).
2. **A deployment is authenticated by its own Ed25519 key, not an X.509 client certificate.** At
   enrollment the deployment generates a key pair on site; the private key never leaves it
   (E20-2), and the plane binds the public key to the `deployment_id`, one key to one deployment.
   Every call is signed over `mandate-cp-req/1`, its method and path (fixed per operation:
   `POST /v1/heartbeat`, `/v1/directory`, `/v1/routes`, checked against the operation called), the
   deployment, its time, and the SHA-256 of its body. It is accepted from 300 seconds behind the plane's
   clock to 5 seconds ahead of it (a call far ahead would lock its deployment out), and only if its time is after the deployment's last accepted call, so no call is
   accepted twice and no older call after a newer one (no directory rollback by replay). Its body is
   canonical JSON of the operation's closed shape, decoded in the core, so what the plane acts on
   is exactly what was signed. This gives design §3.1's binding of a key to a deployment without a
   certificate authority or a new crate (`ring` already verifies Ed25519).
   - **What this depends on:** the channel is TLS to the plane's ingress, which authenticates the
     plane to the deployment; every instruction is signed by an offline key anyway (CP-5,
     DEC-982).
   - **What it does not yet give:** a certificate's lifetime and renewal (CP-8, E20-14). A bare key
     has no expiry; it is replaced by revoking it and enrolling a new one with a new token. E20-14
     adds rotation before the cell needs it.
   - Mutual TLS can replace or join this when a TLS server crate is approved; the binding stays.
3. **Enrollment tokens.** An org admin's creation of a deployment returns its first single-use
   token: 32 random bytes the caller draws, kept only as their SHA-256, bound to that one
   deployment, with a short expiry. Creating an ID that exists is refused, so no creation takes
   over, re-keys or un-enrolls a deployment. A new token is issued only to an unenrolled deployment,
   and enrolling an enrolled one is refused: a key is replaced only after `revoke`, which clears it
   (an outage to the site, design §4). A revocation retires every outstanding token and the
   deployment's call history and last heartbeat, and a new token replaces any earlier one, so a
   leaked token never enrolls after a revocation. A reused, expired, unknown or other deployment's token is
   refused, and the token is spent when it binds a key. The bound key's SHA-256 is what the site
   journals as `ControlPlaneEnrolled.certificate_fingerprint` (journal spec §9.17); the member's
   name stays, and it names this key's fingerprint.
4. **The directory holds IDs and role names only** (E20-1, ID-15): deployments (ID, owner
   organization, mode, endpoint, bound key), workspaces (ID, organization, deployment), and members
   (user ID, workspace ID, `mandate-identity`'s role, active or deactivated). A deployment's endpoint
   is an `https://` URL naming a host, with no user information, query or fragment. A test writes
   every record out and finds no field for an email, a name, a phone number, or an issuer or
   subject.
5. **Workspaces are placed by an org admin; a deployment syncs only their members** (CP-11). An org
   admin registers each workspace on its deployment, first come and never moved by a deployment;
   a hybrid site hosts only its own organization's workspaces. A deployment's sync replaces the
   memberships of the workspaces registered on it, and naming a member of any other workspace is
   refused whole.
6. **Routing.** A client asks through a deployment it already uses: the call is signed by that
   deployment and names the user, who must be an active member of a workspace on that deployment.
   The plane answers the user's active workspaces in the organizations of those memberships, with
   their deployments' endpoints, so no deployment learns another's users or another organization's
   workspaces. The client caches the list, so a deployment it has used stays reachable with the
   plane down (design §3.2); the cache lives with the client and lands with the client's slice.
7. **Fleet health.** Heartbeats carry the release digest and each component's version and health
   (`ok`, `degraded`, `down`), never counts. A deployment silent for 180 seconds (three missed
   60-second heartbeats) is shown `unreachable`; nothing is revoked (CP-8, E20-5). An enrolled deployment
   that has never sent a heartbeat is shown `never_seen`, which the fleet view lists apart; it has
   no deadline of its own in this slice.
8. **Layering.** `mandate-cp` is a safety-critical layer-2 crate over `mandate-canon`,
   `mandate-time`, `mandate-identity` (the role names) and `ring`. Its `forbidden_internal` list
   names the journal crates, the registry, the runtime, the executor, the connections and vault
   crates and the process crates, so the plane has no path into a deployment's trading or
   records (CP-4, CP-7, CP-12).

## Rationale

The plane must be small and hold nothing but IDs; a pure core over a port is the shape every
safety-critical crate here takes, and it lets the HTTP and Postgres slice change without touching
the rules. Signed requests reuse the Ed25519 verification `cp-agent` already depends on and avoid
running a certificate authority before the plane even has a database.

## Alternatives considered

- **Client certificates (mutual TLS), as design §3.1 says.** Needs a TLS server crate and X.509
  issuance (a CA and a certificate-generation crate), both outside DEC-990's pre-approved kinds.
  Deferred; the binding is the same, so it can be added without a data change.
- **Bearer tokens per deployment.** A secret the plane must store and that crosses the wire on
  every call; a signature does neither.
