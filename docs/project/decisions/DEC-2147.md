# DEC-2147: An agent's mandate versions, read over the workspace API

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79, each item the reading DEC-176 lets an agent take. It adds no risk: the route writes nothing, changes no envelope, and reaches no order path; each open reading below says nothing is in effect, or nothing is classified, where the journal does not show it, and fails the read where a record cannot be read) |
| **Date** | 2026-10-28 (UTC) |
| **Decided by** | `claude-code` (lane L1, builder 4), for lane W's finding that the agent page cannot show its versions |
| **Story or claim** | E10-27; workspace API §4.7; PRD FR-3.4, FR-3.5; HLD §4 |

## Context

The web app's agent pages (`/agents/{id}/...`) show `ApiNotYetNotice` where an agent's mandate
versions belong: the server serves no read of them. Workspace API §4.1 serves a version by its
hash, and §4.7's agent read names only the deployed version. Nothing says which versions are an
agent's, which one is in effect, or where a version's classification is read from. The journal
does not link a version to an agent on `MandateVersionCreated`: only `AgentDeployed` and
`MandateConfirmed` versions 2 and 3 name the agent, and only the account stream's
`MandateVersionApplied` says a version took effect.

## Decision

1. **The route.** `GET /v1/workspaces/{ws}/agents/{agent_id}/mandate-versions` returns
   `read-models/agent-mandate-versions` (workspace API §4.7). It writes nothing, takes no query
   (any query is `invalid`), and is served in `live` and `paper` alike.
2. **Who may read.** Identity spec §4.2's "View agents, positions, decisions" row, users only until
   client tokens land (E10-14), authorized as the other §4.7 reads are: a reduction-only session
   is `reduction_only`, a role without the row `forbidden`, and a non-member, another workspace,
   or an agent no `AgentDeployed` names the one `not_found` (API-9).
3. **Which versions are the agent's.** The version its `AgentDeployed` names (deployed once,
   DEC-1173), then each `MandateConfirmed` version 2 or 3 whose `agent_id` is the agent, recorded
   after the deployment, in control-stream order. An id that only a `MandateConfirmed` names is no
   agent: `not_found`. A confirmation recorded before the deployment is not listed, since rule 77
   has it name a deployed agent's version in force and there was none.
4. **What is in effect.** The deployed version, replaced by the `new_version` of each
   `MandateVersionApplied` `applied` for the agent on the account stream of the connection the
   deployed document names (§5.1: application is the executor's). A confirmed version not yet
   applied, or rejected, is not in effect. When that account stream is not found, `in_effect` is
   `null` rather than the deployed version, since a later application could not be seen; once
   `AgentStopped` names the agent, `in_effect` is `null` and `stopped_at` its time.
5. **Classification.** A later version's is mandate spec §9.2's verdict of its confirmation's
   `base_version` → `mandate_version`, computed by `mandate-spec` from the two stored documents,
   as the confirm's own check computes it (§5.1), and `null` when the store cannot give either or
   they do not classify. It is never read from a client's `classification_shown` or another record.
   The deployed version is `first_version`, a value of its own: no earlier version bounds it, and
   the confirmation screen's `risk_increasing` for a new mandate (DEC-2101 item 4) would read as an
   increase over something.
6. **Times.** `created_at`, the first `MandateVersionCreated` naming the version; `confirmed_at`
   and `confirmation_id`, the entry's `MandateConfirmed` (for the deployment, the last one with no
   agent naming its version before the `AgentDeployed`); `deployed_at`, the `AgentDeployed`'s
   `recorded_at`; and a later version's `application`, the first `MandateVersionApplied` for the
   agent whose `causation_id` is its `confirmation_id`, as §5.5's command status matches a step.
   Each is `null` when the journal holds none.
7. **Failures.** A control stream that cannot be read is `membership_unavailable`, as every read's
   is (§3.11 item 8): authorization reads it first. An account stream the store fails, and any row
   of the five kinds folded whose members do not read, is `journal_unavailable`, never a shorter
   list or a version in effect read past a skipped record.

## Rationale

Each item takes the reading that shows no more than the journal proves: a version is in effect only
once the executor says so, a classification is the server's own and never one a client sent, and
what cannot be read fails the read. None of it widens who may see what: the row is the one every
agent read takes, and the history holds hashes, classifications, and times, not the documents.

## Alternatives considered

- **In effect is the latest confirmed version.** Refused: a confirmation may still be refused at
  application (`increase_blocked_while_latched`, §5.1), so the page would show a limit in force
  that is not.
- **The first version classified `risk_increasing`.** Refused for item 5's reason; the confirmation
  screen keeps its own value.
- **`journal_unavailable` for an unreadable control stream.** Refused: the membership read comes
  first, and §3.11 item 8 names its failure `membership_unavailable` for every read. Both are 503
  and retryable.
- **Reading the classification from `MandateVersionApplied`.** Refused: it exists only once a
  version is applied, and the stored documents give the same verdict (journal spec §9.3 refuses a
  record whose classification differs).
