# DEC-2807: Trading spec §2.3 states the client order id the executor derives

| | |
|---|---|
| **Status** | Accepted (agent, under DEC-79 and DEC-176: the spec is aligned to what accepted decisions already bind; no behavior changes, and no rule is loosened. The coordinator assigned it) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | Lane MC (Claude Code), number from the coordinator's trading-core range |
| **Story or claim** | X10a (backlog `X10-client-order-id-form.md`); trading spec §2.3, v0.21 |

## Context

Trading spec §2.3 says an order's `client_order_id` is `"{intent_ulid}-{attempt}"`, and that
`attempt` increments after the broker confirms the previous attempt `Rejected`. The executor has
never written that form, and accepted decisions bind what it writes instead:

- DEC-860 names the ids `md-<intent>`, with their protective and rung forms, and DEC-449 maps
  the runtime's requests to the `md-` ids the journal's submissions carry.
- DEC-506 and DEC-521 make the id a function of the intent id alone, so a resubmission after a
  confirmed absence carries the same id. Their property tests catch an id suffixed with its
  attempt.
- DEC-160 (11) names the watchdog's exit `md-w-<event>`.
- DEC-485 item 2 names a kill switch's flatten `md-k-<switch>-<n>`.
- DEC-876 names a broker replacement's successor `md-r-<origin>`.

§5.7 makes `Rejected` terminal, so no attempt follows one. Because §2.3 disagrees with all of
these, DEC-2803 item 5 could not bind `OrderAbandoned.client_order_id` to its intent.

## Decision

1. **§2.3 states the form the decisions bind** (v0.21). An intent's `client_order_id` is
   `md-{intent}` and a function of the intent id alone. The attempt number is journaled by
   `OrderSubmitted` but is not part of the id. It increments only on §5.7's resubmission after a
   confirmed absence, with the same id, and a rejected intent is never submitted again. §2.3 also
   names `md-r-{origin}` for a broker replacement, `md-w-{event}` for the watchdog's exit, and
   `md-k-{switch}-{n}` for a kill switch's flatten. The protective and rung forms are unchanged and
   build on the intent's id.
2. **No code changes.** `ClientOrderId` (`mandate-executor/src/ids.rs`) already derives every form
   above, and its tests and the DEC-506 property already hold them.
3. **The journal rule waits.** Binding `OrderAbandoned.client_order_id` to `md-` and its
   `intent_id` is a journal spec change with its own vectors, so it stays in the backlog row.

## Rationale

- Accepted decisions bind (`AGENTS.md` rule 9). A spec that disagrees with them misleads every
  reader and blocks rules that depend on it.
- The spec's old reading adds risk. An id that changes with the attempt would let a resubmission
  after an ambiguous absence create a second live order for one intent, which is the risk §5.7's
  same-id rule removes.

## Alternatives considered

- **Change the code to the spec's form.** Rejected for the reason above, and because it would
  overturn four accepted decisions.
- **Add the journal rule in the same change.** Rejected to keep this change to the spec text,
  with no behavior change. The rule needs a journal spec version and vectors.
