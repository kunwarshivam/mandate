|---|---|

| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The lane I4 builder (Claude Code), under DEC-79 and DEC-176 |
| **Story or claim** | E4-4 (new); PRD FR-4.1, FR-4.2, FR-4.5; HLD §6 flow B; claim [#1463](https://github.com/kunwarshivam/mandate/issues/1463) |

## Context

`mandate-backtest` runs a baseline moving-average crossover through the fill model. That proves the
loop (E4-2), but it is not the owner's mandate: the strategy sizes itself, there is no gate, no
autonomy, and no risk state. FR-4.1 asks for a backtest of a **mandate version**, and the go-live
record (mandate spec §10, `AgentDeployed`) names the backtest that was shown. A backtest that runs
other code than the live agent tests nothing the owner deploys.

The live agent's decision lives in four pure crates: `mandate-spec`'s risk state
(`risk::RiskState`), `mandate-builder` (`propose`, `classify`), `mandate-risk` (`evaluate`,
`trim_proposals`, `agent_flatten`), and the executor's protection prices
(`mandate_executor::equity_bracket_prices`). The shell only wires them; it holds no trading logic
(DEC-138 item 3). A backtest can call the same four, in the same order, with the run's own state
in place of the broker's.

## Decision

1. **The decision path.** At each decision instant `t` the run does mandate spec §6.2's steps with
   the live crates, in this order:
   1. the risk state is stepped (`RiskState::step`) over every input since the last instant, in
      time order: the risk day's start at 00:00 New York, each bar's close as a sane mark (a
      regular-session or continuous bar only, trading spec §8.2), and each fill;
   2. **risk exits first** (§6.2 step 1): when the effective mode is `paused` or `stopped` with a
      position held, the agent-scoped flatten plan (`agent_flatten`, initiator `risk_limit`) sells
      the whole sub-ledger position; otherwise `trim_proposals` proposes any `trim_to_target` sell.
      The flatten goes to the gate with origin `automated_kill_switch` and the trim with
      `trim_to_target`, and no builder call is made at that instant. A flatten a
      `flatten_and_pause` rung or the floor starts is the agent-scoped automated kill switch, whose
      orders mandate spec §5.5 and `AGENTS.md` rule 13 exempt from the agent's mode; told
      `risk_engine`, the gate would hold it under the very `paused` mode the rung sets. (The live
      executor's flatten handoff is still E7-4's; this is the reading it must match);
   3. otherwise the order builder (`propose`) sizes from the recorded outputs that are fresh at `t`;
   4. the gate's dry run (`evaluate`) judges the proposal against the run's account, agent,
      instrument, market and conduct state, as live: pass `first`, which sets the agent's own
      resting protection aside; then, when it allows, the protection is canceled (the executor
      cancels it before any agent order, trading spec §5.3) and pass `before_submission` judges
      it again with every rule in full. A second-pass refusal re-places the protection at once;
   5. for a buy, autonomy (`classify` on the builder's action) decides AUTO, ASK, or DENY (§6.2
      steps 3 to 5b: the version's rules, its default, the admission ceiling and the review
      ceiling, which `classify` applies itself). The run holds no delegation and no policy overlay
      beyond the platform base the version was validated under, so §6.2 step 4a and 5c add
      nothing: both only tighten, and leaving them out can only make the run stricter than an
      owner with a delegation. An exit is built-in AUTO;
   6. an allowed order goes to the fill model at the gate's quantity and price (its pacing, when
      it paces): a day limit order, or for a flatten priced `market_or_ladder` in the regular
      session the market order the plan prices; it is eligible from `t` plus the configured
      decision latency, so with no latency it can fill in the bar that starts at `t`;
   7. after an agent order ends with a position held and the mandate's protection on, the run
      places protection as the executor does: `equity_bracket_prices` from the latest entry
      order's limit price, as a bracket's legs are priced at submission, and the mandate's
      distances, then `protective_shape` against the connection's capability profile
      (an input), which answers a GTC OCO when there is a take-profit, a GTC stop-limit when the
      profile offers one and the mandate sets `stop_limit_offset`, or nothing, which refuses the
      run (`protection_not_placeable`): the run never invents a form the executor would not send.
      At most one order works at a time, the agent's or the protection, because the executor
      cancels the protection before every agent order and re-places it on the whole position
      after; so each order is simulated alone and no volume is shared.
2. **An ASK has no one to answer it.** A backtest has no owner at the screen. An ASK resolves as
   an approval that times out does: `skip`, no order (`AGENTS.md` rule 3, journal spec §9.7's
   `on_timeout: skip`). The report counts it as `ask_unanswered`. Assuming an approval would
   report trades the owner never approved.
3. **No look-ahead, enforced by receive times.** The decision instant `t` is the start of the bar
   after each period's closing bar, a regular-session instant, so the gate judges openings in the
   session they would trade in. The information set at `t` is the bars that closed before `t`
   (each regular bar closes at the earlier of the next bar's start and its session's end on the
   trading calendar), and the recorded outputs and theses whose **receive time** (the instant
   the record was journaled) is at or before `t`. The quote at `t` is the last close's (item 7),
   dated at that close, so it is never newer than what was known. A record whose `as_of` is after its receive time
   cannot exist and refuses the run (`record_before_its_data`). The fill model already refuses a
   fill before an order's eligibility (trading spec §6.4 rule 1), and `t` is the next bar's start,
   so nothing decided at `t` fills in a bar that closed before it. What the rule cannot rule out is
   stated in the report (DEC-1001 item 2's `limitations`): a model may have been trained on what
   happened after `as_of` (DEC-99, R-27), so an LLM agent's backtest tests mechanics, never thesis
   quality.
4. **Recorded inputs only.** The run takes model outputs and theses as typed records. It has no
   model port: there is no trait, callback or client through which it could call a model, so a
   live call is unrepresentable rather than merely untested. An instant with no fresh output holds
   (`no_fresh_outputs`), as live.
5. **Theses and the universe.** For a research-agent version the instrument is in the working
   universe at `t` while the latest thesis record for it received at or before `t` (at one receive
   time a refused record outranks an admitted one, then thesis id; [DEC-1140](earlier-900-1999.md#dec-1140) item 1)
   is admitted and has neither expired nor been invalidated at `t`. A later refused
   record ends an earlier admission, so a renewal the admission refused never keeps the instrument
   in. Two records with one thesis id refuse the run (`duplicate_thesis`). Admission verdicts are replayed as journaled, never
   re-judged: the backtest holds none of the sources an admission read. A pinned universe
   (bring-your-own strategy) is the version's own list, and theses play no part.
6. **Inputs are checked, never trusted.** A recorded output not pinned by the version (model id,
   version and content hash) refuses the run (`output_not_pinned`), as the shell refuses it live;
   a thesis or output for another instrument than the run's refuses it
   (`record_other_instrument`), so nothing is silently dropped.
7. **Quotes and marks.** Bars carry no quote. The bid and the ask at a decision are the last close moved by
   the fill model's own `half_spread_bps`, each rounded against the agent onto the tick (the bid
   down, the ask up), so the spread is the one the fills already charge. The risk mark is the bid
   (trading spec §8.2, long only), stepped into the risk state at each bar's close; the account
   ledger marks at the close itself, as E4-2's report does for both the version and the benchmark.
   The gate's participation caps read a trailing five-minute volume, which bars longer than five
   minutes do not carry; without one every opening fails closed. The run takes the last closed
   regular bar's volume spread evenly over its regular-session seconds, times 300, truncated to
   the share grid (`participation_from_bar_volume`). The daily cap reads the mean of the last 20
   periods' volumes, and the eligibility floor their lower median dollar volume, both by
   `mandate-liquidity`'s rules; with fewer than 20 periods neither exists and openings fail
   closed, as live.
8. **Slice 1's scope, refused outside it.** US equities only (`asset_class_not_supported`
   otherwise: crypto's continuous risk clock and asset fees are slice 2); regular-session bars only
   (`bar_outside_regular_session`), so every decision is at a trading day's first regular bar,
   before any of that day's orders or fills, and the day's order, fill and bought-dollar counts the
   gate and autonomy read are zero there; one instrument per run;
   long only (v1); decisions at
   each period's closing bar (the last regular-session bar of a trade date), as the E4-2 loop
   already defines an equity period. A version whose universe needs more than
   one instrument at once, and a mandate whose protection the run cannot place, refuse with a
   named code rather than run a different strategy. Corporate actions inside the bar range are
   refused (`corporate_action_in_range`) until the accounting fold's corporate-action inputs are
   wired (E4-4 slice 2); a report that silently ignored a split would be wrong by the split.
9. **Purity.** The run is a pure function of its inputs: no clock, no file, no randomness,
   ordered collections only (ES-21). The same inputs give the same report bytes.
10. **The oracle.** The property tests check, with an accumulator of their own: the same inputs give
    byte-identical report bytes; no fill is at a price better than any its bar traded (a buy at or
    above the low, a sell at or below the high), and none lies past the bar's range except by the
    fill model's own slippage against the agent, which trading spec §6.4 rules 4 and 6 charge on a
    market or stop fill (`open × (1 − s)`, `S × (1 − s)`); clamping such a fill to the bar would
    understate the cost, so the run does not; no order is decided before the first receive time of
    any output and no fill precedes its order's decision; no ASK ever fills; an exit is never
    denied by the gate and a risk exit never held or deferred (`AGENTS.md` rule 13). Each oracle is
    shown to fail on a seeded bug before it is trusted.
11. **Reference data is point in time.** The instrument reference carries its ETP classifications
    with the instant each was made; at a decision the gate reads the latest made at or before it
    and judges its age by trading spec §3.2 item 6, so a classification is never fresher than the
    data says and a stale one denies the opening, as live.

## Adversaries

- **A careless owner** backtests a version and reads the report as a forecast. The report holds
  figures and fixed codes only, under the hypothetical legend (DEC-1003), and its `limitations`
  say what it cannot know.
- **A bad model** whose recorded outputs were produced after the fact, with an `as_of` earlier than
  what they saw: receive time, not `as_of`, gates visibility, and a record whose `as_of` is after its
  receive time is refused. Hindsight through training data cannot be ruled out by any record; the
  research-agent report says so (`mechanics_not_thesis_quality`).
- **A malicious insider** edits the recorded outputs, theses, or bars to flatter a run: each is
  digested into the report and the record (DEC-1001), so a changed input is a different report.
- **A bad tick** inside the bars: the fill model fills only inside a bar's own range and the gate
  judges the collar against the last close, exactly as live; the run never fills at a price it did
  not see.

## Rationale

The point of a backtest before going live is that it runs what will run. Calling the live crates
rather than re-implementing their rules means a fix to the gate or the builder reaches the
backtest by construction and the run applies the same rules the agent does. What it cannot
reproduce, it states (`limitations`) or refuses (item 8). Every
reading here refuses more than the alternative (an unanswered ask, a record out of order, an
unpinned output, a split in range), so DEC-176 lets an agent take each.

## Alternatives considered

- **Keep the run in `mandate-backtest`.** Rejected once DEC-986 landed: the workspace services
  reach `mandate-backtest` through `mandate-modelhost`'s baseline model, and the run links the
  executor's protection pricing, so the CLI would reach an agent-process crate. The run is
  `mandate-version-backtest` (layer 8, in neither process group), which shares `mandate-backtest`'s
  fold and report encoders; a workspace service that serves `POST /backtests` runs it through the
  journal, never by linking it.
- **Run `mandate_runtime::handle` with simulated ports.** The most faithful in principle, but the
  runtime's ports are the shell's (layer 8), beside the backtest's crate, so neither reaches the
  other. Its decide step calls
  exactly the four crates above, so calling them directly is the same decision without the journal
  effects. Recorded as debt: when the shell's mapping from a mandate document to the gate's
  mandate moves into a shared crate, the backtest and the shell call one mapping (backlog E4-4).
- **Assume approvals are granted.** Rejected: it reports trades nobody approved.
- **Call the model gateway in a backtest.** Rejected: not reproducible, and it would score a model
  on a period it may have read about (DEC-99).
