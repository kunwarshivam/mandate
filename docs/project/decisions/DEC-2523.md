## Context

Journal spec §9.28 check 3 allowed an acknowledgment, and its request, only `cli_confirm` step-up: in
`paper`, and in `live` only on the founder's own connection. Identity spec §6.1 and §7.3 allow `passkey`
in every environment, and `cli_confirm` only in `paper`. The two disagreed. A browser can carry passkey
evidence but not the CLI's typed confirmation, so the workspace API's acknowledgment route, which lane
WB's screen calls, could not be accepted by the executor. No production code fills the executor's
`methods` yet; lane L1's E7-4b wiring does.

The founder's live `cli_confirm` (DEC-529 item 3, continued by DEC-923 until E9-4) is founder-reserved
under DEC-79. The coordinator's first ruling would have removed it for acknowledgments; lane GL raised
that, and the coordinator agreed to leave it unchanged.

## Decision

1. **§9.28 check 3's methods** are `passkey` in every environment, as identity spec §6.1 and §7.3 allow
   it, and `cli_confirm` in `paper`, and in `live` only on the founder's own connection (DEC-529 item 3,
   DEC-923), unchanged. The same methods judge a request's step-up in check 4.
2. **Vectors:** the executor's judgment gains `passkey_in_paper` and `passkey_in_live`, each lifting,
   beside the existing `cli_confirm` cases in paper and on and off the founder's live connection, and
   a seeded mutant that drops passkey. The reference's independent oracle states the rule in its own
   terms.
3. **The executor's code is unchanged.** It reads the methods from the shell's handoff; the shell (L1,
   E7-4b) builds `{passkey, cli_confirm}` in `paper` and `{passkey}` in `live`, with `cli_confirm` added
   on the founder's own connection. The CLI keeps `cli_confirm`; the web uses passkey.

## Rationale

Passkey is stronger evidence than `cli_confirm`: a WebAuthn assertion with user verification, verified by
workspace services, against a typed code. Accepting it wherever `cli_confirm` is accepted, and in live
where identity already allows it, admits nothing weaker, so it adds no risk (DEC-176). Every other check
is unchanged: freshness, the 300 s window judged at processing, reuse across the four record types, and
independence.

## Alternatives considered

- **`cli_confirm` never outside paper.** Refused: it would change the founder's DEC-529 item 3 carve-out,
  which is founder-reserved, and could leave the founder unable to acknowledge a limit on the live order
  from the CLI.
- **A browser `cli_confirm` path, as approvals' DEC-2104.** Refused: it builds a weaker path where a
  stronger one is already specified and served for resume and Stop.
