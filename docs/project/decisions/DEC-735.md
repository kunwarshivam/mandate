## Decision

The JSON Schemas in `schemas/workspace-api/read-models/` are the contract for these reads, one file
per resource:

- `approvals` and `approval`
- `alerts`
- `changes-event`
- `connections` and `connection`
- `timeline`

The command and mutation shapes, command status, `Envelope`, and the problem document are lane L2's.
The schemas reference the shared primitives as `../common.schema.json#/$defs/<Name>` and L2's
envelope as `../envelope.schema.json#/$defs/Envelope`. Each response is the envelope composed with
`allOf`, its own members, and `unevaluatedProperties: false`. The envelope's `as_of` may be empty, for a response that reads no
stream. Every read model here reads at least one stream, so each one narrows `as_of` to the shared
`AsOf`, which needs at least one watermark (API-14). A read model with an empty or missing `as_of`,
or with no `served_at`, is refused.

Each schema `read-models/<name>.schema.json` has a valid example,
`schemas/workspace-api/examples/read-models.<name>.json`. Beside it,
`read-models.<name>.invalid.json` lists the edits the schema must refuse, and
`read-models.<name>.valid.json` lists the edits it must still accept. The workspace API's shared
checker, `schemas/workspace-api/check_examples.py`, runs every case. It uses only the `jsonschema`
package that `reference/mandate/requirements.txt` already pins. Each of eight bugs planted in these
schemas was caught by a case.

1. **One approval serves the content object, not the fixture's shape** (§4.3).
   `GET /approvals/{id}` returns `{approval}`, which holds:
   - `content`, exactly as `ApprovalRequested` holds it and closed key by key (mandate spec §6.4,
     journal spec §9.6), and its `content_hash`;
   - the status folded from the agent stream: `requested_at`, `deadline`, `grants`, and
     `resolution`.

   The fixture's members map onto it like this:

   | Fixture member | Served as |
   |---|---|
   | `bound` | `content.action`, plus `content.trigger.mandate_version`, `content.trigger.decided_by`, and `content.evidence.combined_score` |
   | `trigger` | No member. The client words it from `content.trigger` |
   | `risk_impact` | `content.risk_impact`, all six fields |
   | `evidence` | `model_outputs`, each a `QuotedContent` (API-18), named by event id in `content.evidence.outputs` |
   | `approvers_required` | `content.approvers.required` |
   | `approvals_so_far` | `grants` |
   | `resolution.text` | `cancel_reason`. There is no free text |
2. **No advice rides on an approval (DEC-126).**
   - The approval object is closed.
   - No member may be named for a scorecard, profit, a price target, an expected return, a win
     rate, or performance.
   - The score label is exactly "combined model score, not a probability of profit".
   - `choices` starts with `approve` and then `skip`. Delegation shapes may follow, and nothing
     else.
   - Decimals are strings, so a JSON number is refused.
3. **The content's newer members are optional.** A version-1 record's `trigger` carries
   `mandate_version` and `decided_by` only. DEC-181 and DEC-185 add `requested_by`, `client`, and
   `rule`. When `rule` is present, it must match `mandate.schema.json`'s own `rule` definition.
4. **A change notice is `{stream_id, seq}` and nothing more** (§3.1). Each `/changes` event is
   `watermarks: [{stream_id, seq}]`, with at least one entry. It carries no hash, time, event type,
   or content, even though the shared `Watermark` has a hash and a time. The client refetches what
   it shows.
5. **Alerts carry no text, and their kinds are closed.** Each alert is one `OwnerAlertSent`. It
   names:
   - its `kind`;
   - its subject event, as `{stream_id, seq, event_type}`;
   - its agent or connection, either of which may be `null`;
   - the screen that resolves it.

   `kind` is a closed enum (§3.2). Its values are the notifications spec §3.2 catalogue kinds whose
   cause is an `OwnerAlertSent` (journal spec §9). That is every kind except `approval_requested`
   and `approval_reminder`, whose cause is the `ApprovalRequested`, and `channel_lost`, which is
   the dispatcher's own record. A kind's class (`safety` or `info`) is §3.2's, so it is not served
   again. A new catalogue kind is a new major version, as §3.2 says of safety enums.
6. **A connection is a reference** (API-11).
   - It returns only the fields that connections spec §3 lets the API return:
     - `connection_id`, `broker`, `environment`, `scopes`, `auth_kind`;
     - `account_ref`, `state`, `contract_hash`, `checks`, `terms_version`.
   - It adds the read-model fields O4 shows:
     - `account`: state, equity with its freshness, and day-trading regime;
     - `data_profile`, `agents_granted`, and `loss_carry_usd`.
   - The connection and its `account` are closed.
   - No member may be named for a token, secret, password, credential, key, account number,
     fingerprint, or vault.
7. **The timeline pages per stream, and gate entries carry a summary** (§4.8).
   - Each event names its `event_id`, `stream_id`, `seq`, `event_type`, `recorded_at`, `kind`,
     and deterministic `text`. The text is built from the event's own members and never from
     model output.
   - Entries are a union tagged by `kind`. A `gate` entry has `event_type` `GateDecided` and a
     closed `gate` summary: `{verdict: allow | deny | defer, reason_code, action: {side, qty,
     symbol, limit_price, purpose}}`. The reason code is `null` exactly when the verdict is
     `allow`.
   - Every other kind is closed to the fixture's other seven, and carries no summary.
   - The entry's `event_id` links to the full per-check record, `GET /journal/events/{id}/gate`
     (J6). That record belongs to lane L5's `audit/` schemas.
   - The response carries one cursor per stream read, and `complete`.
8. **Conventions for L2's drift check.**
   - Objects are closed with `additionalProperties: false`, and enums are closed.
   - Nullable inline members are written as `type: [..., "null"]` or as an enum that lists `null`.
   - A nullable `$ref` is written `oneOf: [{$ref}, {type: "null"}]`.
   - The one tagged union, the timeline entry, is `oneOf` with `kind` as its `const` discriminator.

## Gaps

- **G5 is narrower than the alert enum.** G5 lists a subset of the catalogue: rung, reconciliation,
  stale feed, agent held, external activity, account restriction, the 1× check, model and lineage
  status, policy nonconforming, protection, and stalled exits. The enum follows the catalogue,
  because `GET /alerts` serves every `OwnerAlertSent`. Which kinds G5 shows by default is a screen
  choice and needs no API change.

## Rationale

The web app moves from fixtures to these resources (E11-9). Where the spec is exact, each schema
follows it. Where the spec leaves a gap, each schema takes the closed, smaller shape and checks it
against a validated example. Every claim in the items is one of the invalid or valid cases.

## Alternatives considered

- **Serve the fixture's `Approval` shape as it is.** Rejected. Its `trigger` and `resolution.text`
  are free text, and `bound` has a different shape from the hashed content. The approver would then
  see something other than what the hash covers (API-12).
- **Use the full `Watermark` on the change stream.** Rejected. It adds a hash and a time that §3.1
  leaves out of change notices.
- **An open set of alert kinds.** Rejected. §3.2 closes enums whose values change meaning, and the
  UI must never meet an alert it cannot classify.
- **Serve each alert's class.** Rejected. It repeats a fact that is fixed by its kind.
