# DEC-660: The workspace's WebAuthn relying party: dependencies, algorithms, and strict readings

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | Agent (lane L1 builder), under DEC-79 (reversible engineering choices) and DEC-176 (every reading below tightens the spec and adds no risk) |
| **Story or claim** | E9-1, claim [#758](https://github.com/kunwarshivam/mandate/issues/758); identity spec §6.1, §6.3, §7.2 step 4 |

## Decision

1. **A new crate, `mandate-passkey`** (layer 2, pure, safety-critical). Its `enrol` reads a
   registration response and returns the credential to store, and its `verify` checks an
   assertion against a stored credential. It only verifies: it never signs, holds no private key,
   and reads no clock and no randomness.
2. **Dependencies.**
   - `ring` 0.17.14 verifies signatures. It is already in `Cargo.lock` through `rustls`, so it adds
     no crate.
   - `base64` 0.22.1 encodes the issued challenge for the comparison. It is already in
     `Cargo.lock` through `sqlx`.
   - `serde` and `serde_json` read `clientDataJSON`. `mandate-canon`'s strict parser refuses its
     camelCase members (`crossOrigin`), so it cannot be used for this.
   - `mandate-canon`'s `Digest` provides SHA-256, so `sha2` is not taken directly.
   - The crate reads the small CBOR subset WebAuthn needs with its own parser rather than taking a
     CBOR crate.

   `ring` depends on `getrandom`, but only for `SystemRandom`. The crate never calls it; only the
   tests' software authenticator does, to generate keys.
3. **Algorithms.** ES256 (COSE `-7`, P-256) and EdDSA (COSE `-8`, Ed25519). RS256 is not
   supported in v1: `ring` cannot generate RSA keys, so the software authenticator cannot test
   it. Any other algorithm is refused as `algorithm_unsupported`. Passkey platforms all offer ES256.
4. **Strict readings**, each of which refuses something the WebAuthn standard leaves to the
   relying party:
   1. **Attestation.** Only the `none` format is accepted, and only with an empty statement.
      Attestation is not required in v1 (§6.1), and an unverified statement is not kept.
   2. **Origin.** The relying party has exactly one origin, and `clientDataJSON.origin` must equal
      it byte for byte. A prefix, a subdomain, an explicit default port, or a different case is
      refused.
   3. **Cross-origin frames.** `crossOrigin: true` is refused. An absent member is accepted.
   4. **Challenge.** It must have at least 16 bytes. `clientDataJSON.challenge` must be exactly
      its base64url form without padding; standard-alphabet and padded forms are refused.
   5. **`clientDataJSON` structure.** It must be a JSON object starting at its first byte. A
      duplicate of any member the relying party reads (`type`, `challenge`, `origin`,
      `crossOrigin`) is refused. Other members are ignored, as the standard requires,
      duplicates included: a member the relying party never reads cannot change a value it
      checks.
   6. **CBOR.** Definite lengths only. Tags, floats, `undefined`, and indefinite lengths are
      refused. A duplicate map key is refused. Nesting is limited to eight levels below the
      outermost item. A longer length form than a value needs is read like the shortest one.
   7. **Authenticator data.** Nothing may follow what the flags announce. With `ED` set, the
      remainder must be exactly one CBOR map. An assertion with `AT` set is refused. A credential
      ID must have 1 to 1023 bytes.
   8. **Flags.** Both user presence and user verification are required, at enrolment and at
      every assertion (§6.1). Backup state without backup eligibility is refused, and so is an
      assertion whose backup eligibility differs from the one recorded at enrolment.
   9. **Counter.** A signature counter equal to or below the stored one is refused, not just
      one that went backwards (§7.2 step 4). Only a counter that is zero on both sides passes,
      as "not kept".
   10. **Credential ID.** The assertion's credential ID must equal the stored credential's.

## Rationale

The relying party must run inside the workspace deployment without any outside service (ID-10;
identity spec §6.1). Each of the readings in item 4 refuses an input that the standard allows a
relying party to accept, and none of them makes a valid passkey from a supported authenticator
fail. A refusal here never blocks risk reduction: pausing and the kill switch need no step-up
(ID-5). Only the reduction-only session of §6.4 route 2 uses a passkey, and an owner who is
refused can still use routes 1 and 3.

## Alternatives considered

- **`webauthn-rs`.** It brings OpenSSL and about 60 crates, its attestation verification is not
  needed in v1, and it would be a large new surface in a safety-critical crate.
- **`ciborium` or `minicbor` for CBOR.** A new dependency for perhaps 120 lines of parser that the
  mutation gate fully covers.
- **RustCrypto `p256` and `ed25519-dalek` instead of `ring`.** These are new crates, while
  `ring` is already built for TLS.
- **Accepting a counter equal to the stored one.** The standard treats it as a signal of a
  possibly cloned authenticator, and refusing it costs nothing for an authenticator that keeps
  a counter.
