521 to 523 are held on other branches; 524 was free on `main` and every branch when it was
reserved (DEC-516 item 6).

## Decision

1. **The tests PR carries the parse, and only `maintenance_excess` is a stub.** This departs from
   DEC-83's "tests PRs contain stubs only, not logic" for one thing. `BrokerAccount` gains two
   public fields, `last_equity` and `maintenance_margin`, so every constructor must supply them,
   and that includes `mandate-alpaca`'s `wire::account`. Each of `wire::account`'s other choices
   is worse:
   - It could invent a value, such as zero. That fabricates a broker fact, and a zero maintenance
     margin is the least safe reading of all.
   - It could fail every account parse until the implementation PR. That breaks passing tests
     (the recorded account reads and the tracer), which `AGENTS.md` forbids disabling.

   So the tests PR parses both members with the module's existing `usd` reader. As every other
   account field is, each is required, and a missing member is refused as `missing_field`. That
   parse is pinned by ordinary tests that pass in the tests PR: `tests/margin.rs` in
   `mandate-alpaca`, against both recorded accounts and an edited body whose members all differ.
   `BrokerAccount::maintenance_excess` (`mandate-executor/src/margin.rs`) is the stub that
   returns `Unimplemented { story: "E7-19" }`, and the pending tests stop at it.
2. **Maintenance excess is equity less `maintenance_margin`, signed.** A positive value is an
   excess and a negative one is a deficit (trading-domain spec §9.2): a deficit is never floored
   at zero, and nothing is rounded. A negative `maintenance_margin` is refused as
   `NumError::Negative`. The spec states no such requirement, and subtracting one would raise the
   excess above equity, so refusing it only tightens and adds no risk (DEC-176). A difference that
   does not fit a `Usd` is refused as `NumError::Overflow`, never clamped.
3. **Neither figure is journaled.** `AccountStateObserved` and `AccountSnapshotRecorded` are closed
   at schema version 1 (journal spec §9, DEC-458), and the brief keeps their payloads unchanged.
   `account_fields` is untouched. `reconcile.rs`'s
   `the_fee_steps_snapshot_reads_the_account_it_is_given` sets both new fields to values that
   differ from equity, and its hand-written expected payload has neither member.
4. **`last_equity` is read as it stands.** The executor derives nothing from it. It is the
   prior-close equity that §9.2's `legacy_pdt` threshold compares with. Q2 maps it into the gate's
   `prior_close_equity`, and maps `maintenance_excess` into `DayTradeRegime::IntradayMargin`.

## Rationale

1. The two alternatives each break a rule that ranks above DEC-83 (`AGENTS.md` rule 3, and "Do
   not disable tests"). The parse is two lines through a reader the rest of the module already
   uses. The tests pin it before any consumer exists, and the mutation gate still covers it.
2. Trading-domain spec §9.2 checks "broker-reported maintenance excess" and acts on "a deficit".
   A signed difference is the only reading that reports both. A refusal is the safe default for
   a value no broker states.
3. A closed schema changes only by a journal spec revision, and nothing on the first trade's path
   needs either figure replayed. Q2 reads them in the run that uses them.

## Alternatives considered

- **Fill the new fields with zero in the tests PR and register the pending parse tests as
  behaviour-only** (`BEHAVIOUR_ONLY_TESTS`). Rejected: shipping code would carry a fabricated
  maintenance margin, and the exception list would grow for a slice that can avoid it.
- **Accessor methods instead of fields.** Rejected: the implementation PR would then have to add
  the fields to struct literals in `tests/` files, which DEC-77 item 2 forbids.
- **Journal the two figures in a new schema version.** Rejected: that is a journal spec change,
  out of A1's scope. It is left for whoever needs the gate's inputs replayed.

## Not decided here

§9.2's "if the broker reports a deficit, agents go `exits_only` and the owner is alerted" has no
implementation yet. The gate deliberately denies nothing per order on it: `mandate-risk`'s
`a_reported_deficit_is_an_account_state_not_a_denial` says a deficit reaches check 1 as a mode.
Nothing turns a negative `maintenance_excess` into that mode. With 1× long-only exposure no approved
order creates a deficit (§9.2), so it is not on the first trade's path. It is recorded under E7-19
in the backlog.
