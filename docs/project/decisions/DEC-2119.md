## Context

DEC-653 built route 2's gate as `mandate_authn::reduction::ReductionGate`. Its item 3 holds two
readings that DEC-2117 contradicted:
- every refusal of the challenge route is the same one 401 as the assertion route's, so no
  refusal tells a limit from anything else;
- a failed assertion counts for 300 s, and the failure limit only reports. That second reading is
  the founder's, accepted 2026-10-09.

DEC-2117 answered the challenge route's limit with 429 `rate_limited` and counted failures over
15 minutes. DEC-653's memory note also asks the HTTP layer to bound how many keys reach the gate,
and DEC-2117 left the failure keys unbounded.

## Decision

1. **The challenge route over its limits answers the one 401** (DEC-653 item 3). This replaces
   DEC-2117 item 3's 429 and `Retry-After`. §3.5's `rate_limited` row reverts to the principal's
   limit alone.
2. **Failures count for 300 s and only report** (DEC-653 item 3). This replaces DEC-2117 item 3's
   15 minutes. At most 10 per device and 100 per address are kept. No answer of either route
   depends on them, and reaching the limit is recorded as the abuse signal. A verified assertion
   is never refused (DEC-834).
3. **A native IPv6 address counts as its /64 prefix.** This adds to DEC-2117 item 4. One client
   cannot rotate addresses inside its /64 to escape its budget. An IPv4 address counts as itself,
   and so does an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`), the peer's or a forwarded one, read
   as its embedded IPv4 address; otherwise every IPv4 client behind a dual-stack listener would
   share one `::/64` budget (the reviewer's B1). A client holding a /56 or a /48 can still rotate
   across its /64s; the global cap and its reserve (item 11) bound that.
4. **The gate's memory is bounded in all** (the reviewer's B2). The gate on `main` holds neither
   bound today, so both are owed by S2's gate change (E9-1), with tests first, since
   `mandate-authn` is safety-critical:
   - `ReductionLimits` gains `max_outstanding`, 4,096 as DEC-2117 item 3 says, past which the gate
     refuses a challenge as `Unauthenticated`;
   - it gains `reserve`, 3,072, past which an address that already holds a challenge gets no more
     (item 11);
   - it also gains `max_failure_keys`, 65,536 addresses and devices together, evicting the oldest
     failure key first. Dropping one changes no answer, since failures only report.

   Until that lands, the challenge route holds the 4,096 bound and the reserve itself, in front
   of the gate (S1).
5. **DEC-2117 item 5's one 401** now also answers the challenge route over its limits. A
   malformed challenge request is still `invalid`, as §4.10's table says, since a body tells nothing
   about any member.
6. **No idempotency key** (F1). Both route-2 POSTs are exempt from `Idempotency-Key`: each
   challenge has a fresh id and is used once, so a retried opening asks for a new challenge.
7. **The session's origin** (F2). A route-2 session stores a marker that route 2 opened it, which
   no answer exposes. The refresh route refuses such a session `reduction_only` even when the
   provider answers. A session an outage narrowed (route 1) is still restored by a granted refresh
   (DEC-816 item 8). A session cookie presented with the opening ends that earlier session only
   once the assertion verifies.
8. **No oracle by structure** (F3). Past the challenge, every opening runs the same steps:
   - the passkey lookup reads the whole fold without stopping at a match;
   - the signature is verified first, against the passkey's key or, for an unknown passkey, a
     fixed decoy key chosen by the signature's encoding, since authenticator data names no
     algorithm: a DER ECDSA structure against the ES256 decoy, 64 raw bytes against the Ed25519
     decoy, any other shape against the ES256 decoy (the reviewer's B1 on a2d21229). S2's tests
     pin that a known passkey of each algorithm and an unknown id with each signature shape run
     the same verification;
   - the membership and provider-refusal lookups always run, against a decoy principal when the
     passkey is unknown;
   - only then are the results judged.

   A challenge-level refusal costs no verification and is distinguishable by timing. It tells
   nothing about a member, and identity spec §6.4's timing claim covers membership and passkey
   state only.
9. **The abuse signal** (F4) is the operator alert `reduction_failures_over_limit`, an opaque
   code naming no address, device, member or passkey.
10. **The device cookie** (F5) comes from the operating system's generator. A dev or ci cell
    served over plain `http` keeps no `Secure` cookie, so it gets a fresh device on every call.
    That is intended, and the address limit is the bound there.
11. **The peer match** (F6).
    - `MANDATE_API_INGRESS_PEERS` lists exact addresses, no ranges, and any other entry refuses
      the start. Peers match after an IPv4-mapped address is read as IPv4.
    - From a listed peer, `X-Forwarded-For`'s lines are one list, walked from the right, skipping
      every listed peer. A missing or unreadable entry falls back to the TCP peer.
    - The rule cited is DEC-822 item 7, not item 4 as DEC-2117 said.
    - The last 1,024 of the 4,096 challenge slots are a reserve: past 3,072 outstanding, an address
      that already holds one gets no more. The residual is that a flood from about 1,100
      addresses (IPv6 /64s) re-asking as slots free can hold every slot while it lasts.
12. **Membership** (F7). The session covers each workspace where the member holds a membership
    that reaches its scope (`active` or `cooling_off`, identity spec §5.1), with the roles in effect
    at the opening as §8.3 allows. This replaces DEC-2117's "`active`". It widens only risk
    reduction, which rule 13 covers. A passkey in its enrolment cool-off can open one, as identity
    spec §10.1 says.
13. **The rest of the reach** (F8).
    - Route 2 neither reads nor advances the signature counter, and clone detection is out of
      scope.
    - Opening commits `SessionOpened` with the method `passkey_local` once the journal registers
      the event.
    - Sign-out is in reach.
    - The kill switch is the stop alone: the step-up challenge route refuses the session, so its
      privileges beyond the stop are refused, and the kill switch is routed without them, as
      §5.4 routes any kill switch without valid step-up.
    - The opening and `GET /v1/me/session` carry each workspace's `agent_ids` and
      `connection_ids`, read at the answer, so a session that reads nothing else can name a pause
      or kill-switch scope. A failed read answers empty lists, never a refusal (DEC-642 item 10).
    - The alert `reduction_failures_over_limit` is registered in infrastructure design §8.2.
    - API-4 and §3.4 name route 2's two POSTs as the exception to `Idempotency-Key`.

## Rationale

The challenge route holds nothing secret. A distinct answer for a limit still tells a flooder
when the flood bites, and DEC-653 already chose one answer for the whole route. Keeping the
founder's reading, that the failure limit only reports, means nothing a flooder sends can deny a
member who holds a valid key.

Device keys are client-chosen, so a flood of fresh device cookies would grow the failure maps
without bound. A cap that drops the oldest is safe only because failures decide nothing. The /64
rule closes the IPv6 version of the same escape for addresses.

## Alternatives considered

- **Keep 429 with `Retry-After`.** Refused: it contradicts DEC-653 item 3, and the web app can
  simply retry a 401 on this route.
- **Supersede DEC-653 instead.** Refused: its item 3 reading is the founder's, and the gate on
  `main` implements it.
- **Count IPv6 by the full address.** Refused: a client holds a whole /64 and could rotate within
  it freely.
