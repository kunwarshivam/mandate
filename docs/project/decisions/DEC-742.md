## Decision

1. **Shapes.** These response bodies are the JSON Schema 2020-12 documents under
   `schemas/workspace-api/read-models/` that workspace API §4.10 lists:
   - `mandate-draft`, for `GET /mandate-drafts/{id}`;
   - `mandate-validation`, for the result of `POST /mandate-drafts/{id}/validate`;
   - `mandate-version`, for `GET /mandate-versions/{hash}`;
   - `mandate-diff`, for `GET /mandate-versions/{hash}/diff`;
   - `mandate-confirmation`, for `GET /mandate-versions/{hash}/confirmation`.

   They share `mandate-common`. The mandate document itself is `schemas/mandate.schema.json`,
   referenced by its `$id`, not copied. The request bodies are §5.1's and lane L2's. This takes the
   version read that DEC-741 item 8 left to E10-11.
2. **Provenance entries carry the value at their path**, as `MandateVersionCreated` records "every
   `platform_proposed` value and what was proposed" (mandate spec §10). The provenance rules can
   then be schema conditions rather than review items:
   - `user_stated` exactly when a quote is present (§2.1);
   - every `auto` (a default, an admission, a rule's `then`, a whole rule, or a rule list holding
     one) and every delegation is `user_entered` (V-022, MI-12);
   - no `platform_proposed` pinned instrument, environment, or connection (V-038);
   - a `platform_default` only on §7's fields, with §7's values (V-020).
3. **The three answers** (E10-7). A draft whose `origin` is `three_answers` must hold `user_stated`
   entries for `/capital/allocation_usd`, the goal, and `/capital/max_loss_from_allocation`.
4. **A compiled draft passes the mandate schema.** A saved draft may not yet (the form and YAML
   editor save work in progress); validation reports why.
5. **Validation results.**
   - `valid` holds exactly when `violations` is empty.
   - A violation is tagged `rule` (a V-code) or `policy`. A policy violation names the key, the
     violating level and value, and the nearest ancestor's level and value (mandate spec §4.3).
   - Warnings carry their W-code.
6. **Diffs.**
   - The version's classification follows from its paths' classifications (§9.2).
   - `applies` follows from that classification (§2.2).
   - `cancels_pending_approvals` is always true.
7. **Confirmation data.**
   - Step-up is required for a new mandate and for a risk-increasing version.
   - The crypto gap disclosure is present, by document and version, exactly when crypto is an
     allowed asset class.
   - `unasked_usd` is DEC-189's figure, display only.
   - The research-agent flag selects DEC-126's statement.
   - Worst-case figures are §4.2's four dollar amounts.
   - No profit estimate, scorecard, or model text can appear.

## Rationale

The mandate spec already states each of these rules. As schema conditions, a response that breaks
one fails its schema, and each has a refused case in the examples. That covers MI-12, which the
mandate spec checks "by the semantic cases, not fuzzed". Carrying the value with each provenance
entry is what makes V-022 and V-020 checkable at the response, since a source alone cannot show
that a proposed value is `auto`. Every choice narrows a response or restates an existing rule, so
DEC-176 lets an agent accept it.

## Alternatives considered

- **Provenance without values.** This matches the web fixture's `FieldProvenance`, but V-022 and
  V-020 would then be unverifiable from the response.
- **Requiring every draft to pass the mandate schema.** It would refuse the form editor's work in
  progress, which §4.1's save allows and validation reports.
- **Copying the mandate schema's members into the version read.** Two copies would drift; the
  `$id` reference keeps one source.
- **Deep-scanning proposed values for `auto` at any depth.** JSON Schema cannot express it
  generally. The covered shapes (a scalar, a rule, a rule list, and the autonomy object's
  `default`, `admission`, and `delegations`) are every place §6 puts an `auto` or a delegation.
