# DEC-427: The gate's quantity grid is the instrument's own `qty_increment`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-03 (UTC) |
| **Decided by** | the stream G builder (claim [#123](https://github.com/kunwarshivam/mandate/issues/123)) under DEC-79 and DEC-176. It only rounds a risk-reducing trim up, slices a participation cap down, and lets DEC-423's full close reach the venue's own whole position, so it adds no risk |
| **Story or claim** | E6-4, "read the instrument's real quantity grid for a trim" (#466 review, round 1, m3; #530 review, m6); this tests PR is DEC-77 stage 1 |

## Decision

1. **The field.** `InstrumentSnapshot` gains `qty_increment: Qty`, the venue's quantity grid
   (trading-domain spec §2.1): an order quantity is a whole number of it. Whole shares are `1`.
2. **Who reads it.** `trim::proposals` rounds a trim **up** on it (mandate spec §5.5), and
   `conduct::slice` truncates both participation caps **down** to it (trading-domain spec §9.6),
   through one function, `trim::quantity_grid`. Neither reads a grid from `fractionable` any more,
   which knew only whole shares and nine places, while venues use others (DEC-128 item 27 found
   `0.0001` and `0.000001`).
3. **`fractionable` stays** for what it means elsewhere (eligibility, protection of the whole-share
   part). It no longer decides a quantity grid.
4. **The tests PR (DEC-77 stage 1).** Every snapshot states the grid it was already read on:
   `1`, or `0.000000001` where it is fractionable. `quantity_grid` answers that reading and refuses
   any other `qty_increment` as `GateError::Unimplemented("the venue's quantity grid", "E6-4")`.
   So nothing on `main` changes, and only the three pending tests reach the refusal:
   - `trim::tests::a_trim_rounds_up_on_the_venue_s_quantity_grid` and
     `hand::a_trim_rounds_up_on_the_venue_s_quantity_grid`: on a 0.0001 grid at 600,000, 0.0002
     held at factor 0.02 trims the whole 0.0002 (a full close below a 0.001 minimum, the #504
     review's case that DEC-423's Rationale left to this story); 0.001 held at factor 0.3 trims
     0.0003; and with 0.0001 resting, 0.0002.
   - `gate::tests::a_slice_truncates_to_the_venue_s_quantity_grid`: on a 0.25 grid an owner's exit
     of 10 is sliced to 9.75 by the order cap and to 9.25 by the daily cap.
5. **The implementation PR** makes `quantity_grid` return `qty_increment` and has `slice` truncate
   on it, and deletes only the `#[ignore]` lines.
6. **The harness PR after it.** The family-B harness and the trading-domain gate driver state
   `qty_increment` from the case (`qty_increment`, or a pair's `min_trade_increment`) rather than
   the `fractionable` reading, so the reference, the harness and the gate share one grid (#530
   review, m6).

## Rationale

A grid read from `fractionable` is a guess. On a coarser venue grid the gate could size a trim the
broker refuses as off-grid (§5.3 rule 2), or miss that the trim is the whole position and withhold
it below the minimum, which DEC-423 forbids. Rounding a trim up on the coarser grid only sells more
of an over-target position, and it never sells more than is unsold. Truncating a participation
slice to it only slices smaller. Both directions reduce risk, so the reading is a tightening under
DEC-176.

## Alternatives considered

- **`Option<Qty>`, with `None` read from `fractionable`.** Refused: it keeps the guess alive for any
  caller that omits the field, which is the defect this fixes.
- **A grid table in `GateConfig`, keyed by instrument.** Refused: the grid is a property of the
  instrument the snapshot already describes, and a second source could disagree with it.
- **Change `mandate-num`'s `ShareIncrement` to carry a grid.** Refused for now: it is a shared
  crate, and `UsdExact::truncated_quotient` and `ceiled_quotient` already take a `Qty` grid.
