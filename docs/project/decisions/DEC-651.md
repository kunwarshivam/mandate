## Decision

1. **The exception.** Three PRs of the `mandate-authn` A1 stack may exceed ES-13's 400-line
   split threshold (DEC-253 item 3). Each is counted over its own diff against the PR below it,
   in `crates/mandate-authn/` alone, as the review fix push of #791 leaves them. The A1b and
   implementation reviews each confirm their own final count:
   - **#791 (A1a):** the crate, its stub API, the in-memory issuer, and the algorithm, header,
     key, signature, issuer, and check-order tests. 920 lines:
     - stubs 330 (`lib.rs` 160, `oidc.rs` 119, `jwks.rs` 33, `Cargo.toml` 18);
     - harness 291 (`tests/common/mod.rs`);
     - tests 299 (`tests/oidc.rs`).
   - **A1b:** the claims, shape, key-set, property, and ID-9 canary tests. About 730 lines after
     its reviews asked for the extreme-time, claim-type, key-set, signature-length, base64,
     canary, two-audience, and nonce-case cases, and for a valid token to verify before each
     signature refusal: `tests/claims.rs` 250, `tests/shape.rs` 457, `tests/oidc.rs` 8, the
     harness's `sign_input` 6, and the `proptest` dev-dependency.
   - **The A1 implementation:** up to about 460 lines added to `src/oidc.rs` and `src/jwks.rs`, in
     place of the stub bodies.
2. **No split.** The three PRs land as they are, in stack order, each brought onto `main` after
   the one before it merges. DEC-77 holds:
   - the implementation changes the tests only by deleting ignore lines;
   - each PR passes the mutation gate with 0 missed mutants.

## Rationale

- **Every test needs the stub API and the harness.** They make up 621 of #791's 920 lines. The
  harness is the in-memory issuer that identity spec §1.3 requires, and it mints every token any
  A1 test reads. Splitting it from the tests would ship a harness with nothing exercising it.
- **The review asked for the overage.** The #791 review added the header-key, ES256-form,
  check-order, and per-issuer algorithm tests, and widened the confusion secrets and `alg`
  spellings. The reviewer judged the exception justified and advised against splitting.
- **Splitting further** would add review cycles over the same harness and catch nothing new.

## Alternatives considered

- **Split #791 into the harness and the tests.** Rejected, for the first rationale's reason.
- **Trim the stub docs.** Rejected: they are the reading that the review checks the
  implementation against.
