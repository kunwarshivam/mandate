## Context

`ApprovalRequested` version 3 (journal spec §9.6, DEC-2515) names, in `content.deferred_to_binding`, the
checks the dry run left to the binding gate, and the approver is shown them under a fixed sentence
(mandate spec §6.4). Versions 1 and 2 name none. The single approval read (`GET /approvals/{id}`)
served `content` but not its version. The web app therefore read an absent list as "nothing deferred",
which is right for versions 1 and 2. A version 3 request without its list is refused by the journal
(rule 291), and rule 292 ties it to its decision within a batch, but across batches (debt
`E21-30-approval-deferral-range-check`) a split writer could have one served. The screen would then
show no disclosure rather than say it could not tell. That was the one reading where ambiguity did not
resolve toward disclosure (non-negotiable 3).

## Decision

1. **The single read serves `schema_version`:** the `ApprovalRequested` version `content` comes from,
   `1`, `2` or `3`, the journal row's own version. It is required in `read-models/approval`. The
   inbox (`read-models/approvals`) carries no content and no version.
2. **The schema ties the list to the version:** a version 3 approval's `content` requires a non-empty
   `deferred_to_binding` list of names, and a version 1 or 2 approval's content has none.
3. **The web app reads by version:** version 3 with a readable list shows its checks; version 1 or 2
   without a list shows none; anything else (version 3 without a list or with an unreadable one,
   version 1 or 2 with a list, or a version it does not know) says the checks cannot be read and offers
   Skip only, never Approve. The read model refuses a read without a version, so no approval renders
   without one.
4. **No journal change:** the version is the row's `schema_version`, already stored and hashed.

## Rationale

The approver must never be shown "nothing deferred" for a request that deferred checks. Serving the
version makes that reading decidable instead of assumed, and an undecidable read resolves to Skip,
which adds no risk. It is additive to the API (one member on one read), and the web app and the API
change together.

## Alternatives considered

- **The web app treats every absent list as unreadable.** Refused: every version 1 and 2 request would
  then offer Skip only, which blocks approvals the journal holds correctly.
- **The server refuses to serve a version 3 request without its list.** Refused for now: the journal
  already refuses to write one, and hiding a pending approval from the inbox would hide that it
  exists. The web app's refusal to offer Approve is the narrower response.
