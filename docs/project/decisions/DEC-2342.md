## Context

Once the token exchange has stored a connection's token, its executor checks the account and
journals `ConnectionChecked` (occasion `connect`) on the account stream. The control services,
which are the API process (journal spec §9.8), must then establish the connection or refuse it,
and tear the connect down if nothing finishes it in time. `plan_finish` (DEC-884) decides between
those given a fold and an outcome; nothing called it, and the specs leave several readings open.

## Decision

1. **The scopes.** `ConnectionChecked` names no scopes, and the API cannot read the token. The
   scope check passes on exactly `data` and `trading`, so an establishment records exactly those.
2. **The deadline** runs from the open request's `recorded_at`, for 660 seconds: the code's ten
   minutes and one more (connections spec §5.2 step 6's Proposed eleven).
3. **The teardown order** (E10-21, and journal spec §9.8, which says the credential was deleted
   before the refusal): the connection's code and token entries are deleted, then the refusal is
   appended, then both are deleted again, retried until each is absent. A code written in the
   window before the close is gone after it. The teardown never touches
   `personal/accounts/` (DEC-2339 item 4). No token is revoked at Alpaca: DEC-821 allows the
   live host no second request. The exchange and the executor are stopped by the deployment
   manager on the closing record (DEC-1175 item 3, DEC-2335 item 4).
4. **The teardown's reason.** The API sees no pods, so:
   - `timeout`: past the deadline, with no check and no other answer;
   - `restart_past_deadline`: the same, found on the first pass after the API starts;
   - `start_failed` and `executor_stopped`: only once a journaled record shows them. Until then
     the reason is `timeout`.
5. **Only an open version-2 `oauth` request is finished here** (DEC-2621 item 3). Any other open
   request waits, past its deadline too: it is not this writer's.
6. **What is read.**
   - The request is folded from the control stream (rule 131).
   - The check is the latest `ConnectionChecked` of the connection with occasion `connect` on its
     account stream. It has passed when every result is `passed` with a non-null
     `account_pii_ref`, and failed with the first failed result's reason otherwise.
   - A row about the connection that cannot be read so leaves the fold unanswered. Nothing is
     appended, and the next pass reads again.
7. **Checks 3 and 4 go through a port, `Fingerprints`**, which judges the account behind the
   check's reference against the request and every established connection: unique, a mismatch,
   held by another connection, or cannot answer.
   - Connections spec §3.1 holds: the vault computes the keyed fingerprint, and the API receives
     only the hash, never the account id and never the `personal/accounts/` entry. The coordinator
     took that reading over DEC-2339 item 3's under DEC-176, as the one that adds no risk.
   - The backing (a fingerprint key held in the vault, the hash operation, and a persisted
     registry for check 4) is lane V2's F3, under its own decision. None of it exists yet.
   - Until a backing lands, the port answers "cannot answer". Nothing is established, nothing is
     refused on it, and each connect reaches its deadline's teardown. The API never reads a raw
     account id to fill the gap.
8. **The order of a pass's decision:**
   - a request not open, or an unreadable fold or check, goes to `plan_finish` as it is;
   - a failed check refuses with its reason, its `causation_id` that check;
   - a passed check judged unique establishes, `ConnectionEstablished` version 2 caused by that
     check (rule 63; DEC-2341's copy depends on it);
   - a mismatch or a holder refuses with `causation_id` `null` (rule 65);
   - otherwise the deadline decides.
   - The refusal names `connection_id` and occasion `connect`, which is what the executor drains
     on.

9. **The records the finish writes** go on the control stream `ctl:{workspace}`, in the request's
   `environment`.
   - **Actor:** `{kind: system, id: connection_manager, version, build}`.
   - **Event id:** derived, so a retried append writes the same event, as §3.4's ids are. It is the
     ULID of the first 128 bits of the SHA-256 of the canonical
     `{account_ref, connection_id, operation: "connect_finish"}`, the request's members. An
     `account_ref` names one request only (DEC-699 I3), so each request has one finish id.
   - **`causation_id`:** as item 8 says.
   - **`ConnectionEstablished` version 2** carries `connection_id`, `broker`, `environment`, the
     scopes strictly ascending, `account_ref`, `user`, `step_up`, and `margin_attestation` `null`
     (paper; rule 64).
   - **`ConnectionRefused` version 1** carries `connection_id`, `broker`, `environment`,
     `occasion` `connect`, `check`, `reason`, `existing_connection_id` (`null` except for
     `uniqueness`; rule 55), `user` and `step_up`.
10. **The pass.**
    - While a connect is bound, the API runs one pass every five seconds over the open requests on
      its control stream. For each: the request's account stream is read, item 8 decides, and the
      record is appended at the head the pass read. A head that moved is retried on the next pass.
    - The teardown's deletes (item 3) are made as the API's vault identity, which may delete codes
      and tokens and nothing else. A connection whose deletes have not yet succeeded is retried on
      every pass until they do.
    - The first pass after the process starts is the restart pass. It re-runs the deletes, once, for
      every connect request on the control stream that a refusal or a revoke closed, since the
      process keeps no memory of which deletes had succeeded. It then finishes the open requests by
      item 4's restart rule.

## Rationale

The finish is the one writer that turns a connect's evidence into a connection. Every reading
here establishes less, or later, than the alternative: no scope the check did not prove, no
fingerprint the vault did not compute, no request that is not an OAuth one, and a deadline that
ends every connect that nothing else ends.

## Alternatives considered

- **Read the account id from `personal/accounts/` and hash it in the API** (DEC-2339 item 3). It
  would put the account id in the API's memory, which connections spec §3.1 keeps out.
- **Delete the vault entries only after the refusal** (E10-21 alone). A failed append would leave
  them for the next pass; deleting before as well costs nothing.
- **Infer `start_failed` from the absence of a check.** The API cannot tell a slow executor from
  one that never started.
