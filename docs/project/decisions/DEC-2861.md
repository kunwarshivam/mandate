# DEC-2861: An endpoint names the sampling parameters its upstream does not take, and the request leaves them out

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 that carries out inference spec §3.4's "where the provider supports it"; it changes no pin, no model and no routing lock, and loosens no rule) |
| **Date** | 2026-11-01 (UTC) |
| **Decided by** | An agent (Claude Code), on the founder's instruction to get staging ready |
| **Story or claim** | Staging apply 41346558466 (`MeterSettled provider_unavailable`, `ChatRunEnded model_error`); inference spec §3.4, §4.1, §6; [DEC-2203](DEC-2203.md), [DEC-2294](DEC-2294.md) |

## Context

The founder's first chat on staging ended "the model service didn't answer". The gateway's call
settled `provider_unavailable`. Every request the OpenRouter adapter sends carries `temperature: 0`
and `provider.require_parameters: true`, which routes only to an upstream that takes every
parameter sent. OpenRouter's endpoint lists (`/api/v1/models/<slug>/endpoints`, read 2026-11-01)
give no `temperature` and no `seed` among the supported parameters of any endpoint of
`anthropic/claude-sonnet-5.5` or `anthropic/claude-haiku-5.5`, Google Vertex's included. Every
endpoint of `anthropic/claude-sonnet-4.5` lists `temperature`. So every call to a Claude 5.5 entry is
refused before it reaches a model: the chat pins, and the research pins, which also pin a seed.

Inference spec §3.4 already says the gateway sets temperature 0 and a seed "where the provider
supports it", but nothing records which providers do, so the adapter sends both to every upstream.

## Decision

1. **An endpoint lists what its upstream does not take.** A registry endpoint may name
   `unsupported_sampling`, a list drawn from `temperature`, `seed` and `top_p`, each once. It is
   empty when absent.
2. **The request leaves exactly those out.** The adapter sends no member the endpoint lists. It
   still sends every other pinned parameter, and keeps `require_parameters: true` and the rest of
   the routing lock, so an upstream that cannot honour what is still sent is never chosen.
3. **The pin is unchanged.** Endpoints are outside the content hash (§4.1), so the pinned sampling
   (temperature 0, the seed), every content hash, and DEC-2294's ungated chat pins stay as they are.
   The call record's `model.content_hash` and `request_digest` still name the pinned content; the
   endpoint the record names says what was left out.
4. **Staging's registry** names `unsupported_sampling: ["temperature", "seed"]` on its Claude 5.5
   endpoints, from OpenRouter's lists above. `openai/gpt-5.6-terra` on Azure lists `seed` and no
   `temperature`, so its endpoint names `["temperature"]`.

## Rationale

The routing lock (`only`, no fallbacks, `require_parameters`) is what pins the upstream, so it stays.
Dropping `require_parameters` instead would let OpenRouter ignore any parameter silently, `tools`
and `response_format` among them. Leaving out only what the pinned upstream says it does not take
is what the spec already asked for, and the endpoint, which is routing configuration, is where that
fact belongs.

## Alternatives considered

- **Stop sending temperature for every model.** Rejected: models that take it would lose
  temperature 0.
- **A new pin without temperature.** Rejected: a new content hash withholds the chat entries until
  their gate passes (DEC-2294 item 3), and the model has not changed.
