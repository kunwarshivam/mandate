# DEC-687: The executor's connection state machine tracks several causes, refuses the acknowledgment while one is outstanding, and lifts the drift halt only by a new pin

## Context

E7-17's remaining work is the executor's connection state machine: the health signals that degrade
or suspend a connection, `condition_cleared`, the acknowledgment, and the writers of
`ConnectionChecked` and `ConnectionStateChanged` ([DEC-800](DEC-800.md)). The specs leave five
gaps:

- `ConnectionStateChanged` carries one `reason`, and nothing says what happens when a second cause
  arrives while the first is still there;
- nothing says what a degrading signal does while `suspended`, or between `condition_cleared` and
  the owner's acknowledgment;
- contract drift "clears" on "a released connector version", which no spec or decision defines,
  while [DEC-839](DEC-839.md) item 4 lifts the MCP client's drift halt only on a new connection with
  a new pin;
- [connections spec §9.1](../../specs/connections.md#91-states)'s halt paragraph and
  [trading spec §7.3](../../specs/trading-domain.md#73-account-restrictions) row 5 still list "a
  reconnect" as lifting the restriction, against DEC-800 item 5, journal §9.8 rule 68, and DEC-824
  item 6;
- [connections spec §8.2](../../specs/connections.md#82-health)'s thresholds are Proposed, and how
  they count is unstated.

## Decision

**The condition on every item** (`AGENTS.md` rule 13): none of these readings ever holds an exit, a
protective order, a cancel, or the kill switch. The halt they keep in place, or keep longer, is the
halt on openings only: account state `closing_only` with cause `connection_unavailable`, agents
`exits_only` (trading spec §7.3 row 5). DEC-800 item 7's order still holds: the restriction is
committed before any connection record, so a refused append keeps openings halted.

1. **Several causes at once.** The executor keeps the set of **outstanding causes**: every reason
   recorded into `degraded` or `suspended` since the latest `condition_cleared` or `acknowledged`.
   - A new degrading or suspending cause that arrives while the connection is already `degraded` or
     `suspended` is journaled as its own `ConnectionStateChanged`, with that cause as `reason`. A
     cause already outstanding is not journaled again.
   - A suspending cause while `degraded` is `degraded` to `suspended`, as today. The degrading causes
     stay outstanding.
   - `condition_cleared` is written only once every outstanding cause has cleared, each by its own
     path (item 5's good results, item 3 for drift, re-authorization for a suspending cause).
   - **What the journal admits today** (journal §9.8 rules 59, 60, and 68, v0.24):
     - `degraded` to `degraded` with a degrading reason: admitted (rule 59 asks only `to` =
       `degraded`; rule 60 bars `degraded` only from `suspended`).
     - `suspended` to `suspended` with a suspending reason: admitted.
     - `suspended` to `suspended` with a degrading reason: **not admitted**. Rule 59 allows the three
       degrading reasons only into `degraded`, and rule 60 bars `degraded` from `suspended`.
   - **The record it should be:** `ConnectionStateChanged` with `from` = `to` = `suspended` and the
     degrading reason. The state does not move; the record only adds the cause.
   - **Owed journal-spec change** (through the coordinator's journal-spec queue, after E9-7; not in
     this decision's PR):
     - (a) rule 59 admits a degrading reason with `from` = `to` = `suspended`;
     - (b) rule 68's "the `ConnectionStateChanged` that last entered `suspended`" reads as the
       latest record with a suspending reason, `suspended` to `suspended` included, so a new
       suspending cause needs a re-authorization after it;
     - (c) rule 68 requires the copied `OwnerAcknowledged` an `acknowledged` names to come after the
       `condition_cleared` it follows.
   - Until (a) lands, a degrading signal while `suspended` is held in the executor's fold and not
     journaled, and no code writes the record above. Until (b) and (c) land, the executor enforces
     them itself: it asks for a re-authorization after the latest suspending cause, and it counts
     only an `OwnerAcknowledged` that comes after the `condition_cleared` it follows (item 2).
2. **Degrading signals while suspended, or between `condition_cleared` and the acknowledgment.**
   - A degrading signal while `suspended` is an outstanding cause (item 1). It never moves
     `suspended` to `degraded` (rule 60), and a `condition_cleared` out of `suspended` waits for it
     to clear as well as for the rotation rule 68 names.
   - A degrading or suspending cause after `condition_cleared` and before the acknowledgment is
     journaled as item 1 says. The executor then refuses the acknowledgment: it writes no
     `acknowledged`, and the restriction stays. The connection returns to `active` only after a new
     `condition_cleared` and an acknowledgment the owner gives after it. An acknowledgment given
     before the latest `condition_cleared` never counts.
   - **After a restart** in `degraded` or `suspended`, the executor takes `network_errors` and
     `rate_headroom` as outstanding until each meets item 5's recovery count afresh, and
     `contract_drift` as outstanding when recorded or found by the start's contract check. A
     restart never clears a cause.
3. **How drift clears (interim).** In E7-17's first slice, contract drift never clears by itself:
   good probes, a hash that matches again, a reconnect, and a re-authorization each leave it
   outstanding. A reconnect and a session start keep the stored pin (DEC-839 item 5), and so does a
   rotation. The only lift is DEC-839 item 4's: a new connection with a new pin. In this slice
   that lift is not reachable on the drifted account's own stream: a new connection on the same
   account is a reconnect, which continues the stream and its state (journal §9.8 rule 66,
   [DEC-800](DEC-800.md) item 6). So until the founder defines the released-connector-version path
   below, drift does not clear on that account's stream. No code in this slice writes a
   `condition_cleared` while `contract_drift` is outstanding.
   - **Owed:** the "released connector version" path that connections spec §8.2 and §9.1 and journal
     §9.8 name: what a released version is, who confirms its new pin, and how it clears a drifted
     connection's cause. It is recorded under "Waiting on the founder" in the
     [work tracker](../08-work-tracker.md). Until it is decided, a drifted connection keeps openings
     halted and every exit open.
4. **A reconnect lifts nothing (text only).** Connections spec §9.1's halt paragraph and trading spec
   §7.3's `connection_unavailable` row now say the restriction lifts when the connection's own
   condition clears: good probes for `degraded`, re-authorization for `suspended` (DEC-800 item 5,
   rule 68, DEC-824 item 6), and for drift item 3. A reconnect is not a way out. No reference case
   cites the reconnect text, and no outcome for a broker restriction changes.
5. **§8.2's thresholds and how they count.** §8.2's Proposed values are the interim defaults, and
   stay Proposed:
   - 3 consecutive network-class errors: `degraded`, reason `network_errors`;
   - 2 consecutive authorization failures: `suspended`, reason `authorization_failed`;
   - rate-limit headroom under 20% of the published or default budget: `degraded`, reason
     `rate_headroom`;
   - recovery: 3 consecutive good results of the cause's class.

   **Counting is per signal class.** Each class (network, authorization, headroom) keeps its own
   failure count and its own good-result count. A failure count resets only on a good result of the
   same class, and a good-result count only on a failure of the same class. A result of another
   class, or a call that yields no reading of this class, changes neither. A network error between
   two authorization failures therefore leaves the count at two, and suspends.

## Rationale

DEC-176 lets an agent take the reading that only tightens and adds no risk. Every item here only
keeps the opening halt longer or adds a record:

- **Item 1** journals more and clears later. One reason per record loses no cause, because each
  cause gets its own record.
- **Item 2** refuses an acknowledgment that would reopen a connection with a live fault, and a
  restart can only make the executor stricter.
- **Item 3** takes DEC-839 item 4, the stricter of the two texts. A flipping server never reopens on
  its good answer.
- **Item 4** removes a way out that DEC-800 item 5 and rule 68 already closed; the texts now agree.
- **Item 5** is the stricter counting: a mixed run of failures still reaches its threshold, where a
  shared counter would let an unrelated error reset it.

None of them reaches an exit, a protective order, a cancel, or the kill switch: `closing_only` and
`exits_only` allow every one, and connections spec §8.2 already says health never alone blocks an
exit.

## Alternatives considered

- **One record carrying several reasons** (`reasons: [..]`): a schema change to a closed record,
  and the same information as one record per cause.
- **Drop a second cause while one is outstanding**: `condition_cleared` could follow the first
  cause's recovery while the second is live.
- **A degrading signal moves `suspended` to `degraded`**: rule 60 forbids it, and it would leave
  `suspended` without the re-authorization rule 68 requires.
- **Let the acknowledgment stand across a new cause**: the owner would have acknowledged a fault
  they were never shown.
- **Clear drift when the hash matches again**: DEC-839 rejects it; a flipping server would reopen
  on the good answer.
- **Change journal §9.8 in this PR**: journal-spec rule changes go through the coordinator's queue,
  which E9-7 holds next.
- **Mark §8.2's thresholds Accepted**: they are tuning values the founder has not seen; interim
  defaults keep them reviewable.
