# DEC-657: The membership fold reads its own record type in `mandate-identity`, and its readings fold by instant

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | Agent (lane L1 builder, E9-7 M1), under DEC-79's delegation of reversible engineering decisions and DEC-176 for item 4, which only tightens |
| **Story or claim** | E9-7, claim [#760](https://github.com/kunwarshivam/mandate/issues/760); journal spec §9.12 ([DEC-648](DEC-648.md) item 7); identity spec §5.3, ID-7 |

## Decision

1. **The input type lives in `mandate-identity`.** The fold reads `MembershipRecord` (its `seq`,
   its envelope's `event_time`, and a `MembershipEvent`, one variant per §9.12 record with the
   payload members the fold and the cross-record checks read). `mandate-journal` (layer 2) keeps
   the schemas and rules 96 to 106, and `mandate-identity` (layer 1, pure) gains no dependency.
   The workspace store's adapter maps journal records into it and drops every other record, so a
   client, agent, or service account never reaches the fold. Both constructors take the identity
   seal, as `Membership::new` does (DEC-642 items 4 and 7), so no other caller can build a history
   and read a `workspace_users` of its choosing (V-047, ID-7).
2. **Readings take an instant.** `MembershipFold::new(seal, records)` holds the records; each
   reading at *t* (`state`, `effective_roles`, `invitation`, `workspace_users`, `unreadable`,
   `refused`) folds, in `seq` order, the records whose `event_time` is at or before *t*, as §9.12
   states, so a record after *t* never changes a reading at *t*. `refused` names the `seq` of the
   record that made the fold unreadable; `workspace_users` reads 1 while it is unreadable.
3. **Stubs are `todo!()`.** The readings have no error to carry (DEC-137's other form), and
   unreadable is a reading, not a failure (rule 3).
4. **A record out of order reads as unreadable** (DEC-176: it only tightens). Every record held,
   not only those at or before *t*, is compared with the one before it: a `seq` not above it, or an
   `event_time` before it (rule 106 leaves no reason to go back), does not fit, so the fold is
   unreadable from that record's `event_time`; a reading before it is unchanged (item 2).
5. **`workspace_users` counts members `active` at *t*,** past the cool-off of their activation or
   reactivation, whatever their roles (identity spec §5.3 "Any role counts", ID-7). Counting only
   members with an effective role would narrow DEC-411 item 2's count, which §5.3 leaves to the
   founder (§16), so it is not taken.
6. **Rule 103's cool-off arithmetic is not re-checked here.** It is `append`'s rule
   (`mandate-journal`), so the backlog's 1 ns gap vector belongs to the journal's vectors.

## Rationale

A minimal input type keeps the fold pure, within `xtask/layers.toml`, and testable against the
`membership_fold` vectors; the adapter is the one place a journal record's shape meets it.

## Alternatives considered

- **Fold `mandate-journal`'s drafts directly.** Rejected: a layer-1 crate would depend on layer 2.
- **Fold once and read any instant.** Rejected: `unreadable_latches` reads 2 before its bad record.
