# DEC-988: The §8.2 operator alerts as one closed set, raised from stored records and signals, with an opaque payload and no paging vendor

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The agent, under DEC-79 and DEC-176 (reversible engineering choices, each the reading that adds no risk) |
| **Story or claim** | E21-4, lane O2 of the [managed-cells plan](../tasks/managed-cells.md); claim #1440 |

## Decision

1. **A new pure, safety-critical crate, `mandate-alerts`, at layer 3.** It sits above
   `mandate-journal`, whose `StoredEvent` it reads, and `mandate-notify`, whose `NoticeId`,
   `SecureRandom` and canary scan it reuses. Its `forbidden_internal` list keeps it off every
   stream writer, the executor, the runtime, the connectors, the dispatcher and the CLI, so raising
   an alert can never append, act or trade. It is safety-critical because its payload leaves the
   cell, like a notification's (`AGENTS.md`, "Notification payloads").
2. **One `AlertKind` per row of infrastructure design §8.2**, with the row's severity and runbook.
   Three rows name two conditions of different weight, and each becomes two kinds: the kill switch
   (informational; SEV-1 when automated at workspace scope), a stale feed (SEV-3; SEV-2 at scale)
   and backups (a failed backup; a drill overdue or failed). That gives 28 kinds.
3. **Journal-sourced rows are read from the stored record's payload** through `mandate_canon`:
   - `ReconciliationRun` with `result` `mismatch`.
   - `ProtectionChanged` with `action` `interval_limit` or `watchdog`.
   - `GateDecided` with `reason_code` `protection_unattributed`.
   - `KillSwitchActivated`. It is SEV-1 when `scope` is `workspace` and `initiator` is anything
     but `owner`: a risk limit, the platform operator, or none named, which counts as automated.
   - `VerificationRun` with `result` `fail` or `incomplete`.
   - `AnchorComputed` whose `token` is null or absent.
   - `ClockToleranceExceeded`, whatever it holds: no schema is closed yet.
   - `ApprovalDelivered` with `status` `failed`.
   - `OwnerAlertSent` with `kind` `data_feed_down` or `spend_cap`.

   A body that does not parse, or holds no payload object, is an error rather than silence. So is
   a `ReconciliationRun`, `ProtectionChanged`, `VerificationRun`, `ApprovalDelivered` or
   `OwnerAlertSent` whose discriminating member is absent or not text, so a dropped member never
   silences an alert.
4. **Every other row is a `Signal`**, which carries only counts, durations and flags:
   - the global kill switch;
   - an order `Unknown` past its lookup window, which needs a clock the crate does not read;
   - a duplicate order, for which no record exists;
   - a stale feed;
   - gateway, journal-append, standby, fencing, DDL, cold-export, vault-lease and broker
     degradation;
   - a crash loop, an undelivered approval, and a backup or drill.

   Where §8.2 names a threshold it is used: a p99 append over 5 ms, and a cold-export lag over 60
   seconds. Where it names none ("above threshold"), any nonzero count alerts, and two or more
   stale feeds are "at scale". That is the
   conservative reading until E21-39's rules are tuned, and it changes no trading.
5. **The payload is the alert id, the reason code, the runbook id, the severity and fixed text.**
   Nothing else has a field. The id is minted from a `SecureRandom` source, as a notice id is
   (NT-4), so no event id or creation time reaches a pager. What raised the alert stays in the
   cell, keyed by the id.
6. **De-duplication is the caller's.** One cause can raise several alerts: a workspace kill
   switch is journaled on every stream it touches, and every opening held for an unattributed
   leg is its own gate decision. The cell's alert path (E21-39) groups them by its own rules, and
   nothing here drops one.
7. **No paging vendor** (DEC-434 item 20, H6 stays the founder's). A `Sink` trait takes the
   payload bytes. The only implementation is `CaptureSink`, which tests and a cell without a
   paging tool use. The runbook is an identifier (`RB-01` …), and the cell's configuration turns
   it into a link.

## Rationale

Design §8.2 makes journal events authoritative, so the rows they cover are pure functions of
stored records and replay raises them again. The other rows have producers that do not exist yet
(the deployment manager, the model gateway, the writer's metrics, the backup job). A closed
`Signal` gives each future producer an input that cannot carry trading content, and lets each row
fire in a fixture test today. Reusing `mandate-notify`'s id and canary keeps one opaque-payload
rule for owners and operators.

## Alternatives considered

- **Alerts inside `mandate-notify` or `mandate-dispatcher`:** the notice is the owner's closed
  set (NT-1) and the dispatcher writes the notice stream. Operator alerts are neither.
- **Deriving the alert id from the event id:** the same alert would get the same id on replay,
  but a ULID's creation time would reach the pager, which DEC-702 refuses for notices.
- **Waiting for each row's producer before adding its kind:** that leaves rows without a test,
  against E21-4's acceptance.
