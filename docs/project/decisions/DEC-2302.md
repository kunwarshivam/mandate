# DEC-2302: A cancel the broker never confirmed is sent again at every start, and a working report does not end it

| | |
|---|---|
| **Status** | Accepted (agent, under DEC-176: a tightening; it only sends again a cancel the journal already asked, which reduces risk, and adds no action path; the founder may revert) |
| **Date** | 2026-10-18 (UTC) |
| **Decided by** | `claude-code` (lane X, claim [#1498](https://github.com/kunwarshivam/mandate/issues/1498)) under DEC-176, as the coordinator directed |
| **Story or claim** | E21-30; claim #1498; [trading-domain spec §5.7](../../specs/trading-domain.md#57-order-lifecycle) (v0.19), §5.5; `AGENTS.md` rules 3, 5 and 13 |

## Context

A kill switch's batch journals each working order `PendingCancel`, with `cancel_requested`, before
its `Cancel` reaches the broker (rule 5). A crash between the commit and the request leaves a
cancel the journal asked for and the broker never saw.

Before this decision, recovery (`Input::Started`) queried the order. The broker answered `new`,
and §5.7's table maps `new` to `Accepted`, so the order went back to `Accepted` with its cancel
still unconfirmed. Nothing asked the cancel again: the switch skips an order whose cancel is
outstanding, so that it never asks twice. An agent the owner had killed kept a working order at
the broker, against rule 13.

§5.7's diagram leaves `PendingCancel` for its prior state only when the cancel is rejected. A
working status is not a rejection, so taking it as one was a loosening reading of the table.

## Decision

1. **A working report does not end a pending cancel.** Suppose an order is `PendingCancel`, its
   cancel is unconfirmed, and nothing in item 2 has ended it. A status that maps to `Accepted` or
   `PartiallyFilled` then keeps the order `PendingCancel`. A fill it reports is still booked, and
   the filled quantity updated (§5.7: fills during a pending state do not leave it).
2. **The "cancel rejected" edge is a refusal, and never for a kill switch's cancel.** A refusal of
   the cancel marks the wait overdue and asks one lookup by client order id, and no cancel, as
   before (DEC-160 (7), (13)).
   - **Any other cancel:** a working answer to that lookup returns the order to its prior state,
     §5.7's "cancel rejected" edge.
   - **A kill switch's cancel:** a working answer keeps the order `PendingCancel`, so the switch
     never lapses while the order works (§5.5, rule 13). The fold reads these orders from the
     `cancels` member of the switch's own `KillSwitchActivated`.
   - **Bounded within a start:** one refusal costs one lookup and no cancel, and the answer to that
     lookup asks nothing. A refusal and a re-send therefore cannot loop.
3. **Every start sends again each pending cancel the broker never confirmed.** On
   `Input::Started`, every `PendingCancel` order whose cancel is unconfirmed has its `Cancel` sent
   again, in place of the lookup. Its answer decides the order: a confirmation, a terminal state,
   a working state, or a refusal. `Unknown` and unacknowledged orders are still queried, never
   cancelled blind.
4. **No new record is written for the cancel sent again at a start.** The `OrderStateChanged` that asked it
   is already on the journal, so write-before-acting holds (rule 5).
5. **A terminal report always ends a pending cancel.** `Expired` and `Rejected` become edges out of
   `PendingCancel`. Both are reachable through the prior state (`Accepted → Expired`, `Accepted →
   Rejected`), which is how `legal()` already reads a missed update. So no terminal status is
   journaled and ignored for a pending cancel, the reservation is released, and no start sends a
   cancel to an ended order.
   - Until now an expiry reported then waited for §5.4's bound (#286 round 1, B1). The protection
     test that pinned that path now expects the exit in the same step, as for `canceled`.
6. **How a bug fix in safety-critical code goes test-first.** DEC-77's pending form is for a stub,
   and a fix to working code has none. The tests go in the same PR, in their own commit, before
   the fix commit:
   - the tests commit fails on `main` for the stated reason;
   - the fix commit makes them pass;
   - the PR body names both commits.
7. **Within each run, a kill switch's unconfirmed cancel is retried, bounded, and alerted.** On
   every tick, take each order a kill switch named in `cancels` whose cancel is unconfirmed:
   `PendingCancel`, or `Accepted` or `PartiallyFilled` where an ignored ask left it (an order that
   was `Unknown` at the switch and later resolved). Its cancel is asked again once
   `unknown_absent_window_s` has passed by the risk clock (never wall time) since the journal last
   asked it, at most `unknown_absent_lookups` times in each run.
   - **The pacing pair.** §5.7's pair that paces lookups of an `Unknown` order ("N lookups over T
     seconds") now carries this meaning too. Adding configuration would change the serialized
     rule set and the shell's adapters, so the pair is reused instead. A change to it now changes
     both cadences.
   - **Write-before-acting.** Each re-send journals `OrderStateChanged` (`PendingCancel`,
     `cancel_requested`) before the `Cancel` (rule 5).
   - **A budget per run.** A run counts the asks journaled since its start. In a run that began
     with the cancel already asked, the start's re-send (item 3) is the run's first ask; otherwise
     the switch's own ask is. So an outage that spends one run's re-sends leaves the next run a
     full budget, and a lost start re-send never leaves the order working (rule 13).
   - **The alert.** When the window after the run's last re-send passes with the cancel still
     unconfirmed, the tick on which it first passes raises an operator alert,
     `kill_switch_cancel_retries_exhausted`, an opaque key with generic text (rule 6). It references
     that re-send's record, because `OrderStateChanged` has no member for "exhausted". A
     confirmation or a terminal report before then raises none.
   - **After the budget.** Nothing more is sent within the run, and the order stays
     `PendingCancel`. It never becomes `Unknown`, which would hold the instrument against other
     risk reduction. The next start sends the cancel again (item 3) and opens a new budget.
   - **Scope.** Only kill switch cancels are retried. Protection keeps its own re-ask bound
     (§5.4), and an `Unknown` order is queried, never cancelled blind. While one is `Unknown`, the
     switch raises no sell in its instrument, through the live-order rule of `flatten_closes`
     (DEC-485 item 2), not a gate hold, and its sells elsewhere go (rule 13's hold).

## Connectors

A cancel sent again answers cleanly on both connectors:

- **Alpaca.** `cancel_named` looks the order up by client order id, sends `DELETE`, and reads the
  order back. A 2xx is a confirmation once the read-back says `canceled`; otherwise the answer is
  the read-back. A 422 for an order already cancelling or ended also answers with the read-back
  (`pending_cancel`, `canceled`, `filled`). Only 429 and 5xx are in doubt.
- **Robinhood.** The cancel goes by the stored broker `order_id`, which the connector rebuilds
  from the journal at construction. The answer is the order record, a confirmation when it reads
  as cancelled. A refusal is `cancel_refused`, which item 2 handles.

## Not closed here

Nothing in this decision. The connectors' answers to a re-sent cancel are listed above.

## Rationale

Sending a cancel the journal already asked only reduces risk (rules 3 and 13), and the broker
treats a second cancel of a cancelling or ended order as a no-op that answers with the order.
Keeping `PendingCancel` on a working report follows §5.7's diagram as drawn.

## Alternatives considered

- **Re-sending every unconfirmed cancel of a live order at the start, refused or not.** Rejected:
  a cancel that is not a kill switch's keeps §5.7's refusal edge, and the sequence that asked it
  (protection, §5.4) decides whether to ask again.
- **Returning a kill switch's refused cancel to the prior state.** Rejected: the switch would
  lapse while the order works (rule 13).
- **A new journal record for the cancel sent again.** Rejected: the original record already names
  the request, and the `Cancel` is idempotent at the broker.
