# DEC-2374: The release fails while a published public-TLS process would run without CA roots

| | |
|---|---|
| **Status** | Accepted (agent: a reversible CI change under DEC-79. It adds a release gate and weakens none; the coordinator reserved the number and approved the scope) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane D1, claim [#1901](https://github.com/kunwarshivam/mandate/issues/1901)), with lane GO |
| **Story or claim** | E10-25; [DEC-2371](DEC-2371.md) (the chart's CA bundle); E21-35 (release images are bare binaries) |

## Context

Every release image is one static binary with no CA roots. A process whose egress names a public
TLS host cannot build its HTTP client without roots, so on staging every connect would end
`endpoint_failed` before a request is sent. DEC-2371 gives such a process the pinned CA bundle in
its pod, and `test_cell` checks the chart. Nothing tied that to what a release publishes: a binary
published with public egress, or a chart that dropped the wiring, would reach staging first.

## Decision

1. **The check.** `cargo xtask release ca-roots` takes every binary the release publishes
   (`CHART_IMAGE_FOR_BINARY`) and each of their processes in `processes.json` whose egress names a
   public TLS destination. Those destinations are DEC-2371 item 1's, written out in xtask rather
   than read from the chart. It renders the workspace chart with every published image, once with
   the deployment manager and a control run, and once without the manager. Wherever such a process
   renders, as a Deployment, a Job or the manager's pod template, its first container must name
   `/run/ca-bundle/ca-certificates.crt` in `SSL_CERT_FILE` and mount `/run/ca-bundle` read-only, and
   an init container of its pod must copy the system bundle there. A process that renders nowhere
   also fails. The API's copier is part of a longer command, so the copy is matched within the
   joined command.
2. **The gate.** `release.yml` runs it as the job `ca-roots` on every push to `main`. Both arches'
   `publish` jobs need it, so a failure publishes no image, and `xtask`'s release tests pin that.
3. **Not in this check.** The check does not start the binary: the cell's connect drill (#2397)
   already proves at runtime that the token exchange starts with the bundle, and a start-up flag
   for this check would add surface to a production binary. The bundle's refresh stays DEC-2371
   item 4's.

## Rationale

`test_cell` proves the chart holds DEC-2371 for the processes the chart has. This proves it for
what the release ships, at the point of shipping, so a new published binary with public egress and
no bundle stops at the release rather than at its first connect.

## Alternatives considered

- **Run the release binary with and without roots.** Rejected: it needs a test-only flag on a
  production binary, and the drill covers it.
- **Put roots in the release images.** Rejected by DEC-2371: the images stay a pure function of
  their binary.
