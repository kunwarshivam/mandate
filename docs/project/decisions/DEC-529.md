DEC-528 was the highest number on `main` and every branch when this was reserved; the coordinator
reserved DEC-529 for this decision.

## Context

The founder decided on 2026-10-08, in the coordinator's session, that paper trading stays on
Alpaca paper ([DEC-502](DEC-502.md), [DEC-509](DEC-509.md)), and that before 2026-11-02 they want
**one real-money order on their own Robinhood account**, to prove the product thesis privately:
not public and not for customers. It goes through the same production path as the paper order:
a confirmed mandate version, the risk gate, journal before acting, and the Robinhood connector
(E7-6) in place of Alpaca's. Speed matters, and every safety gate stays: tests first (DEC-77), an
independent review on a different model, and zero missed mutants.

Several accepted rules stand in the way as written. Each item below names the rule, what it
narrows, and the recommendation. Every narrowing is for **this one founder-run order** only;
each rule stays in force for everything else.

## Decision

1. **One supervised live order, on the product path** (the founder's request). One opening
   order on the founder's own Robinhood agentic account (the account Robinhood marks
   `agentic_allowed`), through the same deployment path customers will use, with nothing built
   only for this order:
   - the runner is the paper path's deployment runner, generalized so that the environment and
     the broker come from the confirmed mandate and its connection record, not a second binary;
   - the **cap is the mandate's own envelope**: allocation and `max_order_usd`, set and
     confirmed by the founder (recommended 100 USD; `AGENTS.md` rule 11);
   - the **confirmation is the product's approval flow**: the mandate's autonomy rules say
     `ask` for every opening, so the cycle builds the order, the gate passes it, and it waits
     for the founder's grant in the CLI inbox (mandate spec §6.1, `mandate-approval`), which
     shows exactly the order that will be sent;
   - the order is a limit buy in the regular session, long only, on the confirmed mandate's one
     instrument, through every gate: the confirmed version, the pinned model, the order builder,
     the risk gate with the US account rules, the account ledger, journal before acting, and
     the executor's idempotency.

   This narrows `AGENTS.md` rule 8 ("Never place real orders") for this one order, granted by
   the founder. **Agents still never call Robinhood**, never hold or read the founder's
   credentials, and never run the live deployment; every agent test runs against fixtures and
   the simulated broker (DEC-441 item 11 stands).

2. **Whole shares follow from data, not code.** Robinhood's profile ([DEC-531](DEC-531.md))
   allows fractional quantities only for market orders; our policy allows only limit openings.
   The builder intersects the two and sizes in whole shares. So the cap must cover one share of
   the chosen instrument plus the collar and the fee reservation, and with 100 USD the order
   cannot be SPY. The founder chooses the instrument and the cap in the mandate; no rule is
   relaxed to fit either.

3. **The rules this order narrows, and only for it.** Each stays in force everywhere else, and
   each narrowing is a setting the product later tightens without rework.
   - **ES-23** (ADR-0001): "Only the paper trading and data hosts are compiled in; a `live` cargo
     feature is forbidden in CI and release checks. Live credentials will come only from the
     vault ... with a signed `live` build, a step-up-approved `AgentDeployed`, and the M13
     penetration test." Narrowing: the runner's `live` cargo feature adds Robinhood's published
     MCP host to the connector's allowlist. CI never builds a release with it; one CI job
     compiles it so it cannot rot, and a build test proves the default build holds no live
     host. The founder builds it locally from a commit on `main`. The OAuth token is
     session-only, in the connector process's memory (CN-1 already allows that), so no vault is
     needed for a supervised session. No signed build and no M13 test for this order.
   - **DEC-155 item 4 and mandate spec §6.1**: `cli_confirm` is allowed only in `paper`.
     Narrowing: `cli_confirm` is accepted as the step-up method for this live deployment's
     confirmation, deployment, and the one grant, on the founder's own connection only. The
     method is already a field of the approval record, so E9-4's signed assertions replace it
     later without rework.
   - **V-001 and the paper brief's FT-10**: the default build stays paper only. A `live`
     mandate is accepted only on a Robinhood connection the founder recorded through the CLI
     (the first slice of E7-11's connection record, the component the product grows).
   - **DEC-124** (the simulated broker is Robinhood's required paper stage) **is kept, not
     narrowed**: the founder first runs the same live build against the simulated Robinhood
     server, and only then against Robinhood.

4. **DEC-441 item 10, idempotency** (the contract gives a client key but no query by it).
   `place_equity_order` takes `ref_id`, a client UUID by which Robinhood deduplicates; but
   `get_equity_orders` filters by `order_id`, `state`, `symbol`, `created_at_gte` and
   `placed_agent`, not by `ref_id`. Item 10 asked for both, so it is half met and returns to
   the founder. **Recommendation:** build the order path with `ref_id` as the idempotency key,
   derived deterministically from the journaled intent's idempotency key, so a restart
   recomputes the same value, and accept this recovery rule for this order:
   - After a lost answer the order is `Unknown`. The connector **never re-sends** on its own,
     even with the same `ref_id`, because the contract does not say what a retry returns.
   - It lists the account's orders with `symbol` the intent's, `placed_agent` `agentic`, and
     `created_at_gte` the intent's `OrderSubmitted` time less a fixed margin, and adopts a
     record only if exactly one matches the intent on side, type, quantity, limit price and
     time in force (and on `ref_id`, if the records turn out to carry it).
   - Zero matches or several leave the order `Unknown` (DEC-176: when unsure, the reading that
     adds no risk). An `Unknown` order blocks every new order in that instrument (trading spec
     §5.3 rule 9) until the founder reconciles it by hand, and the next run is refused anyway
     while the account holds an order or a position (DEC-470 item 1).

   The match is safe here only because the account is dedicated and flat before the run and
   carries at most one agentic order. It is not safe for customers; the customer path still
   needs Robinhood's written answer on U-R1 and U-R2.

5. **DEC-441 item 15** (whether one platform may act for many customers) **does not block an
   order on the founder's own account.** It still blocks every customer connection: no
   customer connects Robinhood in any environment until Robinhood's written answer is recorded.

6. **DEC-441 item 16, fixtures:** synthesized from the published tool contract only
   ([robinhood-contract.md](../tasks/robinhood-contract.md)). Nothing is recorded from a real
   account, the founder's included, for this path. The live run's own journal is evidence of
   the run, not a fixture.

7. **DEC-441 item 17, protection.** The contract has `stop_limit` with `time_in_force` `gtc`, and
   a `get_advanced_orders` listing that includes OCO groups, but no tool that places an OCO or a
   bracket. **Recommendation:** protection takes the strongest form the connection's profile
   offers (DEC-531 item 2); for Robinhood equities that is one resting GTC stop-limit sell for
   the whole position after the entry fills completely, as crypto does
   ([DEC-36](../04-decision-log.md#decisions)), with the take-profit left to the runtime. The stop-limit may not fill if the price gaps through
   its limit; the founder accepts that gap risk for this order. A mandate with protection off
   is refused for this run, so the position is never left without a resting stop.

8. **DEC-441 item 20** (customer disclosures) **does not apply to the founder's own account.**
   It still blocks any customer connection.

9. **Counsel.** The tracker records that nothing trades live until counsel answers the adviser
   question (compliance questions 31 to 41). Whether counsel must review an order the founder
   places on their own account, with their own money, before it is placed is the **founder's
   call**. This decision states no legal conclusion and contains no legal text.

10. **Credentials** (`AGENTS.md` rule 7). The founder's Robinhood OAuth session lives only on the
    founder's machine and in the memory of the one connector process for the run. It is never
    written to the repository, a log, the journal, an artifact, a fixture, or any agent's
    context, and the runner writes no token to disk: the founder logs in through the browser at
    each run. The account number is typed by the founder (the contract says it must come from
    the user, never defaulted from `get_accounts`), is held by reference, and is never logged or
    journaled in clear (journal spec §6.4).

11. **The account.** The founder's agentic account must be flat (no position, no open order)
    before the run (DEC-470 item 1), must not be shared with another agent (connections spec
    §6.3), and must hold no margin the platform cannot show is capped at 1× (FR-2.6). The
    contract does not show margin status (U-R7), so the founder attests, with `cli_confirm`
    when recording the connection, that the agentic account is a cash account or has margin
    disabled, and the gate's buying power is the lower of cash and the broker's figure, as for Alpaca.

12. **Market data.** Trading spec §4.2 requires the `sip` profile for live equity agents; the
    paper path uses Alpaca's free `iex` feed. **Recommendation:** for this order, the collar and
    the risk mark use Robinhood's own quote (`get_equity_quotes`, re-read by
    `review_equity_order`), which must agree with Alpaca's IEX quote within the collar or the
    run refuses; daily and minute bars stay Alpaca's, as on the paper path (IEX minute volume
    understates, so the participation caps only tighten). This needs a named spec change to
    §4.2. The alternative is Alpaca's paid SIP feed, which is spending and also the founder's.

13. **What does not change.** One order, then stop. A restart or a second run submits nothing.
    No customer connection, no crypto, no options, no extended hours, no market orders. No
    agent runs the live deployment, reads its output during the run, or receives the credential.
    Every safety-critical slice is a DEC-77 tests PR then implementation PR, reviewed on a
    different model, with zero missed mutants.

### Spec changes this needs (named, not made; each is a protected path the founder approves)

- **Connections spec** §4 and §6.6: the Robinhood column and U-R rows from the
  [contract confirmation](../tasks/robinhood-contract.md); §6.2: `GetOrderByClientId` maps to
  item 4's list-and-match; §12: items 15 to 17 and 20 as this decision reads them.
- **Trading-domain spec** §7.2: Robinhood rows for account type and the day-trading regime
  (today the table names Alpaca only); §5.4: Robinhood equity protection is one GTC stop-limit
  for the whole position (item 7); §4.2: the quote source for this order (item 12).
- **Mandate spec** §6.1: `cli_confirm` accepted for a founder-run live deployment on the
  founder's own connection until E9-4 (item 3); V-001: a `live` Robinhood connection.
- **Trading-domain spec** §5.2: "Alpaca capability matrix" becomes "Broker capability
  profiles", with Robinhood's profile beside Alpaca's (DEC-531, ADR-0004).
- **Journal spec**: none expected. `ConnectionEstablished` already carries `broker`,
  `environment` and `scopes`; `account_ref` waits for E7-17, so this run names its account
  stream by an opaque id the founder's CLI creates once.

## Rationale

One real order on the founder's own money tests what paper cannot: Robinhood's real acceptance,
fills, fees, and settlement through the same cycle, gate and journal customers will use. Keeping
it to one capped limit order, sent only after the founder's grant in the approval flow, keeps the
loss bounded by the cap and the decision with the person whose money it is. Each narrowing is
the smallest that lets the order happen: no rule is relaxed for customers, and no agent gains
any route to Robinhood. Item 4 is the one real engineering risk: without a query by `ref_id`,
recovery after a lost answer depends on a match that is safe only on a dedicated, flat account,
so it refuses rather than guesses.

## Alternatives considered

- **A separate live binary with its own cap and typed prompt** (this decision's first draft):
  rejected by the founder on 2026-10-08 as code that needs rework; the mandate's envelope and
  the ASK approval flow already do both jobs.
- **Wait for the full M8 path** (connection manager, vault, signed build, OAuth, M13): the safe
  default, and the one in force until the founder accepts. Rejected as the recommendation: it
  is months away and proves nothing more about the cycle.
- **Let an agent place the order through the Robinhood tools this session can see:** rejected.
  Rule 8 and DEC-441 item 11 forbid it, and it would bypass the gate and the journal.
- **Re-send with the same `ref_id` after a lost answer:** rejected for now; the contract does not
  say whether a retry returns the original order or an error, so an answer could be misread.
  Revisit if Robinhood confirms the retry semantics in writing.
- **A market order or a dollar-amount order** to buy a fraction of SPY under 100 USD: rejected;
  openings are limit orders (`AGENTS.md` rule 12).
- **No protection for one small order:** rejected; trading spec §5.4 protects every position,
  and a resting stop exists.

## Revisit when

The founder accepts or changes any item; Robinhood answers U-R1, U-R2 or U-R4 in writing; or the
live order is placed, after which every narrowing in item 3 lapses.
