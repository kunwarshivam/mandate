DEC-940 item 6 found that `mandate-runtime`'s `bound_proposal` set `execution: None`, so the
production `ExecutorSink` refused every intent a grant released and no granted opening could be
placed. The plan (asset class, time in force, whether protection is required, and the protective
stop and take-profit) is the order builder's: the protective prices come from the mandate's
distances and the quote at planning time, so re-validation cannot re-derive them, and nothing on
the journal recorded them for an asked order. `DecisionMade` records only the time in force, and
`ApprovalRequested`'s content, the object the owner's grant repeats the hash of, recorded none of
it. These are the readings this lane takes.

## Decision

1. **The request binds the builder's plan under the content hash.** `RequestContent` gains
   `execution`, the plan the deterministic order builder produced for the asked proposal, carried
   unchanged. When there is one, the canonical content object gains one member, `execution`, after
   DEC-165 item 3's members, so `content_hash` covers it and a grant that repeats the hash approves
   exactly that plan (`AGENTS.md` rule 4: no model and no re-validation sizes or re-plans it).
   `approvals show` returns the whole content object, so the owner sees the plan they approve.
   When the builder produced no plan, the content object is DEC-165 item 3's exactly, so every
   existing content hash and reference case is unchanged.
2. **`ApprovalRequested` version 2.** Version 1 is unchanged and still refuses an `execution`
   member. Version 2 is version 1 with one more `content` member, required:
   `execution: {asset_class: us_equity | crypto, tif: day | gtc | ioc, protection_required:
   boolean, protection: {stop: decimal, take_profit: decimal?}?}`, closed recursively like the rest
   of §9.6. One more consistency rule: `content.execution.asset_class` equals the top-level
   `asset_class` (`schema` at `payload.content.execution.asset_class`). The existing rule that
   `content_hash` is the hash of the canonical `content` covers the plan. The shell writes
   version 2 exactly when the runtime's request content carries `execution`, and version 1
   otherwise. Journal spec v0.42 states it in §9.6 as rule 136, with generated vectors in its new
   `approval_requests` section, and mandate spec §6.4 lists the content key; the spec change lands
   before the code (ES-22).
3. **The fold recovers the plan byte for byte, or refuses.** Folding an `ApprovalRequested` whose
   payload carries `content`, the runtime refuses the event (`non_canonical`) unless the stated
   `content_hash` is the hash of the canonical `content` bytes, and, when `content.execution` is
   present, unless its members parse, its asset class is the order's, and the canonical object
   written back from the parsed plan equals the journaled member exactly. A stop in another
   spelling, an unknown time in force, a missing or extra member, or a member of the wrong type
   each refuse, so no plan the hash did not cover, and no reading of one, can reach the sink
   (`AGENTS.md` rule 3). A payload with no `content` at all is a shape no journal accepts (§9.6
   requires it); the fold recovers no plan from it, as before, and the sink refuses its grant.
4. **Re-validation hands the plan its request bound.** The bound proposal the classifier and the
   dry run judge (checks 10 and 11), and the `act` the runtime journals as `IntentProposed` and
   hands, carry the recovered plan and nothing else. The order builder is never asked again, so a
   builder that would now produce another plan changes nothing a grant hands. `IntentProposed`'s
   `tif` is the plan's.
5. **An ambiguous plan is not asked.** A proposal whose plan names another asset class than the
   order is journaled as its `DecisionMade` and not asked, as DEC-278 item 2 treats every part that
   cannot be bound, which never adds risk.
6. **No plan, no grant to send.** A builder that produced no plan asks with version 1 content; its
   grant hands no plan, and the production `ExecutorSink` refuses it as before.
7. **Gap 2 is closed; the other gaps stand.** `a_granted_intent_reaches_the_executor_sink_with_its_asked_plan`
   replaces DEC-940 item 6's pin `a_granted_intent_without_its_policy_stops_at_the_sink`, and the
   shell probes' test-only `PolicySink`, which supplied the fixture's plan, is removed. DEC-940
   item 6's gaps 1 (no mark reaches the runtime) and 3 (the grant is judged against the preflight
   quote's age) and item 7 (`ApprovalTimedOut` has no payload schema) are unchanged and still
   refuse with nothing sent.

## Rationale

The grant is the owner's approval of one content hash (EI-14), so the only plan a grant can
release without a second, unapproved decision is one the hash covers. Binding it in the content
object makes the owner's approval cover the protective stop as well as the size and limit, which is
stricter than before, and makes any later change to the plan a change of hash that check 5 refuses.
Re-deriving the plan at re-validation was rejected because its protective prices depend on a quote
the journal does not hold, and asking the builder again would be a new plan. A new schema version
keeps every version 1 record, content hash and reference case byte-identical.

## Alternatives considered

- **Carry the plan beside the content, outside the hash.** Rejected: the grant would not cover it,
  so a plan could change after the owner approved without any check noticing.
- **Keep the plan only in the runtime's memory between the ask and the grant.** Rejected: a
  restart would lose it, and a replay would act differently from the live run.
- **Re-plan at re-validation.** Rejected: rule 4 and the brief's "never a new or re-sized one"; the
  quote that priced the protection is gone.
- **Skip a grant whose request carries no plan inside the runtime.** Rejected for now: it changes
  the journaled outcome of every reference case whose plan has none; the sink already refuses it.
- **Require `content` in the fold.** Rejected for now: no journal accepts a request without it, and
  without it no plan is recovered, so tolerating it adds no risk while shell fixtures still seed it.
