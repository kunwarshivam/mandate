## Context

ES-22 makes a protected path (a spec, a schema, a reference case) ship separately from code, and
`xtask`'s `classify` enforces it with two prefix lists: `PROTECTED_PATHS` and
`CODE_PATHS = ["crates/", "xtask/src/"]`. A path under `crates/` therefore counts as code
whatever it is, so the guard cannot tell `crates/mandate-journal/tests/credentials.rs` from
`crates/mandate-journal/src/lib.rs`.

Three changes have now been refused by it, and in each the every-possible split is mutually red:

- **#1320** (E7-17 reference vectors, [DEC-913](DEC-913.md)): the vectors, their generated
  fixtures, the Python reference and the Rust test that asserts them travel together or the change
  lands inconsistent.
- **#2022** (J1, lane D1): it changes `docs/specs/journal.md`, `docs/specs/reference-cases/journal.yaml`,
  `fixtures/refcases/journal.json`, `reference/journal/` and `crates/mandate-journal/src/deployment.rs`.
  The spec half cannot compile the test that reproduces it; the code half needs the spec's new
  records to exist.
- **#2055** ([DEC-2632](DEC-2632.md)): the schema half needs `SCHEMA_AHEAD_OF_TYPE`, which lives in
  `crates/mandate-api/tests/body_workspace.rs`, and the tests half needs the stems its schemas
  introduce. Both halves are red alone; it merged with `spec-guard` still failing, and that gate
  has been red on `main` since.

## Decision

1. **A crate's tests directory is tests, not code.** The ES-22 split guard classifies a changed
   path as code only when it is not a file under `crates/<crate>/tests/**`. A tests path for this
   reading is that shape, the crate-level integration-test directories.
2. **A `src` file stays code wholesale.** A change under `crates/<crate>/src/**` still splits from
   any protected path it travels with, whatever `#[cfg(test)]` modules the file holds inline. The
   classifier reads paths only, never contents.
3. **`xtask/src/` stays code unconditionally**, and so does a `crates/<crate>/tests/` path that is
   itself a protected path (none is today).
4. Every other ES-22 requirement stands: a protected change still cites a `DEC-<n>`, still cannot
   ship with `src` code, and still takes a green CI and an independent review before merge.

## Rationale

ES-22's split exists so a reviewer cannot smuggle a live-code edit in under a "docs only" banner. A
tests-only Rust change does not serve that smuggling: it alters no behaviour any spec describes. It
is the change ES-22 most wants next to a spec edit, because it is the spec edit's own
reproduction — and the repository already treats such a file as non-behavioural everywhere else
(the mutation gate, the pending gate, the layer check all read it as a test).

The guard's `classify` keeps its shape — a protected prefix list, a code prefix list — and gains
one exclusion. That is the smallest reading that closes the gap, and it is reversible by deleting
one function.

The alternative, and the more common fix, is to edit the *merge gate* or to grant per-PR
exceptions the way [DEC-462](DEC-462.md) did for E7-7. Both were refused: a per-PR marker
accumulates and nobody removes it, and the merge-gate path does not make the change landable — the
guard still fails the PR.

## Alternatives considered

- **Leave the guard as it is and keep splitting.** Refused: the halves are red, so the change
  cannot land at all. #2055 merged with this gate red and main has carried that red since.
- **Classify `src` files that hold only `#[cfg(test)]` as tests.** Refused: it needs file contents,
  not paths, and a `src` file's test module sits beside real code.
- **Exempt a PR that cites a DEC and pairs a spec with its test.** Refused: a marker is a hole that
  nobody revisits, which is why DEC-462 confined its own to one PR number.
- **Broaden it to every file under `crates/` that is not `src/`.** Refused as too wide: benches,
  examples and build scripts are code a spec does not describe, but they also are not the
  reproduction of one, and nobody has shown they need to travel.

## Consequences

- A spec change and the integration test that reproduces it can land in one PR, which unblocks
  #2022 and every later change of that shape.
- A `src` change beside a spec still splits, so ES-22's stated purpose is intact.
- `cargo xtask ci spec-guard`'s behaviour changes for exactly one path shape; `xtask`'s own tests
  cover both sides, and the existing `status_toml_is_protected_not_code` keeps passing.
- No journal event: this changes no runtime state.
