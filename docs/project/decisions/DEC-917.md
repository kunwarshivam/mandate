# DEC-917: The ES-22 split guard does not count a crate's tests-directory files as code

| | |
|---|---|
| **Status** | Proposed |
| **Date** | 2026-10-11 (UTC) |
| **Decided by** | The founder under DEC-79; this PR's agent proposes it and does not decide it |
| **Story or claim** | ES-22 (ADR-0001); the spec guard's refusal of PR [#1320](https://github.com/kunwarshivam/mandate/pull/1320); this PR |

## Context

PR [#1320](https://github.com/kunwarshivam/mandate/pull/1320) (E7-17 reference vectors,
[DEC-913](DEC-913.md)) changes `docs/specs/reference-cases/journal.yaml`,
`fixtures/refcases/journal.json`, `reference/journal/connections.py`, and one Rust file,
`crates/mandate-journal/tests/connection_fold.rs`, the test that reproduces the new vectors. The
spec guard refuses it:

> specs, schemas, or reference cases changed together with code (1 code files); split the change

The cause is `CODE_PATHS = ["crates/", "xtask/src/"]`: a path under `crates/` counts as code
whatever it is, so the guard cannot distinguish `crates/mandate-journal/tests/connection_fold.rs`
from `crates/mandate-journal/src/lib.rs`. The independent review of #1320 proved that every
otherwise-possible split of the PR is mutually red — the vectors, their generated fixtures, the
Python reference, and the Rust test that asserts them travel together or the change lands
inconsistent — so the guard as written makes a sanctioned change unlandable.

ES-22's split exists so a reviewer cannot smuggle a live-code edit in under a "docs only" banner.
A tests-only Rust change does not serve that smuggling: it alters no behavior any spec describes.
It is the change ES-22 most wants next to a spec edit, because it is the spec edit's own
reproduction.

## Decision

1. The ES-22 split guard classifies a changed path as code only when the path is not a file of a
   crate's tests directory. A tests path for this reading is `crates/<crate>/tests/**` — the
   crate-level tests directories, the shape PR #1320 exercises.
2. A `src` file stays code wholesale: a change under `crates/<crate>/src/**` still splits from any
   protected path it travels with, whatever `#[cfg(test)]` modules the file holds inline. The
   classifier reads paths only, never file contents.
3. `xtask/src/` stays code unconditionally.

## Rationale

The guard's `classify` keeps its shape — a protected-path prefix list, a code-path prefix list —
and gains one exclusion: a `crates/<crate>/tests/` prefix reads as tests. The exclusion takes the
smallest reading that unblocks #1320 without opening any src file's inline tests to the same
treatment: a tests-directory file is named by its path alone, while inline `#[cfg(test)]` modules
are invisible without parsing Rust, and ES-22's risk (a live-code edit hidden beside a spec
change) lives in `src` files, whose compiled output is the behavior the spec describes.

## Consequences

1. A change pairing a spec, schema, or reference-case edit with only tests-directory Rust files
   no longer trips the split rule. Every other protected-path requirement stands: it still needs a
   DEC ID cited in the PR description or a commit message.
2. PR #1320's ACCEPT-JOINT review ruling becomes landable as reviewed, unmodified.
3. A reviewer still cannot smuggle a live-code edit beside a spec change: every `crates/` path
   outside a crate's tests directory still counts as code.

## Alternatives considered

- Classify inline `#[cfg(test)]` modules in `src` files as tests too: deliberately not taken. It
  makes the guard parse Rust for a case no review has hit, and an inline test compiles against
  the `src` around it, so a `src` file with test modules is still a src change. Kept minimal; the
  classifier reads paths only.
- Keep the old classification and split #1320 anyway: rejected by evidence — the review of #1320
  proved every otherwise-possible split mutually red, so the old rules make the sanctioned change
  unlandable rather than safer.
- A guard-waiver mechanism, like the E7-7 marker of [DEC-462](DEC-462.md): not proposed. A waiver
  would need one per future tests-with-spec change, each re-arguing this same false positive,
  where the classification fix removes the whole class.
