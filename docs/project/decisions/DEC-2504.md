## Context

Notifications spec §4.6 has a managed deployment send web push to the push service directly. In the
cell every pod starts behind a default-deny network policy, and each external destination is a
values list of CIDRs no wider than /24 (DEC-993 item 8), because a NetworkPolicy filters addresses,
not names. The browsers' push services (`fcm.googleapis.com`, `updates.push.services.mozilla.com`,
`*.push.apple.com`, `*.notify.windows.com`, §4.6's allowlist) answer from large, shared, rotating
address ranges that no short list of /24s covers for long. The dispatcher already refuses every
endpoint whose host is off the allowlist (DEC-792); the question is only what the network lets
through.

## Decision (Proposed)

1. **Recommended: a host-checking egress forward proxy.** One small proxy in the cell is the only
   pod whose egress reaches the internet on 443. It accepts `CONNECT` only for a host on §4.6's
   allowlist, read from the same table the dispatcher's `PushEndpoint` uses, checks that the TLS
   SNI names the same host, and refuses everything else. The dispatcher's network policy reaches
   only the proxy. The allowlist then holds by name at the network layer as well as in the
   dispatcher's code, and no CIDR wider than DEC-993's rule is opened. Cost: one more image, its
   pinning and updates, and one more hop that can fail (a failure is `retryable { timeout }`, which
   §5.3 retries).
2. **Alternative: pinned /24s.** Values list the /24s the push services resolve to today. It keeps
   DEC-993 item 8 as written and adds nothing to the cell, but the services move: a send to an
   address outside the pinned set times out, retries, and is abandoned when its window ends, and
   the list needs watching and updating by hand.
3. **Alternative: wider CIDRs.** Values allow the push operators' published ranges (Apple's whole
   `17.0.0.0/8`, Google's and the clouds' large blocks). It is the simplest to run, and the widest
   hole: it loosens DEC-993's /24 rule, and lets a compromised dispatcher reach any host in those
   ranges.
4. **Interim, until the founder decides.** The chart's push-services egress is a value that is off
   by default, so the dispatcher's pod reaches no push service, and the dispatcher's own
   configuration has web push off (DEC-2500 item 7), so it makes no web-push attempt and journals
   none. Nothing is loosened: DEC-993 is unchanged and no proxy image is added. For the 2026-10-26
   demo the approval ask reaches the founder through the web app's live Approvals screen
   (`web_inbox`, a pull channel), not through phone push. This adds no risk: the pull channels list
   every notice when its cause commits, never suppressed (§3, §5.1), check 4 is met by the pull
   channel (NT-5), and an ask nobody answers times out to `skip`. It is disclosed, not hidden: while
   web push is off, NT-6's push half does not hold for a recipient whose only configured push
   channel is web push.
5. **Web push turns on only when both hold:** the founder has chosen an option here, and the journal
   records one attempt per address (DEC-2502 item 5).

## Rationale

The proxy is the only option that enforces §4.6's allowlist by name at the network layer, which is
what DEC-792 meant by "only the browsers' push services", without widening any CIDR. The interim
keeps every rule as it is and leaves delivery to the channel that cannot fail silently.

## Alternatives considered

Items 2 and 3, and sending managed web push through the relay of §4.6. The relay is for hybrid
deployments whose egress allows only the control plane; it is not built, and it would need the same
egress to the push services from the control plane, so it moves the question rather than answering
it.
