## Context

The connections spec has the connection manager, in the API process, start one token-exchange
process for a connecting connection and hand it a single-use grant on the platform's client secret;
the process exchanges the code, writes the token, and stops, and only then is the connection's
executor started (§5.2 step 4, infrastructure §3.5). `mandate-vault` built that grant
(`SecretSource::issue_grant`) and refuses a mounted credential for the exchange on purpose. In the
cell, though, the API cannot start a pod: the deployment manager (lane D1) starts processes, from
journal records. And a grant must never be journaled, since anyone who reads the journal could
redeem it.

## Decision

1. **The start is record-driven.** On a control-stream `ConnectionRequested` at version 2 with
   `credential` `oauth` (DEC-2621 item 1), the deployment manager starts one token-exchange Job for
   that `connection_id`: at most one live, idempotent per connection, and stopped at the request's
   `recorded_at` plus the `state`'s 600 seconds, after which the code it would exchange has expired
   too. It starts nothing for a connection whose request is closed (`ConnectionEstablished`,
   `ConnectionRefused` with occasion `connect`, or `ConnectionRevoked`).
2. **The grant goes through the vault, never the journal.** At the callback, beside the code and
   PKCE verifier, the API stores a response-wrapped single-use grant for `exchange-{connection_id}`.
   The vault wraps it; the API holds only the wrapping token, and writes it to a path only that
   connection's exchange identity may read and delete. The Job unwraps it once.
3. **The identities are the provisioner's.** On the request, the dedicated provisioner the founder
   chose (DEC-2605 row 23, DEC-2630), which has no egress but the vault and no other duty, creates
   `exchange-{connection_id}`, which may only unwrap its grant, read and delete its code, and write
   its own token, and `executor-{connection_id}`, which may only read that token. No standing
   identity gains reach over another connection.
4. **The exchange is one attempt and journals nothing.** The Job reads the code and verifier once,
   exchanges them through the token-exchange client (DEC-821 item 2), refuses a grant whose scope
   is not exactly the request, writes `connections/{connection_id}/token` in DEC-2624's format,
   deletes the code, and exits `0`. It never retries with a code it has read. It appends nothing to
   the journal (connections spec §5.2 step 4).
5. **What follows.** On the Job's success the deployment manager starts the pending connection's
   executor, with the `account_ref` of the request; its `ConnectionChecked` and the API's
   `ConnectionEstablished` version 2 follow (§5.2 step 5). On a failure, or no success by the stop,
   no executor is started, and the API's deadline teardown closes the request with
   `ConnectionRefused` (`start_failed` or `timeout`, §5.2 step 6). Nothing else closes it.
6. **Who builds what.** Lane X: the exchange process's body and image, the fixture OAuth provider
   for dev and CI cells (DEC-2625), and the callback's writes (DEC-2626). Lane D1: the two
   record-driven starts. Lane V2: the provisioner's two identities and how the grant is wrapped,
   with the grant's exact vault path, which this decision leaves to V2.

## Rationale

The spec's process boundary holds: one process per connect, holding the client secret and the live
token endpoint for one exchange and then gone. The journal, which every service reads, carries
only the request, never a secret that redeems anything; the vault carries the grant, wrapped so it
can be opened once. Starting from the record means a restarted API or manager loses nothing it
needs to resume.

## Alternatives considered

- **A long-running token-exchange service the API calls with each grant.** Simpler to run, but it
  keeps the client secret and the live-host egress in a standing process, which infrastructure §3.1
  and DEC-821 item 2 rule out; it would need a decision that loosens a process boundary.
- **The API starts the Job itself.** It would give the API process the orchestrator's create
  rights, a standing power over every workload in the cell.
- **The exchange identity provisions the executor's.** It needs write access to the vault's auth
  and policy paths, standing reach over every connection, in the one process that holds the live
  host's egress (DEC-2605 row 23 put that power in a dedicated provisioner instead).
