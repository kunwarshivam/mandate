## Context

E6-4 and E6-13 made `mandate-spec`'s risk-state fold and `mandate-executor`'s tripwire fold pass every
MC-R, MC-T, MC-L, and MC-W case. But only the reference-case harness and `mandate-version-backtest`
drive them. The executor refuses the risk-state records (`owner_elsewhere` → `E6-4`), and the shell's
gate is built with nothing latched and mode `normal` (`mandate-shell/src/paper/gate.rs`). So on the
paper and live path a fired tripwire or a latched rung binds nothing. E6-15 folds the account
stream's risk state into the executor and the gate. Its first step is a closed record to write:
journal spec §9.3 closes only `MandateVersionApplied` and `UniverseChanged`, and the other seven
records mandate spec §5.10 lists have no payload schema.

## Decision

1. **§9.27 closes the seven at schema version 1**, with rules 230 to 238, before anything writes
   them. Each member is the fold's event (`mandate_spec::risk::RiskEvent`, `TripwireRiskEvent`) or the
   risk state's snapshot after the input. Mandate spec §5.10 lists the members. The reasons beyond
   §5.10's list are not a loosening reading: they are the founder-approved reference cases' own,
   which tests must reproduce. `hard_breach_pending` is in MC-R04, MC-R18, and MC-R19;
   `hard_breach_cleared` is in MC-R19; `version_loosened` is in MC-R21. The two `GoalCompleted` forms
   are DEC-128 item 15's. N (`net_contributed`) is journal spec §9's addition to §5.10's list. The
   breach time (`breach_time_s`) is what the limit's confirmation had accumulated at the triggering
   input, read before the trigger clears it: 0 when nothing accumulated, and `null` for a tripwire.
   That is exact enough for a replay to reproduce. `drawdown` has no bound, since nothing proves
   agent equity is never negative.
2. **A replayed record the fold would not have produced makes the risk state unreadable,** never
   trusted. The reader is E6-15's fold, which re-derives each record from the inputs and compares.
3. **An unreadable risk state holds new openings as `exits_only` does, and never as `paused`.**
   `paused` would hold the agent's own exits (`AGENTS.md` rule 13). Every cause makes the state
   unreadable:
   - a record the executor cannot decode;
   - a `schema_version` it does not know;
   - a gap in the stream's `seq`;
   - an event type it does not fold;
   - a journaled record its replay would not have produced;
   - a record it could not append.

   A failed append never delays the risk exit, protective order, or automated kill switch that
   follows it. Openings wait, and exits go on. Under rule 3, an ambiguous risk state adds no risk.
4. **Rules that refuse only drafts.** Rules 230 to 238 refuse inconsistent records: a tripwire that
   pauses, a lift no acknowledgment caused, an owner release without step-up, a goal in neither or
   both forms. Each rule is checked against what the fold emits today: a value or shape the fold
   produces is never refused. That is why rule 233 does not round a `realized_loss_usd` value to
   cents, rule 236 lets a goal release 0 (the fold releases whatever the agent holds when a goal
   completes, flat or not), and rule 238 does not fix `then`'s value.
5. **Until E8-8, delegations have no runtime lift to end.** The fold exposes
   `delegations_suspended` for E8-8 and tests it; nothing consumes it yet.
6. **Mandate spec §5.10's reason list is synced in its own docs PR.** Its row lists `hard_trigger`,
   `resolved_at_rollover`, `new_day_breach`, `after_reset`, `owner_acknowledged`, and
   `tripwire_condition`. It is missing the three that item 1 names from the reference cases. The
   coordinator ruled on 2026-10-18 that adding them is a documentation sync under DEC-176: it adds
   no behavior and loosens nothing. The sync goes in a separate small PR, which the founder may
   revert, and changes no other wording in `mandate.md`. This PR does not edit `mandate.md`.

## Consequences

- E6-15's slice A1 adds the `risk_limits` vectors to `reference/journal`, A2 and A3 register the seven
  in `mandate-journal` (tests first), and B builds the fold off R0's path. The wiring into
  `mandate-shell` (slice C) waits for R0 to close, or for the founder's call (claim #1599).
- Journal spec v0.58 renumbers at merge if D1 (v0.56) or M7 (v0.57) land in another order (#1491).

## Alternatives considered

- **Keep the members to the fold's minimal events** (limit, action, reason). That was rejected:
  §5.10 asks for E, H, DD, E₀, C, L, and the breach time, so an auditor can read why a limit
  triggered from the record alone.
- **Edit mandate spec §5.10 here.** That was rejected so the documentation sync stays a separate
  change the founder can revert on its own (item 6).
- **Close the records in E6-15's implementation PR.** That was rejected: the spec guard keeps specs
  and code apart, and the vectors need the schema first.
