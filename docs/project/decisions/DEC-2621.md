## Context

DEC-821 item 4 accepts a paper Alpaca OAuth token whose reach to the live environment Alpaca does
not document (U-A4), on condition that "the token's possible breadth is journaled with the
connection and disclosed to the owner", and says the journal change comes first. E7-27 asks for the
event that records, with the connection, whether the token may reach the other environment and the
disclosure the owner confirmed, and that no Alpaca OAuth connect appends `ConnectionEstablished`
before it.

The journal cannot tell an OAuth connect from another one by its records today. The CLI's
`connection record` (DEC-529 item 3) commits a version-2 `ConnectionEstablished` for a Phase-1
API-key connection with the same `broker` (`alpaca`) and `environment` (`paper`), causation, and
members as an OAuth connect's. A stream rule keyed on those members would refuse the CLI's records,
and one keyed on anything else would miss an OAuth establishment.

## Decision

1. **The breadth is journaled on the request (journal spec v0.68, §9.8).** `ConnectionRequested`
   version 2: version 1's six members, then:
   - `credential`: `oauth` | `api_key`, how the connection's credential is obtained;
   - `breadth`: for `oauth`, `{other_environment: may_reach, disclosure: {document: id, version:
     text}}`, the environment the token may also reach and the disclosure the owner confirmed with
     the connect's step-up; `null` for `api_key`.

   Version 1 stays registered, replayable, and unchanged, and reads as `api_key`: no route that
   starts an OAuth connect existed before v0.68, so no OAuth request was ever written at version 1.
   The start route (workspace API §4.5), the only writer of `ConnectionRequested`, writes version 2
   only. The request is committed before the redirect, in the transaction that marks the connect's
   step-up challenge used (identity spec §7.2 step 5), so the breadth is on the journal before any
   token exists.
2. **Rule 255 (a payload rule, judged by `append`).** A version-2 `ConnectionRequested` has
   `breadth` non-null exactly when `credential` is `oauth`. An `oauth` request names `broker`
   `alpaca` and `environment` `paper` (DEC-821 item 7: Alpaca OAuth connects paper only).
   Its `breadth.disclosure.document` is `alpaca_oauth_token_breadth`. The first clause that fails
   is reported, in that order, as `schema` at the member it names. `other_environment`'s type
   admits only `may_reach`: U-A4 is open, and a later decision adds a value only when Alpaca's
   documentation shows a paper token cannot reach live.
3. **The order E7-27 asks for, held at the writer.** A connect's `ConnectionEstablished` closes
   its open request (rule 131), and an `oauth` request carries its breadth, so an establishment
   that closes it follows the record of its breadth. That holds by rule 131 and the one writer,
   not by a stream rule, which §11 could not judge (below). The connection manager, the only writer of an OAuth connect's
   establishment, appends one only to close an open version-2 `oauth` request (E10-13 slice 6
   tests it). The CLI's `connection record`, which names no request, stays the Phase-1 API-key path
   it is, and §11 reads it as before.
4. **The connect digest binds the disclosure (amends DEC-693 items 1 and 2).** For an `oauth`
   start, the step-up digest of kind `connection` is the SHA-256 of the canonical `{action:
   "connect", broker, disclosure: {document, version}, environment: "paper", workspace_id}`. So
   the step-up that starts the connect proves the owner confirmed that document's version, and
   evidence for one version is refused for another (API-17). The start request names the document
   and version; the route refuses one other than the current version as `invalid` at
   `/disclosure`, before step-up is judged, and journals the version it bound.
5. **The disclosure.** Its document id is `alpaca_oauth_token_breadth` and its first version `1`.
   The text is in [DEC-2622](DEC-2622.md), Proposed: wording shown to an owner is the founder's
   (DEC-79). The workspace API names it by document and version only, never by drafted text
   (workspace API rule 9). The web app holds the text for that version and shows it before the
   start call. Until the founder accepts DEC-2622, no real Alpaca connect can start anyway: the
   platform's Alpaca OAuth client is not registered (DEC-441 item 18), and the cell's start route
   is served against the fixture OAuth provider only. So no gate of its own is built.
6. **Vectors and order.** The journal vectors gain a `connection_requested` section: the base
   drafts at both versions and an invalid draft for each member and for rule 255, generated by `reference/journal/`. Spec and vectors first; then `mandate-journal`'s
   registration, tests first (DEC-77); then the start route (E10-13 slice 2), which writes version
   2.

## Rationale

The request is the one record every OAuth connect writes before a token exists, it is written only
by the start route, and it already carries the step-up the connect spent. Putting the breadth there
gives E7-27's order through rule 131 and the request's one writer, needs no second record to keep in step, and leaves the CLI's
API-key records, which name no request, untouched. Binding the disclosure version into the digest
makes "the owner confirmed it" a property the passkey assertion proves, not a flag the client sets.

## Alternatives considered

- **A separate `ConnectionBreadthDisclosed` record after the request.** Two records to keep in
  step, a window between them, and a rule pairing them, for the same facts.
- **Record the breadth on `ConnectionEstablished`.** Too late: the token has already been issued,
  exchanged, and used for the §8.1 checks by then, and the disclosure belongs before the redirect
  (connections spec §5.2 step 1).
- **Key the rule on `broker` `alpaca` and `environment` `paper`.** It refuses the CLI's Phase-1
  API-key records, which need no breadth: an API key cannot reach the other environment's host,
  whose keys are separate.
