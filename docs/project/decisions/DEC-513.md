# DEC-513: The last completed regular session refuses a clock past the exchange calendar's range

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The E15-13 builder (Claude Code), under DEC-79 and DEC-176 (a reading that only tightens a rule and adds no risk), on the coordinator's ruling on PR #677 |
| **Story or claim** | E15-13; claim [#674](https://github.com/kunwarshivam/mandate/issues/674); PR #677 |

## Decision

1. `ExchangeCalendar::last_completed_regular_session(now)` returns `outside_calendar`
   (`TimeError::OutsideCalendar`) when `now`'s New York date is after the calendar's last valid
   date. It never answers such a clock with the range's last completed session.
2. The New York date is the one compared, not the UTC date: until midnight New York on the last
   valid date, every session that could have ended by `now` lies inside the range, so the answer
   is still known. From midnight New York on, it is not.
3. A clock before the range is unchanged: `Ok(None)`, no session has completed. Callers refuse
   both. The shell's trusted-dataset check maps the error and `None` to the same refusal, "the
   equity calendar cannot name the last completed session"; the model host (M1) refuses both as a
   calendar that cannot name the session.
4. The checked-in calendar runs to 2028-12-31, so the change bites from 2029-01-01 05:00 UTC until
   a calendar extending the range is checked in.

## Rationale

The shell's `latest_completed_equity_day`, which this method lifts, clamped the search to the
range's last date, so a clock in 2029 named 2028-12-29 as the last completed session. The calendar
cannot know which later days traded; the answer is a guess, a silent default of the kind
`AGENTS.md` rule 3 rules out, and `mandate-time`'s own module says a question outside the validity
range "is an error, never a guess". Downstream checks would usually refuse such stale data anyway,
but the model host stamps `as_of` from this answer, and a refusal at the source is simpler to trust
than staleness caught later. Refusing only removes answers, never adds one, so it adds no risk.

## Alternatives considered

- **Keep answering with the range's last session** (the lifted behavior). Rejected: a guess past
  the data, against rule 3.
- **Compare the UTC date.** Rejected: it refuses the evening hours of the last valid date in New
  York, when the answer is still known, for no gain.
- **Return `Ok(None)` past the range too.** Rejected: `None` means "nothing has completed yet",
  which is false past the range; a distinct error names the real cause.
