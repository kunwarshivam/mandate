## Context

The API serves a paper grant (`POST /approvals/{approval_id}/responses`, verdict `approved`) under
`cli_confirm` alone ([DEC-2129](DEC-2129.md)). DEC-2129 item 6 defers the passkey half, "with
`step_up_assertion` on `commands/approval-response-request` and `StepUpAsserted` in its batch",
to its own change, following DEC-2128's shape. The connect, a version's confirmation, a deployment,
a resume, a Stop and the acknowledgments already take passkey step-up that way. The founder wants
passkey to be the path on staging, with `cli_confirm` only as a fallback.

The grant's evidence is judged twice. The API judges it through the step-up port (DEC-2129 item 5).
The runtime then judges `ApprovalResponseSubmitted.step_up` again at check 6 (mandate spec §6.1,
§6.4), and today reads only `cli_confirm`: any other method is no evidence there
(`mandate_runtime::payload::step_up_of`). A passkey grant the API recorded would be refused at check
6, so the route must not serve one before the runtime counts it (item 6).

## Decision

1. **The wire, as DEC-2128 item 1.** `commands/approval-response-request` gains an optional
   `step_up_assertion`: DEC-2108 item 7's object (`envelope.schema.json#/$defs/StepUpAssertion`)
   or `null`, an absent member read as `null`.
   - For `approved`, which is judged strictly: `step_up` of method `passkey` with no assertion is
     `step_up_missing`. An assertion beside `step_up` of method `cli_confirm`, or beside a `null`
     `step_up`, is `invalid` at `/step_up_assertion`, one violation, among the body checks, before
     `step_up_required`.
   - For `skipped`, the member is lenient, as `step_up` is (API-7, DEC-682 item 27): it is dropped
     and listed in `dropped`, and never refuses a Skip.
2. **The judgment, as DEC-2129 item 5.** The port's `asserted` judges the evidence and, now, its
   assertion, with kind `approve` and the request's content hash as digest, bound once and
   dispatched on `step_up.method`. DEC-2129 item 1's order is unchanged: the step-up checks come
   last, after the unknown approval, the matrix row, the approvers, a delegation, and `live`.
3. **The commit, as DEC-2128 item 3.** A grant under passkey step-up stores the assertion's
   canonical bytes as an artifact, then appends `ApprovalResponseSubmitted` and its `StepUpAsserted`
   in one batch, in that order, the assertion's `causation_id` the grant (journal spec §9.32 rules
   253 and 254). The grant's `step_up` is `{assertion_id: the challenge, authenticated_at,
   method: "passkey"}`, `authenticated_at` truncated down to the whole second as DEC-2129 item 3
   says, so rule 253's `payload.step_up` and `payload.challenge` hold. The `StepUpAsserted`'s id is
   §3.4's key under the operation `approval_response_step_up_asserted`. A step-up the server's
   cool-off waiver counted appends its `StepUpCoolOffWaived` right after its `StepUpAsserted`
   (DEC-2146 item 3, journal spec rules 316 to 318). A refused grant appends nothing; a repeat of a
   committed grant (§3.4 step 1) answers as before and judges no assertion.
4. **Nothing else changes.** A Skip needs no step-up and is never refused for it. A grant with a
   delegation stays `invalid` at `/delegation` (DEC-2129 item 4), and `live` stays
   `live_unavailable`, both before any step-up is judged. The runtime still judges the deadline,
   the state, the content hash, the approvers, the quorum, independence and re-validation (checks 1
   to 12).
5. **The interim's end, as DEC-2154 item 2.** Once item 6's last step lands, a `cli_confirm` grant
   from a member who holds a passkey past its cool-off, read as DEC-2154 item 1 reads it, is
   `step_up_method`, as DEC-2126 item 6 refuses a connect's. It is judged with the step-up checks,
   after `live`, and commits nothing. A member who holds no such passkey keeps `cli_confirm` for a
   paper grant (DEC-2104).
6. **Order.** The route takes the member no earlier than the change in which the runtime counts
   `passkey` evidence at check 6, so no grant is recorded that the runtime would refuse. Until
   then nothing changes: the grant's body is decoded strictly, so one carrying `step_up_assertion`
   is `invalid`, and `passkey` evidence with no assertion is `step_up_missing` (DEC-2129 item 5),
   each committing nothing. Within the route's own change, `mandate-api`'s `ApprovalResponseRequest`
   gains the member in its tests, before the schema names it (DEC-2128 item 5's order), and the
   schema and its examples follow with the implementation, which empties `members_ahead` for it.
   Item 5 lands in the change that serves the passkey grant, never before.

## Rationale

- Items 1 to 3 are DEC-2128's readings on one more route that commits one control-stream event
  carrying `payload.step_up`, the shape rule 253 names; DEC-2129 item 6 asked for exactly that.
- Item 6 keeps the API from recording a grant the runtime cannot count, and needs no interim rule:
  today's strict decoding and the port already refuse every passkey grant, committing nothing. The
  owner can still grant under `cli_confirm` in the meantime, and an approval left unanswered takes
  its default at its deadline, as before.
- Item 5 ends the second path only once the first works end to end, so no member is left with no way
  to grant.

## Alternatives considered

- **Serve the passkey grant before the runtime counts it.** Rejected: every such grant would be
  recorded and then refused at check 6, so the owner would see an approval they granted end in its
  default.
- **Judge the passkey only at the API and record the grant with `null` evidence, as an unverified
  resume or Stop is (DEC-2140 item 3).** Rejected: the runtime refuses `null` evidence at check 6,
  and a grant, unlike a brake, is risk-increasing, so it is refused at the API rather than recorded
  to be refused.
