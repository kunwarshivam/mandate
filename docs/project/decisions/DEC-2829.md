## Context

Mandate spec §5.2 lists `CompensatingEvent` among the account stream's risk inputs, but does not say
what one changes. The account risk fold (`mandate_executor::risk_state`) therefore treats it as a
risk input it reads at no version yet, and the view fails closed with `unknown_schema_version`
([DEC-2304](trading-core.md#dec-2304) item 1).

The reconciler writes a `CompensatingEvent` each time it adopts the broker's state for one of our
orders (trading domain spec §11). That includes every paper fill found by polling, which the executor
journals as `OrderStateChanged`, then `CompensatingEvent`, then `FillApplied`. So in the deployed
runtime, the agent's first fill makes its view unreadable for good (DEC-2304 item 2), and every later
opening is held. Exits, protection and the kill switch go on.

Journal spec §9.6 closes `CompensatingEvent` version 1 to these members, and carries no quantity,
price or cash:
- `subject`, the order's client id;
- `difference`, which can only be `order_state`;
- `from` and `to` order states;
- `corrected_event_ids`;
- `risk_clock`.

When it adopts a state, the reconciler writes the compensation in the same batch, right after the
`OrderStateChanged` it corrects (`adopt`). The compensation's `causation_id` and its one
`corrected_event_ids` entry both name that row. The one exception is a crash cut between the two,
which batches make impossible for the executor's own appends, since each is atomic. For it, the
reconciler's `owed` writes the compensation that an adoption already on the journal is still owed,
at the start of a later batch, with no `OrderStateChanged` beside it.

## Invariants first

- Every figure the risk state holds (Q, cash, B, marks, E, E₀, H, N, C, L) moves only on the inputs
  §5.2 names for it. A fill moves Q and cash through its own `FillApplied` or `LateFillApplied`
  (DEC-2393 item 2). A fee moves cash through the fill or `FeesCharged` (item 3).
- Whose an order is comes from `OrderRequestRecorded`, `OrderSubmitted`, and the `replaces` and
  `replaced_by` of the order records (DEC-2393 item 1). The adopted state is the `OrderStateChanged`
  that the compensation corrects, and the fold reads that row for ownership already.
- So a version-1 order-state compensation changes no figure, no ownership and no clock. A fold that
  reads it as stepping nothing ends in exactly the state of a fold that never saw it.
- A compensation the fold cannot pair with the `OrderStateChanged` it corrects is never skipped. The
  fold does not lean on it for state or ownership, and it does not let a lone one pass unread.

## Decision

1. **A paired version-1 order-state compensation steps nothing.** The fold reads a
   `CompensatingEvent` as stepping nothing only when all of these hold:
   - it is at schema version 1, and its `difference` is `order_state`;
   - its `subject`, `from` and `to` are text;
   - the row right before it is an `OrderStateChanged` in the same append. That means the same
     `recorded_at`: the writer gives each append one, and every row of the append carries it. An
     equal `recorded_at` alone does not prove one append, so the checks below pair the two by
     content;
   - its `causation_id` and its one `corrected_event_ids` entry name that row;
   - that row's `client_order_id` is the `subject`, and its `state` is the `to`.

   It returns no records and changes no state. Its `risk_clock` must be a whole-second timestamp,
   as every risk input's is, or the row is `undecodable`.
2. **Anything else fails closed** with `unknown_schema_version`, as today (DEC-2304 item 1): any other
   version, any other difference, or a compensation not paired as item 1 says. A compensation that
   `owed` writes after a crash is one of these. It is safe, but it holds openings until the
   operator's recovery story (DEC-2304 item 2). Backlog row E6-15n records that gap.
   A later version that adds a difference which moves a figure, such as a position or cash
   correction, is read only by its own decision.
3. **Tests.**
   - **Unit tests in the fold:** one for each way item 1 can fail. Another agent's compensated
     order stays that agent's, so its later fill moves no figure.
   - **A contract test:** the batch the executor's own reconciliation journals when it adopts a
     fill is sealed as one append and folded. The view stays readable, and on the old reading it
     fails.
   - **A property test:** random account streams of the agent's orders, fills, fees, marks and
     ticks, with and without paired version-1 compensations. Each compensation is placed before its
     fill, as the reconciler writes it. The test asserts the same snapshot and the same journaled
     records either way. The oracle is the same inputs journaled with no compensation at all. It is
     shown to fail on a seeded bug, a paired compensation that charges a fee.
   - **A process test in the executor daemon:** the agent's opening fills through reconciliation,
     and its view stays readable, so a later opening is judged on the risk state rather than held.
     It lands with R4b (#2675), the first change in which the daemon runs the fold.
4. **Mandate spec §5.2** says what a version-1 order-state compensation changes: nothing (v0.14).
   It also says that any other compensation, a crash's included, fails closed.

## Consequences

- The code change is one reading in `mandate_executor::risk_state`, with its tests, in a separate PR
  that lands before R4b (#2675).
- DEC-2304 item 2 is unchanged: a view already unreadable on a compensation stays unreadable until
  the operator's recovery story. Nothing has deployed the fold yet, so no journal holds such a view.

## Alternatives considered

- **Keep failing closed.** That holds every opening after the agent's first fill, for good. It is safe,
  but the owner's agent could trade only once.
- **Skip every `CompensatingEvent`.** Refused: a later version may carry a figure, and a lone or
  mispaired compensation would pass unread. That loosens DEC-2304 item 1.
- **Pair by `causation_id` alone, anywhere in the stream.** Refused here. It would also read the
  compensation that `owed` writes after a crash, but the coordinator's ruling asks for the pair in
  one append, and a lone compensation fails closed. Backlog row E6-15n weighs reading that one by
  its own decision.
