## Context

DEC-1012 item 6 kept `mandate-daemon`, the cell's runtime process, on `fixture::wiring` until the
post-R0 hook: a gate that denies every proposal, a plan that proposes nothing, and a flatten that
finds nothing held. The hook was to be the production-cycle constructor in `mandate-shell`. But
the cell runs `mandate-daemon`, which `xtask/layers.toml` keeps from reaching the shell, the
executor and every connector, and the shell's production cycle holds the broker connector. That
hook cannot serve the cell. The founder approved the R0 hook at 00:17 UTC on 2026-10-26; this
decision leaves that approval unused, since the cell's path needs no change to an R0 file.

The pure logic the daemon needs already exists: `mandate-ports` sizes, classifies and dry-runs the
gate over contexts its caller gives it, and `mandate-risk` plans an agent flatten. The daemon has
no route to the broker. So every fact those contexts read must come from the journal.

## Decision

1. **Option B, in three slices.** The daemon gets production ports, built from the journal. S1 is
   the shared fold, `mandate-gate-context`. S2 is the daemon's ports over it: an opening is ASKed or
   denied, never sent without its gate, and an exit is never denied. S3 wires paper deployments to
   those ports, and refuses a live environment and an environment it cannot read. The fixture
   wiring stays for every other case. This amends DEC-1012 item 6. The production ports wait for
   these slices, not for the post-R0 hook.
2. **The risk clock is the only time.** `mandate-gate-context` folds journal rows alone. Its
   `now` is the later of two journaled clocks:
   - the account stream's: its latest `risk_clock`, or the `clock` of a `ClockAdvanced` copied
     onto it;
   - the scheduler's: the latest `ClockAdvanced` on its clock stream, `clock:{workspace}`.

   The scheduler's ticks keep coming when the account stream is quiet, so a mark or a snapshot
   ages even when nothing new is written about it. The executor copies a tick onto the account
   stream only when the tick emits something, so the account stream's clock alone could leave a
   fact of any age reading as fresh. R1 found this fail-open on #2432. Each stream's clock only
   moves forward against its own. A clock that goes back, on either stream, holds every later
   answer (item 3). No row from another stream moves either clock, and nothing reads a wall clock.
   An opening also needs the scheduler's clock itself: with no `ClockAdvanced` folded from the
   clock stream, `facts` answers `NoClock`, since the account stream's clock alone can stop. A
   replay of the same rows therefore gives the same facts (mandate spec §5.2). A property test
   checks the fold against an oracle that searches the rows from the newest back. The two clocks
   run independently in it.
3. **It fails closed.** `facts` answers `Held` unless each of these holds:
   - a risk clock is journaled;
   - a mandate version is in force for the agent;
   - a snapshot of the account is journaled and current;
   - the instrument's latest counted mark is sane and current.

   The mandate version in force comes from the agent's `AgentDeployed`. A later
   `MandateVersionApplied` with result `applied`, on the account stream, replaces it, and an
   `AgentStopped` clears it. A rejected version changes nothing. A row of a type the fold reads
   that does not parse is refused. So is a clock that goes back. Either one holds every later
   answer, since that row may have changed a fact.
4. **Marks are read as §9.30 reads them, and counted more tightly.** Only a `MarkUpdated` at
   version 2 is read: a version-1 mark has no verdict, so it is neither sane nor a reason to hold.
   An equity's mark outside the regular session is ignored, sane or not. The latest counted mark
   decides: one that is not sane holds until a sane one follows. A fact is stale once its age, in
   risk-clock seconds, reaches the caller's limit. For an equity this counts every second, not
   only the regular-session seconds of §5.2, so it can only hold more. The calendar's count can
   replace it in a later slice, under its own decision.
5. **For openings only.** An exit, a protective order, a kill switch and a flatten never consult
   the fold. With no facts at all, the flatten still sells the agent's sub-ledger (S2's test), so a
   missing fact never holds risk reduction (`AGENTS.md` rule 13).
6. **One fold for both processes.** `mandate-gate-context` sits at layer 5, below
   `mandate-runtime` and `mandate-executor`. The cell's runtime and the executor both read their
   facts through it, so the two cannot disagree about a mark or a snapshot. It is pure,
   safety-critical, and adds no external dependency.

7. **The agent's sub-ledger.** The fold also keeps what the agent holds, as `held`, computed
   as the executor's `sub_ledger` computes it:
   - **What the agent's own fills hold.** An order is the agent's when the
     `OrderRequestRecorded` journaled immediately before its `OrderSubmitted` names the agent
     (journal spec rule 45). Each `fill_id` counts once. A fill of an order that is not the
     agent's counts for no one.
   - **Less what the agent released to the owner.** Each `PositionReleased` naming the agent is
     subtracted (DEC-2354 invariant 1, DEC-2360 item 4). R1 found that leaving the release out
     would let a flatten sell the owner's shares.
   - **Capped at what the account holds.** That is every fill on the account, less any crypto
     fee charged in the asset itself, and never less than zero.

   A `CorporateActionApplied` is refused, which holds every later opening. The executor's fold
   does not interpret corporate actions yet either, so `held` stays the fills' until both folds
   read splits. Until then a split can make `held` differ from the account's true quantity. But
   `held` never exceeds the executor's sub-ledger, and the executor sells only from its own
   sub-ledger. A flatten reads `held` whether or not the facts an opening needs are there.

## Rationale

The journal is the only thing the daemon and the executor share (`xtask/layers.toml`'s process
groups), so a context built from it alone is one both can trust and a replay can reproduce. Holding
an opening for a missing or stale fact can only stop risk being added (`AGENTS.md` rule 3). Counting
staleness in risk-clock seconds keeps S1 free of the trading calendar, and only ever holds sooner.

## Alternatives considered

- **The post-R0 hook in `mandate-shell` (option A).** This would need the cell to run the shell,
  which holds the broker connector, or the daemon to reach the shell. `xtask/layers.toml` forbids
  both, and the runtime would gain a route to the broker (`AGENTS.md` rule 12).
- **Each process folding its own facts.** Two folds could disagree about whether a mark is sane,
  so the runtime could ASK the owner about an opening that the executor's gate then refuses on
  facts the owner never saw.
- **Counting regular-session seconds now.** That is §5.2's exact count, but it needs the calendar
  and an asset class per instrument. The tighter count is safe in the meantime.
