# DEC-2100: A stub token issuer for dev and CI cells only: loopback, a key made at each start, compiled out of every build without debug assertions

|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and DEC-176; it adds an issuer only where `MANDATE_DEPLOYMENT_TIER` is `dev` or `ci`, and changes nothing a staging or production deployment runs or reads) |
| **Date** | 2026-10-17 (UTC) |

| **Story or claim** | E21-52; claim #1532; the E2E lane's gap 1 (#1528); [workspace API spec](../../specs/workspace-api.md) §3.11 items 2 and 5; [identity spec](../../specs/identity.md) §6.1 |

## Context

`POST /v1/sessions` takes an access token from the one configured issuer and verifies it against
the keys that issuer publishes (workspace API spec §3.11 item 5, identity spec §6.1). The managed
issuer is Supabase Auth. A local cell has no Supabase project, so `cargo xtask cell demo` cannot
open a session, and the demo stops there.

## Invariants

Every item below holds them, and the crate's tests check each one:

- **I1.** No build without debug assertions holds the code that makes a key, signs a token, or
  serves a key set.
- **I2.** No process outside the `dev` or `ci` tier makes a key, binds a port, or signs a token.
- **I3.** No key the stub signs with exists before its process starts or after it ends, and none is
  shared with any other deployment.
- **I4.** No key set or token leaves the host the stub runs on.
- **I5.** A stub token can sign in only as a principal an operator linked for the stub's own issuer.
- **I6.** The API server is unchanged: it trusts the stub only through the three settings it
  already reads, and in any deployment that does not set them to the stub, nothing changes.

## Decision

1. **A tool crate that nothing links.** The stub is the crate `mandate-stub-issuer`, with
   `layer = "tool"` and `allowed_dependents = []` in `xtask/layers.toml`. No workspace crate may
   depend on it, so no product binary can contain it. It is `safety_critical`, so its diff is
   mutated in CI and its external dependencies are listed. It builds one binary,
   `mandate-stub-issuer`.
2. **Compiled out of every build without debug assertions (I1).** The signing and serving code is
   compiled only under `cfg(debug_assertions)`. In a build without debug assertions, the binary
   does one thing: it writes `stub_issuer_not_built` to standard error and exits 2. That covers the
   workspace's `release` profile (ES-09) and every release image lane R1 builds. The check runs
   before the tier is read.
3. **Refused outside dev and CI (I2).** The stub reads `MANDATE_DEPLOYMENT_TIER` with
   `mandate_release::startup::Tier::from_setting`, the reading every process shares. Only `dev` and
   `ci` start it. `staging`, `production`, any other value, and no value write `stub_issuer_tier`
   to standard error and exit 2. This check runs before a key is made or a port is bound.
4. **A key made at each start, held in memory only (I3).** At start, the stub makes one fresh ECDSA
   P-256 key pair from the operating system's random source. The private half is never written,
   printed, logged, or taken from a file, a variable, or an argument. So no key can be shared with
   production, whose issuer keys the platform never holds, and a restart makes every earlier token
   unverifiable. The key's `kid` is 16 random bytes in lowercase hex.
5. **Loopback only (I4).** `--bind <ip>:<port>` must be a loopback address. Any other address
   writes `stub_issuer_bind` and exits 2 before a key is made. The server already accepts `http`
   for `MANDATE_API_JWKS_URL` only to a loopback host, so a stub key set is never fetched over a
   network.
6. **What it serves.** The issuer is exactly `http://<bind>`, with no trailing slash.
   - `GET /jwks.json` answers the key set: one EC P-256 key with `kty`, `crv`, `x`, `y`, `kid`,
     `alg: "ES256"` and `use: "sig"`.
   - `POST /token` with `{"subject": "<s>"}` answers `{"access_token": "<jwt>", "expires_in": 300}`.
     The token's header is `alg: "ES256"`, `typ: "JWT"` and the key's `kid`. Its claims are `iss`,
     `sub`, `aud` (the `--audience` given, `authenticated` by default, as the managed issuer's), and
     `iat`, `nbf` and `exp`, with `exp` 300 seconds after `iat`. It is an access token, so it has
     no `nonce` (`TokenKind::AccessToken`).
   - A subject that is empty, holds a control character, or is longer than 1024 bytes is refused
     with 400, as DEC-992 item 2 refuses one. Any other request is 404.
7. **The server trusts it only as configured (I5, I6).** A cell that uses the stub sets
   `MANDATE_API_ISSUER` to the stub's issuer, `MANDATE_API_JWKS_URL` to its `/jwks.json`, and
   `MANDATE_API_AUDIENCE` to its audience. The server compares the issuer exactly. Each subject-link
   line is the digest of the canonical `{issuer, subject}` object (§3.11 item 7). So a stub token
   signs in only as a principal that `mandate identity link --issuer <the stub's issuer>` linked. A
   link made for Supabase never matches a stub token, and a stub link never matches a Supabase token.
8. **What it never does.** The stub issues no ID token, refresh token, or session cookie. It runs no
   authorization endpoint and checks no password, because it stands in only for the token the web
   app's sign-in client would hold. It keeps no state across restarts.

## Attacks considered

- **A careless operator runs the stub in staging or production.** A release build has no stub
  (item 2). A debug build there refuses to start, because the tier is not `dev` or `ci` (item 3).
- **A production server is pointed at a stub's URL.** No stub can be running there (items 2 and 3),
  so the key fetch fails and every sign-in is the server's outage, failing closed (§3.11 item 5).
- **An insider sets the tier to `dev` on a production host, runs a debug build of the stub there,
  and points that host's server at it.** This needs write access to the deployment's settings and
  its binaries, which already gives full control of that server, so the stub adds no capability
  such an insider lacks. It is recorded as a follow-up: the server should itself refuse an `http`
  key-set URL outside `dev` and `ci` (backlog, "Spec follow-ups").
- **A token is replayed.** Its `exp` bounds it to 300 seconds, and a restart of the stub ends it at
  once (item 4).
- **Something off the host reads the key set or asks for a token.** Loopback only (item 5).

## Rationale

The server's own verification path, unchanged, is what the demo needs to exercise. A stub that
publishes a key set and signs ordinary ES256 access tokens takes that path end to end, and the only
change a deployment makes is the values of three settings it already has. Making a new key at each
start means no key file exists to leak, to copy into another deployment, or to reuse.

## Alternatives considered

- **A fixed test key checked into the repository,** like `mandate-authn`'s RS256 test key:
  refused, because a key in the tree can be configured in any deployment, and the stub must share
  no key with production.
- **A setting in the API server that skips verification in dev:** refused, because it adds a branch
  to the production verification path, and the demo would then not exercise that path.
- **A cargo feature instead of `cfg(debug_assertions)`:** refused for now, because the workspace's
  per-PR test run builds without extra features, so the stub would need its own CI job in `xtask`,
  which is shared. A build without debug assertions is the release build every image uses.
