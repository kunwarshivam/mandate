## Context

`POST /v1/sessions` takes an access token from the one configured issuer and verifies it against
the keys that issuer publishes (workspace API spec §3.11 item 5, identity spec §6.1). The managed
issuer is Supabase Auth. A local cell has no Supabase project, so `cargo xtask cell demo` cannot
open a session, and the demo stops there.

## Invariants

The items below deliver these invariants, and the tests named in E21-52 and E21-53 check each one:

- **I1.** No build without debug assertions holds the code that makes a key, signs a token, or
  serves a key set.
- **I2.** No process outside the `dev` or `ci` tier makes a key, binds a port, or signs a token.
- **I3.** No key the stub signs with exists before its process starts or after it ends, and none is
  shared with any other deployment.
- **I4.** No key set or token leaves the host, or the network namespace, the stub runs in.
- **I5.** A stub token can sign in only as a principal an operator linked for the stub's own issuer.
- **I6.** In a deployment whose settings do not name the stub, nothing changes, and outside `dev`
  and `ci` the server trusts no loopback issuer at all (E21-53).

## Decision

1. **A tool crate that nothing links.** The stub is the crate `mandate-stub-issuer`, with
   `layer = "tool"` and `allowed_dependents = []` in `xtask/layers.toml`. No workspace crate may
   depend on it, so no product binary can contain it. It is `safety_critical`, so its diff is
   mutated in CI and its external dependencies are listed in `allowed_external`. It builds one
   binary, `mandate-stub-issuer`. It depends on `mandate-release` for the tier reading, and on
   crates the workspace already has: `ring` (the key and signatures), `base64`, `serde_json`,
   `tokio`, and `axum`, which lane A1's server (#1457) adds. Any crate the workspace does not
   already have gets its `docs/dependencies.md` row in the same change.
2. **Compiled out of every build without debug assertions (I1).** The signing and serving code is
   compiled only under `cfg(debug_assertions)`. In a build without debug assertions, the binary
   does one thing: it writes `stub_issuer_not_built` to standard error and exits 2. This check
   runs before the tier is read. Three things hold it:
   - The workspace's `release` profile (ES-09) leaves debug assertions off. The code PR extends
     xtask's profile check, which today covers the `dev` and `test` profiles, so that `release`,
     and every profile that inherits from it, may not turn debug assertions on. That change to
     xtask goes under its own claim, as the coordination playbook requires.
   - A test builds the crate with `--release`, runs the binary, and asserts exit 2 and
     `stub_issuer_not_built` with nothing else written.
   - Release images build named binaries (`-p <binary>`), never the whole workspace, and the stub
     is not among them. A `cargo build --workspace --release` does build the stub, which then
     refuses as above.

   The manifest check cannot see flags given outside the manifest (`RUSTFLAGS` with
   `-C debug-assertions`, or `CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS`), and neither can the test,
   which runs with default flags. Only an image build could take such a flag, and its flags are
   lane R1's reproducible build's (E21-8). That build fails when either variable is set: a change
   for lane R1, recorded with E21-52. The test runs in the crate's tests; if the `--release` build
   takes it past the ten-minute budget (DEC-464), it moves to its own shard rather than being
   dropped.
3. **Refused outside dev and CI (I2).** The stub reads `MANDATE_DEPLOYMENT_TIER` with
   `mandate_release::startup::Tier::from_setting`, the reading every process shares. Only `dev` and
   `ci` start it. `staging`, `production`, any other value, and no value write `stub_issuer_tier`
   to standard error and exit 2. This check runs before a key is made or a port is bound.
4. **A key made at each start, held in memory only (I3).** At start, the stub makes one fresh ECDSA
   P-256 key pair from the operating system's random source. The private half is never written,
   printed, logged, or taken from a file, a variable, or an argument. So no key can be shared with
   production, whose issuer keys the platform never holds, and a restart makes every earlier token
   unverifiable. The key's `kid` is 16 random bytes in lowercase hex.
5. **Loopback, in the server's own network namespace (I4).** `--bind <ip>:<port>` takes an IP
   literal, `127.0.0.1` or `[::1]`, never a host name, and a port from 1 to 65535. Any other
   address, or port 0, writes `stub_issuer_bind` and exits 2 before a key is made. The server
   accepts `http` for `MANDATE_API_JWKS_URL` only to a loopback host, and a server in a container
   sees its own loopback, not the host's. So the stub runs in the server's network namespace: as a
   process beside it on the developer's machine or the CI runner, or in the server's pod or
   Compose service (`network_mode: "service:<api>"`). That is the E2E lane's wiring (#1528). A
   stub anywhere else is unreachable, and every sign-in is the server's outage, failing closed.
6. **One exact issuer string.** The issuer is exactly `http://<bind>` as given, with no trailing
   slash: `http://127.0.0.1:8899` and `http://localhost:8899` are different issuers, and so give
   different subject-link digests. At start the stub prints one line to standard output with its
   issuer, its key-set URL and its audience, none of them secret. `MANDATE_API_ISSUER` and
   `mandate identity link --issuer` must use that issuer exactly.
7. **What it serves.** It answers HTTP/1.1 only, and only requests whose `Host` header equals the
   bind address byte for byte, with no case folding (the bind is an IP literal). Any other `Host`
   gets 421, which refuses a DNS-rebinding page that reaches
   loopback from a browser. It sends no CORS headers, so no page can read what it answers.
   - `GET /jwks.json` answers the key set: one EC P-256 key with `kty`, `crv`, `x`, `y`, `kid`,
     `alg: "ES256"` and `use: "sig"`.
   - `POST /token`, with the media type `application/json` (compared ignoring ASCII case, with
     any parameters such as `charset=utf-8` allowed) and the body `{"subject": "<s>"}`, answers
     `{"access_token": "<jwt>", "expires_in": 300}`. Any other content type gets 415, which a
     form or a no-CORS `fetch` from a page cannot send. The token's header is `alg: "ES256"`,
     `typ: "JWT"` and the key's `kid`. Its claims are `iss`, `sub`, `aud` (the `--audience` given,
     `authenticated` by default, as the managed issuer's), and `iat`, `nbf` and `exp`, with `exp`
     300 seconds after `iat`. It is an access token, so it has no `nonce` and no `azp`
     (`TokenKind::AccessToken`, one audience).
   - A subject that is empty, holds a control character, or is longer than 1024 bytes gets 400, as
     DEC-992 item 2 refuses one. A body over 4 KiB gets 413. Any other request is 404.
8. **The server trusts it only as configured (I5, I6).** A cell that uses the stub sets
   `MANDATE_API_ISSUER` to the stub's issuer, `MANDATE_API_JWKS_URL` to its key-set URL, and
   `MANDATE_API_AUDIENCE` to its audience. The server compares the issuer exactly. Each subject-link
   line is the digest of the canonical `{issuer, subject}` object (§3.11 item 7). So a stub token
   signs in only as a principal that `mandate identity link --issuer <the stub's issuer>` linked. A
   link made for Supabase never matches a stub token, and a stub link never matches a Supabase token.
9. **The server refuses a loopback issuer outside dev and CI (E21-53, I6).** The server reads
   `MANDATE_DEPLOYMENT_TIER` too, with the same `Tier::from_setting`, so no value or an unknown one
   is production (§3.11 item 2 lists it). It refuses to start, with its setting refusal for
   `MANDATE_API_JWKS_URL`, when that URL is `http` and the tier is not `dev` or `ci`. This is lane
   A1's change to `mandate-api-server`. `cell demo` runs the stub only once that change is on
   `main`.
10. **Lifecycle.** The stub keeps no state across restarts and flushes nothing. On SIGTERM or
    SIGINT it stops at once: a request in flight may get no answer, and its caller asks again. A
    port already in use writes `stub_issuer_bind` and exits 2. The server fetches the key set at
    its start and then every 300 seconds, with no fetch on an unknown `kid`. So the stub must be
    listening before the server starts: otherwise every sign-in is an outage until the server's
    next fetch. A restart makes a new key with a new `kid`. Until the server's next fetch, up to
    300 seconds later, tokens from the new key fail with the one 401, and tokens from the old key
    still verify until their own `exp`. After that fetch only the new key's tokens verify.
11. **What it never does.** The stub issues no ID token, refresh token, or session cookie. It runs no
    authorization endpoint and checks no password, because it stands in only for the token the web
    app's sign-in client would hold.

## Attacks considered

- **A careless operator runs the stub in staging or production.** A release build has no stub
  (item 2). A debug build there refuses to start, because the tier is not `dev` or `ci` (item 3).
- **A production server is pointed at a stub's URL.** The server refuses to start (item 9). Before
  E21-53 lands, no stub can run there (items 2 and 3), so the key fetch fails and every sign-in is
  the server's outage, failing closed.
- **An insider sets the tier to `dev` on a production host, runs a debug build of the stub there,
  and points that host's server at it.** Getting past the server's own refusal (item 9) then
  needs the server's tier set to `dev` too. Write access to a deployment's settings and binaries
  already gives full control of its server, so the stub adds no capability such an insider lacks.
- **Another local process, or another user on a shared dev or CI host, mints a token.** `POST
  /token` takes any subject, so any process that can reach the loopback port can sign in as any
  principal linked for the stub's issuer in that cell. This is disclosed, not blocked: a `dev` or
  `ci` cell holds paper and demo data only, never a live connection or real credentials
  (AGENTS.md rule 8). A cell on a shared host links only demo principals.
- **A web page in the developer's browser reaches the stub on loopback.** A page cannot read an
  answer, because no CORS header is sent. It cannot mint a token, because `POST /token` needs
  `application/json`, which needs a CORS preflight the stub never grants. DNS rebinding fails on
  the `Host` check (item 7).
- **A token is replayed.** Its `exp` bounds it to 300 seconds. A restart of the stub ends it at
  the server's next key fetch, if its `exp` has not already (item 10).
- **Something off the host reads the key set or asks for a token.** Loopback only (item 5).

## Rationale

The server's own verification path, unchanged, is what the demo needs to exercise. A stub that
publishes a key set and signs ordinary ES256 access tokens takes that path end to end, and a
deployment changes only the values of three settings it already has. Making a new key at each start
means no key file exists to leak, to copy into another deployment, or to reuse.

## Alternatives considered

- **A fixed test key checked into the repository,** like `mandate-authn`'s RS256 test key: refused,
  because a key in the tree can be configured in any deployment, and the stub must share no key
  with production.
- **A setting in the API server that skips verification in dev:** refused, because it adds a branch
  to the production verification path, and the demo would then not exercise that path.
- **A cargo feature instead of `cfg(debug_assertions)`:** refused for now, because the workspace's
  per-PR test run builds without extra features, so the stub would need its own CI job. A build
  without debug assertions is the release build every image uses, and item 2's xtask check keeps
  it so.
