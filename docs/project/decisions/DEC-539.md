## Context

[DEC-529](DEC-529.md) item 7 makes a Robinhood equity's protection one resting GTC stop-limit
sell, "as crypto does" ([DEC-36](../04-decision-log.md#decisions)), because the strongest form
the Robinhood profile offers is a stop-limit ([DEC-531](DEC-531.md) item 2). A stop-limit needs
the distance below the stop at which its limit sits. The mandate holds that distance only as
`protection.crypto_stop_limit_offset`, which V-008 requires only when `universe.asset_classes`
contains `crypto`, and which W-002 adds to the worst-case loss only for crypto. An equity mandate
on a stop-limit-only profile therefore has no limit to place, so it cannot deploy, and the live
order is blocked. Choosing the equity limit is not a tightening, so the SP1 builder left it to
the founder (DEC-620 item 4).

The coordinator put three options to the founder:
- one general field;
- a separate equity field beside the crypto one;
- a workspace policy value outside the mandate.

## Decision

1. **One general field.** `protection.crypto_stop_limit_offset` becomes
   `protection.stop_limit_offset`, an `open_fraction` or `null`. The offset is a fraction below
   the stop price. It applies to every protective stop-limit the platform places, whatever the
   asset class: crypto on Alpaca, and equities on a profile whose strongest protection is a
   stop-limit (Robinhood). The owner confirms it as an envelope field, like every other.
2. **V-008 reads the profile.** With protection enabled, `stop_limit_offset` is set whenever any
   instrument the mandate may hold would be protected by a stop-limit under its connection's
   profile. With protection disabled it is null, as `stop_distance` and `take_profit_distance`
   are. Validation does not see the connection's profile today, so the follow-up gives V-008 the
   profile as an explicit input. Until it has one, V-008 requires the field whenever protection is
   enabled and the connection's broker is not known to offer a bracket or OCO for every instrument
   the mandate may hold. The rule fails closed: an unknown profile requires the offset.
3. **W-002 reads it the same way.** The worst-case loss adds `stop_limit_offset` wherever the
   position's protection is a stop-limit.
4. **Change classification** is unchanged in meaning; only the field is renamed. Newly set or
   larger is increasing. Cleared, because no instrument needs it any more, or smaller is
   reducing.
5. **Migration.** The rename takes a new mandate schema version. A document at the earlier version
   reads `crypto_stop_limit_offset` as `stop_limit_offset`, and the reference cases are
   regenerated, never edited by hand. Documents and journal records already written keep their
   bytes and their hashes. The rename never rewrites a stored version, and a confirmed version
   keeps verifying under the schema version it was written with.
6. **Scope.** The spec, schema and reference-case change is one protected-path PR citing this
   decision. The code change follows DEC-77, tests first.

## Rationale

The quantity means the same thing everywhere: how far below the stop the protective sell may
fill. One field keeps one meaning, one validation rule and one line in the change classification,
and the owner confirms one number. A separate equity field would allow two different gap
tolerances for the same kind of order. A policy value would put a number that sizes the
worst-case loss outside the contract the owner confirms (non-negotiable 11).

## Alternatives considered

- **A separate `equity_stop_limit_offset` beside the crypto field.** Rejected by the founder: two
  values to confirm for one meaning.
- **A workspace policy value.** Rejected by the founder: the protection's key number would live
  outside the mandate the owner signs.
