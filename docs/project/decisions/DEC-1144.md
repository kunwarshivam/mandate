# DEC-1144: A backtest runs in `mandate-backtest-runner`, which stores artifacts only, and `mandate backtest record` journals it as the `backtest_runner` system

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79; the writer reading only narrows DEC-1141's admitted writers, DEC-176) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The lane I4 builder (Claude Code), under DEC-79 and DEC-176 |
| **Story or claim** | E4-4, E4-5; journal spec v0.51 §9.18; DEC-1000, DEC-1001 item 4, DEC-1141, DEC-986; claim [#1463](https://github.com/kunwarshivam/mandate/issues/1463) |

## Context

E4-5 left "the run's append" open: nothing calls `mandate_version_backtest::run_version` outside
tests, and nothing journals `BacktestRunRecorded`, so `GET /backtests/{id}` has nothing to serve in
the local cell. The obvious place, a `mandate backtest run` command in `mandate-cli`, is closed:
`xtask/layers.toml` puts `mandate-cli` in `workspace_services` and `mandate-executor` in
`agent_process`, no crate of one group may reach the other (DEC-986), and the run links the
executor's protection pricing. DEC-1000 already says so: "a workspace service that serves `POST
/backtests` runs it through the journal, never by linking it". The control stream's writer is a
workspace service (journal spec §2).

## Decision

1. **Two steps, meeting in the artifact store.** A new crate, `mandate-backtest-runner` (layer 9,
   in neither process group, safety-critical, nothing may depend on it, and it can reach no
   connector, shell, paper binary, or `mandate-journal-pg`), runs the backtest and writes
   artifacts only; `mandate backtest record` in `mandate-cli` journals what it wrote. The runner
   never touches the journal, and the CLI never links the run.
2. **What the runner stores.** `mandate-backtest-runner run --inputs <dir> --store <dir>
   --mandate-version <ref> --backtest-id <id>` reads the mandate document from the store under its
   version, runs `run_version`, and stores, in this order: its build text
   (`mandate-backtest-runner/<version>`, whose digest is `code_build`), the four input objects
   whose digests the report and the payload name (`VersionObjects`: the bar input, the recorded
   outputs, the theses, the configuration), the canonical report when the run completed, and last
   the §9.18 payload. So every reference the record names resolves (§6.3, §11 check 6). It prints
   `backtest_id=`, `payload=`, and `report=` or `refused=` lines. A run `run_version` refuses still
   stores its payload, `result: refused` with the stable code (rule 143). An input it cannot read
   refuses with a code (`input_invalid`, `backtest_id_invalid`, `mandate_version_invalid`,
   `mandate_missing`, `mandate_invalid`, `mandate_rejected`) and stores no payload. It reads no
   clock, no network, and no randomness: the same inputs give the same bytes.
3. **The input format.** `--inputs` holds five JSON files that `mandate-canon` parses. Decimals
   are strings, counts are integers, instants are RFC 3339 UTC, and dates are `YYYY-MM-DD`. Every
   member is required, `null` only where noted, and an unknown member is refused, so a typo never
   falls back to a default. Each file is an object:
   - `bars.json`: `coverage_start`; `corporate_actions` (the ex-dates in the data, `[date]`); and
     `bars`, a list of `{start, open, high, low, close, volume, trade_date, session, session_start,
     auction, first_bar_median}`. `session` is one of `overnight`, `pre_market`, `regular`,
     `after_hours`, `continuous`; `first_bar_median` is a quantity or `null`.
   - `outputs.json`: `outputs`, a list of `{received_at, model_id, model_version, content_hash,
     instrument, as_of, expires_at, direction, conviction, confidence}`. `direction` is `long`, and
     `content_hash` is `sha256:` and hex.
   - `theses.json`: `theses`, a list of `{thesis_id, received_at, instrument, as_of, expires_at,
     admitted, confidence, invalidated_at}`; `invalidated_at` may be `null`.
   - `instrument.json`: `{asset, ledger_id, asset_class, increment, tick, qty_increment,
     min_order_size, exchange, etp_classifications: [{at, class}], fractionable, ipo,
     ptp_no_exception}`. `tick` is `{rule: reg_nms_equity}` or `{rule: increment, increment}`.
   - `settings.json`: `{sim, fees, gate, profile, account_type, regime, metrics, min_order_usd,
     mark_max_age_s, benchmark_collar_bps}`. Each member mirrors its type's fields, spelt as the
     configuration digest spells them. Three need more than that:
     - `sim` takes `decision_latency_ms` and `approval_latency_ms`, and a `slippage` of model
       `fixed` or `sqrt`.
     - `fees` adds the fee calendar: `{valid_from, valid_to, trading_holidays,
       settlement_holidays}`.
     - `profile` is `{profile_version, rows: [{asset_class, session, cells: [{order_type,
       quantity_form, times_in_force, protection_forms}]}], idempotency}`.

   `crates/mandate-backtest-runner/tests/fixtures/demo/` is a worked example, for the cell's demo
   mandate. It has 25 daily bars of SPY at about 100 and one `quant.ma_crossover` output a day.
   The run completes: the first 19 decisions are denied below the liquidity floor, and the
   openings after them are asked and go unanswered.
4. **The runner's validation context.** The run takes a `ValidatedMandate`, so the runner
   validates the stored document in a backtest context:
   - the account is the version's own allocation and nothing else;
   - one user, no registry, no earlier or current version;
   - the validation date is the coverage start's;
   - the stop-limit classes are the classes the input profile protects with a stop-limit.

   A document this refuses refuses the run. The workspace's own validation is the one that
   counts: `record` journals only the latest confirmed version, which passed it at confirmation.
5. **What `record` re-checks.** `mandate backtest record --workspace <id> [--environment paper]
   --payload <ref> --journal <dsn> --store <dir>` trusts nothing the runner wrote. It refuses
   before anything is appended unless all of these hold:
   - It re-reads the payload by its digest (`payload_ref_invalid`, `payload_missing`,
     `payload_corrupt`).
   - The payload has exactly §9.18's twelve members, with rule 143, `marker: backtest`,
     `report_version: 2`, an id the API can name, and a code the read can serve
     (`payload_invalid`).
   - Every artifact the payload names is re-hashed (`artifact_missing`, `artifact_corrupt`).
   - The report has `kind: backtest_report` and `report_version: 2`, and its `mandate_version` and
     its four `inputs` equal the payload's (`report_mismatch`).
   - The version is stored as a mandate (`document_missing`, `document_corrupt`), and it is the
     stream's latest `MandateConfirmed` (`version_not_confirmed`).
   - The stream has a registered rule set (`rule_set_missing`).
   - No other record holds the id (`backtest_id_taken`), since the read treats two records with
     one id as unreadable.
   - The environment is the stream's own (`workspace_environment`, DEC-952).

   It appends the payload exactly. Its `config_refs` are `{mandate_version, rule_set}`, the rule
   set being the stream's latest registered one. Its `artifact_refs` are the payload's references,
   sorted. A re-run finds the record it committed (DEC-290).
6. **The writer.** The record's actor is the `system` `backtest_runner`, which DEC-1141 admits. In
   `mandate-cli` that writer is admitted for `BacktestRunRecorded` alone, as `control_services`
   is for `StreamOpened` and `MemberActivated`. The command takes no `--user`: no owner asked for
   the run through it.
7. **What is not done.**
   - `POST /backtests` and its `running` state.
   - The cell's run of both steps: the runner binary in the image, a Job that runs `run` then
     `record`, and the artifact store shared with the API pod. These land with the chart change
     after #1572.
   - A data-plane manifest for `data_snapshot` (DP-14).
   - Any test that runs both binaries together. The runner's test commits the store its demo run
     leaves (`crates/mandate-backtest-runner/tests/fixtures/demo-store.json`), and the CLI's
     tests journal that store, so the contract between the two steps is checked from both sides.
   - The fee calendar is an input the run reads, but the configuration digest does not cover it.
     That gap is `mandate-version-backtest`'s, and it is left to E4-4's slice 2.

## Rationale

The split keeps DEC-986's boundary without moving the executor's pricing out of its crate, which
would be a larger change to a safety-critical crate. Artifacts are already what the journal names
for large items (§6.3), so the runner and the CLI meet in the journal's own store, as DEC-1000
asks. Re-checking everything in `record` means a runner bug, or a hand-written payload, can at
worst be refused; it can never journal a record whose report is missing or is another version's.
A strict input format with no defaults fails closed, as every other input in the repository does.

## Alternatives considered

- **Move `mandate-cli` out of `workspace_services`, or exempt this dependency.** Rejected: it
  weakens DEC-986, which is the founder's.
- **The runner appends the record itself.** Rejected: the control stream's writer is a workspace
  service (§2), and the runner would hold a journal connection it does not otherwise need.
- **The record as the owner's `user`.** DEC-1141 admits it for a run the owner asked for through
  `POST /backtests`. This command is not that request, so the record names the runner.
- **Defaults for the settings** (Alpaca's profile, the reference cases' gate). Rejected: a
  backtest's configuration is what its digest pins, and a silent default would pin something
  nobody chose.
