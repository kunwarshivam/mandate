## Context

The web app's pause, hold, and kill-switch controls need the server to commit `OwnerCommandIssued`
on the workspace's control stream. The workspace API spec gives the routes, the idempotency rule,
and the request shapes; journal spec §9.11 gives the members the CLI already writes. They leave
open what the server writes for members the journal has no place for, which step-up it forwards,
how a scope id is found in the workspace, and what an append that does not settle answers.

## Decision

1. **The routes.** `POST /v1/workspaces/{ws}/agents/{agent}/pause` and
   `POST /v1/workspaces/{ws}/kill-switch`, with the operation names `pause` and `kill_switch` for
   §3.4's derivation (the web client's names). Checks run in §3.3 item 1's order: the session
   (401), the CSRF check (403), then `Idempotency-Key` (422 `invalid` when missing, repeated, or
   malformed), the body, read only now and by §5's lenient decoder (422), and authorization. A
   pause and a kill switch on a lapsed full session take the outage refresh of §3.11 item 6.
   **The hold waits for the runtime.** `.../hold` is not mounted, so it answers the one 401 of
   API-1 like any route not landed: the runtime folds no `hold_openings` yet (its command fold
   refuses any command it does not know as non-canonical), so a hold the API recorded would stop
   the runtime at that event, and every later control-stream event, the kill switch included,
   behind it. The route lands after the runtime folds journal spec §9.11's hold, with
   `hold_openings` as its operation name (backlog).
2. **The event is the CLI's.** `OwnerCommandIssued` version 1 on `ctl:{ws}`, with journal spec
   §9.11's members in its order: `agent`, `command`, `scope`, `subject`, `release`,
   `warning_shown`, `bid`, `bid_size`, `floor`, `user`, `submitted_at`, `step_up`. The actor is
   `{kind: "user", id}`, the principal, which `user` repeats (rule 91); `build` is the server's
   build digest. `submitted_at` is the risk-clock second of receipt. The envelope's `environment`
   is the control stream's, read from its first row. A pause names the agent as `agent` and
   `subject` with scope `agent`; a kill switch names `agent` only at agent scope, and
   its `subject` is the agent, the connection, or the workspace.
3. **No step-up is forwarded.** The server verifies no assertion yet, so `step_up` is always
   `null` and the kill switch's `step_up_status` is `missing` when the body carried none, and
   `unbound` when it carried one. A kill switch without valid step-up still cancels and stops,
   and its equity sells wait for the regular session (mandate spec §6.1, DEC-158 option (c)): the
   owner-exit privilege is not available through the API until step-up is bound. A forwarded
   assertion the server had not checked could have claimed that privilege.
4. **Members with no journal place are kept, not recorded.** `record`, `environment_shown`, and
   the kill switch's `owner_exit` pass the lenient decoder but are not written: §9.11 closes the
   hold's members, and the other commands carry the same set so that they close without a member
   renamed. Idempotency (§3.4 step 1) compares
   what is journaled: the event type, the actor, and the payload but `submitted_at`. So a repeat
   that differs only in these members replays the original, and its `dropped` is the repeat's
   own. Recording them is owed with the journal change that closes the remaining commands.
5. **A scope id is found on the control stream.** An agent is one an `AgentDeployed` names, a
   connection one a control-stream event names as `payload.connection_id`, and the workspace is
   the route's. Anything else, and a workspace whose control stream has no rows, is 404
   `not_found`. A kill switch's agent or connection that has since stopped or been revoked is
   still found: stopping it again adds no risk.
6. **The append.** The server looks the derived id up in the control stream first (§3.4 step 1):
   an event with the same journaled members answers its own `202`, and a different one 409
   `idempotency_conflict`. Otherwise each attempt takes a new writer epoch, reads the head, and
   appends the same bytes (the CLI's loop, journal spec §5.1), up to 5 attempts, retrying a moved
   head, a fence, an unavailable store, or an ambiguous commit; the retry of a commit that landed
   answers `AlreadyCommitted`. When the journal reports another event under the id, the server
   reads the control stream again and compares as in step 1: a concurrent copy of the same call
   (whose `submitted_at` differs by a second) replays, and only other content is 409
   `idempotency_conflict`. When the attempts run out, an ambiguous commit seen on any attempt
   answers 503 `outcome_unknown` with `effect: unknown` and the event id; otherwise 503
   `journal_unavailable`, `effect: none`. A draft the journal refuses is a server fault: it is not
   retried, since the same bytes are refused again, and answers `journal_unavailable`, as nothing
   was written.
7. **Never gated on readiness or drain.** These routes are served while the process is not
   ready and while it drains (§3.11 items 3 and 4). `busy` for other calls during a drain stays
   owed with E8-14's code.
8. **A failed membership read refuses them, for now (Proposed; a weakening of API-7 the founder
   must accept or reject).** API-7 and identity spec §4.5
   authorize a risk-reducing call from the session's roles snapshot when the membership read
   fails. Sessions are held in the process with no snapshot until the Postgres session store
   (DEC-978 item 6), so the server answers 503 `membership_unavailable` instead. The other course,
   authorizing any signed-in principal with no membership, would let a non-member stop the
   workspace. Meanwhile the host CLI's kill switch (identity spec §6.4 route 3) needs no
   membership read. The founder may accept this interim, or ask for a snapshot taken at sign-in
   before the demo.
9. **This change follows DEC-990 item 3:** one PR, the tests first, failing on stubs.
10. **An approval's Skip is served; a grant waits for step-up.** `POST
    /v1/workspaces/{ws}/approvals/{approval}/responses` (§5.2), operation name
    `approval_response`, is checked as item 1 orders, with §5's lenient decoder for a Skip and the
    strict one for `approved`. Its row is the matrix's Skip for a Skip and Approve for a grant, so
    a reduction-only session is refused `reduction_only`, as identity spec §4.5 reaches only pause
    and the kill switch from it.
    - The approval is found by equality with an `ApprovalRequested` event id on a deployed agent's
      stream; anything else is 404. Its agent is the stream's.
    - A Skip commits `ApprovalResponseSubmitted` version 1 with journal spec §9.7's members, as the
      CLI writes them: the agent, the approval, `skipped`, the client's `content_hash`, the
      `submitted_at` second of receipt, `step_up: null`, the principal as `responder` (rule:
      the actor's id), and `role: approver`. The `202` is `{response_id, phase: "recorded"}`, with
      `dropped` when the lenient decoder dropped a member.
    - The server does not judge the deadline, the state, the content hash, or whether the user is
      one of the mandate's `approvers`: the runtime judges each again (checks 1 to 12) and records
      a refusal as `ApprovalResponded` `refused`. A Skip it refuses adds no risk, so reading the
      mandate's approvers here is owed with the Approve route, not before.
    - An `approved` is refused 401 after the approval is found: `step_up_required` without
      evidence, and `step_up_missing` with any, since the server verifies none yet (item 3). No
      grant reaches the journal through the API until step-up is bound (backlog).

## Rationale

The server writes what the runtime already reads from the CLI, so nothing downstream changes.
Every open choice takes the course that adds no risk. No unverified step-up is forwarded. A
repeat never commits twice. A scope the workspace does not hold is refused rather than
journaled. The one departure from API-7 is item 8, which refuses rather than widens access, and
it goes to the founder.

## Alternatives considered

- **Forward the body's `step_up` as sent.** The runtime judges freshness and reuse, not the
  passkey signature, so a forged assertion could unlock the owner-exit privilege.
- **Add `record` and `environment_shown` to the payload.** §9.11 closes the hold's members, and
  rule 84's batch reads the kill switch's. A new member needs a journal spec change first.
- **Answer `busy` after the attempts run out.** API-7 does not list contention among its
  refusals. `journal_unavailable` states what happened, and the client retries with the same key.
