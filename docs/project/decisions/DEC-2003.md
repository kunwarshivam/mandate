## Context

E21-30 asks for the account executor as a long-running process beside the runtime's
(`mandate-daemon`, DEC-1012). In one process the shell hands each runtime intent to the executor in
memory. Across processes the journal is the only channel (design §3.1). Three things the in-memory
handoff carries are not journaled as a handoff:
- an opening's protective prices, which `IntentProposed` does not record (DEC-446 item 5);
- a kill switch's flatten plan, which the runtime builds from its own view;
- the agent's mode change, which the executor's core copies only in E7-4's unlanded slice 5.

The core also answers a stub for a flatten handed as an intent (E7-4). The one kill-switch path it
implements is its own `Command::KillSwitch` of the agent scope.

## Decision

1. **A new safety-critical crate, `mandate-executord` (layer 8, process group `agent_process`).**
   `ExecutorProcess` hosts one account's `mandate-executor` core over `mandate-store`, with
   `mandate-process`'s lifecycle. Its `forbidden_internal` list keeps it from `mandate-daemon`,
   `mandate-agentd`, the shell, the paper runner, the MCP client, the CLI, the Robinhood connector
   and the broker simulator. `mandate-daemon`'s own list already keeps the runtime from it. Its
   broker is the `Broker` port, and it names no host. E21-30's criteria named one crate,
   `mandate-daemon`, for both processes; DEC-1012 item 1 keeps that crate from ever reaching the
   executor, so the reading that keeps it is two crates, and the backlog says so now. It tightens
   the runtime's isolation and loosens nothing (DEC-176). The binary, the fixture broker and the cell
   image are their own changes (lane X slices X2 and X3).
2. **The process lifecycle.**
   - **Start.** It refuses any environment but paper before taking the stream. It takes a newer
     epoch on the account stream and folds it. It writes `StreamOpened` only to an empty stream.
   - **`Input::Started`.** The first pass that reads a tick hands that tick and then
     `Input::Started`, because every record the start leads to carries the risk clock (mandate spec
     §5.2).
   - **In doubt, fenced, refused.** An input whose append is in doubt is handed again before
     anything else, as the same bytes, and nothing it asks of the broker leaves first. `Fenced`
     exits `fenced`. Any other refusal exits `cycle_failed`, and the restart replays. Requests
     whose drafts committed but which an answer's own doubt left unsent stay in order and go out
     first on the next pass.
   - **Drain.** SIGTERM drains as DEC-1012 item 7 does.
3. **Which agents it follows.** It follows the account's agents, read from the control stream as
   DEC-1171 item 4 reads them:
   - an agent whose latest version-2 `AgentDeployed` names a connection;
   - and that connection's latest establishment or revocation is a version-2
     `ConnectionEstablished` naming this `account_ref` in this environment.

   A version-1 deployment reaches no executor. An agent whose deployment stopped is still followed,
   since it may still hold orders or a position its kill switch must reach (`AGENTS.md` rule 13).
   A deployment or connection record that does not read stops the process rather than drop an agent
   the account may owe a kill switch (DEC-85).
4. **What it hands, rebuilt from the journal.**
   - **An `IntentProposed` limit order** is handed as the intent the runtime would have handed in
     one process, identified by its event id (journal spec §2). An opening's or increase's
     protective prices come from the `Protections` port: the mandate's protection for an entry at
     the limit, as the executor derives it in one process (`equity_bracket_prices`). A port that
     cannot answer stops the process rather than send an opening without the protection its mandate
     asks for.
   - **A `KillSwitchActivated` on an agent's stream** is applied as the core's own
     `Command::KillSwitch` of that agent alone, over the executor's own ledger. It is never the
     runtime's plan, and never `cancel-all` or `close-position`, whatever scope the copy records
     (`AGENTS.md` rule 13). The executor's ledger is the authoritative record of the agent's orders
     and sub-ledger, so this reads tighter, not looser, than handing the runtime's view.
   - **Applied once, by its own record.** The core's `Command::KillSwitch` gains `cause`, the
     record it copies. The core journals it as the account stream's `KillSwitchActivated`
     `copied_from` (that schema is not closed, journal spec §9.1), and its fold reads it back
     (`ExecutorState::applied_copy`). A switch counts as applied exactly when this stream's own
     records say so. It is never inferred from the agent's mode, which a pause of every agent, an
     earlier pause of the agent, or a blocked account may already have set, and which a lift back
     to `normal` would clear (the #1596 review's major).
   - **The owner's confirmation** is the confirmed bid of the agent-scope `OwnerExitRequested`
     copied from the same command (journal spec §9.1 rule 16), when there is one.
5. **Order of a pass, and readiness.**
   - **Order.** The input in doubt, then unsent requests and a due reconciliation, then every
     agent's kill switches (ES-06), then the latest tick, then the orders in each agent's stream
     order.
   - **Ready.** Epoch held, stream replayed, and the startup reconciliation clean: a reconciliation
     has run and nothing is mismatched (design §3.4).
   - **Openings.** An opening or an increase is handed only while ready. One that a later
     `KillSwitchActivated`, or a later `AgentModeChanged` to any mode but `normal`, follows on its
     agent's stream is never handed: the agent stopped wanting it before the executor took it.
   - **Exits.** Exits and the kill switch are handed once the stream is replayed, ready or not.
   - **An unreadable agent stream row.** It stops the process only after every other agent's
     switches in the pass are applied.
   - **A stream that stops reading** raises one opaque alert (`stream_unreadable`, no subject;
     `AGENTS.md` rule 6), and another only after it has read again.
6. **Gaps, held rather than worked around.** Each fails closed, and each closes when its story
   lands.
   - **Market owner exits and flatten intents.** An owner's exit at the market is not handed: the
     core's handoff takes no market order, and its flatten intent is E7-4's stub. An owner's exit
     at a limit is handed as an order.
   - **The mode copy.** The copy of `AgentModeChanged` into `AgentModeApplied` is E7-4 slice 5.
   - **The kill switch reaches the executor only through the runtime's copy (a disclosed limit
     against `AGENTS.md` rule 13's "the kill switch is always available").** Design §3.6 has the
     kill-switch path need only Postgres, the executor process and the broker. Reading the
     control stream's `OwnerCommandIssued` directly needs the core's account and workspace scopes,
     and its flatten intent needs E7-4's flatten-intent body; both are E7-4 stubs today. Until
     they land, a kill switch reaches the executor only after the runtime has copied it as
     `KillSwitchActivated` on the agent's stream, so a runtime that is down delays it. The
     deployment manager starts at once a process that a kill switch covers and that is down
     (design §3.4), which bounds the delay but does not remove it. The backlog records E7-4's
     flatten-intent body and its account and workspace scopes as a prerequisite before the
     executor process runs anywhere beyond the dev and CI cell (E21-30's *Left*).
   - **The first tick.** Before `Input::Started` nothing is applied, and `Input::Started` waits for
     the scheduler's first tick on the clock stream, so a new executor's first kill switch also
     depends on the scheduler having ticked once. A running executor does not wait on later ticks.
7. **The broker.**
   - **Reconciliation.** The core's four reconciliation reads go as one snapshot, its account
     reported first, as the shell's start does. The reconciliation runs at the head the report
     left.
   - **A lost read.** A read whose answer is lost leaves the reconciliation due for the next pass,
     since a read changes nothing at the broker. The pass goes on, so the kill switch never waits
     on it.
   - **Other failures.** A request that cannot be sent, or an answer that cannot be read, stops
     the process (DEC-85).
   - **The chain bound.** One input may lead at most `max_chain` broker answers deep (64 in the
     binary) before the process stops.
8. **The journal is the only channel; a wake hint only adds a pass** (DEC-17, ES-20). The process
   takes no hint as input. A pass with nothing new journals nothing and sends nothing, and a
   property test shows it.
9. **Paper only.** The start refuses any other environment before it takes the stream (DEC-968
   item 1, DEC-1012 item 10).

## Slices

Lane X lands this decision in two changes, at the coordinator's request. X1a: items 1 to 3, item
4's kill switch, item 5's order of a pass and readiness, and items 6 to 9. X1b, after X1a merges:
item 4's order handoffs and protections and item 5's openings and exits.

## Rationale

The runtime and the executor already meet only in the journal (E21-42), so the executor's process
rebuilds each handoff from journaled facts plus the mandate it is deployed under, and applies the
kill switch through the one path the core implements. Every gap is a refusal or a hold, never a
guess.

## Alternatives considered

- **Host the executor in `mandate-daemon`.** Rejected: the daemon's `forbidden_internal` list is
  what makes "the runtime has no route to a broker" hold by construction (DEC-1012 item 1).
- **Hand the kill switch as a flatten intent with the runtime's plan.** Rejected: the core answers
  a stub for it, and the plan is the runtime's view of a ledger the executor owns.
- **Journal the protective prices on `IntentProposed` (a journal spec change).** Not needed now:
  the executor already derives them from the mandate in one process. Revisit if a runtime ever
  proposes protection the mandate does not imply.
- **Byte-identical journals with and without extra passes.** Rejected as a test: event ids carry
  the writer epoch and races with later runtime records are latency, so the property is stated as
  "a pass with nothing new changes nothing".
