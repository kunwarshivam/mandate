## Context

DEC-2394 lets the agent read Alpaca's news feed. The feed must be read-only, with a paper
credential leased from the vault and never logged, each item journaled before use, through
allowlisted egress, and with recorded items only in CI. `mandate-sources` already fetches and
parses Alpaca news through a `Transport`, and authenticates with `NewsAuth`, an Alpaca key id and
secret. What no process has yet is a credential to read with.

The vault holds two kinds of Alpaca credential today, and neither fits:

- **A connection's OAuth token** (`SecretPath::Token`). It is scoped `trading data`, and only that
  connection's executor may read it (DEC-977). Letting a news reader read it would put an
  order-capable credential in a second process. AGENTS.md rule 7 and DEC-977's one-reader-per-secret
  rule both argue against that.
- **`NewsAuth`'s key id and secret.** No vault path or identity holds them (DEC-1130 item 10 left
  them to the vault work).

DEC-2020 says "a broker's paper key is a connection's credential: it stays the connection's
token". That stays true, and this decision changes nothing about it. The key here is not a
connection's credential. It belongs to a separate paper account that no connection names, and it
is used for news alone. A trading connection's key must never be put where this key goes. Nothing
technical tells two Alpaca keys apart beyond what item 4 checks, so section M of FOUNDER-STEPS
says so.

## Decision

1. **A separate key, for news only.** The news reader authenticates with its own Alpaca API key id
   and secret. These come from an Alpaca **paper** account the founder keeps for this purpose
   alone, with no strategy and no connection to the platform. Alpaca API keys carry no scopes: any
   key can call any endpoint its account allows. So this key's reach is that empty paper account's
   reach. It never touches the trading connections' token, any live account, or any funds. The
   reader can send it only to `https://data.alpaca.markets/v1beta1/news`: `PermittedUrl` is the
   only thing a `Transport` accepts (DP-9), and allowlist version 3 lists that one endpoint
   (DEC-2276).
2. **One identity, one path, DEC-2020's pattern.**
   - `Identity::NewsReader` (role `news-reader`).
   - `SecretPath::Platform(PlatformSecret::NewsDataKey)` (`platform/news-data-key`): one entry
     holding the key id and the secret together.
   - `policy::holders` gives it one reader and one writer:

     | Secret | Read | Write | Delete |
     |---|---|---|---|
     | The news data key | News reader | Secret import | — |

   Every other identity is refused all three, the runtime and the executor included. The news
   reader itself reads nothing else. The OpenBao policy, the Kubernetes-auth role, and the local
   backend follow the same table, as they do for DEC-2020's secrets.
3. **Read once, kept in memory, never logged.** The reader reads the key with
   `SecretSource::read` at start and after a rotation, as DEC-2020 item 3 says. DEC-2394's "leased
   from the vault" is this read: DEC-2020 item 3 reads a platform secret rather than leasing it,
   because the secret is rotated by hand. It keeps the key
   only as `NewsAuth`, whose `Debug` redacts both values, and the HTTPS transport marks both
   headers sensitive. The key appears in no log, error, journal record, notification, or artifact.
4. **No key, no news, nothing else held.** Until the founder writes the key, the reader refuses
   with a typed `NoKey` and fetches nothing.

   **A paper key only (DEC-2394 item 2, AGENTS.md rule 8).** The reader refuses, with a typed
   `NotPaper`, a key whose id does not begin `PK`, the prefix of Alpaca's paper keys (live keys
   begin `AK`). It then fetches nothing and keeps no part of the key. This is a guard against a
   live key pasted by mistake, not a proof: it rests on Alpaca's key-id convention. A stronger
   check, a read-only probe of the paper trading host at start, would add that host to the
   reader's egress, and is left to a later decision. DEC-2394's open item on checking that the key
   is a paper one is narrowed by this guard, not closed.

   A vault outage at start is an outage, not a refusal. With no key, a key refused, or an outage,
   the agent keeps working without news: its scheduled research and every trading path are
   unaffected, and no step waits on the feed.
5. **The founder's step.** The founder creates the paper account and its key in Alpaca, and puts
   the key into the staging vault through `infra`'s secret import, as he does the OpenRouter key
   (`deploy/FOUNDER-STEPS.md`, section M). No agent asks for the key, sees it, or handles it.
6. **Scope.** It is one platform key for the cell's paper workspace. Data-plane spec §4.1, which is
   the founder's (DEC-433 item 16), reads Alpaca news "per workspace, on its own connection". That
   stays the target. This key is an interim, recorded at §4.1. What holds it to the founder's
   workspace:
   - the news reader is deployed only in that workspace's namespace;
   - its vault role is bound only to that namespace's service account.

   Serving any other workspace needs a key per workspace, which is a later decision.

## Consequences

- The code follows in its own PR:
  - `mandate-vault` gains the identity and the path, the policy, the role, and the local backend,
    with the conformance and policy tests;
  - `mandate vault put` gains `news-data-key`;
  - the `infra` apply writes it from the environment secrets `ALPACA_NEWS_KEY_ID` and
    `ALPACA_NEWS_SECRET`;
  - the news reader reads the key, refusing `NoKey` and `NotPaper`, and polls through
    `mandate-sources` with allowlist version 3 (DEC-2276, which lands first).
- CI never holds the key. Its tests use recorded items and a fake vault.
- **Rotation:** replace the environment secrets, `apply`, and restart the reader. To stop all news
  reads at once, revoke the key in Alpaca: every fetch then fails with no item, which is the safe
  default.
