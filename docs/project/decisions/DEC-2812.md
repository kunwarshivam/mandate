# DEC-2812: `FillApplied` version 2 records an unattributed fill

| **Date** | 2026-10-26 (UTC) |
| **Decided by** | Lane MC (Claude Code), number from the coordinator's trading-core range |

## Context

Trading spec §6.1 gives a fill's `client_order_id` as "absent for external fills: each is its own
order". §7.1 says such a fill is ingested unattributed, every agent goes `exits_only`, and the owner
is alerted. `FillApplied` version 1 requires a non-empty `client_order_id`, so the journal refused
the executor's batch for every fill it did not originate. DEC-2805 turned that refusal from a crash
loop into a hold of every agent's openings, but the fill was still never booked. The account's
position and cash were wrong in the executor's books, and the activity cursor never passed the
fill. Every later reconciliation read it again and was refused again, so the hold could not end.

## Decision

1. **`FillApplied` version 2** (journal spec §9.5, v0.94) has version 1's members, in version 1's
   order, with `client_order_id` `text?`. It is `null` for a fill that names no order of ours, and
   nothing else moves. Version 1 stays registered and unchanged. `LateFillApplied` stays at
   version 1, because a late fill is always of an order of ours.
2. **Rule 299.** A non-null `client_order_id` at version 2 is one of ours, as trading spec §2.3
   (v0.21, DEC-2807) states it: `md-`, then one or more ASCII letters, digits or hyphens, at most
   128 characters. A fill that names another system's id names no order of ours, so it is
   written `null`. This tightens what version 1 admitted. The executor's ids are `ClientOrderId`s,
   whose grammar is this one, so every fill it writes satisfies the rule by construction.
3. **The executor writes version 2 for every `FillApplied`.** An unattributed fill is written with
   `client_order_id` `null` in the batch §7.1 already gives it: `ExternalActivityIngested` first,
   then the fill, then every agent's `exits_only` under `reconciliation:external_activity` and the
   owner's alert. The fold moves the account's position and cash, and no order's filled quantity. A
   sell joins the unattributed sells an ended sell's report may net (DEC-421 item 5). The batch
   commits, so a reconciliation that read the fill moves its activity checkpoint past it. The next
   one does not read it again, and the hold lasts until the owner acknowledges `external_activity`,
   as §7.1 says.
4. **Readers.** `mandate-gate-context`'s two folds read a `null` `client_order_id` as naming no
   order. The account's positions move, and no agent's sub-ledger or held quantity does. Before
   this, either fold refused the row, and with it the gate's whole read of the account.

## Not covered

- **A fill in an instrument with no instrument snapshot** carries none of the `config_refs` §9
  requires of `FillApplied` (fee, calendars, instrument snapshot), so the journal still refuses
  it, and DEC-2805's hold stands in. An owner trading another symbol by hand is the likeliest
  case. The backlog holds the row.
- **A fill with an empty fill id** is still refused, because `fill_id` stays `text` (DEC-2803 item
  2), and DEC-2805's hold stands in.

## Rationale

- §6.1 and §7.1 already say what an unattributed fill is. Version 1 was stricter than the trading
  spec, and the strictness did not make anything safer: the fill had happened at the broker, and
  refusing the record only left the executor's books out of step with the account.
- A nullable member at a new version, rather than an edited version 1, keeps every stored record
  replaying byte for byte (journal spec §8).

## Alternatives considered

- **Leave `client_order_id` absent, as §6.1's wording has it.** Rejected: §9.1's absent-member rule
  holds for every closed schema, so the member is present and `null`.
- **A separate `ExternalFillApplied` record.** Rejected: the fold, the gate's read and the
  read models already treat `FillApplied` as the one fill record, and a second type would need
  every reader to learn it.
- **Write an external sentinel id such as `external`.** Rejected: an id that is not an order's would
  read as one, and rule 299 would have to carve it out.
