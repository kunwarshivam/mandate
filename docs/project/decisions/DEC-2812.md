# DEC-2812: The executor process reads its broker's answers by asset id

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79. It adds no risk: every opening still passes the binding gate, and an answer the deployment does not name stays as the broker gave it) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent (Claude Code, lane X, claim [#754](https://github.com/kunwarshivam/mandate/issues/754)) |
| **Story or claim** | E21-30 slice X1b-3, the cell's trade loop; [DEC-938](DEC-938.md) item 1, [DEC-2380](DEC-2380.md) item 2 |

## Context

A process-level test of the cell's whole trade loop found a gap between `mandate-executord` and the
paper shell that stops the loop. The test runs a deployed SPY agent's opening on the fixture broker,
with every port but the broker real. The executor names an equity by its asset id and sends that id
as the order's `symbol`, which Alpaca accepts (DEC-938 item 1). Alpaca answers by ticker: the order
read back, the position and the `FILL` all say `SPY`. The shell reads every answer through
`BrokerSymbols`, which puts the asset id back (#1355). The executor process read them raw, so its
own fill would be another instrument's. The fixture broker echoed the asset id instead of answering
by ticker, the client refused that as a symbol, and the process stopped right after its first
submission.

## Decision

1. **One ticker map, shared.** `BrokerSymbols` moves unchanged from `mandate-shell` into
   `mandate-executor`, which owns the types it maps. The shell's `Platform` connector keeps
   reading through it.
2. **The executor process reads its broker by asset id.** A deployed run's broker
   (`deployment::Named`) reads every answer through the deployment's tickers. These are each
   followed agent's current deployment, else its last that read, so a held position's own orders
   and fills keep their asset id through a store outage (`AGENTS.md` rule 13). A ticker no
   deployment names stays as the broker spelled it, so an instrument the run does not trade is
   never taken for one it does. An undeployed run reads its broker's answers unchanged.
3. **The fixture broker answers as Alpaca does.** Each of its assets carries an asset id: SPY's is
   `b28f4066-5c6d-479b-a2af-85dc1a8f16fb`, and QQQ's is the one the cell's demo snapshot registers.
   It takes an asset id as an order's `symbol` and names that asset by its ticker in every answer,
   position and fill. A symbol that is no asset's id stays as sent. Its asset record carries the
   same id.
4. **The marks stay after the pass's proposals.** The binding gate reads the executor's own latest
   mark. The cell's scheduler ticks every second and the executor marks each instrument every 15
   seconds (`marks::MARK_EVERY`), so that mark is well inside the gate's one-minute bound. Marking
   before the proposals would let a mark whose append goes in doubt hold the pass's exits, since
   nothing may be appended after it until it is offered again. The trade-loop test ticks every
   five seconds; at one tick a minute, every opening would be held as `StaleMark`.

## Rationale

The founder's demo needs the cell's trade loop to fill, book and protect a paper order with only
the broker a fixture. Reading the broker through the same map as the shell keeps the two paths'
reading of one answer the same.

## Alternatives considered

- **Send the ticker instead of the asset id.** Rejected: DEC-938 sends the asset id, which a ticker
  change cannot redirect to another instrument.
- **Journal the marks before the pass's proposals.** Rejected: a mark in doubt would hold that
  pass's exits (`AGENTS.md` rule 13), and at the cell's cadence the gate's mark is already fresh.
