# DEC-836: A re-shown active deployment shows its code with no warnings, and warnings keep `check_rules`' order

| | |
|---|---|
| **Status** | Accepted (an agent, DEC-176) |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The builder agent under DEC-176: the reading adds no risk, because a re-display changes no state |
| **Story or claim** | E10-16 D2c (claim #850), PR #854 |

## Decision

1. `agent deploy` without `--code`, for an agent whose active deployment is the named version,
   shows that deployment's code with no warnings, whatever the rules now say, and writes nothing.
   This reads DEC-530 item 9's "returns that event": a re-run commits nothing new, so there is
   nothing new to acknowledge.
2. While another version is the agent's active deployment, showing a deployment is refused
   `agent_active` (DEC-530 item 9.7), even for a confirmed version.
3. Shown warnings keep the order `check_rules` gives them. That order is already by code, because
   the warnings come from a `BTreeSet` whose order follows the codes (DEC-530 item 4), so no
   separate sort is kept.

## Rationale

The reading came from the independent review of #854, which found the already-deployed branch
untested and the explicit sort an equivalent mutant. Tests-correction PR #860 pinned items 1 to 3
(`a_deployed_agent_shows_its_version_and_refuses_another`, `warnings_are_shown_sorted_by_code`,
and the binary's `warnings none` re-display against Postgres). A re-display writes nothing and
changes no state, so showing no warnings adds no risk; the deploy itself, with `--code`, still
runs every check.

## Alternatives considered

- **Re-run the W-rules on a re-display.** Not taken: it would ask the owner to acknowledge
  warnings for a gesture that commits nothing.
- **Keep the explicit sort.** Not taken: it cannot change the output, so it is code no test can
  pin.
