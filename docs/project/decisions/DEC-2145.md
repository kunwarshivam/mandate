# DEC-2145: The workspace API reads each stream once, then only what follows

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79. It adds no risk: every row served was verified by the store's chain check, only to its own workspace, and a stream is read whole again at its first read a minute after its last whole read) |
| **Date** | 2026-10-27 (UTC) |
| **Decided by** | `claude-code` (lane WB), asked for by the coordinator on 2026-10-27 |
| **Story or claim** | E21-31, the API server's reads; [DEC-2847](DEC-2847.md) |

## Context

Every page the workspace API serves reads each stream it shows from Postgres, verifies it from its
first record, and folds it again: the agent's positions and orders, the account's rows, the
control stream. Measured on the folds alone, a read costs about 4.3 µs a row: 238 rows take about
1 ms, 10,000 about 46 to 62 ms, and 100,000 about 420 ms, before the database read itself, which is
likely the larger cost. A page polled every few seconds against a deployment that has run for weeks
grows past what a reader waits for, and so does the server's load.

## Decision

1. **A verified row cache at the journal port.** The server's [`Journal`] port is a
   `CachedJournal` (`crates/mandate-api-server/src/cache.rs`) over the Postgres journal. The first
   read of a stream reads it whole and holds its rows. Each later read asks the store for the rows
   from the held head row on, through `rows_from` with the same chain check from a trusted start as
   [DEC-2847](DEC-2847.md) item 1, starting from the head row's `prev_hash`. The first row returned
   must be the held head row, seq and hash alike; only then are the rows after it appended.
2. **What a read past the head sees.** Appends, and any change that reaches the held head row or
   cuts the stream below it, are seen at the next read: a tail the store refuses, or one that does
   not begin with the held head row, drops what is held and reads the stream from its first record
   again.
3. **Reverify.** A change only to rows before the held head, leaving the head row's hash as it was,
   breaks the stored chain, so a whole read fails; a tail read from the head cannot see it. A held
   stream is therefore read whole again at its first read once its last whole read is
   `Limits::reverify` old (60 s on the server), or once the clock reads earlier than that whole
   read, since a clock stepped back cannot vouch for it. Growing a stream by a tail read does not
   restart that time. So for a tampered hot store, and only then, a read may serve the rows last
   verified for up to a minute where an uncached read would fail. That is the one difference in
   what is served, and the coordinator accepted it on 2026-10-27.
4. **Fail closed.** A whole read that fails, on that re-read or any other, drops every stream held
   for the workspace and answers `JournalUnavailable`, exactly as the uncached read does (the
   handler's answer and logging are the same); nothing held is served in its place, and the
   workspace's other streams are read whole at their next read.
5. **The executor's gap.** DEC-2847 item 4 accepts the same blind spot for the executor's kept folds
   and the runtime's tails, and there it lasts until the process restarts, not a minute. Backlog
   row `E21-31-executor-periodic-whole-reverify` asks lane D1 to give them the same bound.
6. **Tenancy.** Rows are held per workspace, by the workspace segment every stream id carries
   (journal spec §2; the second segment of any stream id), and per stream id within it. A read returns only the rows held under its own
   stream id. A stream id that names no workspace is not held. Appends, heads, ownership and
   single-event reads go to the store unchanged.
7. **Bounded memory.** `Limits::SERVER`: a workspace no read touched for ten minutes on the
   server's clock, or whose last read the clock now reads as later than now, is dropped whole at
   the next read, and the rows held, counted with every string and body they own (`row_bytes`),
   stay under about 256 MiB (map keys and allocator overhead are not counted), by dropping the least recently read other
   workspaces first; a stream larger than the bound by itself is served and not held. Byte totals
   are kept as rows are held, so no read scans what is held. A read while the clock cannot be read
   goes to the store and holds nothing.
8. **Proof.** `crates/mandate-api-server/tests/read_cache.rs`, over a store that checks its chain
   as `PgJournal` does: a counting test (a read past N new rows reads exactly those N, after the
   held head row), two workspaces read in turn, cut and rewritten streams, a changed head row, a
   change below the head seen at reverify and not before, reverify counted from the last whole read
   through growth, a clock stepped back, a failed whole read dropping its workspace and no other,
   the idle bound at its boundary, held bytes exact after growth, rewrite and cut, the byte bound
   across workspaces and within one, and an oracle that every cached read at
   random points of random appends, cuts, rewrites and failures equals the stream read whole. The
   oracle is shown failing on three seeded caches: one that never reads past its head, one that
   does not read the head row again, and one keyed by the stream's last segment.
9. **Cost.** The store's read and chain check no longer grow with a stream's length. The rows handed
   to each caller are still a copy of the whole stream, since the port returns owned rows, and the
   folds over them still run whole; item 10 takes those on.
10. **Next.** The account folds (positions, orders) become incremental over the held rows in a
   following change, with their own counting test. The Postgres read is measured before and after
   in a cell.

## Alternatives considered

- **Read past the head without re-reading the head row.** It reads one row fewer, but a rewrite
  that keeps the stream's length is not seen, so a read could serve rows that are no longer the
  stream's. Rejected: the API must serve exactly the stream.
- **Cache folded pages per request.** Each page would still fold the whole stream once it changes,
  so the cost would still grow with the stream's length.
- **Re-read the whole stream on every read, to see every change at once.** That is the cost this
  decision removes. A minute's bound on a tampered store, which already fails every whole read and
  every new start, adds no risk.
- **No bound but idle time.** One busy workspace could hold the server's memory; the byte bound
  keeps it fixed.
