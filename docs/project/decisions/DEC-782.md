# DEC-782: The order and report of §11's stream-type range checks in `mandate journal verify` and `verify-cold`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The L5 lane lead (`claude-code`) under DEC-79 and DEC-176: a reversible engineering choice that changes no outcome, only which code a run that fails several checks reports, and takes §11's own fail-closed path where the CLI lacks an input |
| **Story or claim** | E12-3 ([#748](https://github.com/kunwarshivam/mandate/issues/748)); extends [DEC-490](DEC-490.md) items 5 and 7 (`verify-cold`) and E5-4's `verify` |

## Decision

The CLI's two verifiers gain the §11 range checks that exist as library functions:

- on a control stream, `anchor_self_mismatch` and `break_glass_cause_mismatch`
  (`mandate_journal::verify_anchor_self`, `verify_break_glass_causes`);
- on an agent stream, `intent_action_mismatch`, `mode_event_mismatch` and `held_mismatch`
  (`verify_agent_stream_anchored`).

§11 lists the per-range checks without an order (DEC-490 item 5), so:

1. **The run order.** A run executes these steps in order, and the first that fails is the one
   reported:
   1. checks 1 to 6 over the range, unchanged;
   2. the range checks of the export's stream type, read from its `stream_id` (the other types
      run none of these);
   3. with `--anchor`, the anchor checks, unchanged;
   4. for `verify-cold` with `--token`, the token check, unchanged.
2. **Within one stream type, the lowest `seq` wins.** Its checks report the failure at the lowest
   `seq`, with ties broken by §11's listing order. That is how
   `verify_agent_stream_anchored` already reports across its own three checks.
3. **The report.** A failure of these checks is reported at an event (journal spec rule 111), so
   both commands print it as DEC-490 item 7 prints a per-event failure:
   `result: failed, seq <n>, <code>`. The process exits non-zero, as today.
4. **Their inputs.** The checks take the trusted start the command already has.
   - **Hold anchor.** The CLI cannot read the stored chain before a range, so it passes no hold
     anchor, which §11 allows "when the caller cannot read that chain". A range from `seq` 1 is a
     full chain, anchored on nothing before it.
   - **A tail range** therefore fails closed at its first version-2 `AgentModeChanged` that is not
     a hold or a lift. This is §11's own outcome for "no anchor", not a loosening.
5. **The connection checks wait.** The CLI does not yet run `connection_lifecycle_mismatch` or
   `connection_cause_mismatch`.
   - The library's lifecycle check does not take a trusted start, and does not implement rule 131.
   - The cause check spans the control stream and its account streams, which neither command
     reads together.
   - Until the library and a multi-stream input exist, no run of the CLI reports either code.

## Rationale

Every order gives the same verdict: a range that fails any check fails. The order only decides
which code a multiply broken range shows first. Running the stream's own checks before the anchor
checks follows DEC-490 item 5's reason: an anchor vouches for checked events, so the checks it
depends on come first. The report form reuses DEC-490's per-event line, so tooling that already
reads it reads these codes too.

## Alternatives considered

- **The anchor checks first.** Rejected: they assume the range's events are sound, which the
  stream checks establish.
- **A new line form for these codes.** Rejected: rule 111 reports them at an event, which is
  exactly what DEC-490's per-event line carries.
- **Running the lifecycle check from the range's first event.** Rejected: it would fail records
  that refer to state before the range, which is a false failure.

## Follow-up

§11 and rule 111 report `anchor_head_mismatch` at the anchored `seq`, while both commands print it
without one, as DEC-490 item 7 says. Aligning that line is a backlog item, not part of this
decision.
