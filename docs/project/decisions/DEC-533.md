# DEC-533: Close the approval answer and the runtime's two records of it (journal spec v0.17 §9.7)

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | An agent (Claude Code, the J2 builder) under DEC-79 and DEC-176, with the coordinator's rulings on the two choices the spec left open (items 2 and 3). Closing a schema from the members its §9 row already lists refuses unknown members and adds no risk |
| **Story or claim** | J2 (the [first live trade brief](../tasks/first-live-trade.md)'s K1a prerequisite); E8-3; claim [#213](https://github.com/kunwarshivam/mandate/issues/213) |

The coordinator assigned this number.

## Context

`mandate approvals approve` and `skip` commit `ApprovalResponseSubmitted`. The runtime copies each
answer as `ApprovalResponded` and re-validates an admitted grant as `ApprovalRevalidated`. None of
the three could be appended to a real journal:

- `mandate-journal`'s catalogue lists neither `ApprovalResponseSubmitted` nor
  `ApprovalRevalidated`, so a draft of either is refused `unknown_event_type`.
- `ApprovalResponded` is catalogued, but its payload has no registered schema, so it is refused
  `unknown_schema`.

Journal spec §9 lists each record's members only in prose (DEC-131 item 25(h)). §9.6 (DEC-460)
closed `ApprovalRequested` and `ApprovalDelivered` and stopped there. The M7 tests passed only
because the CLI's test journal validates nothing (DEC-257 item 17). As a result, an `ask` cannot be
granted on Postgres, on paper or live, so LT-4 cannot hold.

## Decision

1. **Journal spec v0.17 adds §9.7**, which closes three records at schema version 1 with rules 46
   to 53: `ApprovalResponseSubmitted` on the control stream, and `ApprovalResponded` and
   `ApprovalRevalidated` on the agent stream (both naming `mandate_version`). The members are
   exactly the ones their §9 rows and mandate spec §6.4 list. Their names and types are the ones
   the CLI and runtime write today, except where items 3 and 4 change a writer. The spec's §9
   tables already place each record on its stream; `mandate-journal`'s catalogue gains the two
   records it lacks in J2's implementation.
2. **Times are integer risk-clock seconds.** That covers `submitted_at`, `effective_at` and the
   step-up evidence's `authenticated_at`. This follows DEC-257 item 5, §9.6's
   `ApprovalRequested.deadline`, and both writers, with no code change (the coordinator's choice
   (B)).
   - **The inconsistency, stated openly:** the step-up evidence of every other closed schema
     (`OwnerExitRequested`, `DisclosureAccepted`, `MandateVersionApplied`) types `authenticated_at`
     as a §4.7 timestamp, and §9.2's `risk_clock` type says "never integer seconds".
   - §9.7 gives its evidence a type of its own, `{assertion_id: text, authenticated_at: integer,
     method: text}`, and refuses a timestamp there.
   - Unifying step-up time typing across the journal is a later version bump. It is recorded in
     the backlog (E5-10) and is not part of J2.
3. **`ApprovalResponded` keeps its whole §9 row** (the coordinator's ruling):
   - `quorum`, `{independent: boolean, required: integer}`, is always present. It is `null`
     exactly when check 7 was not judged (rule 48). Today the runtime omits it then, so the
     runtime's writer must write `null` instead.
   - The separation-of-duties result and the delegation shape stay in the record as
     `separation_of_duties` and `delegation`. Both are typed `null`, a member that is always `null`
     at this version, until E8's delegation story gives them a type at a later one. Dropping
     recorded members would weaken the audit record.
   - The runtime writes the three members in a small change of its own: tests first in
     `mandate-runtime`, after this spec, before K1a's Postgres test.
4. **`ApprovalRevalidated.decided_by_now` is `text?`, `null` when the re-classification is not an
   `ask`.** §9.1's `text` is non-empty, and an empty value is `null` (§4.2). The runtime writes `""`
   today (`unwrap_or_default`), so the same runtime change writes `null` instead. That is a
   conformance fix to an existing rule, not a new choice.
5. **The rules** add only what the spec and mandate spec §6.4 already say:
   - 46: the answer's `responder` is the writer's `actor.id`.
   - 47: a reason exactly when refused.
   - 48: a quorum exactly when check 7 was judged.
   - 49: a skip runs checks 1 to 5 only, so it is never `counted` and is refused only for their
     reasons.
   - 50: the copy names its answer.
   - 51: a reason exactly on `skip`.
   - 52: a dry-run reason exactly on `deny`.
   - 53: `band_bp` is 100 or 200, and an `act` passed every check it records, reported at the
     first member that shows a failure. Drift is compared on exact decimals; inside includes the
     band itself.

   `reason` on `ApprovalResponded` is the closed list of admission reasons (§6.4 checks 1 to 7). On
   `ApprovalRevalidated` it is `text?`, because check 11 records the gate's own reason code, an
   open vocabulary.
6. **The CLI's answer must list its `content_hash` in `artifact_refs`** (§3: the sorted digest
   references in the payload). Today `control.rs` drafts it with none, so even with this schema the
   journal would refuse it with reason `artifact_refs`. K1a's implementation fixes the CLI draft.
7. **Vectors:** `journal.yaml` gains a generated `approval_answers` section, from
   `reference/journal/approval.py`, with the schemas and rules in `control.py`'s single validator.
   - It has three base drafts, 114 invalid drafts (every member's type, null and form, the closed
     records, and each rule) and 11 valid drafts (the readings a rule might be misread to refuse).
   - Two oracles of its own check it: the copy equals its answer, and drift is recomputed on
     fractions.
   - 62 validator mutants and 5 vector mutants are all caught.
   - The section is new, so no consumer of an existing section changes. J2's tests PR adds the
     Rust harness for it.

## Order

1. This spec PR (no code).
2. J2's tests, then its implementation, in `mandate-journal`.
3. The runtime writer change (items 3 and 4), tests first.
4. K1a's Postgres grant test, as a tests correction.

## Alternatives considered

- **Timestamps, as the other closed step-ups** (option (A)). Rejected for now: it changes the CLI's
  and the runtime's writers and readers and their tests, on the critical path, for a consistency
  that a later version bump can give every record at once (E5-10).
- **Dropping the separation-of-duties and delegation members from the row.** Rejected: it would
  shrink what the audit record promises. They stay as always-`null` members until E8.
- **Letting `quorum` be absent when not judged.** Rejected: §9's closure convention is that every
  member is present, `null` only where nullable.
- **Typing `ApprovalRevalidated.reason` as a closed list.** Rejected: check 11's gate reason codes
  are the gate's vocabulary, not this record's.
- **Cataloguing `OwnerCommandIssued` here.** Left to M7's agent-commands slice: cataloguing it
  without closing its schema still refuses it `unknown_schema`, and neither K1a nor LT-4 needs it.
