G1a's row says the connector comes from the connection record, the environment from the confirmed
mandate, and a live run refuses unless the account is flat and the record is unspent (DEC-529
item 3). It does not say where each refusal lands, in what order, on what evidence spentness is
decided, or where LT-1's "build test" lives. These are the readings G1a's tests pin.

## Decision

1. **Where the build test lives (LT-1).** A build test proves the default build holds no live
   host on two sides, and both exist when G1a is done. The artifact side is X1's
   `cargo xtask live-feature` and E7-28's resolved-build check (DEC-868, DEC-873), already in
   `ci lint`: only a crate marked `live_feature` may declare `live`, no feature of another build
   turns it on, and no CI build but one compile-only `cargo check -p <runner> --features live`
   resolves it — G1a's implementation, which declares the feature and marks the runner, is judged
   by them, and no new xtask test is added. The runtime side is the runner's connection seam: in
   the default build the record that chooses the Robinhood connector refuses
   `connector_not_built`, so no run of this build can reach a Robinhood host at all. The pending
   test pinning it is ungated until the feature exists; the implementation that declares `live`
   gates it behind `not(feature = "live")` where it adds the live arm.
2. **The connection seam and its refusal order.** The runner reads the control stream for the
   confirmed mandate's connection. A paper mandate whose connection no record names keeps
   today's run exactly (V-001's paper default, LT-14); any mandate whose connection has a
   revoked record and no later establishment refuses, the paper default included. A live
   mandate requires an established record the build can serve, and disagreements fail closed in
   this order, each with its own reason code: no record (`connection_unrecorded`), revoked
   (`connection_revoked`), a member the runner reads missing or not text — a version 1 record or
   a corrupt payload (`connection_record_unreadable`), a record stating another environment
   than the mandate's, whatever text it holds (`connection_environment`), a broker that does
   not serve the mandate's environment or one the runner knows no connector for
   (`connection_broker`), an account stream other than the run's own (`connection_account`),
   and a choice this build does not hold (`connector_not_built`). The environment is the
   mandate's and no record can move it: a paper mandate named by a live record refuses rather
   than trading live under a deployment confirmed for paper. These checks refuse before anything
   runs, ahead of the shell's own `DeploymentRefusal::Live`, which stays for the shell's fold.
3. **The lapse and its evidence.** The lapse checks DEC-529 item 3's pair for a live run alone;
   a paper run makes no check (LT-14). Flat is DEC-470 item 1 read off the connector's snapshot:
   the account is flat only when it lists no position and no working order
   (`account_not_flat`, the flat half refusing first). Unspent is journal evidence: a
   `FillApplied` on the account stream the record binds spends the record, a `LateFillApplied`
   included, and every other event — a working order's `OrderSubmitted`, a cancellation, fees,
   snapshots — leaves it unspent (`connection_spent`). No time bound is needed: the CLI binds
   one account stream to one connection id (K1b's `account_ref_bound`), so no fill on that
   stream can predate the record, and a new connection record, which is how the lapse ends,
   binds a fresh stream. An `OrderSubmitted` without a fill does not spend, because DEC-529
   item 1 allows a further attempt after one that was refused or cancelled with zero filled
   quantity. The runner reads the account stream through the same journal it reads the control
   stream from, so a run that has no journal has no account stream either and no evidence to
   clear — the default-build refusal stands in front of it.

## Rationale

Each reading is the one that refuses more. Refusing a revoked paper record matches the shell's
own V-001 fold rather than leaving the runner to trade on a connection the workspace has
revoked. Reading spentness off the journal keeps the check offline, deterministic and testable
against recorded rows, where the broker's own list cannot be: the fill that spends the record is
by definition the run's own journaled order. Counting late fills as spends errs toward refusing,
and the one-flow case that would over-refuse — a broker event arriving late — is also a case
where shares changed hands under the record. Ordering the refusals makes every one testable on
its own, and the order itself is pinned.

## Alternatives considered

- **Judge spentness from the broker's order list** (C3's list request): rejected as the seam's
  evidence; it makes the refusal depend on a network read, and a crash before the fill was
  journaled leaves the flat check alone to refuse while the position lasts — the journal
  reading closes with the record's own stream and never asks the broker.
- **Bind spentness to a wall-clock window since the record**: rejected; the account stream is
  per-record by the CLI's own binding, so the window adds a clock read to a check that needs
  none, and a boundary would under-refuse at its edge.
- **Let a paper record name any broker**: rejected; the default build compiles the Alpaca
  connector alone (V-001), so a paper run has exactly one broker its build can serve, and a
  record naming another is a deployment written for a build this one is not.
- **Keep `DeploymentRefusal::Live` as the only door**: rejected; it answers "live" and names
  neither the record, the environment mismatch nor the missing connector, and R0 step 4 asks
  the run to report the exact refusal.
