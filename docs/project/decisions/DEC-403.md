# DEC-403: Journal spec v0.8 §9.3 closes the account stream's `MandateVersionApplied` and `UniverseChanged`

| | |
|---|---|
| **Status** | Accepted (agent, DEC-79 and DEC-176) |
| **Date** | 2026-10-02 (UTC) |
| **Decided by** | The agent (stream L), under DEC-79 and DEC-176. Every member is traced to a clause or a writer that exists, and every rule only refuses; nothing loosens a safety rule |
| **Story or claim** | The backlog's "account-stream risk-state records" row (stream K with stream L; DEC-303 item 6); stream L, claim [#171](https://github.com/kunwarshivam/mandate/issues/171); spec PR on `agent/l-risk-state-spec` |

## Decision

1. **Scope.** Journal spec v0.8 adds §9.3, which closes the two account-stream records `ValidationContext::from_journal` reads that §9.2 left open (DEC-303 item 6): `MandateVersionApplied` and `UniverseChanged`. §9.2's conventions carry over, and the rules continue at 29. Until these schemas are registered (a tests PR and an implementation PR, DEC-77), both stay refused at `append` as `unknown_schema`, as they are today, and their `JournaledFact` mapping maps both to none. So the fold fails closed until then.
2. **`MandateVersionApplied`'s members and where each comes from.**
    - `agent_id`, `old_version`, `new_version`, `classification`, the step-up evidence, the allocation change, and the result and reason are mandate spec §5.10's row ("agent, old and new version, classification, step-up evidence, allocation change, result and reason").
    - `reason`'s six values are the `Rejection` codes `mandate-spec`'s risk fold writes on a refused application (`risk/fold/owner.rs`: three for an allocation change, three for a floor loosening). The acknowledgment and flatten codes are left out, since no application writes them.
    - `max_loss_from_allocation` is the writer's `ApplyResult::Applied` member (DEC-128 item 29).
    - `classification` takes mandate spec §9.2's three verdicts. `invalid` is left out, because V-031 refuses such a version before it can apply.
    - `step_up` reuses `DisclosureAccepted`'s closed record.
    - `risk_clock` is §2's member for every account-stream risk input.
    - `old_version` and `new_version` are `ref`s, so each must be a stored artifact (§11 check 6), as `AgentDeployed`'s `mandate_version` is.
3. **`UniverseChanged`'s members and where each comes from.**
    - `instrument`, `change`, `reason`, `thesis_id`, `lineage_id`, and `universe_size_after` are what `mandate-research`'s `UniverseChangedEntry` writes, and mandate spec §5.10's row names them ("agent, instrument, change, reason, thesis and lineage ids, working-universe size after").
    - `instrument` is an `id`, since an asset ID is a lowercase UUID (mandate spec §3).
    - `thesis_id` and `lineage_id` are `id?`, as §9.1 types them on `ModelOutputRecorded`.
    - `agent_id` and `risk_clock` are as above.
4. **The rules, each a reading that only refuses (DEC-176).**
    - **Rule 29:** a risk-increasing version carries step-up. This is mandate spec §9.2's last paragraph.
    - **Rule 30:** a rejected version carries a reason and no allocation change or floor; an applied one carries no reason. This is the writer's `ApplyResult`.
    - **Rule 31:** each reason admits or removes as mandate spec §8.5 says. `version_applied` does either.
    - **Rule 32:**
      - `thesis_id` and `lineage_id` are null together, as rule 13.
      - They are non-null for the four thesis reasons and `operator_halt` (DEC-100 halts per thesis).
      - They are null for an admission with `version_applied`, because a pinned list admits with no thesis.
      - A removal with `version_applied` may carry them or not (#470 round 1, M1). DEC-121's pinning switch removes instruments the research agent had admitted through a thesis, and the executor names that thesis. A pinned list's own removal has none.
      - `eligibility_lost` may be either: a pinned instrument can lose eligibility, and the spec does not say it cannot.
    - **Rule 33** (#470 round 1, B1). `classification` is `risk_increasing` whenever the record itself shows a risk-increasing change. Each implication was checked against `mandate-spec`'s risk fold before the rule was written, and all three hold on every path:
      - **An `applied` record with `allocation_change` > 0.** `allocate` journals `Applied { allocation_change: Some(delta) }` for the delta it applied, and a larger allocation is §9.2's maximums row, increasing.
      - **An `applied` record with `max_loss_from_allocation` non-null.** `loosen_floor` journals it only past its `NotLoosening` check, so only when the floor rose (`owner.rs`, the applied arm).
      - **A `rejected` record with `increase_blocked_while_latched`.** It is reached only when `delta` is positive (`allocate`).
      - **A `rejected` record with `waiting_period` or `still_below_new_floor`.** Each is reached only after `NotLoosening` did not fire, so only on a raise (`loosen_floor`).
      - **Clauses not taken.** `equity_below_exposure`, `would_trigger_limit` and `not_loosening` can follow a decrease, or a version that raises nothing, so they imply no classification.
      - **Where it reports.** It reports after rules 29 and 30 at `payload.classification`. A raise relabelled `neutral` without step-up is therefore reported at the label, not the missing step-up. Rule 29 alone was blind to a mislabelled classification.
5. **Readings not taken, each with its reason.** Each would only refuse more, so each can be added later as a tightening.
    - **The `config_refs` binding.** No rule binds `config_refs.mandate_version` to `old_version` or `new_version`, because §9 does not say which version a record's `man` ref names. As a consequence (#470 round 1, minor 7), an `admitted` `UniverseChanged` with `version_applied` may name an instrument that is in no version's `pinned_instruments`. Nothing in §9.3 changes an envelope field, so `AGENTS.md` rule 11 holds. But the working universe is the gate's universe check, and for that one combination only the single-writer executor stands in the way. Rule 22 (`AgentDeployed`) is the precedent this declines.
    - **Distinct versions.** No rule requires `old_version` and `new_version` to differ.
    - **Bounds.** No rule bounds `max_loss_from_allocation` or the allocation change's sign.
    - **Re-deriving the classification from the stored documents** (#470 round 1, B1's stronger reading). Both versions are stored `ref`s, so §9.2's classification can be recomputed and compared. That needs the classifier in `mandate-journal`, which has no mandate types, so it is left open for the Rust registration, where `mandate-spec`'s mapping already opens `new_version`. The vectors' own oracle already does it, so every fixture states the classification its documents give.
    - **Independent approval** (minor 6). §5.7 lets a latched floor loosen before the waiting period only with independent approval, but the record carries only `step_up`. Mandate §5.10's row does not name it, so the account stream alone cannot show why `waiting_period` did not fire.
    - **`universe_size_after`** (minor 7) is checked against nothing, not even the fold of the stream's own records.
    - **One record per application** (minor 8). `ApplyResult::Applied` sets exactly one of `allocation_change` and `max_loss_from_allocation` per fold call, but rule 30 allows both. Nothing forbids two records for one version pair with different results, which a version that changes the allocation and loosens the floor produces (two inputs). Mandate §2.2 says "journaled as `MandateVersionApplied`" in the singular.
    - **The 64-byte id cap** (minor 5). The mapping reads `agent_id` through `ConnectionId::parse`, a 64-byte cap, as DEC-303 item 16 recorded for `AgentDeployed` and `AgentStopped`. It holds for these two records too. §9.1's `id` stays unbounded in the schema, and a longer id fails closed at the mapping.
    - **Eligibility re-admission** (#470 round 1, review notes). Mandate §5.9 says the `removed_instrument` restriction lifts when the instrument is admitted again, but rule 31 lets `eligibility_lost` only remove, so a pinned instrument that regains eligibility has no journalable re-admission reason. That gap is the mandate spec's. Rule 31 resolves it in the direction that adds no risk: the instrument stays exits-only (DEC-176).
6. **The mapping** (#470 round 1, M3). An applied `MandateVersionApplied` maps to `AgentVersionActive` from the stored document `new_version` names, exactly as `AgentDeployed` maps from its own. A `new_version` whose document is not stored is refused as malformed (`InvalidInput`), never skipped. A `rejected` record yields no fact and no error. `UniverseChanged` maps to `UniverseChanged`.
7. **The vectors.**
    - **A new `risk_state` section,** not more drafts in `control_stream`. The Rust consumers of `control_stream` (`control::tests`, `mandate-refcases`) read every draft there, and these types are not registered yet. So drafts in that section would fail `main`'s tests the moment this spec PR merged, and ES-22 keeps the crate change out of it. Nothing in Rust reads `risk_state` until the tests PR.
    - **The generator.** `reference/journal/risk_state.py` builds and checks the section. The schemas and rules live in `control.py` beside §9.2's, so one validator judges every closed schema.
    - **The documents** (#470 round 1, B1 and M2). Six documents are stored:
      - the control-stream vectors' mandate, as the version in force;
      - four versions after it, each a valid mandate: allocation raised and floor raised (risk-increasing), renamed (neutral), and floor lowered (risk-reducing);
      - the mandate reference cases' `research_equity`, which is unpinned, with a research agent and an admitting model.
    - **The new oracles.**
      - `documents.valid` checks every stored document with `reference/mandate`'s schema and semantic validators.
      - `drafts.classification` checks that every base and valid version record states the classification `ref.classify` gives its two documents.
      - `drafts.thesis_under_research` checks that every admission through a thesis names an unpinned mandate (MI-20).
      - Each has its own vector mutant.
    - **Every member type pinned** (minor 4). `agent_id`, `thesis_id`, `lineage_id`, and `max_loss_from_allocation`, which no draft pinned, each gain an invalid draft and a `loose.*` validator mutant that only that draft catches. The other typed members already had one.

## Rationale

The fold reads both records (DEC-169), and until they close it sees no version change after a deployment and no admitted instrument. Closing them from §5.10's rows and the writers that exist keeps the journal's schemas the single record of what each event carries.

## Alternatives considered

- **Add the drafts to `control_stream`.** Rejected: that would fail `main`'s live Rust tests on unregistered types (item 7).
- **A required `step_up`.** Rejected: mandate spec §9.2 requires step-up only for risk-increasing versions.
- **`instrument` as `text`, as §9.1's `instrument_id`.** Rejected: an asset ID's grammar fits `id`, which refuses more.
