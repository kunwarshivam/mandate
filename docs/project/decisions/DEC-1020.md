# DEC-1020: The agent read model gains its label, its mandate's envelope, and its account's positions

|---|---|
| **Status** | Accepted (agent: a reversible engineering reading under DEC-79 and DEC-176; it closes an unclosed contract by the reading that adds no risk) |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (lane A1, claim [#1444](https://github.com/kunwarshivam/mandate/issues/1444)), under DEC-79 and DEC-176, at the request of lane W2 through the coordinator |
| **Story or claim** | E21-31 and E10-10 (the web app's Home and Agents screens, lane W2); [workspace API spec](../../specs/workspace-api.md) §3.11 item 2, §4.7; DEC-979 |

## Context

DEC-979's agent read is a summary: id, environment, version, deployment time, mode, and pending
approvals. The web app's Agents screen also shows the agent's name, the envelope the owner confirmed
(capital, goal, asset classes, the key limits), its positions, and its limit usage. The journal
names the mandate version only by digest: the document's content is in the content-addressed
store (journal spec §9.2, "read from the stored document … never restated here"), so the name and
the envelope can be read only there. Positions are journaled on the account stream. Limit usage
(the drawdown rung, the day-trade count) is not journaled yet: `RiskLimitTriggered` and
`RiskLimitLifted` have no schema until E6-4, and the gate journals its checks' results only.

## Decision

1. **The store is read, never written.** The server reads the mandate document the deployed version
   names from the content-addressed store at `MANDATE_API_ARTIFACTS` (a directory, read-only, the
   layout of `mandate-artifacts-fs`), by its digest, and checks the bytes hash to it (journal spec
   §11 check 6; the stored-document read of §9.2). The setting is optional; without it, or when
   the document is absent, is stored encrypted (journal spec §6.3 and §6.4: the API holds no key),
   or does not parse as a mandate, the members below are `null` (not reported) and the read still
   answers. A document whose bytes do not hash to its digest is also `null`, and the server writes
   one line to its log naming the check that failed and no content, so tampering or corruption is
   not silent. The store holds no secret, so §3.11 item 2's guard is unchanged. A root that is
   not already a store (no `sha256` directory) refuses the start rather than being created.
2. **`label`** is the document's `name`; **`mandate`** is its envelope as the document states it:
   `allocation_usd` and `max_loss_from_allocation` (`capital`), the `goal`'s type and
   `end_date` (`goal_end_date`), `universe.asset_classes`, and `risk`'s `max_position_usd`,
   `max_order_usd`, `max_orders_per_day`, `max_daily_loss`, and `max_drawdown`. Values pass through
   unchanged; the server computes nothing from them. Both are in the list and the single read.
3. **`account_positions`**, on the single read only, are the account's holdings at its last
   reconciliation:
   for each instrument, the latest `BrokerPositionObserved` on the account stream (journal spec
   §9.6), its `model_qty` as `qty` (the executor's own accounting fold), its `broker_qty`, its
   `mismatch`, and the row's `recorded_at` as `observed_at`; instruments whose two quantities are
   both zero are left out. The account stream is `acct:{ws}:{account_ref}`, where `account_ref` is
   the one the control stream's latest `ConnectionEstablished` at schema version 2 (version 1 names
   none), else its `ConnectionRequested`, binds to the document's `connection_id`; that latest row
   decides, and one without an `account_ref`, or with one outside the id grammar
   (`[A-Za-z0-9_-]+`), binds none, so no stream name is formed from it. `null` when the
   document, the connection, or the account stream's rows are not found; `[]` when the account
   holds nothing. After a `ConnectionRevoked` the last reconciliation is still served, as it was
   journaled; its age is the account stream's watermark in `as_of`, which every read carries.
4. **Positions are the account's, not the agent's,** and the member's name says so. No journaled
   event attributes a fill to an agent short of joining `FillApplied` through the order's
   `OrderRequestRecorded.agent_id`, and the accounting of a shared account is the executor's;
   until a per-agent fold is journaled, the read says what the journal says.
5. **Limit usage is not served.** The drawdown rung, the day-trade count, and headroom are owed with
   the events that journal them (E6-4's `RiskLimitTriggered` and `RiskLimitLifted`, and the gate's
   check inputs); they join as new members then. Nothing is computed here in their place.
6. **No new state, no new authority.** Every member is a fold of journaled rows or a document the
   journal names by digest. The reads are authorized exactly as DEC-979's, tenant-scoped, and no
   notification payload changes (`AGENTS.md` rule 6).

## Rationale

The owner sees the envelope they confirmed, from the very document the journal binds, rather than a
copy that could drift. The positions are the executor's own figures at reconciliation, with the
broker's beside them, so a mismatch is visible rather than hidden. What the journal cannot state
yet is left out, not estimated.

## Alternatives considered

- **Fold `FillApplied` per agent in the API.** It would repeat the accounting fold (fees in the
  asset, corporate actions) outside `mandate-accounting` and the executor; the reconciliation record
  is that fold's own output.
- **Restate the envelope on `AgentDeployed`.** The journal spec keeps the document out of the
  control stream by design (journal spec §9.2); a journal change for a display need is not worth
  it.
- **Serve limit usage from the gate's check results.** They carry pass or fail only, so any number
  would be invented.
