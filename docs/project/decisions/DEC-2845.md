## Context

Trading spec §2.3 gives the executor's own exits their own intent ids:

- a kill switch's flatten is `k-{switch}-{n}`;
- the triggered-stop watchdog's exit is `w-{event}`.

No agent proposed them, so neither is a ULID. Journal spec §9.5 typed `intent_id` as a `ulid` on
every account-stream record such an exit writes: `IntentReceived`, `GateDecided`,
`OrderRequestRecorded` and `ProtectionChanged`. Only `OrderAbandoned` read them, as an `id`, from
v0.93.

A real journal therefore refused every batch that received, gated or protected one of these exits,
and that batch carries the `KillSwitchActivated` and the mode change too. In the 2026-10-27
rehearsal the owner's agent kill switch journaled nothing on the account stream and never sold.
The executor's tests missed it because their journal applies none of the journal's rules.

## Decision

1. **A new type.** Journal spec §9.1 adds the type `intent`. It admits a ULID, or exactly one of
   two forms:
   - `w-` followed by a ULID;
   - `k-`, a ULID, `-` and `n`, where `n` is a decimal from 0 to 999 with no leading zero.

   Every other form is refused as an `id` is: a prefix in another case, a ULID with a suffix, a
   watchdog's id with an ordinal, a flatten without one, an ordinal out of range or not ASCII, and
   the order's `md-` id. `n` is an instrument's ordinal among a kill switch's closes and deferrals.
   The executor applies every switch, whatever its scope, as one switch per agent (trading spec
   §5.5, DEC-2003 item 4), and an agent holds at most 20 instruments (`max_instruments`), so 999
   bounds it with room to spare. A switch that one day enumerates more than one agent's
   instruments must revisit the bound.
2. **Where it applies.** `intent_id` takes the type on seven record versions:
   - `IntentReceived` at versions 1 and 2;
   - `GateDecided` at versions 1 and 2;
   - `OrderRequestRecorded` at version 1;
   - `ProtectionChanged` at versions 1 and 2.

   It stays nullable where it was. `OrderAbandoned` keeps its `id`, and `OwnerConfirmationReceived`
   keeps its `ulid`, since only an agent's owner exit is confirmed.
3. **§2's sentence.** "`intent_id` equals the `event_id` of the agent stream's `IntentProposed`" now
   excepts the executor's own exits.
4. **Nothing else changes.** No rule changes, and no stored vector's outcome, body or hash. The
   regenerated `journal.yaml` and `fixtures/refcases/journal.json` only gain the new `exit_intents`
   section, and the vectors stay version 3.
5. **The vectors.** The new `exit_intents` section holds:
   - a base draft of each of the seven record versions, built from the `account_stream` chain;
   - 28 valid drafts: each version with `w-…`, and with `k-…` at ordinals 0, 2 and 999;
   - 175 invalid drafts: each version with 24 near misses and with a number.

   The section's oracle reads the form with its own regular expression over the cases and a
   generated set of candidates. Five validator mutants and three vector mutants are seeded:
   - reading `intent` as a bare ULID;
   - reading it as any id;
   - dropping the ordinal's bound of 999;
   - admitting a leading zero;
   - admitting a digit that is not ASCII.

   Every one is shown caught by the cases, and every validator mutant also by the oracle.
6. **Order of work.** The journal's code follows in its own change (ES-22). The kill switch's tests
   then run the executor against a journal that applies every rule, and only after that the owner
   exit's fix ([DEC-2846](DEC-2846.md)).

## Rationale

The trading spec's ids exist so that an executor's own exit can never be mistaken for an agent's
intent or a protective order (§2.3). The journal spec had already accepted them on
`OrderAbandoned`, so refusing them elsewhere was a contradiction rather than a rule. Rule 13 says
the kill switch is always available, and a journal that cannot record its flatten makes it
unavailable. Admitting exactly the mandated forms, and nothing broader, keeps every check the ULID
type gave against a malformed or forged id.

## Alternatives considered

- **Give the executor's own exits ULID-shaped ids (trading spec §2.3).** Rejected. An id that looks
  like an agent's intent loses §2.3's guarantee that the two never collide. It would also change
  the client order ids that recovery derives from the journal.
- **Type `intent_id` as any `id`, as `OrderAbandoned` does.** Rejected. It would admit any token
  where the journal now proves an event id, which is broader than the specs need.
