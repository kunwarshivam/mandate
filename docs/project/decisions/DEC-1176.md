# DEC-1176: A dev or ci cell serves the fixture OAuth provider from its own pod, gated by tier

| | |
|---|---|
| **Status** | Accepted (agent: a reversible engineering decision under DEC-79 and DEC-176, approved by the coordinator and agreed by lane GO on 2026-10-19; it renders only in dev and ci cells and adds no reach to staging or production) |
| **Date** | 2026-10-19 (UTC) |
| **Decided by** | `claude-code` (lane D1, the staging push), with lanes GO and X, under DEC-79 and DEC-176 |
| **Story or claim** | DEC-2625 (the fixture OAuth provider), DEC-2100 (the stub issuer on loopback), DEC-2633 (the exchange's cell token URL), DEC-2627, DEC-1175; claim #1901 |

## Context

The OAuth connect's cell drill needs the token-exchange pod, and the owner's browser, to reach the
fixture OAuth provider (DEC-2625, `POST /alpaca/oauth/token`). The provider is served by the stub
issuer, a sidecar of the API pod bound to loopback only (DEC-2100), so no other pod can reach it.
This is for dev and ci cells alone; staging reaches Alpaca's own token host (DEC-2059).

## Decision

1. **Its own pod.** A dev or ci cell renders a one-replica `oauth-fixture` Deployment from the stub
   issuer's image, run as `mandate-stub-issuer --alpaca-only --bind 0.0.0.0:8091 --public-host
   oauth-fixture:8091` with the provider's three flags (item 8): it serves only `/alpaca/oauth/*`
   and answers 404 to everything else, so no sign-in issuer runs in it. A ClusterIP Service `oauth-fixture` fronts it on 8091. The API pod's sidecar stays on
   loopback, unchanged.
2. **Gated on the tier alone.** Any staging or production render that names the fixture or sets
   any of its values fails, whether or not `images.stub-issuer` is named, and the values schema
   refuses it there. A test renders `deploy/gitops/clusters/{staging,production}` and finds no
   `oauth-fixture` Deployment, Service, or NetworkPolicy.
3. **It reaches nothing.** Its NetworkPolicy has `policyTypes` Ingress and Egress and no egress
   rule, not even DNS: the fixture never calls out.
4. **Only the exchange and the browser reach it.** Its ingress admits pods labelled
   `mandate.dev/process: token-exchange` in this workspace on 8091 and nothing else: no
   namespace-wide ingress. The local cell runs no ingress controller (Traefik is disabled), so the
   browser reaches the fixture as it reaches the API, through `kubectl port-forward` to the
   `oauth-fixture` Service on 8091 with `oauth-fixture` resolved to loopback, and so sends the one
   `Host` the fixture answers (item 8); a port-forward is not pod-network ingress, and the policy
   admits no other pod. In dev and ci only, the exchange's `token-host` egress renders as a
   pod selector on `oauth-fixture` port 8091, with no CIDR beside it; in staging and production it
   stays the `token-host` CIDR path of the values, and the fixture's selector never appears there.
5. **The exchange's target.** The token-exchange client's host is Alpaca's
   (`https://api.alpaca.markets`, DEC-821 item 4, DEC-2059). A base-URL override pointing it at
   `http://oauth-fixture:8091/alpaca/oauth/token` is a dev and ci value only, the exchange pod's
   `MANDATE_TOKEN_URL`: the schema refuses it, and the chart fails, under staging or production.
   The binary reads it only in a build with debug assertions, and there only when
   `MANDATE_DEPLOYMENT_TIER` is dev or ci and the origin is loopback or exactly
   `http://oauth-fixture:8091`, scheme, host and port pinned (DEC-2633, which widens DEC-2629 by that
   one origin; `MANDATE_ALPACA_AUTHORIZE_URL` takes the same gate); a release image that is handed it
   refuses to start. A stray value can then never repoint a staging or production exchange.
6. **The fixture's client.** The Secret `oauth-fixture-client` holds the fixture client's fake
   secret under the key `client-secret`. The chart makes no Secret (DEC-822 item 4 holds as it
   is): `cargo xtask cell up` makes it once in the local cell, before the workspace release, from
   32 random bytes written as hex and sent to kubectl on stdin, and keeps one already there, so the
   pod and the vault agree across every `cell up`. The chart only mounts it, read-only, mode 0440
   for the pod's fsGroup as every Secret here is, and an init container copies it to a
   memory-backed directory as 0600, which is the fixture's `--alpaca-client-secret-file`, since the
   stub refuses a file any group can read (DEC-2625 item 2), as the journal role's `pgpass` is
   copied. After the release is installed, `cell up` seeds the same value into the vault at the
   platform client secret's path (`SecretPath::ClientSecret`, `platform/alpaca-oauth-client-secret`),
   so the exchange presents what the fixture expects; it does nothing while the Secret is absent
   (lane V2, #2197). The client id is `alpacaOAuth.clientId`, the one value the API and the exchange
   send. Nothing is generated at the fixture's start, which would need the fixture and the vault
   kept in step.
7. **What is tested.** Each of items 2 to 6 is pinned by a chart test (`deploy/tests/test_oauth_fixture.py`,
   and `test_gitops.py` for the staging and production clusters), with a seeded bug for each: the
   tier gate with and without the image and with the schema skipped, an egress rule on the
   fixture, a CIDR beside the fixture's selector, the token URL repointed or present with the
   fixture off, an ingress rule wider than the exchange's pods, a client Secret the chart makes, and
   the client Secret mounted or copied with wider bits; xtask's tests pin that `cell up` makes the
   Secret before the release and seeds the vault after it.
8. **The stub issuer's fixture mode** (`mandate-stub-issuer`, lane D1 with lane X's agreement).
   `--alpaca-only` runs the fixture provider without the issuer: no signing key is made, and
   `GET /jwks.json` and `POST /token` answer 404 like any other path outside `/alpaca/oauth/*`. It
   needs the provider's three flags (else `stub_issuer_alpaca`) and `--public-host`, the one
   `Host` it answers, 421 to any other or to two, as the issuer answers for its bind (else
   `stub_issuer_public_host`). `--public-host` is a lowercase host name, a dot-separated list of
   labels of letters, digits and inner hyphens, a colon, and a port from 1 to 65535, written
   without a leading zero; nothing else, no scheme, path or user. Only in this mode may `--bind`
   name an address that is not loopback, and only with a port from 1 to 65535 that prints back as
   written, so the pod can listen on its own address. `--public-host` without `--alpaca-only` is
   refused (`stub_issuer_public_host`), so the issuer's own sidecar stays on loopback (DEC-2100
   item 5). The tier and build checks run first, as for the issuer (DEC-2100 items 2 and 3): a
   release build and a tier other than dev or ci still refuse before anything is read.

## Rationale

The fixture runs the provider without the issuer, on a pod that reaches nothing and that only the
exchange and the browser reach, and it exists only where no real money or account does. Keying the
gate on the tier, not on whether an image is named, means no combination of staging values can
render it.

## Alternatives considered

- **Relax the sidecar's bind behind the tier gate.** Rejected: it would expose the API pod's whole
  stub surface, sign-in included, to the namespace.
- **Run the drill against Alpaca's paper OAuth.** Rejected for the cell: it needs a registered
  client and the network, and the cell runs with neither (ADR-0001 ES-19).
