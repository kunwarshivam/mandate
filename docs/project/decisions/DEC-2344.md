## Context

The deployment manager stops an agent's runtime on its `AgentStopped`, and the account's executor
once every agent of the account is retired (journal spec §9.21). The executor learns of a kill
switch only from the runtime's copy on an agent's stream, so after that point a kill switch reaches
nothing on the account. Today that strands nothing: the only writer of `AgentStopped` is the CLI's
retirement of an agent no process ran (DEC-2039), which holds nothing, and the runtime's owner Stop
only sets mode `stopped` and leaves the agent deployed. But the specs let a retirement leave
something behind:

- mandate spec §3.1's `profit_stop` retires "after" a discretionary exit of every position, which
  does not say the exits filled, so an equity exit waiting for the regular session could still be
  working;
- `release` hands the positions to the owner as external holdings, which an account- or
  workspace-scoped kill switch (trading spec §5.5, broker cancel-all and close-position) is still
  meant to reach.

Keeping the executor while the account's fold shows positions or working orders was considered and
rejected: the manager reads only the control stream, and released owner holdings are positions by
design, so it would keep an executor up for ever.

## Decision

1. **A covering kill switch starts an executor no agent wants** (the deployment manager). An
   executor slot that is not desired, has no live instance, and has a covering kill switch it has
   not answered gets exactly one start for it, cause `kill_switch`, journaled first, as journal
   spec §9.21 already gives a crash-looped slot. Its `causation_id` names the first covering
   switch it answers; each later covering switch that finds it down gets one more start. A slot
   with no covering kill switch is never started by this item. The start applies something only
   once the executor reads a kill switch from the control stream itself (DEC-2343).
   - **What answers a switch** (journal spec §9.21, v0.76). Only a start committed after it: the
     manager reads only the control stream, so it answers by starts alone and never reads the
     executor's `KillSwitchActivated`. A generation that ends with success answers only the
     switches committed before its own start: the manager cannot see which later ones the executor
     read, so it reads each covering switch committed since as not answered and starts the executor
     again for it. An extra start finds nothing to apply and ends again.
   - **How it ends (the coordinator's choice (A), 2026-10-22).** The manager never stops such a
     generation itself. The executor ends it: it exits 0 exactly when no agent of its account is
     desired and every covering switch it read at or before its last read is applied, journaled as
     `KillSwitchActivated` on the account stream with its requests sent. It never exits 0 with a
     switch in flight or an `Unknown` order in the covered scope; DEC-2343's executor tests pin
     that predicate. The manager reads the exit as `Succeeded` and starts it again only for a
   covering switch the exit did not answer.
   - **A crash before that** (exit non-zero) is restarted with the usual back-off, cause
     `restart`, so one crash loses no switch. If the crash-loop bound is reached first, the switch
     is unapplied: the manager journals `ProcessCrashLooped` and raises the opaque operator alert
     **`kill_switch_unapplied`** in place of `crash_loop` (a fixed key and no subject, `AGENTS.md`
     rule 6). The owner's alert is the notification service's, from that `ProcessCrashLooped` of
     an executor whose last start's cause is `kill_switch`, with generic text and opaque ids only.
     A later covering switch still gets its one start (§9.21).
2. **Retirement leaves nothing of the agent's** (mandate spec §3.1, journal spec §9.2). A runtime
   writes `AgentStopped` for an agent that ran only once the account stream's fold shows no
   position attributed to the agent and no working order of its own. **Working** is every
   non-terminal state of trading spec §5.7: `Intent`, `Submitting`, `Accepted`, `PartiallyFilled`,
   `PendingCancel`, `PendingReplace`, `Unknown`; the terminal ones are `Filled`, `Canceled`,
   `Rejected`, `Expired`, `Replaced`, and `Abandoned`.
   - After its exits fill for `profit_stop` and a passed `end_date`.
   - For `release` and the owner's "stop and release" (DEC-136): the agent cancels every working
     order of its own, protective orders, exits, and any other, and retires once `PositionReleased`
     is journaled and every cancel is confirmed. A cancel not yet confirmed keeps it un-retired;
     trading spec §5.7's pending-cancel rule and DEC-2302's resend and alert end it.
   - For the owner's Stop, under DEC-136's flat-or-release precondition.
   - A retirement that has waited 24 hours raises the opaque alert `retirement_held` to the owner
     and the operator, and again each 24 hours while it waits.
   It is the writer's rule: no journal member, rule, or vector changes, since a control-stream check
   does not read the account stream. The runtime's property test is an E6-5 backlog row.
3. **An executor stays desired until a switch it was read with is answered** (the deployment
   manager). A covering kill switch the manager reads while the executor runs is answered only by a
   later start, so the account's last `AgentStopped`
   does not stop that generation: the manager journals no `ProcessStopIssued` for it, and it ends
   by its own exit, as item 1's does. A switch issued just before a retirement is not cut off.
4. **Journal spec §9.21 says so** (v0.76, in this PR). A `kill_switch` start's `causation_id` is
   the first covering switch it answers; a start for an executor no agent wants and no live
   instance; what answers a switch; the held stop, with `ProcessStopIssued`'s causes unchanged; and
   `kill_switch_unapplied` in place of `crash_loop`. No member, rule, or vector changes.

## Rationale

Every route to `AgentStopped` then ends an agent that holds nothing, so stopping its runtime and
its account's executor on that record alone strands no order or position of the agent's. What the
owner holds after a release is still reached by an account-scoped kill switch, because item 1
starts the executor for it, and item 3 closes the window between a switch and a retirement. Each
item only delays an end or adds a start in answer to a kill switch, which reduces risk.

## Alternatives considered

- **The manager folds each account stream and keeps the executor while it shows positions or
  working orders.** Rejected: it gives the manager reads and a fold it does not own, and released
  owner holdings would keep the executor up for ever.
- **Leave it to the writer alone (item 2).** Rejected: it does not cover released owner holdings,
  which only an account-scoped kill switch reaches.

## Risks

- Items 1 and 3 apply nothing until the executor reads a control-stream kill switch (DEC-2343),
  and an account- or workspace-scoped switch needs the executor's cancel-all and close-position
  path (lane LV's A2b, DEC-2333).
- Item 2 binds a writer that does not exist yet; until it does, the CLI's retirement of an agent no
  process ran is the only `AgentStopped` writer, and it holds nothing.
- **A retirement that cannot end.** An exit that can never fill, or an order stuck `Unknown`, keeps
  the agent un-retired, its runtime and its account's executor running. The owner's ways out are a
  release (the positions become the owner's, with protection cancelled), the kill switch, or the
  operator's reconciliation of the `Unknown` order (trading spec §11). `retirement_held` (item 2)
  keeps it from being silent.
- **An agent that ran, crash-looped, and holds nothing.** Its runtime is left down by its crash loop
  (§9.21), so it cannot write its own `AgentStopped`, and the CLI's retirement covers only an agent
  no process ran. The agent stays deployed, so its account's executor stays wanted: safe, but the
  owner cannot retire it until a kill switch's start or an operator brings its runtime back.
  Recorded for E6-5.
- **Where the alerts land.** `kill_switch_unapplied` and `retirement_held` join the notification
  spec's owner alerts and infrastructure design §8.2's operator alerts with the implementation of
  items 1 and 2, not here.
