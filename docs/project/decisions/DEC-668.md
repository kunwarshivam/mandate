# DEC-668: What the two E9-8 seal crates hold, their layers, and the SystemContext registration

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The lane L1 builder agent, under DEC-79 and DEC-176: reversible engineering choices that DEC-642 leaves open, each taken by the reading that adds no risk and opens no seal. Item 1 supersedes the wording of DEC-642 item 7 in part, where that wording cannot be built as written |
| **Story or claim** | E9-8 (claim #761); [identity spec](../../specs/identity.md) §4.5, ID-1, ID-5, ID-8; DEC-642 items 5 to 7; DEC-645 item 3; DEC-655 item 4 |

## Decision

1. **`mandate-tenant` holds the `Tenant` trait, its sealing supertrait `Sealed`, and the ID values
   the trait's methods return:** `PrincipalId`, `OrgId`, `WorkspaceId`, `PrincipalKind`, and, so
   that the ULID text codec stays private to one crate, `SessionRef`, `UlidTextError` and the
   codec. `mandate-identity` re-exports every one of them at the path it had before, so no caller
   changes, and does not re-export `Sealed`. DEC-642 item 7 says the crate holds "only the
   `Tenant` trait and its sealing supertrait"; this reads it as "nothing that builds a context, a
   session or a membership". The values build nothing and every crate already names them through
   `mandate-identity`; the allowlist still keeps `Sealed`, and so `Tenant`'s implementations, to
   `mandate-identity` and `mandate-identity-system`.
2. **Layers.** `mandate-tenant` is at layer 0, below `mandate-identity` (1), which depends on it to
   re-export `Tenant`. `mandate-identity-system` is at layer 2, above `mandate-identity`, whose
   `Permission`, `Refusal`, and `demand::Permitted` it uses. Both are safety-critical and pure.
   `mandate-tenant`'s `allowed_dependents` are `mandate-identity` and `mandate-identity-system`
   (DEC-642 item 7). `mandate-identity-system`'s list starts empty: E9-8 adds each bootstrap crate
   of the agent runtime, the executor and the scheduler when it creates it, and no other crate
   ever joins it (DEC-642 item 6).
3. **The `SystemContext` registration.** Its only constructor is `SystemContext::new(org,
   workspace, registration)`: one workspace and its organization, which `Tenant::org` must report,
   both read by the bootstrap from the workspace's own record, and a `Registration` naming the
   process's workload identity (a `PrincipalId`, identity spec §3.1), its actor (`SystemActor::Agent`
   for an agent's runtime, `SystemActor::System` for the executor and the scheduler, so no other
   actor kind is representable), and the set of `Permission`s it lists. `Tenant::kind` reports
   `PrincipalKind::Agent` or `PrincipalKind::Process`, which the journal records as `actor.kind`
   `agent` or `system`.
4. **The witness from a `SystemContext`** (DEC-655 item 4). `mandate-identity`'s `demand` module
   gains a sealed `Grants` trait, a `Tenant` that answers whether it holds a permission, and one
   generic `demand::require`, which yields a `Permitted` exactly when the context grants `P`'s
   permission and is otherwise `Forbidden`. `TenantContext::require` and `SystemContext::require`
   both go through it, so `Permitted` still has no other constructor; it borrows the context as a
   `&dyn Tenant`. `Grants` has `Tenant` as its supertrait, so only `mandate-tenant`'s allowed
   dependents can implement it. A `SystemContext` grants exactly the permissions its registration
   lists. The bootstrap crates list none of the sensitive ones (every `RequiredPermission` marker)
   until a story needs one, and each such listing is that story's decision.

## Rationale

`Tenant`'s methods return `WorkspaceId`, `OrgId`, `PrincipalId`, and `PrincipalKind`, and
`mandate-identity` must depend on `mandate-tenant` to re-export the trait, so the values have to sit
in `mandate-tenant` or below it. Below layer 0 there is nothing, and a separate ID crate at layer 0
would push `mandate-tenant` to layer 1 and `mandate-identity` and every crate above it up a layer.
Item 3 makes the actor kind a two-variant type, so a `SystemContext` can never claim to be a user.
Item 4 keeps `Permitted`'s constructor in one place, so the seal of DEC-655 still holds.

## Alternatives considered

- **A separate ID crate under `mandate-tenant`.** It keeps DEC-642's wording but moves
  `mandate-identity` and every crate above it up a layer; rejected.
- **`Tenant` with associated types for its IDs.** Every `&impl Tenant` API would change shape;
  rejected.
- **A second witness type for a `SystemContext`.** A sensitive API that takes
  `&Permitted<'_, ReadRecords>` could then not be handed one, and a second type would need its own
  seal; rejected.
- **A `SystemContext` built from a workspace alone.** `Tenant::org` would need a store read inside
  the identity core, which reads nothing; rejected.
