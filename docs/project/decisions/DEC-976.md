## Decision

1. **No new crate.** DEC-692's part 2 named `chacha20poly1305`, `getrandom` and `libc`. The
   cipher is `ring`'s `CHACHA20_POLY1305` and the nonce comes from `ring`'s `SystemRandom`;
   `ring` is already a workspace dependency with a row (`docs/dependencies.md`), so the vault
   adds no crate to the lockfile. `libc` is not needed (item 3).
2. **The entry format.** One file per entry: the tag `MVL\x01`, a random 12-byte nonce, and the
   ciphertext with its 16-byte tag. A secret is 1 to 8192 bytes. The associated data is the
   version tag `mandate-vault-local/v1\0`, then the kind (`code`, `token`, `client_secret`), the
   `key_ref`, and the binding (`connection` with its `connection_id` and environment, or
   `platform` for the client secret), each a two-byte big-endian length and its bytes. The file
   name is the `key_ref` in lowercase hex, a dot, and the kind. A `key_ref` is 1 to 100 of
   `A-Z a-z 0-9 . _ - /`. Writes go to an `O_EXCL` temporary file in the same directory, set to
   their exact mode on the open file (so the umask cannot change it), synced, renamed over the
   entry, and the directory synced.
3. **The per-file check, tightened.** DEC-692 item 5 named `O_NOFOLLOW` and `fstat` for tokens
   and the client secret. The vault checks every read, codes included, before decrypting:
   - the name's `lstat` must be a regular file (a symlink, directory, FIFO, or device is refused
     and never opened);
   - the open file's `fstat` must be the same inode (device and inode number), so a name swapped
     between the check and the open is refused. This gives what `O_NOFOLLOW` gives with `std`
     alone, and the open flag's value differs by platform;
   - one link exactly, so a hard link planted beside an entry fails both names;
   - a code is owned by the API user, in the executor's group, `st_mode` exactly `0100640`; a
     token or the client secret is owned by the executor user, `st_mode` exactly `0100600`;
   - a size the format allows, checked before reading.

   Residual, disclosed: the API user, through its group write on `tokens/`, could swap a FIFO in
   between the `lstat` and the open and stall that one read. It learns nothing and stores
   nothing; the executor's read fails closed when the process is restarted.
4. **Roles, tightened.** The API may write only codes and may unlink a code or a token, but not
   the client secret. The executor may not write a code, since only the API's files pass a code
   read. The connect core's `Vault` port answers a call the role does not have with
   `VaultUnavailable` and touches no file.
5. **The import.** `mandate vault import alpaca-oauth-client-secret` reads stdin only: one
   trailing `\n` or `\r\n` is dropped and the rest must be 1 to 8192 bytes of printable ASCII
   with no space. It reads the service users' ids from `/etc/passwd` and `/etc/group`, opens the
   vault as the executor, stores the secret, and reads it back through the executor's checks; an
   import run as anyone but `owlhead_exec` fails that read, deletes its entry, and is refused.
   It prints no part of the secret, whatever refuses it.
6. **Journaling deferred** (DEC-692 item 7). `VaultOperationRecorded` is not in the journal
   spec, and a journal event lands as a spec change first (ES-22). Until it does, the vault
   journals nothing; the event is follow-up work for E7-17's vault events, before the vault
   holds anything but the demo host's paper credentials.

## Rationale

Reusing `ring` keeps the supply chain as it is, and its AEAD is the one the TLS stack already
trusts. Checking codes as well as tokens costs nothing and closes the same planted-file attack
on `pending/`. The same-inode comparison is the portable form of `O_NOFOLLOW`. Reading the
import back is the one check that proves the file is the executor's, without a new crate to ask
the kernel who the process is.

## Alternatives considered

- **`chacha20poly1305` and `getrandom` as DEC-692 said.** Rejected: new crates for what `ring`
  already provides.
- **`O_NOFOLLOW` through `libc` or `rustix`'s `fs` feature.** Rejected: `libc` needs `unsafe`,
  which the workspace forbids, and the `fs` feature widens an approved row for no extra
  protection over the inode comparison.
- **Building `VaultOperationRecorded` in this slice.** Rejected for now: it is a journal spec
  change with its own vectors, and ES-22 puts it in its own PR before the code.
