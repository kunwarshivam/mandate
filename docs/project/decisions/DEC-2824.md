# DEC-2824: An account restriction lifts cause by cause

| | |
|---|---|
| **Status** | Accepted (an agent, under DEC-176: it builds trading spec §7.3's own "Lifts when" for each cause, and every condition it adds to that column only tightens it) |
| **Date** | 2026-10-26 (UTC) |
| **Decided by** | an agent, under DEC-79 (`claude-code`, lane L1) |
| **Story or claim** | Backlog E7-2y (`docs/project/backlog/E7-2-restriction-lift.md`); [journal spec](../../specs/journal.md) §9.5, §9.28; [trading spec](../../specs/trading-domain.md) §7.3; [DEC-2816](DEC-2816.md) item 5; [DEC-441](DEC-441.md) item 23 |

## Context

Trading spec §7.3 says when each cause of an account restriction lifts. A broker cause
(`broker_reject`, `broker_notice`) lifts when the owner acknowledges and the account is refreshed.
`connection_unavailable` lifts when the connection's own condition clears and **then** the owner
acknowledges. Causes lift independently. DEC-2816 put every cause in force on the account stream,
once per restriction, so a lift can name it. But nothing lifts one yet:

- the executor's account state never returns to `active`;
- §9.28's `OwnerAcknowledged` can name only a `RiskLimitTriggered`.

A restricted account therefore stays restricted until its stream is replaced.

## Invariants

Each one has a reference vector or a fuzz property in the spec slice, and a test in the crates that
implement it.

1. **No lift without its cause in force.** A lift names a cause that an `AccountRestrictionChanged`
   raised and that no lift has lifted since.
2. **A broker cause lifts only on its two pieces of evidence, in order.** First an acknowledgment
   of that cause that the executor accepted. Then an account report taken after that acknowledgment
   that shows none of §7.3 row 1's conditions, and that no later report contradicts before the lift.
3. **A connection cause lifts only after its own condition clears, then the acknowledgment.** A
   `condition_cleared` comes after the cause was raised and before the acknowledgment, and no
   degradation of the connection comes after that `condition_cleared` and before the lift. The
   connection's `acknowledged` change, caused by the acknowledgment, comes before the lift, so the
   account never trades again while the connection is still degraded or suspended.
4. **One acknowledgment, one lift.** An acknowledgment lifts at most one cause, at most once.
   - An acknowledgment that names a record superseded by a later restriction of the same cause
     lifts nothing, whether that restriction came before the acknowledgment or after it.
   - A refused acknowledgment lifts nothing.
5. **The account state is the strictest of the causes left in force.** This holds before and after
   every lift, for every reader of the stream (DEC-2816 item 2). A lift that leaves a stricter or an
   equal cause in force leaves the account state unchanged.
6. **No agent is ever looser than the account state, at any record, and no account entry outlives
   its causes.** A lift that loosens the state first applies the state left's agent effect, then
   removes every other account entry. A lift that leaves the state unchanged moves no agent.
7. **A lift only adds risk, so no rule here holds an exit, a protective order, or a kill switch**
   (`AGENTS.md` rules 3 and 13). A refusal or a missing record leaves the account restricted, which
   is the safe default.
8. **Replay decides the same way.** Every check reads the account stream, except §6.1's
   step-up reuse check, which reads the control stream up to the original's position, as §9.28
   already does.

## Decision

1. **An acknowledgment can name a restriction.** `OwnerAcknowledged` and
   `OwnerAcknowledgmentRequested` gain `schema_version` 2, which adds one member, `subject`:
   `limit` or `restriction`.
   - With `limit`, every member means what version 1 says.
   - With `restriction`, `event` names an `AccountRestrictionChanged` on the account stream of
     `agent`'s account. `agent` is any agent of that account, which routes the copy exactly as
     version 1 does.
   - Version 1 stays registered and reads as `subject: limit`.
   - Rules 239 to 241 apply unchanged. A restriction's acknowledgment carries step-up. Its
     independence requirement is the strictest of the one it carries and the overlay's
     `independent_approval_required` at processing of **every** agent deployed on the account,
     stopped or not. A limit
     belongs to one agent, but a restriction belongs to the account, so the owner cannot pick the
     agent whose overlay asks least.
2. **The executor judges a restriction acknowledgment's copy as §9.28 judges a limit's**, in the
   same order and with the same refusal (`OwnerCommandRefused`, `command` `acknowledge`):
   1. **The trigger exists.** `event` names an `AccountRestrictionChanged` on this account stream
      before the copy. Otherwise `trigger_unknown`.
   2. **The trigger stands.** No later `AccountRestrictionChanged` of the same `cause`, and no
      `AccountRestrictionLifted` of it, comes between that record and the copy. Otherwise
      `trigger_superseded`.
   3. **Its step-up holds.** The `step_up_*` reasons apply, as for a limit's acknowledgment.
   4. **Independence**, under item 1's requirement: `not_independent` or `request_invalid`.

   A refusal is the record right after the copy, in the copy's batch, with nothing between them, so
   the risk book's row-by-row fold decides a copy with one row of lookahead (agreed with lane RK).

   An acknowledgment that passes all four is **accepted**. It lifts nothing by itself.
3. **A new account-stream record, `AccountRestrictionLifted`, schema version 1.** It names:
   - `cause`;
   - `acknowledgment`: the accepted acknowledgment copy's `event_id`, which is also its
     `causation_id`;
   - `evidence`: the record that completes the lift;
   - `restriction`: the account state the causes left in force set, `active`, `closing_only`, or
     `blocked`;
   - `risk_clock`.

   It lifts its cause at every restriction the cause was raised at.
   - **Broker causes.** The evidence is an `AccountStateObserved` after the accepted
     acknowledgment copy whose `status` is `ACTIVE` and whose `trading_blocked`, `account_blocked`
     and `trade_suspended_by_user` are all `false`, and which is the latest report before the lift.
     The executor reads the account again when it accepts the acknowledgment, and lifts in the batch
     of the first clean report. A report that still shows a row-1 condition lifts nothing; the
     acknowledgment stays accepted, and the next clean report lifts the cause.
   - **`connection_unavailable`.** The evidence is a `ConnectionStateChanged` with reason
     `condition_cleared`. It comes after the record that raised the cause and before the
     acknowledgment copy, and no `ConnectionStateChanged` into `degraded` or `suspended` comes after
     it and before the lift. The connection's `acknowledged` state change, caused by the
     acknowledgment copy (rule 61), comes after the copy and before the lift, in the lift's batch or
     an earlier one (journal spec §9.8). A reconnect alone lifts nothing.
4. **Rules 310 to 312** (journal spec v0.102). They are stream rules on the account stream, judged
   by `append` after each draft's own rules, with reason `schema`:
   - **310.** The lift's `cause` is in force (`payload.cause`), and its `restriction` is the
     strictest restriction of the causes still in force after it, or `active` when none is
     (`payload.restriction`).
   - **311.** `acknowledgment` names an earlier `OwnerAcknowledged` copy of `subject` `restriction`
     on this stream, and that copy meets all of the following (`payload.acknowledgment`):
     - its `event` names an `AccountRestrictionChanged` of this `cause` that still stands at the
       lift: no later record of this cause, and no lift of it, comes between them. A cause raised
       again after the acknowledgment needs an acknowledgment of its own;
     - no `OwnerCommandRefused` with `command` `acknowledge` names the copy's original.

     A lift ends its record's standing, so an acknowledgment lifts once.
   - **312.** `evidence` is the record decision item 3 names for the cause, in the order that item
     says (`payload.evidence`).

   **Rule 309 is amended.** A cause is in force from the record that raised it **until a lift names
   it**. A cause lifted and raised again is journaled again.
5. **The agents follow the account state** (invariant 6). Agent restrictions are keyed by reason
   code, so a lift that loosens the state does two things in its batch, right after the lift:
   1. it applies the state left's entry, unless the agents already hold it: `exits_only` under
      `account_restricted` when `closing_only` is left;
   2. it then removes every other account entry the agents hold: `AgentModeApplied` to `normal`
      under `account_trading_blocked` or `account_restricted`. So a lift to `active` leaves no
      account entry, even when the cause was raised at both restrictions.

   Removing an entry hands each agent back to the strictest restriction it still holds, so an
   owner's pause, a kill switch, or a held run stays in force. A lift that leaves the state
   unchanged moves no agent. Each record's agent effect follows it in record order, so a cause
   raised again later in the lift's batch applies its entry after the lift's removals. **No owner
   alert** is sent for a lift: the owner's acknowledgment caused it, and notifications spec's
   `account_restriction` kind names a restriction, never a lift.
6. **Slices.**
   - **A.** This decision and the journal spec with its vectors.
   - **B.** `mandate-journal` registers the schemas and rules 310 to 312.
   - **C.** The executor judges and lifts. This needs the executor's copy of the control stream's
     acknowledgments, which is E7-4 slice 5's.
   - **D.** The CLI's acknowledgment of a restriction.

   Until C lands, nothing lifts, which is the reading that adds no risk.

## Rationale

- Each lift names the records it rests on, so `append` can check it, and a replay or an audit reads
  why the account trades again without the executor's memory.
- Reusing §9.28's acknowledgment keeps one step-up, independence, and reuse path for every owner
  lift. It also keeps the copy's routing unchanged.
- Rule 309's amendment is what lets a lifted cause be raised again. Without it a second restriction
  from the same cause could never be journaled, and the account could not be restricted again.

## Alternatives considered

- **Lift every cause on one acknowledgment of the account.** Rejected: §7.3 lifts causes
  independently, and a broker's clearance must never lift the connection's restriction.
- **Treat any account report after a restriction as the refresh, without an acknowledgment.**
  Rejected: §7.3 requires the owner's acknowledgment for every cause.
- **Move agents back to `normal` only when no cause remains.** Rejected in favour of item 5.
  Following the account state keeps agents exactly as §7.3's table says. `exits_only` under
  `closing_only` is stricter than or equal to every looser mode, and an exit is never held by it.
