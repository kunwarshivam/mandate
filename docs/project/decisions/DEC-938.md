# DEC-938: The paper run journals its own fill, and a classifier refusal stops at Classify

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-16 (UTC) |
| **Decided by** | Claude (builder agent), under DEC-79 (reversible engineering decisions) and DEC-176 (items 2 to 4: each reading adds no risk and weakens no safety invariant) |
| **Story or claim** | E2, the first paper trade; the defects #1355 recorded; DEC-921 (one PR, tests first) |

## Decision

The first paper fill (1 SPY at 763.75, 2026-10-16) stopped the run with `the tracer stopped at
Journal: the journal answered Invalid`. The root cause was that Alpaca names an equity by its
ticker (`SPY`) in every answer, a `FILL` activity included, while the executor names it by the
asset id it sent. The executor's fill check compares instruments, so the run's own fill read as
another instrument's: external activity. Its first record, `ExternalActivityIngested`, has no
registered schema, so the journal refused the whole batch. Behind that, the fill records were not
in the shape the journal registers either, and the late fill's reconciliation could not run.

1. **The connector names a registered instrument by its asset id.** `mandate_shell::symbols`
   maps each ticker the run registered (the confirmed mandate's pinned instrument: its `symbol`
   and `asset_id`) to its asset id. It does this in every broker answer: orders and their legs,
   positions, fills, and listed orders. A ticker the run did not register stays as the broker
   spelled it, so an instrument the run does not trade is still external activity.
2. **Fill records take the registered shape.** `FillApplied` and `LateFillApplied` carry
   `instrument_id` (the fold already reads both spellings, DEC-446 item 7). `fees` is a list:
   empty when the broker reported none, as Alpaca's `FILL` never does, and otherwise one USD
   `commission`, `charged` (trading spec §6.2's only per-fill broker charge). The records carry the
   four `config_refs` the catalogue requires (`fee`, `cal`, `set`, `ins`), from a new
   `InstrumentSnapshot::fill_refs` port. The paper run registers no settlement calendar, and
   `mandate-accounting` settles the paper run on its registered trading calendar, so
   `settlement_calendar` names that object: the one the settlement was actually computed on. A
   snapshot that knows no configuration names none, and the journal refuses that fill.
3. **`LateFillApplied` is registered with `FillApplied`'s version-1 schema.** Journal spec §9's
   catalogue gives both one row, with the same required refs and fields. The entry read `filled`
   before its fill was ingested, so the fill is late (trading spec §5.7: a fill for an order in a
   terminal state) and has to be journaled as `LateFillApplied`.
4. **A classifier that cannot answer stops the step at Classify.** It leaves no classification,
   so it has no decider. Rule 5 of journal spec §9.1 needs a `decided_by` on any `DecisionMade`
   the dry run allowed, and the closed label set has no label for "the classifier could not
   answer". Before this change the fail-safe `deny` went out with `decided_by: null`, the journal
   refused it, and the refusal was reported as Journal. Now the shell poisons the step, as it does
   for a flatten planner that cannot plan. It reads the poison before it performs any effect, so
   nothing of the step is journaled or sent, and the run reports Classify. Nothing is sent either
   way; the record the journal would refuse is never drafted.
5. **A reconciliation that ingests a late fill asks for the next one after its own
   `ReconciliationRun`.** The request then reads on from the checkpoint that run recorded, not
   from one already passed. The shell gathers and runs that reconciliation the same way as the
   first, at startup and during the watch, and never steps its reads one by one. A fill is
   ingested once, so the next reconciliation asks for nothing more. If one still asks after two
   rounds, the run stops at Reconcile.

## Rationale

Every item makes the code meet the journal and trading specs as written. No validation is
loosened: the fill now passes the schema the journal already registered, and item 3 registers
the sibling record the catalogue defines with it. Items 2 and 4 are DEC-176 readings. Item 2
records the configuration the computation used. Item 4 stops rather than journaling an unlabelled
decision. Neither adds risk.

## Alternatives considered

- **A new `decided_by` label for the fail-safe deny (for example `fail_safe`).** That is a change
  to journal spec §9.1 and mandate spec §6.4's closed vocabulary, and the spec guard keeps spec
  changes out of code PRs. It is left as a follow-up for a spec PR, if the record is wanted.
- **Prefer the asset id the wire carries.** Orders and positions carry `asset_id`, but a `FILL`
  does not, so the registered ticker is the only key that covers every answer.
- **Treat a fill of an entry that read `filled` as an ordinary `FillApplied`.** That would go
  against trading spec §5.7's literal rule, and skip the reconciliation it requires.

## Not decided here (backlog)

- The executor reads the paper environment only from a `StreamOpened` payload member that the
  registered schema no longer carries. On the paper path it therefore books no simulated fee
  (trading spec §10), and `FeesCharged` has no registered schema yet.
- `ExternalActivityIngested` has no registered schema, and an unattributed `FillApplied` has no
  `client_order_id`, so a genuinely external fill is still refused at the journal.
- On the paper path the executor's account-stream records carry the risk clock
  `1970-01-01T00:00:00Z`: no tick reaches the executor before its first records.
