# DEC-780: Close the records-access, export and verification records (journal spec v0.24 §9.12)

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | An agent (Claude Code, lane L5's S0b builder) under DEC-79 and DEC-176. Each reading closes a previously open schema from the members its §9 row already lists (DEC-176 item 2): it refuses unknown members, adds no risk, and loosens no rule |
| **Story or claim** | E12-3, E12-6; claims [#748](https://github.com/kunwarshivam/mandate/issues/748), [#756](https://github.com/kunwarshivam/mandate/issues/756) |

## Context

Journal spec §9 places `RecordsAccessed` ("accessor (opaque), scope"), `ExportCreated` ("export
manifest") and `VerificationRun` ("scope and result") on the control stream, with no closed payload.
The workspace API's audit routes (workspace API spec §4.8, API-16) and the `mandate-audit` crate
(E12) must draft them, and `mandate-journal` cannot register a schema the spec does not state. Lane
L2's E10-15 claim (#749) names no event; no L2 branch or PR covered these three when this was
written, and the lead was told. L2's journal changes then landed first (#775 and #792, journal
spec v0.21 and v0.22, and the hold of v0.23), so this change follows them on main: its section,
version and rule numbers come after theirs, and `RecordsAccessed` takes the `client` actor of
journal §3 (rules 81 to 83) as main defines it (items 7 and 12).

## Decision

1. **Journal spec v0.24 adds §9.12**, which closes the three records at schema version 1 with rules
   96 to 101, from the members their §9 rows list. None names a configuration.
2. **Scope is stream ranges bounded by hashes.** Every record names what it covers as a list of
   `range`s: `stream_id`, `from_seq`, `to_seq`, `prev_hash` (§11's trusted start) and `to_hash`
   (the head, as workspace API API-14 stamps a read). A verification's range carries its own
   `failure` and may have a null `to_hash` when a failure left no verified head. That reading of
   "scope" is the one §11's input and API-14's stamp already use, and it lets the journal check
   tenancy from the record alone.
3. **Tenant isolation is a journal rule.** Rule 96 refuses a range whose `stream_id` is in another
   workspace than the control stream it is written to. A trace never follows a `causation_id` into
   another workspace's stream.
4. **Payloads carry no content.** Only stream IDs, `seq`s, digests, artifact references, §11 check
   codes and opaque IDs. No instrument, order, position, quantity, price or mandate content.
5. **Two types join §9.1's:** `stream_id` (§2's form, all five stream types) and `digest` (64
   lowercase hex SHA-256: an event's hash, or a digest of bytes the journal does not store). A
   `digest` is not a `ref`: it names no stored artifact, so it is not listed in `artifact_refs` and
   §11 check 6 never looks for it.
6. **"Export manifest" reads as the canonical export's verifier digest.** `ExportCreated` carries
   a `form` (`canonical`, `json` or `csv`, as workspace API §4.8 names them), the ranges, the
   `verifier_digest` of DEC-265 item 3 (`mandate-journal-cold`'s `ExportBundle::verifier_digest`,
   one length-prefixed SHA-256 over every segment manifest and file, anchor root and token), and
   for a view the `digest` of the view's bytes. A view names the digest of the canonical export it
   derives from (API-16), and the export's ID is the record's `event_id`. No second manifest
   shape is defined: the segment manifests are DEC-263's. A `ref` was rejected because neither the
   bundle's digest nor a served view is a stored artifact, and a `ref` to an unstored object would
   fail §11 check 6 on the control stream. The examination bundle (§12), which may carry resolved
   identities, is not a form at this version: a later version adds it with its own record of the
   identities it resolves, so v1 exports carry none.
7. **Who may write each.** `RecordsAccessed`'s `accessor` equals `actor.id` and its actor is not an
   agent or a broker (rule 97); a `client` actor, in journal §3's one shape (v0.22, DEC-671,
   rules 81 to 83), records its own reads with its own `id` as `accessor`, as workspace API §3.8
   requires; and a `platform_operator`'s read names the `PlatformOperatorAction` that opened its
   customer-approved break-glass window as `causation_id` (§7). `ExportCreated`'s actor is a user or `system` (a service account,
   identity spec §3.1), never a client (rule 98). A scheduled verification is `system`'s; a
   requested one is a user's or a service account's (rule 99).
8. **Journaled before served.** §7 now says a read or an export is journaled before it is served.
   API-16 already said it of exports; saying it of reads tightens §7 (a read that cannot be
   journaled is not served) and adds no risk.
9. **A verification records §11's first failure per range** with the `seq` it was reported at
   (null for the four range-level checks, rule 100), and `result` is `pass` exactly when no range
   failed (rule 101). It does not replace §11's incident path.
10. **`operation` is the workspace API operation's name, typed `id`.** The API spec (lane L2) owns
    the route names; the journal checks the form only.
11. **One `RecordsAccessed` serves both lanes.** At lane L2's request (it writes the record for the
    replay, the dry run, notice resolution and every client read), the record also carries
    `resources`, the opaque IDs of the non-stream resources read, sorted and unique (rule 97), and
    `result`, the served response as an artifact in the workspace's own artifact store, or `null`;
    the result never leaves the workspace deployment. The principal stays in the
    envelope: `accessor` equals `actor.id`, and a client's human is `actor.on_behalf_of`, which
    journal §3 (v0.22, rule 81) defines; this record does not redefine it.
12. **A client's read uses §3's client actor exactly, and the client is its own accessor.** Journal
    §3 rules 81 to 83 (v0.22) fix the one client actor shape: `on_behalf_of` present exactly for a
    `client` and an `id` naming the user, never the client's own `id`; `build` null; and only on the
    control stream's `MandateDraftSaved`, `OwnerRequestSubmitted`, `RecordsAccessed` and
    `OwnerCommandIssued`. Rule 83 said `RecordsAccessed`'s payload was not closed yet and that a
    client's read must use that shape once it is. Rule 97 keeps `accessor` equal to `actor.id`, so
    for a client the `accessor` is the client's own `id` and the human stays in
    `actor.on_behalf_of`; workspace API §3.8 already records a client's read "with the client as
    accessor". Two readings were possible: the client's `id` or its human. This decision takes the
    client's `id`, the reading that tightens (DEC-176): the record then names both the agent that
    read and, through the envelope, the person it acted for, so neither is lost, and a client can
    never be recorded as if its user had read. Nothing in rules 81 to 83 says otherwise. Rule 83's
    sentence now points at §9.12, and the vectors refuse a client read with no `on_behalf_of`
    (rule 81), with a `build` (rule 82), or with its human as accessor (rule 97), and refuse a
    client's export or verification (rule 83).

## Rationale

The three records are the audit trail of the audit trail: who read what, what left the workspace,
and whether the chain held. Naming coverage by ranges and hashes makes each record checkable
against the streams it names, keeps it free of trading content (rule 6 of `AGENTS.md`, and the
lane's rule that audit output never leaves the deployment), and puts the tenant check where a
reviewer can see it fail. Every reading refuses more than the prose did, so DEC-176 lets an agent
take it.

## Alternatives considered

- **A free-form `scope` object.** Rejected: unclosed, and the journal could not check tenancy.
- **Listing single events by `event_id`.** Rejected: an event ID does not name its workspace, so
  rule 96 could not be checked; a one-event range does the same job.
- **Closing `operation` to an enumerated set now.** Deferred to the API spec, which owns the routes;
  a later version can narrow the type.
- **Including the examination bundle at v1.** Deferred: it resolves identities, which needs its own
  record and the records custodian's role, neither of which is specified.
