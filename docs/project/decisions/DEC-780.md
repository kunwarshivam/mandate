# DEC-780: Close the records-access, export and verification records (journal spec v0.19 §9.8)

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | An agent (Claude Code, lane L5's S0b builder) under DEC-79 and DEC-176. Closing a schema from the members its §9 row already lists refuses unknown members and adds no risk; every reading below refuses more or records more, and none loosens a rule |
| **Story or claim** | E12-3, E12-6; claims [#748](https://github.com/kunwarshivam/mandate/issues/748), [#756](https://github.com/kunwarshivam/mandate/issues/756) |

## Context

Journal spec §9 places `RecordsAccessed` ("accessor (opaque), scope"), `ExportCreated` ("export
manifest") and `VerificationRun` ("scope and result") on the control stream, with no closed payload.
The workspace API's audit routes (workspace API spec §4.8, API-16) and the `mandate-audit` crate
(E12) must draft them, and `mandate-journal` cannot register a schema the spec does not state. Lane
L2's E10-15 claim (#749) names no event; no L2 branch or PR covered these three when this was
written, and the lead was told.

## Decision

1. **Journal spec v0.19 adds §9.8**, which closes the three records at schema version 1 with rules
   54 to 59, from the members their §9 rows list. None names a configuration.
2. **Scope is stream ranges bounded by hashes.** Every record names what it covers as a list of
   `range`s: `stream_id`, `from_seq`, `to_seq`, `prev_hash` (§11's trusted start) and `to_hash`
   (the head, as workspace API API-14 stamps a read). A verification's range carries its own
   `failure` and may have a null `to_hash` when a failure left no verified head. That reading of
   "scope" is the one §11's input and API-14's stamp already use, and it lets the journal check
   tenancy from the record alone.
3. **Tenant isolation is a journal rule.** Rule 54 refuses a range whose `stream_id` is in another
   workspace than the control stream it is written to. A trace never follows a `causation_id` into
   another workspace's stream.
4. **Payloads carry no content.** Only stream IDs, `seq`s, event hashes, artifact references, §11
   check codes and opaque IDs. No instrument, order, position, quantity, price or mandate content.
5. **Two types join §9.1's:** `stream_id` (§2's form, all five stream types) and `event_hash` (64
   lowercase hex). An event hash is not a `ref`, so it is not listed in `artifact_refs`.
6. **"Export manifest" reads as a `form`, the ranges, the manifest artifact and, for a view, the
   view artifact.** The forms are `canonical`, `json_view` and `csv_view`; a view names the
   manifest it was derived from (API-16), and the export's ID is the record's `event_id`. The
   examination bundle (§12), which may carry resolved identities, is not a form at this version: a
   later version adds it with its own record of the identities it resolves, so v1 exports carry
   none.
7. **Who may write each.** `RecordsAccessed`'s `accessor` equals `actor.id` and its actor is not an
   agent or a broker (rule 55); a client is admitted once journal §3 adds the kind (E9-9), as
   workspace API §3.8 requires. `ExportCreated`'s actor is a user or `system` (a service account,
   identity spec §3.1), never a client (rule 56). A scheduled verification is `system`'s; a
   requested one is a user's or a service account's (rule 57).
8. **Journaled before served.** §7 now says a read or an export is journaled before it is served.
   API-16 already said it of exports; saying it of reads tightens §7 (a read that cannot be
   journaled is not served) and adds no risk.
9. **A verification records §11's first failure per range** with the `seq` it was reported at
   (null for the four range-level checks, rule 58), and `result` is `pass` exactly when no range
   failed (rule 59). It does not replace §11's incident path.
10. **`operation` is the workspace API operation's name, typed `id`.** The API spec (lane L2) owns
    the route names; the journal checks the form only.

## Rationale

The three records are the audit trail of the audit trail: who read what, what left the workspace,
and whether the chain held. Naming coverage by ranges and hashes makes each record checkable
against the streams it names, keeps it free of trading content (rule 6 of `AGENTS.md`, and the
lane's rule that audit output never leaves the deployment), and puts the tenant check where a
reviewer can see it fail. Every reading refuses more than the prose did, so DEC-176 lets an agent
take it.

## Alternatives considered

- **A free-form `scope` object.** Rejected: unclosed, and the journal could not check tenancy.
- **Listing single events by `event_id`.** Rejected: an event ID does not name its workspace, so
  rule 54 could not be checked; a one-event range does the same job.
- **Closing `operation` to an enumerated set now.** Deferred to the API spec, which owns the routes;
  a later version can narrow the type.
- **Including the examination bundle at v1.** Deferred: it resolves identities, which needs its own
  record and the records custodian's role, neither of which is specified.
