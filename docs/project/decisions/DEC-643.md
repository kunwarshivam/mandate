# DEC-643: The refusal codes of the authorization step

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 (UTC) |
| **Decided by** | The lane L1 builder agent, under DEC-79 and DEC-176: it names refusals the spec already makes and adds none that grants |
| **Story or claim** | E9-2 (claim #757); [identity spec](../../specs/identity.md) v0.2 §4.5 |

## Decision

The authorization step and the role-change check return exactly these refusals, each with a
stable code, mapped onto workspace API §3.5:

| Code | When | API |
|---|---|---|
| `no_membership` | No membership reaching the scope, or a non-member principal outside its column's scope, or a principal kind with no column | 404 `not_found` (API-9) |
| `forbidden` | The scope is reached, but no effective role or column grants the row | 403 `forbidden` |
| `inactive_permission` | The row is inactive (DEC-641 item 4) | 403 `forbidden` |
| `own_roles` | A change grants or removes a role of its own author (ID-13) | 403, code `own_roles` |
| `owner_role_reserved` | An org admin grants or removes the org owner role (§4.2 note) | 403, code `owner_role_reserved` |
| `last_owner`, `last_admin` | The change leaves no `active` org owner or workspace admin (§5.2) | 409, the code itself |

ID-13 is read tightly: a principal neither grants nor removes its own roles; it leaves by
deactivating its own membership, which the last-owner and last-admin rules still check.

## Rationale

The API and the web app need one code per refusal to render it, and the tests need to assert
which refusal fired, so a refusal for the wrong reason is caught.

## Alternatives considered

- **A single `forbidden`.** Hides why, and a test could not tell a last-admin refusal from a missing role.
