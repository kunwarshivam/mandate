## Context

§4.3 and §4.7 name `GET /agents`, `GET /agents/{id}`, `GET /approvals`, and `GET /approvals/{id}`
and say what each serves, but no response shape exists: `schemas/workspace-api/` has only the
envelope and the commands, and the web app's reads were left to E11-9. The web app (lane W2) and
the server (lane A1) are built in parallel for the demo, so the shapes must be fixed first. Most of
what the D2 and D5 screens show (limits with headroom, positions, P&L, the bound order in words)
comes from folds that are not built yet.

## Decision

1. **Four closed responses, under `schemas/workspace-api/read-models/`:** `agents`, `agent`,
   `approvals`, and `approval`. Each is the §3.2 envelope plus its own members, with
   `unevaluatedProperties: false`, and an `as_of` naming every stream it read (API-14).
2. **They carry only what the journal states today.** An agent is its id, environment, the
   mandate version it was deployed with, when it was deployed, its mode, and how many approvals
   are pending. An approval is its id, its agent, its state, when it was requested, its deadline,
   and its content hash; the single read adds the content object exactly as `ApprovalRequested`
   holds it. Everything else D2 and D5 show is added by later stories as new optional members,
   which §3.2 allows within `/v1`.
3. **An agent is one that `AgentDeployed` names on the workspace's control stream.** Its mode is
   the `to` of the last `AgentModeChanged` on its agent stream, and `stopped` once `AgentStopped`
   names it. Before either, the mode is `null`, read as "not reported yet", never as `normal`
   (`AGENTS.md` rule 3).
4. **An approval's state is folded from the agent stream's approval events**, as the CLI's
   `approvals list` folds them today: `pending`; `acted` (re-validation acted); or ended as
   `skipped` (by the owner or by re-validation), `timed_out`, or `canceled`. A `refused` or
   `counted` answer leaves it pending. `deadline` is `ApprovalRequested.deadline` as journaled,
   integer risk-clock seconds, not converted.
5. **The approvals inbox lists pending ones by deadline, then resolved ones**, most recent first
   (D5). `?state=pending` or `?state=resolved` narrows it; any other value is `invalid`.
6. **Ids in the path follow the journal's grammar.** An agent id is journal spec §2's identifier,
   at most 64 characters (common `Id`); an approval id is an event id. Anything else, an absent id,
   and another workspace's id answer the same 404 (API-9).

## Rationale

The shapes are small so that nothing in them is guessed: each member is a fact a journal event
states. The web app gets real data for its three demo screens now, and the rest arrives as
additive members when the folds that compute it are built.

## Alternatives considered

- **Mirror the web fixtures' full `Agent` and `Approval` types now.** Most of their members have no
  fold behind them yet; serving them would mean inventing values or nulls the screens would show as
  facts.
- **One dashboard read instead of four.** §4.7's `GET /dashboard` stays planned; the Home screen
  reads `agents` and `approvals`, which it needs anyway.
- **Convert `deadline` to a timestamp.** The risk clock's epoch is the scheduler's; the server
  passes the journaled value through rather than restate it.
