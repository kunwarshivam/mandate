## Context

An owner's request for an order (`OwnerRequestSubmitted`, journal spec §9.9; workspace API §4.6)
is copied by the agent runtime to its order builder. The builder only clips the owner's quantity to
the mandate's caps and classifies it ([DEC-2151](DEC-2151.md) item 3). Two journal rules made that decision
unwritable:

1. **`DecisionMade` rule 8.** A decision with purpose `open` or `increase` "was produced by a §8.3
   evaluation", so `exit_conviction`, `buy_conviction` and `combined_score` must be non-null. An
   owner's request has no §8.3 evaluation: no model outputs, no conviction, no score.
2. **`ApprovalRequested`, every version.** The top-level `combined_score` is a required `decimal`,
   and `content.evidence.combined_score` a required `{label, value}`. An owner-requested opening
   the mandate classifies `ask` has no score to show.

## Decision

1. **An owner's request is not a §8.3 evaluation.** A `DecisionMade` whose `requested_by` is
   `owner` or `client` has `exit_conviction`, `buy_conviction` and `combined_score` `null`, and
   empty `outputs_used` and `model_weights`, whatever its purpose. Its `clips_applied` lists every
   bound that reduced the owner's quantity, from the table's existing values (`max_order_usd`,
   `position_cap`, `gross_exposure_cap`, `target_qty`, `max_spend_usd`, `max_avg_price`), so a cut
   is recorded, never silent. Its `causation_id` is the `OwnerRequestSubmitted`'s `event_id`: the
   runtime copies a request once, and the control stream's `event_id` is the idempotency key
   (journal spec §2).
2. **Its approval shows no score.** An `ApprovalRequested` asking for such a decision has
   `combined_score` `null` at the top level and `content.evidence.combined_score` `null`, with
   `content.evidence.outputs` empty. A request for a decision `requested_by` `agent` keeps a
   non-null score exactly as before. Who asked is the decision's `requested_by`, which mandate
   spec §6.4's `trigger` carries to the approver; no score is invented. Journal spec rule 319
   checks it.
3. **A request without a quantity is not copied.** The API refuses a request without a positive
   size `invalid` at `/size` before journaling ([DEC-2151](DEC-2151.md) item 3). An
   `OwnerRequestSubmitted` with a `null` quantity, which §9.9's schema still admits, can only
   come from another writer. The runtime does not copy it: it journals nothing for it, hands it
   to no builder, and takes no action. The reason, in prose only, is `quantity_required`; no
   record carries it as a code. Adding no risk is the safe default (`AGENTS.md` rule 3).
4. **One instrument for now.** A request for any instrument outside the deployment's working
   universe, its own pinned asset, is not copied, in the same way as item 3. The API refuses it
   `invalid` at `/instrument` before journaling ([DEC-2151](DEC-2151.md) item 1). The reason, in
   prose only, is `not_in_working_universe`. A request never changes the envelope (`AGENTS.md`
   rule 11).
5. **The builder's limit for a buy is the ask**, as for the agent's own openings (mandate spec §8.3
   step 3). No sizing rule is added: the owner's quantity is clipped, never grown.
6. **The runtime has no decision that records an owner-requested sale.** No `DecisionMade` can
   record one: a sell needs an `exit_origin` (rule 8), and none of the origins (`signal`,
   `goal_completion`, `removed_instrument`) fits an owner's request. The API refuses a sell
   `invalid` at `/side` before journaling ([DEC-2151](DEC-2151.md) item 7). An
   `OwnerRequestSubmitted` with side `sell` from any other writer is inert in the runtime: it is not
   copied, in the same way as item 3. The owner's sale is the owner-exit path (`AGENTS.md` rule 13),
   with its own step-up, bid confirmation and pacing, and it stays always available. The reason, in
   prose only, is `owner_sell_use_owner_exit`.
7. **A clip that leaves nothing is the gate's refusal.** When the builder's clip leaves no quantity
   (no room under a cap), the runtime does not invent a hold. It asks the gate's dry run about the
   owner's unclipped quantity, and the `DecisionMade` records the gate's own reason code for the cap
   that binds (`max_order_size`, `concentration_limit`, `gross_exposure_limit`, and so on), with
   `clips_applied` empty. The owner sees exactly which limit refused them.
8. **A rule that reads the score denies an owner's request.** An autonomy rule whose `when` reads
   `combined_score` (mandate spec §6.3) cannot be evaluated for an owner's request, which has no
   score. The builder already treats a field the action does not carry as a condition error,
   never as "does not match" (`mandate-builder`'s first-match walk: a rule that cannot be
   evaluated stops the walk). So when the walk reaches such a rule, the classification is `deny`,
   and the `DecisionMade` records `autonomy` `deny` with `decided_by` `rule:<id>`, that rule's
   id, an existing label (journal spec rule 5). No reason code is added: `reason_code` stays the
   gate dry run's, which is `null` after its `allow` (rule 4). A rule before it that matches
   decides as it would for any proposal. A denial adds no risk (`AGENTS.md` rule 3). The owner
   who wants such requests to run writes a rule that does not read the score, in a confirmed
   mandate version.
9. **This change lands atomically.** The new vectors (an unscored `ApprovalRequested`, a requested
   `DecisionMade` without convictions) are refused by the old `mandate-journal`, and the new
   validator by the old spec's `reference` and `refcases` gates, as J1's and J2's were (DEC-2635,
   DEC-2335). So the spec, its reference and vectors, and `mandate-journal`'s rule 8 and
   `ApprovalRequested` schema ship in one pull request under one `ATOMIC_EXCEPTIONS` entry naming
   it.
10. **An owner's own request runs `auto`, as [DEC-2159](DEC-2159.md) rules (the founder).**
   DEC-2159 supersedes [DEC-2151](DEC-2151.md) item 2 and leaves the runtime's record of it to
   this decision (its item 4). Mandate spec §6.2 gains step 5d, applied last: a decision
   `requested_by` `owner` that the steps before it left `ask` becomes `auto`, labelled
   `owner_request` (a new `decided_by` label), and goes straight to an intent. The owner's Send is
   the confirmation. Only an `ask` changes: a `deny` stays a `deny` (the gate's dry run, a mode, a
   `deny` rule, the policy overlay, item 8's rule that reads the score), and the binding gate at
   submission runs every check and cap as for any opening, so a clip or a denial is told to the
   owner with its reason. A client's request stays `ask` (step 5a, MI-30, DEC-2159 item 3).
   Journal spec rule 7 refuses an owner's opening recorded `ask`, and an `owner_request` label on
   any decision but an owner's `auto` opening. So item 2's unscored approval now arises only for a
   client's request. Item 8 still denies an owner's request at a rule that reads the score, the
   conservative reading until the founder says otherwise.

## Why

The journal records what decided an order. An owner's request was decided by the owner's quantity,
the mandate's caps, the gate and the autonomy rules, and by no model, so its record names no model
figure. Every check that bounds risk still runs on it. Items 3, 4, 6 and 8 refuse; none admits an order
that today's rules would refuse.

## Attack it

- **An agent's or a client's opening labelled `owner_request`, to skip its approval (item 10).**
  Rule 7 refuses the label on any decision but an owner's `auto` opening, and a client's opening
  is never `auto`. `requested_by` is set from the authenticated channel (step 5a), and the runtime
  sets `owner` only on the decision caused by an `OwnerRequestSubmitted`, which the workspace API
  journals only for an authenticated owner (DEC-2151). Whatever the label, the binding gate runs
  every check and cap at submission.
- **An owner's request recorded with a score, to look model-backed.** Rule 8 refuses the decision,
  and rule 319 refuses an approval with a score beside an owner's decision in the same batch.
- **An agent's opening recorded as the owner's, to drop its evaluation.** It loses its numbers and
  outputs, and is still sized, gated and classified as any proposal. `requested_by` comes from the
  authenticated channel and never from content (journal spec rule 79, API-6), and a client's
  opening is never `auto` (MI-30).
- **A silent cut.** Every bound that reduced the quantity is in `clips_applied`; a cut to nothing is
  the gate's denial with its own reason code (item 7).
- **A null quantity, a sell or another instrument from a writer other than the API.** Nothing is
  copied, so nothing is sized or sent (items 3, 4, 6).
- **A rule that reads the score, to make an owner's request run unasked.** It cannot be evaluated,
  so the opening is denied (item 8); no missing score reads as a match or as a miss.

## Consequences

- Journal spec v0.117: rule 8's owner branch, `ApprovalRequested`'s nullable score with rule 319,
  §2's and §9.9's sentences, and the `owner_requests` vectors. The existing owner and client
  `DecisionMade` vectors drop the numbers they no longer carry.
- Mandate spec v0.18: §6.4's `evidence`, §6.2 step 5a and §6.3's `combined_score` say the same.
- A mandate rule whose condition reads `combined_score` denies every owner's or client's request
  the walk reaches it for, so the web app should warn about that when the mandate is set up. The
  cell's demo mandates have no rules, so the demo is unaffected.
- Code: `mandate-journal`'s rule 8 and `ApprovalRequested` schema land with this decision (item
  9); the runtime's copy of the request and the builder's clip follow as tests-first pairs.

## Alternatives considered

- **Fill the convictions from the current model outputs.** Rejected: it would record figures that
  decided nothing, and show an approver a score as if it backed the owner's order.
- **A new `ApprovalRequested` schema version without a score.** Rejected: it multiplies with
  versions 2 and 3 (a plan, deferred checks), and a nullable score in every version says the same
  thing once.
- **Record a refused request as a `DecisionMade` deny.** Rejected by the coordinator: rules 1 to 3
  need a quantity and a limit price, and a sell needs an `exit_origin` that none of the existing
  ones fits.
