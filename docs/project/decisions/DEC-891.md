## Context

The verification run in `mandate-audit` needs two `mandate-journal` helpers that do not exist yet:

- `walk_range`, which walks a range position by position from `from_seq` to `to_seq` and reports
  `checked`;
- `anchor_record`, which reads an `AnchorComputed` row as the `Anchor` and token a verifier
  checks.

Their tests pin three cases that the specs leave open:

- **A row read after `to_seq`.** AU-8 says "a missing, reordered, or extra event fails", and
  §4.8.1 "Coverage" says a missing event fails `seq_gap` at the expected `seq`. Neither says where
  an extra event after the last one is reported. Rule 111 requires a per-event failure's `seq` to
  lie from `from_seq` to `to_seq`.
- **`checked` on a failure.** Rule 132 fixes `checked` as `to_seq − from_seq + 1` when `failure`
  is null. On a failed range it only bounds `checked`, "on purpose", and leaves the value to the
  run.
- **An `AnchorComputed` of another version.** §9.14 closes `AnchorComputed` at schema version 1
  and defines no other.

## Decision

1. **A row left over after `to_seq` fails `seq_gap` at `to_seq`.** Once every position from
   `from_seq` to `to_seq` has passed, any further row the read returned is an extra event (AU-8)
   and fails §11's `seq_gap`. It is reported at `to_seq`, because rule 111 lets a per-event
   failure name no `seq` outside the range. The rows that fail this way are a duplicate of the
   last event and an event read past the range. A duplicate or reordered row inside the range
   already fails `seq_gap` at its own position.
2. **On a failure, `checked` is the number of events that passed every per-event check before
   it.**
   - A failure at position `p` has `checked = p − from_seq`. A missing row counts the same way:
     every row read passed, so `checked` is the number of rows read.
   - A row left over after `to_seq` (item 1) has `checked = to_seq − from_seq + 1`, because every
     event of the range was walked and passed.
   - A range with no failure has `checked = to_seq − from_seq + 1`, as rule 132 requires.

   Every value is within rule 132's bound. Rule 132 bounds the value and this item fixes it, so
   two runs over the same rows record the same `checked`.
3. **`anchor_record` refuses an `AnchorComputed` whose schema version is not 1 as `NotAnAnchor`.**
   §9.14 closes the record at version 1. A later version may change its members, so reading one
   by version 1's shape could misread its leaves, root, or token. The refusal leaves the anchor
   unread, and a run cannot use an unread anchor as a trusted start or pass a check with it. A
   row that is version 1 but does not have §9.14's shape is `Malformed`.

## Rationale

Every reading takes the outcome that cannot produce a false pass.

- Ignoring a left-over row would pass a range that the store read wrongly or that holds a
  duplicated event, which AU-8 forbids. Reporting it after `to_seq` would break rule 111. So
  `to_seq`, where the walk ended and found more, is the only place left.
- Counting an event that failed would overstate what was proven. A fixed count also makes the
  record reproducible and lets the property test compare it with an independent oracle.
- Reading a version no spec defines is a guess. Refusing it costs nothing until a version 2
  exists, and that version's change updates `anchor_record` with it.

## Alternatives considered

- **Ignore rows after `to_seq`, trusting the read's range.** Rejected: a duplicated last event
  would pass, against AU-8.
- **Report the left-over row at `to_seq + 1`.** Rejected: rule 111 requires the `seq` to lie
  within the range.
- **Count the failing event in `checked`.** Rejected: it counts an event that did not pass.
- **Leave `checked` on a failure unspecified.** Rejected: two runs over the same rows could
  record different values, and the tests could not pin the walk.
- **Read any version of `AnchorComputed` by version 1's members.** Rejected: it guesses a shape
  no spec defines.
