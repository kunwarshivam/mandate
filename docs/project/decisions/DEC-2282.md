## Context

The founder wants the best model for each kind of problem, and wants the owner to choose. The
harness's kinds of problem are its **run kinds**. The core picks the run kind before anything
untrusted is read (agent harness spec §6.9, §15):

| Run kind | What it does | Output |
|---|---|---|
| `ideate` | Finds and argues a new thesis | Theses and invalidations |
| `monitor` | Re-checks held instruments and active theses, on the schedule or on news | Risk-reducing output only |
| `owner`, `explain` | The desk: answers the owner, explains an ask (§15, not yet live) | An answer, never an order or a thesis |

Today a run uses one model for all its turns.

**What already holds.** The registry already holds many entries, each with its own identity probe,
§4.3 gate and price table. The meter reserves each call at its own entry's price, under every cap.
Journal rule 146 holds per call.

**What doesn't, and what this record changes.**
- The mandate pins one research model (V-036).
- A call's `model` is that model (agent harness spec §10.1).

A model that picks the model at call time is ruled out. That includes OpenRouter's `openrouter/auto`,
or a "semantic" router choosing freely. It breaks four rules:
- DEC-997: one zero-retention upstream, no fallbacks.
- INF-1: the reported identity must equal the pin.
- Replay.
- The meter, which reserves a known price before each call.

## Decision

1. **The owner assigns a model per run kind, as an envelope field.** The research agent's signal
   model gains `routes`: for each run kind (`ideate` and `monitor` in v1; `owner` and `explain` once
   §15 is live), one entry from the vetted registry, as `model_id`, `version` and `content_hash`.
   The mandate's canonical bytes hold the routes, so a mandate version pins them and the owner
   confirms them, like every envelope field (rule 11). A run's every turn calls its run kind's
   entry. Nothing picks a model at call time.
2. **Only vetted entries can be chosen.** An entry may be routed only if it is in the platform's
   registry with status `offered` for the research role. That means it has:
   - passed the §4.3 gate, including the identity probe on its endpoint;
   - a pinned dated snapshot on one zero-retention upstream, with `allow_fallbacks: false`;
   - a price table;
   - tool calling and structured outputs.

   All of the role's entries pin the same harness content: the template, tools, output schemas per
   run kind, loop bounds and retrieval plan. They differ only in identity, sampling, deadline and
   prices. So a model change never changes what the agent may read or do. There are no free-text
   slugs: validation refuses any route that isn't an offered entry (a new rule beside V-036).
3. **The platform proposes defaults, and the owner confirms them.** The defaults are:
   - `ideate` → Claude Sonnet 5.5 (DEC-2396 A), for thesis writing, where a thesis can open a
     position;
   - `monitor` → Claude Haiku 5.5 (DEC-2396 B), whose output can only reduce risk;
   - the desk → Sonnet 5.5, when live.

   The defaults are shown in the envelope step and confirmed with the rest of the envelope. None is
   applied silently.
4. **Changing a model is a confirmed mandate change.** Mandate spec §9.2 already classifies any
   signal-model change as increasing (fail safe), so it needs the owner's confirmation and a new
   mandate version. That is tighter than a "neutral" class, and costs only a confirmation. A model
   change adds no trading risk: positions, the gate, limits, exits and kill switches never read a
   model. It is never applied without confirmation. Each call is journaled as now:
   `ModelInvocationRecorded`'s `model`, `config_refs.model_version` and `reported_identity`. Every
   routed entry is registered on the control stream.
5. **Cost is shown, and the caps still bind.**
   - **At selection**, the web and API show for each choice the estimated maximum per run: turns
     × (input tokens × input price + output tokens × output price), from the entry's loop bounds and
     price table. They also show the day and the month at the envelope's cadence (`interval_s`,
     event runs), against the research daily cap and the workspace and deployment monthly caps.
   - **A choice that cannot fit** the daily cap at that cadence is warned about, not blocked, with
     the runs a day it does buy.
   - **The meter still refuses** any call past a cap, as today (inference spec §7.3).
6. **The registry is the platform's.** Adding a model is a platform decision: the identity probe,
   zero retention, prices and the §4.3 gate. It is never the owner's. For v1 the vetted list is:

   | Entry | v1? | Why |
   |---|---|---|
   | A. Claude Sonnet 5.5, `google-vertex/global`, 2 / 10 per million | Yes | The default for `ideate` |
   | B. Claude Haiku 5.5, `google-vertex/global`, 0.10 / 0.50, pinned at its highest tier | Yes | The default for `monitor`; a cheaper choice for any run kind |
   | C. GPT-5.6 Terra, `azure`, 2 / 12 | Not in v1 | It adds a second upstream: its own zero-retention terms, key scope, routing lock and probe. Its price is above A's, with no capability the harness needs that A lacks. Add it when an owner needs a second vendor; the record keeps the option |

## Cost

These use DEC-2396's run of 8 turns, each 20k tokens in and 2k out, with no cache: **$0.48** a run on
Sonnet and **$0.024** on Haiku.

The demo envelope runs hourly, with up to 4 event runs a day and $5 a day. It has one instrument, so
it is mostly `monitor`. For a day of 2 `ideate` and 20 `monitor` runs:

## Risks

- **A weaker monitor, if chosen.**
  - A missed invalidation leaves a position open longer. It stays bounded by its stop, the risk
    limits and the kill switch, none of which read a model (rule 13).
  - A false invalidation causes an exit that wasn't needed, which reduces risk.
  - Each entry passes the §4.3 gate and a §8.3 regression of each run kind before it is offered.
- **Haiku's tiered price.** The entry pins the highest listed tier, and the price is re-read before
  the entry is mounted (DEC-2396 item 3).
- **More entries to keep.** Each has its own snapshot, probe and deprecation. When an entry is
  deprecated, the owner is asked to choose again, and a version naming it is refused once the entry
  is withdrawn (inference spec §4.4).
- **Wording.** The picker says that the owner chooses the model and that the platform vetted the
  list. It makes no performance claim about any model (inference spec §8.1).

## Rejected

- **`openrouter/auto`, or any router choosing at call time.** See Context.
- **A route table fixed by the platform.** The founder ruled that owners assign models.
- **Routing per turn.** It would mix models within one transcript and one ceiling.
