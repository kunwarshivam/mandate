# DEC-869: Journal the broker's order id on `OrderStateChanged` version 2 (journal spec v0.34)

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The C3 journal-spec builder (Claude Code), under DEC-79 and DEC-176: the change only adds a member and a reading that refuses by default, and loosens no rule |
| **Story or claim** | E7-6, the [first live trade brief](../tasks/first-live-trade.md)'s C3; [DEC-860](DEC-860.md) item 7; journal spec §9.16; connections spec §6.2 |

## Decision

1. **Is the id already journaled? No.** A place answer reaches the journal only as
   `OrderStateChanged` (executor `orders.rs`, `described`), whose version-1 members are DEC-459's:
   `broker_status`, `filled_qty` and the rest, and no broker order id. `replaced_by_broker_order_id`
   names a replacement's new order only; `ExternalActivityIngested`'s `broker_order_id` names
   orders that are not ours; `BrokerExchangeRecorded` is raw, redacted, optional, and the
   Robinhood connector writes none. So DEC-860 item 7's journal-spec field is needed.
2. **Where.** `OrderStateChanged` at `schema_version` 2: version 1's members in their order, and
   `broker_order_id` (`text?`) last, nothing else moved, as §9.5's version-2 records added
   `risk_clock`. Version 1 is not edited (§8), stays registered, and keeps replaying, so every
   stream written before v0.34 stays valid. Not `OrderSubmitted`, which is journaled before the
   request (`AGENTS.md` rule 5) when no id exists; not a new event type, which would add surface
   for one member.
3. **Who writes it.** Non-null exactly on a record written from a broker order record that carries
   the order's broker id (a place answer, an order query, a cancel answer that is the order, a
   list-and-match or reconciliation adoption); null on every other record. No per-record rule
   checks it: `broker_status` is also written by fills with no order record in hand.
4. **Who reads it.** Only the connector's rebuild of its `client_order_id` → order id map at start.
   No id — a pre-v0.34 stream, a place in doubt not yet adopted — or two different ids for one
   `client_order_id` is no recoverable id: the cancel is `NotSent` (`no_order_id`), the shell
   stops and alerts the owner (DEC-85), the order stays live, and nothing is guessed (CN-7). The
   executor's fold and every risk input are unchanged.
5. **Content.** The broker's opaque order identifier only; never a credential, token, account
   number or vault path, and never in a notification payload (`AGENTS.md` rules 6 and 7).
6. **What follows.** No vectors: `reference/journal` does not model `OrderStateChanged`, and the
   vectors stay version 3. `mandate-journal`'s registration of version 2, the executor's writer,
   and the connector's rebuild with its test
   `a_cancel_after_a_restart_finds_its_order_id_from_the_journal` follow as code changes (ES-22).

## Rationale

A cancel by the broker's id after a restart, the kill switch's order-by-order cancels included,
must find its order (`AGENTS.md` rule 13). Holding the map only in memory loses it on a restart;
the journal is the source of truth for account state. The two-ids reading resolves a gap by the
option that adds no risk: escalating to the owner, never cancelling the wrong order.

## Alternatives considered

- Adding the member to version 1: rejected, a closed version is never edited and stored records
  lacking it would fail validation (§8, DEC-459).
- A new `BrokerOrderAcknowledged` record: rejected, more surface and a second record per
  acknowledgment for one member.
- Reading the id out of `BrokerExchangeRecorded`'s raw body: rejected, it is redacted, optional,
  and not a typed member.
- The latest id wins when two differ: rejected, it could cancel an order that is not ours.
