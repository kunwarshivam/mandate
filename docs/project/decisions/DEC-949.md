# DEC-949: The grant wait ticks the runtime at the ask's deadline, so the runtime closes it

| | |
|---|---|
| **Status** | Accepted (agent: reversible engineering readings under DEC-79, each one under DEC-176 — every reading denies or sends nothing where the code before it denied and sent nothing too) |
| **Date** | 2026-10-16 (UTC) |
| **Decided by** | `claude-code` (builder, the grant-deadline-wake lane), under DEC-79, DEC-176 and DEC-921 |
| **Story or claim** | E7-26; DEC-940 item 7; DEC-944; claim [#1399](https://github.com/kunwarshivam/mandate/issues/1399) |

DEC-940 item 7 left the runner's grant wait handing the runtime nothing at or past an ask's
deadline, because the journal then refused the runtime's `ApprovalTimedOut`. DEC-944 (journal spec
v0.41, #1379 and #1383) registered that record with rule 135, so the reason is gone. Before this
decision the fold still denied `approval_timed_out` at the deadline and nothing was sent, but the
ask stayed pending on the journal: no `ApprovalTimedOut` was ever written by a live or paper run.
These are the readings this lane takes.

## Decision

1. **A wake at or past the deadline ticks the runtime alone.** The shell's `AskedCycle` gains a
   fourth call, `expire(now)`: it moves the session's event time to `now`, hands the runtime one
   `Input::Tick` at `now`'s risk-clock second, and reads both streams back, as `wake` does. The
   runtime's own `expire` then journals `ApprovalTimedOut {approval, on_timeout: skip}`, caused by
   the ask (rule 135). `granted_opening` calls it on every read at or past the deadline, and once
   when the ask it binds is already at or past its deadline, then denies `approval_timed_out`.
   Nothing is sent (rule 3): the runner's fold denies at or past the deadline whatever the read
   holds, and the opening stays held at the shell's door.
2. **The last pause ends at the deadline.** The wait pauses the lesser of the poll interval and
   the time left to the deadline, so the tick lands at the deadline itself, the first tick at or
   after it that mandate spec §6.4 names, and never up to an interval past it.
3. **The deadline's wake reads no quote and hands no answer.** `wake` needs a fresh IEX quote for
   its mark (DEC-943 item 2) and hands the control stream to the runtime first. Neither is needed
   to deny, and both could only hurt: a failed quote read at the deadline would stop the run
   before the runtime closed the ask, and an answer handed before the tick would be judged at the
   previous wake's risk clock, still before the deadline, so the runtime could admit and
   re-validate a grant after its deadline had passed. So `expire` ticks only. An answer committed
   before the deadline and not yet read stays on the control stream; the runtime reads it later as
   `not_pending`.
4. **A refused tick stops the run.** If the shell refuses the tick (a journal refusal, for one),
   the run stops with that refusal instead of the clean `approval_timed_out`. Either way nothing
   is sent; the refusal is the more informative stop.
5. **Rule 13 is unchanged.** The tick passes through the same door as every wake: only a purpose
   that adds risk is held, so an exit, a protective order or a risk exit the tick raises is never
   held by the wait.

## Rationale

The timeout is a deny, and the runner already denied; what was missing was the runtime's own
record of it, which the journal now admits. Ticking the runtime at the deadline is the one input
the runtime needs to write it, and it is the input it already takes at every wake. Keeping the
deadline's wake to a tick alone means the only thing it can do is close the ask.

## Alternatives considered

- **Call `wake` at the deadline with a fresh quote.** Rejected for item 3's reasons: a quote is not
  needed to deny, and a failed read would leave the ask pending again.
- **Hand the control stream before the tick, as `wake` does.** Rejected: it would let the runtime
  judge an answer at a risk clock before the deadline after the deadline had passed.
- **Keep pausing a whole interval.** Rejected: the tick could land up to an interval past the
  deadline, and the runtime's record would carry that later time.
- **Tick the runtime only when the deadline passes during the wait, not for an ask bound already
  past it.** Rejected: that ask is just as pending, and one tick closes it.
