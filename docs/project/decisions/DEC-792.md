## Decision

1. **An allowlist of push-service hosts.** A push subscription's endpoint is accepted, stored, and
   sent to only if it parses as `https`, port 443 (none written, or `:443`), with no user
   information, and a host that is a lowercase ASCII name. An IP literal, a trailing dot, a
   non-ASCII or `xn--` (IDN) label, or a percent-encoded character is refused, never normalized into
   a match. The host must then be on the deployment's allowlist. Anything else is refused: when the
   browser hands it over, when the workspace API stores it (`invalid`), and when the sender or the
   relay builds a request. The sender follows no redirect; a `3xx` is a permanent failure,
   `address_rejected`.
2. **The list is deployment configuration**, with this default. Each entry is either one exact host
   or `*.` and a domain, which matches a proper subdomain at any depth and never the domain itself:
   - `fcm.googleapis.com`, exact (Chrome and other Chromium browsers);
   - `updates.push.services.mozilla.com`, exact (Firefox);
   - any subdomain of `push.apple.com` (Safari; Apple asks servers that restrict endpoints to allow
     every subdomain of it, and endpoints today are `web.push.apple.com`);
   - any subdomain of `notify.windows.com` (Edge, through the Windows Push Notification Services,
     whose endpoints are regional `wns2-*` hosts).

   The retired `android.googleapis.com` (GCM) is not on it. A customer-run deployment may shorten the
   list; adding a host is a configuration change that is reviewed like any other.
3. **Where it is enforced.** One parser, `mandate_webpush::PushEndpoint`, serves the workspace API
   on `PUT /me/channels/web_push` (workspace API spec §5.7), the dispatcher before each send
   (notifications spec §5.1), and the relay (E20-8), with one shared table test. The web client
   ([#833](https://github.com/kunwarshivam/mandate/pull/833), which merges after this change)
   checks the same table before it hands a subscription over.
4. **When the list changes.** Stored addresses on a host that left the list are not sent to again.
   The next attempt is journaled `failed` with `address_rejected`, which marks the address
   `unreachable` and raises `channel_lost` to the member's other channels (notifications spec §5.6).
   The address still counts toward the member's limit until they remove it or set the same endpoint
   again, which replaces it.

## Rationale

The endpoint is the one place where a workspace sends a request to a host chosen by someone else:
the browser picks it, and a malicious page or a tampered subscription could pick any URL. An
allowlist turns the push sender into a client of four known services rather than an open
forwarder, which CP-1 already assumes. It refuses more and spends nothing.

## Alternatives considered

- **Any `https` host** (S8a's parser today). Rejected: the sender and the relay would POST to any
  address a subscription names.
- **The list fixed in code.** Rejected: a browser can move its push service, and a customer-run
  deployment may want a shorter list; configuration with a reviewed default covers both.
