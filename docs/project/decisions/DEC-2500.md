## Context

DEC-701 item 2 made `mandate-dispatcher` the process crate and left its layer to "the change that
creates it, above `mandate-journal`". DEC-704 kept it `pure = true` behind a `Journal` trait until
the process slice (D10), and DEC-707 left open an operator alert for a refused append because no
dispatcher process existed. Slice D10 is that process, run in the managed cell (E21-36's chart,
DEC-993). Today `Journal::committed` returns a `Vec`, so a store that cannot read has no way to say
so: an empty answer would read as an empty notice stream, re-open it, and re-issue every cause.

## Decision

1. **Its own binary and its own image.** `mandate-dispatcher` gains a binary target of the same
   name, as `mandate-agentd` has (E21-2). The cell runs it from its own image, `dispatcher`,
   built like the interim `mandate` image (DEC-993 item 9): the one statically linked binary on an
   empty base (`FROM scratch`), non-root, no shell and no other file. It is not a `mandate`
   subcommand: the `mandate` image is the CLI, which writes the control stream (DEC-701 item 3), and
   `deploy/cell/charts/workspace/processes.json` already gives each long-running process type its
   own image (`runtime`, `executor`, `scheduler`), keeping `mandate` for the one-off Jobs. So no
   control-stream writer is in the dispatcher's container, and no dispatcher code is in the CLI's.
   Its subcommands are `run --config <path>` and `probe live|ready`; any other argument exits 2.
2. **Layer and dependencies.** In `xtask/layers.toml` the crate becomes `pure = false` at layer 9,
   above the journal's Postgres adapter (`mandate-journal-pg`, layer 6), the vault client
   (`SecretSource`, [#1458](https://github.com/kunwarshivam/mandate/pull/1458)), and
   `mandate-telemetry` (8): the layer `mandate-agentd` holds. Its external dependencies are the
   fewest the process needs: `ring` (signing, DEC-2503), `reqwest` over rustls for the push
   services, `secrecy`, `serde_json` (the configuration file), `thiserror`, and `tokio` (the signal
   handler and the client), each already a row of `docs/dependencies.md` whose purpose text the
   code change extends. `mandate-telemetry`'s `allowed_dependents` gains `mandate-dispatcher` (its
   `ProcessType::Dispatcher` exists). Its `forbidden_internal` keeps DEC-701 item 3's list and adds
   `mandate-agentd`, and `mandate-api`, which writes the control stream (DEC-701 item 3's own
   rule). **Nothing may depend on it**: `allowed_dependents = []`. With the
   `[process_groups]` rule (`workspace_services` against `agent_process`, DEC-986), no trading
   crate can reach the dispatcher and the dispatcher reaches none, so a hung dispatcher cannot
   stall trading by any call (NT-9 at rung 1).
3. **`Journal::committed` returns a `Result`.** The trait's read is
   `fn committed(&self, stream: &StreamId) -> Result<Vec<StoredEvent>, DispatchError>`, with a
   closed `DispatchError::JournalUnavailable` that holds no input. A read that fails ends the step
   before it issues, sends, or appends anything; it is never read as an empty stream. The in-memory
   journal of the tests gains a failing mode that pins it.
4. **Lifecycle: `mandate_process::Kind::Writer`.** The process folds its inputs through
   `mandate_process::Lifecycle` with `Kind::Writer`: `StartupPassed` once its start-up checks pass
   (the configuration file parses and is closed, the vault answers, the VAPID keys load when web
   push is on, DEC-2503); `EpochTaken` when it takes the notice stream's writer epoch;
   `Replayed { position, head }` as it replays its notice stream; ready once replayed to the head.
   An append answered `Fenced` is `Fenced`: it sends nothing more and exits `fenced` (DEC-704
   item 3). SIGTERM is `DrainRequested`. A start-up check that fails, or an append the journal
   refuses as `Invalid`, is `Failed`: the process exits, and does not loop over a record it cannot
   write. The cost is stated, not hidden: the restarted dispatcher replays to the same record and
   exits again, so **push stops for the whole workspace**, every stream's notices with it, until a
   human or a hotfix intervenes. The pull channels (`web_inbox`, `cli_inbox`) keep carrying every
   notice, since their list is the journal itself, delivered when the cause commits, not
   anything the dispatcher sends (spec §1.3, §4.1), so no approval becomes ungrantable and an unanswered ask still
   times out to `skip` (NT-5). Nothing alerts on it yet (item 11). A step whose read fails, or whose append answers `Unavailable` or `Ambiguous`, ends with
   nothing more sent, and the next tick tries again; only a step whose reads succeeded is a
   `Heartbeat`, so a dispatcher that cannot read for longer than its liveness bound (60 seconds,
   the lag alert's) fails its liveness probe and is restarted.
5. **Probes over the `mandate-process` socket.** The process serves `mandate_process::probe` on a
   Unix socket in a memory-backed directory of its pod, and the chart's `exec` probes run
   `/usr/local/bin/mandate-dispatcher probe live` and `probe ready`, whose exit status is the
   answer's. No network listener: the dispatcher accepts no connection from anywhere.
6. **The drain.** On SIGTERM it starts no new send, finishes the send in flight and journals its
   outcome, and exits `drained` (`Settled`). The send in flight is one address handle's send, which
   on web push is the handle's whole fan-out (DEC-2502 item 4): its sends to the recipient's
   addresses, at most 10, start together and run concurrently, and each, its vault read included,
   has one 10-second deadline, past which it is `retryable` (`timeout` for the request,
   `provider_error` for a vault read that has not answered, DEC-2502 item 7). So the send in flight
   settles within 10 seconds of its start however many addresses it holds, and with its records
   appended a drain settles well inside `mandate_process::DRAIN_BOUND` (90 seconds); past the bound the drain is
   abandoned, not forced (`drain_incomplete`), and a send with no record is re-sent by the next
   dispatcher under the same idempotency key (at least once, NT-8). The chart's grace period is
   longer than the bound.
7. **Configuration from one file, until NT-10 and E9-2.** `run --config` reads a JSON file mounted
   read-only from the chart, holding no secret and no address: the workspace id, the subject
   streams, the audience as `(recipient, channel)` pairs (DEC-704 item 4), the app origin, the
   environment, the build digest, whether web push is on (DEC-2504's interim: off), the push-service
   allowlist, and the VAPID subject. Unknown members are refused, and a change takes effect only at
   a restart. The configured subject streams are a floor, never a filter: at start and at each step
   the process also reads the journal store's list of the workspace's agent, account, and control
   streams and reads every one, so an agent deployed after the file was written is never missed. The
   audience names recipients in DEC-2502 item 3's form only.
8. **Short reads, no shared locks.** It logs in to Postgres as its own role,
   `mandate_dispatcher` (DEC-993 item 5's one role per process type), and appends only through the
   `NoticeWriter` (DEC-704 item 1); its reads are short read-only
   transactions with a statement deadline, and it takes no lock but its own stream's writer epoch.
   Its pod has CPU and memory limits and no guaranteed share (infrastructure §3.3 reserves that for
   the executor and the scheduler).
9. **The provider message id.** For a web push the `provider_message_id` the dispatcher journals
   (DEC-729 item 1 leaves its choice to this process) is a fresh 128-bit id from the process's
   secure random source, one per attempt, as 32 lowercase hex digits. The push service's `Location`
   header, which names a resource under the subscription's endpoint, is never read into a record.
10. **Telemetry.** It exports `mandate-telemetry`'s metrics with `ProcessType::Dispatcher`: counts
    by channel, class, status, and closed reason, and the lag of its oldest unread cause. No label
    carries a recipient, an address, a host, or a push service's name (NT-2: which push service a
    member's browser uses is personal data).
11. **Open: the operator alert for a refused append** (DEC-707, "Not decided here"). The cell's
    alert path (E21-39) does not exist yet, and `mandate-alerts` has no row for a dispatcher whose
    append is refused `Invalid`. Item 4 makes that case a process exit, and push stays stopped for
    the whole workspace until a human or a hotfix intervenes, with the pull channels carrying every
    notice meanwhile. It is not yet detected: infrastructure §8.2 has no dispatcher row, so neither
    the crash loop nor the notice lag (item 10's metric) alerts anyone until E21-39 builds the alert
    path and §8.2 gains the dispatcher's lag and refused-append rows (owed, a follow-up of this
    change; spec §8). What the dispatcher should do with a record the journal will never accept
    (the poison-record policy) is also open, with DEC-707's alert, for the lane lead and E21-39
    (spec §12 item 8); nothing here adds a mechanism for it.

## Rationale

Items 1, 2, and 8 put the dispatcher where nothing in the trading path can call it, wait on it, or
share a lock with it, which is NT-9 and OPS-4 in the build graph, the image, and the database. Item
3 closes the one way a read failure could become a burst of duplicate notices. Items 4 to 6 reuse
the lifecycle, probe, and drain every long-running process already shares (DEC-994), so the
orchestrator treats the dispatcher like the scheduler: one writer of one stream, fenced by epoch.
Item 7 keeps the interim audience of DEC-704 item 4 and refuses to let a stale file hide a stream's
alerts. Items 9 and 10 keep the endpoint out of the journal and the metrics.

## Alternatives considered

- **A `mandate dispatch` subcommand in the one `mandate` image.** Rejected: the dispatcher's pod
  would carry the CLI's control-stream writer, and the CLI's graph the dispatcher's provider I/O.
  The `FROM scratch` precedent is kept: the dispatcher's image is the same shape with its own
  binary.
- **`Kind::Service`.** Rejected: the dispatcher is the single writer of its notice stream, and
  readiness must wait for its epoch and replay (§5.1 step 4).
- **Keep `committed` infallible and log the failure.** Rejected: the step could not tell an empty
  stream from a failed read.
- **Subject streams from the file alone.** Rejected: a stream missing from the file would drop
  every safety notice its owner raises, against NT-6.
- **The push service's `Location` as the message id.** Rejected: it is derived from the endpoint.
