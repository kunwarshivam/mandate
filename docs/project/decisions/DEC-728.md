# DEC-728: A relay refusal and a relayed subject that is not a role mailbox are a permanent `provider_error`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The L3 builder agent under DEC-79 (a reversible engineering decision), recording the merge coordinator's answer on [#1121](https://github.com/kunwarshivam/mandate/pull/1121) (its "Decisions needed" item 3 and minor (c)) |
| **Story or claim** | E8-14, E8-10, claim [#753](https://github.com/kunwarshivam/mandate/issues/753); [notifications spec](../../specs/notifications.md) §4.6, §5.2, §5.3 |

## Decision

1. **Every relay refusal is `permanent { provider_error }`.** When the relay answers a closed
   refusal (`mandate_push_relay::RelayError`: `invalid_relay_id`, `address_rejected`,
   `invalid_envelope`, `too_large`, `unreachable`, `invalid_authorization`, and any later one), the
   deployment journals the attempt `failed` with spec §5.2's `provider_error`. It is never
   `auth_failed` or `address_rejected`, so no address is marked `unreachable` and no `channel_lost`
   is raised, and it is `permanent`, so §5.3 does not retry that notice on that channel. A push
   service's own status, which the relay returns unchanged (DEC-724 item 6), is not a refusal and is
   not covered here.
2. **A relayed subject that is not a role mailbox is the same outcome.** When the deployment's
   configured subject fails `VapidSubject::check_relayed` (DEC-727), the dispatcher builds no header
   and sends nothing through the relay, and journals the attempt `failed` with `provider_error`.
   Spec §5.2 names no reason for a deployment's own configuration fault, and none is added.
3. **What it replaces.** DEC-724 item 4's clause that the deployment records the relay's
   `address_rejected` as §5.2's `address_rejected` is superseded by item 1. The rest of DEC-724,
   and DEC-792 item 4 for the deployment's own allowlist check before a send, are unchanged: an
   endpoint the deployment itself refuses is still `address_rejected`.

## Rationale

A relay refusal is a verdict on the deployment's request or on the relay's configuration, never on
the member's address: the deployment has already checked the endpoint against its own allowlist
(DEC-792 item 3), so a relay that refuses it is running a shorter list, which is the platform's
setting, not the member's fault. Marking the address would tell the member to replace a working
subscription. `auth_failed` would read the deployment's own header fault, which DEC-726 item 5
keeps away from the push service for exactly that reason, as the address's. Not retrying keeps a
deployment bug from sending the same refused request to the relay every 15 minutes for a day. Each
reading loses only that push, a missed interruption (NT-5) off the trade path (NT-9); the pull
channels list every notice throughout, and NT-6's attempt within 60 seconds is still made.

## Alternatives considered

- **Keep DEC-724 item 4's `address_rejected` for the relay's endpoint refusal.** Rejected: it marks
  a member's address for a list the member did not set.
- **Retry the relay's `unreachable` as a timeout.** Rejected for now: the relay has already made
  its one attempt (DEC-724 item 6), and the coordinator's answer on #1121 is that nothing is
  retried. A later decision may make `unreachable` retryable once the dispatcher's retry path
  (E8-10) can tell a relay outage from a refusal; that would send more, never less.
