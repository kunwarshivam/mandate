# DEC-728: A relay refusal for a fault in the deployment's own request, and a relayed subject that is not a role mailbox, are a permanent `provider_error`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 (UTC) |
| **Decided by** | The L3 builder agent under DEC-176 (a gap resolved by the reading that adds no risk) and DEC-79, as the merge coordinator answered on [#1121](https://github.com/kunwarshivam/mandate/pull/1121) and on #1156 |
| **Story or claim** | E8-14, E8-10, claim [#753](https://github.com/kunwarshivam/mandate/issues/753); [notifications spec](../../specs/notifications.md) §4.6, §5.2, §5.3 |

## Decision

1. **Four relay refusals are `permanent { provider_error }`.** When the relay refuses a request
   as `invalid_relay_id`, `invalid_envelope`, `too_large`, or `invalid_authorization`
   (`mandate_push_relay::RelayError`, DEC-724, DEC-726), the deployment journals the attempt
   `failed` with spec §5.2's `provider_error`. It is never `auth_failed` or `address_rejected`,
   so no address is marked `unreachable` and no `channel_lost` is raised, and it is `permanent`, so
   §5.3 does not retry that notice on that channel.
2. **A relayed subject that is not a role mailbox is the same outcome.** When the deployment's
   configured subject fails `VapidSubject::check_relayed` (DEC-727), the dispatcher builds no header
   and sends nothing through the relay, and journals the attempt `failed` with `provider_error`.
   Spec §5.2 names no reason for a deployment's own configuration fault, and none is added.
3. **Nothing is superseded.** The relay's `address_rejected` stays §5.2's permanent
   `address_rejected`, which marks the address and raises `channel_lost`, as DEC-724 item 4 and
   DEC-792 item 4 say. The relay's `unreachable`, a push service that did not answer, is a timeout:
   `retryable { timeout }`, retried on §5.3's schedule inside the class's window. A push service's
   own status, which the relay returns unchanged (DEC-724 item 6), is not a refusal and is not
   covered here.

## Rationale

Neither DEC-724, DEC-726, nor spec §5.2 and §5.3 says how the four refusals of item 1 map. Each is
a deterministic fault of the deployment's own request (its relay id, its envelope, its body, or its
header), so a retry would send the same refused request again and cannot heal it, and none is a
verdict on the member's address, so marking it would tell the member to replace a working
subscription. `auth_failed` would read the deployment's own header fault as the address's, which
DEC-726 item 5 keeps away from the push service for exactly that reason. The reading sends nothing
more and adds no risk (DEC-176): it loses only that push, a missed interruption (NT-5) off the trade
path (NT-9), the pull channels list every notice throughout, and NT-6's attempt within 60 seconds is
still made.

## Alternatives considered

- **Retry the four faults as `retryable { provider_error }`.** Rejected: the same request is
  refused again for up to 24 hours, and nothing changes between attempts.
- **Map every relay refusal, `address_rejected` and `unreachable` included, to `provider_error`.**
  Rejected: it would silence DEC-724 item 4's `channel_lost` and cut §5.3's retries of a timeout,
  which loosens both; that is not an agent's call.
