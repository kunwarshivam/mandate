## Context

Journal spec v0.26 §9.13 (DEC-780) closed `VerificationRun` with a closed list of §11's check codes
in `failure.check`. Three codes §11 already defined were left out: `held_mismatch` (v0.23,
DEC-672) and `connection_lifecycle_mismatch` and `connection_cause_mismatch` (v0.20, DEC-800). The
reference validator refused each as `non_canonical`, so a `VerificationRun` could not record those
failures.

Rule 108 requires a `platform_operator`'s `RecordsAccessed` to carry a non-null `causation_id`, the
`PlatformOperatorAction` that opened its break-glass window (§7). `append` judges one batch and
cannot see what that ID names, so nothing checked it. `PlatformOperatorAction` itself stays open
(DEC-261 item 9, Proposed), and `append` refuses it as `unknown_schema`.

The review of #1004 found that §11 listed `anchor_head_mismatch`, `intent_action_mismatch`, and
`mode_event_mismatch` under "Per-range checks", while rule 111 and the reference validator treat
them, and `anchor_self_mismatch`, as reported at an event.

## Decision

1. **The three codes join §9.13's list, each reported at an event.** Rule 111's per-event list
   gains `held_mismatch`, `connection_lifecycle_mismatch`, and `connection_cause_mismatch`, so a
   failure on any of them names a `seq` inside its range. §11 reports each at a record:
   `held_mismatch` "at the first record that breaks it" (its fail-closed case with no anchor is
   reported at the first unanchored version-2 record), `connection_lifecycle_mismatch` "at that
   record", and `connection_cause_mismatch` "at the record". None is reported for a range as a
   whole, so none belongs with `anchor_root_mismatch`, `tsa_token_invalid`,
   `segment_manifest_mismatch`, and `segment_gap`.
2. **§11 gains the control stream's check `break_glass_cause_mismatch`, and it fails closed.** A
   `platform_operator`'s `RecordsAccessed` must name, as its `causation_id`, an earlier
   `PlatformOperatorAction` on the same control stream, so of the same workspace. A cause naming a
   later event or an event of another type fails; one naming no event fails in a range that starts
   at seq 1, the full-chain run among them, and a range entered later does not judge it, as §11
   already says of a reference before the trusted start. It is reported at the read, so rule 111
   classes it per event, and §9.13's list admits it. Because `append` refuses every
   `PlatformOperatorAction` until DEC-261 item 9 is decided, **every operator read that `append`
   admits fails this check until then**, and the spec says so in §11 and rule 108. This item does
   not decide or change DEC-261 item 9: that record's members stay the founder's.
3. **§11's per-range checks are labelled by where each is reported.** The four range-wide codes are
   reported for the range with no `seq`; `anchor_head_mismatch` (at the anchored `seq`) and every
   check §11 lists by stream are reported at an event. This changes the text only: rule 111's
   behaviour and the reference validator's classes are as they were.
4. **Vectors.** The `records_access` section gains, for each of the four codes, a valid run failing
   on it with its `seq` and an invalid run naming no `seq`; four validator mutants, one per code,
   that class the code as range-wide; and `range_checks`, five control-stream chains judged by the
   reference verifier (`break_glass_failure` in `reference/journal/control.py`) and by an
   independent walk, with five verifier mutants (the actor, the type, the order, an unresolved
   cause in the full chain, and one in a tail range). The first chain's failing read is the valid
   draft `read_by_an_operator`, which stays valid at `append`. The chain where an operator read
   passes holds a `PlatformOperatorAction` body that `append` refuses today; the check reads only its
   type, ID, and `seq`. The vectors stay version 3.

## Rationale

Item 1 resolves a gap between two parts of one spec by the reading §11 already states, and it lets a
run record a failure it otherwise could not: it adds no risk. Item 2 adds a check that can only fail
records, never admit one, and its fail-closed outcome matches rules 109 and 110, which refuse an
operator's export or verification for the same reason: the break-glass approval has no journaled
form yet, so no operator read can cite an approval the journal holds. A control-stream failure is
SEV-1 and freezes mandate and deployment changes (§11); it never holds a risk exit, a protective
order, or the kill switch (`AGENTS.md` rule 13). Item 3 makes two statements of the same rule
agree.

## Alternatives considered

- Class `connection_cause_mismatch` as range-wide because it runs only in the full chain. Refused:
  §11 reports it at a record, and a `seq` locates the failure.
- Let an operator read pass while `PlatformOperatorAction` is open. Refused: that loosens rule 108's
  intent toward what the code can check, which DEC-176 leaves to the founder.
- Close `PlatformOperatorAction` with a minimal payload so the check can pass. Refused: DEC-261
  item 9 is the founder's.
- Move `anchor_head_mismatch`, `intent_action_mismatch`, and `mode_event_mismatch` under the
  per-event heading. Refused: they read beyond the one event, unlike checks 1 to 6, and the first
  failure order of §11's numbered list would change.
