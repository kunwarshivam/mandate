## Decision

1. **A pure crate that reaches only the push types.** `mandate-push-relay` sits at layer 2 and
   depends on `mandate-webpush` and `thiserror` alone. Its `forbidden_internal` list keeps the
   journal crates, the runtime, the executor, the risk gate, the approval core, the shell, the
   connectors, the paper binary and the CLI out of its graph. So it can write no control-stream
   event (NT-3), and nothing on the trade path can wait on it (NT-9). The network is behind a
   `PushService` trait and the log behind a `RelayLog` trait. Its tests use `mandate-notify`'s
   canary scan as a dev-dependency, which is why it sits above layer 1.
2. **The relay id is exactly 32 lowercase hex digits.** Spec §4.6 names `relay_id` but gives no
   form. Anything else is refused as `invalid_relay_id`, so the one field the relay logs cannot
   carry free text (CP-1). It is the relay's id for one send, never a notice id or a journal event
   id. The deployment mints it, as it mints the notice id (DEC-702).
3. **Only a class's fixed pair passes.** Spec §4.6 has the relay check that `urgency` is `high` or
   `normal`. The relay accepts only DEC-700 item 3's three pairs: `high` with 3 600 s, `high` with
   86 400 s, and `normal` with 21 600 s. Any other pair is refused as `invalid_envelope`. The relay
   does not know the class, but an envelope that is not a class's own pair could only come from a
   deadline or a bug (NT-1).
4. **The endpoint is checked as the deployment checks it, and capped.** It must pass
   `mandate_webpush::PushEndpoint::parse_allowed` against the relay's own allowlist (DEC-792,
   DEC-722; the default list unless the control plane's configuration shortens it). It must also be
   at most 2 048 octets, the workspace API's limit for a stored endpoint (workspace API spec
   §5.7). Anything else is refused as `address_rejected`, which the deployment records as spec
   §5.2's permanent
   `address_rejected` (DEC-792 item 4). **Residual:** within those 2 048 octets, an allowlisted
   endpoint's path is the deployment's choice, so a compromised deployment could carry about 2 KB
   to a push service besides the 512-octet ciphertext. CP-1 already names the endpoint as an
   exception. The threat model owns this residual, as spec §9 says for a compromised deployment.
5. **The push service receives four things.** These are the endpoint as given, the pair's
   `urgency` and TTL, and the ciphertext byte for byte. The relay id is not forwarded; it stays the
   relay's own log key. `Content-Encoding: aes128gcm` is the I/O adapter's fixed header.
6. **One attempt, and the status is returned as it came.** The relay posts once and never
   retries; retries are the dispatcher's (§5.3). A push service that does not answer is refused as
   `unreachable`. Any status, including a `3xx`, is returned to the deployment unchanged. The
   adapter follows no redirect (§4.6), and the deployment maps the status to §5.2's outcome, so
   §4.6's rule that a `3xx` is `address_rejected` still holds, applied by the dispatcher rather
   than the relay. This item tightens nothing and loosens nothing: it only places that mapping.
7. **Nothing is kept.** `relay` is a free function that takes the allowlist by shared reference
   and has no state, so no part of a request outlives the call. Each request leaves exactly one
   `LogEntry`: the relay id (when it parsed) and the closed answer. No log type can hold an
   endpoint or a ciphertext, and the request and forward types have no `Debug`.
8. **Order of checks.** The checks run in this order: relay id, endpoint, envelope, size. The
   first refusal wins, and every check runs before any post.
9. **Proposed (the founder): how a relayed push carries VAPID.** Spec §4.6 says the workspace
   deployment signs with its own application server key (RFC 8292), but the relay's request
   `{relay_id, endpoint, urgency, ttl_s, ciphertext}` has no field for the `Authorization`
   header, and CP-1 allows no other string field in `RelaySend`. Push services require VAPID for
   subscriptions made with an application server key. The options are:
   - (a) add the deployment's VAPID header to the relay request, which loosens CP-1;
   - (b) have the relay sign with a platform key, which changes §4.6's signer and the key the
     browser subscribes with, and needs a spec change.

   **Until the founder decides:** the relay forwards no `Authorization` header and the request
   gains no field. A relayed push may then be refused by the push service, which is only a missed
   interruption (NT-5). This PR's pure core does not depend on the choice.

## Rationale

Items 2 to 4 close the fields a compromised deployment could otherwise fill freely, so that what
reaches the relay is the closed shape CP-1 describes. Items 5 to 7 put "stores nothing, logs opaque
ids" (DEC-438 item 13) on the type rung rather than in review. Item 6 keeps retry policy in one
place, the dispatcher. Item 9 is a real gap between the spec's signer and its envelope. Closing it
either loosens CP-1 or changes the spec, so it goes to the founder.

## Alternatives considered

- **Any `high` or `normal` urgency with any TTL** (the spec's literal check). Rejected: a TTL taken
  from a deadline would pass, which NT-1 forbids.
- **Exactly 230 octets of ciphertext** (DEC-790 item 2's fixed body). Rejected for now: native
  push after v1 shares the relay, and the backlog's acceptance is "over 512 is refused".
- **Retrying at the relay.** Rejected: two retry policies would multiply attempts and hide the
  push service's answer from the dispatcher's record (NT-8).
- **Forwarding the relay id to the push service.** Rejected: the push service does not need it, and
  it would let the relay's log and the push service's records be joined.
