## Context

The workspace API spec says what the API serves but not how its process starts, what it listens
on, how it reports health, how it stops, or how a browser session reaches it. The identity spec
holds sessions server side behind an opaque cookie (§6.2) and verifies the managed issuer's tokens
(§6.1), but names no route that opens one. `deploy/` already fixes the binary's name, its
`--bind 127.0.0.1:8080`, and its two credentials as systemd credential files (DEC-822 item 4).
E21-31 needs each of these closed before its code.

## Decision

1. **The bind is loopback or the pod's own address.** `mandate-api-server --bind <ip>:<port>`
   refuses to start unless the address is a loopback address, or equals the address passed as
   `--pod-address` (the orchestrator's own pod IP). The unspecified addresses (`0.0.0.0`, `::`)
   and every other address are refused. The cell's one ingress is the only way in (infrastructure
   §9, DEC-822 item 2).
2. **No secret in the environment.** The process reads its settings from named, non-secret
   variables only. It refuses to start when any variable in its environment has a name containing
   `SECRET`, `PASSWORD`, `TOKEN`, or `KEY` (ASCII case-insensitive), or when the database URL
   carries a password. Its secrets are files: the session signing key is
   `$CREDENTIALS_DIRECTORY/session-signing-key` (systemd `LoadCredential=`, or a mounted secret
   file in a pod), at least 32 bytes, refused when group- or world-readable.
3. **Probes are outside `/v1` and read no data.** `GET /livez` answers 200 while the process
   serves. `GET /readyz` answers 200 when ready and 503 when not; the body is only
   `{"status": ...}`. Both are unauthenticated, as API-1 already allows the liveness probe; the
   readiness probe joins that exemption because it reads no data either. Readiness comes from the
   process lifecycle (`mandate-process`, E21-28) once it lands; until then a local predicate:
   started, not draining, and the journal answered its last check. A process that is not ready
   still serves every API-7 operation: readiness gates no risk reduction (infrastructure §3.4).
4. **Drain refuses new ordinary calls, never risk reduction.** On SIGTERM the process reports
   not ready, lets in-flight requests finish, and answers each new call that is not an API-7
   operation with `503 busy` (`effect: none`, `retryable: true`, `Retry-After`), so the client
   retries on another replica. API-7 operations are served until the process exits. It exits when
   nothing is in flight or at the drain bound, infrastructure §7.3's Proposed 90 seconds. `busy`
   is the planned code of §3.5 whose title is already "Try again"; this widens its "When" and adds
   no code.
5. **A browser session is opened by the managed issuer's access token.** `POST /v1/sessions`
   carries `{access_token}`, verified as identity spec §6.1 says (the one configured issuer, its
   published keys by `kid`, ES256 only for the managed issuer), under §3.3 item 1's `Origin` and
   `X-Mandate-Request` checks so a cross-site page cannot sign a victim in. The subject maps to a
   user principal through the subject link (item 7). The server opens a `SessionRecord` (identity
   spec §6.2) and sets the `__Host-` cookie of §3.3 item 5, whose value is an opaque session id
   and a fresh 32-byte secret, authenticated with HMAC-SHA256 under the session signing key. The
   record keeps only the secret's digest. Every answer that opens nothing is the one 401.
6. **Refresh rotates the cookie; sign-out ends it.** The record's access lifetime is identity
   spec §6.2's five minutes. `POST /v1/sessions/refresh` with the cookie and a fresh access token
   for the same subject is a granted refresh: the secret rotates and a new cookie is set. A token
   that does not verify, or names another subject, is a failed refresh that ends the session
   (`refresh_failed`). A rotated secret presented again ends it as reuse (`refresh_reuse`).
   `DELETE /v1/sessions/current` ends it (`sign_out`) and clears the cookie. Until a store in
   Postgres exists, sessions are held in the process: a restart ends every session and the user
   signs in again, which fails closed. Pause and the kill switch keep identity spec §6.4's other
   routes.
7. **The subject link is a digest, read from a file.** Identity spec §3.3 keeps IdP subjects in
   the personal-data vault. Until that store exists, the server reads a root-owned file named by
   `MANDATE_API_SUBJECT_LINKS`, one line per link: `sha256:<hex>` of the canonical
   `{"issuer","subject"}` object, a space, and the principal's ULID. The file holds no raw subject,
   and an unlinked subject is refused with the one 401.
8. **The server builds memberships from the control stream.** `authorize` reads memberships
   through `MembershipLookup`, whose implementations need `mandate-identity-seal`. The server is
   added to the seal's `allowed_dependents` and folds journal §9.12's records from the workspace's
   control stream with `MembershipFold`, uncached, for every request (identity spec ID-3). A read
   that fails is a failed membership read (`membership_unavailable`), never an empty membership.
9. **Proposed: one PR per slice.** Each slice of E21-31 lands as one PR: the tests in their own
   first commit, failing on stubs, then the implementation, with every other gate kept (the
   independent review on another model, every mutant killed, `fast` and `full` green). That is
   DEC-921's form, which DEC-921 item 3 limits to R0 rows; the lane's dispatch asked for it, as
   DEC-968 item 9 recorded for E21-2. Until the founder decides, a slice that breaks the 400-line
   limit of ES-13 is split into stacked PRs.

## Rationale

Each item takes the reading that adds no risk. Items 1 and 2 turn the deploy unit's comments into
refusals the process makes itself, so a wrong unit file fails at start rather than exposing a port
or a secret. Item 3 keeps the probes out of the authenticated surface and states that readiness
never gates risk reduction. Item 4 finishes in-flight work and keeps Stop working through an
upgrade (API-7, infrastructure §3.4 and §7.3). Items 5 and 6 map identity spec §6.2's record onto
the access token the web app already holds, with no token in browser storage and no bearer token on
any other route (§3.3 item 2). Item 7 keeps personal data out of the repository, the journal, and
the environment. Item 8 gives the API the uncached membership read ID-3 requires.

## Alternatives considered

- **A new `draining` problem code.** It would be clearer in logs, but a closed code needs a schema,
  contract, and client change, and `busy` already says what the client must do: try again.
- **A bearer access token on every call.** Simpler, but §3.3 item 2 refuses plain bearer tokens,
  and the browser would hold a token where a page script could read it.
- **Sessions in Postgres now.** Needed for two replicas; the demo cell runs one API process, and a
  lost session only asks the user to sign in again. The store moves to Postgres in its own slice.
- **Binding `0.0.0.0` behind a firewall.** It relies on a rule outside the process; the bind check
  holds wherever the process runs.
