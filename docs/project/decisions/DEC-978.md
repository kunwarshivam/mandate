## Context

The workspace API spec says what the API serves but not how its process starts, what it listens
on, how it reports health, how it stops, or how a browser session reaches it. The identity spec
holds sessions server side behind an opaque cookie (§6.2) and verifies the managed issuer's tokens
(§6.1), but names no route that opens one. `deploy/` already fixes the binary's name, its
`--bind 127.0.0.1:8080`, and its credentials as systemd credential files (DEC-822 item 4). E21-31
needs each of these closed before its code. The first draft was reviewed by an agent on another
model; this version takes its findings (an IdP outage that would have expired pause and the kill
switch, probes on the public listener, login CSRF, unbounded sessions).

## Decision

1. **Both listeners are loopback or the pod's own address.** `--bind` (the API) and `--probe-bind`
   (the probes) each refuse the start unless loopback or equal to `--pod-address`. The unspecified
   addresses and every other address are refused. The ingress routes only the API listener
   (infrastructure §9, DEC-822 item 2).
2. **A guard against secrets in the environment.** A variable whose name contains `SECRET`,
   `PASSWORD`, `TOKEN`, or `KEY` (ASCII case-insensitive), or a database URL carrying a password,
   refuses the start. It reads names, not values, so it is a guard against the common mistake, not
   a proof. Secrets are files: the session signing key is `$CREDENTIALS_DIRECTORY/session-signing-key`,
   at least 32 bytes, refused when group- or world-readable. Postgres is reached over its local
   socket by peer authentication (`deploy/api.env.example`), or with a credential file.
3. **Probes on their own listener, reading no data.** `GET /livez` and `GET /readyz` answer only on
   `--probe-bind`, so API-1's surface is unchanged: the API listener has no unauthenticated route
   but the preflight, and `POST /v1/sessions`, whose credential is the token it carries; API-1's
   row now says so, with the session routes' CSRF check first. Readiness
   comes from `mandate-process` (E21-28) once it lands; until then the process is ready once
   serving and not draining. A process that is not ready still serves every API-7 operation.
4. **Drain refuses new ordinary calls, never risk reduction.** On SIGTERM the process reports not
   ready, lets in-flight requests finish, and answers each new authenticated call that is not an
   API-7 operation with `503 busy` (`effect: none`, `retryable: true`, `Retry-After`); an
   unauthenticated call gets the one 401 first. API-7 operations are served until the process
   exits, when nothing is in flight or at its drain bound, Proposed 90 seconds by analogy with
   infrastructure §7.3 (which governs agent processes). `busy` is §3.5's planned code whose title
   is already "Try again"; this widens its "When" and adds no code.
5. **A browser session is opened by the managed issuer's access token.** `POST /v1/sessions`
   carries `{access_token}`, which the web app's sign-in client already holds on the app origin
   (DEC-211); the API stores no token of its own. The route is browser-only: an `Origin` other than
   the app origin, a missing `Origin`, or a missing `X-Mandate-Request` is refused 403 before the
   token is read. The token is verified as identity spec §6.1 says, and the subject maps to a user
   principal through the subject link (item 7); any failure is the one 401. The session record uses
   §6.2's business limits (idle 1 hour, absolute 12 hours), the strictest, for every session until
   the organization's kind is read from its store. The `__Host-` cookie of §3.3 item 5 holds an
   opaque session id and a fresh 32-byte secret, authenticated with HMAC-SHA256 under the session
   signing key; the record keeps only the secret's digest. A cookie presented at open ends that
   earlier session and is never reused. At most 16 sessions per principal: a 17th ends the oldest.
6. **Refresh maps onto identity spec §6.4 route 1.** The record's access lifetime is five minutes.
   `POST /v1/sessions/refresh` (cookie, `Origin`, `X-Mandate-Request`) maps its body onto
   `ProviderAnswer`: a token that verifies for the session's subject is `Granted` and rotates the
   secret; `{access_token: null}`, which the web app sends when its sign-in client cannot reach the
   provider, or the server failing to fetch the issuer's keys, is `Unreachable`, so the session
   keeps pause and the kill switch until its absolute lifetime; a token that fails verification or
   names another subject is a failed refresh, which ends it; a rotated secret presented again ends
   it as reuse. A caller can only narrow its own session with `null`: a user the provider has since
   deprovisioned could claim an outage and keep pause and the kill switch until the absolute
   lifetime, which adds no risk. A pause or kill switch on a full session whose access lapsed with
   no refresh is served after the server records an outage refresh itself, so risk reduction never
   waits on the web app (API-7); any other call gets the one 401. A session's full reach never
   outlasts the last token it was given by more than five minutes, so a leaked access token grants
   at most its own lifetime plus five minutes. `DELETE /v1/sessions/current` ends it. Until a Postgres
   store exists, sessions live in the process, the API runs as one replica, and a restart (a deploy
   included) ends every session: the user signs in again, and with the provider down, pause and the
   kill switch remain through the host CLI (route 3) until route 2's reduction-only sessions are
   served.
7. **The subject link is a digest, read from a file, for the demo cell's paper workspace only.**
   Identity spec §3.3 keeps IdP subjects in the personal-data vault. Until that store serves links,
   the server reads the file named by `MANDATE_API_SUBJECT_LINKS` at each sign-in and refresh,
   refused when group- or world-writable or not owned by the process's user or root: one line per
   link, `sha256:<hex>` of the canonical `{"issuer","subject"}` object, a space, and the principal's
   ULID. It holds no raw subject; a removed line takes effect at the next sign-in or refresh. It is
   a fourth file beside DEC-822 item 4's three secrets, and is not a secret: it maps opaque digests
   to opaque ids. Whether a hashed subject kept in a host file is acceptable beyond this interim,
   paper-only demo scope is the founder's compliance question; the scope ends when the
   personal-data vault serves links.
8. **Memberships come from the control stream.** `authorize` reads memberships through
   `MembershipLookup`, whose implementations need `mandate-identity-seal`. The server joins the
   seal's `allowed_dependents`, a change the code PR carries under the safety-critical review, and
   folds journal §9.12's records from the workspace's control stream with `MembershipFold`,
   uncached, for every request (identity spec ID-3). The deployment hosts one workspace, named
   with its organization in its settings (`MANDATE_API_WORKSPACE`, `MANDATE_API_ORG`), since the
   §9.12 records name neither; any other workspace in a path is absent. A failed read is a failed membership read
   (`membership_unavailable`), never an empty membership.
9. **The read models are DEC-979's.**
10. **Proposed: sign-in is not journaled until the journal registers it.** Identity spec §6.2
    commits `SessionOpened` at every sign-in, which drives the new-device notice (ID-14). The
    journal registers neither `SessionOpened` nor `SessionRevoked` today. Until the founder decides,
    the server serves sessions for the demo cell's paper workspace and journals nothing for them,
    and no new-device notice is sent; the journal registration and the writes are a backlog row
    under E9-7. The conservative alternative, serving no session until they are journaled, would
    leave the web app unable to reach the API for the demo.
11. **One PR per slice, under DEC-990 item 3.** Each slice of E21-31 lands as one PR: the tests in
    their own first commit, failing on stubs, then the implementation, with every other gate kept
    (the independent review on another model, every mutant killed, `fast` and `full` green). DEC-990
    item 3 (the managed-cells plan, #1431) extends DEC-921's form to the managed-cell and demo
    lanes. A slice over ES-13's 400 lines is split into stacked PRs.

## Rationale

Each Accepted item takes the reading that adds no risk. Items 1 and 2 turn the deploy unit's
comments into refusals the process makes itself. Item 3 keeps the probes off the authenticated
surface. Item 4 finishes in-flight work and keeps Stop working through an upgrade (API-7). Items 5
and 6 map identity spec §6.2's record onto the token the web app already holds, keep route 1's
outage reach so an IdP outage never takes pause or the kill switch away, and bound a leaked token
to its own lifetime. Item 7 keeps raw subjects out of the repository, the journal, and the
environment. Item 8 gives the API the uncached membership read ID-3 requires.

## Alternatives considered

- **A new `draining` problem code.** Clearer in logs, but a closed code needs a schema, contract,
  and client change, and `busy` already says what the client must do.
- **A bearer access token on every call.** §3.3 item 2 refuses plain bearer tokens.
- **The server refreshing with the provider itself.** It would need the provider's refresh token,
  which the web app's sign-in client holds; moving it would put a long-lived credential in the API.
- **Requiring a freshly issued token (`iat` within a minute).** `mandate-authn` does not read
  `iat`; item 6 already bounds a session's full reach to the last token's lifetime.
- **Sessions in Postgres now.** Needed for two replicas; the demo cell runs one, and a lost session
  only asks the user to sign in again. The store moves to Postgres in its own slice.
