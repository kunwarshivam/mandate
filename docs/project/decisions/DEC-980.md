# DEC-980: Workspace services and agent processes meet only in the journal, checked by the layers

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | `claude-code` (builder of claim [#1437](https://github.com/kunwarshivam/mandate/issues/1437)), under DEC-79 (reversible engineering) and DEC-176 (it only adds a refusal) |
| **Story or claim** | E21-42 (lane M1 of the managed-cells plan, DEC-967); claim #1437; infrastructure design §3.1; journal spec §2; DEC-17 |

## Context

E21-42 asks that workspace services and an agent's processes meet only in the journal, so the API,
the deployment manager, the approval service or `cp-agent` can never act on a runtime, an executor
or the scheduler behind the journal's back. Until now that held by convention and by a few
`forbidden_internal` lists (the CLI's and the dispatcher's), each written for its own reason. This
decision puts the rule on the "checked" rung for the crates that exist now.

## Decision

1. **Two process groups in `xtask/layers.toml`.** A `[process_groups]` table names the
   `workspace_services` crates and the `agent_process` crates. `cargo xtask layers` (part of
   `cargo xtask ci fast`'s lint) refuses any crate of one group that reaches a crate of the other,
   directly or through any chain of path dependencies of any kind (normal, dev and build), with
   the message "workspace services and agent processes meet only in the journal". Dev-dependencies
   count, as they do for `forbidden_internal` (DEC-525): a test that needs both sides belongs in a
   tool or harness crate, which is in neither group.
2. **The groups today.**
   - `workspace_services`: `mandate-api` (the workspace API contract), `mandate-audit` (the audit
     reads the API serves), `mandate-cli` (Phase 1's workspace control services, infrastructure
     design §3.1), `mandate-dispatcher` (the notification process), and the planned
     `mandate-cp-agent` (control-plane design §3, CP-4) and `mandate-cp-site` (the control
     services' handler behind `cp-agent`'s port, which appends its records), both lane G1's.
     The global control-plane service, `mandate-cp`, runs outside every workspace deployment, so
     it is in neither group; lane G1 keeps it from agent processes and journal writers with its
     own `forbidden_internal` list.
   - `agent_process`: `mandate-agentd` (the long-running agent process, DEC-968), `mandate-shell`
     (the process shell that hosts the runtime and executor stages), `mandate-paper` (the runner),
     `mandate-executor`, the connectors `mandate-alpaca` and `mandate-robinhood`, and
     `mandate-mcp` (the MCP client only the connectors use).
3. **Shared crates are in neither group.** The journal and its stores, the pure cores (domain,
   accounting, risk, spec, builder, approval, identity, notify), connections, artifacts, the vault,
   market data, and two pure decision libraries: `mandate-runtime` and `mandate-modelhost`. Both
   hold functions over values, no loop, no clock and no I/O, so linking them gives a service no
   channel to a running agent process; what runs them (`mandate-shell`, `mandate-agentd`,
   `mandate-paper`) is in the agent group. The CLI uses `mandate_modelhost::content()` to register a
   model's content hash (DEC-525), and the model host's output type lives in `mandate-runtime`, so
   putting either in the agent group would refuse that existing, intended dependency. Tool and
   harness crates (`xtask`, `mandate-refcases`, `mandate-rh-sim`, `mandate-shell-rh-sim`,
   `mandate-identity-testkit`) are in neither group.
4. **Every name is checked.** A group name that is neither a workspace member nor in `planned` is a
   problem, so a typo leaves nothing unguarded; a crate in both groups is a problem. A new crate
   that is a workspace service or an agent process joins its list in the change that creates it
   (the deployment manager, the approval service, the scheduler, the data service when lane M2
   decides its side; `mandate-cp-agent` and `mandate-cp-site` leave `planned` when they are created).
5. **The channels that remain** are listed in infrastructure design §3.1: the journal, the
   host-local market-data channel (runtimes and executors only), and the orchestrator's probes.
6. **Deferred, and why.** E21-42's other criteria need pieces other lanes build: the chart's
   default-deny `NetworkPolicy` showing no route from a workspace-services pod to an agent-process
   pod waits on K1's chart (E21-36); the fault-injection test that drops every `LISTEN`/`NOTIFY`
   wake-up and still delivers each owner command, a kill switch included, by tailing waits on the
   long-running processes (E21-2 and the process lanes). Until then the story is not done.

## Rationale

A crate-graph rule is the highest rung that can hold this today (AGENTS.md trust ladder): two
processes can only call each other in-process if one links the other's code, and the closure the
layers check already computes (DEC-525) sees every chain. Making the groups data keeps the rule
one table that a new crate's author edits, beside the layer it already has to declare.

## Alternatives considered

- **More `forbidden_internal` lists, one per service crate.** Each list would have to name every
  agent-process crate and be kept in step as crates are added; a missed name is silent. One pair
  of groups states the rule once.
- **Put `mandate-runtime` in the agent group.** Stricter, but it refuses the CLI's model
  registration through the model host today, and the runtime crate holds no process loop. If a
  loop ever lands in it, it moves to the agent group and the CLI's dependency moves to a shared
  crate first.
- **Leave the CLI out of the workspace group as a founder-only tool.** It is the control services
  in Phase 1 (infrastructure design §3.1); it already cannot reach an order path (DEC-525), and the
  group adds the executor, the connectors and the agent process to what it can never reach.
