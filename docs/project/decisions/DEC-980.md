# DEC-980: Metrics through the OpenTelemetry API with a Prometheus pull exporter, a closed catalog, and a linted scrape

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-17 (UTC) |
| **Decided by** | The agent, under DEC-79 and DEC-176 (reversible engineering choices); the dependency kind was pre-approved by the founder as D-2 (DEC-990) |
| **Story or claim** | E21-3, lane O1 of the [managed-cells plan](../tasks/managed-cells.md); claim #1440 |

## Decision

1. **A new crate, `mandate-telemetry`, not safety-critical and not a core crate.** It sits at layer
   8 with no workspace dependency. Its `allowed_dependents` in `xtask/layers.toml` names only the
   process binaries that host a cycle (`mandate-agentd` today; `mandate-process` or the daemon
   crates of lane P are added when they take it), so no core crate can record or read a metric:
   this is OPS-11's layering check. `opentelemetry`, `opentelemetry_sdk`,
   `opentelemetry-prometheus` and `prometheus` join `impure_crates`, so no pure crate can take
   them directly either.
2. **The D-2 rows** (DEC-990): `opentelemetry` and `opentelemetry_sdk` `=0.33.0` with only the
   `metrics` feature, `opentelemetry-prometheus` `=0.33.0` without default features, and
   `prometheus` `=0.14.0` without default features, so no protobuf crate is built. 0.33.1 was
   released 2026-10-09, under two weeks ago, so 0.33.0 (2026-09-18) is pinned. Two crates are new
   to the lockfile besides the four: `futures-macro` and `lazy_static`.
3. **The pull endpoint is written on `std::net`, not on an HTTP server crate.** `GET /metrics`
   answers the exposition text; anything else is `404 not_found`. One thread, a request line
   read to at most 1024 bytes, and one second for a scraper's read and write, as
   `mandate-agentd`'s health listener does. No D-1 crate is needed for it, and nothing in it
   connects outward, so it runs air-gapped with no collector (design §8.1).
4. **The metric set is closed and typed.** A `Metric` has private fields and is built only in
   `catalog.rs`; `CATALOG` is every metric. Label keys are the six of design §8.1 (`workspace`,
   `agent`, `account_ref`, `process_type`, `reason_code`, `release`), each taking only its own
   value type: an opaque ID (1 to 64 of `[a-z0-9_]`, starting with a letter, DEC-710 item 4's
   shape), a `ProcessType`, a `ReasonCode` (only `&'static str`, so no runtime value becomes
   one), or a `Release` (never a bare number). Every value a metric carries is a count or a 0 or 1
   state; a duration kind is added with the first metric that needs one.
5. **The label lint is two checks, both run in CI.** `lint::catalog` checks each metric's name
   (`mandate_` and `[a-z0-9_]`), its suffix against its kind, its help text, and a list of
   forbidden words (order details, positions, money, mandate content, people, secrets);
   `lint::exposition` checks a scrape line by line against the catalog. Every scrape is linted
   before it is served, and one the lint finds anything in is answered
   `503 telemetry_unavailable`, never sent. A record whose labels are not its metric's declared
   keys, or offered to a metric of another kind, is dropped and counted in
   `mandate_telemetry_refused_total` by reason.
6. **Telemetry failing changes nothing** (OPS-11). Every record returns nothing and cannot fail.
   `Metrics::off` records and serves nothing, and a process whose metrics cannot be built runs
   with it. An exporter that cannot bind or start its thread is an error the process carries on
   past. The process's announcement lines ignore their own write errors.
7. **`mandate-agentd` counts its host's calls.** `Instrumented` wraps the `Host`, calls through
   unchanged, and after each call returns counts it by outcome (`completed`, `failed`) in
   `mandate_process_reconciliations_total`, `mandate_process_cycles_total` and
   `mandate_process_settles_total`, labeled `process_type="agent_process"`. The binary serves the
   exporter on an ephemeral loopback port and prints `metrics <addr>` after `health <addr>`.
   Binding to the pod address for the cell's Prometheus is the chart's choice (E21-36, E21-39).
8. **Disclosed limit.** The release profile aborts on panic (ES-09), so a panic inside the
   OpenTelemetry or Prometheus crates on the exporter thread would end the process, which then
   recovers from the journal as after any crash (design §3.4). The crate's own code is under the
   same no-panic lints as the trading paths, and its thread is started through
   `thread::Builder`, whose failure is an error rather than a panic.

## Rationale

Design §8.1 and ES-18 already chose the OpenTelemetry API with a Prometheus pull exporter, so the
choice here is how to keep it from leaking strategy and from touching a decision. Making the
catalog and the label keys unrepresentable outside their set (the trust ladder's first rung)
leaves the lint to check what types cannot: the words in names and help text, and the bytes that
actually leave. Linting every scrape before it is served means a defect in the exporter crates,
such as an added scope label or `target_info`, is refused rather than sent. Recording after the
call returns, through a wrapper, keeps the decision cycle's code free of telemetry.

## Alternatives considered

- **The `prometheus` or `prometheus-client` crate alone, without OpenTelemetry:** fewer crates,
  but ES-18 names the OpenTelemetry API so that OTLP push (M8) is an exporter change, not a
  rewrite.
- **Serving `/metrics` from an HTTP server crate (D-1):** no other part of this lane needs one,
  and a GET-only endpoint is about forty lines on `std::net`.
- **A label allowlist checked only in a test over the registry:** catches what tests record, not
  what production records; the typed labels and the served-scrape lint cover both.
- **Making `mandate-telemetry` safety-critical:** the plan names it not a core crate; what is
  safety-critical is that it cannot reach a decision, which the layering rule holds.
