## Context

E6-15 folds the account stream's risk state into the executor. Mandate spec §5.2 lists
`MarkUpdated` as a risk input, and `mandate_spec::risk::Input::Mark { bid, sane }`, stepped with the
session it arrived in (`Step::session`), is what the fold takes. Journal spec §9's `MarkUpdated`
is registered at version 1 only (`instrument_id`, `price`, `source`, `feed`, `risk_clock`), which
carries none of the three: no verdict on trading spec §8.2's checks, a `price` whose meaning depends
on `source`, and no session. A fold reading version 1 would have to re-judge a quote the journal does
not hold, or derive the session from a trading calendar the record does not name; neither replays
from the journal alone.

## Invariants first

- A mark updates E only when the record itself says it is sane (mandate spec §5.2).
- Replaying the account stream gives the same risk state, from the journal alone.
- A record written before this change is never read in a way that adds risk: no mark is sane
  unless a check judged it.
- Nothing here holds an exit, a protective order, or a kill switch (`AGENTS.md` rule 13).

## Decision

1. **`MarkUpdated` version 2** is version 1's members, then `bid` (`decimal?`), `sane` (`boolean`),
   and `session` (`overnight`, `pre_market`, `regular`, `after_hours`, `crypto`), with `risk_clock`
   last. Nothing else is added.
   - `bid` is the quote's bid. Trading spec §8.2 makes the risk mark the bid for a long and the ask
     for a short, and v1 sells no short (`AGENTS.md` rule 12), so the bid is the risk mark and no
     `ask` is recorded. It is `null` only for a quote with no bid, which is never sane.
   - `sane` is whether the quote met every condition §8.2 sets on a risk mark from a quote:
     0 < bid ≤ ask, the spread within the data profile's limit, and the quote fresher than the
     profile's staleness threshold at `risk_clock`. Freshness is part of the verdict, the tighter of
     the two readings of §8.2's row: a stale quote judged sane would update E from an old price and
     restart the staleness count.
   - `session` is recorded because the fold's step carries it and §5.2 makes it decide whether an
     equity's mark updates E. Deriving it at replay needs a trading calendar that `MarkUpdated`, which
     requires no `config_refs`, does not name, and a quote stamped just before a session boundary
     and folded at the next whole-second tick could be placed either side. The writer places it at
     `risk_clock`, by its calendar, and replay reads it back.
   - `price`, `source`, and `feed` stay as version 1 has them. The runtime and the account's
     reporting mark read `price`; the risk fold does not.
2. **Rule 244** (the next after §9.29's 243): at version 2, when `sane` is true, `bid` is non-null
   and greater than 0 (`payload.bid`), since §8.2's checks require 0 < bid. No other rule is added:
   the journal cannot see the ask, the data profile, or the instrument's asset class, so no rule
   ties `bid` to `price`, `sane` to `session`, or `session` to the instrument. A mark that is not
   sane may carry any bid, or none, because the fold reads `bid` only from a sane mark.
3. **A version-1 `MarkUpdated` is still accepted**, by `append` and by verification, and the risk
   fold reads it as **no verdict**: it is not a risk input, the fold applies nothing from it, and it
   is never read as sane. So E is not updated from it, and the instrument's staleness keeps counting
   from its last sane version-2 mark, until `stale_mark` holds openings and increases in that
   instrument (mandate spec §5.2). Reading it as sane would update E from a price no check judged,
   which loosens §5.2. No verdict was chosen over unreadable (DEC-2301 item 3) because a version-1
   mark is a well-formed record the stream legitimately holds: making it unreadable would hold
   every opening on any stream that holds an old mark, while no verdict already fails closed, per
   instrument, through staleness. Whether the fold settles time at it changes no result, as at a
   tick (MI-13).
4. **Who writes which version.** Today the only writer of `MarkUpdated` is the shell's paper path,
   `mandate-shell`'s `tracer.rs` (`mark`), which writes version 1 as the executor with the IEX
   quote's bid as `price` (DEC-943 item 1). `mandate-executor` writes none, and its fold applies
   nothing from one (`fold.rs`). The executor's mark path writes version 2 from the E6-15 slice that
   builds it, once `mandate-journal` registers it; until then version 1 continues, and `append`
   refuses a version-2 draft as `unknown_schema`.

## Consequences

- Journal spec v0.63 adds §9.30, rule 244, and the catalogue row's version 2;
  `reference/journal/marks.py` adds the `risk_marks` vectors (both base drafts, the invalid and
  valid drafts, and the fold's reading of each), with an independent oracle and seeded bugs, and
  `fixtures/refcases/journal.json` is regenerated.
- `mandate-journal` registers version 2 in a later tests-first pair (E6-15), and is unchanged here:
  the spec guard keeps specs and code apart.
- E6-15's slice B2 reads version 2 into `Input::Mark { bid, sane }` with `Step::session`, and reads
  version 1 as no verdict.
- Journal spec v0.63 and rule 244 renumber at merge if another change takes them first.

## Rationale

The record carries what the fold reads, so the risk state replays from the journal alone, and the
verdict that moves E is the one the writer journaled, not one recomputed later from data the
journal never held. A new version, rather than an edit, keeps every record already written
replaying as it always has (§8).

## Alternatives considered

- **Read version 1's `price` as a sane bid.** That was rejected: it would let a price no check
  judged update E and restart staleness, which loosens §5.2.
- **Read a version-1 mark as unreadable risk state.** That was rejected (item 3): it holds every
  opening on any stream with an old mark, where staleness already holds the one instrument.
- **Read a version-1 mark as not sane.** That restricts a held instrument at once on any old mark,
  though nothing judged the quote to have failed; staleness reaches the same hold without claiming
  a verdict the record does not hold.
- **Derive the session from the trading calendar at replay.** That was rejected (item 1): the record
  names no calendar, so replay would depend on configuration outside the journal.
- **Record the ask and the data profile's limits and let the journal judge sanity.** That was
  rejected as scope beyond what §5.2's fold reads; the verdict is the writer's, as §8.2's checks are.
