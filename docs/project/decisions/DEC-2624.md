## Context

The token-exchange process writes an Alpaca OAuth connection's token to the vault, and the
connection's executor reads it through its lease (`SecretPath::Token`, KV
`connections/{connection_id}/token`). The two are different processes, built by different lanes,
and nothing fixed what the bytes are. Lane LV had planned an API key's `{key_id, secret}`; OAuth
yields a bearer token. Alpaca's token response is `access_token`, `token_type`, and `scope`, with
no expiry and no refresh token documented (U-A3).

## Decision

1. **The bytes.** Exactly the canonical JSON (journal spec §4)
   `{"access_token":"<token>","format":1,"scope":["data","trading"],"token_type":"bearer"}`:
   - `access_token`: Alpaca's token as issued, 1 to 4,096 bytes from `!` to `~`, none of them `"`
     or `\`, so it needs no escape and the entry has one byte form;
   - `format`: the integer `1`;
   - `scope`: the granted scopes, sorted, each once, exactly `["data","trading"]`, which
     `grant::check_scope` accepted before the write, so an over- or under-scoped grant is never
     stored (CN-2);
   - `token_type`: exactly `bearer`. The exchange accepts only Alpaca's `bearer`, as it does today.
2. **Writing and reading.** `mandate_connections::token_entry::encode` writes it and refuses a token
   outside the form; `decode` reads it and refuses any other bytes, whitespace, member order,
   escapes, an unknown or missing member, another format, scope, or token type included, as
   `token_entry_invalid`, which names nothing of the bytes. Decoding compares the bytes with the
   form around the token, so nothing but the token is copied out, and only into a `SecretString`
   (OPS-1). The token-exchange process is the only writer (`exchange-{connection_id}` may write
   only that path); the executor decodes it, and an entry it cannot decode is a connection it
   cannot use, never one it guesses at (`AGENTS.md` rule 3).
3. **No expiry.** No member records an expiry or a refresh token while U-A3 is open: §5.4's
   reading holds, the token is valid until a call fails authorization. If Alpaca documents a
   lifetime, the entry gains it as format 2, never as an optional member of format 1.
4. **Order.** The token is in the vault before the executor for the pending connection starts, so
   it is there before any `ConnectionChecked` for the connection can exist; E10-13 slice 6 tests
   that order.

## Rationale

One byte form makes "refused if not canonical" a comparison, not a parser's judgment, and keeps
every copy of the token inside a secret type. Excluding `"` and `\` costs nothing for a bearer
token's alphabet and removes escaping, the one way two byte forms could mean the same token.

## Alternatives considered

- **Parse with `mandate-canon` and check the canonical re-encoding.** Equally strict, but the
  parser copies the token into plain strings that are not zeroized.
- **Store the token's bytes alone, with the scopes beside them in the record.** The executor could
  not then check that the token it reads is the one granted the scopes CN-2 requires.
- **LV's `{key_id, secret}`.** That is an API key's shape; an OAuth connection has no key id.
