## Context

Workspace API §3.6 specifies three passkey routes, the registration challenge, the enrolment, and
the list, and each reads the member's passkeys from the control stream. Building them left four
things the text did not say:

- which fold the three read, now that `mandate_passkey::credentials::CredentialFold` has two views:
  `passkeys`, which refuses a member whose records break stream rule 251 or 254, and `held`, route
  2's view, which never refuses ([DEC-2121](DEC-2121.md), with rule 254 from DEC-2323);
- what the routes answer when that fold refuses the member;
- what instant the list's `enrolled_at` is;
- when a session was "opened", for the 300 s a first enrolment allows, once a refresh has renewed it.

## Decision

1. **One fold.** All three routes read `CredentialFold::passkeys` for the session's member. The
   list serves its passkeys in enrolment order. The registration challenge's `exclude` is their
   ids, and its `step_up_needed` is true when there is at least one. A passkey still in its
   cool-off counts, as [DEC-2108](DEC-2108.md) item 5's third bullet already reads it: such a
   member enrols another only with step-up, which `step_up_missing` refuses until a cool-off ends.
2. **A broken fold is refused.** When `passkeys` refuses the member (a record of theirs breaks
   rule 251 or 254), each of the three routes answers `journal_unavailable`, as it does for a
   control stream it cannot read. None serves a list, an exclusion, or an enrolment from records it
   does not trust. Route 2's opening (workspace API §4.10) reads `held`, never refuses, and is
   unchanged (`AGENTS.md` rule 13).
3. **`enrolled_at` is the row's `recorded_at`.** It is the instant the journal committed the
   `CredentialEnrolled`, as this API's other reads date a record (the orders read's `submitted_at` is
   the first `OrderSubmitted`'s `recorded_at`), not the writer's `event_time`.
4. **"Opened" is the sign-in.** A session is opened at the sign-in that opened it (identity spec
   §6). A refresh renews its tokens and does not reopen it, so the 300 s in which a member with no
   passkey may ask for a registration challenge and enrol count from that sign-in. A member past
   them signs in again, as DEC-2115 item 2 says.

## Rationale

The three routes describe one set of passkeys to one member, so they read it once and the same
way. Fold disagreement would let `exclude` miss a passkey the list shows, or let `step_up_needed`
say false while the enrolment demands step-up. A broken fold is a journal the server cannot
trust, so it answers as it does for one it cannot read, and it fails closed (`AGENTS.md` rule 3).
Nothing the three routes do reduces risk, so refusing them costs nothing rule 13 protects. Dating
by `recorded_at` keeps every read on the journal's own clock. Counting from the sign-in is the
stricter reading of "a fresh full session": a silent refresh is not the member's presence.

## Alternatives considered

- **Serve the list and `exclude` from `held`.** Rejected: it would show a member passkeys their
  step-up cannot use, and invite an enrolment the fold then refuses.
- **A new error code for a broken fold.** Rejected: DEC-2115 item 2 adds no code to these routes,
  and the client's remedy is the same as for an unreadable stream, to try later while an operator
  looks. `journal_unavailable`'s `retryable: true` is accurate for that: the stream is repaired
  by an operator, not by the member.
- **Count the 300 s from the last refresh.** Rejected: a refresh proves the provider still grants
  the subject, not that the member is at the keyboard.

## Consequences

- `mandate_passkey::credentials::Enrolment` gains the row's `recorded_at`, or the API server
  carries it beside the fold, so the list can date each passkey.
- The API server keeps each session's sign-in instant, which a refresh leaves unchanged.
- The S3.3 tests pin each item: one fold for the three routes, `journal_unavailable` on a broken
  member, `enrolled_at` from `recorded_at`, and a refreshed session past 300 s still refused.
