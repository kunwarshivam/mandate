## Context

Cell #1 runs the existing chart (E21-36) on k3s on two DigitalOcean droplets in `nyc3` (DEC-995),
for the 2026-10-26 demo, paper and demo data only. The founder buys the droplets once every C1 drill
has passed on `main` (DEC-990 item 2); agents never get account or host access (DEC-822) and create
no cloud resource. The lane brief asks for everything else: cloud-init for both nodes, k3s pinned,
the chart installed with hosted values, private GHCR images pulled with a read token held in the
cluster, ingress only through Cloudflare Tunnel with Access in front of the API's hostname, the
firewall in code, the journal's cold segments bound for R2, a dry run that prints every call, a
local proof, and a runbook with no secret in it.

## Decision

1. **`deploy/hosted/cell1.py` is the one scripted run**, Python's standard library only, run by
   the founder from their own machine in five steps (`cloudflare`, `droplets`, `nodes`, `cluster`,
   `check`, or `all`). Every step prints each doctl, cloudflared, ssh, kubectl, helm and curl
   command and each Cloudflare API request before it runs; `--dry-run` prints them all and calls
   nothing. Each step is idempotent: it lists before it creates. Settings are `cell1.json` and
   `firewall.json`; secrets are only ever file paths, mode 0600, read into memory and handed on a
   process's stdin or in a request header. Any command line or printed line that would carry a
   secret value is refused before it runs. doctl uses the founder's own `doctl auth init` context,
   which the program never reads.
2. **No inbound port from the internet, SSH included.** The cloud firewall, applied by tag before
   the first droplet exists, admits only the cell's own droplets (k3s, the WireGuard pod network,
   SSH from cell1-a to cell1-b); outbound to the internet is by port only (443, 80, 53, 123, 7844).
   The brief allowed "SSH limited to a key"; DEC-995 item 5 says "never an open SSH or API port".
   Taking DEC-995's reading only tightens the rule and adds no risk, so it is recorded here under
   DEC-176.
3. **The founder reaches the cell through an ops tunnel behind Access.** cell1-a runs a second,
   host-level tunnel, `cell1-ops` (cloudflared as a hardened systemd unit, its token a systemd
   credential), routing `ssh-cell1.<zone>` to `ssh://localhost:22` and `kube-cell1.<zone>` to
   `tcp://localhost:6443`, each behind its own Access application. SSH takes keys only, for the
   admin user `cell1_admin` only, never root; cell1-b is reached by `ProxyJump` over the VPC.
   kubectl and helm run on the founder's machine through `cloudflared access tcp` to
   `127.0.0.1:16443`, a name in k3s's serving certificate. The in-cluster tunnel (`cell1-app`, the
   chart's `cloudflared` pod) carries only the API's hostname.
4. **The ops tunnel's first token is in cell1-a's user data, and only there.** It is the one secret
   in either droplet's user data: the cell cannot be reached before the tunnel runs, and nothing
   else could carry it there without an open port or a manual console step. cloud-init writes it as
   a root-only 0600 file, and starts the ops tunnel before anything else, so a later first-boot
   failure can still be read over SSH. Residuals, disclosed: DigitalOcean holds it, and any process on the host
   can read the metadata service. No pod can: a raw-table `PREROUTING` drop from the pod bridge to
   `169.254.169.254` is in place before k3s first starts, and k3s requires it. What the token gives
   is limited: whoever holds it can run a connector for `cell1-ops`, but each connection behind it
   still passes Access first, the SSH host key is pinned on first contact (made through Access),
   and kubectl verifies k3s's own CA, so no session can be read or replayed through it. The token
   is not rotated in this story: rotation would cut the very session that carries the new token;
   rotating it through a second, temporary path is backlog (E21-51's follow-up). The agent's user
   data holds no secret.
5. **k3s `v1.35.5+k3s1`**, the local cell's version, from its GitHub release, checked by SHA-256
   before it is installed (cloudflared `2026.9.3` likewise); no install script. Its own units, never
   started by cloud-init: `nodes` starts the server, makes the agents' join token on it from the
   kernel's random source, pipes it to cell1-b over SSH, and starts the agent. Pod traffic between
   the droplets is WireGuard (`flannel-backend: wireguard-native`) though the VPC is private;
   Secrets are encrypted at rest (`secrets-encryption`); Traefik and the service load balancer are
   off. Each node's `/var/lib/rancher`, the data and the local-path volumes, is its block volume.
6. **Proposed, the founder's: the hosted cell's tier is `dev` until release signing exists.** The
   published images carry no binary signature (DEC-971 item 6), so in `staging` or `production`
   nothing starts. DEC-971 item 7(b) asks the founder whether hosted cell #1, paper and demo only,
   may run unsigned before the hardware key is wired; the lane brief asks for `dev`. This story
   adds the chart's `deploymentTier` value, which sets `MANDATE_DEPLOYMENT_TIER` on every process
   and nothing else does: `production` by default, `ci` in the local cell, and `dev` in
   `deploy/hosted/values/cell1.yaml`. `cell1.py cluster` refuses to run on cell #1 without
   `--accept-dev-tier`, which the runbook passes only once the founder has answered DEC-971 item
   7(b) in their own words. The hosted cell has no live connection (E21-48
   is after the demo) and its environment is `paper`, which the chart's schema enforces.
7. **Proposed, the founder's: `doctl`.** The founder's own DigitalOcean CLI, version `1.186.0`,
   which `cell1.py` calls and no script fetches. It is none of D-1 to D-7, so its
   `docs/dependencies.md` row stays Proposed. Without it the `droplets` step can be done by hand in
   the DigitalOcean console from the dry run's printed plan.
8. **The GHCR read token is a `kubernetes.io/dockerconfigjson` Secret, `ghcr-pull`, in the
   workspace's namespace**, made from the founder's token file on kubectl's stdin, and named on
   the namespace's default service account's `imagePullSecrets`, so the chart is unchanged and no
   pod mounts it. A classic token with `read:packages` only, which GHCR requires. The images stay
   private.
9. **R2 for the journal's cold segments**: the Secret `object-store-r2` (`access-key-id`,
   `secret-access-key`), from an R2 API token the founder scopes to the bucket
   `mandate-cell1-journal-cold` with Object Read and Write only, and the ConfigMap `object-store`
   (bucket, endpoint, region `auto`). No process ships segments yet: E5-7's shipper and S2's
   backups (E21-41) read these when they land, and the `object-storage` egress CIDRs are set then.
10. **One Access policy for every hostname**, `cell1-operators`, allowing the emails the founder
    names; sessions of an hour on the ops hostnames and a day on the API's. `check` requires that
    an unauthenticated request to the API's hostname is redirected to Access. A server-side caller
    (the `web/` Worker) needs an Access service token, which lane W2 adds; not this story.
11. **The local proof.** `cell1.py --target k3d` runs the same `cluster` step against a two-node
    k3d cluster (a server and an agent, as cell #1 has), with the tunnel off and the change's own
    image; its only differences from cell #1's rendering are those two values. The node stage
    (cloud-init, k3s's units, the join) is proven before purchase by the dry run and
    `deploy/tests/test_hosted.py` alone, and on the droplets by `nodes` itself. Nothing is bought
    until every C1 drill has passed on `main` (DEC-990 item 2), the runbook's first check.

## Rationale

DEC-995 item 5 rules out any open port, and the brief rules out a manual step in the middle of the
run; the ops tunnel with its token in the user data is the one way to meet both, and items 3 and 4
bound what that token can do. Keeping kubectl and helm on the founder's machine means the node
needs neither, and the same `cluster` code runs against k3d. Python's standard library parses JSON
and makes HTTPS requests without a new dependency, which shell would need `jq` for.

## Alternatives considered

- **SSH open to the founder's address during the run** (the brief's "SSH limited to a key"):
  rejected by DEC-995 item 5, and the founder's address changes.
- **The ops token pasted through DigitalOcean's recovery console**: no secret in user data, but a
  manual step, and the console needs a password the admin user does not have.
- **Terraform**: state to keep and a provider plugin to pin, for nine resources.
- **The pull token in k3s's `registries.yaml`**: a node file rather than the cluster's secret
  store the brief names, and outside k3s's Secret encryption.
- **A chart value for `imagePullSecrets`**: a chart change for what the service account already
  does.
