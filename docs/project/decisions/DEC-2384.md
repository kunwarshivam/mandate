| **Story or claim** | E7-31; supersedes [DEC-953](DEC-953.md) item 3's membership case only; closes [DEC-2129](DEC-2129.md) item 8's divergence; mandate spec §6.4 check 3, V-024; identity spec §3.2, §4.3, §5.1; journal spec §9.12 |

## Context

DEC-953 resolves `autonomy.approval.approvers` to the `user` of the mandate connection's latest
`ConnectionEstablished`, and to no one once the control stream holds any §9.12 membership record,
because the shell did not fold memberships. Every workspace `mandate workspace found` founds
(DEC-991), the local cell's and staging's included, holds its founding `MemberActivated`, so the
runtime refused every grant there `not_an_approver`, the web app's and the CLI's alike (DEC-2129
item 8). No approval in a founded workspace could pass.

## Invariants

- An approver the run resolves is a member `active` (identity spec §5.1) at the stream's latest
  record, holding the approver role in effect then (V-024: "users with the approver role").
- A stream the run cannot fold resolves no one, so every grant is refused, never passed
  (`AGENTS.md` rule 3).
- The resolved set never holds anyone the API's check (DEC-2129 item 7) would refuse.
- Building the roster gives the run no seal: nothing it builds reaches `authorize` or V-047.

## Decision

1. **A roster, read inside the identity crate.** `mandate_identity::Roster::read(records, at)`
   folds the stream's `MembershipRecord`s (each mapped by `control_entry`) with `MembershipFold` and
   answers each member `active` at `at` with its effective roles, and the founder: the member of
   the stream's first membership record when that record is a founding grant (an activation with no
   invitation), while it is `active`. A fold unreadable at `at` is
   `RosterRefused::Unreadable`. The roster is not a `MembershipLookup`, builds no session or
   membership and carries no `workspace_users` count, so DEC-642 item 7's seal still keeps
   `authorize` and V-047 to the store; the shell needs no seal and `xtask/layers.toml`'s seal list
   is unchanged.
2. **The instant is the stream's latest record.** `ControlRecord` carries its envelope's
   `event_time`. With any §9.12 record on the stream, `members` folds at the latest `event_time`
   of every record the run read, with no clock: a cool-off that ended after that record reads as
   still running, which can only refuse.
3. **What resolves.** With the stream folded, each reference resolves only among the active members
   holding the approver role in effect:
   - `role:approver`: each of them;
   - `role:workspace_admin`: each of them who also holds workspace admin in effect;
   - `role:owner`: the founder, who is the org owner (identity spec §3.2's owner bundle; the
     workspace stream holds no org role);
   - `user:<id>`: the one whose principal's canonical ULID text is `<id>`, byte for byte.

   Each is DEC-2129 item 7's list narrowed to approvers, so the runtime admits no one the API would
   not (DEC-176: it only tightens).
4. **What resolves no one.** Any record on the stream with no `event_time`, a membership record
   that does not map, and a fold unreadable at the instant read each give `Members::Unread`, as
   DEC-953 item 3 did for every membership record. A stream with no §9.12 record keeps DEC-953's
   reading unchanged.
5. **Live stays as it was.** `live_cli_confirm` names DEC-923's owner only on DEC-953's reading; on
   a folded stream it gives no scope, as it did before, so every live `cli_confirm` grant there is
   still refused `step_up_method`. Folding the owner for live is its own change.
6. **Read once, at deployment.** The roster is read where DEC-953's reading was, when the run folds
   its confirmed version. A membership change after that reaches the run's resolution at its next
   start. Until then the API's check, which folds per request (DEC-2129 item 7), still refuses a
   member deactivated since, and the backlog records the re-read (E7-31's follow-up).

## Rationale

The membership fold already exists and is tested against an independent oracle (E9-7, E9-11); the
roster reuses it rather than writing a second reading of §9.12. Folding at the stream's latest
record keeps the shell pure and deterministic, and errs only toward refusing. Requiring the
approver role makes `role:workspace_admin` and `user:` mean what V-024 says, and keeps the two
gates' sets nested.

## Alternatives considered

- **Add `mandate-shell` to the seal's `allowed_dependents`.** Rejected: the seal keeps
  `authorize`'s inputs to the store (DEC-642 item 7), and an agent process holding it could build
  a lookup of its own.
- **Fold at the run's clock.** Rejected for this change: `confirmed_version` has no clock, and the
  latest record's instant can only refuse more.
- **Admit DEC-2129 item 7's list as written.** Rejected: a workspace admin without the approver
  role would approve, which V-024 does not allow.
