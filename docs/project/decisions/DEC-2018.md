# DEC-2018: a hosted cluster is bootstrapped once, by the founder's approved workflow from `main`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-18 (UTC) |
| **Decided by** | an agent (Claude Code, lane GO), under DEC-79: a reversible engineering and process choice. It keeps every credential behind the founder's review, so it weakens no safety rule (ES-12, DEC-1005) |
| **Story or claim** | E21-58, claim [#1635](https://github.com/kunwarshivam/mandate/issues/1635); DEC-2015 items 4 and 5; the founder's DEC-2011 |

## Context

DEC-2015 has Flux reconcile each hosted cluster from `main`, read-only, with workload secrets
written into the cluster by an approved workflow until the vault (E21-32). Something has to install
Flux and hand it its first `sync.yaml` once per cluster. That step needs the cluster's credential,
so no agent may run it, and no pull request may reach it.

## Decision

1. **One workflow, dispatched from `main`.** `.github/workflows/gitops-bootstrap.yml` has only
   `workflow_dispatch`. Its one job runs only on `refs/heads/main`, under the GitHub environment
   the dispatch names (`staging` or `production`), with `contents: read` and no other permission.
   The founder is each environment's required reviewer, so nothing runs until the founder approves
   that run.
2. **What the environment holds.** Each environment holds `KUBECONFIG_DATA` (the cluster's
   kubeconfig, from lane IAC), `JOURNAL_ARCHIVE_ACCESS_KEY_ID` and `JOURNAL_ARCHIVE_SECRET_KEY`
   (the Spaces key the journal archives with, scoped to its bucket), and `CLOUDFLARED_TUNNEL_TOKEN`
   (the tunnel's token). Only the job's two `cargo xtask gitops` steps receive them.
3. **`cargo xtask gitops bootstrap`** refuses to run outside a GitHub Actions run of `main`.
   - It installs Flux v2.9.6's three controllers from `flux install --export`. It pins each image to
     the digest `docs/dependencies.md` records, and refuses any image it does not pin and any pin
     the export never uses.
   - It applies them server-side and waits for each to roll out.
   - It writes the workload secrets, then applies `deploy/gitops/clusters/<environment>/sync.yaml`.
     From then on, Flux keeps that file and everything under the directory it names.
4. **`cargo xtask gitops secrets`** writes the workload secrets alone, to set or rotate them. Each
   Secret is built in memory, base64-encoded, and handed to `kubectl` on stdin. The kubeconfig
   is a 0600 file in a 0700 directory, deleted when the command ends. Nothing prints a value, and
   an empty value is refused.
5. **Flux upgrades go through this workflow too.** Flux's own manifests are not in git (5,000
   lines of CRDs for three controllers). To upgrade Flux, change the pinned version and digests in
   `xtask/src/gitops.rs`, `docs/dependencies.md`, `ci.yml` and `install.sh`, merge, and dispatch
   `bootstrap` again. Re-applying is idempotent.
6. **Tools.** flux (already a row, DEC-2015) and kubectl v1.35.9, the cluster's minor version, each
   downloaded in the job and checked against its SHA-256.

## Rationale

Every credential stays in a GitHub environment behind the founder's review, which is where
DEC-1005 keeps the web deploy's. The workflow's job and the xtask guard each refuse anything but
`main`, so a branch cannot change what the bootstrap does before review. Writing the secrets in the
same run as Flux means the journal finds its archive key on first install, rather than failing until
a second step runs.

## Alternatives considered

- **`flux bootstrap github`:** it needs a GitHub token able to create deploy keys, and it commits
  Flux's manifests. DEC-2015 item 2 needs neither.
- **Flux's manifests committed under `deploy/gitops/`, kept by Flux itself:** this adds 5,000
  generated lines to review, and Flux would apply its own upgrades on merge, outside the founder's
  approval of a run.
- **The founder runs the commands by hand from their machine:** possible, and the runbook says how,
  but it leaves no record of the run. The workflow logs each run against its commit.
