## Context

Workspace API §5.7 says the vault holds each web-push address under its `address_ref`, answers
"which of this member's entries hold this endpoint" from a keyed hash it never exports, and lets
the sweep delete an inert entry by a conditional delete. No such store exists. The API server sits
at layer 7 and can take neither `mandate-vault` (layer 8) nor `mandate-vault-local` (layer 7, and
the token store), and the dispatcher, which reads an entry for each send, must not be able to
write one. This decision sets where the store lives, who can reach it, and what each side can do.

## Decision

1. **A new crate, its own directory, key, and users.**
   - `mandate-vault-addresses`, layer 6, safety-critical. Its only external dependencies are
     `ring` (ChaCha20-Poly1305, HKDF, HMAC, `SystemRandom`) and `secrecy`, with `thiserror` for its
     errors. It never takes `mandate-connections`, `mandate-vault-local`, `mandate-vault`, or any
     crate that names a token, a code, or a client secret.
   - The dispatcher runs as its own Unix user, `owlhead_notify`, in its own unit, never inside the
     API's or the executor's process. `owlhead_notify` is in neither `owlhead_api`'s nor
     `owlhead_exec`'s group, and neither of them is in its group.
   - Under `MANDATE_VAULT_DIR` (DEC-692 item 1's vault root, owned by root, `0755`):

     | Path | Owner and group | Mode | Who can do what |
     |---|---|---|---|
     | `addresses/` | `owlhead_api:owlhead_notify` | `2750` (setgid) | The API creates workspace directories; the dispatcher can only traverse |
     | `addresses/<workspace_id>/` | `owlhead_api:owlhead_notify` | `2750` (setgid) | One per workspace. The API creates, replaces, and unlinks entries; the dispatcher opens an entry by name |
     | `addresses/<workspace_id>/<address_ref>` | `owlhead_api:owlhead_notify` | `0640` | One sealed entry. The dispatcher reads it; nobody else |

     The executor (`owlhead_exec`) can neither read nor list an address. The filesystem, not code,
     enforces that the dispatcher cannot write, as DEC-692 item 1 enforces that the API cannot read
     a token: `pending/` and `tokens/` are unchanged and this crate never opens them.
   - **The key** is `vault-address-key`, 32 bytes, a root-only `0600` file loaded with systemd
     `LoadCredential=` and read only from `$CREDENTIALS_DIRECTORY`, never from the environment.
     The API's unit and the dispatcher's unit load it. The API's unit keeps DEC-692 item 2's
     pending key and never the token key; the dispatcher's unit loads this key alone.
   - **Startup refuses rather than repairs**, as DEC-692 item 3 does. Either handle refuses to open
     when any of `MANDATE_VAULT_ADDRESS_KEY`, `MANDATE_VAULT_KEY`, `MANDATE_VAULT_PENDING_KEY`, or
     `MANDATE_VAULT_TOKEN_KEY` is set, whatever its value; when `vault-address-key` is missing, is a
     symlink, is not a regular file, is not exactly 32 bytes, or grants any group or other
     permission; when `vault-token-key` is among its credentials; and when either directory above
     has another owner, group, or exact mode (setgid included) or is a symlink. A workspace
     directory is checked the first time a handle touches it.
   - **Every entry read checks the open file first.** The entry is opened, `fstat`'d, and must be
     a regular file owned by `owlhead_api`, group `owlhead_notify`, mode exactly `0640`, and the
     same inode as the name's `lstat`, which is not a symlink; otherwise it is refused before
     decryption. The users' ids come from the host's `/etc/passwd` and `/etc/group`, as
     `mandate-vault-local` reads them, so the crate needs no `libc`.

2. **Entries.** Namespaced per workspace by directory and keyed by `address_ref`. Each holds:

   | Field | Meaning |
   |---|---|
   | `member` | The user principal whose address it is (journal §9.15's `member`) |
   | `endpoint` | The push endpoint (workspace API §5.7) |
   | `keys` | `{p256dh, auth}` |
   | `key_id` | The workspace VAPID key the subscription was made with ([DEC-2503](DEC-2503.md) item 5); not journaled |
   | `request_digest` | The step-up digest of the `PUT` that wrote it (§5.7) |
   | `endpoint_hash` | Item 4's keyed hash |
   | `version` | `1` on the first write; every write bumps it by one |
   | `written_at` | UTC, nanoseconds, set by every write |

   The whole entry is one ChaCha20-Poly1305 seal under `vault-address-key` with a random 12-byte
   nonce from `SystemRandom`. The associated data is a domain tag
   (`mandate-vault-addresses/entry/v1`) followed by the length-prefixed `workspace_id`,
   `address_ref`, and `member`, so an entry renamed onto another `address_ref`, moved to another
   workspace's directory, or presented for another member fails to decrypt. A write goes to a
   temporary file in the same directory, is synced, and is renamed over the name; the writer holds
   an exclusive lock on the workspace directory's lock file across each read-compare-write, so
   `version` checks and put-if-absent are atomic between API workers.

3. **Operations, by type.**
   - **`AddressWriter`**, the API's handle:
     - `put_if_absent(entry)` writes a new entry at `version` 1. An entry already under that
       `address_ref` with the same member and request digest is the same request and answers its
       current version without writing; a different digest or member is `Conflict`, which the API
       answers `idempotency_conflict` (§5.7 setting step 1).
     - `put_again(entry)` is §5.7 setting step 6: it writes the same entry again, bumping `version`
       and `written_at`, and recreates it if a sweep deleted it meanwhile; a different digest or
       member is `Conflict`.
     - `entries_holding(member, endpoint)` returns the `address_ref` and `version` of each of that
       member's entries whose `endpoint_hash` matches, compared in constant time; it never returns
       another member's entry. The caller keeps only the active ones (§4.11).
     - `compare_and_delete(address_ref, version)` deletes the entry only while its `version` is
       the one given: `Deleted`, `Stale` (a later write), or `Absent`.
     - `inert_older_than(cutoff)` returns the `address_ref`, `version`, and `written_at` of each
       entry written before `cutoff`. The store cannot tell an inert entry: the sweep keeps those
       with no committed `added`, or removed and past their last send, from the journal's active
       set, and deletes each with `compare_and_delete`, so an entry rewritten after the listing
       stays.
     Every operation takes the workspace id, so one handle never reaches across workspaces by a
     missing argument.
   - **`AddressReader`**, the dispatcher's handle, offers one operation:
     `entry(workspace_id, recipient, address_ref)`, which returns `None` unless an entry exists
     under that `address_ref` and its stored `member` equals the recipient, so another member's
     entry reads exactly as a missing one. An entry that fails item 1's file check or item 2's
     decryption is an error naming only the `address_ref`. The endpoint, keys, and `key_id` come
     back as `secrecy` types for one send.
   - **The reader is read-only by type.** `AddressReader` has no write, delete, or list method, it
     cannot be converted into or obtained from an `AddressWriter`, and a `compile_fail` doctest
     pins that calling a writer operation on it does not compile. The filesystem's `2750` and
     `0640` hold the same line if code ever drifted.

4. **The keyed endpoint hash.** A per-workspace subkey is derived inside the crate with
   HKDF-SHA-256 from `vault-address-key`, with the info string
   `mandate-vault-addresses/endpoint-hash/v1` and the length-prefixed `workspace_id`. The hash is
   HMAC-SHA-256 under that subkey over the length-prefixed `member` and `endpoint`, so it is scoped
   to the member as well as the workspace: one endpoint held by two members, or in two workspaces,
   hashes differently. It is stored inside the sealed entry and deleted with it, and no operation
   returns it, logs it, or hands it to a caller to journal. The subkey never leaves the crate.

5. **Nothing secret in any output.** No endpoint, key, `key_id`, request digest, hash, subkey, or
   key material appears in a log, an error, a `Display` or `Debug` output, a metric, or a
   notification (`AGENTS.md` rule 6, notifications spec NT-2). Errors carry opaque ids only: the
   workspace id, the `address_ref`, and a closed reason. A canary test plants a recognizable
   endpoint and keys and scans every error and `Debug` output the crate can produce.

6. **OpenBao comes later.** `mandate-vault`'s `SecretPath` gains an `Address` path, so the
   address store has an OpenBao backend behind the same two handles, as a backlog row under
   E21-32. Until it lands, the demo host and the cell use this local store.

7. **Deactivation writes no vault.** E9-7's membership writer (lane L1) appends the `removed`
   records for a member's active addresses inside its own commit (§4.11 "Deactivation", DEC-795
   item 5), and computes them with a pure helper that E8-14's slice A2 provides,
   `removals_on_deactivation`, over plain `(seq, member, action, address_ref)` records with no
   journal types and no I/O, in a crate at or below the writer's layer (`mandate-identity` is
   layer 1). The entries are then swept as for any removal (item 3). A backlog row under E9-7
   records the call.

## Rationale

The endpoint and keys are the member's personal data, and the push path is the only reader. A
directory and a key of their own keep a mistake in this store from reaching tokens, and keep the
token key out of a process that has no use for it. Writing the dispatcher's read-only line into
both the type and the filesystem means neither a code change nor a misconfigured unit alone lets
the dispatcher alter where notices go. Binding the member into the associated data and the reader's
answer means one record or one bug cannot route a member's notices to another's browser.

## Alternatives considered

- **Put addresses in `mandate-vault-local`'s `tokens/` under a new kind.** Rejected: the API cannot
  read `tokens/` by design (DEC-692 item 1), and the dispatcher would need the token key.
- **Have the API server take `mandate-vault`.** Rejected: layer 8 is above it, and it carries the
  token paths.
- **Let the dispatcher read as `owlhead_api`.** Rejected: it could then write and delete entries,
  and redirect a member's notices.
- **One endpoint-hash key for every workspace, or a hash over the endpoint alone.** Rejected: an
  equal hash would link one browser across members or workspaces.
- **The hash in the file name, for a lookup without decryption.** Rejected: the name would then
  reveal which entries share an endpoint to anyone who can list the directory.
