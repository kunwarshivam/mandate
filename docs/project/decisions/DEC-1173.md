## Context

[DEC-1171](DEC-1171.md)'s review left six minors under the freeze rule, recorded under E21-33 in
the backlog. Two are design choices, made here:
- **m1.** The CLI's `agent deploy` refuses a second deployment of an *active* agent
  (`agent_active`, DEC-530 item 9.7). It lets an agent whose latest record is an `AgentStopped`
  be deployed again under the same id. §9.21 reads `AgentStopped` as final, and the deployment
  manager never restarts a runtime after it. So a reused id would be a deployment the writer
  accepts and the manager never runs.
- **m3.** The manager starts nothing for a version-1 `AgentDeployed` (DEC-1171 item 4). While the
  manager is rendered, the runtime and executor render as no Deployment of their own (DEC-1172
  item 7). So a manager shipped into a workspace with a running version-1 deployment would leave
  that agent with no runtime and its account with no executor. Its open position would keep only
  what the broker already holds.

The other four (m2, m4, m5, m6) are vectors and wording, and are done in the changes that follow.

## Decision

1. **An agent id is deployed once (m1).** A writer of `AgentDeployed` (the CLI's `agent deploy`,
   the workspace API's deployment) refuses an agent that an `AgentStopped` on the control stream
   names, whatever version it would deploy, appending nothing:
   - the CLI's code is `agent_stopped`, checked where `agent_active` is today, after the code
     check;
   - the workspace API answers `invalid` at `/agent_id`, as for an active agent with another
     version.

   An agent that is active with the same version still answers with its deployment and commits
   nothing. A stop, and every risk reduction, is unchanged: this refuses only a deployment, which
   adds risk (`AGENTS.md` rule 13). The owner deploys under a new agent id. Agent ids are never
   reused, so §9.21's reading of a stop as final and the writers' agree. Every stop counts,
   whatever its `reason`: an agent retired by `goal_complete`, `profit_stop_reached` or
   `end_date` also needs a new id to run again. Journal spec v0.56 §9.24 states the rule. It is a
   writer's check over its own fold, which `append` cannot see, so its tests land with the
   writers' code changes (the CLI's refusal table and the workspace API's deploy tests), not as a
   journal vector.
2. **The manager treats a stop as final even when it never read the deployment it stops (m2).**
   An `AgentStopped` of an agent whose deployment named no account (version 1, or a version 2 that
   rule 201 refuses) still makes that agent gone. A later deployment of the same id starts
   nothing. The writers of item 1 never write one, so this only matters for a stream that was
   written before them. Journal spec v0.56 §9.21 states it, and the `agent_deployed` vectors
   show it.
3. **A version-1 deployment is retired before the manager runs its workspace (m3).** No hosted
   workspace exists yet (DEC-967 item 3), and the local cell's demo deploys afresh at every
   `cargo xtask cell up`, so no deployment is stranded today. (The manager's own pod is why the
   runtime and executor render no Deployment while it runs: DEC-1172 item 7.) For any workspace
   that later holds one:
   - before its cell renders the manager, the owner stops each active version-1 agent with
     `agent stop`, while the processes that run it today still run;
   - once the connection is recorded (`connection record`), the owner deploys a new agent id,
     which the writers then write at version 2 (DEC-1171 item 3).

   Once the manager runs, it raises one opaque operator alert, `deployment_unread` (runbook
   RB-14), for each version-1 deployment of an agent that is not stopped and that no later
   version-2 deployment runs. A stranded deployment is visible rather than silent. The alert
   carries a reason code and a runbook only (`AGENTS.md` rule 6).
   - **Restarts.** Each manager process raises it once per such deployment. A restarted manager
     rebuilds its fold from the journal and raises it once more, as it does for the crash-loop
     alert (DEC-1170 item 7). De-duplicating is the alert path's, as DEC-1170 item 7 leaves the
     crash-loop alert's, so a restart loses no alert.
   - **Where it is specified.** It is not a journal record, so no journal vector holds it. It is
     deferred to the manager's code change (step 4 of the claim's plan), which:
     - adds it to the infrastructure design's §8.2 alert list;
     - tests it against the `agent_deployed` streams, with an oracle computed from each stream's
       own records;
     - shows a mutant of its fold caught.
4. **Vectors (m2, m4).** The `agent_deployed` section adds:
   - a stream holding a version-1 deployment, its stop, then a version-2 deployment of the same
     agent, which starts nothing;
   - a stream whose only establishment is an account stream's copy, which rule 201 refuses;
   - a range anchored after a revocation that follows the deployment, which passes.

   It also seeds three bugs in the oracle, each caught: a later revocation failing rule 201, a
   revocation stopping a running deployment, and a stop of an unread deployment ignored. It also
   seeds one in the fold: an account stream's copy counted as an establishment.
5. **Wording (m5, m6).** The §9 catalogue row for `AgentDeployed` names version 2. The workspace
   API spec states which version its deployment writes and item 1's refusal. m6's other half,
   the infrastructure design, stays open until the manager's code change, which updates it in
   the same change as the code (it is not a protected path).

6. **Proposed, for the founder (DEC-79, a safety rule's scope): key the daily-loss and conduct
   controls by connection.** A same-day redeploy under a new agent id restarts the per-agent
   daily and conduct state listed under *Attacks considered*: the daily-loss, drawdown and
   tripwire latches, the `goal_complete` restriction, the re-entry cooldown, the per-agent
   order-to-fill, order-rate and daily order limits, and MI-25's ask caps and suppressions. Keying it by connection instead
   would stop that. Nothing is built for it here, and the controls stay per agent as the specs
   define them until the founder decides.

## Attacks considered

- **Redeploying under a fresh id to reset limits.** Two limits are unaffected by the id:
  - The loss carry, and with it the lifetime floor, is the connection's. An `AgentStopped` adds
    its `loss_added` to the connection's carry (journal spec §9.2, mandate spec §5.7). V-032
    refuses a deployment whose carry has reached the limit, whatever the agent id.
  - The high-water mark starts from the deployment, under a new id or an old one (mandate spec
    §5.5).

  The per-agent daily and conduct state does restart with a new id, on the same risk day too:
  - the `max_daily_loss` latch and its E₀ (mandate spec §5.4);
  - the drawdown ladder's `exits_only` and `flatten_and_pause` latches (§5.5, §5.8);
  - the tripwire windows and a fired tripwire's latch (restriction `tripwire`, limit
    `tripwire:<id>`; §5.8, §5.9, §6.7), so a fresh id clears a fired `exits_only` tripwire;
  - the `goal_complete` restriction;
  - the re-entry cooldown keyed by the agent's last exit fill;
  - the order-to-fill limit (trading spec §9.6), and the per-agent part of the order-rate limit
    and `max_orders_per_day` (§9.7); the order-rate limit's per-account part does not restart;
  - MI-25's per-agent ask caps, with their `skipped_today` and `recent_timeout` suppressions.

  The 60-second opposite-fill block and daily participation are keyed by the related-accounts
  group, not the agent, and do not restart.

  This is not new with this decision: an owner could already deploy another agent on the same
  connection. It is bounded by the lifetime floor, and by a deployment being the owner's
  stepped-up gesture, never an agent's. Whether these should be keyed by connection instead is
  item 6, left to the founder.
- **Stops for a goal.** An agent retired by `goal_complete` or `end_date` is stopped like any
  other. Running it again needs a new id, and the same carry applies.
- **A stranded version-1 deployment.** It never runs under the manager and is reported (item 3).
  The retirement order keeps an executor beside any open position until the owner has stopped
  the agent.

## Rationale

Refusing a reused id at the writer costs an owner nothing they could have had: the manager would
never run it. It keeps one reading of a stop for every reader. Retiring a version-1 deployment
while its processes still run keeps an executor beside any open position until the owner has
stopped the agent.

## Alternatives considered

- **Reuse agent ids, and have the manager start a stopped id's later deployment.** Rejected: it
  would make §9.21's final stop depend on which record came later. It would also change a spec
  section to admit a deployment the writer has no reason to make.
- **Have the manager read a version-1 deployment from the document when one is at hand.**
  Rejected by DEC-1171 already: two paths to one answer, one through a store the manager cannot
  rely on.
- **Refuse to start the manager while any version-1 deployment is active.** Rejected: it would
  hold kill-switch starts and every version-2 deployment hostage to one stranded record. An alert
  shows the stranded record, and holds nothing else back.
