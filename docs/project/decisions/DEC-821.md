| **Date** | 2026-10-08 (UTC) |

## Context

The demo connects Alpaca paper by OAuth (DEC-820). The L2 lane read Alpaca's public OAuth
documentation on 2026-10-08 and found two blockers.

1. **U-A4 is not cleared.** A grant can be requested per environment (`env=paper`), but the
   documentation never says the live host refuses a paper-environment token, and the token response
   carries no environment field. DEC-441 item 21 therefore refuses every Alpaca OAuth grant, paper
   included.
2. **The code exchange runs on the live host.** It is `POST https://api.alpaca.markets/oauth/token`,
   even for paper. ES-23 and infrastructure §2 compile only paper hosts into non-production
   builds.

The coordinator offered connecting with paper API keys. Those are already allowed (connections
§5.1, DEC-441 item 3) and need no new decision. The founder chose OAuth now.

## Decision

DEC-690 is the L2 lane's decision in [#769](https://github.com/kunwarshivam/mandate/pull/769),
not yet on `main`. Its items 6 and 7 are restated here in full, so this decision stands on its own.

1. **A paper grant is treated as paper-only (DEC-690 item 6).** A grant requested with `env=paper`
   is treated as meeting U-A4 for paper connections. The residual risk the founder accepts is that
   such a token might be honoured by Alpaca's live host.
2. **One call to the live host (DEC-690 item 7).** In builds that otherwise compile only paper
   hosts, exactly one call to the live host is allowed: `POST https://api.alpaca.markets/oauth/token`.
   - **Who makes it.** Only a dedicated token-exchange client in the token-exchange process, which
     is not the executor, makes it, during the code exchange and refresh. That client is a separate
     type that can be built only with that one URL, and it is never used for anything else.
   - **What it carries.** The form body carries only the members the OAuth exchange needs:
     `grant_type`, `code` or `refresh_token`, `client_id`, `client_secret`, `redirect_uri` and the
     PKCE `code_verifier` when PKCE is used. Nothing else is sent: no account, order or trading
     data.
   - **What it returns.** The response is parsed only for the token fields, and the token goes
     straight to the vault.
   - **What is refused.** No other path or method on that host is reachable. The call sends no
     query string and follows no redirect. The pinned tests are:
     - the allowlist is that one method and path;
     - the body holds exactly the members above;
     - every other request to the host is refused before it leaves the process.
   - **Refresh.** A refresh happens only if Alpaca issues refresh tokens. That is still U-A3, and it
     is open.
   - **Who calls the live host.** Agents never do; their tests use fixtures (rule 8). The first real
     exchange is the founder's own act, when they connect.
3. **The code is bound to a paper request.** A code is exchanged only when its single-use `state`
   names a request the server itself issued with `env=paper`, for that workspace, and not yet
   used. Any other code is refused before the exchange.
4. **What still holds, so the residual risk cannot become an order:**
   - The workspace sends every order only to the paper trading host the connection's environment
     names (`paper-api.alpaca.markets`). No code path sends an order, or any trading or account
     call, to the live host with any token.
   - **The process boundary.** The token-exchange process is not the executor. It holds no order
     client and no token lease. The executor's network egress contains no live host.
   - **The limit, stated plainly.** `api.alpaca.markets` is both the token host and the live
     trading API, and network allow lists work on addresses, not paths. The token-exchange process
     can therefore reach the whole live API at the network level. In that process, the dedicated
     client type of item 2 is the only barrier.
   - DEC-441 item 22's recommended conditions apply in full:
     - the executor is bound to its own environment's host;
     - no live trading host is compiled outside production; the token endpoint of item 2 is the
       only exception;
     - egress is limited to the paper trading host and that one token endpoint;
     - the token's possible breadth is journaled with the connection and disclosed to the owner.
       The journal spec change that adds that event comes first.
   - The grant requests `env=paper` and only the scopes the connections spec allows (FR-2.2, exact
     scope refusal).
   - The token stays in the vault, and in memory only as `SecretString` (rule 7, OPS-1).
   - The connection's permission checks (§8.1) still run.
   - DEC-441 item 21 still refuses a grant that names `live` or both environments.
5. **Rules this narrows, for paper Alpaca OAuth only.** The spec PR that implements this decision
   records each of these amendments as a narrowing that cites this decision, and changes nothing
   else in them:
   - **ES-23** (ADR-0001) and **infrastructure §2**: the one token endpoint of item 2;
   - **CN-3** (connections spec): a paper grant is treated as paper-only under item 1;
   - **DEC-441 item 21**: superseded for `env=paper` grants only.
6. **DEC-441 item 18 (registration) is resolved.** The founder registers the Alpaca OAuth app,
   for paper only, after reading Alpaca's app terms, with the redirect URI the L2 lane specifies.
7. **Scope.** This decision covers paper connections only. A live Alpaca OAuth connection needs a
   new decision. The founder may still ask Alpaca in writing whether a paper-environment token is
   refused by the live host. A written "yes" retires the residual risk, and a "no" is reported at
   once.

## Rationale

The founder wants the full OAuth journey in the demo. The two narrowings are the smallest that make
it possible, and the guardrails in items 3 and 4 keep any order on the paper host whatever the token
could technically reach.

## Alternatives considered

- **Paper API keys for the demo, with OAuth deferred until Alpaca confirms in writing.** This was
  the coordinator's recommendation, and the founder did not choose it. It stays available as a
  fallback under the existing rules.
- **DEC-441 item 22.** This was the Proposed fallback for the case where U-A4 fails. For paper,
  it is adopted with the token-endpoint exception of item 2, and item 4 applies its conditions in
  full.
