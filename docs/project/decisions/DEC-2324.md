## Context

§4.10 item 4 asks route 2 to verify the signature first, before anything is judged, against the
passkey's key or a decoy for an unknown passkey, so timing tells no passkey state apart. Item 2
names `mandate_passkey::verify` as the judge. That function cannot meet item 4:
- It returns at the first check that fails, and the signature check comes after the client data
  and the authenticator data.
- It compares the assertion's backup-eligible flag with the stored credential's. A held passkey
  whose flag differs is refused before any signature work, while an unknown one runs the decoy's
  signature check: a timing oracle on whether the passkey exists.

Journal spec §9.31 records no backup-eligible flag, so route 2 has no stored flag to compare
anyway; DEC-2121's follow-ups leave its source open. The key is a COSE_Key held as an artifact,
and the crate's COSE parser is private.

## Decision

1. **`mandate_passkey::reduction::verify_reduction(rp, challenge, key, assertion)`** is route 2's
   judge, in its own module so the step-up verifier and the credentials fold are untouched. It:
   - verifies the signature over the authenticator data and the client data's SHA-256 first,
     whatever else is wrong, and answers `signature_invalid` whenever it fails;
   - then judges the client data (a `get` ceremony, the challenge, the origin, not cross-origin),
     then the authenticator data (no attested credential, the RP ID hash, user presence and
     verification, and backup flags consistent with each other);
   - compares no credential id (the caller looked the key up by it), no backup-eligible flag, and
     no counter (route 2 neither reads nor advances it, §4.10 item 2).

   `verify` stays as it is for step-up.
2. **No backup-eligible compare on route 2.** This fills a gap and loosens nothing: no record holds
   the flag, so there is nothing to compare. Where the flag comes from stays open, as DEC-2121's
   follow-ups say; when a record holds it, route 2 may compare it, signature first still.
3. **`reduction::cose_key(bytes)`** parses a COSE_Key's bytes (ES256 or EdDSA, DEC-660 item 3,
   nothing after the key), for the caller that resolves a `CredentialEnrolled`'s `public_key`
   artifact.
4. **Constant work: one ES256 and one Ed25519 check on every call** (the review of #2153, which
   replaces DEC-2119 item 8's decoy chosen by the signature's encoding). `ring` refuses a signature
   of the wrong shape for its algorithm without any arithmetic: measured, a DER signature against a
   held Ed25519 key took 346 ns against 76 µs for an unknown id, and 64 bytes against a held ES256
   key 759 ns against 45 µs, which told a held key, and its algorithm, apart. So
   `verify_reduction(rp, challenge, key: Option<&PublicKey>, assertion)` always makes exactly one
   ES256 check and then one Ed25519 check over the same message and signature: the held key for
   its own algorithm and the other algorithm's decoy for the other, or both decoys for `None`.
   Only the held key's check answers; with `None` the signature never verifies. `DECOY_ES256` is
   the P-256 base point and `DECOY_ED25519` is RFC 8032's first test key: both valid keys, so a
   check against one runs to the end. Their secrets are published, which does not matter: a
   decoy's check never answers. `verify_reduction_with` takes the checks through a
   `SignatureCheck`, so a test counts them; `RingCheck` is the crate's own.
5. **The caller's rule** (S2b-3): a passkey that is unknown, or whose key does not resolve, does
   not parse, or is not the algorithm its enrolment recorded, is judged with `None`, and refused
   with the one 401.

## Rationale

A judge that cannot return before both signature checks have run, and runs the same two for
every request, leaves no timing difference between a held passkey and an unknown one, or between
the two algorithms, that the caller's code could introduce by accident. Keeping it a
separate function keeps step-up's verifier and its tests unchanged.

## Alternatives considered

- **Change `verify` to check the signature first.** Rejected: step-up's checks and their order are
  L1's and pinned by their tests; route 2 needs a different contract (no counter, no flag compare)
  anyway.
- **Store a backup-eligible flag of `false` for every key.** Rejected: it would refuse every synced
  passkey on route 2 and invent data no record holds.
- **A decoy chosen by the signature's encoding** (DEC-2119 item 8 as first written). Rejected by
  the review: a held key of the other algorithm skips the arithmetic, a measured oracle.
- **A random decoy key per process.** Rejected: a fixed, published key is as good, since its answer
  is never accepted, and keeps tests reproducible.
