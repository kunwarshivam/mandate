# DEC-948: The paper run stops on any reconciliation mismatch, books its simulated fee, and journals at the run clock

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-16 (UTC) |
| **Decided by** | Claude (builder agent), under DEC-79 (reversible engineering decisions) and DEC-176 (each item tightens a check or makes the code meet the spec as written, and weakens no safety invariant) |
| **Story or claim** | E2, the first paper trade; the follow-ups #1369's review and DEC-938's backlog recorded; DEC-921 (one PR, tests first) |

## Decision

1. **A mismatch stops the run wherever the reconciliation ran.** The watch used to drop the
   verdicts of the reconciliations it asked for, so a mismatch there raised no alert and the run
   went on. Now the startup and the watch both use one rule: the first round that answers
   `Mismatch` pushes the opaque alert key `reconciliation_mismatch` (rule 6) and stops the run
   with `ShellError::ReconciliationMismatch`. Nothing is sent after that, and no round it asked
   for is run. The startup used to run every round it was asked for before it read any verdict.
2. **The executor learns its environment from the stream's envelope.** Journal spec §9's
   registered `StreamOpened` carries the environment in the envelope, not in the payload. The
   executor's fold reads only the payload member, so on the paper path it never learned that it
   was on paper and booked no simulated fee (trading spec §10). When the shell folds an
   account-stream `StreamOpened` whose payload has no `environment`, it hands the executor the
   environment the journal stored with the record. The executor then books the fee the
   registered fee configuration defines on each of its own paper equity fills.
3. **`FeesCharged` version 1 is registered as the simulated equity fee.** It is a closed record
   of §9's key fields (`family`, `day`, `accrued`, `charged`), plus `simulated`,
   `client_order_id`, the three equity components `sec`, `taf` and `cat` (each always present, and
   `null` where the side owes none), and `risk_clock`. `family` is only `equities`, the one family
   anything books today. A broker-posted or crypto fee registers its own shape when its writer is
   built. The record names `fee_config`, the one reference the catalogue requires. It is the same
   object its fill names, taken from `InstrumentSnapshot::fill_refs`. A snapshot that names none
   leaves the fee unbound, and the journal refuses it, as it refuses an unbound fill.
4. **The executor's risk clock starts at the run clock.** Mandate spec §5.2 defines the risk
   clock as the latest tick the executor has seen. On the paper path no tick reached it before
   its first records, so they all carried `1970-01-01T00:00:00Z`. The shell now hands the
   executor a tick at the run clock's whole second before `Input::Started`. A tick before the
   start only sets the clock: it evaluates nothing, emits nothing, and leaves the executor
   unstarted. Any other input before the start is still refused `not_started`.
5. **The cash comparison measures from the snapshot before this one, and counts each fill
   once.** Trading spec §11 compares the broker's cash with the last broker cash snapshot plus the
   fills since then. The shell records the snapshot's own account report before the run (DEC-458
   item 2), so that report was the base. That had two effects. First, the broker's cash was
   compared with itself. Second, a fill the run then ingested, which that cash already held, was
   counted again. So every late fill mismatched by its notional, and no real drift could ever
   show. Item 1 made that false mismatch stop the paper run after its first fill. Now, when the
   base is a report folded after the snapshot's head (the snapshot's own report), the model is the
   report it replaced, plus every fill folded since that one: before the report, after it, and the
   ones the run ingests. The executor keeps the replaced report and the fills folded up to it
   (`PriorBase`). With no earlier report there is nothing to measure from, and the snapshot is its
   own base, as at a first start. A base set by an earlier report is measured from as before. This
   tightens the check: a drift between two snapshots now mismatches on the shell path, where
   before it could not.

## Rationale

Items 1, 2 and 4 make the code do what the specs already say: a mismatch alerts and holds
(trading spec §11, `AGENTS.md` rule 3), paper books its shadow fees (§10), and records carry the
risk clock (mandate spec §5.2). Item 3 registers the exact record the executor already wrote, in
a closed shape. That is narrower than the catalogue's open row, so it loosens no validation. Item
5 brings the cash comparison back to §11's wording, so that each snapshot is measured from the one
before it, and it detects more than the code did. Without item 5, item 1 would stop every paper
run after its own fill on a false mismatch. Without item 1, the watch would go on hiding a real
one. The independent review of the first draft of item 5 found it measured the snapshot from
itself. That would have removed the false mismatch only by leaving nothing compared, so the draft
was replaced before merge.

## Alternatives considered

- **Record the snapshot's account report after the reconciliation run.** That would compare cash
  against the earlier base too. But it reverses DEC-458 item 2, and it breaks the fail-closed rule
  that an ambiguous account report stops the run before any reconciliation runs. It was rejected
  in favour of keeping the replaced base in the fold.
- **Leave the ingested fills out of the model when its own report is the base.** This was item 5's
  first draft. It removes the false mismatch, but it compares the broker's cash with itself, so
  the check sees nothing. It was rejected at review.
- **Add `environment` to `FoldedEvent`.** About seventy constructions across eleven crates would
  change for one record type. The shell hands the executor what the journal stored instead.
- **Emit only the components a fill owes, and register optional members.** The journal's records
  have exactly their listed members, each always present (journal spec §4.2), so a missing
  component is `null`.
- **Tick the executor right after `Input::Started`.** The records the start itself writes (an
  abandoned intent, the startup reconciliation's) would still carry zero.

## Not decided here (backlog)

- A fill's `set` reference still names the trading calendar until a distinct settlement calendar
  is registered (DEC-938 item 2).
- A truly external fill is still refused at the journal: `ExternalActivityIngested` has no
  schema.
- A labelled fail-safe deny needs a spec change (DEC-938 item 4).
- A fill that lands between the snapshot's account read and its activity read is in the model but
  not yet in the broker's cash, so it stops the run on a false cash mismatch (fail-safe).
- The first account report an account journal ever holds has no earlier report to be measured
  from. When it is also the snapshot's own report, that one comparison checks the broker's cash
  against itself, and the fills that run ingests go uncompared. This happens once per account
  journal.
- `PriorBase` reaches back one report only. An account push between two snapshots becomes the base
  the next snapshot is measured from, so drift between the earlier snapshot and the push is never
  compared with the model. Pushes re-anchored the base before this decision too.
