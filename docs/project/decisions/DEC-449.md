| **Story or claim** | E7-7 (the tracer bullet); claim [#171](https://github.com/kunwarshivam/mandate/issues/171) |

## Decision

1. **`RiskExitPath`'s mid-run `plan` folds the journal at request time, and the journal arrives
   with the call.** The run's bridge — which owns the stages — hands the journal's read
   capability to each `plan` call, so the adapter holds no journal of its own and no plan can be
   taken over a fold the run has already written past; a scratch run's memory journal is
   readable through the same hand, which a journal opened by name could never be. What the
   adapter holds is the mandate's path. At `plan` time it folds the journal's records into the
   state `mandate_risk::agent_flatten` reads: the agent's positions and working orders from the
   account-stream fold (`mandate-executor`'s public `fold` over the journaled §9.5 records), the
   broker's positions from the observed-position records, each instrument's asset class from the
   validated mandate's universe, and the session from the clock. A construction-time fold is
   refused: a kill switch must see the current state, and the adapter is constructed before the
   session opens, so a fold taken then is stale by definition.
2. **`mandate-runtime`'s port is unchanged.** `FlattenPlanner::plan` stays infallible with the
   poisoned adapter, exactly as the task brief's ruling holds it; `FlattenRequest` carries no
   more than it does today. The runtime's own fold is not re-implemented in the adapter for any
   purpose but the flatten: the two folds are deterministic over the same records, so they agree,
   and the kill switch is journaled before the planner runs (AGENTS.md rule 5), so a fold at
   `plan` time sees everything that exists.
3. **The mapping the adapter owes.** The risk crate's `FlattenPlan` and the runtime's are distinct
   types, and so are their working-order ids: the risk crate's are numeric, the runtime's and the
   journal's are strings, and the numeric space is the adapter's internal mapping, invisible to
   the runtime. What is pinned is the round trip: the cancels a plan names come back as the
   strings the request's fold keys orders by. Beyond the ids, the adapter maps: each sell and
   each deferred sell becomes a leg, a deferred one waiting for the regular session; the purpose
   carries over (`RiskExit` for a risk-limit kill switch, `OwnerExit` for an owner's); the
   request's confirmation carries over; and the account-wide endpoints and the mode-first flag
   have no runtime counterpart, because the runtime type cannot carry them — §5.5's
   unrepresentable half.
4. **The probe** is the task brief's ruling, unchanged: one `agent_flatten` call over a synthetic
   kill-switch request built from the mandate fixture, before anything is armed.

## Alternatives refused

- **Extending `FlattenRequest` to carry the folded state** (the runtime holds it at the call
  site): it changes another stream's public type to save a fold that happens rarely, and the
  earlier ruling keeps the port as it is.
- **A construction-time fold held by the adapter**: stale for every mid-run kill switch, which is
  the only caller `plan` has.
- **The runtime planning flattens itself** (`mandate-runtime` calling `agent_flatten` directly):
  it moves the shell's stage trait out of the path the tracer's fail-closed suite pins, and the
  brief keeps the exit path a shell stage.

## What it changes downstream

The tracer's risk-exit probe flip (E7-7 stream L) implements against this: the tests PR reshapes
the adapter's stub API to the journal handle and the mandate path, and the implementation PR folds
at `plan` time. The BTC/USD paper run (DEC-450, the founder's call) rides the same path once the
flips land.
