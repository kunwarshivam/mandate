## Context

[DEC-1170](DEC-1170.md) built the deployment manager as a library, `mandate-deploy-manager`, with a
fake orchestrator and a Kubernetes adapter, and left its process to this slice (item 9): the loop,
its probes, the Postgres journal port, the chart's templates and RBAC. The cell's demo (E21-54,
DEC-2002) names "the agent's processes started from `AgentDeployed`" as a gap this slice closes.

Three things in the cell stood in the way:
- The manager's crate sits at layer 4, below the Postgres journal (layer 6).
- Every pod's first container, the egress gate, refuses to start until the Kubernetes API server
  stops answering, because that is how it proves its own network policy is programmed. The
  manager has to reach that server to create pods.
- No pod has a service account token today.

## Decision

1. **A process crate, `mandate-deployd`, safety-critical, at layer 8, beside the scheduler and the
   runtime's daemon.** It wires the manager's ports and decides nothing:
   - the control stream over `mandate-journal-pg`;
   - the Kubernetes adapter, built from the pod's mounted service-account files, never from an
     environment variable (DEC-822 item 4);
   - operator alerts as one stderr line each, a code and a runbook only;
   - `mandate-process`'s lifecycle and exec probes over a Unix socket, the same as the scheduler.

   It reads the host clock only at its edge (ES-05). It passes once a second and drains on
   SIGTERM. Its `forbidden_internal` list is the manager's: no crate that writes an agent or
   account stream, holds a broker credential, or edits a mandate.

2. **Each pass's outcome folds into the lifecycle the fail-closed way.**
   - A pass that could not read, write or list, or that found the stream not yet opened, is a
     heartbeat; the next pass starts again from the journal, having done nothing unjournaled.
   - A record the journal refuses as invalid is a defect: the process exits rather than retry it
     blind.

3. **The journal port takes a writer epoch for each append and writes at the head it reads then**,
   because workspace control services share the control stream (journal spec §5.1). It is the same
   protocol the API server uses. A record's derived `event_id` makes a retry, or a second manager's
   draft of the same step, one event.

4. **The manager's service account reaches pods only, and an admission policy bounds the pods it
   can make.**
   - **The Role is pods only.** A namespaced Role's only rule is `pods` in the core group, with
     `create`, `get`, `list` and `delete`. It has no secrets, no `exec`, no other resource or verb,
     and no ClusterRole or cluster scope. A RoleBinding binds it to the manager's ServiceAccount
     alone. Only the manager's pod mounts a token; every other pod keeps
     `automountServiceAccountToken: false`.
   - **Creating pods is itself powerful.** RBAC cannot shape a pod, and the namespace has no Pod
     Security label. Unbounded, `create pods` would let a compromised manager mount any Secret in
     the namespace (another role's `journal-role-*` pgpass), name any ServiceAccount, claim any
     process's egress labels, or run a privileged pod or one with a host path.
   - **A ValidatingAdmissionPolicy bounds it to pods shaped like the chart's templates.** It is
     `admissionregistration.k8s.io/v1`, GA since Kubernetes 1.30; the cell runs k3s v1.35.5. The
     chart renders it and its binding only with the manager, named with the namespace and release
     as a prefix, since both are cluster-scoped. It matches the creation and update of core pods in
     the release's namespace, and, by a match condition, only requests whose user is
     `system:serviceaccount:<namespace>:deploy-manager`, so no other client or pod is affected. It
     fails closed (`failurePolicy: Fail`, `validationActions: [Deny]`). A pod the manager makes
     must:
     - mount no service-account token (`automountServiceAccountToken: false`) and name no service
       account but `default`;
     - share no host network, PID or IPC namespace, and mount no host path;
     - have every container and init container unprivileged with `allowPrivilegeEscalation:
       false`, and no ephemeral container;
     - run only the images its rendered templates name (the runtime's, the executor's, and the
       gate's and credentials' `images.postgres`);
     - mount only memory (`emptyDir`) and the Secrets its rendered templates name: the started
       processes' own role Secrets and `journal-ca`; read no Secret through `env`, `envFrom` or an
       image pull secret;
     - carry `app.kubernetes.io/managed-by: mandate-deploy-manager`, a `mandate.dev/process` that
       has a template, and the release's `mandate.dev/workspace`;
     - carry exactly that process's `mandate.dev/egress-*` labels from processes.json, so a runtime
       cannot claim the executor's vault or broker egress.

     The images, Secrets and egress labels are list and map literals built from the rendered
     templates and processes.json, never by hand.
   - **Residual: what the policy does not check.** A pod inside these bounds may still set any
     other field: its command and arguments, its resources, its node placement (`nodeName`,
     affinity, tolerations), its pod-level `runAsUser`, its capabilities, its
     `readOnlyRootFilesystem`, and any label outside those above, such as the subject or
     generation. It runs one of the templates' images with one of their roles, so it can
     do what a runtime or executor can, as that process. The manager can also delete any pod in its
     namespace, the journal's Postgres pods included, which their operator restarts.

5. **One new egress target, `kube-api`, for the manager's pod alone.**
   - A NetworkPolicy cannot select the API server by pod label (in k3s it is not a pod), so it is
     an external-style target: its CIDRs and port come from values, and an empty list allows
     nothing.
   - `cargo xtask cell up` reads the API server's addresses from the cluster's `kubernetes`
     EndpointSlice and passes each as a /32 with its port (6443 in k3s, behind the Service's 443).
     No value file can hold them, because docker picks the k3d network when the cluster is made.
   - No other process lists it, and the chart's invariant tests check that.

6. **The manager's egress gate proves its policy by probing a destination that policy denies**,
   instead of the API server its policy allows: the cluster resolver's metrics port, 9153, at the
   `nameserver` of the pod's `/etc/resolv.conf`. Every policy allows the resolver on port 53 only.
   Every other pod's gate is unchanged. The proof keeps its meaning, since a pod whose filter is not
   yet programmed reaches everything, the denied port included.
   - The vault and the journal were rejected as probe targets. The vault has no pod in the local
     cell, so it never answers, filtered or not. The journal's Services expose only the port the
     manager is allowed.
   - Residual: on a cluster whose resolver serves no metrics port, the gate reads as filtered at
     once.

7. **The runtime's and executor's pods are the chart's templates, which the manager reads.** The
   chart renders each as JSON into a ConfigMap the manager mounts read-only, with the security
   context, egress gate, credentials, volumes, colocation and labels their policies select.
   - A template exists only once its image is named; until then the manager journals the start,
     and the start fails until the image exists.
   - While the manager is rendered, the runtime and executor render as no Deployment of their own:
     the manager starts every agent process itself (design §3.4).
   - The contract with lane P: the pod runs `mandate-daemon run --probe /tmp/process.sock` and
     reads its identity from `MANDATE_WORKSPACE`, `MANDATE_PROCESS`, `MANDATE_SUBJECT` and
     `MANDATE_GENERATION`. It resolves the rest from the journal and refuses, before it is ready,
     anything it cannot match.

8. **A pod is selectable by its subject, and the chart's labels are kept.** The adapter adds the
   label `mandate.dev/subject-key`, the first 16 hex digits of the SHA-256 of the subject, and
   `mandate.dev/workspace-key`, the same of the workspace. It selects its own pods by that key and
   `app.kubernetes.io/managed-by`.
   - The template's `mandate.dev/workspace` label stays as the chart wrote it. The network policies,
     the colocation affinity and the model gateway's ingress select by it. Slice 1 overwrote it,
     which would have left every started pod outside its egress policy.
   - The manager reads the hosted workspace's ULID (`api.workspace`), whose control stream is
     `ctl:{workspace_id}`, never the release's label.
   An agent id or `account_ref` is not always label-safe, so the subject itself stays the
   `mandate.dev/subject` annotation. The demo selects the agent's pods by process and subject key.

9. **Until a deployment names its connection on the journal ([DEC-1171](DEC-1171.md)), the
   process's resolver knows no account, so the manager starts nothing for a deployment.** That
   fails closed. A kill switch is never delayed by it: kill switches never ask the resolver. The
   next change reads the account from `AgentDeployed` version 2 and drops the resolver.

## Rationale

Each item gives one pod exactly what its job needs, and checks it where a later change could widen
it:
- The Role names one resource and four verbs. Because creating a pod is itself powerful, the
  admission policy shapes every pod the manager makes like the chart's templates: their images,
  their Secrets, their labels and egress, no token, nothing privileged and nothing of the host.
- The egress policy names one destination, for one pod.
- The gate keeps proving the filter before anything runs.
- The chart's invariant tests fail on a widened Role, a second pod with a token or with `kube-api`
  egress, and a gate that probes the API server again. They also fail on a missing or ignoring
  admission policy, a match condition naming another account, a widened image or Secret list, and a
  dropped bound. They check each template as the manager starts it passes the policy's bounds, and
  that a pod mounting another role's Secret, claiming another process's egress, or running
  privileged does not.

The kill switch's path stays as design §3.6 lists it. Its running processes read the switch
themselves, and the manager only starts a covered process that is down.

## Alternatives considered

- **A ClusterRole, or a Role over every resource the chart renders.** Rejected: the manager only
  creates, reads and deletes bare pods in its own namespace.
- **Turning the egress gate off for the manager's pod.** Rejected: until the policy controller
  programs the pod's filter, the pod reaches anything (AGENTS.md rule 3). Probing a denied
  destination keeps that proof.
- **A Compose adapter now.** Left to a later change: the demo runs on k3d only, and the Compose
  file holds no manager.
- **Passing the connection and owner to the runtime as flags.** Rejected with lane P: the manager
  would have to read the mandate document, which the cell has nowhere shared to store. The runtime
  resolves them from the journal and refuses on any mismatch.

## Consequences

- The cell's demo can observe `ProcessStartIssued` for an agent's runtime and executor once
  [DEC-1171](DEC-1171.md)'s reading lands. It selects their pods by `mandate.dev/process` and
  `mandate.dev/subject-key`.
- Left to later changes:
  - a Compose adapter;
  - alerts through the cell's alert path rather than stderr;
  - alerts for stuck `Pending` or `Unknown` pods;
  - deleting exited pods;
  - the restart drill through `cargo xtask cell drill`;
  - an owner's resume lifting a crash-loop pause, after E21-30 copies the pause.
