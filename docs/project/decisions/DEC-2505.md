## Context

The workspace API writes `NotificationAddressChanged` on the control stream when a member sets or
removes one of their own web-push addresses, and a deactivation writes a `removed` for each of the
member's active addresses (workspace API §4.11, §5.7; identity spec §5.2 step 3, DEC-816 item 7).
Journal spec §9 catalogued its row "closed with E8-14" but gave it no schema, so `append` refused it
as `unknown_event_type` and the routes stayed Planned.

DEC-2502 made one web-push send, one idempotency key, and one `NoticeAttempted` per address, and
said the record must name the address (item 5): `NoticeAttempted` version 2 names a recipient and a
channel but no address, so a verdict on one browser could not be told from one on another. Until a
record can hold it, the dispatcher makes no web-push attempt.

## Decision

1. **`NotificationAddressChanged` at schema version 1, on the control stream only.** Exactly the
   members workspace API §5.7 and identity spec §12.1 name: `member` (`ulid`, the user principal,
   as journal §9.12 types it), `channel` (`web_push`), `action` (`added` | `removed`),
   `address_ref` (`ulid`), and `step_up` (journal §9.2's evidence, nullable). On any other stream it
   is `wrong_stream`.
2. **The address is a reference, never a value** (NT-2, API-11). An `added`'s `address_ref` is its
   own `event_id`; a `removed`'s names an earlier one (rule 210). `pii_refs` is exactly
   `[address_ref]` (rule 211). No member holds an endpoint, `p256dh`, `auth`, a push service or
   host, or a hash of any of them; the closed schema refuses each as `schema`. The VAPID `key_id`
   (DEC-2503 item 5) is not journaled either: it names the workspace's key, it is read with the
   vault entry for each send, and the rotation's "no active address names it" joins the journal's
   active set to entries by `address_ref` without listing the vault.
3. **Who writes it** (rules 212 and 213). An `added` carries step-up. Non-null step-up is valid at
   `event_time` as journal rule 102 reads it (method; 0 to 300 seconds). With step-up, the actor is a
   `user` whose `id` is the `member`: one's own addresses only (API-6). Without step-up, the record is
   a `removed` riding a deactivation, by a `user` or `system` actor as rule 98 has the
   deactivation's.
4. **The batch** (rule 214). A request's records (non-null step-up) are at most one `added` and at
   most one `removed`, of one member with equal evidence; a pair is a replacement (an unreachable
   address, or one under a retired key, DEC-2503 item 7). Each `added`, and a lone `removed` with
   step-up, is the subject of an `OwnerAlertSent` of kind `notification_address_changed` in the
   batch; a replacement's `removed` is the subject of none. A `removed` without step-up rides a
   `MemberDeactivated` or `MemberRemoved` of the same member by the same actor in the batch, has no
   alert, and shares no batch with a request's record. No two `removed` name one address, and no
   `removed` names the batch's own `added`. Every `notification_address_changed` alert names a
   record that clause requires an alert for. Reported after rule 130.
5. **The active set's fold.** An address is active from its `added` until the first later `removed`
   naming it with the same `member`. A `removed` of an address not active, or added by another
   member, changes nothing: reading it as a removal would let one record silence another member's
   address. The 10-address limit and "a deactivation removes every active address" stay workspace
   services' checks across records; a fold that meets more than 10 sends to each.
6. **`NoticeAttempted` version 3.** Version 2's members in their order, then `address_ref`
   (`ulid?`), non-null exactly when `channel` is `web_push`, with `pii_refs` exactly
   `[address_ref]` then and empty otherwise (rule 215). The reason enum gains `address_retired`, on
   an `abandoned` web-push attempt only (rules 127 and 216): the send whose address was removed or
   marked `unreachable` by another attempt before its next attempt (notifications spec §5.3).
   DEC-795's last send to a removed address keeps `retry_window_ended` when its entry is gone. Rule
   134 (the verdict) holds unchanged.
7. **Per address.** A terminal attempt is judged per notice, recipient, channel, and `address_ref`
   (`null` off web push); a marking reason marks only the address its `address_ref` names;
   `address_missing` is reported once per `address_ref`; `address_retired` marks and causes nothing.
8. **Versions 1 and 2 are refused on append from v0.51**, as `unknown_schema` at `payload`, and
   every writer appends version 3. Both still replay, with `address_ref` read as `null`. The exception
   considered, keeping version 2 appendable for the channels without an address, is not taken: it
   would say nothing version 3 cannot, and it would also admit a version-2 web-push record that
   names no address, which no reader could attribute. This is DEC-706 item 6's reasoning. No
   deployment holds a web-push `NoticeAttempted` at any version (no dispatcher process runs, and the
   dispatcher makes no web-push attempt); were one read, it is the attempt of no address, ending and
   marking none.
9. **Vectors and order (ES-22).** `docs/specs/reference-cases/journal.yaml` and `reference/journal`
   model neither record, so the vectors are unchanged and stay version 3;
   `crates/mandate-journal/tests/notices.rs` pins §9.15 (DEC-720 item 7). The pending tests, then
   the `mandate-journal` registration, the dispatcher's version-3 writer, and the workspace API's
   writer follow in their own code changes.

## Lifecycles walked

- **Add:** active from its `added`; its alert's notice reaches it and the member's other addresses.
- **Remove:** inactive from its `removed`; a due send is `abandoned` `address_retired`; only the
  removal's own notice is sent once more (DEC-795).
- **Re-add:** a new `address_ref`; marks and the `address_missing` report start afresh.
- **Replace:** `removed` and `added` in one batch with one alert on the `added`; no last send to the
  old address.
- **Deactivation:** a `removed` per active address in the deactivation's batch, same actor, no
  step-up, no alert, no last send; due sends are `address_retired`.
- **Rejected:** `failed` `address_rejected` marks that address `unreachable` (no other); its other
  due sends are `address_retired`, later notices skip it, and it stays active and counted
  until removed or replaced.
- **Key retirement:** no control-stream record; a send whose key is gone is `failed`
  `provider_error`, `permanent`, marking nothing (DEC-2503 items 5 and 7).

## Attacks considered

- **A stolen session adds the attacker's browser.** Step-up is required and must be fresh at
  `event_time` (rule 212); the actor must be the member (rule 213); the batch must raise the alert
  (rule 214), whose notice goes to every address the member holds, not only the newest (DEC-2502
  item 10). Residual, disclosed: an attacker who also passes step-up is detected, not prevented.
- **A stolen session silences the member.** A removal needs step-up and an alert; the removed
  address gets one last send (DEC-795). A `removed` without step-up is admitted only beside a
  deactivation of that same member, which ends their membership and tells the admins.
- **A removal of another member's address.** The actor must be the `member`, and the fold ignores a
  `removed` whose member did not add the address.
- **An insider reading the journal.** Both records hold an opaque ULID and closed values only: no
  endpoint, key, host, push-service name, or hash; the web-push `provider_message_id` is a fresh
  random id per attempt (DEC-2500 item 9). `step_up.assertion_id` is §9.2's `text`, as on every
  step-up record; the API sets it from its own challenge.
- **A writer that writes the older shape.** Versions 1 and 2 are refused on append.

## Rationale

Every item either gives a record accepted decisions already require the shape they name, or refuses
more. The batch rule checks at append what workspace API §5.7 and identity spec §5.2 already promise,
so a writer bug cannot commit an unalerted address change.

## Alternatives considered

- **Journal the `key_id`.** Rejected for now: it is not in workspace API §5.7's or identity spec
  §12.1's members, it would be a second copy that could disagree with the vault entry the send
  reads, and the rotation check needs only the active set. A change that wants rotation audited
  from the journal alone can add it at a new version.
- **Keep version 2 appendable off web push:** item 8.
- **A `removed` without step-up allowed anywhere for `system`:** rejected; it would let a system
  writer silence a member's addresses without a deactivation beside it.
- **No batch rule, relying on the API:** rejected; the alert is the member's only signal of an
  address change (DEC-795), so its absence should be impossible to commit.
