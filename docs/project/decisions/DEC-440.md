## Decision

### Accepted (agent)

1. **A closed message set.** Every message between a workspace deployment and the global control
   plane is one of the types in design §3.8. Outbound types carry only opaque IDs, enumerations,
   counts, costs, versions, digests, and timestamps, with no free-text field (CP-1). The two stated
   exceptions are `RelaySend`'s push `endpoint` and its ciphertext of at most 512 bytes, forwarded
   and not kept; the endpoint is treated as personal data. The organization's display handle is
   generated by the plane, never set by the customer. A v1 heartbeat carries versions and health
   only; counts arrive in the usage report. Anything else is refused and journaled.
2. **The control plane never asks.** There is no message by which it requests data from a site.
   Every outbound message is the site's own initiative (design §3.8).
3. **Instructions are signed, journaled first, and bounded.** No inbound instruction is exempt: a
   data bundle (`DataBundleImported`, journaled before any byte is used) and a catalog entry
   (`CatalogEntryRegistered`) each journal their kind, content hash, and sequence. A receipt is not
   an instruction; it has no effect and is stored, not journaled. An inbound instruction takes effect only if it
   verifies against a key pinned in the installed release (not the TLS channel alone), is journaled
   on the control stream by workspace control services, its single writer (journal spec §2, §5.1),
   before its effect, and its effect is in the closed list: it may
   only restrict new activity or offer something for local approval. It never changes a mandate,
   an envelope field, a policy, an order, a kill switch, or a credential, and never deploys,
   resumes, pauses, or stops an agent. The one mode effect is item 13's `exits_only` restriction
   (CP-4, CP-5, CP-6).
4. **One `cp-agent` per deployment** owns the link, the queues, and signature checks, and is the
   only process with egress to the control plane (design §3). It is not a journal writer: it hands
   verified instructions to workspace control services, which append them under their writer epoch,
   the one-writer shape of DEC-431 item 1. The kill-switch path never depends on it (CP-3). Its
   crate depends on no journal, runtime, executor, mandate registry, or vault crate (CP-4): it
   declares a port that workspace control services implement, as `mandate-executor`'s `ports.rs`
   does for its collaborators.
5. **Offline signing keys, one per kind.** Release (binaries and connector packages, the founder's
   hardware key per ES-17), license, registry, and data keys are held outside the control plane's
   general compute; the control plane only serves what they signed (design §3.4, §3.6, §6).
6. **Anti-rollback.** A site refuses any signed license, manifest, catalog entry, or data bundle
   whose sequence is below the highest it has journaled for that kind, except a release rollback its
   own operator starts under DEC-434 item 8 (CP-9). All four kinds journal their sequence.
7. **Hybrid installs are the site's act.** The control plane offers releases; a hybrid site installs
   only by its operator's action (the default) or in an update window the customer set. A
   withdrawal refuses new installs and alerts; it changes no running process (design §3.4).
8. **The managed global kill switch is issued per cell, never from the global control plane.** It is
   a `PlatformOperatorAction` that stops and risk-exits every agent in scope, so issuing it from one
   global service would let that service liquidate every managed workspace. Operators issue it
   through each cell's tooling with step-up, journaled in each workspace, like the per-thesis halt
   (HLD §8). The switch itself is unchanged; only where it can be issued from narrows (CP-12,
   design §3.7).
9. **Usage reports are a signed hash chain** per deployment, queued on disk until acknowledged,
   de-duplicated by report ID, never estimated across a gap (CP-10).
10. **Two-person license changes.** Issuing or changing a license takes two platform staff, with
    step-up, logged in the control plane's audit log (design §5.2).
11. **Epic E20, Global control plane.** E19 is the agent harness (DEC-431); E20 was unused on
    `main` and in open PRs, and is reserved in the decision log's Reserved identifiers table. Its
    stories are Proposed and not yet in the epic overview.
12. **No personal data in the directory.** Routing is by `user_id` and a client's cached list of
    deployments; the directory holds no email, name, or IdP subject (ID-15 in the identity spec,
    PR #556, applied to routing).

### Proposed for the founder

The most conservative option holds until each is decided: nothing is offered to customers, and the
design is built against the recommendations below.

13. **What a lapsed license does.** Recommendation, in the wording shared with #556 and #565:
    after grace a lapsed license refuses only new deployments and new openings; it never blocks an exit, a protective order, the kill switch, or any risk reduction. Grace is 30 days. The openings are refused only through the existing mechanism, an agent
    restriction `license_lapsed` with mode `exits_only` (mandate spec §5.9; trading spec §7.4),
    journaled as `AgentModeApplied`; never a new risk-gate check and never a liquidation (CP-6). The
    name joins mandate spec §5.9's list in a spec change before E20-4's code.
14. **Hybrid license term.** Recommendation: the contract term (annual), so no control-plane outage
    inside a term can reach a lapse (CP-8).
15. **Billing provider.** Recommendation: decided in gap 11; ingest forwards totals behind an
    interface.
16. **Hosting the control plane.** Recommendation: with DEC-434 item 13 at M8, on the same provider
    as managed cells, in separate accounts with separate keys; its recovery targets are hours, not
    seconds, under DEC-434 item 17 (E20-15).
17. **Usage-report period and an audit right over hybrid usage.** Recommendation: hourly reports;
    an audit right in the hybrid license terms, worded by counsel.

## Rationale

The HLD already fixes the shape: a thin plane, metadata only, outbound-only links, never in the
trade path. What it left open is what the plane may *tell* a site, which is the only way it could
add risk. Items 1 to 8 close that with the readings that add no risk: a closed message set, signed
instructions whose only effects restrict or offer, keys the plane does not hold, and no global
trigger for a liquidating switch. Each tightens; none loosens a spec, an invariant, or a
non-negotiable, and each can be reversed by a later decision.

Items 13 to 17 set commercial terms, choose vendors, or spend money, which DEC-79 reserves for the
founder.

## Alternatives considered

- **License lapse stops the agents.** Rejected: stopping invites a liquidation or leaves positions
  unmanaged, which adds risk (rules 2, 3).
- **License lapse changes nothing on trading.** Possible, and what identity spec §11.2 currently
  says; left to the founder (item 13), since it is a license term.
- **Automatic hybrid upgrades by default.** Rejected: a stolen release key would then reach every
  site at once.
- **The global switch in the control plane, protected by two-person approval.** Rejected: still one
  service whose compromise reaches every managed workspace; the per-cell path costs minutes, not
  safety.
- **Email-based routing in the directory.** Rejected: puts personal data in the global plane.
