## Context

The founder clarified on 2026-10-17 that DEC-997 item 3's $50 a month "is my demo cap and not
customer": it is the platform's own provider spend for the demo and dev deployment. DEC-2203 item 9
(#1540) reads it so: budgets are configuration, a deployment cap is a deployment setting, and each
workspace's monthly budget is its own setting. `mandate-gateway` had it as a constant,
`DEMO_WORKSPACE_MONTHLY_MICROS`, applied per workspace.

A deployment cap counts every workspace's calls, but journal spec §9.19's meter stream is one
workspace's (`meter:{workspace_id}`), written by that workspace's one meter writer. No writer sees
another workspace's stream, so a cap checked from one workspace's records alone would let each
workspace spend the whole cap. This decision says where the deployment's spend folds from.

## Decision

1. **Settings, no constants.** The deployment's monthly cap and each workspace's monthly budget are
   configuration the gateway is given, never a figure in code. The deployment cap is one deployment
   setting; a workspace's budget is that workspace's setting, read from deployment configuration
   until a policy key exists (DEC-2203 item 9). This deployment's setting will be $50 a month once
   DEC-997 is Accepted (item 3, Proposed); until then no live call runs at all. A cap that is not set refuses every call (`AGENTS.md` rule 3): no
   default figure stands in for a missing one.
2. **A deployment meter stream.** The deployment has one more meter stream,
   `dmeter:{deployment_id}` (the deployment's enrolled id, journal spec §9.17), written by the
   deployment's one meter writer, one replica at a time and fenced by epoch like every meter writer.
   It holds `StreamOpened` (`{stream_type: "deployment_meter", deployment_id: id}`) and a copy of
   every workspace's `MeterReserved` and `MeterSettled`, on the meter stream's schemas. A copy is
   its own record with its own `event_id`; every member equals the workspace record's except a
   settlement's `reservation`, which names the deployment stream's copy of its reservation. So rule
   158 binds it as written, and call ids, ULIDs, never repeat across workspaces. Rules 155 to 158
   bind it as they bind a workspace's meter stream, and rule 154 names its id.
3. **Spend for the deployment cap** folds from the deployment meter stream alone, exactly as
   journal spec §9.19's fold, with the deployment as the one scope and the calendar month of risk
   days as the period. Both key owners count, as for every cap (journal spec §9.19's `key_owner`),
   so a customer's own key can only make the platform's cap refuse sooner.
4. **The order of a reservation.** The workspace's writer first checks every workspace cap against
   its own stream, appending nothing. Then the deployment's writer checks the deployment cap and
   appends the copy, its check and append one step. Then the workspace's writer appends its
   reservation, and only then may the first attempt leave. The workspace's writer admits one
   reservation at a time, from its check to its own append, so no two calls are admitted against the
   same headroom on either stream. A refusal at either check, or a deployment writer that cannot be
   reached or is fenced, appends nothing anywhere and is `meter_unavailable` or `budget_exhausted`.
   A workspace append that fails after the copy leaves an **orphan**: a deployment reservation with
   no workspace record and no call record naming it, open, counted at its maximum and never
   settled. The call is `meter_unavailable`, sends nothing, and alerts the operator. This is the one
   refusal that leaves a meter record anywhere, and inference spec §3.6 and journal spec §9.19 say
   so. A caller that tries again makes a new call with a new call id.
5. **The order of a settlement.** The settlement is appended to the workspace stream and then copied
   to the deployment stream. Either append that fails leaves that stream's reservation open at its
   maximum, as a crash does (DEC-998 item 5). So the deployment stream never counts a call below its
   reserved maximum, nor below the workspace stream's count of it, except for a settlement above its
   reservation (journal spec §9.19 records those as reported) that the workspace stream holds and
   the copy failed to bring.
6. **Who reads it.** The deployment meter stream holds other workspaces' call, agent, and model ids,
   so it is the platform operator's: its hot-store rows carry no `workspace_id`, no workspace
   member's read, range, or export includes it, and no workspace's records copy from it. It carries
   ids and costs only, never a prompt, an output, or a position (`AGENTS.md` rule 6). A workspace's
   offboarding or erasure leaves its ids there for the retention period. Like every meter stream it
   is never a risk input. One coupling is real and accepted for the demo deployment: one
   workspace's calls, on any key, can spend the cap another workspace would have used.
7. **What tests it, and when.** The meter streams are not yet registered in `mandate-journal`
   (DEC-998 item 8), and no live call runs before they are. Until then the gateway's deployment meter
   is the same in-memory store its workspace meter is, behind the same `MeterStore` port. The
   claims above are property tests in `mandate-gateway` (slice 2's code change): random sequences of
   calls across several workspaces with failures injected at each append, an independent accumulator
   over the deployment stream asserting that spend never exceeds the cap and never counts a call
   below the workspace stream's count of it, each oracle shown to catch a seeded bug. The journal's
   reference vectors for `dmeter` (rule 154's new branch, the `stream_id` type) land with the
   registration, before any live call.

## Rationale

Items 2 to 5 make the deployment cap hold across workspaces with one writer per stream, the
journal's single-writer rule kept whole. A reservation is appended to the deployment stream before
the workspace stream, so any failure between them leaves spend over-counted, which only refuses
calls sooner (INF-7). Copying the records unchanged keeps every existing schema, rule, and fold.

## Alternatives considered

- **Per-workspace shares of the deployment cap that sum to at most it.** Rejected: every workspace
  would have to be listed in configuration before it could make a call, and a share left unused in
  one workspace could not serve another.
- **Each workspace's writer reading every other workspace's stream.** Rejected: two writers could
  each admit a call against the same headroom, so the cap could be exceeded.
- **A per-workspace $50 cap, as the constant had it.** Rejected by the founder's clarification: the
  figure is the deployment's, not a customer's.
