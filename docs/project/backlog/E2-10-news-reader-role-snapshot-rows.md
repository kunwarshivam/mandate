- **E2-10 Narrow the news reader's Postgres role to the control stream's instrument snapshots (hardening, DEC-2280 item 1).** The news reader reads only `ConfigSnapshotRegistered` rows of kind `instrument_snapshot` from the workspace's control stream, but its role can read the whole stream. Give it a view or row policy that admits only those rows, and test that it reads no other. *The constraint:* `Store::rows` verifies a stream's records from its first, so a row policy that hides `ctl:` rows from the role breaks every control-stream read, and the narrowing needs its own read path. *A shape (proposed 2026-10-29, deferred by the coordinator as too much hot-store risk before the demo):* migration 0003 adds a `security_barrier` view of the `ctl:` rows whose type is `ConfigSnapshotRegistered` and whose payload kind is `instrument_snapshot`, selectable by `mandate_news_reader` alone. Row-level security on `events` and `event_ids` gets a permissive `USING (true)` policy for every other role and a restrictive one that admits no `ctl:` row to `mandate_news_reader`, as session user or current user, as migration 0002 does. A new `Store::instrument_snapshots` reads the view, and `tickers.rs` uses it. The snapshot rows then lose chain verification on that path, which adds no risk (a forged row could only make the reader ask about another ticker) and is stated in its DEC. Tests run as the role under both session user and `SET ROLE`, with hand mutants on the policies and a cell drill check; journal spec §6.1's wording is its own spec PR.
