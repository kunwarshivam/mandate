# Playbook: ship a PR

Agents land their own work (DEC-79). Green CI is necessary, not sufficient: an independent review
decides.

1. Open every PR against `main`. Never base a PR on another PR's branch: a merge into that branch
   never reaches `main`. When work is sequenced (tests, implementation, status), open the next PR
   only after the previous one has merged, from the updated `main`.
2. Wait until both required checks (`fast`, `full`) are green on the PR's final head.
   Before asking for review, the author runs every check the reviewer will run, and reports each
   result in the PR body. These are the findings that cost review rounds when a builder skipped
   them:
   - **Do-nothing check (tests PRs):** stub every entry point with a plausible do-nothing
     implementation (unchanged state, empty or default outputs, `Ok(())`) and run the pending tests
     with `--run-ignored only`. The count that pass must be 0; a test that passes on a do-nothing
     stub checks nothing (#152 had 34, #156 had 7).
   - **Every planted bug:** try each row of the brief's planted-bug table against a throwaway
     implementation, never committed, and name the test that catches it. No row may be untried.
   - **Oracles and assertions:** no oracle reuses the crate's own functions or self-reported flags;
     no escape hatch accepts two outcomes (`A | B`); no loop or `all()` runs over a collection the
     test never checks is non-empty; every expected value is recomputed, not copied.
   - **Test inputs:** decimal literals in canonical text (`100`, not `100.00`); generators inside the
     brief's domain; clocks monotone; every pending test a plain `fn` with its own
     `#[ignore = "pending <story>"]` literal, never generated by a macro.
   - **Implementation PRs:** after every fix, re-run the adversarial scenarios the reviewer named,
     including restart and replay: the state after a restart from the journal must equal the live
     state. Run `cargo mutants --in-diff` on the changed src by hand when the CI gate skips the
     crate, and paste the line.
   - **The body:** current test counts and results, and exactly one session URL, last.
   These checks add to the independent review in step 3; they never replace it.
3. Get an independent review from an agent on a different model from the author's, in a fresh
   cloud agent. Cloud agents cannot launch other agents, so a delegated agent stops here with the
   PR open and CI green and reports it; the coordinating session launches the reviewer, which
   also merges on PASS and opens the next sequenced PR. Give the reviewer the PR number, the story
   or DEC, and this checklist; it must not have written the change:
   - check out the PR head and run `cargo xtask check`;
   - read the diff against the story's acceptance criteria, the specs it cites, and `AGENTS.md`;
   - for safety-critical crates, confirm zero missed mutants in the `full` log and run the
     `interrogate` skill on the diff;
   - return PASS or FAIL with file and line evidence for each finding.
4. On FAIL, fix the findings in the same PR and repeat from step 2.
5. On PASS, the coordinating session approves the head the review passed (DEC-175). It writes
   `Coordinator-approved-head: <full sha>` into the PR description and adds the
   `coordinator-approved` label. The `merge` workflow squash-merges when that sha is still the head,
   GitHub reports the PR mergeable, and the latest `ci` run on the head succeeded (and `web`, for a
   change under `web/`), with the PR title and description as the commit message; otherwise it
   does nothing. A push moves the head off the approved sha, so new commits need a new PASS and a
   new line. A session that can merge directly squash-merges through the
   GitHub API with the story ID in the title and an explicit `commit_message` (the PR
   description): GitHub's default squash message copies every commit message, including
   `Co-authored-by` trailers, which must not reach `main`. Never force-push `main`, never label or
   enable auto-merge on a PR that has not passed step 3.
6. Report the merge, the review verdict, and anything the founder should look at after the fact.
